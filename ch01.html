프로그램 만들기

컴퓨터는 0과 1밖에 모르는 기계입니다. 사람이 쓴 C 코드가 어떤 과정을 거쳐 CPU가 실행하는 기계어가 되는지를 처음부터 끝까지 따라가 봅니다. 이 흐름을 한 번 제대로 잡아 두면, 이후 모든 장에서 만나는 오류 메시지와 이상한 동작의 '이유'가 보이기 시작합니다.

이 장에서 배울 것

  • 프로그램이란 무엇이며 CPU와 메모리가 프로그램을 어떻게 실행하는지 이해합니다.
  • 기계어, 어셈블리어, 고급 언어의 차이와 C 언어가 차지하는 위치를 설명할 수 있습니다.
  • C 언어의 역사와 특징, 그리고 은행·증권·카드사의 계정계 시스템에서 C가 여전히 쓰이는 이유를 압니다.
  • 전처리 → 컴파일 → 어셈블 → 링크로 이어지는 빌드 과정을 그림으로 설명할 수 있습니다.
  • gcc와 Visual Studio로 프로그램을 직접 빌드하고 실행합니다.
  • 컴파일 오류와 경고, 링크 오류, 실행 시간 오류를 구분하고 대처하는 방법을 익힙니다.

01-1프로그램과 C 언어

이 과정의 첫 장에서는 코드를 많이 쓰지 않습니다. 대신 앞으로 수백 쪽에 걸쳐 작성할 모든 코드가 어디에서, 어떻게, 왜 그렇게 실행되는지의 큰 그림을 먼저 그립니다. 처음 C를 배우는 분들이 포인터에서 무너지는 가장 큰 이유는 포인터 자체가 어려워서가 아니라, "변수가 메모리에 있다"는 그림이 머릿속에 없기 때문입니다. 그래서 이 절에서는 프로그램, CPU, 메모리, 기계어라는 네 가지 단어를 확실하게 정리합니다.

프로그램이란 무엇인가

프로그램(program)은 컴퓨터가 수행할 명령어들의 순서 있는 묶음입니다. 일상의 예로 바꾸면 요리 레시피와 같습니다. 레시피에는 "물 500ml를 끓인다 → 면을 넣는다 → 4분 기다린다 → 수프를 넣는다"처럼 순서대로 할 일이 적혀 있습니다. 요리사가 레시피를 한 줄씩 읽고 그대로 따라 하듯, 컴퓨터의 CPU도 프로그램에 적힌 명령어를 하나씩 꺼내 그대로 수행합니다.

그런데 요리사와 CPU에는 결정적인 차이가 있습니다. 요리사는 "적당히 끓인다"라는 애매한 문장도 경험으로 해석하지만, CPU는 해석이라는 것을 전혀 하지 않습니다. CPU는 미리 정해진 몇 백 가지의 아주 단순한 명령(두 수를 더하라, 메모리의 몇 번지 값을 읽어라, 값이 0이면 다른 곳으로 건너뛰어라 등)만 알고 있고, 그 명령도 사람이 읽는 글자가 아니라 0과 1의 비트 패턴으로만 받아들입니다. 이 비트 패턴으로 된 명령을 기계어(machine code)라고 합니다.

한 줄 요약

프로그램은 CPU가 수행할 명령어의 묶음이고, CPU가 직접 이해하는 유일한 언어는 0과 1로 된 기계어입니다. 우리가 배우는 C 언어는 사람이 쓰기 쉬운 글을 기계어로 바꿔 주기 위한 '중간 다리'입니다.

CPU와 메모리: 프로그램이 실행되는 무대

프로그램이 실행되려면 두 주인공이 필요합니다. 계산을 하는 CPU(Central Processing Unit, 중앙 처리 장치)와 계산할 대상과 명령어를 담아 두는 메모리(주기억장치, RAM)입니다. 하드디스크나 SSD 같은 보조기억장치는 전원이 꺼져도 내용이 남지만 느리고, 메모리는 전원이 꺼지면 내용이 사라지지만 훨씬 빠릅니다.

여러분이 바탕화면의 hello.exe를 더블클릭하면 다음 일이 일어납니다.

  1. 운영체제(Windows, Linux)가 SSD에 저장된 실행 파일을 읽어 메모리에 적재(load)합니다. 이때 기계어 명령들이 들어가는 영역(코드 영역)과 변수가 들어갈 영역(데이터, 스택, 힙)이 마련됩니다.
  2. 운영체제가 CPU에게 "이 프로그램의 첫 명령은 메모리 몇 번지에 있다"라고 알려 줍니다. CPU 안의 프로그램 카운터(PC, x86에서는 RIP 레지스터)에 그 주소가 들어갑니다.
  3. CPU는 PC가 가리키는 주소에서 명령어를 가져오고(Fetch), 무슨 명령인지 해석하고(Decode), 실행합니다(Execute). 그리고 PC를 다음 명령의 주소로 옮깁니다.
  4. 이 인출-해독-실행 사이클을 1초에 수십억 번 반복하는 것이 '프로그램이 돈다'의 실체입니다.

메모리는 1바이트(8비트)마다 번호가 붙은 거대한 사물함이라고 생각하면 됩니다. 이 번호를 주소(address)라고 합니다. 64비트 컴퓨터에서 주소는 보통 0x7ffd5c1a2b3c처럼 16진수로 표시합니다. 9장에서 배울 포인터는 결국 이 '사물함 번호'를 저장하는 변수일 뿐입니다. 지금 이 그림을 기억해 두면 포인터가 훨씬 쉬워집니다.

왜 그럴까? — 왜 CPU는 메모리에서 직접 계산하지 않을까?

CPU의 연산장치(ALU)는 레지스터라는 CPU 내부의 아주 작은 저장소에 있는 값만 가지고 계산합니다. 레지스터는 x86-64 기준으로 범용 레지스터가 16개 정도뿐이고 각각 8바이트입니다. 메모리는 CPU 칩 바깥에 있어서 값 하나를 읽는 데 수십~수백 클록이 걸리지만, 레지스터는 1클록 안에 접근됩니다. 그래서 CPU는 "메모리에서 레지스터로 읽기(load) → 레지스터끼리 계산 → 결과를 메모리에 쓰기(store)"의 3단계를 반복합니다.

C 코드 a = a + 1; 한 줄도 기계어로는 보통 이 세 단계로 쪼개집니다. 4장에서 배울 i = i++ 같은 코드가 왜 위험한지, 22장 이후 멀티스레드에서 count++가 왜 안전하지 않은지가 모두 이 사실에서 출발합니다. 하나의 C 문장이 CPU 입장에서는 여러 단계라는 것, 이것이 이 장에서 가져가야 할 가장 중요한 감각입니다.

기계어, 어셈블리어, 고급 언어

초창기 컴퓨터 프로그래머는 기계어를 직접 썼습니다. 예를 들어 x86-64 CPU에서 "eax 레지스터에 5를 넣어라"는 기계어로 B8 05 00 00 00(16진수)입니다. 사람이 이것을 수천 줄 쓰는 것은 거의 불가능에 가깝습니다. 그래서 기계어 명령 하나하나에 사람이 읽을 수 있는 이름(mov, add, jmp)을 붙인 어셈블리어(assembly language)가 나왔습니다. 어셈블리어는 기계어와 거의 1:1로 대응하므로 저급 언어(low-level language)라고 부릅니다.

어셈블리어도 여전히 CPU 종류마다 명령어가 다르고(인텔 x86과 ARM은 완전히 다릅니다), 큰 프로그램을 쓰기에는 너무 세세합니다. 그래서 사람의 말에 더 가까운 고급 언어(high-level language)가 등장했습니다. C, Java, Python, COBOL 등이 여기에 속합니다. 고급 언어로 쓴 코드는 컴파일러(compiler)나 인터프리터(interpreter)가 기계어로 바꿔 주어야 실행할 수 있습니다.

여기서 잠깐 — Java는 어디에 속할까?

Java는 소스를 먼저 바이트코드라는 중간 코드로 컴파일한 뒤, JVM이라는 가상 기계가 이를 해석하거나 실행 중에 기계어로 다시 컴파일(JIT)합니다. 컴파일과 인터프리트를 섞은 하이브리드 방식입니다. 국내 은행의 차세대 시스템 상당수가 Java 기반으로 바뀌었지만, 성능이 극도로 중요한 코어 거래 처리나 대외 통신 모듈, 오래된 배치에는 여전히 C가 많이 남아 있습니다. 면접에서 "컴파일 언어와 인터프리터 언어의 차이"를 물으면 이 하이브리드 사례까지 언급하면 좋은 인상을 줍니다.

정답은 (다)입니다. CPU는 메모리에 올라온 기계어만 실행합니다.

  • (가) C 소스는 글자(텍스트)일 뿐입니다. 컴파일러가 전처리·컴파일·어셈블·링크를 거쳐 실행 파일로 만들어야 합니다.
  • (나) 어셈블리 파일도 텍스트입니다. 어셈블러가 기계어 목적 파일로 바꾸고, 링커가 실행 파일로 묶어야 합니다.

C 언어의 역사

C 언어는 1972년 무렵 미국 AT&T 벨 연구소의 데니스 리치(Dennis Ritchie)가 만들었습니다. 당시 리치와 켄 톰슨(Ken Thompson)은 UNIX 운영체제를 개발하고 있었는데, 처음에는 어셈블리어로 작성했기 때문에 다른 기종의 컴퓨터로 옮기려면 전부 다시 써야 했습니다. 톰슨이 만든 B 언어를 개량해 자료형 개념을 넣은 것이 C이고, 1973년 UNIX의 대부분이 C로 다시 작성되었습니다. "운영체제를 고급 언어로 쓸 수 있다"는 것을 처음 증명한 사건이며, 이식성(portability)이라는 C의 가장 큰 장점이 여기서 나왔습니다.

왜 그럴까? — C는 왜 배열 범위를 검사해 주지 않을까?

Java에서 길이 10인 배열의 11번째 칸에 접근하면 ArrayIndexOutOfBoundsException이 납니다. 이것이 가능한 이유는 Java가 배열마다 길이 정보를 함께 저장하고, 접근할 때마다 "인덱스 < 길이"인지 비교하는 기계어를 몰래 넣기 때문입니다. 비교 한 번은 싸지만, 반복문 안에서 수억 번 접근하면 무시할 수 없는 비용이 됩니다.

C를 설계한 1970년대 컴퓨터는 지금보다 수만 배 느렸고, C의 목표는 어셈블리어를 대신해 운영체제를 쓰는 것이었습니다. 그래서 C는 "프로그래머가 알아서 잘 할 것이다. 필요 없는 일은 하지 않는다"를 원칙으로 삼았습니다. 그 결과 C의 배열 접근은 주소 계산 한 번으로 끝나지만, 범위를 벗어나면 다른 변수나 반환 주소를 덮어쓰는 일이 생기며, 표준은 이를 미정의 동작(Undefined Behavior, UB)이라고 부르고 어떤 결과도 보장하지 않습니다.

미정의 동작(UB)이라는 말을 지금 익혀 두기

C 표준은 프로그램의 동작을 세 종류로 나눕니다. (1) 정의된 동작: 표준이 결과를 정해 둠. (2) 구현 정의 동작(implementation-defined): 컴파일러마다 다를 수 있지만 문서화해야 함(예: int의 크기). (3) 미정의 동작(UB): 표준이 아무것도 보장하지 않음. 프로그램이 정상처럼 돌 수도, 죽을 수도, 엉뚱한 값을 낼 수도 있고, 컴파일러는 "UB는 일어나지 않는다"고 가정하고 최적화합니다. 금융 시스템에서 UB는 "어제까지 잘 돌던 배치가 컴파일러 버전을 올렸더니 잔액이 틀린다" 같은 최악의 장애로 나타납니다. 이 과정 전체에서 UB가 나올 때마다 표시하겠습니다.

왜 금융권 계정계에 C가 아직 쓰이는가

은행 IT는 크게 계정계(예금·대출·외환 등 고객 돈의 원장을 직접 다루는 핵심 시스템), 정보계(데이터 분석, 마케팅, 리스크 관리), 대외계(금융결제원 같은 대외기관이나 다른 금융회사와 전문을 주고받는 시스템), 채널계(인터넷뱅킹, 모바일앱, ATM, 창구 단말)로 나눕니다. 이 중 계정계와 대외계, 그리고 밤마다 도는 일마감 배치에는 오랫동안 C(그리고 메인프레임 시절의 COBOL)가 쓰였습니다.

C가 이 영역에서 살아남은 이유는 다음과 같습니다.

  1. 성능과 예측 가능성: 월급날 오전, 카드 결제 대금 출금일 같은 피크 시간에는 초당 수천 건의 거래가 몰립니다. C에는 가비지 컬렉터가 없으므로 "GC 때문에 0.5초 멈춤" 같은 일이 생기지 않습니다. 응답 시간이 일정하다는 것은 금융 거래에서 매우 중요한 품질입니다.
  2. 검증된 레거시 자산: 수십 년 동안 수많은 감사와 장애를 거치며 다듬어진 이자 계산, 수수료 계산 로직은 그 자체로 은행의 자산입니다. 단 1원의 차이도 허용되지 않기 때문에 "잘 돌아가는 코드를 새 언어로 다시 쓰는 위험"이 매우 큽니다.
  3. 고정길이 전문 처리에 최적: 대외기관과 주고받는 전문(電文)은 "1~4바이트 전문 길이, 5~8바이트 거래코드, 9~24바이트 계좌번호…"처럼 바이트 위치가 정해진 형식이 많습니다. C의 구조체와 memcpy는 이런 바이트 단위 처리에 딱 맞습니다(17장, PART 2에서 자세히 다룹니다).
  4. TP 모니터와 UNIX 환경: 계정계는 Tmax, Tuxedo 같은 TP 모니터(트랜잭션 처리 미들웨어) 위에서 돌아가는 경우가 많고, 이들의 서비스 프로그램 작성 언어로 C가 오래 쓰였습니다. 서버도 AIX, HP-UX, Linux 같은 UNIX 계열이 주류였습니다.
  5. Pro*C와 같은 DB 연동: C 코드 안에 SQL을 직접 넣는 Embedded SQL(Oracle의 Pro*C 등)로 원장 테이블을 처리하는 프로그램이 많습니다.

은행 시스템에서는 — 차세대 이후에도 C를 알아야 하는 이유

최근 10여 년 사이 많은 은행이 '차세대 시스템' 프로젝트로 계정계를 Java 기반으로 전환했습니다. 그렇다면 C는 필요 없을까요? 현장의 답은 "아닙니다"입니다. 첫째, 전환되지 않은 대외계·배치·보안 모듈이 많이 남아 있고, 이를 유지보수하는 인력이 부족합니다. 둘째, Java로 바뀐 시스템에서도 장애 분석을 할 때 결국 메모리, 스택, 바이트 순서(엔디안), 문자 인코딩(EUC-KR과 UTF-8) 같은 개념이 필요한데, 이 개념을 가장 정직하게 보여 주는 언어가 C입니다. 셋째, 전산직 필기·면접에서 C 포인터와 메모리 구조는 가장 많이 나오는 주제 중 하나입니다. 이 과정이 C를 금융 실무와 엮어 가르치는 이유가 여기에 있습니다.

정답과 해설 보기

모범 답안은 다음과 같은 요소를 포함합니다.

  1. 검증 비용과 위험: 기존 C 모듈은 수년간 운영되며 예외 케이스까지 반영된 상태입니다. 새로 작성하면 모든 전문 유형과 오류 코드에 대해 다시 테스트하고 대외기관과 연동 테스트를 거쳐야 합니다.
  2. 바이트 단위 처리 호환성: 전문은 고정길이 바이트 배열이고 한글은 EUC-KR 같은 인코딩으로 들어오는 경우가 많습니다. Java의 String은 내부적으로 UTF-16이라 바이트 길이 계산이 달라지는 함정이 있습니다.
  3. 성능·지연 특성: GC로 인한 지연이 허용 기준을 넘지 않는지 확인해야 합니다.
  4. 운영 인력과 도구: 운영 중인 모니터링·로그 체계, 장애 대응 절차가 C 기반으로 맞춰져 있을 수 있습니다.

즉, 언어 선택은 '언어의 우열'이 아니라 '위험과 비용의 관리' 문제입니다. 면접에서도 이런 균형 잡힌 답이 좋은 평가를 받습니다.

처음 만나는 C 프로그램

이론은 여기까지 하고 실제 C 프로그램을 하나 봅니다. 다음 장에서 한 줄씩 자세히 분해할 것이므로, 지금은 "이렇게 생겼구나" 정도로 봐도 충분합니다.

이 일곱 줄짜리 파일이 실행되기까지 실제로는 수십 개의 단계가 숨어 있습니다. #include는 누가 처리하는지, printf의 실제 코드는 어디에 있는지, return 0은 누가 받는지를 다음 절에서 하나씩 파헤칩니다.

자주 하는 실수 — void main()

오래된 책이나 인터넷 예제에는 void main()이 자주 보입니다. 하지만 C 표준이 보장하는 main의 형태는 int main(void)와 int main(int argc, char *argv[]) 두 가지(및 그와 동등한 형태)입니다. void main은 일부 컴파일러가 허용할 뿐 표준이 아니며, 운영체제에 종료 상태를 제대로 돌려주지 못합니다. 금융권 배치 작업은 셸 스크립트나 배치 스케줄러가 프로그램의 종료 코드를 보고 다음 작업을 실행할지 결정하므로, 종료 코드를 반환하지 않는 프로그램은 실제 장애의 원인이 됩니다.

프로그램 개발 과정 한눈에 보기

실무에서 프로그램 하나를 만드는 과정은 '코드를 친다'보다 훨씬 깁니다. 다음 다섯 단계를 반복합니다.

  1. 요구사항 분석: 무엇을 만들지 정합니다. 예) "정기예금 만기 시 세후 이자를 계산해 입금하는 배치".
  2. 설계: 입력(계좌 원장), 처리(이자 = 원금 × 이율 × 기간, 원 미만 절사), 출력(입금 거래, 결과 리포트)을 정하고 알고리즘을 순서도나 의사코드로 씁니다.
  3. 코딩: 편집기로 C 소스 파일(.c)을 작성합니다.
  4. 빌드(컴파일·링크): 컴파일러로 실행 파일을 만듭니다. 오류가 있으면 3으로 돌아갑니다.
  5. 테스트와 디버깅: 실행해서 결과가 기대와 같은지 확인합니다. 틀리면 원인을 찾아 3 또는 2로 돌아갑니다. 금융권은 단위 테스트 → 통합 테스트 → 인수 테스트 → 이행 리허설처럼 테스트 단계가 특히 깁니다.

01-2컴파일과 컴파일러 사용법

"컴파일한다"는 말은 흔히 소스 코드를 실행 파일로 만드는 전체 과정을 뜻하지만, 정확히는 네 단계로 나뉩니다. 각 단계가 무엇을 입력받아 무엇을 내놓는지 알면 오류 메시지만 보고도 "어느 단계에서 문제가 생겼는지"를 바로 알 수 있습니다. 이것은 실무에서 장애를 빨리 해결하는 사람과 그렇지 못한 사람을 가르는 능력입니다.

빌드의 4단계: 전처리 → 컴파일 → 어셈블 → 링크

① 전처리(Preprocessing)

전처리기는 #으로 시작하는 줄(전처리 지시자)을 처리하는 텍스트 치환기입니다. C 문법은 전혀 모릅니다. 하는 일은 다음과 같습니다.

  • #include <stdio.h>: stdio.h 파일의 내용을 그 자리에 그대로 복사해 붙입니다. 그래서 일곱 줄짜리 hello.c를 전처리하면 수백~수천 줄이 됩니다.
  • #define RATE 3: 이후 소스에 나오는 RATE라는 단어를 3으로 바꿉니다.
  • 주석을 공백 하나로 바꿉니다. 그래서 컴파일러는 주석을 아예 보지 못합니다.
  • #if, #ifdef로 조건에 따라 코드를 넣거나 뺍니다.
gcc -E hello.c -o hello.i      # 전처리만 하고 결과를 hello.i에 저장
wc -l hello.i                   # 줄 수 확인 (환경에 따라 수백~천 줄 이상)

② 컴파일(Compilation)

좁은 의미의 컴파일러가 전처리된 C 코드를 읽어 어셈블리어로 번역합니다. 이 단계에서 일어나는 일은 다음과 같습니다.

  1. 어휘 분석: 글자들을 int, main, (, void, ) 같은 토큰으로 자릅니다.
  2. 구문 분석: 토큰 배열이 C 문법에 맞는지 검사해 트리 구조를 만듭니다. 세미콜론 누락 같은 오류가 여기서 걸립니다.
  3. 의미 분석: 선언되지 않은 변수 사용, 자료형 불일치 등을 검사합니다.
  4. 최적화: -O2 같은 옵션을 주면 불필요한 계산을 줄이고 더 빠른 명령으로 바꿉니다.
  5. 코드 생성: 대상 CPU의 어셈블리 코드를 만듭니다.
gcc -S hello.c -o hello.s      # 어셈블리 파일까지만 만들기

③ 어셈블(Assembly)

어셈블러가 어셈블리 코드를 기계어로 바꿔 목적 파일(object file)을 만듭니다. 리눅스는 .o, 윈도우(MSVC)는 .obj 확장자를 씁니다. 목적 파일은 기계어이지만 아직 실행할 수 없습니다. printf를 호출하는 자리에 실제 주소 대신 "여기에 printf의 주소를 채워 주세요"라는 빈칸(재배치 정보)만 남아 있기 때문입니다.

gcc -c hello.c -o hello.o      # 목적 파일까지만 만들기 (가장 자주 쓰는 옵션)
nm hello.o                      # 심볼 확인: main은 T(정의됨), puts 또는 printf는 U(미정의)

여기서 잠깐 — printf를 썼는데 왜 puts가 보일까?

gcc는 printf("Hello, C!\n")처럼 서식 지정자가 없고 \n으로 끝나는 문자열 출력을 더 단순한 puts("Hello, C!") 호출로 바꾸는 최적화를 기본으로 합니다. 결과가 똑같으니 허용되는 변환입니다. 컴파일러는 "관찰 가능한 동작"만 같다면 코드를 마음대로 바꿀 수 있다는 원칙(as-if 규칙)의 첫 사례입니다.

④ 링크(Linking)

링커는 여러 목적 파일과 라이브러리를 하나로 합쳐 실행 파일을 만듭니다. 이때 목적 파일에 남아 있던 빈칸들을 실제 주소로 채웁니다. printf의 진짜 기계어는 C 표준 라이브러리(리눅스에서는 glibc의 libc.so)에 있으며, 링커가 이를 연결합니다. 또 main보다 먼저 실행되어 환경을 준비하고 main을 호출한 뒤 그 반환값으로 exit을 부르는 시작 코드(crt1.o 등)도 이때 붙습니다.

왜 그럴까? — 왜 굳이 컴파일과 링크를 나눌까?

은행 계정계 소스는 파일이 수천 개, 줄 수로 수백만 줄에 이릅니다. 만약 한 파일의 한 줄을 고칠 때마다 수백만 줄 전체를 다시 번역해야 한다면 빌드에 몇 시간이 걸릴 것입니다. 컴파일을 파일 단위로 나눠 .o를 만들어 두면, 수정한 파일만 다시 컴파일하고 나머지는 기존 .o를 그대로 링크하면 됩니다. 이것을 분할 컴파일이라 하며 19장에서 자세히 다룹니다. 또 printf 같은 공통 기능은 라이브러리로 한 번만 만들어 두고 모두가 링크해서 쓰므로 중복이 사라집니다. "컴파일 단위 = 소스 파일 하나(전처리 후)"라는 사실은 나중에 static, extern을 이해하는 열쇠이기도 합니다.

여기서 잠깐 — 정적 링크와 동적 링크

라이브러리 코드를 실행 파일 안에 아예 복사해 넣는 것을 정적 링크(.a, .lib), 실행할 때 운영체제가 공유 라이브러리를 메모리에 올려 연결해 주는 것을 동적 링크(.so, .dll)라고 합니다. 동적 링크는 실행 파일이 작고 라이브러리를 여러 프로그램이 공유하지만, 운영 서버에 라이브러리 버전이 다르면 "개발 서버에서는 되는데 운영에서는 안 되는" 문제가 생깁니다. 금융권 이행(배포) 체크리스트에 "공유 라이브러리 버전 확인"이 들어가는 이유입니다. 리눅스에서는 ldd ./hello로 실행 파일이 어떤 공유 라이브러리를 쓰는지 볼 수 있습니다.

(2) printf("hi") 뒤에 세미콜론을 빠뜨렸다.
(3) calc_interest() 함수를 선언하고 호출했지만 어떤 파일에도 함수 본체를 만들지 않았다.

정답과 해설 보기

(2) 컴파일 단계(구문 분석). error: expected ';' before ... 같은 오류가 납니다.

(3) 링크 단계. 각 파일의 컴파일은 선언만 있어도 성공합니다. 컴파일러는 "어딘가에 있겠지" 하고 빈칸을 남기기 때문입니다. 그러나 링커가 모든 목적 파일과 라이브러리를 뒤져도 본체를 찾지 못하면 undefined reference to calc_interest 형태의 오류를 냅니다. 링크 오류 메시지에는 소스 줄 번호가 없거나 호출한 위치만 대략 표시된다는 점이 특징입니다.

(4) 실행 시간(런타임). 빌드는 성공했지만 실행 중에 문제가 생긴 것입니다. 정수를 0으로 나누는 것은 C에서 UB이며, x86 리눅스에서는 보통 Floating point exception이라는 메시지와 함께 프로세스가 종료됩니다(이름과 달리 정수 나눗셈에서도 이 신호가 납니다).

컴파일 오류 메시지 읽는 법

$ gcc -Wall err01.c -o err01
err01.c: In function 'main':
err01.c:5:24: error: expected ';' before 'return'
    5 |     printf("Balance\n")      /* 세미콜론 누락 */
      |                        ^
      |                        ;
    6 |     return 0;
      |     ~~~~~~

메시지는 파일명:줄:칸: 종류: 내용 형식입니다. err01.c:5:24는 5번째 줄 24번째 칸이라는 뜻입니다. gcc는 친절하게 "여기에 ;를 넣으라"고 제안까지 해 줍니다(메시지 모양은 gcc 버전마다 조금씩 다릅니다).

왜 그럴까? — 왜 오류 줄 번호가 실제 실수한 줄보다 뒤에 나올 때가 있을까?

C에서 줄바꿈은 문법적으로 의미가 없습니다. 컴파일러 입장에서 위 코드는 printf("Balance\n") return 0;이라는 한 덩어리입니다. 컴파일러는 ) 다음에 return이라는 토큰을 만났을 때 비로소 "여기에 ;가 있어야 하는데"라고 깨닫습니다. 그래서 오류는 문제를 발견한 지점을 기준으로 보고됩니다. 이 예에서는 gcc가 똑똑하게 앞 줄을 가리켰지만, 구조체 선언 끝의 ;를 빠뜨리면 다음 줄이나 심지어 다른 헤더 파일에서 엉뚱한 오류가 나기도 합니다.

이렇게 해결합니다 — 오류 메시지 대처 순서

  1. 첫 번째 오류부터 고칩니다. 오류 하나가 연쇄적으로 수십 개의 가짜 오류를 만들 수 있습니다. 첫 오류를 고치고 다시 컴파일하면 나머지가 한꺼번에 사라지는 경우가 많습니다.
  2. 보고된 줄에서 문제가 안 보이면 바로 윗줄을 봅니다(세미콜론, 괄호 짝).
  3. 메시지의 핵심 영어 단어를 익힙니다: expected(기대했는데 없음), undeclared(선언 안 됨), implicit declaration(함수 선언 없이 호출), incompatible types(자료형 불일치), undefined reference(링크 단계에서 정의 못 찾음).
  4. 오류 메시지를 검색할 때는 내 파일명과 변수명은 빼고 검색합니다.

경고를 무시하면 안 되는 이유와 -Wall

경고(warning)는 "문법상 번역은 할 수 있지만, 이건 아마 당신이 의도한 게 아닐 것"이라는 컴파일러의 조언입니다. 초보자는 경고가 있어도 실행 파일이 만들어지니 무시하기 쉬운데, 실무에서는 경고 0건을 빌드 통과 기준으로 삼는 조직이 많습니다.

$ gcc warn01.c -o warn01          # 옵션 없이: 경고가 적게 나오거나 아예 안 나옴
$ gcc -Wall -Wextra warn01.c -o warn01
warn01.c: In function 'main':
warn01.c:8:27: warning: format '%d' expects argument of type 'int', but argument 2 has type 'double' [-Wformat=]
warn01.c:6:13: warning: 'balance' is used uninitialized [-Wuninitialized]

경고의 정확한 문구와 순서는 gcc 버전에 따라 조금씩 다르지만 두 가지 모두 심각한 버그입니다. 첫째, 초기화하지 않은 지역 변수의 값은 정해져 있지 않습니다(3장에서 '쓰레기값'으로 자세히 다룹니다). 둘째, %d에 double을 넘기면 UB이며, x86-64 리눅스에서는 double 인수가 정수 레지스터가 아닌 부동소수점 레지스터(xmm0)로 전달되므로 printf는 엉뚱한 정수 레지스터의 값을 읽어 무의미한 숫자를 출력합니다.

이렇게 해결합니다 — 권장 컴파일 옵션

gcc -std=c11 -Wall -Wextra -pedantic -g -o hello hello.c
  • -std=c11: C11 표준에 맞춰 컴파일합니다(-std=c99도 가능).
  • -Wall: 흔히 문제가 되는 주요 경고를 켭니다. 이름과 달리 "모든(all)" 경고는 아닙니다.
  • -Wextra: -Wall에 포함되지 않은 추가 경고를 켭니다.
  • -pedantic: 표준에 없는 컴파일러 확장 문법을 쓰면 경고합니다.
  • -g: 디버거(gdb)가 쓸 수 있도록 디버깅 정보를 넣습니다.
  • -Werror: 경고를 오류로 취급해 빌드를 실패시킵니다. 팀 프로젝트의 품질 기준으로 자주 씁니다.
  • -O2: 최적화. 운영 빌드에 사용합니다. 초기화 안 된 변수 같은 일부 경고는 최적화를 켜야 더 잘 잡히기도 합니다.

은행 시스템에서는 — 경고 하나가 1원 차이를 만든다

어느 카드사 배치에서 수수료를 int로 계산하던 함수를 개발자가 double로 바꾸면서 printf의 %d를 그대로 두었고, 컴파일러는 경고를 냈지만 아무도 보지 않았다고 가정해 봅니다. 화면 출력만 이상했다면 다행이지만, 같은 실수가 sprintf로 전문 필드를 만드는 코드에 있었다면 대외기관으로 엉뚱한 금액이 송신됩니다. 그래서 금융권의 소스 품질 관리 도구(정적 분석기)와 빌드 체크리스트는 컴파일 경고를 결함으로 집계합니다. "경고는 미래의 장애"라고 기억하십시오.

gcc로 빌드하고 실행하기

gcc(GNU Compiler Collection)는 리눅스·유닉스 계열에서 가장 널리 쓰이는 C 컴파일러입니다. 금융권 서버의 상당수가 리눅스이거나 AIX 같은 유닉스이므로 터미널에서 gcc(또는 그 서버의 cc, xlc)를 다루는 능력은 필수입니다. 윈도우에서는 MSYS2를 설치해 MinGW-w64 gcc를 쓰거나, WSL(Windows Subsystem for Linux)로 리눅스 환경을 만들어 쓰는 방법을 권장합니다.

설치 확인

왜 그럴까? — 왜 리눅스에서는 ./hello처럼 ./를 붙여야 할까?

셸은 명령 이름을 받으면 환경 변수 PATH에 적힌 디렉터리들(/usr/bin, /bin 등)에서만 실행 파일을 찾습니다. 리눅스는 보안상 현재 디렉터리(.)를 기본 PATH에 넣지 않습니다. 만약 넣는다면, 누군가 공유 디렉터리에 ls라는 이름의 악성 프로그램을 놓아 두었을 때 여러분이 그 디렉터리에서 ls를 치는 순간 악성 프로그램이 실행될 수 있기 때문입니다. ./는 "현재 디렉터리의"라는 뜻의 명시적 경로입니다. 윈도우 cmd는 역사적으로 현재 디렉터리를 먼저 찾기 때문에 ./가 필요 없습니다.

종료 코드(exit status)와 main의 return

main 함수가 return하는 정수는 시작 코드가 받아 exit()에 넘기고, 운영체제를 거쳐 이 프로그램을 실행한 쪽(셸, 배치 스케줄러)에 전달됩니다. 관례적으로 0은 성공, 0이 아닌 값은 실패를 뜻합니다. 표준은 <stdlib.h>에 EXIT_SUCCESS와 EXIT_FAILURE 매크로도 제공합니다.

여기서 잠깐 — main에서 return을 빼먹으면?

C99부터는 main 함수에 한해, 끝 중괄호 }에 도달하면 return 0;을 한 것으로 간주합니다. 하지만 C89에서는 종료 코드가 정해지지 않으며, 다른 함수에서 반환값을 빠뜨리고 그 값을 사용하면 UB입니다. 명시적으로 return 0;을 쓰는 습관을 들이십시오.

Visual Studio로 빌드하고 실행하기

윈도우에서 가장 많이 쓰는 통합 개발 환경(IDE)은 Microsoft Visual Studio이며, 컴파일러는 MSVC(cl.exe)입니다. 무료인 Community 판을 설치할 때 "C++를 사용한 데스크톱 개발" 워크로드를 선택하면 C도 컴파일할 수 있습니다.

  2. 소스 파일 추가: 솔루션 탐색기에서 [소스 파일] 우클릭 → [추가] → [새 항목] → 파일 이름을 hello.c로 지정합니다. 확장자를 반드시 .c로 해야 C 컴파일러 모드로 번역됩니다. .cpp로 만들면 C++로 컴파일되어 일부 C 코드가 오류를 냅니다.
  3. 빌드: [빌드] → [솔루션 빌드] (단축키 Ctrl+Shift+B). 아래 [출력] 창에 결과가 나옵니다.

자주 하는 실수 — scanf에서 C4996 오류가 나요

Visual Studio에서 scanf, strcpy 같은 함수를 쓰면 "error C4996: 'scanf': This function or variable may be unsafe. Consider using scanf_s instead."가 납니다. MSVC가 보안상 위험할 수 있는 함수 사용을 막는 것이며, scanf_s는 Microsoft 확장(표준 C11 부록 K의 선택 사항)이라 gcc에서는 보통 쓸 수 없습니다. 이 과정은 표준 C를 따르므로 소스 맨 위(모든 #include보다 앞)에 다음 한 줄을 넣어 경고를 끄는 방법을 권장합니다.

#define _CRT_SECURE_NO_WARNINGS
#include <stdio.h>

또는 프로젝트 속성 → C/C++ → 전처리기 → 전처리기 정의에 _CRT_SECURE_NO_WARNINGS를 추가합니다. 경고를 끈다고 위험이 사라지는 것은 아니므로, 3장과 22장에서 배울 안전한 입력 방법을 함께 익혀야 합니다.

왜 그럴까? — 같은 64비트인데 long 크기가 왜 다를까?

C 표준은 long이 "최소 32비트"라는 것만 정하고 정확한 크기는 구현에 맡깁니다(구현 정의 동작). 64비트 리눅스·유닉스는 LP64 모델(long과 포인터가 64비트)을, 64비트 윈도우는 LLP64 모델(long long과 포인터만 64비트, long은 32비트)을 택했습니다. 윈도우는 기존 32비트 프로그램과의 호환성을 위해 long을 그대로 둔 것입니다. 그래서 잔액처럼 큰 금액을 다룰 때는 어디서나 최소 64비트가 보장되는 long long이나 <stdint.h>의 int64_t를 써야 합니다. 3장에서 다시 다룹니다.

실무 프로그램은 거의 항상 여러 파일로 나뉩니다. 아주 작은 예로 미리 감을 잡아 봅니다. 함수는 7장에서 정식으로 배우므로 지금은 구조만 보십시오.

$ gcc -Wall -c interest.c          # interest.o 생성
$ gcc -Wall -c main.c              # main.o 생성
$ gcc main.o interest.o -o bank    # 링크
$ ./bank

은행 시스템에서는 — 이율을 왜 정수 만분율로 표현했을까?

위 예에서 연 3.50%를 0.035라는 실수 대신 350이라는 정수(베이시스 포인트, bp: 1bp = 0.01%)로 표현했습니다. 실수(double)는 0.035 같은 값을 2진수로 정확히 표현하지 못해 아주 작은 오차가 생기고, 수백만 계좌에 적용하면 원 단위 차이가 발생할 수 있습니다. 그래서 금융 계산에서는 금액을 원 단위 정수(long long)로, 이율을 정수 배율로 다루고, 곱셈을 먼저 한 뒤 마지막에 나누면서 절사·반올림 규칙을 명시적으로 적용하는 방식을 많이 씁니다. 왜 곱셈을 먼저 해야 하는지는 4장 연산자에서, 부동소수점 오차의 원리는 21장에서 자세히 다룹니다.

실행 시간 오류와 디버거 맛보기

빌드가 성공했다고 끝이 아닙니다. 다음 프로그램은 경고 없이 컴파일되지만 실행하면 죽습니다.

왜 그럴까?

정수 0으로 나누기는 C 표준에서 UB입니다. x86 CPU의 정수 나눗셈 명령(idiv)은 제수가 0이면 하드웨어 예외(#DE)를 일으키고, 리눅스 커널은 이를 SIGFPE 신호로 바꿔 프로세스에 보냅니다. 이 신호를 처리하지 않으면 프로세스는 종료됩니다. 컴파일러가 이 오류를 미리 잡지 못한 이유는 count가 0인지가 실제로는 실행 중에 데이터에 따라 정해지기 때문입니다(이 예처럼 상수면 일부 컴파일러가 경고를 내기도 합니다).

"core dumped"는 프로세스가 죽는 순간의 메모리 내용을 파일로 남겼다는 뜻입니다(시스템 설정에 따라 실제 파일이 생기지 않을 수도 있습니다). 운영 서버에서 새벽 배치가 죽었을 때 개발자가 아침에 출근해 gdb ./batch core로 죽은 순간의 변수 값과 호출 경로를 분석합니다. 금융권 유닉스 서버 운영에서 매우 자주 쓰이는 기술입니다.

실행 파일의 정체와 프로세스

링커가 만든 실행 파일은 단순한 기계어 덩어리가 아니라, 운영체제가 읽을 수 있는 정해진 형식의 파일입니다. 리눅스는 ELF, 윈도우는 PE 형식을 씁니다. 이 파일 안에는 기계어(.text), 초기값이 있는 전역 변수(.data), 문자열 상수(.rodata), 그리고 "어디서부터 실행할지(진입점)" 같은 정보가 들어 있습니다. 실행 파일이 메모리에 적재되어 실행 중인 상태를 프로세스(process)라고 합니다. 같은 실행 파일을 두 번 실행하면 프로세스가 두 개 생기고, 각자 독립된 메모리 공간을 가집니다.

이 그림은 앞으로 이 과정 전체에서 계속 다시 등장합니다. 지역 변수는 왜 함수가 끝나면 사라지는지(스택), malloc으로 받은 메모리는 왜 free해야 하는지(힙), 문자열 상수는 왜 수정하면 안 되는지(.rodata는 읽기 전용) 모두 이 그림으로 설명됩니다.

예제 1-5 난이도 ★★★

같은 소스 파일을 리눅스 서버에서 빌드한 실행 파일을 윈도우 PC로 복사하면 실행되지 않습니다. 소스가 똑같은데 왜 그런지 두 가지 이상의 이유를 드십시오. 그리고 C의 '이식성'이 정확히 무엇을 뜻하는지 설명하십시오.

정답과 해설 보기
  1. 실행 파일 형식이 다릅니다. 리눅스는 ELF, 윈도우는 PE 형식을 씁니다. 윈도우의 로더는 ELF 파일을 해석할 줄 모릅니다.
  2. 시스템 호출과 라이브러리가 다릅니다. printf는 결국 운영체제에 "화면에 써 달라"고 요청하는데, 리눅스는 write 시스템 호출을, 윈도우는 다른 API를 씁니다. 링크된 libc도 다릅니다.
  3. (서버가 다른 CPU라면) 기계어 명령 집합이 다릅니다. 예를 들어 IBM Power CPU 기반 AIX 서버의 기계어는 x86 PC에서 실행할 수 없습니다.

그러므로 C의 이식성이란 "실행 파일이 어디서나 돈다"가 아니라 "소스 코드를 각 플랫폼의 컴파일러로 다시 빌드하면 돈다"는 소스 수준 이식성을 뜻합니다. 그것도 long 크기처럼 구현 정의 부분에 의존하지 않도록 작성했을 때에 한합니다. 금융권에서 유닉스 서버를 리눅스로 전환(이른바 U2L, Unix to Linux)할 때 대규모 재컴파일과 테스트가 필요한 이유입니다.

핵심 정리

  • 프로그램은 CPU가 수행할 명령어의 묶음이며, CPU는 메모리에 적재된 기계어만 실행합니다. CPU는 인출-해독-실행 사이클을 반복합니다.
  • 메모리는 1바이트마다 주소가 붙은 칸의 연속입니다. CPU는 메모리 값을 레지스터로 읽어 계산하고 다시 씁니다. C 한 문장은 여러 기계어 명령이 될 수 있습니다.
  • 기계어 → 어셈블리어(저급) → C, Java 등(고급) 순으로 추상화가 높아집니다. C는 고급 언어이면서 메모리를 직접 다룰 수 있습니다.
  • C는 1972년 UNIX 개발을 위해 탄생했고, C89/C99/C11/C17/C23 표준이 있습니다. 이 과정은 C99/C11 기준입니다.
  • C의 특징: 빠르고 작고 이식성이 높지만, 범위 검사가 없고 메모리 관리를 프로그래머가 책임집니다. 정의된 동작 / 구현 정의 동작 / 미정의 동작(UB)을 구분해야 합니다.
  • 금융권 계정계·대외계·배치에서는 성능, 예측 가능한 응답 시간, 검증된 레거시, 고정길이 전문 처리 때문에 C가 여전히 중요합니다.
  • 빌드는 전처리(.i) → 컴파일(.s) → 어셈블(.o) → 링크(실행 파일)의 4단계입니다. gcc의 -E, -S, -c로 각 단계까지만 수행할 수 있습니다.
  • 오류는 컴파일 오류, 경고, 링크 오류(undefined reference), 실행 시간 오류, 논리 오류로 나뉩니다. 첫 번째 오류부터 고치고, 경고도 반드시 없앱니다.
  • 권장 옵션: gcc -std=c11 -Wall -Wextra -pedantic -g. Visual Studio에서는 .c 확장자와 _CRT_SECURE_NO_WARNINGS에 주의합니다.
  • main은 int를 반환하며, 그 값은 종료 코드로 셸·배치 스케줄러에 전달됩니다(0 = 성공).
  • 64비트 리눅스(LP64)와 윈도우(LLP64)는 long 크기가 다릅니다. 금액에는 long long을 씁니다.

Q1. 컴파일 언어와 인터프리터 언어의 차이를 설명해 주세요.

컴파일 언어는 실행 전에 소스 전체를 대상 CPU의 기계어로 번역해 실행 파일을 만들고, 인터프리터 언어는 실행 시점에 소스를 한 단위씩 해석하며 실행합니다. 컴파일 방식은 실행이 빠르고 오류를 미리 많이 잡지만 플랫폼마다 다시 빌드해야 하고, 인터프리트 방식은 이식이 쉽고 개발 주기가 빠르지만 실행 속도가 상대적으로 느립니다. Java처럼 바이트코드로 컴파일한 뒤 JVM이 해석하거나 JIT 컴파일하는 하이브리드 방식도 있습니다.

꼬리 질문 대비: "JIT는 무엇인가요?" → 실행 중 자주 쓰이는 코드를 기계어로 컴파일해 캐시하는 기법으로, 실행 시간 정보를 활용한 최적화가 가능합니다.

Q2. C 소스 코드가 실행 파일이 되기까지의 과정을 설명해 주세요.

전처리기가 #include, #define, 조건부 컴파일, 주석 제거를 처리해 확장된 소스를 만들고, 컴파일러가 이를 구문·의미 분석과 최적화를 거쳐 어셈블리어로 번역합니다. 어셈블러는 어셈블리를 기계어 목적 파일로 만들고, 링커가 여러 목적 파일과 라이브러리를 합치면서 외부 심볼의 주소를 해결(재배치)해 실행 파일을 만듭니다. 실행 시에는 로더가 실행 파일을 메모리에 적재하고 동적 라이브러리를 연결합니다.

꼬리 질문 대비: "선언만 있고 정의가 없으면 어느 단계에서 오류가 나나요?" → 링크 단계의 undefined reference입니다.

Q3. 정적 링킹과 동적 링킹의 차이와 장단점은 무엇인가요?

정적 링킹은 라이브러리 코드를 실행 파일에 복사해 넣으므로 배포가 단순하고 실행 환경 차이에 강하지만, 실행 파일이 커지고 라이브러리 보안 패치 시 재빌드가 필요합니다. 동적 링킹은 실행 시 공유 라이브러리를 연결하므로 메모리와 디스크를 절약하고 라이브러리만 교체해 패치할 수 있지만, 버전 불일치 문제(DLL 지옥)가 생길 수 있습니다.

꼬리 질문 대비: "금융 서버 배포 시 주의점은?" → 개발·운영 서버의 공유 라이브러리 버전 일치 여부를 확인하고, ldd 등으로 의존성을 점검합니다.

Q4. 미정의 동작(Undefined Behavior)이란 무엇이고 왜 위험한가요?

C 표준이 결과에 대해 어떤 요구도 하지 않는 동작으로, 배열 범위 밖 접근, 부호 있는 정수 오버플로, 초기화 안 된 변수 읽기, 정수 0으로 나누기 등이 해당합니다. 컴파일러는 UB가 일어나지 않는다고 가정하고 최적화하기 때문에, 같은 코드가 최적화 수준이나 컴파일러 버전에 따라 다르게 동작할 수 있어 재현이 어렵습니다. 구현 정의 동작(예: int 크기)은 컴파일러가 문서화된 일관된 결과를 내는 것이므로 UB와 구별해야 합니다.

꼬리 질문 대비: "UB를 어떻게 찾나요?" → 경고 옵션, 정적 분석 도구, 그리고 -fsanitize=undefined,address 같은 새니타이저를 사용합니다.

Q5. CPU가 명령어를 실행하는 과정을 설명해 주세요.

CPU는 프로그램 카운터가 가리키는 메모리 주소에서 명령어를 가져오고(Fetch), 해독한 뒤(Decode), 실행(Execute)하고 결과를 레지스터나 메모리에 씁니다. 그리고 프로그램 카운터를 다음 명령으로 옮기거나 분기 명령이면 다른 주소로 바꿉니다. 현대 CPU는 이 단계들을 겹쳐 실행하는 파이프라이닝과 분기 예측으로 성능을 높입니다.

꼬리 질문 대비: "레지스터, 캐시, 메모리의 차이는?" → CPU에 가까울수록 빠르고 작으며 비쌉니다. 캐시는 메모리 접근의 지역성을 이용해 자주 쓰는 데이터를 CPU 근처에 보관합니다.

Q6. 프로그램과 프로세스의 차이는 무엇인가요?

프로그램은 디스크에 저장된 실행 파일, 즉 정적인 명령어와 데이터의 묶음이고, 프로세스는 그 프로그램이 메모리에 적재되어 실행 중인 상태입니다. 프로세스는 코드·데이터·힙·스택으로 구성된 독립된 주소 공간과 PCB 같은 운영체제 관리 정보를 가집니다. 같은 프로그램을 여러 번 실행하면 서로 독립된 여러 프로세스가 생깁니다.

꼬리 질문 대비: "스레드와의 차이는?" → 스레드는 한 프로세스 안에서 코드·데이터·힙을 공유하고 스택과 레지스터만 따로 가지는 실행 흐름입니다(PART 2에서 다룹니다).

Q7. 왜 금융권 핵심 시스템에 아직 C가 쓰인다고 생각하나요?

첫째, 가비지 컬렉션이 없어 응답 시간이 예측 가능하고 대량 거래 처리 성능이 좋습니다. 둘째, 수십 년간 검증된 이자·수수료 계산 로직을 재작성하는 위험이 큽니다. 셋째, 대외기관과의 고정길이 전문처럼 바이트 단위 데이터 처리에 C의 구조체와 메모리 조작이 잘 맞고, TP 모니터·Pro*C 같은 기존 인프라도 C를 지원합니다. 다만 메모리 안전성 문제가 있으므로 시큐어 코딩 규칙과 정적 분석을 함께 적용해야 한다고 답하면 균형 잡힌 답이 됩니다.

Q8. main 함수의 반환값은 어디로 가며, 왜 void main을 쓰면 안 되나요?

main의 반환값은 C 런타임의 시작 코드가 받아 exit에 전달하고, 운영체제를 거쳐 부모 프로세스(셸, 스케줄러)가 종료 상태로 받습니다. 0은 성공, 0이 아닌 값은 실패를 뜻하는 관례가 있어 배치 작업 흐름 제어에 쓰입니다. 표준이 보장하는 형태는 int main(void)와 int main(int argc, char *argv[])이며, void main은 비표준이고 종료 상태를 신뢰할 수 없게 만듭니다.

Q9. 32비트와 64비트 환경에서 C 자료형 크기는 어떻게 다른가요?

포인터는 32비트 환경에서 4바이트, 64비트에서 8바이트입니다. int는 보통 둘 다 4바이트입니다. long은 64비트 리눅스(LP64)에서 8바이트, 64비트 윈도우(LLP64)에서는 4바이트로 다릅니다. 그래서 크기가 중요한 데이터에는 <stdint.h>의 int32_t, int64_t 같은 고정 폭 정수형을 쓰는 것이 안전합니다.

연습문제 1-10 난이도 ★★★

리눅스 서버(64비트)에서 잘 돌던 다음 코드를 64비트 윈도우의 Visual Studio로 옮겼더니 결과가 달라졌습니다. 이유를 설명하고 두 환경에서 모두 같은 결과를 내도록 고치십시오.

연습문제 1-11 난이도 ★★☆

금융권 배치 스케줄러가 A → B → C 순으로 프로그램을 실행하며, 앞 프로그램의 종료 코드가 0일 때만 다음 프로그램을 실행합니다. B 프로그램 개발자가 오류가 나도 항상 return 0;을 하도록 작성했다면 어떤 일이 생길 수 있는지, 운영 관점에서 설명하십시오.

정답과 해설 보기

B가 실패해도 스케줄러는 성공으로 판단하고 C를 실행합니다. 예를 들어 B가 "당일 거래 원장 집계"이고 C가 "집계 결과로 대외기관 정산 파일 생성"이라면, 불완전한 집계 결과로 정산 파일이 만들어져 대외기관에 송신될 수 있습니다. 장애는 다음 날 대사(맞춰 보기) 과정에서야 발견되고, 원인 추적도 어렵습니다. 따라서 오류 상황에서는 반드시 0이 아닌 종료 코드를 반환하고, 오류 원인을 로그에 남겨야 합니다. 종료 코드는 프로그램과 운영 체계 사이의 '계약'입니다.
