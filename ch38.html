Transformer·LLM과 금융/OMS 활용

2017년 "Attention Is All You Need" 논문 이후, 자연어 처리는 완전히 다른 세상이 되었습니다. GPT, Claude, Gemini 같은 LLM이 코딩·요약·대화를 사람 수준으로 처리하는 지금, 금융권도 LLM을 뉴스 감성 분석·공시 요약·고객 상담·심지어 OMS 로그 분석에까지 쓰기 시작했습니다. 이 장은 Attention과 Transformer의 핵심 아이디어, 사전학습-파인튜닝-RAG의 흐름, 프롬프트 엔지니어링, 그리고 하나증권 퀀트실·OMS 운영에서 지금 당장 쓸 수 있는 활용 패턴을 다룹니다.

38-1어텐션·Transformer·LLM 기초

Self-Attention — "모든 단어가 모든 단어를 본다"

RNN은 시퀀스를 왼쪽부터 하나씩 처리하며 과거를 "기억"해 미래로 전달했습니다. 긴 문장에서는 멀리 떨어진 단어 사이 관계가 희석됐죠. Transformer의 Self-Attention은 "모든 위치의 단어가 다른 모든 위치의 단어와 직접 비교"하도록 바꿉니다.

각 단어는 세 가지 벡터로 표현됩니다.

  • Query (Q): "내가 무엇을 찾고 있는가"
  • Key (K): "나는 어떤 정보를 담고 있는가"
  • Value (V): "실제로 가져갈 정보"

Attention(Q, K, V) = softmax(QKᵀ / √d) · V

이 구조의 장점:

  • 병렬 처리 가능: RNN처럼 순차 처리 안 해도 됨 → GPU에서 압도적으로 빠름.
  • 장거리 의존성: 100번째 토큰이 1번째 토큰을 직접 "볼" 수 있음.
  • 해석 가능: 어텐션 가중치로 "이 단어가 어떤 단어를 주목했는지" 시각화.

Transformer 블록

Transformer는 Self-Attention + FFN(Feed-Forward Network) + 잔차연결 + Layer Normalization의 블록을 여러 층 쌓습니다. GPT-3는 96층, GPT-4는 추정 100+층입니다.

GPT와 BERT — 디코더형 vs 인코더형

구분GPT (OpenAI)BERT (Google)
구조디코더 전용 (단방향)인코더 전용 (양방향)
학습 목표다음 토큰 예측 (Causal LM)마스킹된 토큰 복원 (Masked LM)

임베딩 모델도 BERT 계열이다

LLM 시대에도 BERT 계열은 "텍스트를 벡터로 바꾸는" 임베딩 모델로 활발히 쓰입니다. RAG 시스템에서 사용자 질문과 문서를 벡터로 매칭할 때, OpenAI text-embedding-3이나 BGE·E5 같은 임베딩 모델이 전부 BERT 계열입니다. 생성은 GPT가, 검색·분류는 BERT가 — 둘은 경쟁이 아니라 분업입니다.

LLM은 어떻게 "학습"되는가 — 사전학습 · SFT · RLHF

GPT, Claude, Llama 같은 오늘날의 LLM은 보통 다음 세 단계로 만들어집니다. 각 단계는 "무엇을 학습시키는가"가 완전히 다릅니다.

단계별 요점.

  • ① 사전학습: "다음 토큰을 맞혀라"만 수조 번 반복. 이 과정에서 문법·세상지식·추론 능력이 "부수적으로" 생긴다. Base model은 질문에 답을 하기보다는 문장을 이어 쓴다.
  • ② SFT (Supervised Fine-Tuning): 사람이 작성한 "질문 → 좋은 답변" 쌍 수만 건으로 지도학습. 이 단계에서 비로소 모델이 "질문에 답하는" 포맷을 익힌다.
  • ③ RLHF (Reinforcement Learning from Human Feedback): 한 질문에 대해 모델이 생성한 두 답변을 사람이 비교(A가 B보다 낫다) → 그 선호를 보상모델(Reward Model)이 학습 → PPO·DPO로 정책(LLM)을 강화학습. ChatGPT가 "거부해야 할 때 거부하고, 공손하고, 길이가 적당"한 이유의 대부분이 여기서 나온다.
  • ④ 추론: 사용자가 보는 세상. 가중치가 더 이상 바뀌지 않는다. 당신이 뭘 묻든, 어떤 피드백을 주든, LLM 자신은 그걸 "기억하지 못한다". 다음 섹션의 전제가 여기서 나온다.

파인튜닝 · LoRA · DPO · RLAIF

  • Full fine-tuning: 모델의 모든 파라미터를 다시 학습. 비싸고 큰 GPU 필요.
  • LoRA / QLoRA: 전체가 아니라 "작은 adapter 레이어"만 학습. 몇 십만원 ~ 몇 백만원으로 가능. 금융권 사내 LLM 커스터마이징의 사실상 표준.
  • DPO (Direct Preference Optimization): 보상모델 없이 선호 데이터로 바로 LLM을 학습. RLHF보다 안정적이고 간단해 최근 많이 쓰임.
  • RLAIF (Constitutional AI): 사람 대신 "다른 LLM"이 피드백을 주는 방식. Anthropic Claude가 대표. 사람 레이블러 의존도를 낮춤.

인-컨텍스트 학습(ICL)은 "학습"이라는 말이 붙지만 가중치가 바뀌지 않습니다. 프롬프트에 몇 개 예시를 보여주면 그 패턴을 따라 답할 뿐, 세션이 끝나면 흔적도 남지 않습니다. 이게 LLM의 "기억" 문제의 출발점입니다.

LLM의 환각과 금융 리스크

환각(hallucination)은 LLM의 디자인 결함이 아니라 특성이다

LLM은 "다음 토큰 확률"을 최대화하도록 학습된 모델이지 "진실"을 담도록 학습되지 않습니다. 그래서 그럴듯한 거짓말을 자신 있게 합니다. 금융에서 치명적인 사례:

  • 존재하지 않는 종목 코드·종목명을 만들어냄
  • 실적·배당 숫자를 틀리게 요약
  • 법령·규정 조항을 그럴듯하게 지어냄
  • 과거 날짜의 뉴스를 사실인 양 생성

그래서 금융권 LLM 배포에는 반드시 (1) 출처 명시, (2) 검증 레이어, (3) "모르면 모른다" 응답 유도, (4) 신뢰도 라벨링이 들어갑니다. 특히 투자자 대상 콘텐츠는 법적 문제까지 걸릴 수 있어 사람 검토(Human-in-the-loop)가 필수입니다.

LLM의 "기억" — 세 가지 치명적 한계

LLM을 실무에 쓸 때 가장 많이 하는 실수는 "모델이 기억한다"고 착각하는 것입니다. LLM은 세 가지 다른 종류의 "모름"을 가지고 있습니다.

이 세 가지 한계는 전부 "모델 바깥"에서 해결해야 합니다. 모델을 바꾸는 게 아니라, 모델에게 뭘 보여줄지(context)와 어떻게 묻는지(prompt)를 바꾸는 겁니다.

자주 하는 착각

  • "어제 알려줬잖아요" → API는 매번 백지. 히스토리를 다시 넣지 않으면 모름.
  • "방금 가르쳐 줬는데 왜 또 틀려?" → 가중치는 안 바뀜. 같은 세션이어도 다른 "관련 없는" 질문 사이에선 흘려버림. 중요하면 system 프롬프트로 못박아야 함.
  • "오늘 공시 알려줘" → 학습 컷오프 이후면 당연히 모름. RAG·검색 도구 없이는 환각 발생.
  • "PDF 100개 다 넣고 요약" → context window 넘기면 뒷부분이 잘림. 또는 중간 정보가 희석(Needle in a Haystack 성능 저하).

38-2RAG·프롬프트·퀀트/OMS 실무 활용

RAG (Retrieval-Augmented Generation)

LLM은 학습 시점 이후의 정보를 모르고, 환각 리스크가 있습니다. 두 문제의 해결책이 RAG입니다: 사용자 질문에 관련된 문서를 먼저 검색해, 그 문서를 프롬프트에 붙여서 LLM에 넘깁니다.

리서치·OMS에서 쓰는 RAG 사례

  • 리서치 보조: 사내 리서치 리포트 수만 건을 임베딩 → 애널리스트가 "삼성전자 메모리 사이클" 질문하면 과거 보고서 요지 + 출처로 답변.
  • 공시 요약: DART 공시가 올라오면 자동으로 핵심 요약 + 영향 추정 → OMS 알림.
  • 규정 Q&A: 자본시장법·내부통제 규정 수백 페이지에 RAG → 운영팀이 "이체 한도 규정" 질문하면 조문 번호와 함께 답변.
  • OMS 매뉴얼 봇: 수백 개 운영 매뉴얼·장애 보고서 → "9001 응답코드 왜 뜨지" 질문에 과거 사례 포함 답변.

지식 그래프 vs 벡터 RAG — "외부 기억"의 두 접근

LLM에게 외부 지식을 주는 방법은 크게 두 갈래입니다. 둘 다 "모델 바깥의 기억"이지만 접근 방식이 완전히 다릅니다.

관점지식 그래프벡터 RAG
저장 단위엔티티·관계 (삼각형)텍스트 청크 + 임베딩 벡터
검색 방식그래프 쿼리(Cypher, SPARQL)·탐색코사인 유사도 top-k
잘하는 것다단계 추론, 정확한 사실, 관계 질의자연어 질의, 유연한 유사 매칭
약한 것구축·유지가 비쌈, 스키마 설계 필요관계 추론 X, 반복 사실 중복
예시 질의"HBM 공급망에서 삼성전자의 2단계 거래처는?""작년 삼성전자 메모리 호황 리포트 찾아줘"
구축 비용중~고 (엔티티·관계 추출 필요)저~중 (임베딩만 돌리면 됨)
대표 도구Neo4j, Amazon Neptune, TigerGraphFAISS, Milvus, Pinecone, pgvector
LLM 환각 억제★★★ (사실 그 자체를 주입)★★ (문서 조각을 주입)

왜 둘 다 필요한가. 벡터 RAG는 "비슷한 문서"는 잘 찾지만 "A가 B의 자회사이고 B가 C에 투자했다" 같은 다단계 관계 추론이 약합니다. 지식 그래프는 그 반대입니다. 그래서 2024년부터 GraphRAG(Microsoft 등)·하이브리드 RAG가 뜨고 있습니다.

어느 쪽을 먼저 깔까

  • 단일 문서 Q&A·요약·검색 — 벡터 RAG부터. 구축이 싸고 즉시 가치. (매뉴얼 봇, 리서치 검색)
  • 관계·공급망·규정 조문 참조 — 지식 그래프 가치가 큼. (금융 규제, 그룹 지분, HBM 공급망)
  • 복잡한 금융 분석 (A→B→C 영향) — GraphRAG. 구축 비용 들지만 환각이 극적으로 줍니다.
  • OMS 로그/장애 Q&A — 보통 벡터 RAG로 시작, 반복되는 "장애 유형 → 조치 → 유관 시스템"을 그래프로 승격시키는 패턴이 효율적.

실전 프롬프트 — "LLM이 못 기억한다는 전제"에서 설계하라

프롬프트 엔지니어링은 결국 "LLM이 모르는 것을 알게 하고, 아는 것으로 정확히 답하게 만들기"입니다. 앞 섹션(38-1-6)에서 본 세 가지 한계 — 학습 컷오프·컨텍스트 윈도우·세션 무상태 — 를 그대로 뒤집으면 좋은 프롬프트의 뼈대가 나옵니다.

PROMPT 7

  1. Persona — 역할 부여. "너는 15년차 퀀트 애널리스트" → 답변 톤·깊이가 맞춰진다.
  2. Reference — 참고 자료 주입. 학습 컷오프 뒤 사실·사내 매뉴얼은 반드시 프롬프트로 넣는다 (RAG).
  3. Objective — 목표 명시. "요약" ❌ → "5개 불릿, 각 50자, 수치 보존" ✓.
  4. Manner — 출력 포맷 지정. JSON·마크다운 표·CSV. 파이프라인에 바로 넣을 수 있게.
  5. Principles — 금칙·거부 규칙. "모르면 모른다", "추측 금지", "참고 문서 밖은 답하지 마라".
  6. Thoughts — Chain-of-Thought. "단계별로 생각 후 답" → 추론 정답률 상승.
  7. Check — 자기 검증. "답 작성 후 사실 확인·형식 검사하고 틀리면 수정".

  • 동일 입력에도 LLM 응답이 미세하게 바뀐다 → 버저닝이 필수. 운영 프롬프트는 git에 커밋.
  • 프롬프트가 바뀌면 테스트 세트로 회귀 테스트: 100개 샘플에 자동 평가(라벨 일치, JSON valid 등).
  • 모델 바뀌면(예: gpt-4o-mini → gpt-5) 프롬프트 조정이 필요할 수 있다. 모델 버전도 고정.
  • 민감정보·내부전략은 프롬프트에 넣지 마라. 넣어야 한다면 사내망 LLM.

텍스트 데이터는 전통적 퀀트가 놓쳐 온 "비정형 알파" 소스입니다. LLM이 다음 영역에서 활용됩니다.

LLM in OMS 운영 — 로그·장애·매뉴얼

OMS 운영은 LLM이 가장 즉시 가치를 내는 영역 중 하나입니다. 로그가 많고, 패턴이 있고, 설명 가능한 답이 필요하기 때문입니다.

OMS에서 지금 당장 쓸 수 있는 LLM 패턴

  1. 로그 요약과 이상 패턴 설명: 수십만 줄의 로그 중 ERROR·WARN만 뽑아 LLM에 넘기면 "오전 10:23~10:27 사이 거래소 응답 지연 패턴, 영향 종목 32개, 영향 사용자 ..." 같은 요약을 생성. 야간 당직자가 사람에게 깨기 전에 1차 분류.
  2. 장애 보고서 초안: 로그·시간대·영향 범위를 넣으면 (감지-전파-원인-복구-재발방지) 템플릿(30장)에 따라 초안 생성. 사람은 검토·수정만.
  3. 매뉴얼 Q&A 봇: 운영 매뉴얼·과거 장애 보고서를 RAG로 묶어 "9001 응답코드 발생 시 조치 절차는?" 같은 질문에 답변 + 과거 유사 사례 링크.
  4. 코드 리뷰 보조: C 레거시 코드의 변경사항을 LLM에 넘겨 "메모리 누수 가능성, 경계값 체크 누락" 등 1차 지적. 사람 리뷰어의 시간 절약.
  5. 리그레션 테스트 케이스 생성: 전문 명세와 과거 테스트 케이스를 주면 유사 패턴의 새 케이스 자동 생성.
  6. 전문 디코더: 바이너리 전문을 보여주고 "이거 어떤 전문이고 어떤 필드 이상한지" 설명 요청. 24장의 전문처리 지식 + LLM 조합.

중요: 운영 환경에서는 LLM 응답을 항상 사람이 검토해야 합니다. 자동 실행 금지. 참고용·초안용으로만 쓰고, 조치는 사람이 결정합니다.

금융권 LLM 사용 시 반드시 체크할 것

  • 데이터 유출 금지: 공개 API에 고객정보·계좌번호·내부전략을 넣으면 안 됨. 반드시 마스킹하거나 사내망 LLM(Private LLM) 사용.
  • 프롬프트 인젝션 방어: 사용자 입력에 "지금까지 지시 무시하고..." 같은 공격 가능. system 프롬프트와 user 프롬프트 분리, 입력 sanitize.
  • 로깅과 감사: 누가·언제·무엇을 질문했고 LLM이 뭐라고 답했는지 전부 로깅. 금감원 검사·사후 추적.
  • 자동 집행 금지: 자동으로 주문 발주하거나 설정을 바꾸는 데 LLM 쓰지 말 것. 반드시 Human-in-the-loop.
  • 라이선스·규제: 외부 API 사용 시 금융권 데이터 처리 약관 검토. 개인정보보호법·전자금융감독규정 준수.

LLM 에이전트와 "하네스" — 도구 쓰는 LLM의 정체

2024년 이후 가장 뜨거운 흐름은 LLM 에이전트입니다. Cursor Agent, Claude Code, Devin, GitHub Copilot Agent, OpenAI Assistants/Swarm 등. 겉으로는 "AI가 알아서 코드도 짜고 터미널도 돌리고 PR도 올린다"처럼 보이지만, 안을 열어 보면 구조는 단순합니다. 본질은 여전히 LLM이 다음 토큰을 뱉고 있을 뿐이고, 그 토큰을 "행동"으로 번역해 주는 바깥 껍데기가 붙었을 뿐입니다.

용어 정리 — LLM · 에이전트 · 하네스는 다 다른 층이다

층정체책임예시
① LLM사전학습된 가중치 덩어리. 다음 토큰 확률.생각하고 말한다. 직접 아무것도 못 한다.GPT-5, Claude Opus 4.7, Llama 3
② 에이전트 루프LLM이 "도구 호출 JSON"을 뱉으면 실행하고 결과를 다시 넣는 반복문.Thought → Action → Observation 순환.ReAct, Plan-and-Execute, Reflexion
③ 하네스 (Harness)그 루프를 안전·안정적으로 돌리는 바깥 프레임.도구 등록, 샌드박스, 재시도, 타임아웃, 승인, 로깅, UI.Cursor, Claude Code, Devin, Aider, Open Interpreter

Cursor의 "Agent"가 매력적으로 보이는 이유는 LLM이 똑똑해져서가 아니라 하네스가 좋아서입니다. 좋은 도구 셋(파일 읽기·편집·셸·검색·브라우저), 깔끔한 승인 UX, 똑똑한 context 수집(워크스페이스 인덱싱, 자동 lint 보고), 안전가드, 그리고 "되돌릴 수 있는" 커밋 흐름이 핵심 가치입니다. LLM만 바꿔 끼워도 쓸만한 이유가 여기에 있습니다.

Tool Calling — 에이전트의 심장

에이전트가 돌아가는 메커니즘은 OpenAI/Anthropic의 function calling(tool use)입니다. LLM이 자유 텍스트 대신 "이 함수를 이 인자로 호출해 달라"는 JSON을 뱉고, 하네스가 그걸 실행해 결과를 다시 LLM에 전달합니다.

이 20줄이 전부입니다. Cursor Agent나 Claude Code도 이 구조에 (1) 좋은 도구들, (2) 승인 UI, (3) 전체 리포 context 수집, (4) 안전가드를 얹었을 뿐입니다.

에이전트의 대표 패턴

패턴아이디어어울리는 작업
ReActThought → Action → Observation 반복탐색·디버깅·검색 중심
Plan-and-Execute먼저 전체 계획을 세우고, 각 단계를 실행목표가 분명한 다단계 작업

에이전트의 한계 — "결국 LLM이 결정한다"

에이전트의 핵심을 한 문장으로 요약하면: LLM이 다음 토큰을 뱉어서 행동이 결정된다. 그래서 LLM의 모든 약점이 그대로 "실행된 행동"으로 번역됩니다.

  1. 환각의 행동화: LLM이 존재하지 않는 함수·파일·필드를 "자신 있게" 호출한다. 운영에서 이게 실제 명령으로 나가면 사고.
  2. 비결정성: 같은 목표·같은 코드에도 매번 다른 경로로 간다. 재현이 어렵고 테스트가 어렵다.
  3. 도구 선택 실수: 비슷한 도구가 많으면 엉뚱한 걸 쓴다. 설명·이름·스키마가 품질을 좌우한다.
  4. 무한 루프·헛돌이: 같은 실패를 반복, 조금 다른 쿼리로 재시도. max_steps·타임아웃이 필수.
  5. Context 희석: 긴 작업에서 중요한 지시가 뒤로 밀려 잊힌다 ("lost in the middle").
  6. 비용 폭증: 한 번 질문에 10~100번 LLM 호출. 쉽게 수십 달러.
  7. 프롬프트 인젝션의 "실행 공격": 사용자가 열어 준 문서/웹페이지에 숨은 지시로 에이전트가 파일 삭제·메일 발송·돈 이체까지. 샌드박스·화이트리스트·승인 게이트 없으면 치명적.
  8. 평가 어려움: "성공률 83%"가 무슨 뜻인가? 라벨링된 벤치마크가 거의 없다. 사내에서 반드시 자체 평가셋을 만들어야 함.
  9. 책임 소재: 에이전트가 잘못 주문·설정 변경·보고서 오보를 하면 누가 책임지나? 법·내부통제가 아직 못 따라옴.

그래서 운영에서 쓸 때 원칙: 돈이 움직이거나 되돌릴 수 없는 행동은 반드시 사람 승인. 모든 tool call은 감사 로그. 에이전트는 "초안·탐색·분류"에만, "집행·확정"은 사람 또는 결정론적 코드.

금융/OMS에서 에이전트 — 지금 당장 유용한 쓰임

OMS 운영 현장에서 쓸만한 에이전트 유즈케이스

  • 장애 1차 조사 에이전트: "최근 10분 ERROR 로그 → 유형 분류 → 과거 유사 티켓 검색 → 1차 가설 3개 생성 → 영향 범위 집계". 집행 X, 보고서만.
  • 리그레션 테스트 에이전트: 전문 명세 바뀌면 기존 테스트 케이스를 열어 수정 PR 생성 → 사람이 리뷰·머지.
  • 코드 리뷰 에이전트: 변경 diff + 과거 장애 보고서 RAG → 비슷한 사고의 조짐이 있는지 코멘트. 승인 X.
  • 리서치 Deep Research: 특정 종목·테마에 대해 뉴스·공시·리서치 수십 건을 수 시간 돌면서 요약 리포트 초안. 애널리스트가 검증 후 사용.
  • Cursor Agent / Claude Code: 운영 스크립트·대시보드 수정 같은 "읽기·쓰기 중심" 개발 작업. 터미널 실제 집행은 승인 모드로.

절대 하지 말 것: 자동 주문·자동 포지션 변경·자동 설정 변경·고객에게 자동 응답 전송. 모두 Human-in-the-loop.

"에이전트 쓸 때 가장 신경 쓰는 건?"

면접관은 "에이전트가 똑똑하다"는 답을 듣고 싶어 하지 않습니다. "에이전트는 LLM이 결정하기 때문에 환각이 행동으로 번역된다. 그래서 샌드박스·화이트리스트·승인 게이트·감사 로그로 하네스에서 막아야 하고, 집행은 결정론적 코드로 분리한다"라고 답하는 게 운영 신뢰도를 보여 줍니다.

예제 38-1 — RAG 설계 난이도 ★★☆

OMS 운영팀이 "매일 수만 건의 ERROR 로그 중 과거에 봤던 패턴은 자동 분류, 새 패턴만 사람에게 알림"을 받고 싶어 합니다. LLM과 임베딩을 활용한 아키텍처를 어떻게 설계할까요?

정답과 해설 보기

단계별 설계:

  1. 로그 정규화: 가변 부분(계좌번호, 시각, 금액, 종목코드)을 placeholder로 치환해 "로그 템플릿"으로 변환. 예: Order rejected acct=***, code=9001, msg=TIMEOUT.
  2. 과거 패턴 DB 구축: 지난 1년 로그 템플릿을 임베딩해 벡터DB(FAISS)에 저장. 각 템플릿에 "원인·조치"가 라벨링된 과거 분석 노트 연결.
  3. 실시간 분류: 새 로그 → 템플릿화 → 임베딩 → 벡터DB에서 top-1 검색. 코사인 유사도가 임계값(예: 0.9) 이상이면 "알려진 패턴"으로 자동 분류, 과거 조치 안내.
  4. 신규 패턴 처리: 유사도가 임계값 미만이면 LLM(RAG + 운영 매뉴얼)에 넘겨 1차 설명 생성 + 담당자 알림. 담당자가 조치 후 결과를 벡터DB에 추가 → 다음부터 자동 분류됨.
  5. 검증·감사: LLM이 분류·설명한 모든 건을 로그에 남기고, 주간 샘플링으로 사람이 품질 체크. 오분류율이 올라가면 임계값 조정.

핵심 포인트: LLM만 쓰면 비용·지연·환각 리스크 큼. 임베딩 기반 "닮은 과거"로 1차 거르고, 신규 건에만 LLM 사용 → 비용 90% 이상 절감 가능하고 "학습하는 OMS 운영"이 됩니다.

핵심 정리

  • Self-Attention은 "모든 토큰이 모든 토큰을 가중 참조"하는 메커니즘. Q·K·V를 만들어 유사도 → softmax → Value 가중합.
  • Transformer = Multi-Head Attention + FFN + 잔차 + LayerNorm을 쌓은 구조. RNN을 거의 완전히 대체.
  • GPT는 생성형(디코더), BERT는 분류·임베딩형(인코더). 임베딩 모델은 RAG의 핵심.
  • LLM 학습 3단계: ① 사전학습(다음 토큰 예측) → ② SFT(지시 따르기) → ③ RLHF/DPO(사람 선호 정렬). ④ 추론부터는 가중치가 더 안 바뀐다.
  • LoRA·QLoRA·DPO·RLAIF 덕에 사내 파인튜닝 비용이 극적으로 낮아짐.
  • LLM이 못 기억하는 세 영역: ① Training Cutoff ② Context Window ③ 세션 무상태. 셋 다 "모델 바깥"에서 메꾼다.
  • 환각은 디자인 특성이지 버그가 아니다. 반드시 출처·검증·사람 검토 레이어 필요.
  • RAG는 환각과 지식 cut-off를 동시에 해결. 금융 실무의 1순위 패턴.
  • 지식 그래프 vs 벡터 RAG: 그래프 = 다단계 관계·사실에 강함, 벡터 = 자연어 유사검색에 강함. GraphRAG로 결합.
  • 프롬프트 7원칙(PROMPT 7): Persona · Reference · Objective · Manner · Principles · Thoughts · Check.
  • "기억 못 함" 3대 대응: 세션 히스토리 재주입 · 장기 메모리 임베딩 · RAG + "모르면 모른다" 강제.
  • 퀀트: 뉴스감성·공시요약·실적콜 톤 분석 등 비정형 알파. OMS: 로그 요약·장애보고서 초안·매뉴얼 Q&A.
  • 에이전트 = LLM + 도구 호출(ReAct 루프) + 하네스. Cursor·Claude Code도 이 구조이고, "똑똑함"의 상당 부분은 LLM이 아니라 하네스에서 나온다.
  • 에이전트의 한계는 모두 LLM에서 유래: 환각이 행동으로 번역됨, 비결정성, 도구 선택 실수, 무한 루프, 프롬프트 인젝션의 실행 공격, 비용 폭증.
  • 운영 원칙: 집행은 결정론적 코드 또는 사람 승인. 모든 tool call은 감사 로그. 샌드박스·화이트리스트·타임아웃 필수.
  • 금융 LLM 체크리스트: 데이터 마스킹 · 프롬프트 인젝션 방어 · 감사 로깅 · 자동 집행 금지 · 프롬프트 버저닝.

면접 질문

자주 나오는 질문

Q1. Self-Attention을 쉽게 설명해 보세요.

문장의 각 단어가 "다른 모든 단어를 얼마나 참조할지"를 가중치로 학습하는 방식입니다. 각 단어마다 Query(찾는 것)·Key(가진 정보)·Value(실제 정보) 벡터를 만들고, Query와 모든 Key의 내적으로 유사도를 구한 뒤 softmax로 가중치화해 Value의 가중합을 돌려줍니다. RNN처럼 순차 처리할 필요가 없어 병렬 가능하고, 장거리 의존성에 강합니다.

Q2. Transformer가 RNN·LSTM을 대체한 이유는?

세 가지입니다. (1) 병렬성: RNN은 t시점이 t-1에 의존해 순차적이지만 Transformer는 전체 시퀀스를 한 번에 처리 → GPU에서 압도적으로 빠름, (2) 장거리 의존성: Self-Attention은 어떤 두 위치든 1 홉으로 연결, (3) 스케일링: 모델 크기·데이터·계산량에 성능이 예측 가능하게 비례(Scaling Laws). 결과적으로 데이터·GPU 많으면 많을수록 좋아져서 GPT·Claude 같은 초거대 모델이 가능해졌습니다.

Q3. GPT와 BERT의 차이와 쓰임새는?

GPT는 디코더 전용·단방향 어텐션으로 "다음 토큰 예측"을 학습 → 생성·대화·코딩에 강함. BERT는 인코더 전용·양방향 어텐션으로 "마스킹된 토큰 복원"을 학습 → 분류·NER·임베딩에 강함. 둘은 경쟁보다 분업: RAG 시스템에서 검색은 BERT 계열 임베딩, 생성은 GPT 계열이 쓰입니다.

Q4. RAG는 왜 필요하고 어떻게 구성하나요?

필요한 이유: (1) LLM은 학습 시점 이후를 모름 → 최신 뉴스·공시 반영 못 함, (2) 환각 리스크 → 자신 있게 거짓말, (3) 사내 전용 데이터는 모름. RAG는 질문을 임베딩 → 벡터DB에서 관련 문서 top-k 검색 → 그 문서를 프롬프트에 붙여 LLM에 넘김. 파인튜닝 없이도 최신·사내 데이터에 "접지"할 수 있고 출처를 명시해 환각을 억제합니다. 구성 요소: 임베딩 모델, 벡터DB(FAISS/Milvus/Pinecone), 청크 분할 전략, 재순위(reranker), 프롬프트 템플릿.

Q5. 금융권에서 LLM 쓸 때 가장 주의할 점은?

(1) 데이터 유출: 고객·내부 정보를 공개 API에 넣지 말 것. 반드시 마스킹 또는 사내 LLM. (2) 프롬프트 인젝션: 사용자 입력에 숨은 지시로 LLM 탈취 가능 → system·user 프롬프트 분리, 입력 sanitize. (3) 환각: 사실 확인 가능한 영역에만 사용, 반드시 출처 명시, 자신 없을 땐 모른다고 답하도록 지시. (4) 감사·규제: 모든 입출력 로깅, 금감원 검사 대응. (5) 자동 집행 금지: 주문·설정 변경 같은 실제 액션은 사람이 결정. LLM은 보조·초안·분류용으로만.

Q6. OMS 운영자가 LLM으로 할 수 있는 가장 가치 있는 일은?

개인적 체감으로는 (1) 로그 요약·분류: 수만 줄 로그 중 사람이 봐야 할 것만 추려 주고, 과거 유사 사례와 조치 매뉴얼까지 연결, (2) 장애 보고서 초안: 로그와 타임라인만 넣으면 감지-전파-원인-복구-재발방지 템플릿 자동 작성, (3) 신규 운영자 교육: 매뉴얼 Q&A 봇으로 새 멤버의 러닝커브 단축. 모두 "사람 검토 전 1차 가공"이라는 공통점이 있고, 반드시 수동 결정 단계를 남겨 둬야 합니다.

Q7. LLM은 어떻게 학습되나요? 사전학습·SFT·RLHF를 각각 설명해 보세요.

세 단계입니다. (1) 사전학습: 웹·책·코드 수조 토큰으로 "다음 토큰 예측"만 수없이 반복 → 문법·세상지식·추론 능력이 부수적으로 형성. 결과물은 질문에 답하기보다 문장을 이어쓰는 Base Model. (2) SFT(Supervised Fine-Tuning): 사람이 작성한 "질문 → 좋은 답변" 쌍 수만 건으로 지도학습 → 모델이 지시를 따르는 포맷을 익힘. (3) RLHF(또는 DPO): 두 답변 중 어느 쪽이 나은지 사람이 비교 → 보상모델 학습 → 그 보상을 최대화하도록 PPO/DPO로 정책을 강화학습. 유용성·무해성·정직성이 이 단계에서 만들어집니다. 추론 단계부터는 가중치가 더 이상 바뀌지 않습니다.

Q8. LLM은 왜 "어제 알려 준 걸 기억 못" 하나요? 어떻게 해결하나요?

세 가지 "모름"이 겹쳐 있어서입니다. (1) Training Cutoff: 학습 완료 시점 이후의 사실은 가중치에 없음. (2) Context Window: 한 번 호출에 넣을 수 있는 토큰에 상한. (3) 세션 무상태: API 호출은 매번 독립, 지난 호출을 모름. 해결은 "모델 바깥"에서 합니다. (a) 최신 정보는 RAG·웹 검색으로 주입, (b) 긴 문서는 요약·청크·관련 조각만 주입, (c) 과거 대화는 매 호출에 함께 보내거나 중요한 사실만 임베딩해 벡터DB에 적립 후 질의 때 재주입. ChatGPT UI의 "기억"도 결국 매 호출에 요약·사실을 재주입하는 앱 레벨 기능입니다.

Q9. 지식 그래프와 벡터 RAG는 어떻게 다르고 언제 뭘 쓰나요?

지식 그래프는 "엔티티─[관계]→엔티티"를 명시적으로 저장해 Cypher·SPARQL로 다단계 추론을 할 수 있습니다. 사실이 정확하고 환각이 극히 적지만 구축·유지 비용이 큽니다. 벡터 RAG는 문서를 임베딩해 코사인 유사도 top-k로 검색합니다. 구축이 쉽고 자연어 질의에 유연하지만 관계 추론이 약합니다. 쓰임새: 매뉴얼 Q&A·리서치 검색은 벡터 RAG로 시작, 공급망·규정 조문·그룹 지분 같은 관계 질의는 지식 그래프, 복합 금융 분석은 둘을 결합한 GraphRAG가 환각을 가장 많이 줄입니다.

Q10. 좋은 프롬프트의 조건은 무엇인가요?

저는 PROMPT 7원칙으로 정리합니다. Persona(역할), Reference(참고 자료 주입 — RAG), Objective(목표 명시), Manner(출력 포맷), Principles(모르면 모른다·추측 금지), Thoughts(단계적 추론 요구), Check(자기 검증). 핵심은 "LLM은 학습 시점·세션·창문 밖은 모른다"는 전제에서 시작해, 필요한 사실을 프롬프트로 떠먹여 주고, 모르면 거부하도록 강제하는 겁니다. 운영 프롬프트는 코드처럼 git에 커밋하고, 변경 시 회귀 테스트를 돌립니다.

Q11. LLM 에이전트와 하네스는 뭐가 다른가요? Cursor Agent는 어느 쪽인가요?

세 층으로 나눠서 설명합니다. ① LLM은 다음 토큰 확률만 뱉는 가중치 덩어리고 직접 아무것도 못 합니다. ② 에이전트 루프는 LLM이 "tool call JSON"을 뱉으면 실행하고 결과를 다시 넣어 주는 Thought-Action-Observation 반복문입니다(ReAct). ③ 하네스(Harness)는 그 루프를 안전하게 돌리기 위한 바깥 프레임 — 도구 레지스트리, 샌드박스, 승인 게이트, 타임아웃, 감사 로그, UI를 담당합니다. Cursor Agent·Claude Code·Devin·Aider는 전부 하네스이고, 그 안에서 돌아가는 LLM은 교체 가능합니다. 에이전트가 똑똑해 보이는 상당 부분은 모델이 아니라 하네스의 품질(좋은 도구 셋, 워크스페이스 인덱싱, 승인 UX)에서 나옵니다.

Q12. LLM 에이전트의 한계와 금융권에서의 사용 원칙을 말해 보세요.

핵심 한 문장: "에이전트는 결국 LLM이 결정하기 때문에 LLM의 모든 약점이 '실행된 행동'으로 번역된다." 구체적으로 (1) 환각의 행동화 — 없는 함수·파일을 자신 있게 호출, (2) 비결정성 — 같은 입력에 매번 다른 경로, (3) 도구 선택 실수, (4) 무한 루프·헛돌이, (5) context 희석, (6) 비용 폭증, (7) 프롬프트 인젝션이 "코드 실행 공격"으로 승격됨, (8) 평가 어려움, (9) 책임 소재 모호. 금융/OMS에서는 그래서 반드시: 집행은 결정론적 코드나 사람 승인으로 분리, 모든 tool call은 감사 로그, 샌드박스·화이트리스트·타임아웃·max_steps 상한, 되돌릴 수 없는 액션(주문·설정 변경·외부 메일)은 승인 게이트 필수. 에이전트는 "초안·분류·탐색"에만 쓰고 "집행·확정"은 사람이 합니다.
