이 장은 과정 전체를 "면접관의 질문"이라는 렌즈로 다시 꿰는 장입니다. C 언어, 메모리, 컴퓨터 구조, 운영체제, 네트워크, 데이터베이스, 자료구조, 그리고 금융권 전산직 특화 질문까지 110개가 넘는 질문에 대해 면접장에서 그대로 말할 수 있는 모범 답변, 이어지는 꼬리 질문, 그리고 "이렇게 답하면 감점"인 함정을 정리했습니다.

이 장에서 배울 것

  • 한국 IT 기업·금융권 전산직 기술 면접에서 자주 나오는 CS 질문 110여 개의 핵심 답변

  • 틀린 말, 과장, 모호한 표현처럼 감점으로 이어지는 답변 습관
  • 계정계·정보계·대외계, 배치와 온라인, 이중화·DR, 금융 보안 같은 금융권 특화 질문
  • 실전 모의 면접 세트로 스스로 점검하는 방법

질문을 펼치기 전에 먼저 소리 내어 30초~1분 동안 직접 답해 보십시오. 그다음 모범 답변과 비교해 빠진 키워드, 틀린 설명, 순서를 확인합니다. 모범 답변을 외우는 것이 목적이 아닙니다. 면접관은 외운 문장을 금방 알아채고, 꼬리 질문 하나로 이해 여부를 확인합니다. 각 답변의 "왜"를 이 과정의 해당 장에서 다시 찾아 읽으면 꼬리 질문에도 흔들리지 않습니다. 질문 옆 괄호의 장 번호가 관련 본문입니다.

포인터와 배열

포인터와 배열 (ch09, ch10, ch14, ch15)

Q1. 포인터란 무엇이고 왜 쓰나요?

모범 답변 포인터는 다른 객체의 메모리 주소를 값으로 저장하는 변수입니다. C의 함수 인자는 모두 값으로 복사되어 전달되므로, 함수가 호출한 쪽의 변수를 바꾸거나 큰 구조체를 복사 없이 넘기려면 주소를 넘겨야 합니다. 또 malloc으로 얻은 동적 메모리, 연결 리스트·트리 같은 자료구조, 배열과 문자열 처리, 함수 포인터를 이용한 콜백도 모두 포인터로 다룹니다. 포인터의 타입은 그 주소에서 몇 바이트를 어떤 형식으로 읽을지와, p + 1이 몇 바이트를 이동할지를 결정합니다.

꼬리 질문 "64비트 시스템에서 char *와 double *의 크기는?" → 둘 다 8바이트입니다. 포인터 크기는 가리키는 타입이 아니라 주소 공간의 크기로 정해집니다.

감점 포인트 "포인터는 주소다"로 끝내는 답. 포인터는 주소를 담는 변수이고 자신도 메모리에 주소를 가집니다. 타입의 의미(역참조 크기, 산술 단위)를 빠뜨리면 이해가 얕아 보입니다.

Q2. 배열과 포인터의 차이를 설명해 주세요.

모범 답변 배열은 같은 타입 원소들이 연속으로 놓인 메모리 블록 자체이고, 포인터는 주소 하나를 담는 변수입니다. 배열 이름은 대부분의 식에서 첫 원소의 주소로 변환(decay)되기 때문에 arr[i]와 p[i]가 똑같이 *(x + i)로 동작해 비슷해 보입니다. 하지만 sizeof arr는 배열 전체 크기, sizeof p는 포인터 크기이고, 배열 이름에는 대입할 수 없지만 포인터는 다른 주소를 가리키도록 바꿀 수 있습니다. 또 char arr[] = "abc"는 수정 가능한 복사본이지만 char *p = "abc"는 읽기 전용 문자열 상수를 가리켜 수정하면 미정의 동작입니다.

꼬리 질문 "함수 매개변수로 int a[]를 쓰면 sizeof a는?" → 매개변수의 배열 선언은 포인터로 조정되므로 포인터 크기(8)입니다. 그래서 배열을 넘길 때는 길이를 별도 인자로 넘깁니다.

감점 포인트 "배열 이름은 상수 포인터다"라고 단정하는 답. 흔한 비유지만 정확하지 않습니다(sizeof, &arr의 타입이 다름). "변환된다"고 말해야 합니다.

Q3. arr와 &arr의 차이는 무엇인가요?

모범 답변 int arr[5]에서 arr는 식에서 첫 원소의 주소로 변환되어 타입이 int *이고, &arr는 배열 전체의 주소로 타입이 int (*)[5]입니다. 두 값은 같은 주소를 나타내지만 타입이 다르므로 arr + 1은 4바이트, &arr + 1은 20바이트를 이동합니다. 2차원 배열을 함수에 넘길 때 int (*p)[5] 같은 배열 포인터가 필요한 이유도 이것입니다.

꼬리 질문 "sizeof와 & 말고 배열이 포인터로 변환되지 않는 경우는?" → 문자 배열을 문자열 리터럴로 초기화할 때(char s[] = "abc")입니다(표준이 정한 예외는 sizeof, 단항 &, 그리고 이 경우입니다).

감점 포인트 "둘은 완전히 같다"는 답.

Q4. Call by value와 call by reference의 차이는? C는 어느 쪽인가요?

모범 답변 값에 의한 호출은 인자의 값을 복사해 넘기므로 함수 안에서 매개변수를 바꿔도 호출한 쪽 변수는 바뀌지 않습니다. 참조에 의한 호출은 변수 자체에 대한 별칭을 넘겨 함수가 원본을 바꿀 수 있습니다. C는 오직 값에 의한 호출만 지원합니다. 원본을 바꾸려면 주소를 값으로 넘기고(포인터 값의 복사) 함수가 그 주소를 역참조하는 방식으로 참조 효과를 냅니다. C++의 참조(int &)가 진짜 참조에 의한 호출입니다.

꼬리 질문 "포인터를 넘겼는데 함수 안에서 p = malloc(...)을 해도 호출한 쪽 포인터가 안 바뀌는 이유는?" → 포인터 자체도 값으로 복사되었기 때문입니다. 포인터를 바꾸려면 이중 포인터(int **)를 넘겨야 합니다(ch15).

감점 포인트 "C에서 포인터를 넘기면 call by reference다"라고 단정. 면접관은 바로 위 꼬리 질문으로 확인합니다.

Q5. 이중 포인터는 언제 쓰나요?

모범 답변 포인터 변수 자체를 함수 안에서 바꿔야 할 때와, 포인터들의 배열을 다룰 때 씁니다. 대표적으로 함수가 메모리를 할당해 호출한 쪽 포인터에 돌려줄 때(int alloc_buf(char **out)), 연결 리스트의 헤드를 바꾸는 삽입·삭제 함수, main의 char **argv, 문자열 배열이 있습니다. 연결 리스트 삭제에서 Node **pp로 "현재 노드를 가리키는 포인터의 주소"를 따라가면 헤드와 중간 노드를 구분 없이 처리할 수 있습니다.

꼬리 질문 "char **argv와 char *argv[]는 같은가?" → 함수 매개변수에서는 같습니다(배열 매개변수의 포인터 조정).

감점 포인트 사용 예를 하나도 못 대는 답.

Q6. void 포인터는 무엇이고, 어떤 제약이 있나요?

모범 답변 void *는 타입 정보 없이 주소만 담는 범용 포인터입니다. 어떤 객체 포인터든 캐스팅 없이 void *로, 또 그 반대로 변환할 수 있어서 malloc, memcpy, qsort처럼 타입과 무관한 함수의 인터페이스에 쓰입니다. 가리키는 크기를 모르므로 직접 역참조할 수 없고, 표준 C에서는 포인터 산술도 할 수 없습니다(gcc는 확장으로 1바이트 단위 허용). 사용할 때는 실제 타입으로 변환해야 하며, 잘못된 타입으로 해석하는 책임은 프로그래머에게 있습니다.

꼬리 질문 "C에서 malloc 반환값을 캐스팅해야 하나?" → C에서는 필요 없고, 캐스팅하면 stdlib.h를 빠뜨렸을 때의 경고를 가릴 수 있어 오히려 권하지 않는 의견이 많습니다. C++에서는 필요합니다.

감점 포인트 "void 포인터는 NULL 포인터다"처럼 개념을 혼동.

Q7. 함수 포인터는 어디에 쓰나요?

모범 답변 함수 포인터는 함수의 주소를 저장해 실행 시점에 호출할 함수를 고를 수 있게 합니다. qsort의 비교 함수 같은 콜백, 거래 코드별 처리 함수를 표로 만드는 디스패치 테이블, 상태 머신, 플러그인 구조에 씁니다. 금융 전문 서버라면 {"2000", txn_deposit} 같은 표를 두면 거래 코드가 늘어도 if-else 사슬 없이 표에 한 줄을 추가하면 됩니다. 선언은 int (*fp)(int, int)처럼 괄호 위치가 중요하고, 보통 typedef로 읽기 쉽게 만듭니다.

꼬리 질문 "int *f(int)와 int (*f)(int)의 차이는?" → 앞은 int 포인터를 반환하는 함수 선언, 뒤는 int를 반환하는 함수를 가리키는 포인터 변수입니다.

감점 포인트 정의만 말하고 실제 용도를 못 대는 답.

Q8. 댕글링 포인터와 와일드 포인터는 무엇인가요?

모범 답변 댕글링 포인터는 이미 해제되었거나 수명이 끝난 메모리를 여전히 가리키는 포인터입니다. free 후의 포인터, 함수가 끝나 사라진 지역 변수의 주소를 반환한 경우가 대표적입니다. 와일드 포인터는 초기화되지 않아 임의의 주소를 담고 있는 포인터입니다. 둘 다 역참조하면 미정의 동작이며, 당장 오류 없이 다른 데이터를 오염시켜 재현이 어려운 버그가 됩니다. 포인터는 선언 시 NULL로 초기화하고, free 직후 NULL을 대입하며, 지역 변수의 주소는 반환하지 않는 습관으로 예방하고, ASan·Valgrind로 검출합니다.

꼬리 질문 "free(p); p = NULL;이면 완전히 안전한가?" → 같은 메모리를 가리키는 다른 포인터 복사본은 여전히 댕글링입니다. 소유권(누가 해제할 책임이 있는가)을 설계로 정해야 합니다.

감점 포인트 "free하면 포인터 값이 NULL이 된다"는 오해.

Q9. 프로세스의 메모리 구조(코드·데이터·BSS·힙·스택)를 설명해 주세요.

모범 답변 코드(.text) 영역에는 기계어가, 읽기 전용 데이터(.rodata)에는 문자열 상수와 const 전역이 있습니다. 데이터(.data) 영역에는 초기값이 있는 전역·static 변수가, BSS에는 초기값이 없거나 0인 전역·static 변수가 있으며 BSS는 실행 파일에 크기만 기록되고 적재 시 0으로 채워집니다. 힙은 malloc으로 실행 중에 할당하는 영역으로 낮은 주소에서 높은 쪽으로, 스택은 함수 호출마다 지역 변수·매개변수·반환 주소를 담는 프레임이 쌓이는 영역으로 높은 주소에서 낮은 쪽으로 자랍니다. 스택은 함수가 끝나면 자동으로 정리되고, 힙은 명시적으로 해제해야 합니다.

꼬리 질문 "BSS를 따로 두는 이유는?" → 0으로 채울 데이터를 실행 파일에 실제로 저장하지 않아 파일 크기와 적재 시간을 줄이기 위해서입니다.

감점 포인트 static 지역 변수를 스택에 있다고 답하는 실수. static 지역 변수는 데이터/BSS에 있습니다.

Q10. 스택과 힙의 차이는 무엇인가요?

모범 답변 스택은 함수 호출 단위로 자동 할당·해제되며, 스택 포인터를 움직이는 것만으로 할당이 끝나 매우 빠르고 캐시 지역성도 좋습니다. 대신 크기가 작고(리눅스 기본 8MB, 스레드 스택은 더 작을 수 있음) 함수가 끝나면 사라지므로 수명을 연장할 수 없습니다. 힙은 크기와 수명을 실행 중에 자유롭게 정할 수 있지만, 할당기가 빈 공간을 찾고 관리하는 비용이 있고, 해제를 잊으면 누수, 두 번 해제하면 메모리 손상이 생기며, 오래 쓰면 단편화가 생깁니다. 크기가 작고 수명이 함수 안에 한정되면 스택, 크거나 크기가 실행 중에 정해지거나 함수 밖으로 수명을 넘겨야 하면 힙을 씁니다.

꼬리 질문 "스택 오버플로는 언제 생기나?" → 깊은 재귀, 큰 지역 배열(예: char buf[16*1024*1024])로 스택 한도를 넘을 때 생기며, 보통 세그멘테이션 폴트로 종료됩니다.

감점 포인트 "힙이 스택보다 크다", "스택이 빠르다"만 말하고 이유(포인터 이동 vs 할당기 탐색, 자동 vs 수동 수명)를 못 대는 답.

Q11. malloc, calloc, realloc, free의 차이와 주의점은?

모범 답변 malloc(n)은 n바이트를 할당하고 내용은 초기화하지 않습니다. calloc(cnt, size)는 cnt×size바이트를 할당하고 0으로 채우며, 곱셈 오버플로를 검사하는 구현이 대부분입니다. realloc(p, n)은 크기를 바꾸며, 제자리에서 늘릴 수 없으면 새로 할당해 내용을 복사하고 옛 블록을 해제하므로 반환된 주소가 바뀔 수 있습니다. free는 할당받은 블록을 돌려주며 free(NULL)은 아무 일도 하지 않습니다. 모든 할당 함수는 실패 시 NULL을 반환하므로 검사해야 합니다.

꼬리 질문 "p = realloc(p, n);의 문제는?" → 실패하면 NULL이 반환되어 원래 블록의 주소를 잃어 누수가 됩니다. 임시 변수에 받아 성공했을 때만 대입합니다.

감점 포인트 "calloc은 malloc보다 항상 느리다"(OS가 0으로 준 새 페이지는 다시 지우지 않아도 되어 비슷할 수 있음)처럼 단정하거나, realloc이 항상 제자리 확장한다고 답하는 것.

Q12. 메모리 누수란 무엇이고, 어떻게 찾고 막나요?

모범 답변 동적으로 할당한 메모리를 더 이상 쓰지 않는데 해제하지 않고, 그 주소마저 잃어버려 다시 해제할 수 없게 된 상태입니다. 짧게 끝나는 프로그램은 종료 시 OS가 회수하지만, 수개월 떠 있는 온라인 서버에서는 메모리 사용량이 계속 늘어 결국 장애가 납니다. 오류 처리 경로에서 해제를 빠뜨리는 경우가 가장 흔하므로, 함수 끝에 정리 레이블을 두고 goto cleanup으로 모으는 패턴을 씁니다. 찾을 때는 Valgrind(memcheck)나 ASan의 LeakSanitizer를 쓰고, 운영 중에는 프로세스 RSS 추이를 모니터링합니다.

꼬리 질문 "누수가 없는데도 메모리 사용량이 줄지 않는 이유는?" → free한 메모리를 할당기가 OS에 바로 반환하지 않고 재사용을 위해 보관하거나, 힙 단편화 때문입니다.

감점 포인트 "프로그램이 끝나면 다 회수되니 괜찮다"는 태도.

Q13. double free와 use-after-free는 왜 위험한가요?

모범 답변 할당기는 해제된 블록을 내부 자유 목록에 연결해 관리하는데, 같은 블록을 두 번 해제하면 이 목록이 손상되어 이후 할당이 같은 메모리를 두 번 돌려주는 등 힙 전체가 망가질 수 있습니다. use-after-free는 해제된 블록이 다른 용도로 재할당된 뒤 옛 포인터로 읽고 쓰는 것이라, 전혀 관계없는 데이터를 오염시킵니다. 둘 다 미정의 동작이고 공격자가 힙 구조를 조작해 임의 코드 실행으로 이어지게 할 수 있는 대표적 보안 취약점입니다. 해제 후 NULL 대입, 소유권 규칙, ASan으로 예방·검출합니다.

꼬리 질문 "glibc가 double free를 탐지하는 경우가 있던데?" → 일부 단순한 경우를 검사해 free(): double free detected로 중단시키지만 모든 경우를 잡지는 못합니다.

감점 포인트 "그냥 프로그램이 죽는 것"으로만 설명하고 보안 측면을 빠뜨림.

Q14. 지역 변수의 주소를 반환하면 왜 안 되나요?

모범 답변 지역 변수는 함수의 스택 프레임에 있고, 함수가 반환하면 그 프레임은 해제되어 다음 함수 호출이 같은 공간을 덮어씁니다. 반환된 주소는 수명이 끝난 객체를 가리키는 댕글링 포인터가 되고, 역참조는 미정의 동작입니다. 당장은 값이 남아 있어 맞게 보이다가, 다른 함수를 한 번 호출하는 순간 값이 바뀌는 식으로 나타나 디버깅이 어렵습니다. 결과를 돌려주려면 호출자가 버퍼를 넘기거나, 동적 할당하거나, 값으로 반환합니다.

꼬리 질문 "static 지역 변수의 주소는 반환해도 되나?" → 수명이 프로그램 전체이므로 가능하지만, 함수가 재진입 불가능해지고 스레드 안전하지 않습니다(strtok, localtime의 문제).

감점 포인트 "컴파일러가 막아 준다". 경고는 주지만 컴파일은 됩니다.

Q15. 구조체 패딩이란 무엇이고 왜 생기나요?

모범 답변 CPU는 N바이트 데이터를 N의 배수 주소에서 읽을 때 가장 효율적이고, 일부 아키텍처는 정렬되지 않은 접근을 아예 허용하지 않습니다. 그래서 컴파일러는 구조체 멤버가 각자의 정렬 요구를 만족하도록 멤버 사이에 빈 바이트를 넣고, 구조체 배열에서도 정렬이 유지되도록 끝에도 패딩을 넣습니다. 예를 들어 {char c; int i; char d;}는 64비트 리눅스에서 6바이트가 아니라 12바이트입니다. 큰 멤버부터 배치하면 패딩을 줄일 수 있고, 파일·전문에 구조체를 그대로 쓰면 플랫폼마다 패딩이 달라 호환성이 깨지므로 명시적으로 직렬화해야 합니다.

꼬리 질문 "패딩 바이트의 값은?" → 정해지지 않았습니다(쓰레기 값). 그래서 memcmp로 구조체를 비교하면 안 되고, 전송 전에 memset으로 0을 채우기도 합니다(정보 유출 방지).

감점 포인트 "#pragma pack(1)을 쓰면 해결된다"고만 답하는 것. 정렬 위반 접근 성능 저하나 SIGBUS 위험을 함께 말해야 합니다.

Q16. 메모리 단편화란 무엇인가요?

모범 답변 외부 단편화는 전체 빈 메모리는 충분한데 작은 조각으로 흩어져 있어 큰 연속 블록을 할당하지 못하는 현상이고, 내부 단편화는 할당 단위나 정렬 때문에 요청보다 크게 할당되어 블록 안에 쓰지 않는 공간이 생기는 현상입니다. 크기가 다양한 할당·해제를 오래 반복하는 서버에서 외부 단편화가 문제가 됩니다. 고정 크기 객체는 메모리 풀로, 수명이 같은 객체들은 아레나(한꺼번에 해제)로 관리해 줄이고, OS 수준에서는 페이징이 물리 메모리의 외부 단편화를 해결합니다.

꼬리 질문 "페이징은 단편화를 완전히 없애나?" → 외부 단편화는 없애지만 마지막 페이지의 남는 공간 같은 내부 단편화는 생깁니다.

감점 포인트 내부와 외부 단편화를 구분하지 못함.

Q17. sizeof는 함수인가요? 언제 값이 정해지나요?

모범 답변 sizeof는 함수가 아니라 연산자이며, 결과 타입은 size_t입니다. 피연산자가 가변 길이 배열(VLA)이 아니면 컴파일 시점에 상수로 계산되고, 피연산자 식은 실제로 평가되지 않습니다. 그래서 sizeof(i++)는 i를 증가시키지 않습니다. 변수에는 괄호 없이 sizeof x로 쓸 수 있고, 타입에는 괄호가 필요합니다. malloc(n * sizeof *p)처럼 변수 기준으로 쓰면 타입이 바뀌어도 코드가 안전합니다.

꼬리 질문 "printf("%d", sizeof(int))의 문제는?" → size_t는 64비트에서 8바이트 부호 없는 정수라 %d와 맞지 않아 미정의 동작입니다. %zu를 씁니다.

감점 포인트 "sizeof는 런타임에 메모리 크기를 재는 함수"라는 답.

Q18. 문자열 처리에서 버퍼 오버플로를 막는 방법은?

모범 답변 버퍼 오버플로는 버퍼 크기보다 많은 데이터를 써서 인접 메모리(다른 변수, 반환 주소)를 덮어쓰는 것으로, 프로그램 오동작과 원격 코드 실행 취약점의 원인입니다. 길이를 검사하지 않는 gets, strcpy, strcat, sprintf, 폭 지정 없는 scanf("%s")를 쓰지 않고, fgets, snprintf, 폭 지정 %31s처럼 크기를 받는 함수를 씁니다. strncpy는 NUL 종료를 보장하지 않으므로 주의합니다. 외부 입력의 길이 필드는 반드시 버퍼 크기와 비교하고, 컴파일러의 스택 보호(-fstack-protector-strong), _FORTIFY_SOURCE, ASLR, NX 같은 완화 기법을 함께 씁니다.

꼬리 질문 "snprintf의 반환값은 무엇을 의미하나?" → 버퍼가 충분했다면 썼을 문자 수입니다. 반환값이 버퍼 크기 이상이면 잘렸다는 뜻이므로 검사해야 합니다.

감점 포인트 "strncpy를 쓰면 안전하다"고 단정.

키워드와 언어 규칙

static, const, volatile, extern, UB (ch13, ch19, ch20, ch31)

Q19. static 키워드의 세 가지 의미를 설명해 주세요.

모범 답변 첫째, 함수 안의 static 지역 변수는 정적 저장 기간을 가져 프로그램 시작부터 끝까지 존재하고, 초기화는 한 번만 되며, 함수 호출 사이에 값이 유지됩니다. 둘째, 파일 범위의 전역 변수나 함수에 static을 붙이면 내부 링크(internal linkage)가 되어 그 소스 파일 안에서만 보이므로, 다른 파일과 이름이 충돌하지 않고 정보 은닉이 됩니다. 셋째, C99부터 배열 매개변수의 int a[static 10]은 "최소 10개 원소를 가진 배열이 전달된다"는 약속을 컴파일러에 알려 줍니다. 실무에서 가장 중요한 것은 두 번째로, 모듈 내부 함수는 모두 static으로 숨기는 것이 좋은 습관입니다.

꼬리 질문 "static 지역 변수를 쓰는 함수는 멀티스레드에서 안전한가?" → 모든 스레드가 같은 변수를 공유하므로 동기화 없이는 안전하지 않습니다.

감점 포인트 지역 변수용 의미 하나만 말하는 답. 링크 범위 제한이 핵심입니다.

Q20. const의 의미와 const int *p, int *const p의 차이는?

모범 답변 const는 그 lvalue를 통해 객체를 수정하지 않겠다는 약속이며 컴파일러가 위반을 오류로 잡아 줍니다. const int *p는 "가리키는 int가 const"로, *p = 1은 안 되지만 p가 다른 곳을 가리키게 할 수는 있습니다. int *const p는 "포인터 자체가 const"로, 가리키는 값은 바꿀 수 있지만 p를 바꿀 수 없습니다. const가 *의 왼쪽에 있으면 대상, 오른쪽에 있으면 포인터를 고정한다고 읽으면 됩니다. 함수 매개변수의 const char *는 "이 함수는 문자열을 바꾸지 않는다"는 인터페이스 문서 역할도 합니다.

꼬리 질문 "const 변수를 포인터 캐스팅으로 바꾸면?" → 원래 const로 정의된 객체를 수정하는 것은 미정의 동작입니다. 읽기 전용 메모리에 있으면 세그폴트가 납니다.

감점 포인트 C의 const 변수를 C++처럼 "컴파일 시점 상수"라고 답하는 것. C에서 const int n = 10;은 상수 식이 아니어서 전역 배열 크기 등에 쓸 수 없습니다.

Q21. volatile은 무엇이고 언제 쓰나요? 멀티스레드 동기화에 쓸 수 있나요?

모범 답변 volatile은 그 객체가 프로그램이 모르는 방식으로 바뀌거나 접근 자체가 부수 효과를 가질 수 있으니, 읽기·쓰기를 생략하거나 레지스터에 캐싱하지 말고 코드에 적힌 대로 매번 메모리에 접근하라고 컴파일러에 알리는 한정자입니다. 하드웨어 레지스터(메모리 맵 I/O), 시그널 핸들러가 바꾸는 플래그(volatile sig_atomic_t), setjmp/longjmp 사이의 지역 변수에 씁니다. 하지만 원자성도, CPU 간 메모리 순서(가시성)도 보장하지 않으므로 멀티스레드 동기화에는 쓸 수 없습니다. 스레드 간에는 뮤텍스나 C11 _Atomic/stdatomic.h를 써야 합니다.

꼬리 질문 "volatile int cnt; cnt++;가 두 스레드에서 안전하지 않은 이유는?" → cnt++는 읽기-증가-쓰기 세 단계로, 두 스레드가 같은 값을 읽고 각각 써서 증가 하나가 사라질 수 있습니다.

감점 포인트 "volatile을 붙이면 스레드 안전해진다". 가장 흔한 감점 답변입니다.

Q22. extern은 무엇이고 선언과 정의의 차이는?

모범 답변 선언은 이름과 타입을 알려 주는 것이고, 정의는 실제로 저장 공간을 만들거나 함수 몸체를 제공하는 것입니다. 정의는 프로그램 전체에 하나만 있어야 하고 선언은 여러 번 해도 됩니다. extern int g_count;는 "어딘가에 정의된 전역 변수가 있다"는 선언이므로 헤더에 두고, 정의 int g_count = 0;은 한 .c 파일에만 둡니다. 헤더에 정의를 넣으면 여러 파일이 포함할 때 multiple definition 링크 오류가 납니다(gcc 10부터 -fno-common이 기본이라 초기값 없는 정의도 오류).

꼬리 질문 "함수 선언에 extern을 붙여야 하나?" → 함수는 기본이 외부 링크라 생략해도 같습니다.

감점 포인트 선언과 정의를 구분하지 못함.

Q23. 미정의 동작(UB), 미지정 동작, 구현 정의 동작의 차이는?

모범 답변 구현 정의 동작은 표준이 여러 선택지를 허용하되 컴파일러가 무엇을 택했는지 문서화해야 하는 것으로, int의 크기, char의 부호, 음수의 오른쪽 시프트 결과 등이 있습니다. 미지정 동작은 몇 가지 가능성 중 하나가 일어나지만 문서화 의무가 없는 것으로, 함수 인자의 평가 순서가 대표적입니다. 미정의 동작은 표준이 아무 요구도 하지 않는 것으로, 부호 있는 정수 오버플로, 배열 범위 밖 접근, NULL 역참조, 초기화 안 된 변수 읽기, 한 식에서 같은 변수를 순서 없이 두 번 수정(i = i++) 등이 있습니다. UB가 있으면 최적화 컴파일러가 "일어나지 않는다"고 가정해 코드를 지우거나 바꿀 수 있어서, 결과가 컴파일 옵션마다 달라집니다.

꼬리 질문 "부호 없는 정수 오버플로도 UB인가?" → 아닙니다. 부호 없는 정수는 2N으로 나눈 나머지로 감싸이도록(wrap) 정의되어 있습니다.

감점 포인트 "UB는 그냥 결과값이 이상하게 나오는 것"이라는 답. 프로그램 전체 동작이 보장되지 않는다는 점과 최적화와의 관계를 말해야 합니다.

Q24. i = i++ + ++i;의 결과는?

모범 답변 결과를 말할 수 없습니다. 하나의 식 안에서 같은 객체 i를 순서가 정해지지 않은 채(시퀀스 포인트 없이) 여러 번 수정하므로 미정의 동작입니다. 컴파일러마다, 최적화 옵션마다 다른 값이 나올 수 있고, 어떤 값이 나오든 그것은 "정답"이 아닙니다. 실무 코드에서는 증감 연산자를 다른 연산과 섞지 않고 별도 문장으로 씁니다.

꼬리 질문 "printf("%d %d", i++, i++)는?" → 함수 인자 사이에도 순서가 정해져 있지 않아 역시 UB입니다.

감점 포인트 특정 숫자를 계산해 답하는 것. 면접관은 UB를 알아보는지를 묻고 있습니다.

Q25. 매크로 함수와 inline 함수의 차이는?

모범 답변 매크로는 전처리기가 컴파일 전에 텍스트를 치환하는 것이라 타입 검사가 없고, 인자가 여러 번 평가되며, 괄호를 빠뜨리면 연산자 우선순위 문제가 생깁니다. 예를 들어 #define SQ(x) x*x에서 SQ(a+1)은 a+1*a+1이 되고, #define MAX(a,b) ((a)>(b)?(a):(b))에 MAX(i++, j)를 넣으면 i가 두 번 증가할 수 있습니다. inline 함수는 진짜 함수라 타입 검사와 한 번 평가가 보장되고 디버거로 추적할 수 있으며, 호출 비용은 컴파일러가 인라인 확장으로 없앨 수 있습니다. 그래서 타입에 무관한 코드 생성이나 __FILE__/__LINE__이 필요한 로깅 외에는 inline 함수를 권합니다.

꼬리 질문 "inline을 붙이면 반드시 인라인되나?" → 아닙니다. 힌트일 뿐이고 컴파일러가 판단합니다.

감점 포인트 매크로의 부작용 예를 하나도 못 대는 답.

Q26. 헤더 가드는 왜 필요한가요?

모범 답변 같은 헤더가 한 번역 단위에 여러 경로로 두 번 포함되면 구조체·typedef 정의가 중복되어 컴파일 오류가 납니다. #ifndef X_H / #define X_H / ... / #endif로 감싸면 두 번째 포함부터는 내용이 무시됩니다. #pragma once도 대부분의 컴파일러가 지원하지만 표준은 아닙니다. 헤더 가드는 한 번역 단위 안의 중복만 막을 뿐, 여러 .c 파일에 정의가 중복되는 링크 오류는 막지 못하므로 헤더에는 선언만 둡니다.

꼬리 질문 "헤더 가드 매크로 이름을 밑줄+대문자로 시작하면?" → _FOO_H처럼 밑줄+대문자는 구현용 예약 식별자라 피해야 합니다.

감점 포인트 헤더 가드가 링크 단계의 중복 정의도 막는다고 답하는 것.

Q27. 재귀 함수의 장단점과 주의점은?

모범 답변 재귀는 트리 순회, 분할 정복처럼 문제 자체가 재귀적일 때 코드를 간결하고 정확하게 만듭니다. 하지만 호출마다 스택 프레임이 쌓이므로 깊이가 크면 스택 오버플로가 나고, 함수 호출 비용이 있으며, 피보나치 단순 재귀처럼 같은 계산을 반복하면 지수 시간이 됩니다. 반드시 종료 조건이 있어야 하고, 깊이가 입력에 비례해 커질 수 있는 곳(예: 연결 리스트 길이, 외부 입력의 중첩)에는 반복문이나 명시적 스택으로 바꿉니다. 꼬리 재귀는 컴파일러가 반복으로 최적화할 수 있지만 C 표준은 이를 보장하지 않습니다.

꼬리 질문 "피보나치를 효율적으로 하려면?" → 메모이제이션이나 반복문으로 O(n), 행렬 거듭제곱으로 O(log n)입니다.

감점 포인트 스택 오버플로 위험을 언급하지 않는 답.

Q28. setjmp/longjmp는 무엇이고 왜 조심해야 하나요?

모범 답변 setjmp는 현재 실행 상태(스택 포인터, 레지스터 등)를 저장하고, longjmp는 그 지점으로 비지역 점프를 해 여러 함수 호출 단계를 한 번에 빠져나옵니다. C에서 예외 처리를 흉내 낼 때 쓰지만, 중간 함수들의 정리 코드(free, close, 잠금 해제)가 실행되지 않아 누수와 잠금 미해제가 생기고, setjmp 이후 바뀐 비-volatile 지역 변수의 값은 보장되지 않으며, 이미 반환한 함수의 jmp_buf로 점프하면 미정의 동작입니다. 금융 서버 코드에서는 오류 코드 반환과 정리 레이블 방식을 쓰는 것이 일반적입니다.

꼬리 질문 "시그널 핸들러에서 빠져나올 때는?" → 시그널 마스크까지 저장·복원하는 sigsetjmp/siglongjmp를 씁니다.

감점 포인트 정리 코드가 건너뛰어진다는 핵심 위험을 빠뜨림.

컴파일 과정과 링크

컴파일·링크·빌드 (ch01, ch19, ch31)

Q29. 소스 코드가 실행 파일이 되기까지의 과정을 설명해 주세요.

모범 답변 네 단계입니다. 전처리기가 #include를 펼치고 매크로를 치환하며 조건부 컴파일을 처리해 순수 C 코드(.i)를 만듭니다. 컴파일러가 구문·타입을 검사하고 최적화한 뒤 어셈블리(.s)를 만듭니다. 어셈블러가 이를 기계어 오브젝트 파일(.o)로 바꾸는데, 이때 다른 파일의 함수 주소는 아직 모르므로 심볼 테이블과 재배치 정보로 남겨 둡니다. 마지막으로 링커가 여러 오브젝트와 라이브러리를 모아 미해결 심볼을 연결하고 주소를 확정해 실행 파일을 만듭니다. 실행 시에는 로더가 실행 파일을 메모리에 올리고, 동적 라이브러리는 동적 링커가 연결합니다.

꼬리 질문 "헤더 파일은 컴파일되나?" → 따로 컴파일되지 않고 전처리 단계에서 포함한 .c 파일의 일부로 컴파일됩니다.

감점 포인트 "컴파일하면 실행 파일이 나온다"로 단계를 뭉뚱그림.

Q30. 정적 링크와 동적 링크의 차이는?

모범 답변 정적 링크는 링크 시점에 라이브러리의 필요한 오브젝트 코드를 실행 파일에 복사하므로 실행 파일이 자기 완결적이고 배포 환경에 의존하지 않지만, 크기가 크고 라이브러리 수정 시 재링크가 필요합니다. 동적 링크는 실행 시 동적 링커가 공유 라이브러리를 적재·연결하므로 여러 프로세스가 코드 페이지를 공유해 메모리를 아끼고 라이브러리만 교체해 수정을 반영할 수 있지만, 실행 환경에 맞는 버전이 있어야 하고 PLT/GOT를 통한 간접 호출 비용이 약간 있습니다. 동적 라이브러리는 -fPIC로 만들어 어느 주소에 적재되어도 코드를 고치지 않고 공유할 수 있게 합니다.

꼬리 질문 "실행 시 라이브러리를 못 찾는 오류는 어떻게 해결하나?" → ldd로 확인하고 rpath, ldconfig 등록, 또는 LD_LIBRARY_PATH로 경로를 지정합니다.

감점 포인트 장단점 한쪽만 말하는 답.

Q31. undefined reference와 multiple definition 오류의 원인은?

모범 답변 둘 다 링크 오류입니다. undefined reference는 선언은 있지만 정의를 링크 입력 어디에서도 찾지 못한 것으로, 정의 누락, 오브젝트나 라이브러리를 빠뜨림, 라이브러리를 사용하는 오브젝트보다 앞에 둔 링크 순서, static 함수, C/C++ 이름 맹글링 차이가 원인입니다. multiple definition은 같은 외부 심볼의 정의가 둘 이상인 것으로, 헤더에 변수나 함수 정의를 넣고 여러 .c에서 포함한 경우가 대표적입니다. nm으로 심볼의 정의(T/D)와 참조(U)를 확인해 진단합니다.

꼬리 질문 "링크 순서가 왜 중요한가?" → GNU ld는 아카이브를 왼쪽에서 오른쪽으로 한 번 훑으며 그 시점의 미해결 심볼만 해결하기 때문입니다.

감점 포인트 컴파일 오류와 링크 오류를 구분하지 못함.

Q32. make는 어떻게 동작하나요?

모범 답변 Makefile에 타깃, 선행조건, 레시피로 의존성 그래프를 기술하면, make는 기본 타깃부터 재귀적으로 선행조건을 최신화하고, 선행조건 중 하나라도 타깃보다 수정 시각이 새로우면 레시피를 실행합니다. 그래서 바뀐 파일과 그에 의존하는 것만 다시 빌드합니다. 헤더 의존성은 손으로 관리하면 빠지기 쉬우므로 gcc -MMD -MP로 자동 생성하고, clean 같은 파일이 아닌 타깃은 .PHONY로 선언합니다.

꼬리 질문 "make -j에서만 빌드가 깨지는 이유는?" → 선언되지 않은 의존성이 있어 순차 빌드에서는 우연히 순서가 맞았던 것입니다.

감점 포인트 "Makefile은 컴파일 명령을 모아 둔 스크립트"라고만 답함.

Q33. 최적화 옵션을 켰을 때 디버깅이 어려운 이유와 대처는?

모범 답변 -O2에서는 변수가 레지스터에만 있거나 아예 사라지고, 함수가 인라인되며, 코드 순서가 재배치되어 소스 줄과 기계어가 1:1로 대응하지 않습니다. 그래서 gdb에서 변수가 <optimized out>으로 보이거나 단계 실행이 앞뒤로 튑니다. 운영 바이너리도 -g로 디버그 정보를 넣어 두면(성능 영향 없음, 크기만 증가) 코어 덤프 분석이 훨씬 쉬워지고, 개발 중에는 -Og를 씁니다. 또 최적화에서만 재현되는 버그는 대부분 UB이므로 UBSan·ASan을 먼저 돌려 봅니다.

꼬리 질문 "디버그 정보를 운영 서버에 두기 싫다면?" → objcopy --only-keep-debug로 분리해 별도 보관하고, 운영 바이너리는 strip합니다.

감점 포인트 "운영은 -O0으로 빌드하면 된다"는 답.

Q34. 전처리기의 #if 0과 주석의 차이, 조건부 컴파일의 용도는?

모범 답변 블록 주석 /* */는 중첩되지 않아 이미 주석이 있는 코드를 감싸면 깨지지만, #if 0 ... #endif는 중첩된 주석이 있어도 안전하게 코드를 비활성화합니다. 조건부 컴파일은 플랫폼별 코드(#ifdef _AIX), 디버그 전용 코드(#ifndef NDEBUG), 기능 토글, 헤더 가드에 쓰입니다. 다만 분기가 많아지면 모든 조합을 테스트하기 어려우므로 플랫폼 차이는 한 모듈로 모으는 것이 좋습니다.

꼬리 질문 "assert를 운영 코드의 입력 검증에 쓰면 안 되는 이유는?" → NDEBUG가 정의되면 assert 문이 통째로 사라지기 때문입니다. 입력 검증은 항상 실행되는 코드로 해야 합니다.

감점 포인트 assert와 오류 처리를 같은 것으로 취급.

자료형, 정수와 부동소수점

데이터 표현 (ch02, ch20, ch21)

Q35. 2의 보수란 무엇이고 왜 쓰나요?

모범 답변 2의 보수는 음수를 "모든 비트를 뒤집고 1을 더한 값"으로 표현하는 방식입니다. 이렇게 하면 덧셈 회로 하나로 양수·음수 덧셈과 뺄셈(빼기는 보수를 더하기)을 모두 처리할 수 있고, 0의 표현이 하나뿐이라 부호-크기 방식의 +0/−0 문제가 없습니다. 8비트 기준 범위는 −128~127로 음수 쪽이 하나 더 많습니다. 그래서 INT_MIN의 절댓값은 int로 표현할 수 없고 -INT_MIN은 오버플로입니다. C23부터 표준이 2의 보수를 의무화했고, 그 전에도 사실상 모든 플랫폼이 2의 보수입니다.

꼬리 질문 "−1을 8비트 2의 보수로?" → 1은 00000001, 뒤집으면 11111110, 1을 더해 11111111(0xFF)입니다.

감점 포인트 1의 보수와 혼동.

Q36. 정수 오버플로는 어떻게 방지하나요? 금액 계산에서는?

모범 답변 부호 있는 정수의 오버플로는 미정의 동작이므로 연산 전에 범위를 검사해야 합니다. 예를 들어 a + b 전에 b > 0 && a > LLONG_MAX - b를 검사하거나, gcc/clang의 __builtin_add_overflow를 씁니다. 연산 후에 결과가 음수가 되었는지 보는 방식은 컴파일러가 검사를 지울 수 있어 틀린 방법입니다. 금액은 원 단위 long long(약 ±922경)으로 다루고, 곱셈(금액 × 이율)이 있는 곳은 중간 결과 범위를 따져 한도를 두며, 업무 한도(1회·1일 이체 한도)로도 상한을 제한합니다.

꼬리 질문 "int 두 개를 곱해 long long에 담으면 안전한가?" → 아닙니다. int * int는 int로 계산된 뒤 변환되므로 이미 넘친 값이 들어갑니다. 한쪽을 먼저 (long long)으로 캐스팅해야 합니다.

감점 포인트 "결과가 음수면 오버플로"라는 사후 검사.

Q37. 부동소수점으로 금액을 계산하면 안 되는 이유는?

모범 답변 float/double은 IEEE 754 이진 부동소수점이라 0.1 같은 십진 소수를 정확히 표현할 수 없고, 가장 가까운 이진 근사값을 저장합니다. 그래서 0.1 + 0.2 == 0.3이 거짓이 되고, 많은 건을 더하면 오차가 누적되며, 덧셈 순서에 따라 결과가 달라집니다. 금융은 1원 단위까지 정확해야 하고 대사로 검증하므로 금액은 원(또는 최소 통화 단위) 정수로 저장·계산하고, 이율은 bp 같은 정수 배율로 표현하며, 반올림·절사 규칙을 명시적으로 적용합니다. 외화처럼 소수가 필요하면 고정 소수점(예: 1/100 단위 정수)이나 십진 연산 라이브러리를 씁니다.

꼬리 질문 "double의 유효 숫자는 몇 자리?" → 가수 52비트(+숨은 1비트)로 십진 약 15~17자리입니다. 큰 금액에 소수 계산이 섞이면 아래 자리부터 정밀도를 잃습니다.

감점 포인트 "double은 정밀도가 높으니 괜찮다"는 답.

Q38. 부호 있는 정수와 부호 없는 정수를 섞으면 어떤 문제가 생기나요?

모범 답변 같은 크기의 signed와 unsigned를 연산하면 일반 산술 변환으로 signed가 unsigned로 바뀝니다. 그래서 -1 < 1u는 −1이 0xFFFFFFFF로 바뀌어 거짓이 되고, for (size_t i = n - 1; i >= 0; i--)는 i가 0 다음에 최대값으로 감싸져 무한 루프가 됩니다. 길이가 음수로 계산될 수 있는 곳에서 unsigned를 쓰면 엄청나게 큰 값이 되어 버퍼 오버플로로 이어지기도 합니다. -Wsign-compare, -Wsign-conversion 경고를 켜고, 비교 전에 범위를 확인합니다.

꼬리 질문 "strlen(a) - strlen(b) < 0은?" → size_t끼리의 뺄셈은 음수가 될 수 없어 항상 거짓입니다.

감점 포인트 정수 승격·일반 산술 변환을 전혀 모름.

Q39. 비트 연산은 어디에 쓰나요? 플래그 설계 예를 들어 주세요.

모범 답변 여러 개의 참/거짓 상태를 한 정수의 비트에 담아 저장 공간과 비교 비용을 줄일 때 씁니다. 예를 들어 계좌 상태를 #define ACC_FROZEN 0x01, ACC_DORMANT 0x02, ACC_LOSS 0x04(사고 신고)로 정의하고, 설정은 flags |= ACC_FROZEN, 해제는 flags &= ~ACC_FROZEN, 검사는 flags & ACC_FROZEN, 토글은 ^=로 합니다. 출금 가능 여부를 (flags & (ACC_FROZEN | ACC_LOSS)) == 0 한 번으로 판단할 수 있습니다. 비트 연산은 부호 없는 타입으로 하는 것이 안전합니다(음수 시프트·부호 비트 문제).

꼬리 질문 "2의 거듭제곱인지 판별하려면?" → n != 0 && (n & (n - 1)) == 0입니다.

감점 포인트 &와 &&를 혼동.

Q40. char는 signed인가요 unsigned인가요?

모범 답변 구현 정의입니다. x86 리눅스·윈도우는 signed, ARM 리눅스와 AIX(POWER)는 unsigned가 기본입니다. 그래서 char c = 0xFF;의 값이 −1일 수도 255일 수도 있고, fgetc의 반환값을 char에 담아 EOF와 비교하는 코드는 플랫폼에 따라 0xFF 바이트에서 멈추거나 EOF를 영원히 못 찾습니다. 바이트 데이터는 unsigned char, getc 반환값은 int, isdigit 같은 함수에는 (unsigned char)로 변환해 넘깁니다.

꼬리 질문 "isdigit(c)에 음수 char를 넘기면?" → EOF 이외의 음수는 미정의 동작입니다.

감점 포인트 "char는 항상 signed"라는 단정.

Q41. 엔디안이란 무엇이고, 시스템의 엔디안을 확인하는 코드를 작성해 보세요.

모범 답변 엔디안은 2바이트 이상의 데이터를 메모리에 저장하는 바이트 순서입니다. 최상위 바이트를 낮은 주소에 두면 빅 엔디안, 최하위 바이트를 낮은 주소에 두면 리틀 엔디안입니다. 네트워크 프로토콜은 빅 엔디안(네트워크 바이트 순서)으로 정해져 있어 htonl/ntohl로 변환하고, 바이너리 파일이나 공유 메모리를 다른 아키텍처와 주고받을 때도 변환이 필요합니다. 확인은 정수 1의 첫 바이트를 보면 됩니다.

꼬리 질문 "같은 기계 안에서 비트 연산(x >> 8)도 엔디안의 영향을 받나?" → 받지 않습니다. 시프트는 값에 대한 연산이고, 엔디안은 메모리에 바이트로 저장할 때만 드러납니다.

감점 포인트 비트 순서와 바이트 순서를 혼동하거나, 문자열(char 배열)도 엔디안에 따라 뒤집힌다고 답하는 것.

Q42. CPU 캐시와 지역성을 설명해 주세요.

모범 답변 CPU는 DRAM보다 수백 배 빠르기 때문에, 그 사이에 작고 빠른 SRAM 캐시를 L1·L2·L3 단계로 둡니다. 캐시는 64바이트 캐시 라인 단위로 데이터를 가져오고, 최근에 쓴 데이터는 다시 쓸 확률이 높다는 시간 지역성과, 쓴 주소 근처를 곧 쓸 확률이 높다는 공간 지역성에 기대어 동작합니다. 그래서 배열 순차 접근, 2차원 배열의 행 우선 순회, 연속 메모리 자료구조가 빠르고, 연결 리스트나 큰 간격의 접근은 캐시 미스로 느립니다. 같은 알고리즘이라도 접근 패턴만 바꿔 수 배 빨라지는 경우가 많습니다.

꼬리 질문 "캐시 미스의 종류는?" → 처음 접근하는 강제(compulsory) 미스, 용량이 부족한 용량(capacity) 미스, 같은 세트에 매핑되어 밀려나는 충돌(conflict) 미스가 있습니다(멀티코어에서는 일관성 미스도).

감점 포인트 캐시를 "자주 쓰는 데이터를 저장하는 곳"으로만 설명하고 라인 단위·지역성을 빠뜨림.

Q43. 파이프라인과 분기 예측은 무엇인가요?

모범 답변 파이프라인은 명령어 처리를 인출·해독·실행·메모리·쓰기 같은 단계로 나눠, 여러 명령어를 단계별로 겹쳐 실행해 처리량을 높이는 기법입니다. 분기 명령은 결과가 나오기 전에 다음 명령을 인출해야 하므로, CPU는 분기 방향을 예측해 미리 실행하고 틀리면 파이프라인을 비우고 다시 시작합니다(수십 사이클 손해). 그래서 예측하기 어려운 무작위 분기가 많은 루프는 느리고, 정렬된 데이터를 처리하는 같은 루프가 더 빠른 현상이 생깁니다. 성능이 중요한 곳에서는 분기를 줄이거나 조건부 이동 같은 분기 없는 코드로 바꿉니다.

꼬리 질문 "파이프라인 해저드의 종류는?" → 구조 해저드, 데이터 해저드(앞 명령의 결과가 필요), 제어 해저드(분기)입니다.

감점 포인트 파이프라인이 명령 하나의 실행 시간을 줄인다고 답하는 것(처리량을 늘리는 것).

Q44. 정렬(alignment)이 맞지 않는 메모리 접근은 왜 문제가 되나요?

모범 답변 4바이트 정수가 4의 배수 주소에 있지 않으면 하나의 값이 두 개의 메모리 워드나 캐시 라인에 걸쳐 CPU가 두 번 접근해야 합니다. x86은 하드웨어가 처리해 주지만 느려질 수 있고, 일부 RISC 아키텍처는 SIGBUS 예외를 일으킵니다. 또 C 표준에서 잘못 정렬된 포인터로 접근하는 것은 미정의 동작입니다. 전문 버퍼의 임의 위치를 *(int *)(buf + 3)처럼 읽는 코드가 대표적인 문제이고, memcpy로 정렬된 변수에 복사해 읽으면 안전하며 컴파일러가 효율적인 명령으로 바꿔 줍니다.

꼬리 질문 "malloc이 반환하는 주소의 정렬은?" → 모든 기본 타입에 맞도록 정렬되어 있습니다(보통 16바이트).

감점 포인트 "x86에서는 아무 문제 없다"고만 답함.

Q45. 32비트와 64비트 시스템의 차이는? LP64와 LLP64는?

모범 답변 가장 큰 차이는 주소(포인터) 크기로, 32비트는 4GB 주소 공간에 제한되고 64비트는 사실상 제한이 없습니다. 64비트 CPU는 레지스터도 64비트라 큰 정수 연산이 빠르고 레지스터 개수도 늘어납니다. 데이터 모델은 플랫폼마다 달라서 64비트 리눅스·유닉스는 LP64(long과 포인터가 64비트), 64비트 윈도우는 LLP64(long은 32비트, long long과 포인터가 64비트)입니다. 그래서 long에 포인터나 큰 금액을 담는 코드는 이식성이 없고, int64_t, intptr_t, size_t를 써야 합니다.

꼬리 질문 "64비트로 이전하면 메모리 사용량이 왜 늘어나나?" → 포인터가 8바이트가 되고 정렬 패딩이 커져, 포인터가 많은 자료구조는 크게 늘어납니다.

감점 포인트 "64비트에서는 int도 8바이트"라는 오해.

Q46. 인터럽트와 시스템 호출은 무엇인가요?

모범 답변 인터럽트는 하드웨어(타이머, 디스크, 네트워크 카드)가 CPU에 "처리할 일이 생겼다"고 알리는 신호로, CPU는 현재 작업을 잠시 멈추고 커널의 인터럽트 핸들러를 실행합니다. 시스템 호출은 사용자 프로그램이 파일·네트워크·프로세스 생성처럼 커널만 할 수 있는 일을 요청하는 통로로, 특별한 명령(x86-64의 syscall)으로 사용자 모드에서 커널 모드로 전환합니다. 모드 전환 비용 때문에 시스템 호출은 일반 함수 호출보다 훨씬 비싸서, 작은 I/O를 버퍼로 모아 호출 횟수를 줄이는 것이 성능의 기본입니다.

꼬리 질문 "printf는 시스템 호출인가?" → 아닙니다. 라이브러리 함수이고, 내부 버퍼가 차거나 비울 때 write 시스템 호출을 합니다.

감점 포인트 사용자 모드/커널 모드 구분을 모름.

Q47. 메모리 계층에서 레지스터, 캐시, 메인 메모리, 디스크의 속도 차이는 어느 정도인가요?

모범 답변 대략적인 크기 순서로 레지스터는 1사이클 미만, L1 캐시는 수 사이클(약 1ns), L2는 10여 사이클, L3는 수십 사이클, DRAM은 약 100ns(수백 사이클), NVMe SSD 임의 읽기는 수십~100μs, HDD 탐색은 수 ms입니다. DRAM과 SSD 사이가 약 1,000배, SSD와 HDD 사이가 다시 수십 배입니다. 그래서 디스크 I/O를 한 번 줄이는 것이 수만 번의 연산을 줄이는 것보다 효과가 크고, DB가 버퍼 캐시를, 운영체제가 페이지 캐시를 두는 이유가 됩니다.

꼬리 질문 "fsync가 느린 이유는?" → 데이터가 저장 장치에 실제로 기록될 때까지 기다리기 때문에 메모리 쓰기보다 수천 배 느립니다.

감점 포인트 정확한 숫자를 외우는 것보다 자릿수 감각이 중요한데, 순서조차 틀리는 것.

Q48. 멀티코어에서 캐시 일관성과 false sharing은 무엇인가요?

모범 답변 코어마다 자기 캐시가 있으므로 같은 주소의 데이터가 여러 캐시에 사본으로 존재할 수 있습니다. 한 코어가 값을 바꾸면 다른 코어의 사본을 무효화해 모두가 최신 값을 보게 하는 프로토콜(MESI 등)이 캐시 일관성입니다. False sharing은 서로 다른 스레드가 서로 다른 변수를 쓰는데 그 변수들이 우연히 같은 캐시 라인에 있어, 한쪽이 쓸 때마다 다른 코어의 라인이 무효화되어 성능이 크게 떨어지는 현상입니다. 스레드별 카운터 배열 같은 곳에서 생기며, 변수 사이를 캐시 라인 크기(64바이트)로 띄우거나 정렬해 해결합니다.

꼬리 질문 "캐시 일관성이 있으면 락 없이 공유 변수를 써도 되나?" → 안 됩니다. 일관성은 한 주소에 대한 최종 값 합의일 뿐, 읽기-수정-쓰기의 원자성이나 여러 주소 사이의 순서를 보장하지 않습니다.

감점 포인트 false sharing을 데이터 경쟁(진짜 공유)과 혼동.

금융권 전산직 면접은 C 언어보다 오히려 운영체제, 네트워크, DB 질문의 비중이 높은 경우가 많습니다. 계정계는 거대한 트랜잭션 처리 시스템이고, 대외계는 네트워크 시스템이며, 모든 데이터는 결국 DB에 있기 때문입니다. 마지막에는 금융권만의 특화 질문을 모았습니다.

프로세스·스레드 (ch26, ch28)

Q49. 프로세스와 스레드의 차이는 무엇인가요?

모범 답변 프로세스는 실행 중인 프로그램으로, 독립된 가상 주소 공간(코드·데이터·힙·스택)과 파일 디스크립터 같은 자원을 가진 자원 할당의 단위입니다. 스레드는 프로세스 안의 실행 흐름으로, 자기만의 스택·레지스터·프로그램 카운터를 갖지만 코드·데이터·힙·열린 파일은 같은 프로세스의 다른 스레드와 공유하는 CPU 스케줄링의 단위입니다. 스레드는 생성과 문맥 교환이 가볍고 데이터 공유가 쉽지만, 그만큼 동기화가 필요하고 한 스레드의 메모리 오류가 프로세스 전체를 죽입니다. 프로세스는 격리가 강해 한 프로세스가 죽어도 다른 프로세스는 살아남지만 통신에 IPC가 필요합니다.

꼬리 질문 "금융 온라인 서버에서 멀티프로세스와 멀티스레드 중 무엇을 선택하겠나?" → 장애 격리가 중요하면 멀티프로세스(전통적인 TP 모니터 방식), 공유 캐시와 처리량이 중요하면 멀티스레드입니다. 실제로는 여러 프로세스 각각이 스레드 풀을 갖는 혼합형이 많습니다.

감점 포인트 "스레드는 가벼운 프로세스"로만 답하고 무엇을 공유하는지 말하지 못함.

Q50. 문맥 교환(context switch)이란 무엇이고 비용은?

모범 답변 CPU가 실행 중인 프로세스나 스레드를 바꿀 때, 현재 레지스터·프로그램 카운터·스택 포인터 등 실행 상태를 저장하고 다음 것의 상태를 복원하는 작업입니다. 직접 비용은 상태 저장·복원과 커널 진입이고, 더 큰 간접 비용은 캐시와 TLB가 새 작업과 맞지 않아 생기는 미스입니다. 프로세스 간 교환은 주소 공간이 바뀌므로 TLB를 비우거나 태그를 바꿔야 해 스레드 간 교환보다 비쌉니다. 스레드를 코어 수보다 지나치게 많이 만들면 문맥 교환이 늘어 처리량이 오히려 떨어집니다.

꼬리 질문 "문맥 교환은 언제 일어나나?" → 타임 슬라이스 만료, I/O나 잠금 대기로 블록될 때, 더 높은 우선순위 작업이 준비될 때, 시스템 호출로 자발적으로 양보할 때입니다.

감점 포인트 캐시·TLB 간접 비용을 모름.

Q51. fork()와 exec()는 어떻게 동작하나요?

모범 답변 fork는 현재 프로세스를 복제해 자식 프로세스를 만들고, 부모에게는 자식의 PID를, 자식에게는 0을 반환합니다. 주소 공간을 실제로 복사하지 않고 Copy-on-Write로 공유하다가 한쪽이 쓰는 페이지만 복사하므로 빠릅니다. exec 계열 함수는 현재 프로세스의 메모리를 새 프로그램으로 교체하며, 성공하면 반환하지 않습니다. 셸은 fork 후 자식에서 exec하고 부모는 waitpid로 종료를 기다립니다. 자식이 종료했는데 부모가 wait하지 않으면 좀비 프로세스가 남습니다.

꼬리 질문 "멀티스레드 프로세스에서 fork하면?" → 호출한 스레드 하나만 자식에 복제되고, 다른 스레드가 잡고 있던 뮤텍스는 잠긴 채로 남을 수 있어 위험합니다. fork 후에는 곧바로 exec하는 것이 안전합니다.

감점 포인트 fork 반환값 규칙을 틀리거나 COW를 모름.

Q52. 좀비 프로세스와 고아 프로세스는?

모범 답변 좀비 프로세스는 이미 종료했지만 부모가 wait로 종료 상태를 회수하지 않아 프로세스 테이블 항목만 남은 상태입니다. 메모리는 해제되었지만 PID를 차지하므로 많이 쌓이면 새 프로세스를 만들 수 없습니다. 고아 프로세스는 부모가 먼저 종료한 자식으로, init(또는 subreaper)이 새 부모가 되어 종료 시 회수해 줍니다. 자식을 많이 만드는 서버는 SIGCHLD 핸들러에서 waitpid(-1, &st, WNOHANG)을 반복 호출해 좀비를 정리합니다.

꼬리 질문 "좀비 프로세스를 kill -9로 없앨 수 있나?" → 이미 종료한 상태라 시그널로 없앨 수 없고, 부모가 회수하거나 부모를 종료시켜야 합니다.

감점 포인트 좀비와 고아를 반대로 설명.

Q53. IPC(프로세스 간 통신) 방법에는 무엇이 있나요?

모범 답변 파이프(부모-자식 간 단방향 바이트 스트림), 이름 있는 파이프(FIFO), 메시지 큐, 공유 메모리, 세마포어(동기화용), 유닉스 도메인 소켓과 TCP 소켓, 시그널, 파일·메모리 맵 파일이 있습니다. 공유 메모리는 커널을 거치지 않아 가장 빠르지만 동기화를 직접 해야 하고, 소켓은 같은 코드로 원격 통신까지 확장할 수 있습니다. 금융권 레거시 시스템에서는 System V 공유 메모리에 코드 테이블이나 세션 정보를 두고 여러 서버 프로세스가 함께 읽는 구조가 흔합니다.

꼬리 질문 "공유 메모리에 포인터를 저장하면 안 되는 이유는?" → 프로세스마다 같은 공유 메모리가 다른 가상 주소에 매핑될 수 있어 포인터 값이 무의미합니다. 시작 주소로부터의 오프셋을 저장합니다.

감점 포인트 방법 나열만 하고 장단점을 말하지 못함.

Q54. 스레드 풀은 왜 쓰나요?

모범 답변 요청마다 스레드를 만들고 없애면 생성 비용이 들고, 요청이 몰리면 스레드가 무한정 늘어 메모리와 문맥 교환 비용으로 시스템 전체가 느려집니다. 스레드 풀은 정해진 수의 작업자 스레드를 미리 만들어 두고, 작업을 큐에 넣으면 놀고 있는 스레드가 꺼내 처리합니다. 생성 비용이 없고 동시 처리 수에 상한이 생겨 과부하 시에도 예측 가능하게 동작합니다. 풀 크기는 CPU 바운드면 코어 수 근처, I/O 대기가 많으면 더 크게 잡고, 큐 길이에도 상한을 두어 넘치면 거절 응답을 줍니다.

꼬리 질문 "작업 큐는 어떻게 구현하나?" → 뮤텍스로 보호하는 원형 큐와, 비었을 때 기다리고 넣었을 때 깨우는 조건 변수로 구현합니다(생산자-소비자).

감점 포인트 상한(백프레셔) 개념을 빠뜨림.

Q55. 사용자 수준 스레드와 커널 수준 스레드, 그리고 코루틴의 차이는?

모범 답변 커널 수준 스레드는 커널이 직접 스케줄링하므로 여러 코어에서 병렬 실행되고, 한 스레드가 블록되어도 다른 스레드가 진행합니다. 사용자 수준 스레드는 라이브러리가 사용자 공간에서 전환해 매우 가볍지만, 커널은 하나의 실행 흐름으로 보므로 하나가 블록되는 시스템 호출을 하면 전체가 멈추고 멀티코어를 못 씁니다. 현대 리눅스의 pthread는 1:1 커널 스레드입니다. 코루틴(그린 스레드)은 협력적으로 양보하는 사용자 수준 실행 흐름으로, 많은 수의 동시 I/O를 적은 스레드로 처리하는 데 쓰이며 보통 M:N으로 여러 커널 스레드 위에 매핑됩니다.

꼬리 질문 "C에서 코루틴을 쓰려면?" → 표준 기능은 없고, ucontext나 라이브러리, 또는 상태 머신으로 직접 구현합니다.

감점 포인트 블로킹 시스템 호출의 영향을 모름.

Q56. 경쟁 조건(race condition)과 임계 구역이란?

모범 답변 경쟁 조건은 여러 스레드가 공유 자원에 동시에 접근하고 그중 하나 이상이 쓰기를 할 때, 실행 순서(타이밍)에 따라 결과가 달라지는 상황입니다. 예를 들어 두 스레드가 같은 계좌 잔액을 읽고 각각 출금액을 빼서 쓰면 한쪽 출금이 사라지는 갱신 손실이 생깁니다. 임계 구역은 공유 자원에 접근하는 코드 구간으로, 한 번에 한 스레드만 실행해야 합니다. 임계 구역 해결 조건은 상호 배제, 진행(아무도 없으면 들어갈 수 있음), 한정 대기(무한히 기다리지 않음)입니다.

꼬리 질문 "경쟁 조건 버그는 왜 찾기 어렵나?" → 타이밍에 따라 가끔만 재현되고, 디버거나 로그를 넣으면 타이밍이 바뀌어 사라지기도 합니다. ThreadSanitizer(-fsanitize=thread)로 검출합니다.

감점 포인트 예시를 들지 못하는 추상적 답.

Q57. 뮤텍스와 세마포어의 차이는?

모범 답변 뮤텍스는 상호 배제를 위한 잠금으로, 한 번에 하나의 스레드만 소유할 수 있고 잠근 스레드가 풀어야 하는 소유권 개념이 있습니다. 세마포어는 정수 카운터로, wait(P)는 값이 0보다 크면 감소시키고 0이면 대기, post(V)는 증가시키며 대기자를 깨웁니다. 카운트가 N이면 N개 자원을 동시에 쓰도록 허용할 수 있고(예: DB 커넥션 풀), 소유권이 없어 다른 스레드가 post할 수 있으므로 신호 전달 용도로도 씁니다. 이진 세마포어는 뮤텍스와 비슷해 보이지만 소유권이 없어 우선순위 상속 같은 기능을 적용할 수 없습니다.

꼬리 질문 "스핀락은 언제 쓰나?" → 잠금 보유 시간이 매우 짧고 멀티코어일 때, 잠들고 깨어나는 비용보다 잠깐 돌며 기다리는 것이 싸면 씁니다. 보유 시간이 길면 CPU를 낭비합니다.

감점 포인트 "세마포어는 여러 개, 뮤텍스는 한 개"로만 답하고 소유권 차이를 모름.

Q58. 데드락의 4가지 필요조건과 해결 방법은?

모범 답변 상호 배제(자원을 한 번에 하나만 사용), 점유 대기(자원을 가진 채 다른 자원을 기다림), 비선점(남이 가진 자원을 빼앗을 수 없음), 순환 대기(대기 관계가 원을 이룸)의 네 조건이 동시에 성립해야 데드락이 생깁니다. 해결은 예방(조건 하나를 깨기 — 가장 실용적인 것은 모든 잠금에 전역 순서를 정해 순환 대기를 없애는 것), 회피(은행원 알고리즘처럼 안전 상태일 때만 할당), 탐지 후 회복(대기 그래프에서 순환을 찾아 한 트랜잭션을 롤백 — DB가 쓰는 방식), 무시가 있습니다. 이체에서는 두 계좌를 항상 계좌번호 오름차순으로 잠그면 순환이 생기지 않습니다.

꼬리 질문 "pthread_mutex_trylock으로 해결할 수 있나?" → 두 번째 잠금을 trylock으로 시도하고 실패하면 첫 잠금을 풀고 다시 시도하면 점유 대기를 깨지만, 라이브락이 생길 수 있어 무작위 대기를 섞습니다.

감점 포인트 4조건을 외우지만 실제 해결책(잠금 순서)을 못 대는 답.

Q59. 기아(starvation)와 라이브락(livelock)은?

모범 답변 기아는 특정 스레드가 우선순위나 스케줄링 정책 때문에 자원을 계속 얻지 못하고 무한히 기다리는 상태로, 에이징(기다린 시간만큼 우선순위를 올림)이나 공정한 큐로 해결합니다. 라이브락은 스레드들이 블록되지는 않고 계속 움직이지만, 서로의 행동에 반응해 양보만 반복하면서 진행하지 못하는 상태입니다. 좁은 복도에서 두 사람이 계속 같은 방향으로 비켜서는 상황과 같습니다. 재시도 사이에 무작위 지연(지수 백오프)을 넣어 해결합니다.

꼬리 질문 "우선순위 역전이란?" → 높은 우선순위 작업이 낮은 우선순위 작업이 가진 잠금을 기다리는 동안, 중간 우선순위 작업이 낮은 작업을 선점해 높은 작업이 무기한 지연되는 현상입니다. 우선순위 상속으로 해결합니다.

감점 포인트 데드락과 라이브락을 같은 것으로 설명.

Q60. 조건 변수는 무엇이고, 왜 while로 조건을 검사하나요?

모범 답변 조건 변수는 "어떤 조건이 참이 될 때까지" 스레드를 재우고, 조건을 바꾼 스레드가 깨우는 동기화 도구로, 항상 뮤텍스와 함께 씁니다. pthread_cond_wait는 뮤텍스를 원자적으로 풀고 잠들었다가, 깨어나면 다시 뮤텍스를 잡고 반환합니다. 조건을 if가 아니라 while로 다시 검사하는 이유는, 명세상 신호 없이 깨어나는 가짜 깨어남(spurious wakeup)이 허용되고, 깨어난 사이에 다른 스레드가 먼저 조건을 소비했을 수 있기 때문입니다.

꼬리 질문 "signal과 broadcast의 차이는?" → signal은 대기자 하나, broadcast는 모두를 깨웁니다. 조건이 여러 대기자에게 의미 있을 때 broadcast를 씁니다.

감점 포인트 if로 검사하는 코드를 정답으로 제시.

Q61. 원자적 연산(atomic)과 CAS는 무엇인가요?

모범 답변 원자적 연산은 중간 상태가 다른 스레드에 보이지 않고 한 번에 완료되는 연산입니다. CAS(Compare-And-Swap)는 "메모리 값이 기대값과 같으면 새 값으로 바꾸고, 아니면 실패"를 하드웨어가 원자적으로 수행하는 명령으로, 잠금 없는(lock-free) 자료구조와 카운터의 기반입니다. C11에서는 stdatomic.h의 atomic_fetch_add, atomic_compare_exchange_strong 등으로 씁니다. 짧은 카운터 증가는 원자 연산이 뮤텍스보다 훨씬 빠르지만, 여러 변수를 함께 바꿔야 하는 복잡한 불변식은 뮤텍스가 안전합니다.

꼬리 질문 "ABA 문제란?" → CAS 사이에 값이 A→B→A로 바뀌면 바뀌지 않은 것으로 오인하는 문제로, 버전 카운터를 함께 비교해 해결합니다.

감점 포인트 volatile을 원자 연산으로 설명.

Q62. 스레드 안전(thread-safe)과 재진입 가능(reentrant)의 차이는?

모범 답변 스레드 안전 함수는 여러 스레드가 동시에 호출해도 올바르게 동작하는 함수로, 내부에서 잠금을 써서 달성할 수도 있습니다. 재진입 가능 함수는 실행 도중 같은 함수가 다시 호출되어도(시그널 핸들러나 재귀) 올바른 함수로, 전역·정적 상태를 쓰지 않고 호출자가 넘긴 데이터만 사용합니다. 잠금을 쓰는 함수는 스레드 안전이지만, 잠금을 잡은 상태에서 시그널 핸들러가 같은 함수를 부르면 교착되므로 재진입 가능하지 않습니다. strtok, localtime은 정적 버퍼를 써서 둘 다 아니고, strtok_r, localtime_r을 써야 합니다.

꼬리 질문 "시그널 핸들러에서 printf를 쓰면 안 되는 이유는?" → printf는 내부 잠금과 버퍼를 쓰는 비동기 시그널 안전하지 않은 함수라서, 메인 흐름이 printf 도중에 시그널을 받으면 교착이나 버퍼 손상이 생길 수 있습니다.

감점 포인트 두 개념을 같은 것으로 답함.

메모리 관리, 가상 메모리, 페이징

메모리 관리 (ch16, ch26, ch31)

Q63. 가상 메모리란 무엇이고 왜 필요한가요?

모범 답변 가상 메모리는 각 프로세스에 독립된 연속 주소 공간을 주고, 실제 물리 메모리 위치와의 대응은 운영체제와 MMU가 페이지 단위로 관리하는 기법입니다. 이를 통해 프로세스 간 메모리를 격리해 한 프로세스가 다른 프로세스의 메모리를 건드릴 수 없게 하고, 물리 메모리보다 큰 주소 공간을 쓸 수 있으며(필요한 페이지만 메모리에), 공유 라이브러리 코드를 여러 프로세스가 같은 물리 페이지로 공유하고, fork의 Copy-on-Write를 가능하게 합니다. 프로그램은 항상 같은 가상 주소 체계로 컴파일·실행되므로 적재 위치를 신경 쓰지 않아도 됩니다.

꼬리 질문 "두 프로세스에서 같은 가상 주소를 출력하면 같은 값이 나올 수 있는데, 같은 메모리인가?" → 아닙니다. 각자의 페이지 테이블로 서로 다른 물리 프레임에 매핑됩니다.

감점 포인트 가상 메모리를 "디스크를 메모리처럼 쓰는 것(스왑)"으로만 설명. 격리와 주소 추상화가 핵심입니다.

Q64. 페이징과 세그먼테이션의 차이는?

모범 답변 페이징은 주소 공간과 물리 메모리를 같은 크기(보통 4KB)의 페이지와 프레임으로 나눠 매핑하므로 외부 단편화가 없고 관리가 단순하지만, 마지막 페이지의 내부 단편화와 페이지 테이블 크기 부담이 있습니다. 세그먼테이션은 코드·데이터·스택처럼 의미 단위의 가변 크기 세그먼트로 나눠 보호와 공유를 논리적으로 할 수 있지만 외부 단편화가 생깁니다. 현대 x86-64 운영체제는 세그먼테이션을 사실상 쓰지 않고 다단계 페이지 테이블 기반 페이징을 씁니다.

꼬리 질문 "페이지 테이블이 너무 크면?" → 다단계(x86-64는 4~5단계) 페이지 테이블로 쓰지 않는 영역의 테이블을 만들지 않고, 큰 페이지(2MB, 1GB)로 항목 수를 줄입니다.

감점 포인트 내부·외부 단편화를 반대로 연결.

Q65. 페이지 폴트는 무엇이고 어떻게 처리되나요?

모범 답변 접근한 가상 페이지가 물리 메모리에 매핑되어 있지 않을 때 MMU가 일으키는 예외입니다. 커널은 그 주소가 합법적인지 확인해, 합법이면 빈 프레임을 확보하고(없으면 페이지 교체로 희생 페이지를 내보냄) 디스크나 스왑에서 내용을 읽어 오거나 0으로 채운 뒤 페이지 테이블을 갱신하고 명령을 재실행합니다. 합법적이지 않은 주소면 SIGSEGV를 보냅니다. 디스크 읽기가 필요한 메이저 폴트는 수 ms가 걸려 매우 비싸고, 이미 메모리에 있는 페이지를 매핑만 하는 마이너 폴트는 가볍습니다.

꼬리 질문 "malloc으로 1GB를 할당하면 즉시 1GB 물리 메모리를 쓰나?" → 보통 아닙니다. 가상 주소만 예약하고, 실제로 쓰는 페이지에 처음 접근할 때 폴트로 물리 프레임이 할당됩니다(지연 할당).

감점 포인트 페이지 폴트를 무조건 오류라고 답함.

Q66. 페이지 교체 알고리즘을 설명해 주세요.

모범 답변 빈 프레임이 없을 때 어떤 페이지를 내보낼지 정하는 알고리즘입니다. FIFO는 가장 먼저 들어온 페이지를 내보내 단순하지만 프레임을 늘려도 폴트가 늘 수 있는 벨라디의 모순이 있습니다. OPT(최적)는 앞으로 가장 오래 쓰이지 않을 페이지를 내보내는 이론적 최적이지만 미래를 알아야 해 비교 기준으로만 씁니다. LRU는 가장 오래 쓰이지 않은 페이지를 내보내 성능이 좋지만 정확한 구현 비용이 커서, 실제로는 참조 비트를 이용한 클럭(Second Chance) 같은 근사 알고리즘을 씁니다.

꼬리 질문 "LRU 캐시를 직접 구현한다면?" → 해시 테이블과 이중 연결 리스트를 조합해 조회·갱신·제거를 모두 O(1)로 만듭니다.

감점 포인트 알고리즘 이름만 나열.

Q67. 스래싱(thrashing)이란 무엇인가요?

모범 답변 실행 중인 프로세스들이 자주 쓰는 페이지 집합(워킹 셋)의 합이 물리 메모리보다 커서, 페이지 폴트와 교체가 끊임없이 일어나 CPU가 실제 일보다 페이지 입출력 대기에 대부분의 시간을 쓰는 상태입니다. CPU 사용률이 낮아 보여 프로세스를 더 띄우면 오히려 악화됩니다. 동시 실행 프로세스 수를 줄이거나, 메모리를 늘리거나, 워킹 셋 기반으로 메모리를 할당해 해결합니다. 운영 서버에서 스왑 사용량과 메이저 폴트 수가 급증하면 의심합니다.

꼬리 질문 "DB 서버에서 스왑을 끄는 경우가 있는 이유는?" → 스왑으로 인한 예측 불가능한 지연을 피하고, 대신 메모리 사용을 엄격히 관리하기 위해서입니다(대신 OOM 위험).

감점 포인트 스래싱을 CPU 과부하로 설명.

Q68. mmap은 무엇이고 read/write와 어떻게 다른가요?

모범 답변 mmap은 파일이나 익명 메모리를 프로세스의 가상 주소 공간에 매핑해, 파일을 메모리 배열처럼 포인터로 읽고 쓰게 하는 시스템 호출입니다. read/write는 커널 버퍼에서 사용자 버퍼로 복사가 일어나지만, mmap은 페이지 캐시를 직접 매핑하므로 복사가 줄고, 큰 파일의 임의 접근에 유리하며, 여러 프로세스가 같은 파일을 매핑해 공유 메모리로도 씁니다. 대신 매핑·해제와 페이지 폴트 비용이 있어 작은 순차 I/O에는 이득이 작고, 파일이 잘리면 접근 시 SIGBUS가 나며, 디스크 반영 시점은 msync로 제어해야 합니다.

꼬리 질문 "malloc은 내부적으로 무엇을 쓰나?" → glibc는 작은 할당은 brk/sbrk로 늘린 힙에서, 큰 할당(기본 128KB 이상)은 mmap으로 따로 받습니다.

감점 포인트 mmap이 항상 read보다 빠르다는 단정.

CPU 스케줄링

스케줄링 (ch26)

Q69. CPU 스케줄링 알고리즘의 종류와 특징은?

모범 답변 FCFS는 도착 순서대로 처리해 단순하지만 긴 작업 뒤의 짧은 작업이 오래 기다리는 호위 효과가 있습니다. SJF는 실행 시간이 짧은 작업부터 처리해 평균 대기 시간이 최소지만 실행 시간을 미리 알기 어렵고 긴 작업이 기아에 빠질 수 있습니다. 우선순위 스케줄링은 기아를 에이징으로 보완합니다. 라운드 로빈은 정해진 시간 할당량마다 돌아가며 실행해 응답성이 좋고, 할당량이 너무 작으면 문맥 교환 비용이 커집니다. 다단계 피드백 큐는 작업의 행동에 따라 큐를 옮겨 대화형 작업에 높은 우선순위를 줍니다. 리눅스의 CFS(및 후속 EEVDF)는 각 작업의 가상 실행 시간을 공정하게 맞추는 방식입니다.

꼬리 질문 "선점형과 비선점형의 차이는?" → 선점형은 실행 중인 작업에서 CPU를 강제로 빼앗을 수 있고, 비선점형은 작업이 스스로 양보하거나 끝날 때까지 기다립니다.

감점 포인트 알고리즘별 단점을 말하지 못함.

Q70. CPU 바운드 작업과 I/O 바운드 작업은 어떻게 다르게 다루나요?

모범 답변 CPU 바운드 작업은 계산이 대부분이라 CPU를 오래 쓰고, I/O 바운드 작업은 디스크·네트워크를 기다리는 시간이 대부분이고 CPU는 짧게 씁니다. 스케줄러는 I/O 바운드 작업을 우선해 빨리 I/O를 다시 걸게 하면 CPU와 장치를 동시에 바쁘게 만들어 전체 처리량이 오릅니다. 스레드 수도 CPU 바운드는 코어 수 근처, I/O 바운드는 대기 비율만큼 더 많이 잡습니다. time의 real과 user+sys를 비교하면 어느 쪽인지 알 수 있습니다.

꼬리 질문 "배치 작업이 I/O 바운드라면 어떻게 빠르게 하나?" → I/O 단위를 키우고(버퍼링), 순차 접근으로 바꾸고, 계산과 I/O를 겹치거나(비동기·이중 버퍼), 작업을 분할해 병렬로 처리합니다.

감점 포인트 개념만 말하고 측정·대응 방법이 없음.

Q71. 응답 시간, 처리량, 대기 시간 같은 스케줄링 지표는?

모범 답변 CPU 이용률은 CPU가 일한 비율, 처리량은 단위 시간당 완료한 작업 수, 반환 시간은 제출부터 완료까지의 시간, 대기 시간은 준비 큐에서 기다린 시간의 합, 응답 시간은 요청 후 첫 반응까지의 시간입니다. 온라인 거래 시스템은 응답 시간(특히 상위 백분위, 예: 99% 응답 시간)이 중요하고, 배치 시스템은 처리량과 전체 반환 시간(배치 시간 창 안에 끝나는가)이 중요합니다. 두 목표는 서로 상충하는 경우가 많아, 같은 서버에서 온라인과 배치를 돌릴 때는 우선순위나 자원 제한으로 온라인을 보호합니다.

꼬리 질문 "평균 응답 시간만 보면 안 되는 이유는?" → 대부분 빠르고 일부가 매우 느린 경우를 숨기므로 백분위(p95, p99)를 함께 봅니다.

감점 포인트 처리량과 응답 시간을 같은 것으로 취급.

Q72. 실시간 스케줄링과 nice 값은?

모범 답변 리눅스는 일반 작업(SCHED_OTHER)과 실시간 작업(SCHED_FIFO, SCHED_RR)을 구분하며, 실시간 작업은 항상 일반 작업보다 먼저 실행됩니다. nice 값(−20~19)은 일반 작업 사이의 상대적 가중치로, 값이 클수록 CPU 몫이 작아집니다. 운영 서버에서 대용량 백업이나 로그 압축처럼 급하지 않은 작업은 nice와 ionice로 낮춰 온라인 서비스에 영향을 줄입니다. 실시간 우선순위를 잘못 주면 그 작업이 CPU를 독점해 시스템이 응답하지 않을 수 있어 신중해야 합니다.

꼬리 질문 "일반 사용자가 nice 값을 낮출(우선순위를 높일) 수 있나?" → 기본적으로 높일(값을 키울) 수만 있고, 낮추려면 권한이 필요합니다.

감점 포인트 nice 값이 클수록 우선순위가 높다고 거꾸로 답함.

네트워크: TCP/UDP, HTTP

네트워크 (ch27)

Q73. TCP와 UDP의 차이는?

모범 답변 TCP는 연결 지향 프로토콜로, 3-way handshake로 연결을 맺고 순서 번호와 확인 응답, 재전송으로 데이터가 빠짐없이 순서대로 도착하도록 보장하며, 흐름 제어와 혼잡 제어를 합니다. 대신 연결 설정과 제어 오버헤드가 있고 경계 없는 바이트 스트림입니다. UDP는 비연결형으로 데이터그램을 그대로 보내며 도착·순서·중복을 보장하지 않지만, 오버헤드가 작고 메시지 경계가 유지되어 DNS, 실시간 음성·영상, 시세 멀티캐스트처럼 지연이 중요하거나 응용이 신뢰성을 직접 관리하는 곳에 씁니다. 금융 거래 전문은 신뢰성이 필수이므로 TCP를 씁니다.

꼬리 질문 "UDP로 신뢰성 있는 전송을 하려면?" → 응용 계층에서 순서 번호, 확인 응답, 재전송, 중복 제거를 구현해야 합니다(QUIC이 UDP 위에서 이를 구현한 예).

감점 포인트 "TCP는 느리고 UDP는 빠르다"로만 답함.

Q74. TCP 3-way handshake와 4-way handshake를 설명해 주세요.

모범 답변 연결 수립 시 클라이언트가 초기 순서 번호를 담은 SYN을 보내고, 서버가 자신의 순서 번호를 담은 SYN과 클라이언트 SYN에 대한 ACK를 함께 보내며, 클라이언트가 서버 SYN에 대한 ACK를 보내 연결이 성립합니다. 세 번이 필요한 이유는 양쪽이 서로의 초기 순서 번호를 확인받아야 하기 때문이고, 오래된 중복 SYN으로 잘못된 연결이 생기는 것도 막습니다. 종료는 각 방향을 따로 닫으므로, 한쪽이 FIN을 보내고 상대가 ACK한 뒤, 상대도 보낼 데이터를 다 보내고 FIN을 보내 ACK를 받는 4단계입니다.

꼬리 질문 "SYN flooding 공격이란?" → 마지막 ACK를 보내지 않는 SYN을 대량으로 보내 서버의 반연결 큐를 채우는 공격으로, SYN 쿠키 등으로 방어합니다.

감점 포인트 왜 2번이 아니라 3번인지 설명하지 못함.

Q75. TIME_WAIT 상태는 왜 있고, 문제가 되면 어떻게 하나요?

모범 답변 연결을 먼저 닫은 쪽은 마지막 ACK를 보낸 뒤 2MSL(최대 세그먼트 수명의 두 배, 리눅스는 60초) 동안 TIME_WAIT에 머뭅니다. 마지막 ACK가 유실되어 상대가 FIN을 재전송하면 다시 ACK하기 위해서이고, 지연된 옛 연결의 패킷이 같은 포트 조합의 새 연결에 섞이는 것을 막기 위해서입니다. 짧은 연결을 대량으로 맺고 끊는 클라이언트는 TIME_WAIT 소켓이 쌓여 로컬 포트가 고갈될 수 있고, 서버를 재시작할 때 bind가 "Address already in use"로 실패할 수 있습니다. 서버는 SO_REUSEADDR로 재시작 문제를 해결하고, 근본적으로는 연결 재사용(keep-alive, 커넥션 풀)으로 연결 수를 줄입니다.

꼬리 질문 "CLOSE_WAIT가 많이 쌓이면?" → 상대가 닫았는데 내 프로그램이 close를 호출하지 않는 버그(소켓 누수)입니다.

감점 포인트 TIME_WAIT를 단순히 "없애야 할 낭비"로 설명.

Q76. TCP 흐름 제어와 혼잡 제어의 차이는?

모범 답변 흐름 제어는 수신자가 처리할 수 있는 속도를 넘지 않게 하는 것으로, 수신자가 남은 수신 버퍼 크기(윈도)를 알리면 송신자는 그만큼만 확인 응답 없이 보냅니다. 혼잡 제어는 네트워크 경로가 감당할 수 있는 양을 넘지 않게 하는 것으로, 송신자가 혼잡 윈도를 슬로 스타트로 빠르게 늘리다가 손실이나 지연 증가를 감지하면 줄입니다(AIMD, CUBIC, BBR 등). 실제 보낼 수 있는 양은 두 윈도 중 작은 쪽입니다. 즉 흐름 제어는 종단 간, 혼잡 제어는 네트워크 전체를 보호합니다.

꼬리 질문 "수신 윈도가 0이 되면?" → 송신자는 멈추고 주기적으로 윈도 탐색 패킷을 보내 윈도가 열리기를 기다립니다. 수신 응용이 데이터를 읽지 않으면 이런 일이 생깁니다.

감점 포인트 둘을 같은 개념으로 설명.

Q77. TCP는 왜 메시지 경계가 없나요? 전문 통신에서 어떻게 처리하나요?

모범 답변 TCP는 응용이 보낸 바이트를 순서대로 전달하는 스트림 서비스이고, 세그먼트 크기는 MSS, 윈도, Nagle 알고리즘 등에 따라 TCP가 정합니다. 그래서 send 한 번이 recv 여러 번으로 쪼개지거나 여러 send가 recv 한 번에 붙어 올 수 있습니다. 전문 통신에서는 응용 계층에서 경계를 정의해야 하며, 금융권은 보통 고정 길이 길이 헤더를 붙이고 수신 측이 헤더만큼 정확히 읽은 뒤 그 길이만큼 반복해서 읽습니다. 고정 길이 전문, 구분자 방식도 있습니다.

꼬리 질문 "길이 헤더 값을 그대로 믿으면?" → 위조된 큰 값으로 버퍼 오버플로나 메모리 고갈이 생기므로 최대 길이와 비교해 검증합니다.

감점 포인트 "recv 한 번에 전문 하나가 온다"는 가정.

Q78. OSI 7계층과 TCP/IP 4계층을 설명해 주세요.

모범 답변 OSI는 물리, 데이터 링크, 네트워크, 전송, 세션, 표현, 응용의 7계층 참조 모델이고, 실제 인터넷은 링크(네트워크 접근), 인터넷(IP), 전송(TCP/UDP), 응용(HTTP, DNS 등)의 4계층 TCP/IP 모델로 동작합니다. 각 계층은 아래 계층의 서비스를 이용하고 자기 헤더를 붙여 캡슐화합니다. 이더넷 프레임 안에 IP 패킷, 그 안에 TCP 세그먼트, 그 안에 응용 데이터가 들어갑니다. 계층을 나누면 각 계층을 독립적으로 바꾸고 문제 위치를 좁혀 진단할 수 있습니다.

꼬리 질문 "라우터와 스위치는 어느 계층에서 동작하나?" → 스위치는 MAC 주소로 2계층, 라우터는 IP 주소로 3계층입니다(L4/L7 스위치는 더 위 정보까지 봄).

감점 포인트 계층 이름만 외우고 캡슐화를 설명하지 못함.

Q79. 브라우저에 URL을 입력하면 일어나는 일을 설명해 주세요.

모범 답변 브라우저는 URL을 해석하고 캐시를 확인한 뒤, DNS로 도메인의 IP 주소를 조회합니다(브라우저·OS 캐시 → 리졸버 → 루트·TLD·권한 서버). 그 IP의 443 포트로 TCP 연결을 맺고, TLS 핸드셰이크로 서버 인증서를 검증하고 세션 키를 합의합니다. 암호화된 채널로 HTTP 요청을 보내면, 로드 밸런서·웹 서버·애플리케이션 서버·DB를 거쳐 응답이 돌아오고, 브라우저는 HTML을 파싱해 DOM을 만들고 CSS·JS·이미지를 추가로 요청하며 렌더링합니다. 연결은 keep-alive로 재사용됩니다.

꼬리 질문 "HTTPS에서 대칭키와 공개키는 각각 어디에 쓰이나?" → 공개키(및 키 교환 알고리즘)는 핸드셰이크에서 서버 인증과 세션 키 합의에, 대칭키는 실제 데이터 암호화에 씁니다. 대칭키가 훨씬 빠르기 때문입니다.

감점 포인트 DNS나 TLS 단계를 통째로 빠뜨림.

Q80. HTTP의 특징과 GET/POST의 차이, 상태 코드는?

모범 답변 HTTP는 요청-응답 방식의 응용 계층 프로토콜로, 기본적으로 무상태(stateless)라 각 요청이 독립적이며 상태 유지는 쿠키, 세션, 토큰으로 합니다. GET은 자원 조회로 데이터를 URL 쿼리에 담고 멱등·안전하며 캐시될 수 있습니다. POST는 자원 생성이나 처리 요청으로 데이터를 본문에 담고 멱등하지 않습니다. 그래서 계좌번호·주민번호 같은 민감 정보는 URL(로그·브라우저 기록에 남음)에 넣지 않습니다. 상태 코드는 2xx 성공, 3xx 리다이렉트, 4xx 클라이언트 오류(400, 401, 403, 404), 5xx 서버 오류(500, 502, 503, 504)입니다.

꼬리 질문 "PUT과 PATCH의 차이는?" → PUT은 자원 전체를 교체하고 멱등이며, PATCH는 일부를 수정합니다.

감점 포인트 "POST는 암호화되어 안전하다". 암호화는 HTTPS가 하는 것이고, POST 본문도 평문 HTTP에서는 그대로 보입니다.

Q81. 블로킹/논블로킹, 동기/비동기 I/O와 select/poll/epoll의 차이는?

모범 답변 블로킹 I/O는 데이터가 준비될 때까지 호출이 반환되지 않고, 논블로킹 I/O는 준비되지 않았으면 즉시 EAGAIN으로 반환합니다. I/O 다중화는 여러 소켓 중 준비된 것을 한 번에 알려 주는 기법으로, select는 감시할 fd 수가 FD_SETSIZE(보통 1024)로 제한되고 매번 전체 집합을 복사·검사하며, poll은 개수 제한이 없지만 역시 O(n)입니다. 리눅스 epoll은 관심 목록을 커널에 등록해 두고 준비된 것만 돌려주어 연결이 수만 개여도 효율적입니다. 비동기 I/O는 요청 후 완료 통지를 받는 방식으로 리눅스의 io_uring이 대표적입니다.

꼬리 질문 "epoll의 레벨 트리거와 엣지 트리거의 차이는?" → 레벨 트리거는 읽을 데이터가 남아 있는 한 계속 알리고, 엣지 트리거는 상태가 바뀔 때 한 번만 알리므로 EAGAIN이 날 때까지 다 읽어야 합니다.

감점 포인트 논블로킹과 비동기를 같은 것으로 설명.

Q82. Nagle 알고리즘과 TCP_NODELAY는?

모범 답변 Nagle 알고리즘은 작은 패킷이 네트워크를 낭비하지 않도록, 확인 응답을 기다리는 데이터가 있는 동안 작은 데이터를 모았다가 보내는 기법입니다. 그런데 수신 측의 지연 ACK와 맞물리면, 송신 측이 응답 헤더와 본문을 따로 write할 때 두 번째 조각이 ACK를 기다리며 수십 ms 지연될 수 있습니다. 지연에 민감한 거래 전문 통신에서는 TCP_NODELAY로 Nagle을 끄거나, 더 좋게는 한 전문을 하나의 버퍼로 모아 write 한 번으로 보냅니다.

꼬리 질문 "TCP_NODELAY를 켜고 1바이트씩 write하면?" → 패킷마다 40바이트 이상의 헤더가 붙어 대역폭이 낭비되고 시스템 호출도 많아집니다.

감점 포인트 Nagle을 "항상 끄는 것이 좋다"고 단정.

Q83. 트랜잭션과 ACID를 설명해 주세요.

모범 답변 트랜잭션은 하나의 논리적 작업 단위로, 그 안의 연산이 모두 반영되거나 하나도 반영되지 않아야 합니다. 원자성(Atomicity)은 전부 아니면 전무, 일관성(Consistency)은 트랜잭션 전후로 무결성 제약(잔액 ≥ 0, 차변 = 대변)이 유지됨, 격리성(Isolation)은 동시에 실행되는 트랜잭션이 서로의 중간 결과를 보지 않음, 지속성(Durability)은 커밋된 결과가 장애 후에도 남음입니다. 계좌 이체에서 출금과 입금이 한 트랜잭션이어야 하는 이유가 원자성이고, 커밋 응답 후 정전이 나도 이체가 남아야 하는 것이 지속성입니다. DB는 원자성·지속성을 로그(WAL, 언두/리두)로, 격리성을 잠금이나 MVCC로 구현합니다.

꼬리 질문 "커밋 직후 서버가 죽으면 데이터 파일에 아직 반영 안 된 변경은?" → 리두 로그가 디스크에 있으므로 재기동 시 로그를 재생해 복구합니다.

감점 포인트 각 글자를 단어로만 풀고 구현 방법이나 금융 예시가 없음.

Q84. 트랜잭션 격리 수준과 각 수준에서 생기는 현상은?

모범 답변 READ UNCOMMITTED는 커밋되지 않은 데이터를 읽는 더티 리드가 생깁니다. READ COMMITTED는 커밋된 것만 읽지만, 같은 행을 두 번 읽을 때 값이 달라지는 반복 불가능한 읽기가 생깁니다(Oracle 기본). REPEATABLE READ는 같은 행은 같게 읽지만, 범위 조회 결과에 새 행이 나타나는 팬텀 리드가 표준상 가능합니다(MySQL InnoDB 기본, 실제로는 MVCC와 갭 잠금으로 상당 부분 방지). SERIALIZABLE은 순차 실행과 같은 결과를 보장하지만 동시성이 가장 낮습니다. 격리 수준이 높을수록 정확하지만 잠금 경합과 대기가 늘어납니다.

꼬리 질문 "잔액 차감에서 갱신 손실을 막으려면?" → SELECT ... FOR UPDATE로 행을 잠그고 갱신하거나, UPDATE acct SET bal = bal - :amt WHERE no = :no AND bal >= :amt처럼 조건부 단일 UPDATE로 처리하고 영향 행 수를 확인합니다.

감점 포인트 격리 수준과 이상 현상을 엇갈려 연결.

Q85. 인덱스는 무엇이고 어떻게 동작하나요? 단점은?

모범 답변 인덱스는 특정 컬럼 값으로 행을 빠르게 찾기 위한 별도의 정렬된 자료구조로, 대부분의 RDBMS는 B+트리를 씁니다. B+트리는 한 노드가 디스크 페이지 하나에 많은 키를 담아 높이가 매우 낮으므로 수백만 건에서도 3~4번의 페이지 읽기로 찾고, 리프가 연결되어 범위 검색과 정렬에도 유리합니다. 단점은 인덱스도 저장 공간을 차지하고, INSERT·UPDATE·DELETE 때마다 인덱스를 갱신해야 해 쓰기가 느려진다는 것입니다. 그래서 조회 조건에 자주 쓰이고 선택도가 높은(값이 다양한) 컬럼에 만들고, 무분별하게 늘리지 않습니다.

꼬리 질문 "인덱스가 있어도 안 타는 경우는?" → 인덱스 컬럼을 함수나 연산으로 가공(WHERE SUBSTR(acct_no,1,3)='110'), 암묵적 형 변환, 앞부분 와일드카드 LIKE('%123'), 결합 인덱스의 선두 컬럼 누락, 조회 비율이 높아 전체 스캔이 더 싼 경우입니다.

감점 포인트 "인덱스는 많을수록 좋다".

Q86. 클러스터드 인덱스와 논클러스터드 인덱스의 차이는?

모범 답변 클러스터드 인덱스는 테이블 데이터 자체가 인덱스 키 순서로 물리적으로 정렬·저장되는 것이라 테이블당 하나만 가능하고, 범위 검색에서 데이터를 연속으로 읽을 수 있습니다(InnoDB는 기본 키가 클러스터드 인덱스). 논클러스터드(보조) 인덱스는 키와 행 위치(또는 기본 키)를 담은 별도 구조라 여러 개 만들 수 있지만, 인덱스에서 찾은 뒤 실제 행을 다시 읽어야 합니다. 조회에 필요한 컬럼이 모두 인덱스에 있으면 행을 읽지 않아도 되는데, 이것을 커버링 인덱스라고 합니다.

꼬리 질문 "InnoDB에서 기본 키를 무작위 UUID로 하면?" → 삽입 위치가 무작위라 페이지 분할이 잦고 보조 인덱스도 커져 성능이 떨어집니다.

감점 포인트 둘의 저장 구조 차이를 설명하지 못함.

Q87. 결합 인덱스에서 컬럼 순서는 어떻게 정하나요?

모범 답변 결합 인덱스는 첫 번째 컬럼으로 정렬하고, 같으면 두 번째 컬럼으로 정렬한 구조라서 선두 컬럼 조건이 없으면 효율적으로 쓸 수 없습니다. 보통 등치(=) 조건으로 항상 쓰이는 컬럼을 앞에, 범위 조건 컬럼을 뒤에 둡니다. 예를 들어 "계좌번호별 거래일자 범위 조회"가 주된 패턴이면 (acct_no, txn_date) 순서가 맞고, 반대로 하면 날짜 범위로 넓게 읽은 뒤 계좌로 거르게 됩니다. 실제 쿼리 패턴과 실행 계획을 보고 결정합니다.

꼬리 질문 "(a, b) 인덱스로 WHERE b = 1을 처리할 수 있나?" → 일반적으로 효율적인 탐색은 못 하고, 일부 DB는 인덱스 전체 스캔이나 스킵 스캔으로 처리합니다.

감점 포인트 "선택도 높은 컬럼을 무조건 앞에"라고만 답함.

Q88. 정규화란 무엇이고, 반정규화는 언제 하나요?

모범 답변 정규화는 데이터 중복을 제거해 삽입·수정·삭제 이상을 막기 위해 테이블을 분해하는 과정입니다. 1NF는 모든 컬럼이 원자값, 2NF는 기본 키 일부에만 종속되는 부분 함수 종속 제거, 3NF는 키가 아닌 컬럼 사이의 이행 종속 제거, BCNF는 모든 결정자가 후보 키가 되도록 합니다. 정규화하면 일관성은 좋아지지만 조회 시 조인이 늘어납니다. 반정규화는 조회 성능을 위해 의도적으로 중복을 허용하는 것으로, 예를 들어 계좌 잔액을 매번 거래내역에서 합산하지 않고 원장 테이블에 잔액 컬럼을 두는 것이 대표적입니다. 이때 두 값이 어긋나지 않도록 트랜잭션과 대사로 관리합니다.

꼬리 질문 "삽입 이상의 예는?" → 고객과 지점 정보를 한 테이블에 두면, 고객이 없는 신설 지점 정보를 넣을 수 없는 경우입니다.

감점 포인트 정규형 이름만 외우고 목적(이상 현상 방지)을 말하지 못함.

Q89. DB 잠금(락)의 종류와 데드락은?

모범 답변 공유 잠금(S)은 읽기용으로 여러 트랜잭션이 함께 잡을 수 있고, 배타 잠금(X)은 쓰기용으로 하나만 잡을 수 있습니다. 범위는 행, 페이지, 테이블 단위가 있으며, 행 잠금이 동시성이 높지만 관리 비용이 큽니다. 두 트랜잭션이 서로 상대가 잠근 행을 기다리면 DB 데드락이 생기고, DB는 대기 그래프에서 순환을 탐지해 한쪽을 롤백시켜 해결합니다. 응용에서는 같은 자원을 항상 같은 순서로 접근하고, 트랜잭션을 짧게 유지하며, 데드락 오류 시 재시도하도록 설계합니다.

꼬리 질문 "MVCC는 무엇인가?" → 데이터의 여러 버전을 유지해, 읽기는 잠금 없이 자기 시점의 스냅숏을 보고 쓰기만 잠금을 잡게 해 읽기-쓰기 충돌을 줄이는 방식입니다.

감점 포인트 트랜잭션을 길게 잡는 설계를 문제로 인식하지 못함.

Q90. 조인의 종류와 조인 방식(Nested Loop, Hash, Sort Merge)은?

모범 답변 논리적 조인은 양쪽에 모두 있는 행만 내는 INNER JOIN, 한쪽 행을 모두 남기는 LEFT/RIGHT OUTER JOIN, 양쪽 모두 남기는 FULL OUTER JOIN, 모든 조합의 CROSS JOIN이 있습니다. 물리적 실행 방식으로는, 바깥 테이블의 행마다 안쪽을 인덱스로 찾는 Nested Loop(소량·인덱스 있을 때 유리, 온라인 거래에 적합), 작은 쪽으로 해시 테이블을 만들어 큰 쪽을 탐색하는 Hash Join(대량 등치 조인, 배치에 적합), 양쪽을 정렬해 병합하는 Sort Merge Join이 있습니다. 옵티마이저가 통계를 보고 선택하므로, 통계가 오래되면 잘못된 방식을 골라 성능이 급락합니다.

꼬리 질문 "실행 계획은 어떻게 확인하나?" → EXPLAIN(Oracle은 EXPLAIN PLAN, 실행 통계는 SQL 트레이스)으로 접근 경로, 조인 순서와 방식, 예상 건수를 봅니다.

감점 포인트 논리 조인과 물리 조인 방식을 구분하지 못함.

Q91. 대량 배치에서 건별 커밋을 하면 안 되는 이유는?

모범 답변 커밋은 로그를 디스크에 확정(fsync)하므로 비싼 연산이라, 100만 건을 건별로 커밋하면 100만 번의 디스크 동기화와 네트워크 왕복이 생겨 매우 느립니다. 반대로 전체를 한 트랜잭션으로 묶으면 언두 공간이 부족해지고, 잠금을 오래 잡아 온라인을 방해하며, 실패 시 전부 롤백되어 처음부터 다시 해야 합니다. 그래서 수천~수만 건 단위로 묶어 커밋하는 중간 커밋을 하고, 커밋할 때마다 처리 위치(체크포인트)를 같은 트랜잭션에 기록해 재시작 시 그 지점부터 이어서 처리하게 합니다. 배열 처리(bulk insert, array fetch)로 왕복 횟수도 줄입니다.

꼬리 질문 "체크포인트를 별도 트랜잭션으로 기록하면?" → 데이터 커밋과 체크포인트 기록 사이에 장애가 나면 재시작 위치가 어긋나 중복 처리나 누락이 생깁니다. 같은 트랜잭션에 넣어야 합니다.

감점 포인트 재처리(재시작) 관점을 빠뜨림.

Q92. SQL 인젝션은 무엇이고 어떻게 막나요?

모범 답변 사용자 입력을 문자열 연결로 SQL에 넣을 때, 입력에 SQL 구문을 섞어 의도하지 않은 쿼리를 실행시키는 공격입니다. 예를 들어 "... WHERE id='" + input + "'"에 ' OR '1'='1을 넣으면 조건이 항상 참이 됩니다. 근본 대책은 바인드 변수를 쓰는 준비된 문장(Prepared Statement)으로, 입력이 SQL 구문이 아닌 값으로만 처리됩니다. 여기에 입력값 검증(형식·길이), 최소 권한 DB 계정, 오류 메시지에 SQL 정보 노출 금지를 더합니다. C의 Pro*C나 ESQL에서도 호스트 변수 바인딩을 씁니다.

꼬리 질문 "바인드 변수가 성능에도 좋은 이유는?" → SQL 문장이 같아 파싱된 실행 계획을 재사용할 수 있기 때문입니다(하드 파싱 감소).

감점 포인트 "특수 문자를 이스케이프하면 된다"를 주 대책으로 제시.

Q93. 시간 복잡도와 빅오 표기법을 설명해 주세요.

모범 답변 시간 복잡도는 입력 크기 n이 커질 때 연산 횟수가 늘어나는 비율이고, 빅오는 최고차항만 남기고 상수를 버린 상한 표기입니다. 대표적으로 O(1) 해시 조회, O(log n) 이진 탐색, O(n) 선형 탐색, O(n log n) 효율적인 비교 정렬, O(n²) 이중 루프, O(2ⁿ) 부분집합 전수 조사가 있습니다. n이 100만이면 O(n log n)은 약 2천만 번이지만 O(n²)은 1조 번이라, 대용량 배치에서는 복잡도 선택이 시간을 좌우합니다. 다만 빅오는 상수와 캐시 효과를 무시하므로 작은 n이나 실제 성능은 측정으로 확인해야 합니다.

꼬리 질문 "평균과 최악, 상각(amortized) 복잡도의 차이는?" → 동적 배열의 끝 삽입은 가끔 재할당으로 O(n)이지만, 크기를 두 배씩 늘리면 n번 삽입의 총비용이 O(n)이라 상각 O(1)입니다.

감점 포인트 빅오를 "정확한 실행 시간"으로 설명.

Q94. 배열과 연결 리스트의 차이는?

모범 답변 배열은 연속 메모리라 인덱스로 O(1) 임의 접근이 가능하고 캐시 지역성이 좋지만, 중간 삽입·삭제는 원소 이동으로 O(n)이고 크기를 늘리려면 재할당과 복사가 필요합니다. 연결 리스트는 노드가 흩어져 포인터로 연결되므로, 위치를 알고 있다면 삽입·삭제가 O(1)이고 크기가 자유롭지만, 임의 접근은 O(n)이고 노드마다 포인터 공간이 들며 캐시 미스가 많습니다. 실무에서는 대부분 배열(동적 배열)이 더 빠르고, 연결 리스트는 자주 중간 삽입·삭제하며 반복자 위치를 유지해야 하는 경우(LRU 캐시, 커널의 대기 큐)에 씁니다.

꼬리 질문 "연결 리스트의 사이클을 찾는 방법은?" → 한 칸씩 가는 포인터와 두 칸씩 가는 포인터를 동시에 움직여 만나면 사이클이 있습니다(플로이드 알고리즘, O(n) 시간 O(1) 공간).

감점 포인트 "연결 리스트 삽입은 항상 O(1)"(위치 탐색 비용 누락).

Q95. 스택과 큐를 설명하고 활용 예를 들어 주세요.

모범 답변 스택은 마지막에 넣은 것을 먼저 꺼내는 LIFO 구조로, 함수 호출 스택, 괄호 짝 검사, 수식 계산, 깊이 우선 탐색, 실행 취소에 씁니다. 큐는 먼저 넣은 것을 먼저 꺼내는 FIFO 구조로, 작업 대기열, 너비 우선 탐색, 버퍼, 생산자-소비자에 씁니다. 배열로 큐를 만들 때는 앞에서 꺼낼 때마다 원소를 옮기지 않도록 원형 큐(인덱스를 모듈러로 순환)로 구현하고, 가득 참과 비어 있음을 구분하기 위해 개수를 따로 두거나 한 칸을 비웁니다. 금융 시스템에서는 전문 송신 대기열, 배치 작업 큐가 큐의 예입니다.

꼬리 질문 "스택 두 개로 큐를 만들려면?" → 넣기용 스택에 넣고, 꺼낼 때 꺼내기용 스택이 비었으면 넣기용을 모두 옮긴 뒤 꺼냅니다. 상각 O(1)입니다.

감점 포인트 원형 큐의 가득 참/비어 있음 판정을 설명하지 못함.

Q96. 해시 테이블의 동작과 충돌 해결 방법은?

모범 답변 해시 함수로 키를 버킷 인덱스로 바꿔 평균 O(1)에 삽입·조회·삭제하는 구조입니다. 서로 다른 키가 같은 버킷에 오는 충돌은 체이닝(버킷마다 연결 리스트)이나 개방 주소법(선형·이차 탐사, 이중 해싱으로 빈 칸 탐색)으로 해결합니다. 적재율(원소 수/버킷 수)이 높아지면 충돌이 늘어 성능이 떨어지므로, 일정 적재율(예: 0.75)을 넘으면 크기를 늘려 재해싱합니다. 최악의 경우(모두 같은 버킷) O(n)이 되므로 키 분포에 맞는 해시 함수가 중요하고, 외부 입력 키라면 해시 충돌 공격도 고려합니다. 개방 주소법에서 삭제는 빈 칸이 아니라 "삭제됨" 표시를 남겨야 탐색이 끊기지 않습니다.

꼬리 질문 "해시 테이블로 범위 검색을 할 수 있나?" → 순서가 없으므로 비효율적입니다. 범위 검색이 필요하면 균형 트리나 B+트리를 씁니다.

감점 포인트 "해시는 항상 O(1)"이라는 단정.

Q97. 정렬 알고리즘을 비교해 주세요.

모범 답변 버블·선택·삽입 정렬은 O(n²)이지만, 삽입 정렬은 거의 정렬된 데이터에서 O(n)에 가깝고 작은 배열에 빨라 다른 정렬의 마무리에 쓰입니다. 퀵 정렬은 평균 O(n log n)이고 캐시 효율이 좋아 실전에서 빠르지만, 피벗 선택이 나쁘면 최악 O(n²)이고 불안정합니다. 병합 정렬은 항상 O(n log n)이고 안정적이며, 메모리에 다 들어가지 않는 대용량 파일의 외부 정렬에 쓰이지만 O(n) 추가 공간이 필요합니다. 힙 정렬은 최악에도 O(n log n), 추가 공간 O(1)이지만 캐시 효율이 낮습니다. 비교 기반 정렬의 하한은 O(n log n)이고, 키 범위가 제한되면 계수·기수 정렬로 O(n)이 가능합니다.

꼬리 질문 "안정 정렬이 중요한 예는?" → 거래내역을 먼저 시각으로 정렬한 뒤 계좌번호로 다시 정렬할 때, 같은 계좌 안에서 시각 순서가 유지되어야 하는 경우입니다.

감점 포인트 퀵 정렬의 최악 경우나 안정성을 모름.

Q98. 이진 탐색의 조건과 구현 시 주의점은?

모범 답변 이진 탐색은 정렬된 배열에서 가운데 값과 비교해 탐색 범위를 절반씩 줄이는 방법으로 O(log n)입니다. 데이터가 정렬되어 있고 임의 접근이 가능해야 합니다. 구현 시 중간값을 (lo + hi) / 2로 계산하면 큰 인덱스에서 오버플로가 날 수 있어 lo + (hi - lo) / 2로 쓰고, 반복 조건과 경계 갱신(lo = mid + 1, hi = mid - 1)을 일관되게 해 무한 루프를 막습니다. 중복 값이 있을 때 첫 위치나 마지막 위치를 찾는 lower/upper bound 변형도 자주 나옵니다. C 표준 라이브러리의 bsearch도 쓸 수 있습니다.

꼬리 질문 "1,000만 건이면 최대 몇 번 비교하나?" → log₂(10⁷) ≈ 23.3이므로 최대 24번입니다.

감점 포인트 정렬 전제를 빠뜨림.

Q99. 트리, 이진 탐색 트리, 균형 트리의 차이는?

모범 답변 트리는 사이클 없는 계층 구조이고, 이진 탐색 트리(BST)는 왼쪽 서브트리 값 < 노드 < 오른쪽 서브트리 값을 만족해 탐색·삽입·삭제가 트리 높이에 비례합니다. 정렬된 순서로 삽입하면 BST는 한쪽으로 치우쳐 연결 리스트처럼 O(n)이 됩니다. AVL 트리나 레드-블랙 트리 같은 균형 트리는 회전으로 높이를 O(log n)으로 유지해 최악에도 O(log n)을 보장하고, 중위 순회로 정렬된 순서를 얻을 수 있어 범위 검색이 가능합니다. 디스크 기반에서는 노드 하나에 많은 키를 담는 B-트리 계열을 씁니다.

꼬리 질문 "힙과 BST의 차이는?" → 힙은 부모가 자식보다 크거나(작거나) 같다는 조건만 있어 최대·최소값을 O(1)로 보지만 임의 탐색은 O(n)이고, 우선순위 큐에 씁니다.

감점 포인트 BST의 최악 경우를 모름.

Q100. 그래프 탐색 BFS와 DFS의 차이는?

모범 답변 BFS는 시작점에서 가까운 정점부터 큐로 차례로 방문해, 가중치 없는 그래프에서 최단 경로를 찾습니다. DFS는 한 경로를 끝까지 따라간 뒤 되돌아오는 방식으로 스택이나 재귀로 구현하며, 연결 요소, 사이클 탐지, 위상 정렬에 씁니다. 둘 다 인접 리스트로 O(V + E)이고 방문 표시가 필요합니다. 재귀 DFS는 깊은 그래프에서 스택 오버플로가 날 수 있습니다. 가중치가 있는 최단 경로는 다익스트라(음수 가중치 불가), 데드락 탐지의 대기 그래프 사이클 검사는 DFS의 응용입니다.

꼬리 질문 "배치 작업의 선후 관계로 실행 순서를 정하려면?" → 작업을 정점, 선후 관계를 간선으로 하는 DAG에서 위상 정렬을 합니다. 사이클이 있으면 실행 불가능한 의존성입니다.

감점 포인트 최단 경로에 DFS를 쓴다고 답함.

Q101. 동적 계획법(DP)과 분할 정복, 그리디의 차이는?

모범 답변 분할 정복은 문제를 겹치지 않는 부분 문제로 나눠 각각 풀고 합치는 방식(병합 정렬)입니다. 동적 계획법은 부분 문제가 겹칠 때 그 결과를 표에 저장해 재사용하는 방식으로, 최적 부분 구조와 중복 부분 문제가 있을 때 씁니다(피보나치, 배낭 문제, 최장 공통 부분 수열). 그리디는 매 단계 지금 가장 좋아 보이는 선택을 하는 방식으로 빠르지만, 탐욕 선택 속성이 증명된 문제(활동 선택, 다익스트라, 특정 화폐 체계의 거스름돈)에서만 최적을 보장합니다. 예를 들어 화폐 단위가 1, 4, 6원이면 8원 거스름돈은 그리디(6+1+1, 3개)보다 DP(4+4, 2개)가 정답입니다.

꼬리 질문 "메모이제이션과 바텀업의 차이는?" → 메모이제이션은 재귀로 필요할 때 계산해 저장하고, 바텀업은 작은 문제부터 표를 채워 재귀 비용과 스택 위험이 없습니다.

감점 포인트 그리디가 항상 최적이라고 답함.

Q102. 계정계, 정보계, 대외계의 차이를 설명해 주세요.

모범 답변 계정계는 예금·대출·외환 같은 은행 본업의 거래를 처리하고 원장을 관리하는 핵심 시스템으로, 입출금·이체 같은 온라인 거래와 일마감·이자 계산 같은 배치를 수행합니다. 정합성과 가용성이 최우선이라 검증된 기술과 엄격한 변경 관리를 적용합니다. 정보계는 계정계 데이터를 적재해 경영 분석, 리스크 관리, 감독기관 보고, 마케팅에 쓰는 분석 중심 시스템입니다. 대외계는 금융공동망, 타 금융기관, 카드사, 공공기관 등 외부와 전문을 주고받는 연계 시스템으로, 전문 형식 변환, 라우팅, 송수신 대사를 담당합니다. 고객 접점인 인터넷뱅킹·모바일·창구 단말은 채널계로 구분하기도 합니다.

꼬리 질문 "정보계 조회를 계정계 DB에 직접 하면 안 되는 이유는?" → 대량 분석 쿼리가 온라인 거래의 자원(CPU, I/O, 잠금)을 빼앗아 응답 지연이나 장애를 일으킬 수 있어 분리합니다.

감점 포인트 계정계를 "회계 시스템"으로만 이해.

Q103. 온라인 거래와 배치 처리의 차이는?

모범 답변 온라인 거래는 고객 요청에 즉시 응답하는 건별 실시간 처리로, 짧은 응답 시간과 높은 동시성, 건별 정합성이 중요합니다. 배치는 정해진 시점에 대량 데이터를 일괄 처리하는 것으로, 일마감, 이자 결산, 대외기관 파일 송수신, 정보계 적재가 해당하며, 처리량과 정해진 시간 창 안의 완료, 장애 시 재처리 가능성이 중요합니다. 같은 원장을 다루므로 배치가 원장을 갱신하는 동안 온라인과 충돌하지 않도록 작업 시간대를 나누거나, 잠금 범위를 짧게 하고, 업무 일자 전환으로 배치 대상과 온라인 거래를 구분합니다.

꼬리 질문 "배치가 시간 안에 안 끝나면?" → 병목 작업을 측정해 I/O 단위·SQL·커밋 주기를 개선하고, 계좌 범위로 분할 병렬 처리하며, 선후 관계를 재검토해 병렬 가능한 작업을 늘립니다.

감점 포인트 배치를 "야간에 도는 프로그램"으로만 설명하고 재처리를 모름.

Q104. 금액 계산에서 반올림·절사 규칙은 왜 중요한가요?

모범 답변 이자, 수수료, 세금, 환율 계산은 원 미만 단수가 생기는데, 처리 규칙(절사·반올림·절상)과 적용 시점(건별인지 합계인지)에 따라 결과가 달라집니다. 예를 들어 계좌별 이자를 절사해 합한 값과 합계 잔액으로 한 번에 계산한 값은 다릅니다. 이 차이가 쌓이면 고객 민원, 대사 불일치, 회계 오류가 되므로, 상품 약관과 업무 규정에 정해진 규칙을 코드에 정확히 반영하고 모든 시스템이 같은 공통 함수를 쓰게 합니다. 계산은 정수로 하고, 음수의 반올림 방향(0 쪽인지, 음의 무한대 쪽인지)도 명시합니다.

꼬리 질문 "C에서 음수 정수 나눗셈의 방향은?" → C99부터 0 쪽으로 버림(truncation)으로 정해졌습니다. −7/2는 −3입니다.

감점 포인트 "double로 계산한 뒤 round()하면 된다".

Q105. 전문(電文)이란 무엇이고, 고정 길이 전문의 장단점은?

모범 답변 전문은 시스템 간에 주고받는 정해진 형식의 메시지로, 보통 공통부(전문 길이, 종별, 거래 코드, 추적번호, 응답 코드, 일시)와 개별부(거래별 데이터)로 구성됩니다. 금융권은 필드마다 위치와 길이가 고정된 텍스트 전문을 많이 씁니다. 장점은 파싱이 단순·빠르고, 엔디안이나 플랫폼 차이가 없으며, 사람이 덤프를 읽기 쉽고, 기관 간 표준으로 오래 안정적으로 쓸 수 있다는 것입니다. 단점은 필드 추가·길이 변경 시 모든 연계 기관이 함께 바꿔야 하고, 빈 공간 패딩으로 크기가 크며, 반복부 처리가 번거롭다는 것입니다. 최근에는 오픈 API에서 JSON도 함께 씁니다.

꼬리 질문 "한글 필드에서 주의할 점은?" → 인코딩(EUC-KR, UTF-8, EBCDIC 계열)에 따라 바이트 길이가 다르고, 고정 길이에서 자를 때 글자 중간이 잘리지 않게 해야 합니다.

감점 포인트 전문과 프로토콜(TCP)을 혼동.

Q106. 이중화와 DR(재해 복구)을 설명해 주세요. RTO와 RPO는?

모범 답변 이중화는 서버·네트워크·저장 장치·DB를 두 벌 이상 두어 하나가 고장 나도 서비스를 계속하는 것으로, 둘 다 처리하는 Active-Active와 대기했다가 넘겨받는 Active-Standby가 있습니다. DR은 데이터센터 전체가 화재·지진 등으로 마비될 때를 대비해 지리적으로 떨어진 재해 복구 센터에 시스템과 데이터를 복제해 두는 것입니다. RTO(목표 복구 시간)는 장애 후 서비스를 재개하기까지 허용되는 시간, RPO(목표 복구 시점)는 잃어도 되는 데이터의 시간 범위입니다. 금융권 핵심 시스템은 규정상 RTO를 짧게(수 시간 이내) 요구받고, 정기적으로 DR 전환 훈련을 합니다.

꼬리 질문 "동기 복제와 비동기 복제의 차이는?" → 동기 복제는 원격 저장이 끝나야 커밋을 완료해 RPO가 0에 가깝지만 거리만큼 지연이 늘고, 비동기 복제는 빠르지만 장애 시 최근 데이터가 유실될 수 있습니다.

감점 포인트 백업과 DR을 같은 것으로 설명. 백업은 데이터 보존, DR은 서비스 연속성입니다.

Q107. 금융 시스템에서 "결과 불명 거래"는 어떻게 처리하나요?

모범 답변 요청을 보냈는데 타임아웃이나 연결 끊김으로 응답을 받지 못하면, 상대 시스템에서 거래가 처리되었는지 알 수 없습니다. 이때 실패로 간주해 다시 보내면 이중 출금·이중 이체가 생길 수 있으므로, 추적번호를 이용한 결과 조회 전문으로 처리 여부를 확인하거나, 망 취소 전문을 보내 상대가 처리했다면 취소하게 합니다. 이를 위해 모든 요청에 고유 거래 추적번호를 붙이고, 수신 측은 같은 추적번호의 중복 요청을 거르는 멱등 처리를 합니다. 확인되지 않은 거래는 일마감 대사에서 반드시 정리합니다.

꼬리 질문 "망 취소 전문도 응답이 안 오면?" → 정해진 횟수만큼 재전송하고, 그래도 안 되면 대사 파일로 사후 정리하는 절차를 둡니다.

감점 포인트 "타임아웃이면 재시도한다".

Q108. 대사(reconciliation)란 무엇인가요?

모범 답변 독립적으로 관리되는 두 기록이 같은 사실을 나타내는지 비교·검증하는 작업입니다. 계좌 원장 합계와 총계정원장의 계정과목 잔액, 우리 은행의 거래 내역과 대외기관(금융공동망, 카드사)이 보낸 거래 내역, 원장과 거래 로그 등을 건수와 금액으로 맞춰 봅니다. 불일치가 있으면 원인(누락, 중복, 결과 불명 거래, 시각 차이)을 찾아 정정합니다. 프로그램 버그, 데이터 손상, 내부 부정을 조기에 발견하는 금융 시스템의 핵심 통제 장치입니다.

꼬리 질문 "대사 파일을 받았는데 건수는 맞고 금액이 다르면?" → 같은 건의 금액이 다른 경우(수수료 포함 여부, 반올림 차이)나 서로 다른 건이 우연히 건수만 맞는 경우일 수 있어, 추적번호 기준으로 건별 대조합니다.

감점 포인트 대사를 "데이터 검증"으로만 말하고 실제 대상을 예로 들지 못함.

Q109. 금융 보안에서 중요한 개인정보·암호화 원칙은?

모범 답변 고유식별정보(주민등록번호 등), 계좌번호·카드번호, 비밀번호 같은 민감 정보는 저장 시 암호화하고, 비밀번호는 복호화할 수 없도록 솔트를 쓴 안전한 해시(일방향 암호화)로 저장합니다. 전송 구간은 TLS 등으로 암호화하고, 화면·로그·전문 덤프에는 마스킹해 출력하며, 암호 키는 HSM 같은 별도 장치나 키 관리 체계로 분리 보관합니다. 접근 권한은 최소 권한 원칙으로 부여하고 접근 기록을 남겨 감사합니다. 국내에서는 전자금융감독규정, 개인정보 보호법, 신용정보법 등이 이를 요구하므로, 개발자는 시큐어 코딩 가이드를 지키고 운영 데이터를 개발·테스트에 그대로 쓰지 않습니다(변환·가명 처리).

꼬리 질문 "비밀번호를 SHA-256 한 번으로 저장하면 안 되는 이유는?" → 빠른 해시는 무차별 대입과 미리 계산한 테이블 공격에 취약하므로, 솔트와 반복 횟수가 있는 PBKDF2, bcrypt, scrypt, Argon2 같은 함수를 씁니다.

감점 포인트 암호화와 해시를 구분하지 못함.

Q110. 시큐어 코딩에서 C 개발자가 특히 주의할 점은?

모범 답변 메모리 안전이 가장 큽니다. 버퍼 오버플로(길이 검증, 안전한 함수), 정수 오버플로(연산 전 범위 검사, 특히 길이 계산), 형식 문자열 취약점(printf(user_input) 금지, 항상 printf("%s", s)), use-after-free와 double free, 초기화되지 않은 메모리 사용을 막아야 합니다. 그 외 외부 입력(전문, 파일, 환경 변수) 전부 검증, 오류 처리 누락 금지, 민감 정보를 메모리에서 사용 후 지우기(최적화로 지워지지 않는 방식으로), 로그에 민감 정보 출력 금지, 경쟁 조건(TOCTOU) 주의가 있습니다. 정적 분석 도구와 ASan·퍼징으로 검증합니다.

꼬리 질문 "memset으로 비밀번호 버퍼를 지웠는데 남아 있을 수 있는 이유는?" → 이후 사용되지 않는 버퍼에 대한 memset을 컴파일러가 불필요한 쓰기로 보고 제거할 수 있어, explicit_bzero나 memset_s, volatile 포인터를 통한 지우기를 씁니다.

감점 포인트 웹 취약점(XSS 등)만 나열하고 C 고유 위험을 모름.

Q111. 장애가 발생했을 때 어떻게 대응하나요?

모범 답변 가장 먼저 영향 범위(어떤 거래, 어떤 채널, 몇 건)를 파악하고 보고 체계에 따라 즉시 알립니다. 원인 분석보다 서비스 복구가 우선이므로, 최근 변경이 있었다면 롤백, 특정 프로세스 문제라면 재기동이나 이중화 전환으로 먼저 서비스를 살립니다. 그다음 로그, 코어 덤프, 모니터링 지표, 거래 추적번호로 원인을 분석하고, 장애 동안의 결과 불명 거래와 데이터 정합성을 대사로 확인해 정정합니다. 마지막으로 근본 원인과 재발 방지 대책(코드 수정, 모니터링 추가, 절차 개선)을 문서로 남깁니다.

꼬리 질문 "재기동했더니 해결되었다면 끝인가?" → 아닙니다. 메모리 누수, 자원 고갈, 경쟁 조건 같은 근본 원인은 다시 발생하므로 반드시 원인을 찾아야 합니다.

감점 포인트 원인 분석부터 하겠다며 서비스 복구를 뒤로 미루는 답, 또는 데이터 정합성 확인을 빠뜨린 답.

Q112. 운영 반영(배포) 시 주의할 점은?

모범 답변 금융권은 변경 관리 절차에 따라 승인된 소스만 빌드 서버에서 운영과 같은 환경으로 빌드하고, 테스트·검증 서버에서 통합 테스트와 회귀 테스트를 마친 뒤 반영합니다. 반영은 거래량이 적은 시간대에, 영향 범위와 순서(공통 모듈 → 업무 모듈, DB 변경 → 프로그램), 롤백 방법을 미리 문서화해 수행합니다. 공통 구조체나 전문 레이아웃 변경은 관련 프로그램을 모두 함께 재빌드·반영해야 하고, 반영 직후 모니터링과 샘플 거래로 정상 여부를 확인합니다. 개발자가 운영 서버에 직접 접속해 파일을 바꾸는 일은 원칙적으로 금지되며, 직무 분리(개발자와 운영 반영자 분리)를 지킵니다.

꼬리 질문 "무중단 반영은 어떻게 하나?" → 이중화된 서버를 한 대씩 서비스에서 빼고 반영한 뒤 넣는 순차 반영, 또는 새 버전을 띄우고 트래픽을 전환하는 방식을 씁니다. 신·구 버전이 동시에 동작하는 동안 전문·DB 호환성을 유지해야 합니다.

감점 포인트 롤백 계획 없이 "테스트를 잘하면 된다".

Q113. 레거시 C 코드를 유지보수할 때의 원칙은?

모범 답변 먼저 현재 동작을 정확히 파악하고, 수정 전후 결과를 비교할 수 있는 테스트(입력 전문과 기대 출력)를 확보합니다. 변경 범위는 요구사항에 필요한 만큼으로 최소화하고, 같은 공통 함수나 구조체를 쓰는 다른 프로그램에 미치는 영향을 조사합니다. 컴파일 경고를 줄이고 정적 분석으로 기존 위험을 파악하되, 동작하는 코드를 대규모로 고치는 리팩터링은 별도 계획으로 분리합니다. 코드 표준(명명, 오류 처리, 로그 형식)은 기존 시스템의 관례를 따릅니다. 오래된 코드가 이상해 보여도 업무 규칙이 숨어 있을 수 있으므로 함부로 "정리"하지 않습니다.

꼬리 질문 "64비트 이전 과제를 맡으면 무엇부터 보겠나?" → long과 포인터 크기 가정, printf 형식 지정자, 구조체를 그대로 쓰는 파일·공유 메모리, 엔디안과 char 부호 차이를 우선 점검합니다.

감점 포인트 "다 새로 짜겠다".

Q114. 금융 IT 개발자에게 가장 중요한 역량은 무엇이라고 생각하나요?

모범 답변 정확성에 대한 책임감이라고 생각합니다. 금융 시스템의 1원 오류는 고객 자산과 신뢰의 문제이므로, 정상 경로보다 실패 경로(입력 오류, 장애, 결과 불명, 재처리)를 먼저 생각하는 습관이 중요합니다. 이를 뒷받침하는 기술 역량으로는 메모리와 데이터 표현에 대한 정확한 이해, 트랜잭션과 정합성 설계, 장애 분석 능력이 필요하고, 업무 규칙을 이해하려는 자세와 변경 관리 절차를 지키는 규율도 필요합니다. 저는 이 과정에서 미니 코어뱅킹을 만들며 거래로그 선기록과 멱등 복구, 일마감 대사를 직접 구현했고, 장애를 일부러 주입해 복구를 검증해 보면서 이 점을 체감했습니다.

꼬리 질문 "그 경험에서 가장 어려웠던 점은?" → 자기 경험을 구체적으로(무엇이 문제였고, 어떻게 확인했고, 무엇을 배웠는지) 1분 안에 말할 수 있게 준비합니다.

감점 포인트 추상적인 덕목만 나열하고 근거 경험이 없는 답.

은행 시스템에서는 — 면접관이 보는 것

금융권 전산직 기술 면접관은 대부분 현업 개발자이거나 운영 책임자입니다. 그들이 확인하고 싶은 것은 "어려운 용어를 아는가"보다 "우리 시스템에 사고를 내지 않을 사람인가"입니다. 그래서 모르는 것을 아는 척하는 답변, 실패 경로를 생각하지 않는 답변, "그냥 재시도하면 된다" 같은 답변에 특히 민감합니다. 반대로 "확실하지 않지만 이렇게 확인해 보겠습니다"라는 태도와, 정합성·재처리·로그 같은 키워드를 자연스럽게 쓰는 지원자에게 높은 점수를 줍니다.
