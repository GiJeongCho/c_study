19-1전처리 지시자

전처리기란 무엇인가

1장에서 소스 코드가 실행 파일이 되는 과정을 "컴파일"이라고 뭉뚱그려 불렀지만, 실제로는 네 단계가 있습니다. 그 첫 단계가 전처리(preprocessing)입니다. 전처리기는 C 문법을 이해하지 못하는 텍스트 치환기에 가깝습니다. #으로 시작하는 줄(전처리 지시자)을 찾아 파일을 끼워 넣고, 매크로를 글자 그대로 바꾸고, 조건에 맞지 않는 코드를 지운 뒤, 그 결과를 컴파일러에게 넘깁니다.

전처리 결과는 gcc -E로 직접 볼 수 있습니다. 매크로가 이상하게 동작할 때 가장 먼저 해 볼 일입니다.

gcc -E main.c -o main.i      # 전처리 결과만 저장
gcc -E main.c | tail -n 20   # 끝부분(내 코드)만 보기

전처리 지시자의 공통 규칙은 다음과 같습니다.

  • 줄의 첫 비공백 문자가 #이어야 합니다(앞에 공백은 허용).
  • 세미콜론으로 끝나지 않습니다. 줄바꿈이 지시자의 끝입니다.
  • 여러 줄로 쓰려면 줄 끝에 역슬래시(\)를 둡니다. 역슬래시 뒤에 공백이 있으면 안 됩니다.
  • 주석은 전처리 전에 공백 하나로 바뀌므로 지시자 뒤에 주석을 달아도 됩니다.

#include의 원리

#include는 지정한 파일의 내용을 그 자리에 통째로 복사해 붙여 넣습니다. 그 이상도 이하도 아닙니다. 헤더 파일이 특별한 파일이 아니라, 붙여 넣기 좋게 선언들을 모아 둔 평범한 텍스트 파일일 뿐입니다.

두 가지 형식이 있으며 차이는 파일을 찾는 위치입니다.

왜 그럴까? — 헤더 파일이 왜 필요할까?

C 컴파일러는 파일을 하나씩 따로 컴파일하며, 다른 파일의 내용을 보지 못합니다. main.c에서 account.c에 정의된 account_deposit을 호출하려면, 컴파일러는 적어도 그 함수의 매개변수 형과 반환형(원형)을 알아야 올바른 호출 코드를 만들 수 있습니다. 모든 .c 파일에 원형을 손으로 복사하면 하나가 바뀔 때 전부 고쳐야 하므로, 원형을 헤더 한 곳에 모아 두고 #include로 붙여 넣게 합니다. 헤더는 모듈의 공개 인터페이스(계약서) 역할을 합니다.

또한 #include는 단순 복사이므로 큰 헤더를 많이 포함하면 전처리 결과가 수만 줄로 커집니다. #include <stdio.h> 한 줄만 있는 hello.c도 gcc -E 결과는 수백 줄입니다. 대형 프로젝트의 빌드 시간이 긴 이유 중 하나입니다.

자주 하는 실수 — .c 파일을 #include 하기

#include "account.c"는 문법적으로는 가능하지만, account.c의 함수 정의가 포함한 파일에 복사됩니다. 그 파일과 account.c를 함께 링크하면 같은 함수가 두 번 정의되어 "multiple definition" 링크 오류가 납니다. 헤더에는 선언만, 소스에는 정의를 둡니다(19-2 참고).

#define: 기호 상수

#define 이름 대체텍스트는 이후 소스에서 이름이라는 토큰을 만나면 대체텍스트로 바꾸라는 지시입니다. 이런 이름을 매크로(macro)라고 합니다.

왜 그럴까? — 문자열 안의 MAX_ACCOUNTS는 왜 안 바뀔까?

전처리기는 소스를 글자 단위가 아니라 토큰(식별자, 숫자, 문자열 리터럴, 연산자) 단위로 봅니다. "MAX_ACCOUNTS는 ..."은 통째로 하나의 문자열 리터럴 토큰이므로 그 안의 글자는 매크로 이름으로 취급되지 않습니다. 마찬가지로 MAX_ACCOUNTS_X처럼 더 긴 식별자의 일부도 바뀌지 않습니다.

함수형 매크로와 괄호 함정

매크로에 매개변수를 줄 수 있습니다. 이름과 여는 괄호 사이에 공백이 없어야 함수형 매크로가 됩니다.

왜 그럴까? — 함수와 매크로는 무엇이 다른가

함수 호출 square(1 + 2)는 인자 식을 먼저 계산해 3이라는 값을 넘깁니다. 매크로는 전처리 단계에서 동작하므로 "계산"이라는 개념이 없습니다. 인자 1 + 2라는 토큰 열을 그대로 x 자리에 끼워 넣고, 그 결과를 컴파일러가 연산자 우선순위대로 해석합니다. 그래서 두 가지 괄호가 필요합니다.

  1. 각 매개변수를 괄호로: 인자 안의 낮은 우선순위 연산자(+, -, ?: 등)가 매크로 본문의 연산자와 섞이는 것을 막습니다.
  2. 전체를 괄호로: 매크로를 사용하는 바깥 식의 연산자(100 / 등)가 매크로 본문 일부와 결합하는 것을 막습니다.

은행 시스템에서는 — 수수료 매크로 사고

다음과 같은 매크로를 상상해 봅시다: #define FEE(amt) amt * 15 / 10000. FEE(a + b)는 a + b * 15 / 10000이 되어 a 전체가 수수료로 계산됩니다. total - FEE(x)는 total - x * 15 / 10000이라 우연히 맞지만, 10000 / FEE(x) 같은 다른 식에서는 틀립니다. 이런 버그는 대부분의 테스트 케이스(단일 변수 인자)를 통과하기 때문에 운영에서 특정 거래 유형에서만 금액이 틀리는 형태로 늦게 발견됩니다. 그래서 많은 금융권 코딩 표준은 "계산용 함수형 매크로 금지, static inline 함수 사용"을 규정합니다.

매크로의 부작용과 안전한 매크로 작성법

괄호를 완벽히 쳐도 해결되지 않는 문제가 있습니다. 매크로는 인자를 본문에 등장하는 횟수만큼 복사하므로, 부작용이 있는 인자는 여러 번 실행됩니다.

추적해 봅시다. MAX(i++, j)는 ((i++) > (j) ? (i++) : (j))입니다. 조건에서 5 > 3을 비교하며 i가 6이 되고, 참이므로 두 번째 i++가 실행되어 m에 6이 들어가고 i는 7이 됩니다. ?: 연산자의 조건 뒤에는 시퀀스 포인트가 있어서 이 경우는 미정의 동작은 아니지만, 의도(m=5, i=6)와 완전히 다릅니다.

MAX(next_seq(), 5)는 ((next_seq()) > (5) ? (next_seq()) : (5))입니다. 조건의 첫 호출이 10을 반환하고 10 > 5가 참이므로 next_seq()가 한 번 더 호출되어 20이 반환됩니다. 비교한 값(10)과 반환된 값(20)이 다르고, 일련번호가 하나 건너뛰어졌습니다. 거래 일련번호 채번 함수였다면 번호가 누락되는 사고입니다. inline 함수 max_int는 인자를 한 번만 평가하므로 10을 반환하고 호출도 한 번입니다.

이렇게 해결합니다 — 안전한 매크로 작성 규칙

  1. 계산을 하는 매크로는 가능하면 static inline 함수로 바꿉니다(C99). 형 검사도 받고, 인자가 한 번만 평가되며, 디버거에서 단계 실행도 됩니다. 최적화가 켜지면 매크로와 같은 속도입니다.
  2. 매크로를 써야 한다면 모든 매개변수와 전체 식을 괄호로 감쌉니다.
  3. 매크로 인자에 ++, --, 대입, 함수 호출을 넣지 않습니다. 매크로 이름을 대문자로 짓는 관례는 "이것은 매크로이니 조심하라"는 신호입니다.
  4. 여러 문장으로 된 매크로는 do { ... } while (0)으로 감쌉니다(아래).

왜 그럴까? — 왜 그냥 중괄호 { }가 아니라 do-while(0)일까?

#define M(a) { ...; ...; }로 정의하면 if (c) M(p); else ...는 if (c) { ... }; else ...가 됩니다. 중괄호 블록 뒤의 세미콜론은 빈 문장으로 해석되어 if 문이 거기서 끝나고, else가 짝을 잃어 컴파일 오류가 납니다. do { ... } while (0)은 뒤에 세미콜론이 반드시 필요한 하나의 완전한 문장이므로 일반 함수 호출과 똑같이 쓸 수 있습니다. 반복은 정확히 한 번이고, 컴파일러가 최적화로 반복 구조를 없애므로 비용도 없습니다.

# 연산자와 ## 연산자

함수형 매크로 본문에서만 쓸 수 있는 두 가지 특수 연산자가 있습니다.

  • # (문자열화, stringizing): 매개변수 앞에 붙이면 인자로 넘어온 토큰을 문자열 리터럴로 바꿉니다. #x에 balance가 오면 "balance"가 됩니다.
  • ## (토큰 결합, token pasting): 양쪽 토큰을 하나의 토큰으로 붙입니다. acc_ ## no는 acc_no라는 식별자가 됩니다.

왜 그럴까? — STR(LIMIT)은 왜 "LIMIT"이 될까?

규칙상 #나 ##의 피연산자가 되는 매개변수는 인자를 매크로 확장하기 전에 그대로 사용됩니다. 그래서 STR(LIMIT)은 LIMIT이 5000000으로 바뀌기 전에 문자열화되어 "LIMIT"이 됩니다. 반면 XSTR(LIMIT)에서 XSTR의 본문 STR(x)의 x는 #의 피연산자가 아니므로 먼저 5000000으로 완전히 확장된 뒤 STR에 넘어가고, 그 결과 "5000000"이 됩니다. 이 "두 단계 매크로" 기법은 버전 번호나 줄 번호(__LINE__)를 문자열로 만들 때 자주 씁니다.

SHOW에서 #expr " = %lld\n"은 두 문자열 리터럴이 나란히 놓인 것인데, C는 인접한 문자열 리터럴을 하나로 이어 붙이므로 하나의 서식 문자열이 됩니다.

여기서 잠깐 — 매크로로 코드 생성은 적당히

##로 함수와 변수를 찍어 내는 기법(X-매크로 등)은 반복 코드를 줄여 주지만, grep으로 get_balance를 검색해도 정의가 나오지 않아 유지보수자를 괴롭힙니다. 오류 코드 표와 메시지 표를 한 번에 정의하는 경우처럼 이득이 분명할 때만 쓰고, 주석으로 "GETTER 매크로가 get_xxx 함수를 생성함"을 남깁니다.

조건부 컴파일

조건부 컴파일은 조건에 따라 코드의 일부를 컴파일 대상에서 아예 빼 버리는 기능입니다. if 문은 실행 중에 분기하지만, #if는 전처리 단계에서 코드를 지우므로 빠진 코드는 실행 파일에 존재하지 않습니다.

지시자의미
#if 상수식정수 상수식이 0이 아니면 포함
#ifdef 이름 / #if defined(이름)매크로가 정의되어 있으면 포함
#ifndef 이름 / #if !defined(이름)정의되어 있지 않으면 포함
#elif, #else, #endif그 밖의 경우, 끝
#undef 이름매크로 정의 취소
#error 메시지전처리 단계에서 컴파일을 중단시키고 메시지 출력
gcc -Wall ex19-5.c -o app && ./app
gcc -Wall -DENV=2 ex19-5.c -o app && ./app
gcc -Wall -DDEBUG ex19-5.c -o app && ./app

왜 그럴까? — #if에서 정의되지 않은 이름은 어떻게 될까?

#if의 식에서 매크로로 정의되지 않은 식별자는 0으로 취급됩니다. 그래서 #if ENV == 2는 ENV가 정의되지 않아도 오류 없이 거짓이 됩니다. 편리하지만 오타(#if EVN == 2)도 조용히 0이 되어 운영 코드가 빠지는 위험이 있습니다. gcc의 -Wundef 옵션을 켜면 이런 경우 경고해 줍니다. 위 예제처럼 #ifndef로 기본값을 먼저 정의해 두는 것도 좋은 습관입니다. 또한 #if는 전처리 단계라 sizeof나 enum 상수, const 변수를 쓸 수 없습니다(전처리기는 C의 형을 모름).

자주 하는 실수 — 운영 설정을 소스에 하드코딩

위 예제는 조건부 컴파일을 보여 주기 위한 것입니다. 실무에서 운영 접속 정보(호스트, 계정, 비밀번호)를 소스나 실행 파일에 넣는 것은 금지입니다. 접속 정보는 권한이 통제된 설정 파일이나 비밀 관리 시스템에서 실행 시점에 읽고, 조건부 컴파일은 플랫폼 차이(윈도우/리눅스), 디버그 코드, 기능 토글 정도에만 씁니다. 또 개발/운영 빌드의 코드가 크게 달라지면 "테스트한 바이너리와 운영 바이너리가 다른" 문제가 생기므로 최소화합니다.

컴파일러는 몇 가지 매크로를 미리 정의해 둡니다.

이것들을 조합하면 "어느 파일 몇 번째 줄, 어느 함수에서 찍은 로그인지" 자동으로 남기는 로그 매크로를 만들 수 있습니다. 함수로는 불가능합니다. 함수 안에서 __LINE__을 쓰면 항상 그 함수 내부의 줄 번호가 나오기 때문입니다. 매크로는 호출한 자리에서 펼쳐지므로 호출한 곳의 위치가 찍힙니다.

왜 그럴까? — 디버그 로그가 왜 안 나왔을까? 그리고 비용은?

LOG_LEVEL이 LOG_INFO(2)이므로 LOGD의 조건 3 <= 2가 거짓입니다. 이 조건은 상수끼리의 비교라서 컴파일러가 컴파일 시점에 거짓임을 알고 그 블록을 통째로 제거합니다(dead code elimination). 따라서 운영 빌드에서 디버그 로그는 실행 비용이 0입니다. 그러면서도 #if로 지우는 것과 달리 컴파일러가 서식 문자열과 인자의 형을 계속 검사해 주므로, 디버그 로그 코드가 썩지 않습니다. gcc -DLOG_LEVEL=3으로 빌드하면 디버그 로그가 나옵니다.

이 매크로는 인자가 서식 문자열 하나뿐인 LOGI("시작")도 처리할 수 있도록 서식과 인자를 통째로 __VA_ARGS__로 받아 두 번째 fprintf에 넘겼습니다. #define LOG(fmt, ...) fprintf(stderr, fmt, __VA_ARGS__)처럼 쓰면 가변 인자가 없을 때 끝에 쉼표가 남아 컴파일 오류가 납니다. gcc 확장 , ##__VA_ARGS__나 C23의 __VA_OPT__로 해결할 수도 있습니다.

은행 시스템에서는 — 로그 표준과 개인정보

금융권 시스템의 로그는 장애 분석과 감사(audit)의 근거이므로 형식이 표준화되어 있습니다. 보통 시각(밀리초까지), 프로세스/스레드 ID, 거래 추적 번호(글로벌 ID), 소스 위치, 레벨, 메시지를 한 줄에 남기며, 위의 LOG 매크로가 그 출발점입니다. 그리고 반드시 지켜야 할 규칙이 있습니다. 계좌 비밀번호, 카드 번호 전체, CVC, 주민등록번호 같은 민감 정보를 로그에 평문으로 남기면 안 됩니다. 디버그 레벨이라도 마찬가지이며, 운영에서 디버그 레벨을 잠시 켰다가 민감 정보가 대량으로 로그에 남는 사고가 실제로 발생합니다. 그래서 로그 함수 단계에서 마스킹(예: 110-***-***890)을 강제하는 설계를 씁니다.

#pragma와 기타 지시자

#pragma는 컴파일러에게 표준 밖의 특별한 지시를 내리는 통로입니다. 내용은 컴파일러마다 다르며, 컴파일러가 모르는 pragma는 무시해야 한다고 표준이 정하고 있습니다(경고는 낼 수 있음).

자주 하는 실수 — pack을 헤더에 넣고 pop을 잊기

#pragma pack(1)만 쓰고 복원하지 않은 헤더를 포함하면, 그 뒤에 포함된 다른 헤더의 구조체까지 1바이트 정렬로 바뀝니다. 같은 구조체를 어떤 .c 파일은 패딩 있게, 어떤 파일은 패딩 없게 해석하는 상황이 되어, 함수 사이에 구조체 포인터를 넘기면 멤버 값이 엉뚱하게 읽힙니다. 컴파일도 링크도 성공하므로 찾기 매우 어려운 버그입니다. 반드시 push/pop 쌍으로 쓰고, 꼭 필요한 구조체만 감쌉니다. 또한 packed 구조체 멤버의 주소를 int *로 받아 쓰면 비정렬 접근이 되므로 피합니다.

그 밖에 #line 번호 "파일"(코드 생성기가 원래 소스 위치를 알려 줄 때, 예: Pro*C 같은 내장 SQL 전처리기의 출력)과 C11의 _Static_assert(전처리 지시자가 아니라 선언이지만, 컴파일 시점 검증이라는 점에서 #error와 짝을 이룸)도 알아 두면 좋습니다.

19-2분할 컴파일

왜 파일을 나누는가: 헤더와 소스의 분리

지금까지는 프로그램 전체를 파일 하나에 썼습니다. 하지만 수만 줄짜리 프로그램을 한 파일에 두면 (1) 한 줄만 고쳐도 전체를 다시 컴파일해야 하고, (2) 여러 개발자가 같은 파일을 동시에 고치다 충돌이 나며, (3) 계좌 처리, 이자 계산, 전문 처리처럼 관심사가 다른 코드가 뒤엉킵니다. 그래서 C 프로젝트는 기능 단위의 모듈로 나누고, 모듈마다 두 개의 파일을 만듭니다.

  • 헤더 파일(.h): 모듈이 외부에 공개하는 것의 선언. 자료형 정의(구조체, enum, typedef), 함수 원형, 외부 변수 선언(extern), 매크로 상수.
  • 소스 파일(.c): 그 선언의 정의(구현). 함수 본문, 전역 변수의 실제 정의, 외부에 숨길 내부 함수(static).

왜 그럴까? — 구현 파일도 자기 헤더를 #include 하는 이유

account.c가 account.h를 포함하지 않아도 컴파일은 됩니다. 하지만 포함해야 컴파일러가 선언과 정의의 일치를 검사할 수 있습니다. 헤더에는 int account_deposit(Account *a, Money amt);라고 쓰고 구현에서 실수로 int account_deposit(Account *a, int amt)라고 정의하면, account.c가 헤더를 포함한 경우에만 "conflicting types" 오류가 납니다. 포함하지 않으면 컴파일도 링크도 성공하고(링커는 이름만 보므로), 실행 중에 금액이 잘못 전달되는 끔찍한 버그가 됩니다. 그래서 "모든 .c 파일은 자기 .h를 가장 먼저 #include한다"는 규칙을 둡니다. 맨 먼저 포함하면 헤더가 필요한 다른 헤더를 스스로 포함하고 있는지(자기 완결성)도 함께 검증됩니다.

번역 단위와 링크의 원리

컴파일러가 한 번에 처리하는 단위를 번역 단위(translation unit)라고 합니다. .c 파일 하나에 그 파일이 #include한 모든 내용을 붙여 넣은 전처리 결과가 번역 단위 하나입니다. 컴파일러는 번역 단위마다 독립적으로 목적 파일(.o)을 만들고, 각 목적 파일에는 기계어와 함께 심볼 표가 들어갑니다.

  • 정의한 심볼(defined): 이 파일 안에 본체가 있는 함수·전역 변수. 다른 파일에 제공할 수 있음.
  • 미정의 심볼(undefined): 이 파일이 사용하지만 다른 곳에 있다고 믿는 함수·변수. 주소가 비어 있음.

링커는 모든 목적 파일과 라이브러리를 모아, 각 미정의 심볼을 어딘가의 정의와 연결(주소를 채움)합니다. 이것이 링크(link)입니다.

심볼 표는 nm 명령으로 직접 볼 수 있습니다(대문자는 외부 공개, 소문자는 파일 내부 전용).

extern: 여러 파일이 공유하는 전역 변수

함수는 원형만 있으면 다른 파일에서 쓸 수 있습니다. 전역 변수도 다른 파일과 공유할 수 있는데, 이때 선언(declaration)과 정의(definition)를 엄격히 구분해야 합니다.

구분예메모리 할당프로그램 전체에서
정의int g_count = 0;함정확히 한 번
선언extern int g_count;안 함("어딘가에 있다")여러 번 가능

규칙은 간단합니다. 헤더에는 extern 선언을, 정확히 하나의 .c 파일에 정의를 둡니다.

왜 그럴까? — 헤더에 정의를 두면 왜 안 될까?

헤더에 long long g_daily_limit = 50000000LL;(정의)를 두고 두 .c 파일이 그 헤더를 포함하면, #include는 복사이므로 두 번역 단위가 각각 같은 이름의 변수를 정의합니다. 각 파일은 따로 컴파일되므로 컴파일 단계에서는 아무 문제가 없지만, 링커가 두 목적 파일을 합치는 순간 같은 심볼의 정의가 두 개라서 "multiple definition" 오류를 냅니다. 이것이 C의 단일 정의 규칙(one definition rule)입니다.

참고로 초기값이 없는 int g_count;(잠정 정의, tentative definition)를 헤더에 두면 예전 gcc(9 이하)는 "공통 심볼(common)"로 처리해 오류 없이 하나로 합쳐 주었습니다. gcc 10부터는 기본값이 -fno-common으로 바뀌어 이것도 multiple definition 오류가 납니다. 오래된 코드를 새 컴파일러로 빌드할 때 갑자기 링크 오류가 쏟아지는 흔한 이유입니다.

자주 하는 실수 — 전역 변수 남용

extern 전역 변수는 어느 파일에서든 바꿀 수 있어서, 값이 이상해졌을 때 누가 바꿨는지 추적하기 어렵고 멀티스레드 환경에서는 경쟁 상태(race condition)의 원인이 됩니다. 꼭 필요한 설정값 정도만 전역으로 두고, 가능하면 static으로 숨긴 뒤 접근 함수(get_daily_limit())를 공개하는 방식을 씁니다.

static 함수와 static 전역 변수: 파일 안에 숨기기

함수나 파일 범위 변수 앞에 static을 붙이면 내부 링크(internal linkage)가 되어 그 번역 단위 안에서만 보입니다. 다른 파일에서 같은 이름을 써도 충돌하지 않고, 다른 파일에서 extern으로 접근할 수도 없습니다. 14장에서 배운 "함수 안의 static 지역 변수"(수명 연장)와 같은 키워드지만 의미가 다르다는 점에 주의하십시오.

왜 그럴까? — 왜 내부 함수에 static을 붙여야 할까?

  1. 이름 충돌 방지: C에는 네임스페이스가 없습니다. 수천 개의 파일이 하나의 실행 파일로 링크되는데, account.c와 card.c가 둘 다 check()라는 외부 함수를 정의하면 multiple definition 오류가 납니다. static이면 각자 자기 파일의 check를 씁니다.
  2. 캡슐화: 공개 함수는 다른 팀이 의존할 수 있는 "계약"이 됩니다. 내부 도우미 함수를 static으로 숨기면 나중에 마음대로 바꾸거나 지워도 다른 모듈이 깨지지 않습니다. C로 객체지향의 private을 흉내 내는 방법입니다.
  3. 최적화: 컴파일러는 static 함수가 이 파일 밖에서 호출되지 않는다는 것을 알기 때문에 적극적으로 인라인하거나, 쓰이지 않으면 제거할 수 있습니다.

그래서 실무 규칙은 "헤더에 공개하지 않는 함수와 파일 범위 변수는 모두 static"입니다.

include guard: 헤더 중복 포함 막기

헤더가 다른 헤더를 포함하다 보면 같은 헤더가 한 번역 단위에 두 번 들어가는 일이 흔합니다. 예를 들어 main.c가 account.h와 transfer.h를 포함하고, transfer.h도 account.h를 포함하는 경우입니다.

함수 원형이나 extern 선언은 여러 번 나와도 괜찮지만, 구조체 정의와 typedef(C11 이전), enum 정의는 같은 번역 단위에서 두 번 나오면 "redefinition" 컴파일 오류입니다. 이를 막는 표준 기법이 include guard입니다.

왜 그럴까? — #pragma once와 무엇이 다를까?

#pragma once는 컴파일러가 "이 파일은 이미 포함했다"는 것을 파일 단위로 기억하게 하는 비표준 확장입니다. 한 줄이라 간편하고 매크로 이름 충돌 걱정이 없으며, 주요 컴파일러가 모두 지원합니다. 다만 표준이 아니고, 심볼릭 링크나 네트워크 드라이브로 같은 파일이 다른 경로로 보이면 같은 파일임을 판단하지 못하는 경우가 있습니다. include guard는 100% 표준이지만, 매크로 이름이 다른 헤더와 겹치면(복사해 붙이다 이름을 안 바꾼 경우) 한쪽 헤더가 통째로 무시되는 사고가 납니다. 그래서 가드 이름은 프로젝트_경로_파일_H처럼 고유하게 짓습니다. 실무에서는 팀 표준에 따라 둘 중 하나, 또는 둘 다 씁니다.

밑줄 + 대문자로 시작하는 이름(_ACCOUNT_H)이나 이중 밑줄을 포함한 이름은 표준이 구현용으로 예약해 두었으므로 가드 이름으로 쓰지 않습니다.

분할 컴파일 빌드와 간단한 Makefile

여러 파일로 된 프로그램은 두 가지 방식으로 빌드할 수 있습니다.

# 방법 1: 한 번에 (매번 전부 다시 컴파일)
gcc -Wall -Wextra -std=c11 main.c account.c -o bank

# 방법 2: 파일별로 컴파일(-c) 후 링크 (바뀐 파일만 다시 컴파일 가능)
gcc -Wall -Wextra -std=c11 -c account.c      # account.o 생성
gcc -Wall -Wextra -std=c11 -c main.c         # main.o 생성
gcc main.o account.o -o bank                 # 링크

방법 2에서 account.c만 고쳤다면 account.o만 다시 만들고 링크하면 됩니다. 파일이 수천 개인 프로젝트에서 이 차이는 몇 시간과 몇 초의 차이입니다. 어떤 파일을 다시 컴파일해야 하는지 자동으로 판단해 주는 도구가 make이고, 그 규칙을 적는 파일이 Makefile입니다.

왜 그럴까? — make는 무엇을 보고 다시 컴파일할지 정할까?

make는 파일의 수정 시각을 비교합니다. 대상 파일(account.o)이 없거나, 의존 파일(account.c, account.h) 중 하나라도 대상보다 최근에 수정되었으면 명령을 실행합니다. 이것을 재귀적으로 적용해 bank → account.o → account.c 순으로 확인합니다. 그래서 의존 관계에 헤더를 빠뜨리면 헤더의 구조체를 바꿔도 main.o가 다시 컴파일되지 않아, 서로 다른 구조체 정의로 컴파일된 목적 파일이 링크되는 위험한 상황이 생깁니다. 실무에서는 gcc -MMD -MP 옵션으로 헤더 의존 관계를 자동 생성합니다. 명령 줄이 공백이 아니라 탭이어야 하는 것은 make의 오래된 문법 규칙으로, 공백을 쓰면 "missing separator" 오류가 납니다.

실습: 계좌 모듈 account.h / account.c

17장의 계좌 코드를 재사용 가능한 모듈로 분리해 보겠습니다. 공개할 것(형, 함수 원형, 오류 코드)은 헤더에, 구현과 내부 도우미는 소스에 둡니다.

make
gcc -Wall -Wextra -std=c11 -O2 -c main.c
gcc -Wall -Wextra -std=c11 -O2 -c account.c
gcc main.o account.o -o bank
./bank

왜 그럴까? — main.c에서 valid_amount를 부르면 어떤 오류가 날까?

main.c에는 valid_amount의 선언이 없으므로 C99 이후에는 먼저 컴파일 단계에서 "implicit declaration of function" 오류(gcc 14부터 기본 오류, 이전에는 경고)가 납니다. 선언을 억지로 써 넣어 컴파일을 통과시켜도, account.o의 valid_amount는 소문자 t(내부 심볼)이므로 링커가 찾지 못해 "undefined reference to `valid_amount'"가 납니다. static이 파일 경계에서 이름을 확실히 숨긴다는 증거입니다.

은행 시스템에서는 — 대규모 C 프로젝트의 모듈 구조

계정계·대외계의 C 소스는 보통 업무 단위(수신, 여신, 외환, 대외 송수신)와 공통 단위(전문 파싱, 로그, DB 접근, 날짜/영업일 계산, 금액 연산)로 디렉터리가 나뉩니다. 공통 모듈은 정적 라이브러리(libcommon.a)나 공유 라이브러리(libcommon.so)로 만들어 업무 프로그램이 링크합니다. 이때 다음 규칙이 중요합니다.

  • 헤더 변경은 신중히: 공통 헤더의 구조체 하나를 바꾸면 그 헤더를 쓰는 모든 프로그램을 다시 빌드·배포해야 합니다. 구조체 끝에 예비 필드(filler)를 미리 두는 관행도 이 때문입니다.
  • 이름 접두어 규칙: 네임스페이스가 없으므로 acc_, cmn_, ext_처럼 모듈 접두어를 붙여 이름 충돌을 막습니다.
  • 빌드 재현성: 운영 배포 바이너리는 형상 관리된 소스와 고정된 컴파일 옵션으로 빌드 서버에서만 만들고, 개발자 PC에서 빌드한 파일을 운영에 올리지 않습니다. __DATE__/__TIME__을 바이너리에 넣으면 같은 소스라도 빌드마다 결과가 달라지므로 재현 가능한 빌드를 위해 빌드 번호를 별도로 주입하기도 합니다.

핵심 정리

  • 빌드는 전처리 → 컴파일 → 어셈블 → 링크 순으로 진행되며, 전처리기는 C 문법을 모르는 토큰 치환기입니다. gcc -E로 결과를 확인할 수 있습니다.
  • #include는 파일 내용을 그 자리에 복사합니다. <>는 시스템 경로, ""는 현재 디렉터리부터 찾습니다. .c 파일은 include하지 않습니다.
  • #define 매크로는 값이 아니라 글자를 치환하므로 매개변수와 전체를 괄호로 감싸야 합니다. 인자가 여러 번 복사되므로 ++나 함수 호출을 넣으면 부작용이 반복됩니다. 계산용 매크로는 static inline 함수로 대체합니다.
  • 여러 문장 매크로는 do { ... } while (0)으로 감싸 하나의 문장처럼 동작하게 합니다.
  • #는 인자를 문자열로, ##는 두 토큰을 하나로 붙입니다. 매크로를 먼저 펼친 뒤 문자열화하려면 두 단계 매크로가 필요합니다.
  • 조건부 컴파일(#if, #ifdef, -D 옵션)은 코드를 실행 파일에서 아예 빼며, 정의되지 않은 이름은 #if에서 0으로 취급됩니다. #error로 빌드를 중단할 수 있습니다.
  • __FILE__, __LINE__, __func__로 호출 위치를 기록하는 로그 매크로를 만들 수 있습니다. 로그에는 민감 정보를 남기지 않습니다.
  • #pragma는 컴파일러별 확장입니다. pack은 반드시 push/pop 쌍으로 씁니다.
  • 헤더에는 선언(형, 원형, extern), 소스에는 정의를 둡니다. 각 .c는 자기 헤더를 맨 먼저 include해 선언·정의 일치를 검사받습니다.
  • 번역 단위마다 목적 파일이 만들어지고, 링커가 미정의 심볼을 정의와 연결합니다. 전역 변수는 정확히 한 번 정의하고 나머지는 extern으로 선언합니다.
  • 파일 범위의 static은 내부 링크로 이름을 숨겨 충돌을 막고 캡슐화합니다. 공개하지 않을 함수는 모두 static으로 둡니다.
  • include guard(또는 #pragma once)로 헤더 중복 포함을 막습니다. undefined reference는 정의 누락, multiple definition은 정의 중복을 뜻합니다. Makefile은 수정 시각과 의존 관계로 필요한 파일만 다시 빌드합니다.

Q1. C 프로그램이 실행 파일이 되기까지의 과정을 설명해 주세요.

전처리기가 #include, #define, 조건부 컴파일을 처리해 번역 단위를 만들고, 컴파일러가 이를 어셈블리로 번역하며, 어셈블러가 기계어 목적 파일(.o)을 만듭니다. 마지막으로 링커가 여러 목적 파일과 라이브러리를 합치면서 미정의 심볼을 정의와 연결하고 주소를 확정해 실행 파일을 만듭니다. 실행 시에는 로더가 실행 파일을 메모리에 올리고, 공유 라이브러리를 사용하면 동적 링커가 실행 시점에 연결합니다.

꼬리 질문 대비: "정적 링크와 동적 링크의 차이는?" 정적 링크는 라이브러리 코드를 실행 파일에 복사해 독립적이지만 크고, 동적 링크는 실행 시 공유 라이브러리를 연결해 메모리를 공유하고 라이브러리만 교체해 업데이트할 수 있지만 버전 의존성이 생긴다고 답합니다.

Q2. 매크로 함수와 일반 함수(또는 inline 함수)의 차이는?

매크로는 전처리 단계의 텍스트 치환이라 함수 호출 비용이 없고 형에 무관하게 쓸 수 있지만, 형 검사가 없고, 괄호를 빠뜨리면 연산자 우선순위 문제가 생기며, 인자가 여러 번 평가되어 부작용이 반복되고, 디버깅이 어렵습니다. 함수는 인자를 한 번만 평가하고 형 검사를 받으며, inline 함수는 최적화 시 호출 비용도 없앨 수 있습니다. 그래서 현대 C에서는 계산용 매크로 대신 static inline 함수를 권장합니다.

Q3. 매크로에서 do { } while(0)을 쓰는 이유는?

여러 문장으로 된 매크로를 하나의 문장처럼 쓰기 위해서입니다. 중괄호 없이 쓰면 if 문 아래에서 첫 문장만 조건의 영향을 받고, 중괄호만 쓰면 사용하는 쪽이 붙인 세미콜론 때문에 if-else 구조가 깨집니다. do-while(0)은 끝에 세미콜론이 필요한 단일 문장이라 일반 함수 호출과 똑같이 사용할 수 있고, 한 번만 실행되며 컴파일러가 반복 구조를 제거하므로 비용도 없습니다.

Q4. static 키워드의 의미를 모두 설명해 주세요.

쓰이는 위치에 따라 의미가 다릅니다. 함수 안의 지역 변수에 붙이면 저장 기간이 정적이 되어 함수가 끝나도 값이 유지되고 한 번만 초기화됩니다. 파일 범위의 전역 변수나 함수에 붙이면 내부 링크가 되어 그 파일 안에서만 보이므로 이름 충돌을 막고 캡슐화를 제공합니다. C99부터는 배열 매개변수 int a[static 10]처럼 최소 원소 개수를 약속하는 용도도 있습니다.

꼬리 질문 대비: "static 지역 변수는 메모리의 어디에 있나요?" 스택이 아니라 데이터 영역(초기값이 있으면 .data, 없으면 .bss)에 있다고 답합니다.

Q5. extern은 무엇이고 선언과 정의의 차이는?

정의는 객체의 메모리를 실제로 할당하거나 함수의 본체를 제공하는 것이고, 선언은 이름과 형만 알려 주는 것입니다. extern은 "이 변수는 다른 곳에 정의되어 있다"는 선언으로 메모리를 할당하지 않습니다. 단일 정의 규칙에 따라 외부 링크를 가진 객체는 프로그램 전체에서 정확히 한 번 정의되어야 하므로, 헤더에는 extern 선언을 두고 한 소스 파일에서만 정의합니다.

Q6. include guard는 왜 필요한가요?

헤더가 다른 헤더를 포함하면서 같은 헤더가 한 번역 단위에 여러 번 포함될 수 있는데, 구조체 정의 같은 내용이 두 번 나오면 재정의 컴파일 오류가 납니다. #ifndef/#define/#endif로 처음 포함될 때만 내용이 들어가게 합니다. #pragma once도 같은 목적이지만 비표준입니다. include guard는 같은 번역 단위 안의 중복을 막을 뿐, 서로 다른 .c 파일 간의 변수 중복 정의(multiple definition)는 막지 못한다는 점도 함께 설명하면 좋습니다.

Q7. "undefined reference"와 "multiple definition" 링크 오류의 원인과 해결은?

undefined reference는 사용한 함수나 변수의 정의를 링커가 어디에서도 찾지 못한 것으로, 구현 파일이나 라이브러리를 링크에서 빠뜨렸거나(-l 옵션 누락 포함), 이름이 다르거나, 정의가 static이라 보이지 않을 때 생깁니다. multiple definition은 같은 외부 심볼이 둘 이상의 목적 파일에 정의된 것으로, 헤더에 변수나 함수 정의를 넣었거나 .c 파일을 include했을 때 주로 생깁니다. 오류 메시지의 심볼 이름을 nm 결과와 대조하면 원인을 빨리 찾을 수 있습니다.

Q8. 조건부 컴파일은 언제 사용하나요?

운영체제나 컴파일러별로 다른 코드(윈도우/리눅스 API), 디버그 빌드에서만 필요한 검증·로그 코드, 기능 토글, 헤더 중복 포함 방지, 표준 버전 확인 등에 사용합니다. 빠진 코드는 실행 파일에 존재하지 않으므로 실행 비용이 없습니다. 다만 남용하면 빌드 조합마다 다른 프로그램이 되어 테스트가 어려워지므로 최소화하고, 가능하면 상수 조건의 if로 두어 컴파일러 검사를 유지합니다.

Q9. 헤더 파일에 함수 정의를 넣어도 되는 경우가 있나요?

static inline 함수는 헤더에 정의해도 됩니다. static이므로 포함한 각 번역 단위가 자기만의 사본을 가지며 외부 심볼이 생기지 않아 multiple definition이 나지 않고, 작은 함수는 인라인되어 사본이 남지도 않습니다. 매크로 대체용 작은 도우미 함수에 적합합니다. 일반 외부 함수의 정의를 헤더에 넣으면 두 곳 이상에서 포함될 때 링크 오류가 납니다.

연습문제 19-2 출력 예측: 부작용 난이도 ★★☆

#include <stdio.h>
#define ABS(x) ((x) < 0 ? -(x) : (x))
int main(void)
{
    int a = -3, n = 0;
    int r = ABS(a--);
    printf("%d %d\n", r, a);
    int v[] = { -5, 7 };
    r = ABS(v[n++]);
    printf("%d %d\n", r, n);
    return 0;
}
정답과 해설 보기

출력: 4 -5와 -7 2.

첫째: ((a--) < 0 ? -(a--) : (a--)). 조건에서 -3 < 0 참, a는 -4. 그다음 -(a--)는 -(-4) = 4, a는 -5. 둘째: 조건 v[0] < 0(-5) 참, n은 1. 그다음 -(v[n++])는 -(v[1]) = -7, n은 2. 절댓값이 음수로 나오는 황당한 결과입니다. 인라인 함수 static inline int abs_i(int x)로 바꾸면 각각 3 -4와 5 1처럼 인자를 한 번만 평가해 기대대로 동작합니다.

연습문제 19-7 버그 찾기: 헤더 난이도 ★★★

다음 헤더의 문제점을 모두 찾으십시오.

/* util.h */
#define _UTIL_H
#include "util.c"
#define MIN(a,b) a < b ? a : b
int g_err_count;
int round_won(double v) { return (int)(v + 0.5); }
정답과 해설 보기

(1) include guard가 불완전합니다. #define만 있고 #ifndef/#endif가 없어 중복 포함을 막지 못합니다. 또 밑줄+대문자로 시작하는 _UTIL_H는 예약된 이름입니다. (2) .c 파일을 include하면 정의가 여러 번역 단위에 복사됩니다. (3) MIN 매크로에 괄호가 없어 MIN(x, y) * 2나 MIN(a & m, b) 등에서 오동작합니다. (4) int g_err_count;는 헤더에 둔 잠정 정의로 gcc 10 이상에서 multiple definition 오류가 납니다. extern 선언으로 바꾸고 한 .c에서 정의합니다. (5) round_won은 static inline이 아닌 함수 정의라 두 곳 이상에서 포함하면 링크 오류입니다. 또한 금액 반올림을 double로 하는 것은 오차와 음수 처리(-2.5 → -2) 문제가 있으므로 정수 연산으로 구현해야 합니다.
