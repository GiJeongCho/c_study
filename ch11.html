문자

컴퓨터에게 문자는 그저 정수입니다. 이 사실 하나를 이해하면 대소문자 변환, 숫자 문자의 정수 변환, 전문 필드 파싱이 모두 간단한 산술이 됩니다. 그리고 키보드 입력이 프로그램에 도착하기까지 거치는 "입력 버퍼"를 이해하면, 초보자를 가장 괴롭히는 "scanf 다음 getchar가 건너뛰어지는" 문제의 정체가 선명하게 보입니다.

이 장에서 배울 것

  • 문자가 정수(문자 코드)로 저장된다는 사실과 ASCII 코드표의 구조를 이해합니다.
  • getchar/putchar의 사용법과 getchar가 int를 반환하는 이유를 압니다.
  • <ctype.h>의 문자 판별·변환 함수를 올바르게(부호 문제 없이) 사용합니다.
  • 숫자 문자 '0'~'9'를 정수로 바꾸고, 전문의 숫자 필드를 금액으로 변환합니다.
  • 입력 버퍼와 엔터 키('\n')의 정체를 그림으로 이해하고, scanf와 getchar 혼용 문제를 해결합니다.
  • EOF의 의미, 올바른 입력 버퍼 비우기, fflush(stdin)이 UB인 이유를 설명합니다.
  • 라인 버퍼링·풀 버퍼링·무버퍼의 차이와 로그 유실 문제를 이해합니다.

11-1아스키 코드 값과 문자 입출력 함수

문자는 정수로 저장된다

메모리에는 0과 1만 저장할 수 있습니다. 그러니 'A'라는 글자 모양을 그대로 저장할 방법은 없습니다. 대신 사람들이 약속을 했습니다. "65라는 수는 A를 뜻하기로 하자." 이렇게 문자마다 번호를 붙인 약속을 문자 코드(character code) 또는 문자 집합이라고 하고, 그중 가장 기본이 되는 것이 1963년에 제정된 ASCII(American Standard Code for Information Interchange)입니다. ASCII는 0~127까지 128개의 번호에 영문 대소문자, 숫자, 기호, 제어 문자를 배정했습니다.

C의 char는 1바이트 정수형입니다. char c = 'A';는 c에 65를 저장하는 것과 정확히 같습니다. 작은따옴표 'A'는 "A의 문자 코드 값"을 뜻하는 정수 상수일 뿐입니다.

%c와 %d의 차이는 "해석"뿐이다

메모리의 c에는 01000001(65)이 들어 있을 뿐입니다. printf의 %d는 이 값을 10진수 숫자 "65"로 바꿔 출력하고, %c는 65번 문자의 글꼴 모양을 터미널에 그리도록 바이트 65를 그대로 내보냅니다. 같은 비트, 다른 해석입니다. 9장에서 포인터 자료형이 해석 방법을 결정했던 것과 같은 원리입니다.

마지막 줄의 sizeof 'A'가 4인 것도 주목하세요. C에서 문자 상수 'A'의 자료형은 char가 아니라 int입니다(C++에서는 char이고 1). 역사적으로 C의 연산은 모두 int 이상으로 승격되어 이루어지므로 문자 상수도 int로 정의되었습니다. 그래서 c + 2의 결과도 int이며, %c에 int를 넘겨도 문제가 없습니다.

char는 부호가 있을까, 없을까? — 구현 정의

char가 signed char(-128~127)처럼 동작할지 unsigned char(0~255)처럼 동작할지는 C 표준이 정하지 않은 구현 정의(implementation-defined) 사항입니다. x86-64의 gcc와 MSVC는 signed, ARM 리눅스의 gcc는 unsigned가 기본입니다. ASCII 범위(0~127)만 다룰 때는 차이가 없지만, 한글 UTF-8 바이트(0x80 이상)를 다루면 x86에서는 음수가 되어 문제가 생깁니다(11-1-4의 ctype 함정, 11-2-5의 EOF 함정). 바이트 데이터를 다룰 때는 unsigned char를 명시하는 것이 안전합니다.

ASCII 설계에 숨은 영리한 규칙들

  • 숫자 '0'~'9'가 0x30~0x39: 하위 4비트가 곧 숫자 값입니다('7' = 0x37 → 하위 4비트 7). 그래서 c - '0' 또는 c & 0x0F로 숫자 값을 얻습니다.
  • 대문자와 소문자가 0x20(32) 차이: 'A' = 0100 0001, 'a' = 0110 0001. 딱 한 비트(0x20)만 다릅니다. 옛 하드웨어에서 Shift 키는 이 비트 하나를 끄는 회로였습니다.
  • 알파벳이 사전 순서로 연속: 'A' < 'B' < ... < 'Z'이므로 문자 비교가 곧 사전 순 비교가 됩니다. 단, 대문자가 소문자보다 모두 작으므로 'Z' < 'a'입니다.
  • 제어 문자가 맨 앞 32개: 출력 가능한 문자인지 판별하려면 32 이상 126 이하인지만 보면 됩니다.

C 표준이 연속성을 보장하는 것은 숫자 '0'~'9'뿐입니다. 알파벳의 연속성은 ASCII의 성질일 뿐 표준의 보장이 아닙니다. IBM 메인프레임의 EBCDIC 코드에서는 'I'와 'J' 사이에 다른 코드가 끼어 있어 c - 'A'로 알파벳 순번을 구하면 틀립니다. 그래서 이식성 있는 코드는 isupper, toupper 같은 표준 함수를 씁니다.

은행 시스템에서는 — EBCDIC과 코드 변환

은행의 오래된 계정계 중에는 IBM 메인프레임(z/OS) 위에서 COBOL로 운영되는 시스템이 아직 있고, 이 세계의 문자 코드는 ASCII가 아니라 EBCDIC입니다. EBCDIC에서 숫자 '0'은 0xF0, 'A'는 0xC1입니다. 리눅스 기반 대외계·채널계 서버가 메인프레임과 전문을 주고받을 때는 반드시 ASCII↔EBCDIC 코드 변환을 거치며, 한글은 또 별도의 2바이트 코드(메인프레임 한글 코드 ↔ EUC-KR/UTF-8) 변환이 필요합니다. 변환 표가 한 칸만 틀려도 고객 이름이 깨지거나 금액 필드의 숫자가 엉뚱한 문자로 바뀌는 장애가 납니다. "문자는 정수이고, 어떤 정수가 어떤 문자인지는 약속(코드 체계)에 달려 있다"는 이 장의 첫 문장이 실무에서 그대로 문제로 나타나는 지점입니다.

한글은 char 하나에 들어가지 않습니다

ASCII에는 한글이 없습니다. 한글은 EUC-KR/CP949에서 2바이트, 현재 표준인 UTF-8에서 3바이트로 표현됩니다('가' = 0xEA 0xB0 0x80). 그래서 char c = '가';는 의도대로 동작하지 않습니다(gcc는 "multi-character character constant" 경고 후 구현 정의 값을 넣습니다). 한글은 문자열(char s[] = "가";, 4바이트: 3바이트 + '\0')로 다뤄야 하며, strlen("가나다")는 글자 수 3이 아니라 바이트 수 9를 돌려줍니다. 글자 단위 처리가 필요하면 와이드 문자(wchar_t)나 UTF-8 디코딩이 필요합니다. 이 장의 예제는 ASCII 문자를 중심으로 다룹니다.

대소문자 변환 — 직접 구현과 표준 함수

ASCII 구조를 알면 대소문자 변환은 덧셈·뺄셈 한 번입니다. 소문자 c를 대문자로 바꾸려면 "알파벳 순번(c - 'a')"을 구한 뒤 'A'에 더하면 됩니다.

직접 구현보다 toupper를 권하는 이유

my_toupper는 ASCII에서만 맞고, c ^ 0x20 같은 비트 트릭은 알파벳이 아닌 문자까지 바꿔 버립니다('@'(64) ^ 0x20 = '`'(96)). 표준 toupper는 ① 소문자가 아니면 원래 값을 그대로 반환한다는 것을 보장하고, ② 실행 환경의 문자 코드(EBCDIC 포함)와 로캘을 고려하며, ③ 보통 표 조회 방식으로 구현되어 분기 없이 빠릅니다. 학습용으로는 직접 구현해 원리를 익히고, 실무에서는 표준 함수를 쓰는 것이 정답입니다.

숫자 문자 '0'~'9'를 정수로 바꾸기

키보드나 파일에서 읽은 "1500"은 숫자 1500이 아니라 문자 4개 '1'(49), '5'(53), '0'(48), '0'(48)입니다. 이것을 정수 1500으로 바꾸려면 두 단계가 필요합니다.

  1. 문자 하나 → 숫자 하나: c - '0'. '5'(53) - '0'(48) = 5. C 표준이 '0'~'9'의 연속 배치를 보장하므로 어떤 문자 코드에서도 맞습니다.
  2. 자릿수 누적: 지금까지의 값에 10을 곱하고 새 숫자를 더합니다. n = n * 10 + (c - '0').

왜 n > (LLONG_MAX - d) / 10 으로 검사할까?

n * 10 + d가 LLONG_MAX를 넘는지 확인하고 싶지만, 넘는지 보려고 먼저 계산하면 이미 부호 있는 정수 오버플로(UB)가 일어난 뒤입니다. 그래서 식을 변형해 오버플로가 날 수 없는 형태로 검사합니다. n × 10 + d ≤ MAX ⇔ n ≤ (MAX − d) / 10 (정수 나눗셈에서도 성립). 이처럼 "계산하기 전에 범위를 확인"하는 것이 C에서 정수 오버플로를 다루는 정석입니다. 12자리 금액 필드는 최대 999,999,999,999로 long long 범위 안이지만, 필드 길이가 바뀌거나 잘못된 길이가 넘어오는 경우를 대비한 방어 코드입니다.

또 field가 널 종료 문자열이 아니라는 점에 주목하세요. 전문은 필드가 구분자 없이 이어진 바이트 덩어리이므로, 길이를 정확히 넘겨서 그 범위만 처리합니다. atoi(msg + 4)를 쓰면 금액 뒤의 "KRW"에서 멈추기는 하지만, 통화 코드 자리에 숫자가 오는 전문이라면 다음 필드까지 이어 읽어 버립니다.

은행 시스템에서는 — 고정 길이 전문과 숫자 필드 검증

은행 간 이체, 카드 승인, 대외기관 조회 전문의 상당수는 "필드마다 길이가 정해진 고정 길이 전문"입니다. 숫자 필드는 오른쪽 정렬·앞 0 채움(000001500000), 문자 필드는 왼쪽 정렬·뒤 공백 채움이 일반적인 규칙입니다. 수신 측 프로그램은 위의 parse_amount처럼 각 바이트가 정말 '0'~'9'인지를 반드시 검사합니다. 송신 측 버그로 숫자 필드에 공백이나 영문자가 섞여 오면 즉시 "전문 형식 오류" 응답 코드로 거절해야지, 이상한 값을 금액으로 해석해 원장에 반영해서는 안 되기 때문입니다. 실제로 숫자 0과 영문 O, 숫자 1과 영문 l이 섞인 데이터는 수기 입력·OCR 경로에서 종종 발생합니다.

예제 11-3 난이도 ★★☆

정수를 받아 지정한 길이의 0 채움 숫자 문자열로 만드는 함수 int format_amount(long long n, char *buf, int len)를 sprintf 없이 작성하세요. 1500000, len 12 → "000001500000". n이 음수이거나 자릿수가 len을 넘으면 -1을 반환합니다.

정답과 해설 보기

파싱의 반대 방향입니다. 낮은 자리부터 n % 10 + '0'으로 숫자 문자를 만들어 버퍼의 오른쪽 끝부터 채우고, n을 10으로 나눕니다. 다 채운 뒤 n이 0이 아니면 자릿수가 모자란 것입니다.

11-2버퍼를 사용하는 입력 함수

11-1의 예제에서 글자를 하나씩 입력했는데도 엔터를 누를 때까지 아무 일도 일어나지 않았습니다. 그리고 엔터 키도 문자 하나로 세어졌습니다. 이 두 현상의 원인이 바로 입력 버퍼(input buffer)입니다. 버퍼를 이해하지 못하면 "scanf 다음의 getchar가 입력을 기다리지 않고 지나가 버리는" 문제에 반드시 걸려 넘어집니다.

입력 버퍼란 무엇인가

버퍼(buffer)는 데이터를 잠시 모아 두는 임시 저장 공간입니다. 키보드로 친 글자는 프로그램에 바로 전달되지 않고 두 단계의 버퍼를 거칩니다.

  1. 운영체제 터미널의 줄 버퍼: 리눅스 터미널은 기본적으로 "정규 모드(canonical mode)"로 동작합니다. 사용자가 입력하는 글자를 모아 두면서 백스페이스로 지우는 등의 줄 편집을 처리하고, 엔터를 누르는 순간 그 줄 전체('\n' 포함)를 프로그램에 넘겨줍니다. 그래서 엔터 전까지는 프로그램이 아무것도 받지 못합니다.
  2. C 라이브러리의 stdin 버퍼: getchar가 호출될 때마다 운영체제에 "1바이트 주세요"라고 시스템 콜(read)을 하면 너무 느립니다. 그래서 C 라이브러리는 한 번에 가능한 만큼(보통 수 KB) 읽어 와 자기 버퍼에 쌓아 두고, getchar는 그 버퍼에서 한 글자씩 꺼내 줍니다.

왜 버퍼를 쓸까? — 시스템 콜은 비싸다

운영체제에게 무언가를 요청하는 시스템 콜은 CPU가 사용자 모드에서 커널 모드로 전환했다가 돌아오는 과정을 거치므로, 일반 함수 호출보다 수십~수백 배 비쌉니다. 1MB 파일을 1바이트씩 시스템 콜로 읽으면 100만 번의 모드 전환이 일어나지만, 4KB 버퍼를 쓰면 256번으로 줄어듭니다. 키보드 입력에서는 성능보다 줄 편집 기능(백스페이스로 고친 뒤 엔터로 확정)이 버퍼의 더 큰 이유입니다. 버퍼가 없으면 사용자가 지운 글자까지 프로그램이 받아 버리겠지요.

엔터 키의 정체 — '\n'도 입력된다

사용자가 'Y'를 치고 엔터를 누르면 버퍼에는 'Y'와 '\n' 두 글자가 들어갑니다. getchar를 두 번 호출해 확인해 봅시다.

윈도우의 엔터는 \r\n 아닌가요?

윈도우에서 텍스트 파일의 줄 끝은 CR LF('\r' '\n') 두 바이트입니다. 하지만 C의 표준 입출력은 텍스트 모드에서 이를 자동으로 '\n' 하나로 바꿔 줍니다. 그래서 위 프로그램은 윈도우 콘솔에서도 c2 = 10을 출력합니다. 단, 파일을 바이너리 모드("rb")로 열거나, 윈도우에서 만든 파일을 리눅스로 옮겨 읽으면 '\r'이 그대로 보여, "줄 끝 공백 제거" 로직이 이를 놓치는 문제가 자주 생깁니다. 금융권에서 윈도우 단말이 만든 파일을 리눅스 배치가 읽을 때 흔히 겪는 문제입니다.

scanf와 getchar를 섞어 쓸 때 생기는 문제

이제 초보자들이 가장 많이 질문하는 문제를 재현해 봅시다. 이체 금액을 입력받고, "정말 이체할까요? (Y/N)"를 물어보는 프로그램입니다.

scanf는 왜 '\n'을 남길까?

%lld 변환은 "앞쪽 공백류 문자는 건너뛰고, 숫자로 해석할 수 있는 문자까지만 읽고, 숫자가 아닌 첫 문자를 만나면 그 문자는 버퍼에 되돌려 놓고 멈춘다"고 정의되어 있습니다. 숫자 뒤의 '\n'은 숫자가 아니므로 소비되지 않고 버퍼에 남습니다. scanf 입장에서는 "그 문자는 다음 입력 함수의 몫"이니까요. 그 다음 getchar는 버퍼가 비어 있지 않으므로 기다릴 이유가 없고, 남은 '\n'을 즉시 가져갑니다.

같은 이유로 scanf("%d", &n); scanf("%c", &ch);도 실패합니다. %c는 %d와 달리 공백류 문자를 건너뛰지 않는 유일한 변환(그 밖에 %[, %n) 중 하나라서 '\n'을 그대로 읽기 때문입니다. 반대로 scanf("%d")를 두 번 연속 쓰면 문제가 없습니다. 두 번째 %d가 앞의 '\n'을 공백류로 보고 건너뛰기 때문입니다.

이렇게 해결합니다 — 세 가지 방법

  1. scanf 직후 그 줄의 나머지를 버린다 (가장 일반적): 다음 소절의 clear_input_line()을 호출합니다.
  2. scanf(" %c", &ch): 형식 문자열의 공백은 "공백류 문자를 0개 이상 건너뛰라"는 뜻입니다. %c 앞에 공백 하나를 두면 남은 '\n'을 건너뛰고 실제 문자를 읽습니다. 다만 "숫자 뒤에 쓰레기 문자가 남은 경우"(예: 50000abc)까지 처리해 주지는 않습니다.
  3. 한 줄을 통째로 읽고 직접 해석 (실무 권장): fgets로 한 줄 전체를 문자열로 읽은 뒤 strtoll/sscanf로 해석합니다. 입력과 해석이 분리되어 버퍼에 찌꺼기가 남지 않고, 형식 오류도 깔끔하게 처리됩니다(12장에서 자세히).

입력 버퍼를 올바르게 비우는 방법

"버퍼를 비운다"는 것은 정확히는 현재 줄의 끝('\n')까지 남은 문자를 읽어서 버리는 것입니다. 이것을 표준에 맞게 이식성 있게 하는 방법은 단 하나, 직접 읽어 버리는 것입니다.

왜 c != EOF 조건이 꼭 필요할까?

입력이 파일 리다이렉션(./a.out < input.txt)으로 들어오고 마지막 줄에 '\n'이 없다면, '\n'을 영원히 만나지 못합니다. 입력 끝에서 getchar는 계속 EOF를 반환하므로 while ((c = getchar()) != '\n');만 쓰면 무한 루프에 빠집니다. 야간 배치에서 이런 코드가 CPU 100%로 멈추지 않고 돌아 다음 날 업무 개시가 지연되는 사고는 실제로 일어나는 유형입니다. 루프 조건에 항상 EOF 검사를 넣는 습관을 들이세요.

예제 11-4 난이도 ★★☆

사용자가 "Y" 또는 "N"을 입력할 때까지 반복해서 묻는 함수 int ask_yes_no(const char *question)을 작성하세요. "yes"처럼 여러 글자를 입력하면 첫 글자만 보고 나머지는 버립니다. Y/y면 1, N/n이면 0, EOF면 -1을 반환합니다.

정답과 해설 보기

c가 이미 '\n'이면(빈 줄 입력) 그 줄은 끝났으므로 clear_input_line을 호출하면 안 됩니다. 호출하면 다음 줄 전체를 먹어 버려 사용자가 한 번 더 입력해야 하는 이상한 동작이 됩니다. 이처럼 "버퍼에 지금 무엇이 남아 있는가"를 항상 추적하는 것이 입력 처리의 핵심입니다.

EOF — 입력의 끝, 그리고 getchar가 int를 반환하는 이유

EOF(End Of File)는 <stdio.h>에 정의된 매크로로, "더 이상 읽을 입력이 없다(또는 오류)"를 나타내는 음수 정수입니다. 거의 모든 구현에서 -1입니다. EOF는 파일 안에 저장된 특별한 문자가 아니라, 입력 함수가 "끝에 도달했음"을 알리기 위해 돌려주는 신호값입니다.

그렇다면 getchar는 왜 char가 아니라 int를 반환할까요? 경우의 수를 세어 보면 답이 나옵니다.

char c로 받으면 무슨 일이 생길까? — 플랫폼마다 다른 두 가지 버그

  • char가 signed인 경우(x86 gcc, MSVC): 입력에 바이트 0xFF가 있으면(이진 파일, 일부 한글 인코딩, Latin-1의 'ÿ') c에 저장될 때 -1이 됩니다. 이것이 EOF(-1)와 같으므로 파일 중간에서 읽기가 멈춥니다. 데이터 일부가 조용히 사라지는 버그입니다.
  • char가 unsigned인 경우(ARM 리눅스 gcc 등): getchar가 EOF(-1)를 반환해도 c에 저장되면 255가 됩니다. 255 != -1은 항상 참이므로 루프가 영원히 끝나지 않습니다. x86 서버에서 잘 돌던 프로그램이 ARM 서버로 옮기자 무한 루프에 빠지는 사례입니다.

해결은 간단합니다. getchar, getc, fgetc의 반환값은 항상 int 변수에 받고, EOF 검사를 마친 뒤에 char로 사용합니다.

EOF인지 오류인지 구분하기 — feof와 ferror

getchar는 입력이 끝났을 때와 읽기 오류가 났을 때 모두 EOF를 반환합니다. 둘을 구분하려면 반복문이 끝난 뒤에 feof(stdin)(끝에 도달했으면 참)과 ferror(stdin)(오류가 났으면 참)을 확인합니다. 흔한 실수인 while (!feof(fp)) { c = fgetc(fp); ... }는 마지막 EOF를 데이터로 한 번 더 처리하게 되므로 잘못된 패턴입니다. feof는 "읽기 시도가 이미 실패한 뒤"에야 참이 되기 때문입니다.

fflush(stdin)이 정답이 아닌 이유

인터넷과 오래된 교재에서 "버퍼를 비우려면 fflush(stdin);을 쓰라"는 조언을 자주 봅니다. 결론부터 말하면 표준 C에서 fflush(stdin)은 미정의 동작(UB)이므로 쓰면 안 됩니다.

왜 UB일까?

C 표준은 fflush를 이렇게 정의합니다. "스트림이 출력 스트림이거나, 갱신(update) 스트림에서 마지막 연산이 입력이 아니었다면, 아직 기록되지 않은 데이터를 파일로 내보낸다. 그 밖의 경우 동작은 정의되지 않는다." 즉 fflush의 "flush(쏟아내다)"는 출력 버퍼에 쌓인 데이터를 목적지로 밀어내는 동작이지, 입력 버퍼를 버리는 동작이 아닙니다. 입력 버퍼를 "어디로" 쏟아낼지 정의할 수 없으니까요.

그런데도 이 코드가 퍼진 이유는 과거 마이크로소프트 C 런타임이 확장 기능으로 fflush(stdin)을 "입력 버퍼 비우기"로 동작시켰기 때문입니다. 반면 리눅스 glibc에서는 터미널 입력에 대해 아무 효과가 없어서, 윈도우에서 잘 되던 과제가 리눅스에서는 그대로 실패합니다. 이후 마이크로소프트의 새 런타임(UCRT)에서도 동작이 달라졌다고 알려져 있어, 같은 윈도우에서도 버전에 따라 결과를 장담할 수 없습니다. 이처럼 "특정 컴파일러에서 우연히 되는 코드"가 UB의 전형입니다.

풀 버퍼링 (_IOFBF)버퍼(보통 4KB 등)가 가득 찰 때, fflush·fclose·정상 종료 시파일, 파이프로 리다이렉트된 stdout, fopen한 파일
무버퍼 (_IONBF)즉시stderr

"[1] 이체 처리 시작"은 왜 출력되지 않았을까?

printf는 문자열을 stdout 버퍼에 복사만 하고 반환했습니다. '\n'이 없으니 라인 버퍼링 규칙상 아직 내보낼 때가 아닙니다. 그 직후 segfault로 프로세스가 강제 종료되면 C 라이브러리가 버퍼를 비울 기회(정상 종료 시의 자동 flush)가 사라지고, 버퍼 내용은 프로세스 메모리와 함께 증발합니다. 개발자는 "1번 로그도 안 찍혔으니 시작도 안 했나 보다"라고 잘못된 결론을 내리게 됩니다.

출력을 파일로 리다이렉트하면(./a.out > out.log) stdout이 풀 버퍼링으로 바뀌어, '\n'이 있어도 수 KB가 쌓이기 전까지는 기록되지 않습니다. "터미널에서는 로그가 보이는데 파일에는 없다"는 현상이 이 때문입니다.

이렇게 해결합니다

  • 중요한 진단 메시지는 무버퍼인 stderr로 출력합니다: fprintf(stderr, "...");
  • 꼭 즉시 내보내야 하는 지점에서 fflush(stdout);을 호출합니다. 출력 스트림의 fflush는 표준에 정의된 올바른 사용입니다.
  • 스트림의 버퍼링 방식을 직접 지정합니다: setvbuf(stdout, NULL, _IOLBF, 0); (반드시 그 스트림에 첫 입출력을 하기 전에 호출)
  • 입력 프롬프트처럼 '\n' 없이 출력한 뒤 입력을 받는 경우, glibc 등 대부분의 구현은 입력 요청 시 라인 버퍼링된 stdout을 먼저 비워 주지만, 이식성을 위해 fflush(stdout)을 명시하는 것이 안전합니다.

은행 시스템에서는 — 거래 로그와 버퍼링

계정계 온라인 프로그램과 야간 배치는 모든 거래의 처리 과정을 로그 파일에 남깁니다. 장애가 나면 이 로그가 "어디까지 처리되었는가"를 판단하는 유일한 근거입니다. 그런데 로그 파일은 기본적으로 풀 버퍼링이므로, 프로세스가 비정상 종료되면 마지막 수십~수천 줄이 사라질 수 있습니다. 그 결과 "실제로는 원장 반영까지 끝났는데 로그에는 시작 기록조차 없는" 상황이 생겨 이중 처리 위험으로 이어집니다. 그래서 금융권 로그 모듈은 ① 거래 단위마다 fflush, ② 중요 로그는 setvbuf로 라인 버퍼링, ③ 정말 중요한 기록(거래 저널)은 fflush 후 fsync까지 호출해 운영체제 캐시에서 디스크로 확실히 기록하는 식의 정책을 둡니다. 반대로 대량 배치 로그를 매 줄 flush하면 시스템 콜이 폭증해 배치 시간이 길어지므로, 성능과 안전성 사이의 균형을 업무 중요도에 따라 정합니다.

핵심 정리

  • 문자는 문자 코드라는 정수로 저장됩니다. %c와 %d는 같은 값의 해석 차이일 뿐이며, C에서 문자 상수 'A'의 자료형은 int입니다.
  • ASCII는 0~127을 사용하며 제어 문자(0~31), 숫자(48~57), 대문자(65~90), 소문자(97~122)가 구역별로 연속 배치되고, 대소문자는 0x20 차이입니다. 표준이 연속성을 보장하는 것은 '0'~'9'뿐입니다.
  • char의 부호 여부는 구현 정의입니다. 바이트 데이터와 한글은 unsigned char로 다루고, ctype 함수에는 (unsigned char)로 변환해 넘깁니다.
  • c - '0'은 숫자 문자를 숫자로, n = n * 10 + d는 숫자 문자열을 정수로 바꿉니다. 전문 숫자 필드는 숫자 여부와 오버플로를 계산 전에 검사합니다.
  • 키보드 입력은 OS 줄 버퍼와 stdin 버퍼를 거치며, 엔터 키는 '\n'으로 버퍼에 들어갑니다. 입력 함수는 버퍼가 비었을 때만 기다립니다.
  • scanf("%d")는 숫자 뒤의 '\n'을 남기므로 이어지는 getchar/%c가 그것을 읽습니다. 줄 나머지 버리기, " %c", fgets 후 해석으로 해결합니다.
  • 버퍼 비우기의 표준 방법은 while ((c = getchar()) != '\n' && c != EOF);입니다. EOF 검사가 없으면 무한 루프가 될 수 있습니다.
  • EOF는 입력 끝/오류를 알리는 음수 신호값입니다. getchar는 256가지 바이트와 EOF를 구분하기 위해 int를 반환하므로 반환값은 반드시 int 변수에 받습니다.
  • fflush(stdin)은 표준상 UB입니다. fflush는 출력 스트림용입니다.
  • stdout은 터미널이면 라인 버퍼링, 파일·파이프면 풀 버퍼링, stderr는 무버퍼입니다. 비정상 종료 시 버퍼의 로그가 사라질 수 있으므로 중요한 로그는 fflush·setvbuf·stderr로 관리합니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. getchar의 반환형이 char가 아니라 int인 이유는 무엇인가요?

getchar는 0부터 255까지의 모든 바이트 값과, 입력의 끝이나 오류를 뜻하는 EOF를 서로 구분해서 돌려줘야 합니다. 총 257가지라 1바이트 char로는 표현할 수 없기 때문에 int를 반환합니다. 반환값을 char에 저장하면 char가 signed인 플랫폼에서는 0xFF 바이트를 EOF로 오인해 읽기가 중간에 끝나고, unsigned인 플랫폼에서는 EOF를 영원히 감지하지 못해 무한 루프가 생깁니다.

Q2. 입력 버퍼와 출력 버퍼를 사용하는 이유는 무엇인가요?

시스템 콜은 사용자 모드와 커널 모드 전환 비용이 커서, 1바이트마다 호출하면 매우 느립니다. 버퍼에 데이터를 모아 한 번에 읽고 쓰면 시스템 콜 횟수가 크게 줄어 성능이 좋아집니다. 또 터미널 입력에서는 줄 단위 버퍼 덕분에 사용자가 엔터를 누르기 전까지 백스페이스로 입력을 수정할 수 있습니다. 대신 출력 버퍼에 남은 데이터는 프로세스가 비정상 종료되면 유실될 수 있다는 단점이 있습니다.

꼬리 질문: "라인 버퍼링과 풀 버퍼링의 차이는?" → 줄바꿈마다 내보내는지, 버퍼가 찰 때 내보내는지의 차이이며, stdout은 터미널이면 라인, 파일이면 풀 버퍼링이라고 답합니다.

Q3. scanf로 숫자를 입력받은 다음 getchar를 호출하면 입력을 기다리지 않는 이유와 해결책은?

scanf의 %d 변환은 숫자 부분만 소비하고 뒤따르는 줄바꿈 문자를 입력 버퍼에 남겨 둡니다. 다음 getchar는 버퍼가 비어 있지 않으므로 기다리지 않고 남은 '\n'을 바로 읽어 갑니다. 해결책은 scanf 직후 '\n' 또는 EOF까지 읽어 버리는 루프를 돌리거나, %c 앞에 공백을 넣어 공백류를 건너뛰거나, fgets로 한 줄을 통째로 읽고 strtol이나 sscanf로 해석하는 것입니다.

Q4. fflush(stdin)을 쓰면 안 되는 이유는?

C 표준에서 fflush는 출력 스트림이나 마지막 연산이 입력이 아닌 갱신 스트림에 대해서만 정의되어 있고, 입력 스트림에 대해서는 미정의 동작입니다. 과거 일부 윈도우 런타임이 확장 기능으로 입력 버퍼를 비워 줬기 때문에 퍼졌지만, 리눅스 glibc 등에서는 효과가 없어 이식성이 없습니다. getchar 루프나 fgets 방식처럼 표준에 맞는 방법을 써야 합니다.

Q5. ASCII, 유니코드, UTF-8의 차이를 설명해 주세요.

ASCII는 0~127의 7비트 코드로 영문과 기호, 제어 문자만 정의합니다. 유니코드는 전 세계 문자에 고유 번호(코드 포인트)를 부여한 문자 집합이고, UTF-8은 그 번호를 1~4바이트로 저장하는 인코딩 방식입니다. UTF-8은 ASCII 범위를 1바이트 그대로 표현해 하위 호환되며, 한글은 대부분 3바이트입니다. 그래서 C에서 UTF-8 한글 문자열에 strlen을 쓰면 글자 수가 아니라 바이트 수가 나옵니다.

꼬리 질문: "EUC-KR과 UTF-8이 섞이면?" → 같은 바이트를 다른 규칙으로 해석해 글자가 깨지며, 금융권 레거시 연계에서는 인코딩 변환 계층을 명시적으로 둔다고 답합니다.

Q6. char, signed char, unsigned char의 차이는?

세 가지는 모두 1바이트지만 서로 다른 자료형입니다. signed char는 보통 -128~127, unsigned char는 0~255이며, 그냥 char가 둘 중 어느 쪽처럼 동작할지는 구현 정의로 x86에서는 보통 signed, ARM에서는 보통 unsigned입니다. 그래서 바이트 데이터나 ctype 함수 인자, 비트 연산에는 unsigned char를 명시하는 것이 안전합니다.

Q7. 문자 '5'를 정수 5로 바꾸는 방법과 그것이 항상 동작하는 이유는?

'5' - '0'으로 구합니다. C 표준이 '0'부터 '9'까지의 문자 코드가 연속이고 증가 순서임을 모든 실행 문자 집합에 대해 보장하기 때문에, ASCII든 EBCDIC이든 항상 동작합니다. 반면 알파벳의 연속성은 보장되지 않아 'c' - 'a' 같은 계산은 ASCII 전제가 됩니다.

Q8. 프로그램이 비정상 종료되었는데 printf로 찍은 마지막 로그가 보이지 않습니다. 왜 그럴까요?

printf의 출력은 stdout 버퍼에 쌓였다가 줄바꿈이나 버퍼가 찰 때, 또는 정상 종료 시점에 실제로 기록됩니다. segfault 같은 비정상 종료는 버퍼를 비울 기회 없이 프로세스를 끝내므로 버퍼에 있던 내용이 사라집니다. 특히 출력을 파일로 리다이렉트하면 풀 버퍼링이 되어 더 많이 유실됩니다. 중요한 로그는 stderr로 출력하거나 fflush를 호출하고, setvbuf로 버퍼링 방식을 조정합니다.

%d가 남긴 '\n'을 %c가 읽기 때문입니다. 최소 수정은 scanf(" %c", &yn);처럼 %c 앞에 공백을 넣는 것입니다. 더 견고하게 하려면 첫 scanf의 반환값이 1인지 확인하고, clear_input_line()으로 줄 나머지를 버린 뒤 질문합니다(사용자가 "2abc"처럼 입력한 경우까지 대비).

연습문제 11-8 계좌번호 입력 검증 난이도 ★★★

getchar로 한 줄을 읽으며 하이픈('-')은 무시하고 숫자만 최대 14자리까지 버퍼에 모으는 함수 int read_account(char *buf, int max)를 작성하세요. 숫자·하이픈 외 문자가 있거나 자릿수가 10~14가 아니면 -1, 정상이면 자릿수를 반환합니다. 줄 끝까지 반드시 소비해야 합니다.

정답과 해설 보기

핵심은 ① 오류를 발견해도 즉시 return하지 않고 '\n'까지 읽어 버퍼에 찌꺼기를 남기지 않는 것, ② 버퍼 크기를 넘는 문자는 저장하지 않되 개수는 세어 "너무 길다"를 판단하는 것입니다. 즉시 return하면 다음 입력이 남은 문자들을 읽어 연쇄 오류가 납니다.

연습문제 11-9 출력 버퍼링 난이도 ★★☆

./batch > batch.log로 실행한 배치가 중간에 segfault로 죽었는데, 로그 파일이 비어 있습니다. 터미널에서 실행할 때는 로그가 보였습니다. 원인과 대책 두 가지를 쓰세요.

정답과 해설 보기

stdout이 터미널이면 라인 버퍼링이라 '\n'마다 출력되지만, 파일로 리다이렉트되면 풀 버퍼링으로 바뀌어 버퍼(수 KB)가 찰 때까지 기록되지 않습니다. segfault는 버퍼를 비우지 않고 종료하므로 쌓여 있던 로그가 모두 사라졌습니다. 대책: ① 프로그램 시작 시 setvbuf(stdout, NULL, _IOLBF, 0);으로 라인 버퍼링 지정, ② 처리 단위마다 fflush(stdout); 호출, ③ 진단 로그는 무버퍼인 stderr로 출력하고 2>로 함께 저장.

연습문제 11-10 개념 판정 난이도 ★☆☆

다음 문장의 참/거짓을 판정하세요. (1) EOF는 파일 끝에 저장된 특수 문자다. (2) fflush(stdout)은 표준에 맞는 사용이다. (3) isdigit(c)는 c가 -50이어도 안전하게 0을 반환한다. (4) scanf("%d") 두 번을 연속 호출하면 '\n' 문제는 생기지 않는다. (5) '0'~'9'의 연속성은 C 표준이 보장한다.

정답과 해설 보기

(1) 거짓 — EOF는 입력 함수가 반환하는 신호값이지 파일 안의 문자가 아닙니다. (2) 참 — 출력 스트림의 fflush는 정의되어 있습니다. (3) 거짓 — 인자는 0~255 또는 EOF여야 하며 그 외는 UB입니다. (4) 참 — %d는 앞쪽 공백류를 건너뜁니다. (5) 참.

연습문제 11-11 금융 응용 — 전문 숫자 필드 검사기 난이도 ★★★

길이 len인 필드가 "모두 숫자"인지, "모두 공백"인지(미입력), "그 외"인지 판정하는 함수 int check_numeric_field(const char *f, int len)를 작성하세요. 반환값: 1 숫자, 0 공백, -1 오류. 공백 필드를 0원으로 처리할지 오류로 볼지는 업무 규칙에 따르므로 구분해서 알려 줍니다.

정답과 해설 보기

숫자 필드는 앞 0 채움이 규칙이므로 공백과 숫자가 섞인 " 1500"은 형식 오류로 봅니다. 길이 기반으로 처리하므로 필드가 널 종료되지 않아도 안전합니다.
