유닉스 시스템 프로그래밍

은행 계정계와 대외계의 C 프로그램은 대부분 유닉스(AIX, HP-UX, Solaris)나 리눅스 위에서 수십·수백 개의 프로세스로 돌아갑니다. 프로세스를 띄우고 거두는 법, 운영자가 보내는 종료 신호에 안전하게 반응하는 법, 프로세스끼리 데이터를 나누는 법을 모르면 미들웨어 로그 한 줄도 제대로 읽을 수 없습니다. 이 장은 금융 C 개발자의 "운영체제 문해력"을 길러 줍니다.

이 장에서 배울 것

  • 프로세스의 메모리 구조, 시스템 콜과 라이브러리 함수의 차이, 파일 디스크립터를 이해합니다.
  • fork/exec/wait로 프로세스를 만들고 거두며, 좀비·고아 프로세스가 생기는 이유와 해결법을 압니다.
  • 서버 프로그램을 데몬으로 만드는 절차를 구현합니다.
  • SIGINT, SIGTERM, SIGCHLD, SIGPIPE, SIGSEGV의 의미와 sigaction 사용법, async-signal-safe 규칙을 익힙니다.
  • 거래 처리 중 종료 신호를 받아도 데이터가 깨지지 않는 graceful shutdown 패턴을 구현합니다.
  • 파이프, FIFO, 공유메모리, 세마포어, 메시지 큐의 원리와 차이를 비교합니다.
  • 금융 미들웨어처럼 공유메모리에 환율·코드 테이블을 캐시하는 구조를 만들고, ipcs/ipcrm으로 운영합니다.

26-1프로세스와 시그널

프로세스란 무엇인가

프로그램(program)은 디스크에 저장된 실행 파일이고, 프로세스(process)는 그 프로그램이 메모리에 올라가 실행 중인 상태입니다. 요리책(프로그램) 한 권으로 여러 요리사(프로세스)가 동시에 각자 요리할 수 있는 것처럼, 하나의 실행 파일 trfsvr로 프로세스 50개를 띄울 수 있습니다. 각 프로세스는 운영체제가 부여한 고유 번호 PID와 자신을 만든 부모의 번호 PPID를 가지며, 무엇보다 자기만의 독립된 가상 주소 공간을 가집니다.

프로세스 A의 주소 0x7ffd1000과 프로세스 B의 주소 0x7ffd1000은 서로 다른 물리 메모리를 가리킵니다. 운영체제가 페이지 테이블로 가상 주소를 물리 주소에 따로 매핑하기 때문입니다. 그래서 한 프로세스가 포인터를 잘못 써서 메모리를 망가뜨려도 다른 프로세스는 안전합니다. 이 격리가 금융 미들웨어가 "프로세스 여러 개" 구조를 선호하는 큰 이유입니다. 한 거래 처리 프로세스가 SIGSEGV로 죽어도 나머지 49개는 계속 거래를 받습니다. 대신 프로세스끼리 데이터를 주고받으려면 운영체제가 제공하는 특별한 통로, 즉 26-2절의 IPC가 필요합니다.

여기서 잠깐 — 프로세스 상태 확인 명령

ps -ef | grep trfsvr          # 전체 프로세스 중 trfsvr (UID PID PPID ... CMD)
ps -o pid,ppid,stat,rss,cmd -p 41233   # 특정 프로세스의 상태(STAT), 메모리(RSS)
ls -l /proc/41233/fd          # (리눅스) 열린 파일 디스크립터 목록
pstree -p 41000               # 부모-자식 트리

STAT 열의 R은 실행 중, S는 대기(sleep), D는 디스크 I/O 등으로 중단 불가 대기, Z는 좀비, T는 정지입니다. 장애 상황에서 프로세스가 D 상태로 오래 머물면 스토리지·NFS 문제를 의심합니다.

시스템 콜과 라이브러리 함수

시스템 콜(system call)은 프로세스가 커널에게 일을 부탁하는 공식 창구입니다. 파일 읽기(read), 프로세스 생성(fork), 메모리 매핑(mmap), 소켓 통신(send)처럼 하드웨어나 다른 프로세스와 관련된 일은 사용자 프로그램이 직접 할 수 없고 반드시 시스템 콜을 거칩니다. 라이브러리 함수는 C 표준 라이브러리(libc) 등에 있는 일반 함수로, 사용자 공간에서 실행되며 필요할 때 내부적으로 시스템 콜을 호출합니다.

자주 하는 실수 — errno를 늦게 읽기

errno는 실패한 직후에만 의미가 있습니다. 시스템 콜이 실패한 뒤 로그 함수(fprintf 등)를 먼저 호출하면 그 함수가 내부에서 다른 시스템 콜을 하며 errno를 바꿀 수 있습니다. 실패 직후 int e = errno;로 저장하세요. 또 성공한 호출은 errno를 0으로 되돌리지 않으므로 "errno != 0이면 실패"라는 판단은 틀립니다. 반환값으로 실패를 판단하고 원인만 errno로 봅니다. 참고로 errno는 스레드마다 따로 있는(thread-local) 값입니다.

파일 디스크립터

유닉스 철학은 "모든 것은 파일이다"입니다. 일반 파일뿐 아니라 터미널, 파이프, 소켓, 장치도 모두 open(또는 socket, pipe)으로 열면 작은 정수 하나를 돌려받습니다. 이것이 파일 디스크립터(file descriptor, fd)입니다. fd는 프로세스별 fd 테이블의 인덱스이고, 테이블의 각 칸은 커널의 열린 파일 테이블 항목(현재 offset, 열기 모드)을 가리키며, 그 항목은 다시 실제 파일(inode)을 가리킵니다.

  • 0, 1, 2는 관례적으로 표준 입력·출력·오류이며, open은 항상 비어 있는 가장 작은 번호를 돌려줍니다. 그래서 close(1); open("log", ...)을 하면 그 파일이 표준 출력이 됩니다. dup2(fd, 1)은 이를 명시적으로 하는 시스템 콜입니다.
  • 프로세스가 열 수 있는 fd 수에는 한도가 있습니다(ulimit -n, 보통 1024 또는 운영 설정값). 소켓을 닫지 않는 fd 누수가 있으면 며칠 뒤 EMFILE(Too many open files)로 새 연결을 받지 못합니다. 메모리 누수만큼 흔한 금융 서버 장애 원인입니다.
  • exec로 다른 프로그램을 실행해도 열린 fd는 기본적으로 유지됩니다. 의도치 않게 자식에게 소켓이 새지 않도록 O_CLOEXEC 플래그를 씁니다.

은행 시스템에서는 — 사흘마다 멈추는 대외계 게이트웨이

어느 대외계 게이트웨이가 정확히 사흘에 한 번꼴로 새 연결을 받지 못하고 멈췄습니다. 재기동하면 멀쩡해서 "주기적 재기동"으로 버티고 있었는데, 원인은 상대 기관 응답 타임아웃이 나는 경로에서 소켓을 close하지 않고 return하는 코드였습니다. 하루 수백 건의 타임아웃이 쌓여 fd 한도 1024에 도달하는 데 사흘이 걸렸던 것입니다. ls /proc/PID/fd | wc -l을 시간대별로 기록하는 모니터링을 추가하자 증가 추세가 바로 보였습니다. fd 수는 메모리 사용량처럼 반드시 모니터링해야 하는 지표입니다. 그리고 오류 경로마다 자원을 정리하는 goto cleanup 패턴(18장)을 습관화해야 합니다.

fork, exec, wait

유닉스에서 새 프로세스를 만드는 방법은 독특합니다. 새 프로그램을 바로 띄우는 대신 ① fork()로 자기 자신을 복제하고 ② 복제된 자식이 exec() 계열 함수로 다른 프로그램으로 변신하며 ③ 부모는 wait()로 자식이 끝나기를 기다려 종료 상태를 거둡니다.

이것이 25장에서 말한 "배치 스케줄러"의 가장 작은 형태입니다. 실제 스케줄러도 본질적으로 fork → exec → waitpid → 종료 코드 판정을 반복합니다.

왜 그럴까? — fork는 프로세스 전체를 복사하는데 왜 빠를까? (Copy-on-Write)

1GB 메모리를 쓰는 프로세스가 fork할 때마다 1GB를 복사한다면 엄청나게 느릴 것입니다. 현대 유닉스는 쓰기 시 복사(Copy-on-Write, CoW)를 씁니다. fork 직후 부모와 자식은 같은 물리 페이지를 공유하고, 그 페이지들을 읽기 전용으로 표시해 둡니다. 어느 한쪽이 페이지에 쓰려고 하면 페이지 폴트가 나고, 커널이 그 순간 그 페이지 하나(보통 4KB)만 복사해 줍니다. 곧바로 exec하는 자식은 거의 아무것도 복사하지 않고 새 프로그램으로 바뀌므로 비용이 매우 작습니다. 그래도 페이지 테이블 복사 비용은 있어서, 거대한 프로세스에서 자주 fork하는 것은 피합니다(posix_spawn이 대안).

왜 그럴까? — 자식에서 exec 실패 시 왜 exit가 아니라 _exit일까?

fork는 부모의 stdio 버퍼까지 그대로 복사합니다. 부모가 printf("처리 시작 ")처럼 아직 출력되지 않은 내용을 버퍼에 가지고 있었다면 자식도 같은 내용을 가집니다. 자식이 exit()를 호출하면 stdio 버퍼를 비우면서(flush) 그 내용을 한 번 더 출력하고, atexit로 등록된 부모의 정리 함수(임시 파일 삭제, DB 연결 종료 등)까지 실행해 버립니다. _exit()은 이런 사용자 공간 정리를 하지 않고 즉시 커널에 종료를 요청합니다. 그래서 fork된 자식이 exec 없이 끝날 때는 _exit을 씁니다.

터미널에서도 start end가 두 줄 나옵니다. "start\n"으로 바꾸면 터미널(줄 버퍼)에서는 한 번만 나오지만, 출력을 파일로 리다이렉트하면(완전 버퍼) 다시 두 번 나옵니다. 그래서 fork 직전에는 fflush(NULL)로 모든 출력 버퍼를 비우는 것이 정석입니다.

8번입니다. fork 한 번마다 프로세스 수가 두 배가 됩니다: 1 → 2 → 4 → 8. 각 프로세스가 printf를 한 번씩 실행합니다. 개행이 있고 터미널이라 버퍼 중복 문제는 없습니다. 출력 순서는 스케줄링에 따라 매번 다를 수 있고, 부모가 자식을 기다리지 않으므로 셸 프롬프트가 중간에 섞여 나올 수도 있습니다. 실무에서 루프 안에 fork를 잘못 넣으면 이렇게 프로세스가 기하급수적으로 늘어나는 fork 폭탄이 되어 서버 전체가 멈춥니다. ulimit -u로 사용자별 프로세스 수 한도를 거는 이유입니다.

좀비 프로세스와 고아 프로세스

자식 프로세스가 종료되면 커널은 메모리 등 대부분의 자원을 회수하지만, PID와 종료 상태는 부모가 wait로 가져갈 때까지 남겨 둡니다. 부모가 거두기 전까지의 이 상태를 좀비(zombie)라고 부릅니다(ps에서 STAT Z, <defunct>). 반대로 부모가 먼저 죽으면 자식은 고아(orphan)가 되고, 커널은 이를 PID 1(init 또는 systemd, 또는 지정된 subreaper)에게 입양시킵니다. 입양한 부모가 대신 wait해 주므로 고아는 좀비로 남지 않습니다.

이렇게 해결합니다 — 좀비를 남기지 않는 세 가지 방법

  1. 동기적으로 기다리기: 위 run_job처럼 waitpid(pid, &st, 0)로 끝날 때까지 기다립니다. 순차 배치에 적합합니다.
  2. SIGCHLD에서 거두기: 자식이 끝나면 부모에게 SIGCHLD가 옵니다. 핸들러 또는 메인 루프에서 while (waitpid(-1, &st, WNOHANG) > 0)로 끝난 자식을 모두 거둡니다. 27장의 fork 기반 동시 서버가 이 방식입니다.
  3. 종료 상태가 필요 없으면: SIGCHLD의 처리를 SIG_IGN으로 설정하면(POSIX.1-2001 이상) 커널이 자식을 자동으로 거둡니다. 단, 이후 wait은 자식의 종료 상태를 받을 수 없습니다.

자주 하는 실수 — SIGCHLD 핸들러에서 wait 한 번만 호출

유닉스 표준 시그널은 쌓이지 않습니다(not queued). 자식 세 개가 거의 동시에 죽으면 SIGCHLD는 한 번만 전달될 수 있습니다. 핸들러에서 wait(&st)를 한 번만 하면 나머지 둘은 좀비로 남습니다. 반드시 WNOHANG과 함께 반환값이 0 이하가 될 때까지 반복해야 합니다.

데몬화

데몬(daemon)은 터미널과 무관하게 백그라운드에서 계속 실행되는 서버 프로세스입니다. 금융 미들웨어의 거래 처리 서버, 대외계 게이트웨이, 파일 전송 에이전트가 모두 데몬입니다. 운영자가 SSH로 접속해 서버를 띄우고 로그아웃해도 살아 있어야 하고, 터미널의 Ctrl+C나 연결 끊김(SIGHUP)의 영향을 받으면 안 됩니다.

왜 그럴까? — 왜 fork를 두 번 할까?

유닉스에서 세션 리더가 터미널 장치를 열면 그 터미널이 제어 터미널로 붙을 수 있습니다(System V 계열 동작). 첫 번째 fork + setsid()로 터미널과 분리된 새 세션의 리더가 되었지만, 리더인 채로 남아 있으면 나중에 실수로 터미널 장치를 열 때 다시 제어 터미널을 얻을 위험이 있습니다. 두 번째 fork로 만든 손자 프로세스는 세션 리더가 아니므로 그럴 가능성이 원천적으로 사라집니다. 또 첫 번째 fork는 setsid가 "프로세스 그룹 리더는 호출할 수 없다"는 제약을 피하기 위해 필요합니다(셸이 실행한 프로세스는 보통 그룹 리더입니다).

여기서 잠깐 — systemd 시대의 데몬

최근 리눅스에서는 systemd 같은 서비스 관리자가 프로세스를 띄우고 감시합니다. 이 경우 프로그램이 스스로 데몬화하지 않고 포그라운드로 실행되는 것이 권장됩니다(Type=simple). 서비스 관리자가 터미널 분리, 로그 수집, 비정상 종료 시 재시작을 대신 해 줍니다. 하지만 AIX·HP-UX 같은 상용 유닉스와 오래된 금융 미들웨어 환경에서는 여전히 자체 데몬화 코드가 표준이므로 둘 다 알아야 합니다. 어느 쪽이든 PID 파일(/var/run/trfsvr.pid)을 25장의 락 파일 방식으로 관리하면 중복 기동을 막을 수 있습니다.

시그널의 종류

시그널(signal)은 프로세스에게 비동기적으로 전달되는 짧은 알림입니다. "전화벨"에 비유할 수 있습니다. 벨이 울리면 하던 일을 잠시 멈추고 응대(핸들러 실행)하거나, 무시하거나, 기본 동작(대부분 종료)을 하게 됩니다. 운영자의 kill 명령, 키보드 Ctrl+C, 자식 프로세스 종료, 잘못된 메모리 접근 같은 사건이 시그널로 전달됩니다.

은행 시스템에서는 — 상대 기관이 연결을 끊자 서버가 사라졌다

대외계 송신 프로세스가 아무 로그도 남기지 않고 사라지는 일이 가끔 있었습니다. 코어 덤프도 없고, 종료 로그도 없었습니다. 원인은 SIGPIPE였습니다. 상대 기관이 점검을 위해 TCP 연결을 끊은 직후에 우리 쪽이 그 소켓에 write하자 커널이 SIGPIPE를 보냈고, 기본 동작인 "조용한 종료"로 프로세스가 사라진 것입니다. 해결은 프로그램 시작 시 signal(SIGPIPE, SIG_IGN)(또는 send에 MSG_NOSIGNAL)을 설정하여, write가 -1과 errno == EPIPE를 반환하도록 하고 이를 "상대 연결 끊김"으로 로그를 남긴 뒤 재연결하는 것이었습니다. 소켓 서버의 첫 줄은 SIGPIPE 무시라고 외워 두세요.

sigaction과 async-signal-safe

시그널 처리 방식을 등록하는 함수로 signal()과 sigaction()이 있습니다. signal()은 표준 C에 있지만 핸들러 실행 후 기본 동작으로 되돌아가는지, 끊긴 시스템 콜을 재시작하는지 등이 플랫폼마다 다릅니다(System V와 BSD의 역사적 차이). 실무에서는 동작이 명확히 정의된 POSIX sigaction()을 씁니다.

왜 그럴까? — 시그널 핸들러에서 printf, malloc을 쓰면 왜 안 될까?

시그널은 프로그램의 아무 지점에서나 끼어듭니다. 메인 코드가 malloc 안에서 힙의 내부 연결 리스트를 고치는 도중, 즉 자료구조가 반쯤 바뀐 순간에 시그널이 오면 핸들러가 실행됩니다. 핸들러가 다시 malloc을 부르면 깨진 자료구조를 건드려 힙이 오염되거나, malloc이 내부 락을 잡고 있던 상태라면 같은 락을 다시 잡으려다 영원히 멈추는 교착 상태(deadlock)에 빠집니다. printf도 내부 버퍼와 락, 때로는 malloc을 쓰므로 마찬가지입니다. 이런 함수를 재진입 불가(non-reentrant)라고 합니다.

POSIX는 핸들러에서 안전하게 호출할 수 있는 async-signal-safe 함수 목록을 정해 두었습니다. write, read, _exit, waitpid, kill, sigaction, open, close 등 대부분 시스템 콜 래퍼이고, printf, malloc, free, exit, syslog, 대부분의 pthread 함수는 들어 있지 않습니다. 그리고 핸들러가 공유하는 변수는 volatile sig_atomic_t여야 합니다. volatile은 컴파일러가 루프에서 값을 레지스터에 캐시해 변경을 놓치는 최적화를 막고, sig_atomic_t는 읽기·쓰기가 시그널에 의해 중간에 쪼개지지 않는 정수 타입을 보장합니다.

자주 하는 실수 — 핸들러에서 errno를 바꾸기

핸들러에서 waitpid나 write를 호출하면 그 함수가 errno를 바꿀 수 있습니다. 메인 코드가 read 실패 직후 errno를 확인하려는 바로 그 순간에 핸들러가 끼어들어 값을 바꾸면 엉뚱한 오류 원인이 보고됩니다. 핸들러 시작에서 int saved = errno;, 끝에서 errno = saved;로 복원하는 것이 안전한 관용구입니다.

graceful shutdown — 거래 도중에 죽지 않기

운영자가 야간 배포를 위해 거래 서버에 kill(SIGTERM)을 보냈다고 합시다. 그 순간 서버는 이체 한 건을 처리하는 중이었습니다. 출금은 DB에 반영했고 대외기관으로 입금 요청 전문을 보내려던 참입니다. 여기서 프로세스가 즉시 죽으면 어떻게 될까요? "돈은 빠졌는데 상대에게는 가지 않은" 상태가 남고, 이를 정리하는 데 사람 손이 필요합니다. graceful shutdown은 종료 요청을 받으면 새 일은 받지 않고, 하던 일은 마무리하고, 자원을 정리한 뒤 종료하는 것입니다.

왜 그럴까? — 왜 SA_RESTART를 끄고 EINTR을 받도록 했을까?

서버가 accept나 read에서 요청을 기다리며 블로킹되어 있을 때 SIGTERM이 오면, 핸들러가 플래그를 세운 뒤 원래 호출로 돌아갑니다. 이때 SA_RESTART가 켜져 있으면 커널이 그 블로킹 호출을 자동으로 다시 시작하므로, 다음 요청이 올 때까지(심야라면 몇 시간) 루프 조건 !g_stop을 다시 볼 기회가 없습니다. SA_RESTART를 끄면 블로킹 호출이 -1과 EINTR로 즉시 반환되어 루프 조건을 확인하고 종료 단계로 넘어갑니다. 반대로 SIGHUP 같은 "알림성" 시그널은 진행 중인 I/O를 끊을 이유가 없으니 SA_RESTART를 켜 둡니다. (단, 시그널이 "플래그 확인 직후, 블로킹 호출 진입 직전"에 오면 놓칠 수 있는 경쟁 조건이 있습니다. 이를 완벽히 막으려면 pselect/ppoll이나 self-pipe 기법을 씁니다 — 27장에서 다룹니다.)

여기서 잠깐 — SIGSEGV는 잡아서 살리면 안 됩니다

SIGSEGV(세그멘테이션 오류)는 NULL 역참조, 해제된 메모리 접근, 배열 범위 초과, 스택 오버플로 등 이미 메모리가 오염되었다는 신호입니다. 핸들러에서 잡아 "계속 실행"하면 오염된 상태로 거래를 처리하게 되어 훨씬 큰 사고가 납니다. 올바른 대응은 ① 코어 덤프를 남기고 죽게 두기(ulimit -c unlimited, 코어 저장 경로 설정) ② 감시 프로세스가 자동 재기동 ③ gdb ./trfsvr core.41233 → bt로 원인 분석입니다. 핸들러를 둔다면 async-signal-safe한 write로 최소한의 로그를 남기고 기본 동작으로 되돌린 뒤 raise(sig)로 다시 죽는 정도까지만 합니다.

26-2IPC: 파이프, 공유메모리, 세마포어

26-1절에서 본 것처럼 프로세스는 서로의 메모리를 볼 수 없습니다. 그런데 금융 미들웨어에서는 프로세스끼리 협력할 일이 많습니다. 채널 처리 프로세스가 받은 요청을 거래 처리 프로세스에 넘겨야 하고, 50개의 거래 프로세스가 같은 환율 테이블을 참조해야 하며, 전문일련번호 카운터를 겹치지 않게 나눠 써야 합니다. 운영체제가 제공하는 이런 통로를 IPC(Inter-Process Communication, 프로세스 간 통신)라고 합니다.

파이프

파이프(pipe)는 가장 오래되고 단순한 IPC입니다. 셸의 ls | grep dat에서 |가 바로 파이프입니다. pipe(fd)를 호출하면 커널 안에 작은 버퍼(리눅스 기본 64KB)가 생기고 두 개의 fd를 받습니다. fd[1]에 쓴 바이트는 fd[0]에서 읽힙니다. 이름이 없으므로 fork로 fd를 물려받은 친족 프로세스끼리만 쓸 수 있고, 한 방향으로만 흐릅니다.

왜 그럴까? — 안 쓰는 쪽 끝을 왜 꼭 닫아야 할까?

파이프에서 읽는 쪽이 EOF(0 반환)를 받는 조건은 "그 파이프의 쓰기 끝을 가리키는 fd가 시스템 전체에 하나도 남지 않았을 때"입니다. fork 직후에는 부모와 자식이 모두 쓰기 끝 fd[1]을 가지고 있습니다. 자식이 자기 fd[1]을 닫지 않으면, 부모가 쓰기를 끝내고 닫아도 자식 자신이 쓰기 끝을 쥐고 있으므로 자식의 fgets는 EOF를 받지 못하고 영원히 기다립니다. 부모는 waitpid로 자식을 기다리니 둘 다 멈춥니다. 반대로 읽는 쪽이 모두 닫힌 파이프에 쓰면 SIGPIPE가 발생합니다. 파이프는 버퍼가 가득 차면 쓰기가, 비어 있으면 읽기가 블록되므로 흐름 제어가 자동으로 됩니다.

여기서 잠깐 — popen

FILE *p = popen("sort -k2 trf.txt", "r");는 pipe + fork + exec(셸)을 한 번에 해 주는 라이브러리 함수입니다. 외부 명령의 출력을 읽거나 입력을 줄 때 편리하지만, 명령 문자열이 셸에 그대로 전달되므로 외부 입력(파일명 등)을 섞으면 명령 주입(command injection) 취약점이 됩니다. 반드시 pclose로 닫아 자식을 거두고 종료 코드를 확인하세요.

FIFO (이름 있는 파이프)

FIFO는 파일시스템에 이름을 가진 파이프입니다. mkfifo /app/run/req.fifo로 만들면 친족 관계가 없는 프로세스도 그 경로를 open해 통신할 수 있습니다. 데이터는 디스크에 저장되지 않고 커널 버퍼만 거칩니다.

mkfifo -m 600 /app/run/cmd.fifo
ls -l /app/run/cmd.fifo        # prw------- : 첫 글자 p 가 FIFO
echo "RELOAD RATE" > /app/run/cmd.fifo     # 운영자가 데몬에 명령 전달

FIFO의 특징은 ① open이 상대방이 반대쪽을 열 때까지 블록된다는 점(O_NONBLOCK으로 바꿀 수 있음) ② PIPE_BUF(리눅스 4096바이트) 이하의 쓰기는 원자적이라 여러 쓰는 프로세스의 메시지가 섞이지 않는다는 점입니다. 운영 명령 채널이나 간단한 로그 수집에 쓰입니다.

공유메모리 — System V와 POSIX

공유메모리(shared memory)는 같은 물리 메모리 페이지를 여러 프로세스의 주소 공간에 매핑하는 방식입니다. 한 번 연결하면 일반 포인터로 읽고 쓰므로 커널을 거치는 복사가 없고, IPC 중 가장 빠릅니다. 대신 커널이 아무것도 조율해 주지 않으므로 여러 프로세스가 동시에 쓰는 문제(경쟁 조건)는 세마포어 등으로 프로그래머가 직접 막아야 합니다.

자주 하는 실수 — 공유메모리에 포인터 저장

공유메모리 안에 연결 리스트를 만들며 node->next = &other_node;처럼 포인터를 저장하면, 그 주소는 저장한 프로세스의 가상 주소입니다. 다른 프로세스는 같은 세그먼트를 다른 주소에 붙였을 수 있으므로 그 포인터는 엉뚱한 곳을 가리킵니다. 공유메모리 안에서는 포인터 대신 세그먼트 시작으로부터의 오프셋(인덱스)을 저장합니다. 또 구조체 레이아웃이 바뀌면(필드 추가) 이미 떠 있는 프로세스와 새 프로세스가 같은 메모리를 다르게 해석하므로, 맨 앞에 매직 넘버와 레이아웃 버전을 두고 붙을 때 검사합니다.

세마포어

세마포어(semaphore)는 다익스트라가 고안한 동기화 도구로, 0 이상의 정수 카운터와 두 연산으로 이루어집니다. P(wait): 값이 0보다 크면 1 감소하고 진행, 0이면 양수가 될 때까지 대기. V(post): 값을 1 증가하고 대기 중인 프로세스 하나를 깨움. 초기값이 1이면 한 번에 한 프로세스만 들어가는 이진 세마포어(상호 배제), N이면 N개까지 동시에 허용하는 카운팅 세마포어(예: 대외기관 동시 연결 수 제한)가 됩니다.

왜 그럴까? — SEM_UNDO는 왜 금융권에서 중요할까?

세마포어를 잡은(P) 프로세스가 V를 하기 전에 SIGSEGV나 kill -9로 죽었다고 합시다. 세마포어 값은 0으로 남고, 나머지 49개 프로세스는 영원히 P에서 대기합니다. 거래 서버 전체가 멈추는 것입니다. SEM_UNDO 플래그를 주면 커널이 프로세스별로 "이 프로세스가 세마포어를 얼마나 바꿨는지"를 기록해 두었다가, 프로세스가 어떤 이유로든 종료하면 그 변경을 자동으로 되돌립니다. POSIX 이름 있는 세마포어(sem_open)에는 이 기능이 없어서, 오래된 금융 미들웨어가 System V 세마포어를 고집하는 이유 중 하나가 됩니다. 단, 되돌려지는 것은 세마포어 값뿐이고 공유메모리 내용은 반쯤 수정된 채로 남을 수 있다는 점을 기억하세요. 그래서 임계 구역은 짧게, 그리고 "중간 상태"가 남아도 복구 가능한 방식으로 설계합니다.

여기서 잠깐 — 세마포어와 뮤텍스의 차이

뮤텍스(mutex)는 "잠근 사람만 열 수 있는" 소유권 개념이 있는 잠금이고, 주로 한 프로세스 안의 스레드 사이에서 씁니다(28장). 세마포어는 소유권이 없는 카운터라 A가 P하고 B가 V하는 것도 가능하며, 그래서 "작업이 끝났음을 알리는 신호" 용도로도 쓸 수 있습니다. 이진 세마포어는 뮤텍스처럼 쓸 수 있지만, 소유권 검사가 없어 실수로 다른 프로세스가 V를 하면 상호 배제가 깨집니다. 면접 단골 질문입니다.

메시지 큐

메시지 큐(message queue)는 커널이 관리하는 우편함입니다. 파이프와 달리 메시지 경계가 보존되어 한 번 보낸 덩어리가 그대로 한 번에 읽히고, 각 메시지에 타입(mtype)을 붙여 받는 쪽이 원하는 타입만 골라 꺼낼 수 있습니다. 채널 프로세스가 거래 요청을 큐에 넣고, 여러 거래 처리 프로세스가 꺼내 가는 작업 분배 구조에 잘 맞습니다.

은행 시스템에서는 — 가득 찬 메시지 큐

메시지 큐의 총 용량은 커널 파라미터(리눅스 kernel.msgmnb, 기본 16KB 내외)로 제한됩니다. 월말 오전처럼 거래가 몰리는 시간에 거래 처리 프로세스 몇 개가 DB 락 대기로 느려지자, 채널 프로세스가 넣는 요청이 쌓여 큐가 가득 찼습니다. 채널 프로세스는 IPC_NOWAIT 없이 msgsnd를 호출하고 있었기 때문에 그대로 블록되었고, 채널 쪽 소켓까지 막히면서 모바일 앱 전체가 "응답 없음" 상태가 되었습니다. 해결은 ① 큐 크기 상향과 모니터링(ipcs -q의 used-bytes, messages) ② IPC_NOWAIT로 즉시 실패시켜 고객에게 "잠시 후 다시 시도" 응답을 주는 부하 차단(load shedding) ③ 처리 프로세스 수 자동 조절이었습니다. 블로킹 IPC 호출에는 언제나 "상대가 영원히 안 받으면?"이라는 질문을 던져야 합니다.

금융 미들웨어의 공유메모리 캐시 — 환율·코드 테이블

거래 처리 프로세스 수십 개가 매 거래마다 은행코드 테이블, 지점 테이블, 수수료 테이블, 환율을 조회합니다. 이것을 매번 DB에서 읽으면 DB 부하가 폭증하고 응답 시간이 늘어납니다. 프로세스마다 메모리에 따로 캐시하면 50개 프로세스가 같은 데이터를 50벌 들고 있게 되고, 환율이 바뀌었을 때 50개를 모두 갱신해야 합니다. 그래서 금융 미들웨어는 전통적으로 공유메모리에 참조 테이블을 한 벌 올려 두고 모든 프로세스가 읽는 구조를 씁니다.

읽기가 압도적으로 많고(초당 수만 회) 쓰기는 드문(수 분에 한 번) 패턴입니다. 읽을 때마다 세마포어를 잡으면 수십 개 프로세스가 세마포어에서 줄을 서게 됩니다. 여기서는 리눅스 커널에서도 쓰는 시퀀스 락(seqlock) 기법을 씁니다. 쓰는 쪽은 시작할 때 seq를 홀수로, 끝날 때 짝수로 올립니다. 읽는 쪽은 락 없이 읽되, 읽기 전후의 seq가 같은 짝수일 때만 결과를 믿고, 아니면 다시 읽습니다.

왜 그럴까? — 왜 메모리 펜스(fence)가 필요할까?

현대 CPU와 컴파일러는 성능을 위해 메모리 읽기·쓰기의 순서를 바꿀 수 있습니다. writer가 "seq를 홀수로 → 데이터 쓰기 → seq를 짝수로" 순서로 코드를 써도, 다른 CPU 코어에서 보기에는 데이터 쓰기 일부가 seq 홀수 변경보다 먼저 보일 수 있습니다. 그러면 reader가 "seq 짝수(안정)"를 본 상태에서 반쯤 바뀐 데이터를 읽고, 두 번째 seq 검사도 통과할 수 있습니다. atomic_thread_fence와 release/acquire 순서 지정은 "이 지점 앞의 메모리 연산이 뒤의 연산보다 먼저 보이게" 하는 약속을 컴파일러와 CPU에 강제합니다. 엄밀히 말해 C11 메모리 모델에서는 seqlock의 데이터 읽기 자체가 경쟁(data race)으로 분류될 여지가 있어, 커널이나 고성능 라이브러리는 데이터 필드도 relaxed 원자 연산으로 읽는 등 더 엄격하게 구현합니다. 실무에서 직접 구현하기보다는 검증된 라이브러리를 쓰고, 원리를 이해하는 데 이 코드를 활용하세요. 메모리 순서는 28장에서 더 다룹니다.

은행 시스템에서는 — 레이아웃 버전을 검사하지 않은 대가

어느 은행에서 수수료 코드 테이블 구조체에 "우대 구분" 필드 하나를 추가한 버전을 배포했습니다. 배포 절차상 로더 프로세스가 먼저 재기동되어 공유메모리를 새 레이아웃으로 다시 채웠는데, 아직 재기동되지 않은 거래 프로세스들은 옛 레이아웃으로 같은 메모리를 읽었습니다. 필드가 하나씩 밀려서 수수료 금액 위치에서 다른 값을 읽었고, 약 20분간 일부 이체에 잘못된 수수료가 부과되었습니다. 이후 공유메모리 헤더에 매직 넘버와 레이아웃 버전을 두고, 버전이 다르면 붙기를 거부하며, 구조 변경 시에는 새 이름의 세그먼트(/fee_tbl_v2)를 만들어 순차 전환하도록 배포 절차를 바꾸었습니다. 위 rate_attach가 버전을 검사하는 이유입니다.

ipcs와 ipcrm으로 운영하기

System V IPC 자원(공유메모리, 세마포어, 메시지 큐)은 프로세스가 죽어도 커널에 남습니다. 이는 장점(프로세스 재기동 후에도 캐시 유지)이자 단점(찌꺼기 누적)입니다. 운영자는 ipcs로 현황을 보고 ipcrm으로 정리합니다.

ipcs -a                 # 모든 IPC 자원 (-m 공유메모리, -s 세마포어, -q 메시지 큐)
ipcs -m -p              # 공유메모리를 만든 PID(cpid), 마지막 사용 PID(lpid)
ipcs -q                 # 메시지 큐: used-bytes, messages 가 계속 늘면 소비자 문제
ipcs -l                 # 커널 한도 (shmmax, semmni, msgmnb ...)
ipcrm -m 32769          # shmid로 공유메모리 삭제 표시
ipcrm -M 0x5201a3c4     # key로 삭제
ipcrm -s 98304          # 세마포어 삭제
sysctl kernel.shmmax kernel.sem kernel.msgmnb   # (리눅스) 한도 확인

nattch는 붙어 있는 프로세스 수, status의 dest는 삭제 표시가 되었지만 아직 붙은 프로세스가 있어 실제로는 남아 있는 상태입니다(위 예에서는 nattch 0이므로 곧 사라짐).

자주 하는 실수 — 운영 중인 IPC를 ipcrm

  • 장애 복구 중 "찌꺼기 정리"라며 ipcrm을 돌렸는데 그것이 살아 있는 다른 업무의 세마포어였다면, 그 업무 프로세스들의 다음 semop이 EIDRM/EINVAL로 실패해 업무가 중단됩니다. 삭제 전에 ipcs -p로 소유 프로세스와 key를 확인하고, 시스템별 key 목록을 운영 문서에 관리합니다.
  • ftok는 파일의 inode 번호와 디바이스 번호 일부로 key를 만듭니다. 키 파일을 지웠다가 다시 만들면 inode가 바뀌어 다른 key가 되고, 새 프로세스는 옛 세그먼트를 찾지 못한 채 새로 만듭니다. 또 서로 다른 파일이 같은 key를 만드는 충돌도 드물게 일어납니다. 그래서 금융 미들웨어는 key를 설정 파일에 고정 숫자로 정의하는 경우가 많습니다.
  • 권한을 0666으로 만들면 같은 서버의 모든 사용자가 환율 테이블을 바꿀 수 있습니다. 최소 권한(0640, 전용 그룹)을 씁니다.

예제 26-3 난이도 ★★☆

전문일련번호 채번을 공유메모리 카운터로 하는데, 세마포어 없이 v = s->next_seq++;만 했다면 어떤 일이 생길 수 있습니까? 구체적인 실행 순서로 설명하세요.

정답과 해설 보기

s->next_seq++는 기계어로 "메모리에서 읽기 → 레지스터에서 1 증가 → 메모리에 쓰기" 세 단계입니다. next_seq가 100일 때 프로세스 A가 100을 읽고, 증가 후 쓰기 전에 프로세스 B가 역시 100을 읽으면, 둘 다 100을 일련번호로 사용하고 둘 다 101을 씁니다. 같은 일련번호의 전문 두 개가 대외기관으로 나가 두 번째는 중복 전문으로 거절되거나, 응답 매칭이 꼬입니다. 이 경쟁 조건은 부하가 높을 때만 드물게 나타나 테스트에서 발견하기 어렵습니다. 세마포어로 임계 구역을 보호하거나, C11 atomic_fetch_add(공유메모리에서 lock-free 원자 타입이면 프로세스 간에도 동작)로 원자적 증가를 해야 합니다.

핵심 정리

  • 프로세스는 실행 중인 프로그램이며 독립된 가상 주소 공간(text, data, bss, heap, stack)을 가집니다. 격리 덕분에 한 프로세스의 메모리 오류가 다른 프로세스로 번지지 않습니다.
  • 시스템 콜은 커널 모드로 들어가는 공식 창구(-1 + errno), 라이브러리 함수는 사용자 공간 함수입니다. errno는 실패 직후 저장합니다.
  • fd는 프로세스 fd 테이블의 인덱스이며 열린 파일 테이블(offset 공유)을 거쳐 inode를 가리킵니다. fd 누수는 EMFILE 장애로 이어지므로 모니터링합니다.
  • fork는 Copy-on-Write로 자신을 복제하고 부모에게 자식 PID, 자식에게 0을 반환합니다. 자식은 exec로 다른 프로그램이 되고, 부모는 waitpid와 WIFEXITED/WEXITSTATUS로 종료 상태를 거둡니다. fork 전 fflush(NULL), exec 실패 시 _exit.
  • 거두지 않은 종료 자식은 좀비, 부모를 잃은 자식은 고아(PID 1이 입양)입니다. SIGCHLD에서 waitpid(-1, ..., WNOHANG)를 반복해 모두 거둡니다.
  • 데몬화: fork → setsid → fork → umask → chdir("/") → 표준 입출력 /dev/null. systemd 환경에서는 포그라운드 실행이 권장됩니다.
  • 시그널: SIGTERM/SIGINT는 graceful shutdown, SIGKILL은 잡을 수 없음, SIGPIPE는 반드시 무시, SIGSEGV는 잡아서 계속 실행 금지, SIGCHLD는 자식 거두기.
  • sigaction을 쓰고, 핸들러는 volatile sig_atomic_t 플래그만 세웁니다. 핸들러 안에서는 async-signal-safe 함수만 호출하고 errno를 보존합니다.
  • IPC: 파이프(친족, 스트림), FIFO(이름 있음), 메시지 큐(메시지 경계·타입), 공유메모리(가장 빠름, 동기화 직접), 세마포어(동기화). 각각의 블로킹·용량·수명 특성을 이해하고 고릅니다.
  • System V 세마포어의 SEM_UNDO는 프로세스가 죽어도 세마포어를 복구해 줍니다. 공유메모리에는 포인터 대신 오프셋을, 맨 앞에 매직·레이아웃 버전을 둡니다.
  • 읽기 위주 공유 캐시는 seqlock 같은 락 없는 읽기로 확장성을 얻습니다. System V IPC는 ipcs로 감시하고 ipcrm은 소유자를 확인한 뒤에만 씁니다.

Q1. 프로세스와 스레드의 차이를 설명해 보세요.

프로세스는 독립된 주소 공간과 자원(fd 테이블 등)을 가진 실행 단위이고, 스레드는 한 프로세스 안에서 코드·데이터·힙·fd를 공유하고 스택과 레지스터만 따로 가진 실행 흐름입니다. 프로세스는 격리가 강해 한쪽이 죽어도 다른 쪽이 안전하지만 생성·문맥 전환 비용과 통신 비용(IPC)이 큽니다. 스레드는 가볍고 메모리 공유가 쉽지만 하나의 메모리 오류가 프로세스 전체를 죽이고 동기화 버그 위험이 큽니다. 금융 미들웨어가 다중 프로세스 구조를 오래 써 온 이유가 장애 격리입니다. 꼬리 질문: "멀티프로세스에서 데이터 공유는?" → IPC(공유메모리 + 세마포어 등).

Q2. fork()의 반환값과 동작을 설명하고, Copy-on-Write가 무엇인지 말해 보세요.

fork는 호출한 프로세스를 복제해 자식을 만들며, 부모에게는 자식의 PID, 자식에게는 0, 실패 시 -1을 반환합니다. 자식은 부모의 메모리, fd, 시그널 설정 등을 복사받습니다. 실제 메모리 복사는 Copy-on-Write로 미뤄져서, 처음엔 같은 물리 페이지를 읽기 전용으로 공유하다가 한쪽이 쓰는 순간 그 페이지만 복사합니다. 그래서 fork 직후 exec하는 패턴이 저렴합니다.

Q3. 좀비 프로세스와 고아 프로세스는 무엇이고, 어떻게 처리하나요?

좀비는 종료했지만 부모가 wait로 종료 상태를 가져가지 않아 프로세스 테이블에 항목이 남은 상태이고, 쌓이면 PID가 고갈됩니다. 부모가 waitpid로 거두거나, SIGCHLD 핸들러에서 WNOHANG 루프로 거두거나, SIGCHLD를 SIG_IGN으로 설정해 해결합니다. 고아는 부모가 먼저 종료한 프로세스로, init(PID 1)이나 subreaper가 입양해 대신 거둡니다. 좀비는 이미 죽었으므로 kill로 제거할 수 없고 부모를 고치거나 부모를 종료해야 합니다.

Q4. 시그널 핸들러에서 printf나 malloc을 호출하면 안 되는 이유는?

시그널은 임의의 지점에서 끼어들기 때문에, 메인 흐름이 malloc이나 printf 내부에서 락을 잡거나 자료구조를 수정하는 도중일 수 있습니다. 핸들러가 같은 함수를 다시 호출하면 교착 상태나 자료구조 손상이 발생합니다. 이런 함수는 재진입 불가능하며, POSIX가 정한 async-signal-safe 함수(write, _exit, waitpid 등)만 호출해야 합니다. 일반적인 패턴은 핸들러에서 volatile sig_atomic_t 플래그만 세우고 실제 처리는 메인 루프에서 하는 것입니다.

Q5. kill -9와 kill -15의 차이는? 서버를 내릴 때 어느 것을 먼저 써야 하나요?

-15(SIGTERM)는 프로세스가 잡아서 정리 작업을 할 수 있는 종료 요청이고, -9(SIGKILL)는 커널이 즉시 강제 종료하며 잡거나 무시할 수 없습니다. 먼저 SIGTERM을 보내 진행 중인 거래 마무리, 커밋, 버퍼 flush, 체크포인트 저장을 하게 하고, 제한 시간 안에 끝나지 않을 때만 SIGKILL을 씁니다. SIGKILL은 정리 없이 죽으므로 임시 파일, 미커밋 트랜잭션, 세마포어(SEM_UNDO가 없으면)가 남을 수 있습니다.

Q6. IPC의 종류와 각각의 장단점을 말해 보세요.

파이프는 단순하지만 친족 간 단방향 바이트 스트림, FIFO는 이름으로 무관한 프로세스도 쓸 수 있는 파이프, 메시지 큐는 메시지 경계와 타입을 보존하지만 용량 한도가 있고, 공유메모리는 복사가 없어 가장 빠르지만 동기화를 직접 해야 하며, 세마포어는 데이터가 아닌 동기화 도구입니다. 소켓은 네트워크를 넘어 통신할 수 있지만 상대적으로 느립니다. 대용량 공유 상태는 공유메모리 + 세마포어, 작업 분배는 메시지 큐, 원격은 소켓이 일반적입니다.

Q7. 세마포어와 뮤텍스의 차이는 무엇인가요?

뮤텍스는 잠금을 획득한 주체만 해제할 수 있는 소유권 기반 상호 배제 도구이고, 세마포어는 소유권이 없는 정수 카운터로 P/V 연산을 통해 N개까지 동시 접근을 허용하거나 이벤트 신호로 쓸 수 있습니다. 이진 세마포어는 뮤텍스처럼 쓸 수 있지만 소유권 검사, 우선순위 상속 같은 뮤텍스 기능이 없습니다. 꼬리 질문: "프로세스가 세마포어를 잡은 채 죽으면?" → System V의 SEM_UNDO로 커널이 복구, 그렇지 않으면 영구 대기 위험.

Q8. 시스템 콜과 일반 함수 호출의 차이를 설명해 보세요.

시스템 콜은 트랩 명령으로 CPU를 커널 모드로 전환해 커널 코드를 실행하고 다시 사용자 모드로 돌아오는 과정이라, 권한 검사와 모드 전환 비용이 듭니다. 일반 함수 호출은 같은 사용자 모드에서 스택 프레임만 만들고 점프합니다. 그래서 fread처럼 버퍼링으로 시스템 콜 횟수를 줄이는 라이브러리가 성능에 중요합니다.

Q9. 파일 디스크립터란 무엇이며, fork 후 부모와 자식이 같은 파일을 읽으면 어떻게 되나요?

fd는 프로세스의 fd 테이블 인덱스로, 커널의 열린 파일 항목을 가리킵니다. fork하면 자식은 fd 테이블을 복사하지만 가리키는 열린 파일 항목은 공유하므로 파일 offset도 공유됩니다. 부모가 100바이트를 읽으면 자식의 다음 읽기는 101번째 바이트부터입니다. 각자 독립적으로 읽으려면 fork 후 각자 open을 다시 해야 합니다.

Q10. volatile 키워드는 무엇이며 멀티스레드 동기화에 충분한가요?

volatile은 컴파일러에게 그 변수를 최적화로 레지스터에 캐시하거나 접근을 생략하지 말고 매번 메모리에서 읽고 쓰라고 지시합니다. 시그널 핸들러와 공유하는 플래그나 메모리 매핑된 하드웨어 레지스터에 씁니다. 하지만 원자성이나 CPU 간 메모리 순서를 보장하지 않으므로 멀티스레드·멀티프로세스 동기화에는 부족하며, C11 _Atomic과 메모리 순서, 또는 뮤텍스·세마포어를 써야 합니다.

정답과 해설 보기

원인 후보: ① 세마포어를 잡은 프로세스가 V 전에 죽었고 SEM_UNDO를 쓰지 않음 ② 세마포어를 잡은 프로세스가 임계 구역 안에서 다른 블로킹 작업(DB 락 대기, 네트워크 I/O)에 걸려 있음 ③ 코드 경로 중 V를 빠뜨린 오류 처리 분기. 확인: ipcs -s -i SEMID로 세마포어 값과 마지막 조작 PID(sempid)를 보고, 그 PID가 살아 있는지 ps로 확인, 살아 있다면 pstack/gdb -p로 어디서 멈췄는지 확인. 응급 조치: 원인 프로세스가 죽었다면 공유 데이터 무결성을 확인한 뒤 semctl SETVAL로 값을 1로 복구하는 운영 도구를 실행(사전에 준비해 둘 것). 근본 해결: SEM_UNDO 사용, 임계 구역에서 블로킹 호출 금지, 모든 경로에서 V 보장(goto unlock 패턴), semtimedop으로 대기 시간 제한 및 경보.

연습문제 26-9 메시지 큐 vs 파이프 난이도 ★★☆

채널 프로세스 1개가 160바이트 전문을 거래 프로세스 여러 개에 분배합니다. 파이프 하나를 여러 거래 프로세스가 함께 읽으면 어떤 문제가 생기고, 메시지 큐는 이를 어떻게 해결합니까?

정답과 해설 보기

파이프는 메시지 경계가 없는 바이트 스트림이라, 여러 읽는 프로세스가 각자 read(fd, buf, 160)을 해도 커널은 160바이트 경계를 보장하지 않습니다. 한 프로세스가 전문 앞 100바이트, 다른 프로세스가 나머지 60바이트와 다음 전문 앞부분을 가져갈 수 있습니다(쓰기는 PIPE_BUF 이하면 원자적이지만 읽기 분배는 보장되지 않음). 메시지 큐는 msgsnd 한 번이 메시지 하나로 보존되고 msgrcv는 메시지 단위로만 꺼내므로, 여러 소비자가 경쟁적으로 꺼내도 전문이 쪼개지지 않습니다. mtype으로 거래 종류별 라우팅도 할 수 있습니다.

연습문제 26-10 종합 — 거래 서버 운영 스크립트 난이도 ★★★

거래 서버 trfsvr는 데몬으로 실행되며 PID 파일 /app/run/trfsvr.pid를 남깁니다. 서버를 안전하게 내리는 셸 함수 stop_trfsvr의 동작을 단계별로 설계하고, C 서버 쪽이 지켜야 할 약속을 쓰세요.

정답과 해설 보기

셸 단계: ① PID 파일 읽기, kill -0 PID로 생존 확인(없으면 PID 파일 정리 후 종료) ② ps -p PID -o comm=이 trfsvr인지 확인(PID 재사용으로 엉뚱한 프로세스를 죽이지 않도록) ③ kill -TERM PID ④ 1초 간격으로 최대 30초 kill -0 확인 ⑤ 여전히 살아 있으면 경고 로그 후 kill -KILL PID ⑥ IPC 자원은 지우지 않음(공유 캐시는 다른 프로세스가 사용 중일 수 있음).
C 서버의 약속: SIGTERM 핸들러는 플래그만 세움 → 메인 루프는 새 요청 수락 중지, 진행 중 거래 완료, 대외기관 응답 대기 중인 거래는 타임아웃 규칙에 따라 정리 → 로그·통계 flush, 세마포어·락 해제, PID 파일 삭제 → exit(0). 자식 프로세스가 있다면 자식들에게도 SIGTERM을 전달하고 모두 거둔 뒤 종료합니다. 30초 안에 끝나지 않을 수 있는 작업은 그 사실을 로그로 남겨야 운영자가 SIGKILL의 영향을 판단할 수 있습니다.
