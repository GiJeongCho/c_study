다차원 배열과 포인터 배열

은행 업무의 데이터는 대부분 표입니다. 지점 × 월, 상품 × 금리 구간, 계좌 × 거래일. C에서는 이런 표를 2차원 배열로 담고, 길이가 제각각인 문자열 목록은 포인터 배열로 담습니다. 둘은 사용법이 비슷해 보이지만 메모리 구조가 완전히 다릅니다. 이 장에서는 그 차이를 그림으로 확실히 잡고, 집계표와 배치 프로그램 인자 처리까지 실무 형태로 만들어 봅니다.

이 장에서 배울 것

  • 2차원 배열이 메모리에 행 우선(row-major)으로 연속 배치되는 원리를 그림으로 설명할 수 있습니다.
  • 2차원·3차원 배열을 선언·초기화하고 행 단위·열 단위로 순회할 수 있습니다.
  • 순회 순서가 성능(캐시)에 주는 영향을 설명할 수 있습니다.
  • 2차원 배열을 함수에 전달할 때 열 크기가 왜 필요한지 압니다.
  • 지점별·월별 거래 집계표를 만들어 행 합계, 열 합계, 총계를 구할 수 있습니다.
  • char *names[]와 char names[][20]의 메모리 차이를 비교할 수 있습니다.
  • 포인터 배열로 문자열을 정렬하고, argc/argv로 배치 프로그램의 인자를 처리할 수 있습니다.

14-1다차원 배열

지금까지 배운 배열은 원소가 한 줄로 늘어선 1차원 배열이었습니다. 한 계좌의 30일치 잔액, 한 지점의 12개월 거래 금액처럼 "한 방향"으로 나열되는 데이터에 적합합니다. 그런데 "5개 지점의 12개월 거래 금액"처럼 두 가지 기준으로 정리해야 하는 데이터는 어떻게 담을까요? 엑셀 표처럼 행(row)과 열(column)이 있는 구조가 필요합니다. 이것이 2차원 배열입니다.

2차원 배열의 선언과 사용

2차원 배열은 대괄호를 두 번 써서 선언합니다. 앞의 숫자가 행의 수, 뒤의 숫자가 열의 수입니다.

원소에 접근할 때는 배열명[행][열]로 씁니다. 인덱스는 1차원 배열과 마찬가지로 0부터 시작하므로 sales[3][4]의 마지막 원소는 sales[2][3]입니다.

왜 그럴까? — sizeof sales[0]은 왜 32일까요?

C에는 사실 "2차원 배열"이라는 별도의 자료형이 없습니다. long long sales[3][4]는 정확히 말하면 "원소가 long long[4](long long 4개짜리 배열)인 배열 3개"입니다. 즉 배열의 배열입니다. 그래서 sales[0]은 첫 번째 행, 곧 long long[4] 타입의 배열 하나이고 크기는 8 × 4 = 32바이트입니다. 전체는 32 × 3 = 96바이트입니다.

이 관점이 이 장 전체의 열쇠입니다. "2차원 배열 = 1차원 배열들을 원소로 가진 1차원 배열"이라는 사실을 기억하면, 메모리 배치, 함수 전달, 배열 포인터가 모두 자연스럽게 이해됩니다.

메모리 배치 — 행 우선(row-major)

메모리는 표가 아니라 한 줄로 이어진 바이트의 나열입니다. 그렇다면 표 모양의 2차원 배열은 메모리에 어떻게 놓일까요? C는 행 우선(row-major) 순서를 씁니다. 0번 행의 원소를 모두 놓고, 이어서 1번 행, 그 다음 2번 행을 놓습니다.

직접 주소를 출력해서 확인해 보겠습니다.

왜 그럴까? — 컴파일러는 a[i][j]를 어떻게 계산할까요?

주소가 4바이트씩 빈틈없이 증가하고, a[0][2](…78) 바로 다음이 a[1][0](…7c)입니다. 행과 행 사이에 틈이 없습니다. 컴파일러는 a[i][j]를 만나면 다음처럼 계산합니다.

  1. a[i]: a는 "int[3] 배열"들의 배열이므로 i번째 행은 시작 주소에서 i × sizeof(int[3]) = i × 12바이트 떨어져 있습니다.
  2. a[i][j]: 그 행 안에서 j번째 int이므로 j × 4바이트를 더 갑니다.
  3. 합치면 시작 + i×12 + j×4 = 시작 + (i×3 + j)×4.

여기서 중요한 사실은 열의 수(3)는 계산에 쓰이지만 행의 수(2)는 쓰이지 않는다는 것입니다. 이것이 나중에 "함수에 2차원 배열을 넘길 때 행 크기는 생략해도 되지만 열 크기는 꼭 써야 한다"는 규칙의 이유가 됩니다.

참고로 flat[4]처럼 2차원 배열을 1차원으로 훑는 기법은 실무에서 흔히 쓰이지만, C 표준을 엄격히 해석하면 &a[0][0]에서 시작한 포인터로 첫 행(원소 3개)의 범위를 넘어 접근하는 것은 미정의 동작으로 볼 여지가 있습니다. 모든 주요 컴파일러에서 기대대로 동작하지만, 이식성이 중요한 코드에서는 처음부터 1차원 배열로 선언하고 i*cols + j로 인덱스를 계산하는 편이 더 깔끔합니다.

여기서 잠깐 — 열 우선(column-major) 언어도 있습니다

포트란(Fortran), MATLAB, R, 그리고 수치 계산 라이브러리(LAPACK)는 열 우선 배치를 씁니다. 0번 열을 위에서 아래로 다 놓고 그 다음 1번 열을 놓습니다. C 프로그램이 이런 라이브러리와 데이터를 주고받을 때 행과 열이 뒤바뀌는 버그가 자주 나므로, 다른 언어와 행렬을 교환할 때는 배치 순서를 꼭 확인해야 합니다.

예제 14-1 난이도 ★★☆

double rate[5][8];에서 rate의 시작 주소가 0x1000이라면 &rate[3][5]는 몇 번지일까요? 또 sizeof rate, sizeof rate[2]는 각각 얼마인가요? (double은 8바이트)

정답과 해설 보기

오프셋 = (3 × 8 + 5) × 8 = 29 × 8 = 232바이트 = 16진수 0xE8. 따라서 0x1000 + 0xE8 = 0x10E8입니다.

sizeof rate = 5 × 8 × 8 = 320바이트, sizeof rate[2] = 한 행 = 8 × 8 = 64바이트입니다. 행 인덱스 3은 "3개 행(3 × 64 = 192바이트)을 건너뛴다", 열 인덱스 5는 "그 행 안에서 5 × 8 = 40바이트를 더 간다"로 생각하면 192 + 40 = 232로 같은 결과가 나옵니다.

2차원 배열의 초기화

2차원 배열은 중괄호를 중첩해서 초기화합니다. 행 하나를 중괄호 하나로 묶는 것이 가장 읽기 좋습니다.

왜 그럴까? — ③과 ④는 왜 결과가 다를까요?

③ { {1}, {4, 5} }는 안쪽 중괄호가 "이 값들은 이 행의 것"이라고 행 경계를 명시합니다. 그래서 0번 행에 1만, 1번 행에 4, 5가 들어가고 나머지가 0입니다. ④ { 1, 2, 3, 4 }는 행 경계 없이 값만 나열했으므로 메모리 순서(행 우선)대로 앞에서부터 채웁니다. 0번 행에 1, 2, 3이 들어가고 넘쳐서 1번 행의 첫 칸에 4가 들어갑니다.

⑤에서 행 수를 생략할 수 있는 이유는 컴파일러가 초기값의 개수를 세서 행 수를 알아낼 수 있기 때문입니다. 하지만 열 수는 생략할 수 없습니다. int e[][] = {...}는 에러입니다. 열 수를 모르면 원소 타입(int[?])의 크기를 결정할 수 없기 때문입니다.

자주 하는 실수 — 쉼표 연산자 함정

다른 언어(파이썬 numpy, 파스칼)에 익숙한 사람이 자주 하는 실수입니다. C에서 [1, 2]는 쉼표 연산자로 계산되어 [2]가 되고, m[2]는 존재하지 않는 2번 행(배열)이므로 대입 자체가 컴파일 에러입니다. 읽기라면(x = m[1, 2][0]) 컴파일이 되면서 범위 밖 접근이 되어 더 위험합니다. 반드시 m[1][2]로 씁니다.

행 단위 순회와 열 단위 순회

2차원 배열의 모든 원소를 방문하는 방법은 두 가지입니다. 바깥 반복을 행으로 하면 행 단위 순회, 바깥 반복을 열로 하면 열 단위 순회입니다. 집계표에서 지점별 합계(행 합계)를 낼 때는 행 단위, 분기별 합계(열 합계)를 낼 때는 열 단위가 자연스럽습니다.

왜 그럴까? — 같은 계산인데 행 단위가 훨씬 빠른 이유

CPU는 메모리에서 값을 하나 읽을 때 그 값만 가져오지 않고 주변 64바이트(캐시 라인)를 통째로 캐시에 올립니다. "방금 읽은 곳 근처를 곧 또 읽을 것"이라는 공간 지역성(spatial locality)을 기대하는 것입니다. 행 단위 순회는 다음에 읽을 값이 바로 옆에 있으므로 이미 캐시에 있습니다(캐시 적중). 열 단위 순회는 한 행 크기만큼 건너뛰므로, 행이 길면(예: 열이 1000개인 int 배열이면 4000바이트) 매번 다른 캐시 라인을 읽어야 해서 캐시 미스가 연달아 납니다.

작은 배열에서는 차이가 보이지 않지만 10000 × 10000 같은 큰 배열에서는 열 단위 순회가 몇 배 느려지는 것이 흔합니다. 그래서 안쪽 반복문이 마지막 인덱스(열)를 돌도록 짜는 것이 C의 기본 원칙입니다. 열 합계가 필요하면 행 단위로 돌면서 열마다 누적 배열에 더하는 방법(아래 집계표 예제)이 더 빠릅니다.

예제 14-2 난이도 ★★☆

3 × 3 정수 배열의 주대각선(m[0][0], m[1][1], m[2][2]) 합과 부대각선(m[0][2], m[1][1], m[2][0]) 합을 구하는 프로그램을 작성하세요. 배열은 { {1,2,3}, {4,5,6}, {7,8,9} }입니다.

정답과 해설 보기

주대각선은 행 = 열, 부대각선은 행 + 열 = n − 1인 원소입니다. 이중 반복 없이 반복 한 번으로 구할 수 있습니다.

1 + 5 + 9 = 15, 3 + 5 + 7 = 15입니다.

3차원 배열

차원은 얼마든지 늘릴 수 있습니다. "2개 연도 × 3개 지점 × 4개 분기"의 거래 건수를 담으려면 3차원 배열을 씁니다. 3차원 배열은 2차원 배열들의 배열입니다. 책장 비유로 말하면, 2차원 배열이 한 페이지의 표라면 3차원 배열은 그 페이지를 여러 장 묶은 책입니다.

2025년: (10+12+9+15) = 46, (7+8+6+11) = 32, (20+18+22+25) = 85, 합계 163. 2026년: 50 + 38 + 91 = 179입니다.

자주 하는 실수 — 차원을 무작정 늘리기

3차원을 넘어가면 사람이 머릿속으로 구조를 그리기 어렵고 인덱스 순서를 헷갈리기 쉽습니다. 또 long long data[100][365][24] 같은 배열은 8 × 876,000 = 7,008,000바이트(약 7MB)로, 지역 변수로 두면 스택 오버플로 위험이 있습니다. 실무에서는 3차원 이상이 필요하면 구조체 배열(17장)이나 동적 할당(16장)으로 설계를 바꾸는 경우가 많습니다.

함수에 2차원 배열 전달하기

1차원 배열을 함수에 넘기면 배열 전체가 복사되지 않고 첫 원소의 주소가 넘어간다는 것을 배웠습니다(int a[] 매개변수는 사실 int *a). 2차원 배열도 같은 규칙을 따릅니다. 다만 "첫 원소"가 int가 아니라 첫 번째 행(int[4])이라는 점이 다릅니다.

왜 그럴까? — 열 크기는 왜 꼭 써야 하나요?

함수 안에서 m[i][j]의 주소를 계산하려면 m + i × (한 행의 바이트 수) + j × 8을 해야 합니다. 한 행의 바이트 수 = 열 수 × 원소 크기입니다. 함수가 받는 것은 시작 주소뿐이므로 열 수를 타입에 적어 주지 않으면 컴파일러가 다음 행이 어디서 시작하는지 알 방법이 없습니다. 반면 행 수는 주소 계산에 쓰이지 않으므로(그림 14-2 참고) 생략해도 되고, 대신 반복 범위를 위해 별도 매개변수로 받습니다.

또 sizeof m이 8인 것은 1차원 배열 때와 같은 이유입니다. 매개변수 m은 배열이 아니라 "long long[4]를 가리키는 포인터"이므로 포인터 크기 8바이트가 나옵니다. 함수 안에서 sizeof로 행 수를 구하려는 시도는 항상 틀립니다.

자주 하는 실수 — 2차원 배열을 int **로 받기

"2차원이니까 포인터도 두 번"이라고 생각하기 쉽지만 완전히 틀렸습니다. a가 변환된 값은 int (*)[3](행을 가리키는 포인터)이고, int **는 "int * 변수를 가리키는 포인터"입니다. m[i]를 계산할 때 int **는 메모리에서 포인터 값(8바이트)을 꺼내 그것을 주소로 씁니다. 그런데 그 자리에는 포인터가 아니라 정수 1과 2가 들어 있으므로, 주소 0x0000000200000001 같은 엉뚱한 곳에 접근해 Segmentation fault가 납니다. 둘의 차이는 15장에서 그림으로 자세히 비교합니다.

이렇게 해결합니다

  • 열 크기가 고정이면 int m[][COLS] 또는 int (*m)[COLS]로 받습니다.
  • 열 크기가 실행 중에 정해지면 C99의 가변 길이 배열(VLA) 매개변수를 쓸 수 있습니다: int sum(int rows, int cols, int m[rows][cols]). 크기 매개변수가 배열 매개변수보다 앞에 와야 합니다. 단, C11부터 VLA는 선택 기능이고 MSVC는 지원하지 않습니다.
  • 이식성이 가장 좋은 방법은 1차원 배열로 받고 m[i * cols + j]로 직접 계산하는 것입니다. 금융권 레거시 코드에서 가장 흔히 보는 형태입니다.

예제 14-3 난이도 ★★☆

다음 중 double rate[4][6];을 인수로 받을 수 있는 올바른 매개변수 선언을 모두 고르세요.

(가) double r[][] (나) double r[][6] (다) double r[4][] (라) double (*r)[6] (마) double **r (바) double *r[6] (사) double r[10][6]

정답과 해설 보기

정답: (나), (라), (사)

  • (가), (다): 열 크기가 없어 원소 타입이 불완전하므로 컴파일 에러입니다.
  • (나), (라): 둘 다 "double 6개짜리 배열을 가리키는 포인터"입니다.
  • (사): 첫 번째 크기 10은 무시되므로 (나)와 같습니다. 문법상 맞지만 오해를 부르므로 권장하지 않습니다.
  • (마): double **는 포인터의 포인터로 타입이 다릅니다(위 주의 박스).
  • (바): double *r[6]은 "double 포인터 6개의 배열"로, 매개변수에서는 double **r와 같습니다. 괄호가 있는 (라)와 의미가 완전히 다릅니다. 선언 해석법은 15장에서 다룹니다.

실무 예제 — 지점별·월별 거래 집계표

이제 배운 것을 모아 실무형 프로그램을 만들어 보겠습니다. 하루 동안 쌓인 거래 내역(지점 번호, 월, 금액)이 있을 때, 이를 지점 × 월 집계표로 만들고 행 합계(지점 합계), 열 합계(월 합계), 총계를 출력합니다. 은행의 일·월 마감 배치가 하는 일이 본질적으로 이것입니다.

왜 그럴까? — 설계 포인트 세 가지

  1. 0으로 초기화: table은 지역 배열이므로 초기화하지 않으면 쓰레기값에 누적됩니다. = { 0 } 한 번으로 12칸이 모두 0이 됩니다.
  2. 범위 검사: 지점 번호가 3이나 -1인 잘못된 내역이 들어오면 table[3][m]은 배열 밖(다른 변수의 메모리)을 덮어씁니다. 컴파일러도 실행 환경도 이것을 막아 주지 않습니다. 외부에서 들어온 데이터로 인덱스를 만들 때는 반드시 검사해야 합니다.
  3. 한 번의 행 단위 순회: 열 합계를 위해 열 단위로 다시 돌지 않고, 행 단위로 한 번 돌면서 col_sum[m]에 누적했습니다. 메모리를 순서대로 한 번만 읽으므로 캐시 효율이 좋습니다.

은행 시스템에서는 — 집계와 대사(검증)

은행의 마감 배치는 거래 원장을 읽어 지점별·과목별·일자별 집계를 만들고, 이를 총계정원장(GL)과 맞춰 봅니다. 이때 핵심은 교차 검증입니다.

  • 행 합계의 합과 열 합계의 합이 총계와 같아야 합니다(위 예제에서 225000 + 155000 + 750000 = 195000 + 70000 + 80000 + 785000 = 1130000).
  • 집계표 총계가 원장 거래 금액의 단순 합계와 같아야 합니다. 범위 검사에서 건너뛴 오류 건이 있으면 차이가 나므로, 오류 건수와 금액을 별도로 집계해 "정상 + 오류 = 전체"를 확인합니다.
  • 금액은 반드시 정수(원 단위 long long)로 다룹니다. double로 누적하면 수백만 건을 더할 때 부동소수점 오차가 쌓여 대사가 1원 단위로 맞지 않습니다.

실제로는 지점 수가 수백~수천 개이고 계정 과목도 수백 개이므로 고정 크기 2차원 배열 대신 동적 할당(16장)이나 해시 테이블을 쓰지만, "키 두 개로 칸을 찾아 누적한다"는 원리는 똑같습니다.

각 행에서 최댓값의 열 인덱스를 찾습니다. 최댓값 변수를 0이 아니라 그 행의 첫 원소로 초기화하는 것이 안전합니다(음수 금액, 예를 들어 취소 거래가 섞일 수 있기 때문). >로 비교하므로 같은 값이면 앞선 월이 유지됩니다.

14-2포인터 배열

포인터 배열(array of pointers)은 이름 그대로 원소가 포인터인 배열입니다. int a[3]이 int 3개를 담듯이, char *p[3]은 char *(문자열 주소) 3개를 담습니다. 포인터 배열이 가장 빛나는 곳은 길이가 서로 다른 문자열 여러 개를 다룰 때입니다. 상품명 목록, 오류 메시지 표, 명령행 인자가 모두 포인터 배열입니다.

포인터 배열의 선언과 구조

왜 그럴까? — *accts[i]는 어떤 순서로 해석될까요?

후위 연산자 []는 단항 연산자 *보다 우선순위가 높습니다. 그래서 *accts[i]는 *(accts[i])로 해석됩니다. 먼저 배열의 i번째 원소(주소)를 꺼내고, 그 주소가 가리키는 long long을 역참조합니다. 선언 long long *accts[3]도 같은 규칙으로 읽습니다. accts는 먼저 [3]과 결합하여 "3개짜리 배열"이 되고, 그 원소가 long long *입니다. 크기는 포인터 3개 × 8바이트 = 24바이트입니다.

char *names[] 와 char names[][20] 비교

여러 개의 문자열을 담는 방법은 두 가지입니다. 겉보기에는 사용법이 거의 같지만, 메모리 구조와 할 수 있는 일이 완전히 다릅니다. 이 차이는 면접에서도 자주 나오는 주제입니다.

왜 그럴까? — 같은 초기값인데 왜 하나는 수정되고 하나는 안 될까요?

char arr[3][10] = { "KB", ... }에서 문자열 리터럴은 배열을 채우는 초기값 목록으로 쓰였습니다. 컴파일러는 'K', 'B', '\0'을 arr의 칸에 복사하고 나머지를 0으로 채웁니다. 그래서 arr의 내용은 내 메모리이고 마음대로 고칠 수 있습니다.

const char *ptr[3] = { "KB", ... }에서는 리터럴이 그 자체로 .rodata에 놓인 배열이고, ptr에는 그 첫 글자의 주소만 저장됩니다. 그 주소로 가서 글자를 바꾸면 읽기 전용 메모리에 쓰는 것이므로 미정의 동작이며 리눅스에서는 대개 Segmentation fault가 납니다. 이 위험을 컴파일 단계에서 막기 위해 const char *로 선언하는 것이 올바른 습관입니다.

자주 하는 실수 — 열 크기 부족으로 널 문자가 빠짐

C에서는 초기값 문자열의 길이가 배열 크기와 정확히 같으면 널 문자를 생략하고 넣는 것이 합법입니다(C++에서는 에러). 그래서 경고 없이 컴파일되고, code[0]에는 널 문자가 없습니다. printf("%s")는 널 문자를 만날 때까지 읽으므로 바로 뒤에 붙어 있는 code[1]까지 이어서 출력합니다. 행 우선 배치 때문에 생기는 전형적인 버그입니다.

이렇게 해결합니다

고정 길이 코드를 담는 2차원 char 배열은 최대 길이 + 1로 열 크기를 잡습니다(char code[2][6]). 금융 전문처럼 의도적으로 널 문자 없는 고정 길이 필드를 다룰 때는 %s 대신 printf("%.5s", code[0])처럼 정밀도로 길이를 제한하거나 memcpy로 다룹니다.

정답과 해설 보기
  • (1) 정상. a의 내용은 수정 가능한 배열입니다.
  • (2) 미정의 동작. p[1]은 리터럴 "LOAN"을 가리키므로 읽기 전용 메모리 수정입니다. p를 char *로 선언해서 컴파일러가 막지 못했습니다.
  • (3) 컴파일 에러. a[1]은 배열이므로 대입의 왼쪽에 올 수 없습니다(assignment to expression with array type).
  • (4) 정상. 포인터에 다른 리터럴의 주소를 대입합니다.
  • (5) 정상. "CARD"는 널 포함 5바이트로 8바이트 행에 들어갑니다.
  • (6) 미정의 동작. p[0]이 가리키는 리터럴 "SAVING"을 덮어쓰려 합니다.

포인터 배열로 문자열 정렬하기

포인터 배열의 가장 큰 장점은 문자열 자체를 옮기지 않고 주소만 바꿔서 순서를 바꿀 수 있다는 것입니다. 고객 이름 1만 개를 정렬할 때 이름(수십 바이트)을 매번 복사하는 대신 포인터(8바이트)만 교환하면 훨씬 빠릅니다. 원본 데이터는 그대로 두고 "보는 순서"만 바꾸는 것이므로 인덱스를 만드는 것과 같은 원리입니다.

왜 그럴까? — strcmp로 비교하는 이유

names[j] < names[min]처럼 쓰면 문자열 내용이 아니라 주소를 비교합니다. 리터럴이 메모리 어디에 놓였는지에 따라 결과가 정해지므로 의미가 없습니다(서로 다른 배열을 가리키는 포인터의 대소 비교는 표준상 미정의 동작이기도 합니다). strcmp는 두 문자열을 한 글자씩 비교해서 첫 번째로 다른 글자의 코드 값 차이에 따라 음수, 0, 양수를 반환합니다. "BOND"와 "CARD"는 첫 글자 'B'(66) < 'C'(67)이므로 음수가 나옵니다.

한글 문자열은 UTF-8 바이트 순서로 비교되므로 대체로 가나다순과 일치하지만, 인코딩이 EUC-KR인 레거시 시스템에서는 순서가 다를 수 있습니다. 금융권에서는 아직 EUC-KR(또는 CP949) 데이터가 많으므로 정렬 기준을 명시해야 합니다.

main 함수의 argc와 argv

지금까지 main은 int main(void)로만 썼습니다. 하지만 main은 운영체제로부터 명령행 인자(command-line arguments)를 받을 수 있습니다. 터미널에서 ./batch 20261028 BR001 --dry-run처럼 실행하면, 프로그램 이름 뒤의 단어들이 main에게 전달됩니다.

  • argc(argument count): 인자의 개수. 프로그램 이름도 하나로 셉니다.
  • argv(argument vector): 각 인자 문자열을 가리키는 포인터 배열. argv[0]은 프로그램 이름, argv[argc]는 반드시 NULL입니다(표준 보장).
gcc -Wall -o args ex14-12.c
./args 20261028 "BR 001" --dry-run

왜 그럴까? — 인자는 왜 전부 문자열일까요?

셸(bash)은 사용자가 입력한 명령줄을 공백 기준으로 잘라 단어 목록을 만들고(따옴표로 묶으면 공백 포함 한 단어), 운영체제의 execve 시스템 호출에 문자열 배열로 넘깁니다. 운영체제는 숫자인지 날짜인지 모르므로 모든 인자는 문자열입니다. "20261028"을 숫자로 쓰려면 프로그램이 직접 변환해야 합니다. 이때 atoi는 변환 실패를 알려 주지 않으므로("abc"도 0), 실무에서는 strtol로 변환하고 오류를 검사합니다.

argv의 문자열은 리터럴이 아니므로 표준상 프로그램이 수정해도 됩니다. 하지만 수정할 일은 거의 없으며, 수정하면 ps 명령에 보이는 프로세스 정보가 바뀌기도 합니다.

실무 예제 — 배치 프로그램 인자 처리

은행의 일마감 배치는 스케줄러(예: 작업 관리 솔루션, cron)가 정해진 시간에 실행합니다. 이때 처리할 영업일자, 대상 지점, 실제 반영 없이 검증만 하는 모의 실행 여부 등을 명령행 인자로 받습니다. 인자 처리는 배치의 첫 관문이므로, 잘못된 인자를 받았을 때 명확한 메시지와 종료 코드로 즉시 실패하는 것이 중요합니다.

./eod 20261028 -b BR001 --dry-run ; echo "종료코드 $?"
./eod 20261328 ; echo "종료코드 $?"
./eod 20261028 -b ; echo "종료코드 $?"

왜 그럴까? — i + 1 >= argc 검사가 왜 필수일까요?

-b가 마지막 인자이면 argv[i + 1]은 argv[argc], 즉 NULL입니다. 검사 없이 branch = argv[++i]를 하면 branch가 NULL이 되고, 나중에 printf("%s", branch)나 strcmp(branch, ...)에서 NULL 역참조로 프로그램이 죽습니다(glibc의 printf는 "(null)"을 찍어 주기도 하지만 표준상 미정의 동작입니다). 포인터 배열의 끝을 넘어 읽지 않도록 인덱스를 늘리기 전에 항상 개수를 확인하는 것이 원칙입니다.

은행 시스템에서는 — 배치 인자와 종료 코드의 약속

  • 종료 코드는 스케줄러와의 계약입니다. 0은 정상, 그 외는 오류로 간주되어 후속 작업(예: 이자 계산 → 원장 반영 → 대외기관 파일 송신)이 멈추고 운영자에게 알람이 갑니다. 오류인데 0을 반환하면 잘못된 데이터로 후속 작업이 진행되는 대형 사고가 됩니다.
  • 오류 메시지는 stderr로, 처리 결과는 stdout이나 로그 파일로 분리합니다. 운영 로그 수집기가 둘을 따로 수집합니다.
  • 영업일자는 시스템 날짜(time())를 쓰지 않고 반드시 인자로 받습니다. 자정을 넘겨 실행되거나 장애로 다음 날 재처리할 때 시스템 날짜를 쓰면 엉뚱한 날을 마감하게 됩니다.
  • --dry-run(모의 실행)은 운영 반영 전 검증용으로 거의 모든 배치가 갖추는 옵션입니다.
  • 옵션이 많아지면 POSIX의 getopt 함수를 사용합니다(윈도우 MSVC에는 기본 제공되지 않음).

예제 14-7 난이도 ★★☆

명령행으로 금액 여러 개를 받아 합계를 출력하는 프로그램 sum을 작성하세요. 숫자가 아닌 인자가 있으면 "잘못된 금액: xxx"를 stderr에 출력하고 종료 코드 1로 끝냅니다. 예: ./sum 15000 230000 4800 → 합계 249800원 (3건)

정답과 해설 보기

end == argv[i]는 숫자를 하나도 읽지 못한 경우(빈 문자열 등), *end != '\0'는 숫자 뒤에 다른 문자가 남은 경우, errno != 0은 범위 초과(ERANGE)를 잡습니다. 이 세 가지 검사가 strtol 계열의 표준 사용 패턴입니다.

핵심 정리

  • C의 2차원 배열은 "배열의 배열"입니다. T a[R][C]의 원소 a[i]는 T[C] 타입의 행입니다.
  • 메모리에는 행 우선(row-major)으로 빈틈없이 연속 배치되며, &a[i][j] = 시작 + (i×C + j)×sizeof(T)입니다. 행 수 R은 주소 계산에 쓰이지 않습니다.
  • 초기화는 행마다 중괄호로 묶는 것이 명확합니다. 행 수는 생략할 수 있지만 열 수는 생략할 수 없습니다. 일부만 초기화하면 나머지는 0입니다.
  • 안쪽 반복이 마지막 인덱스를 돌게 하는 행 단위 순회가 캐시 지역성 덕분에 빠릅니다.
  • 3차원 배열은 2차원 배열의 배열이며, 맨 끝 인덱스가 메모리에서 가장 빨리 변합니다.
  • 2차원 배열을 함수에 넘기면 T (*)[C](행 포인터)로 변환됩니다. 매개변수에 열 크기를 반드시 쓰고, 행 수는 따로 넘깁니다. T **와는 호환되지 않습니다.
  • 집계표는 "키 두 개로 칸을 찾아 누적"하는 구조이며, 0 초기화·인덱스 범위 검사·교차 검증(행 합 = 열 합 = 총계)이 필수입니다.
  • 포인터 배열은 원소가 포인터인 배열입니다. char *p[N]은 길이가 다른 문자열을 낭비 없이 담고, 정렬 시 포인터만 교환합니다.
  • char a[N][M]은 문자열 내용을 배열 안에 복사해 수정 가능, const char *p[N]은 리터럴 주소만 담아 내용 수정 불가·주소 교체 가능입니다.
  • main(int argc, char *argv[])에서 argc는 프로그램 이름을 포함한 인자 수, argv는 문자열 포인터 배열이고 argv[argc]는 NULL입니다.
  • 배치 인자는 strtol 계열로 엄격히 검증하고, 실패 시 stderr 메시지와 0이 아닌 종료 코드로 즉시 끝냅니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. C에서 2차원 배열은 메모리에 어떻게 저장되나요?

행 우선(row-major) 순서로 한 줄로 연속 저장됩니다. 0번 행의 모든 원소 다음에 1번 행이 빈틈없이 이어집니다. 그래서 a[i][j]의 주소는 시작 주소 + (i × 열 수 + j) × 원소 크기로 계산됩니다. 포트란이나 MATLAB은 열 우선이라 다른 언어와 행렬을 주고받을 때 주의해야 합니다.
꼬리 질문 대비: "그래서 순회 순서가 성능에 영향을 주나요?" → 네, 행 단위 순회가 연속 메모리를 읽어 캐시 라인을 효율적으로 쓰므로 큰 배열에서 몇 배 빠를 수 있습니다.

Q2. 2차원 배열을 함수 인자로 넘길 때 열 크기를 생략할 수 없는 이유는?

배열을 넘기면 첫 원소, 즉 첫 행의 주소만 전달됩니다. 함수 안에서 m[i][j]를 계산하려면 i번째 행이 몇 바이트 뒤에 있는지 알아야 하고, 그것이 열 수 × 원소 크기입니다. 행 수는 주소 계산에 필요 없어서 생략 가능하지만 열 수가 없으면 원소 타입 자체가 불완전해 컴파일되지 않습니다.
꼬리 질문 대비: "열 크기가 실행 중에 정해지면?" → C99 VLA 매개변수나 1차원 배열 + 인덱스 직접 계산을 씁니다.

Q3. int a[3][4]를 int **로 받으면 왜 안 되나요?

a는 int (*)[4], 즉 int 4개짜리 행을 가리키는 포인터로 변환됩니다. int **는 int 포인터 변수를 가리키는 포인터라서 m[i]를 할 때 메모리에서 포인터 값을 읽어 다시 주소로 씁니다. 실제 그 자리에는 정수 데이터가 있으므로 엉뚱한 주소를 역참조하게 되어 크래시가 납니다. 메모리 구조가 다른 두 타입입니다.
꼬리 질문 대비: "그럼 int**로 2차원처럼 쓰는 경우는?" → 행마다 malloc하고 포인터 배열로 묶은 동적 2차원 배열(16장)이나 포인터 배열이 그런 구조입니다.

Q4. char *s[]와 char s[][N]의 차이를 설명해 보세요.

char *s[]는 문자열의 주소를 담는 포인터 배열로, 문자열 자체는 배열 밖(리터럴이면 읽기 전용 영역)에 있어 길이 제한과 낭비가 없고 포인터만 바꿔 정렬할 수 있지만 리터럴 내용은 수정할 수 없습니다. char s[][N]은 문자열 내용이 각 행에 복사된 2차원 배열로 수정이 가능하지만 모든 행이 N바이트를 차지해 낭비가 있고, 교환하려면 문자열을 복사해야 합니다. sizeof도 각각 포인터 수 × 8, 행 수 × N으로 다릅니다.

Q5. 포인터 배열(int *p[4])과 배열 포인터(int (*p)[4])의 차이는?

int *p[4]는 int 포인터 4개를 담은 배열로 크기가 32바이트입니다. int (*p)[4]는 int 4개짜리 배열 하나를 가리키는 포인터 변수 하나로 크기가 8바이트이며, p + 1을 하면 16바이트(배열 하나 크기)만큼 이동합니다. 괄호가 있으면 *가 먼저 결합해 "포인터"가 되고, 없으면 []가 먼저 결합해 "배열"이 됩니다.
꼬리 질문 대비: 15장의 선언 해석 규칙(오른쪽-왼쪽 규칙)으로 설명할 수 있어야 합니다.

Q6. argc와 argv는 무엇이며 argv[0]과 argv[argc]에는 무엇이 들어 있나요?

argc는 프로그램 이름을 포함한 명령행 인자 개수, argv는 각 인자 문자열을 가리키는 포인터 배열입니다. argv[0]은 보통 실행할 때 사용한 프로그램 이름(경로)이고, argv[argc]는 표준이 NULL임을 보장합니다. 모든 인자는 문자열이므로 숫자는 strtol 등으로 직접 변환해야 합니다.
꼬리 질문 대비: "argv[0]이 항상 프로그램 이름인가요?" → 관례일 뿐 보장되지 않으며 exec 호출자가 임의로 정할 수 있고 argc가 0일 수도 있습니다.

Q7. 캐시 지역성(locality)이란 무엇인가요?

프로그램이 최근에 접근한 데이터나 그 근처를 곧 다시 접근하는 경향입니다. 같은 데이터를 다시 쓰는 시간 지역성과, 인접한 주소를 쓰는 공간 지역성이 있습니다. CPU는 캐시 라인(보통 64바이트) 단위로 메모리를 가져오므로 배열을 메모리 순서대로 순회하면 캐시 적중률이 높아집니다.
꼬리 질문 대비: "연결 리스트가 배열보다 순회가 느린 이유는?" → 노드가 힙에 흩어져 있어 공간 지역성이 낮기 때문입니다.

Q8. atoi 대신 strtol을 써야 하는 이유는?

atoi는 변환 실패와 실제 0을 구분할 수 없고 범위를 넘으면 미정의 동작입니다. strtol은 변환이 끝난 위치를 endptr로 알려 주어 숫자 뒤 잡문자나 빈 문자열을 검출할 수 있고, 범위 초과 시 errno를 ERANGE로 설정합니다. 외부 입력을 다루는 배치나 전문 처리에서는 반드시 검증 가능한 strtol 계열을 씁니다.

연습문제 14-10 금융 응용 난이도 ★★★

정답과 해설 보기

2차원 배열을 직접 정렬하면 교환할 때마다 40바이트 문자열을 세 번(임시 버퍼 포함) 복사합니다. 정렬은 대략 n log n ≈ 2천만 번의 비교와 그에 비례하는 교환이 일어나므로 수백 MB~GB 단위의 메모리 복사가 생깁니다. 포인터 배열을 정렬하면 교환 시 8바이트만 옮기므로 복사량이 5분의 1 이하로 줄고, 원본 데이터는 그대로 남아 다른 기준(계좌번호순 등)의 인덱스를 여러 개 동시에 만들 수 있습니다. 대신 포인터 배열 8MB가 추가로 필요하고, 비교할 때 포인터를 따라가 흩어진 문자열을 읽으므로 캐시 효율은 다소 떨어집니다. 또 char names[1000000][40]은 40MB이므로 지역 변수로 두면 스택 오버플로가 나며, static이나 힙에 두어야 합니다. 데이터베이스의 인덱스가 바로 이 "원본은 두고 정렬된 포인터(행 위치) 목록을 따로 유지"하는 원리입니다.
