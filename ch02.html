02-1C 프로그램의 구조와 데이터 출력 방법

1장에서 본 첫 프로그램을 이번에는 한 글자도 빠뜨리지 않고 분해합니다. "그냥 외워서 쓰는" 줄이 하나도 없도록, 각 줄이 왜 거기 있는지를 설명합니다.

C 프로그램의 기본 구조

① 전처리 지시자 #include

#include <stdio.h>는 "stdio.h라는 헤더 파일의 내용을 이 자리에 붙여 넣어라"는 전처리기 명령입니다. stdio는 standard input/output의 약자이고, .h는 header의 머리글자입니다. 이 파일 안에는 printf, scanf, puts 같은 입출력 함수의 선언(원형)이 들어 있습니다. 함수의 실제 기계어는 라이브러리에 있고, 헤더에는 "이런 이름과 모양의 함수가 있다"는 정보만 있다는 점이 중요합니다.

< >로 감싸면 컴파일러가 정해 둔 시스템 헤더 디렉터리에서 찾고, " "로 감싸면(#include "interest.h") 현재 소스 파일이 있는 디렉터리부터 찾은 뒤 시스템 디렉터리를 찾습니다. 직접 만든 헤더는 큰따옴표를 씁니다.

왜 그럴까? — 전처리 지시자 끝에는 왜 세미콜론이 없을까?

세미콜론은 C 문장의 끝을 알리는 기호이고, 이를 해석하는 것은 컴파일러입니다. 그런데 #include는 컴파일러가 아니라 그보다 먼저 동작하는 전처리기가 처리하며, 전처리기는 줄 단위로 일합니다. 지시자는 줄바꿈으로 끝나므로 세미콜론이 필요 없습니다. 만약 #define RATE 3;처럼 세미콜론을 붙이면 전처리기는 RATE를 3;으로 그대로 치환해 버려, x = RATE * 2;가 x = 3; * 2;가 되어 엉뚱한 오류가 납니다(19장).

② 함수 머리 int main(void)

C 프로그램은 함수(function)들의 모임입니다. 함수는 특정 작업을 하는 코드 묶음이고, 그중 main은 프로그램이 시작될 때 가장 먼저 호출되는 특별한 함수입니다. 프로그램에 main은 정확히 하나 있어야 합니다(없으면 링크 오류 undefined reference to main).

  • int: 반환형. 함수가 끝날 때 정수 하나를 돌려준다는 뜻입니다.
  • main: 함수 이름.
  • (void): 매개변수 목록. void는 "받는 값이 없다"는 뜻입니다. C에서 int main()처럼 괄호를 비우면 C17까지는 "매개변수 정보를 지정하지 않음"이라는 다른 의미가 되므로(C23에서는 (void)와 같아짐), 받는 값이 없으면 void를 명시하는 것이 정석입니다.

③⑦ 함수 몸체와 블록

중괄호 { }로 감싼 부분을 블록(block) 또는 복합문이라고 합니다. 함수 몸체는 하나의 블록이며 그 안에 실행할 문장을 순서대로 씁니다. 블록 안의 문장은 위에서 아래로 차례대로 실행됩니다(순차 구조).

④⑤ 문장과 세미콜론

문장(statement)은 실행의 최소 단위이며, 대부분 세미콜론 ;으로 끝납니다. 한국어 문장의 마침표와 같습니다. 줄바꿈은 아무 의미가 없으므로 한 줄에 여러 문장을 써도 되고, 한 문장을 여러 줄에 걸쳐 써도 됩니다. 하지만 읽기 좋게 한 줄에 한 문장, 블록 안은 4칸 들여쓰기를 권장합니다.

⑥ return 0;

main을 끝내고 운영체제에 종료 코드 0(정상)을 돌려줍니다(1장 그림 1-7).

자주 하는 실수 — 대소문자와 전각 문자

  • C는 대소문자를 구별합니다. Printf, MAIN, Return은 모두 다른 이름이며 오류가 납니다.
  • 한글 입력 상태에서 친 전각 괄호 （ ）, 전각 세미콜론 ；, 전각 공백은 눈으로는 비슷하지만 다른 문자입니다. gcc는 stray '\357' in program 같은 알 수 없는 오류를 냅니다. 큰따옴표 안(문자열)이 아닌 곳에서는 반드시 영문 반각 기호를 쓰십시오.
  • 워드프로세서나 메신저에서 복사한 코드의 따옴표가 “ ”(둥근 따옴표)로 바뀌어 있으면 역시 오류가 납니다.

printf 함수의 원리

printf는 print formatted, 즉 "서식에 맞춰 출력한다"는 뜻입니다. 첫 번째 인수로 서식 문자열(format string)을 받고, 그 안의 %로 시작하는 변환 지정자(conversion specification) 자리에 뒤따르는 인수들을 순서대로 끼워 넣어 출력합니다.

왜 그럴까? — printf는 인수가 몇 개인지 어떻게 알까?

printf는 인수의 개수가 정해지지 않은 가변 인자 함수입니다. 그런데 C의 함수 호출에는 "인수가 몇 개이고 각각 무슨 자료형인지"라는 정보가 함께 전달되지 않습니다. 호출하는 쪽은 그냥 값들을 레지스터와 스택에 올려 둘 뿐입니다. 그래서 printf는 오직 서식 문자열만 보고 "%d가 있으니 다음 자리에서 int 하나를 꺼내자", "%s니까 주소 하나를 꺼내 그 주소부터 0바이트까지 글자를 출력하자"라고 판단합니다.

이것이 바로 서식 지정자와 인수의 자료형·개수가 반드시 일치해야 하는 이유입니다. %d를 두 개 쓰고 인수를 하나만 주면 printf는 있지도 않은 두 번째 인수 자리의 쓰레기 값을 읽습니다. %s에 정수를 주면 그 정수를 주소로 착각해 엉뚱한 메모리를 읽다가 프로그램이 죽습니다. 표준은 이를 모두 미정의 동작으로 규정합니다. 다행히 gcc는 서식 문자열이 상수일 때 -Wall(정확히는 -Wformat)로 이 불일치를 검사해 줍니다.

자주 하는 실수 — 사용자 입력을 서식 문자열로 쓰기

printf(name);처럼 외부에서 들어온 문자열을 서식 문자열 자리에 그대로 넣으면, 그 문자열에 %s, %n 같은 것이 들어 있을 때 printf가 이를 변환 지정자로 해석해 메모리를 읽거나 쓰게 됩니다. 이것이 유명한 서식 문자열 취약점(format string vulnerability)이며 금융보안 시큐어 코딩 점검 항목입니다. 항상 printf("%s", name);처럼 서식 문자열은 상수로 쓰십시오.

printf의 반환값과 출력 버퍼

printf는 실제로 출력한 바이트 수를 반환하고, 오류가 나면 음수를 반환합니다. 예를 들어 printf("abc\n")은 4를 반환합니다. 한글은 인코딩에 따라 한 글자가 UTF-8에서 3바이트, EUC-KR(CP949)에서 2바이트이므로 반환값도 달라집니다.

printf가 출력한 글자는 곧바로 화면으로 가지 않고 먼저 출력 버퍼(stdout buffer)라는 메모리 공간에 모였다가 한꺼번에 운영체제에 전달됩니다. 운영체제에 출력을 요청하는 시스템 호출은 비용이 크기 때문에, 글자 하나마다 부르지 않고 모아서 보내는 것입니다.

왜 그럴까? — 프로그램이 죽기 직전에 찍은 로그가 안 보이는 이유

stdout이 터미널에 연결되어 있으면 보통 줄 버퍼링(\n을 만나면 비움)이고, 파일이나 파이프로 리다이렉트되면 완전 버퍼링(버퍼가 가득 차야 비움, 보통 4KB 이상)으로 바뀝니다. 배치 프로그램은 대부분 출력을 로그 파일로 리다이렉트해 실행하므로 완전 버퍼링 상태입니다. 이때 프로그램이 Segmentation fault로 비정상 종료하면 버퍼에 남아 있던 내용은 영영 파일에 쓰이지 않습니다. 그래서 "죽기 직전까지 진행 로그를 찍었는데 로그에는 훨씬 앞부분까지만 남아 있다"는 일이 생깁니다.

이렇게 해결합니다

중요한 진행 로그 뒤에는 fflush(stdout);를 호출해 버퍼를 즉시 비우거나, 오류 메시지는 버퍼링되지 않는 표준 오류 stderr로 출력합니다: fprintf(stderr, "오류: 계좌 없음\n");. 참고로 fflush는 출력 스트림에만 정의되어 있으며, fflush(stdin)은 표준상 미정의 동작입니다(3장에서 다시 다룹니다).

이스케이프 시퀀스

왜 그럴까? — 마지막 줄이 왜 "처리완료!50%"로 보일까?

\r(캐리지 리턴)은 커서를 현재 줄의 맨 앞으로만 옮기고 줄을 바꾸지 않습니다. 그래서 먼저 출력된 처리중...50% 위에 처리완료!가 덮어쓰입니다. 화면 기준으로 "처리중..."은 한글 3글자(터미널에서 6칸)와 점 3개로 9칸, "처리완료!"는 한글 4글자(8칸)와 느낌표로 9칸이므로 앞 9칸이 정확히 덮이고 뒤의 "50%"가 남습니다. 이 기법은 진행률 표시(프로그레스 바)를 같은 줄에서 갱신할 때 씁니다. 단, 출력이 파일로 리다이렉트되면 덮어쓰기가 아니라 \r 문자 자체(0x0D)가 파일에 그대로 기록된다는 점에 주의하십시오.

은행 시스템에서는 — 줄 끝 문자 하나로 파일 송신이 실패한다

은행은 매일 대외기관과 파일을 주고받습니다(예: 자동이체 의뢰 파일, 지로 수납 파일). 이런 파일은 "레코드 길이 300바이트 고정, 레코드 끝은 LF" 같은 규격이 정해져 있습니다. 윈도우에서 만든 파일은 줄 끝이 \r\n(2바이트)이므로 레코드가 301바이트가 되어 상대 기관 시스템이 "레코드 길이 오류"로 파일 전체를 반려할 수 있습니다. 반대로 유닉스에서 만든 파일을 윈도우 메모장으로 열면 줄바꿈이 안 보이던 시절도 있었습니다. 그래서 파일 송수신 프로그램은 바이트 단위로 길이를 검증하고, 개발자는 od -c 파일명이나 16진 편집기로 \r(0D)과 \n(0A)을 직접 확인하는 습관을 들입니다.

주석

주석(comment)은 사람을 위한 메모로, 전처리 단계에서 공백으로 바뀌어 실행에 영향을 주지 않습니다.

  • /* ... */: 블록 주석. 여러 줄에 걸쳐 쓸 수 있습니다. C89부터 있던 방식입니다.
  • // ...: 한 줄 주석. 그 줄 끝까지가 주석입니다. C99부터 표준입니다.

자주 하는 실수 — 블록 주석은 중첩되지 않는다

블록 주석은 처음 만나는 */에서 끝납니다. 그래서 /* 테스트 출력 */의 */에서 주석이 끝나 버리고, printf("B");와 마지막 */가 코드로 남아 컴파일 오류가 납니다.

#if 0 ~ #endif는 안에 주석이 있어도 안전하게 코드를 제외합니다. 다만 운영 소스에 이런 '죽은 코드'를 오래 남겨 두는 것은 좋지 않으며, 변경 이력은 형상관리 도구(Git, SVN)로 관리하는 것이 원칙입니다.

여기서 잠깐 — 좋은 주석이란?

좋은 주석은 코드가 무엇을 하는지보다 왜 그렇게 하는지를 설명합니다. i++; // i를 1 증가는 쓸모없는 주석이고, fee = fee / 10 * 10; // 수수료는 10원 미만 절사 (수수료 규정 제5조)는 좋은 주석입니다. 금융권 소스에는 관련 규정, 요구사항 번호, 변경 요청(CSR) 번호를 주석으로 남겨 감사 추적에 활용하는 경우가 많습니다.

puts와 putchar

단순히 문자열 하나를 출력하고 줄을 바꿀 때는 puts, 문자 하나를 출력할 때는 putchar를 쓸 수 있습니다. 서식 해석을 하지 않으므로 조금 더 빠르고, %를 그대로 출력합니다.

02-2상수와 데이터 표현 방법

프로그램 안에 값을 직접 적어 넣은 것을 상수(constant) 또는 리터럴(literal)이라고 합니다. 15000, 3.14, 'A', "계좌"가 모두 상수입니다. 상수에도 자료형이 있고, 자료형에 따라 메모리에 저장되는 모양과 printf에서 써야 할 변환 문자가 달라집니다. 이 절의 핵심은 "상수의 자료형 ↔ 변환 문자"의 짝을 정확히 맞추는 것입니다.

정수 상수와 진법

정수 상수는 세 가지 진법으로 쓸 수 있습니다. 어떤 진법으로 쓰든 메모리에는 똑같은 2진수로 저장됩니다. 진법은 사람이 적는 '표기법'일 뿐입니다.

진법표기 규칙예 (모두 같은 값 255)
10진수0이 아닌 숫자로 시작255
8진수0으로 시작, 0~7만 사용0377
16진수0x 또는 0X로 시작, 0~9와 a~f(A~F)0xFF, 0xff
2진수0b로 시작 (C23 표준, 그 전에는 gcc 확장)0b11111111

왜 그럴까? — 프로그래머는 왜 16진수를 좋아할까?

컴퓨터의 기본 단위인 1바이트는 8비트이고, 16진수 한 자리는 정확히 4비트입니다. 그래서 1바이트는 언제나 16진수 두 자리(00~FF)로 딱 떨어지게 표현됩니다. 10진수로는 비트 패턴이 보이지 않지만, 16진수 0x41을 보면 곧바로 0100 0001을 떠올릴 수 있습니다. 메모리 덤프, 전문의 바이트 분석, 문자 인코딩(한글 '가'는 UTF-8로 EA B0 80) 확인 등에 16진수가 쓰이는 이유입니다. 8진수는 3비트 단위라 UNIX 파일 권한(chmod 755) 정도에서 주로 쓰입니다.

자주 하는 실수 — 앞에 0을 붙인 숫자

지점 코드나 월(月)을 int month = 08;처럼 쓰면 컴파일 오류(invalid digit "8" in octal constant)가 납니다. 0으로 시작하는 정수는 8진수이고 8진수에는 8, 9가 없기 때문입니다. 더 위험한 것은 int branch = 0123;처럼 오류 없이 8진수로 해석되어 값이 83이 되는 경우입니다. 지점 코드, 계좌번호처럼 앞자리 0이 의미 있는 값은 숫자가 아니라 문자열로 다뤄야 합니다.

정수 상수는 기본적으로 int형입니다. 값이 int 범위를 넘으면 컴파일러가 자동으로 더 큰 형(long, long long)을 고릅니다. 직접 지정하려면 접미사를 붙입니다.

예제 2-4 난이도 ★★☆

정답과 해설 보기

010은 8진수이므로 1×8 = 8, 0x10은 16진수이므로 1×16 = 16, 10은 10진수 10이고, 마지막 10을 %x로 출력하면 16진수 소문자 a입니다. 상수를 어떤 진법으로 쓰는지(입력 표기)와 printf로 어떤 진법으로 보여 주는지(출력 형식)는 완전히 독립적이라는 점이 핵심입니다.

실수 상수

소수점이 있거나 지수 표기를 쓴 상수는 실수(부동소수점) 상수이며 기본 자료형은 double입니다.

  • 소수점 표기: 3.14, 0.5, .5(=0.5), 5.(=5.0)
  • 지수 표기: 1.5e3 = 1.5 × 103 = 1500.0, 2.5E-4 = 0.00025
  • 접미사: 3.14f는 float, 3.14L은 long double

%f소수점 형태, 기본 소수 6자리1234.567800
%e지수 형태, 가수 소수 6자리1.234568e+03
%E지수 형태(대문자 E)1.234568E+03

여기서 잠깐 — float도 %f, double도 %f인 이유

가변 인자 함수에 float 값을 넘기면 C 언어 규칙(기본 인수 승격, default argument promotion)에 따라 자동으로 double로 변환되어 전달됩니다. 그래서 printf 입장에서는 항상 double만 받으므로 %f 하나로 둘 다 출력합니다(C99부터는 %lf도 printf에서 %f와 같은 의미로 허용). 같은 이유로 char, short는 int로 승격되어 전달됩니다. 그러나 3장의 scanf는 값이 아니라 주소를 받으므로 승격이 일어나지 않고, float는 %f, double은 반드시 %lf로 구분해야 합니다. 면접에서 자주 묻는 함정입니다.

왜 그럴까? — printf("%.2f", 2.675)는 왜 2.68이 아니라 2.67일까?

double은 숫자를 2진 소수로 저장합니다. 10진수 0.1이 2진수로는 0.0001100110011…처럼 끝없이 반복되듯, 2.675도 2진수로 정확히 표현할 수 없어서 가장 가까운 값인 2.67499999999999982236431605997495353221893310546875가 저장됩니다. printf는 이 실제로 저장된 값을 반올림하므로 2.67이 됩니다. 0.25는 2진수로 정확히 표현되는 값(1/4)이라 정확히 중간인데, glibc는 이때 짝수 쪽으로 반올림(round half to even)해 0.2를 냅니다. 0.35는 실제로 0.34999999999999997779…로 저장되어 0.3이 됩니다.

결론: printf의 반올림은 금액 계산에 쓸 수 없습니다. 화면 표시용일 뿐이며, 금액은 정수(원 단위)로 계산하고 반올림·절사 규칙을 코드로 명시해야 합니다(21장).

은행 시스템에서는 — 금액은 왜 정수로 출력하는가

원화는 소수점 이하 단위가 없으므로 계정계 원장의 금액 필드는 대부분 정수(예: long long 또는 DB의 NUMBER(15))로 저장합니다. 달러처럼 센트가 있는 외화는 "센트 단위 정수"로 저장하고, 출력할 때만 printf("%lld.%02lld", cents / 100, cents % 100)처럼 정수 연산으로 소수점을 만들어 냅니다. 예를 들어 123456센트는 1234.56으로 출력됩니다. 이렇게 하면 double의 표현 오차가 원장에 끼어들 틈이 없습니다. 이자율처럼 소수가 꼭 필요한 값도 내부적으로는 정수 배율(bp, 만분율)로 보관하는 경우가 많습니다.

문자 상수와 문자열 상수

문자 상수는 작은따옴표로 감싼 문자 하나입니다: 'A', '7', '\n'. 컴퓨터는 문자를 그대로 저장할 수 없으므로 문자 코드표(ASCII)의 번호로 저장합니다. 'A'는 65, 'a'는 97, '0'은 48입니다. 즉 C에서 문자 상수는 사실 정수이며, 자료형도 int입니다(C++에서는 char라는 점이 다릅니다).

문자열 상수는 큰따옴표로 감싼 글자들입니다: "A", "계좌". 문자열은 메모리에 글자들의 코드가 연속으로 저장되고, 맨 끝에 널 문자 '\0'(값 0)이 자동으로 붙습니다. 그래서 "A"는 2바이트입니다.

왜 그럴까? — '7' - '0'이 왜 7일까?

ASCII 코드에서 숫자 문자 '0'~'9'는 48~57로 연속해서 배치되어 있습니다(C 표준도 숫자 문자의 연속성은 보장합니다). 그래서 '7'(55) - '0'(48) = 7입니다. 전문에서 "0001500" 같은 숫자 문자열을 정수로 바꿀 때 이 원리를 씁니다. 반면 알파벳의 연속성은 표준이 보장하지 않습니다(EBCDIC 같은 문자 집합에서는 연속이 아닙니다). 메인프레임 시절 금융 데이터는 EBCDIC 인코딩이었기 때문에, 레거시 연동에서 이런 차이가 실제로 문제가 됩니다.

자주 하는 실수 — 작은따옴표와 큰따옴표 혼동

  • printf("%s", 'A');: %s는 문자열의 주소를 기대하는데 정수 65를 주었으므로 65번지를 읽으려다 프로그램이 죽습니다(UB). gcc -Wall이 경고합니다.
  • printf("%c", "A");: 문자열의 주소값 일부를 문자로 출력해 이상한 글자가 나옵니다.
  • 'AB': 다중 문자 상수로, 값이 구현 정의입니다. gcc는 multi-character character constant 경고를 냅니다. 쓰지 마십시오.
  • '가': 한글은 UTF-8에서 3바이트이므로 문자 상수 하나에 담을 수 없습니다. 한글은 항상 문자열로 다룹니다.

예제 2-5 난이도 ★★☆

정답과 해설 보기

printf의 폭과 정밀도는 글자 수가 아니라 바이트 수로 계산됩니다. UTF-8에서 "거래일"은 3글자 × 3바이트 = 9바이트이므로 %-10s는 공백을 1개만 붙입니다. 그런데 터미널에서 한글 한 글자는 보통 2칸 너비로 그려지므로, 화면상 6칸 + 공백 1칸 = 7칸만 차지해 영문 행(10칸)과 어긋납니다. "합계"(6바이트)도 공백 4개만 붙어 8칸이 됩니다. EUC-KR(CP949) 환경이라면 한글이 2바이트 = 2칸이라 우연히 맞아떨어집니다. 이 차이가 레거시 금융 시스템에서 EUC-KR을 오래 써 온 이유 중 하나이기도 합니다.

정렬이 중요한 보고서나 전문에서는 (1) 한글 필드를 별도로 다루거나, (2) 전문 규격처럼 바이트 기준으로 길이를 정의하고 그에 맞게 패딩하며, (3) 화면 표시용이라면 와이드 문자 함수(wchar_t, wcwidth)로 표시 폭을 계산합니다. 금융 전문은 거의 항상 "필드 길이 = 바이트 수"로 정의되므로 (2)가 표준적인 방법입니다.

예제 2-6 난이도 ★★☆

다음 출력 결과를 정확히 쓰십시오(공백 개수 주의, [ ]는 그대로 출력됩니다).

printf("[%5d][%-5d][%05d]\n", 42, 42, 42);
printf("[%8.3f][%-8.1f][%.0f]\n", 3.14159, 2.75, 2.5);
printf("[%3d][%.2s][%5.1s]\n", 123456, "KOREA", "BANK");
정답과 해설 보기
  • %8.3f: 3.14159 → 3.142(5자) 앞에 공백 3개.
  • %-8.1f: 2.75는 2진수로 정확히 표현되는 값(2 + 1/2 + 1/4)이라 소수 첫째 자리에서 정확히 중간입니다. 짝수 쪽 반올림 규칙에 따라 2.8(8이 짝수)이 됩니다. 뒤에 공백 5개.
  • %.0f: 2.5도 정확히 중간이므로 짝수 쪽인 2가 됩니다(glibc, 최신 MSVC 공통). "무조건 올림"이라고 생각하면 틀립니다.
  • %3d: 폭보다 값이 길면 잘리지 않고 전부 출력됩니다.
  • %5.1s: 최대 1글자 "B"를 폭 5에 오른쪽 정렬.

실무 예 1: 금액을 천 단위로 구분해 출력하기

잔액 조회 화면이나 거래 명세서에는 1,234,567,890원처럼 천 단위 쉼표가 들어가야 읽기 쉽습니다. 아쉽게도 표준 C의 printf에는 천 단위 구분 기능이 없습니다. 여기서는 지금까지 배운 것만으로 만들 수 있는 방법과 그 한계를 봅니다.

방법 1: 나눗셈과 나머지로 자릿수 묶음을 분리

정수 나눗셈 /는 몫만 남기고, %는 나머지를 구합니다(4장에서 자세히). 1,234,567,890을 1000으로 나눈 나머지는 890, 1000으로 나눈 몫을 다시 1000으로 나눈 나머지는 567입니다. 각 묶음을 %03lld로 출력하면 앞자리 0이 채워집니다.

왜 그럴까? — %03lld가 꼭 필요한 이유

두 번째 금액 2,005,003,001에서 백만 단위 묶음은 2005003001 / 1000000 % 1000 = 2005 % 1000 = 5입니다. 이를 %lld로 출력하면 2,5,3,1이라는 완전히 다른 금액이 됩니다. %03lld는 최소 3칸을 확보하고 빈칸을 0으로 채우므로 005가 됩니다. 반대로 맨 앞 묶음은 0으로 채우면 안 되므로 %lld를 씁니다. 이처럼 출력 형식 하나의 실수가 금액을 바꿔 보이게 할 수 있습니다.

이 방법의 한계

위 코드는 10억 이상의 금액에서만 올바릅니다. 15000원을 넣으면 0,000,015,000원이 출력됩니다. 또 음수(출금, 환불)는 각 묶음의 나머지가 음수가 되어 -1,-234,...처럼 깨집니다(C99부터 음수의 % 결과는 왼쪽 피연산자의 부호를 따릅니다). 자릿수에 따라 다르게 처리하려면 조건문(5장)과 반복문(6장)이 필요하며, 어떤 금액이든 처리하는 범용 함수는 12장 문자열에서 완성합니다.

방법 2: POSIX의 ' 플래그 (비표준)

리눅스(glibc)와 유닉스는 POSIX 확장으로 작은따옴표 플래그 %'lld를 지원합니다. 로케일(지역 설정)에 맞는 천 단위 구분자를 넣어 줍니다. 표준 C가 아니므로 Visual Studio에서는 동작하지 않고, -pedantic에서 경고가 납니다.

로케일이 기본값 "C"이면 구분자가 없어 1234567890원이 출력됩니다. 운영 서버의 환경 변수에 따라 출력이 바뀌는 셈이므로, 금융권 운영 프로그램에서는 이런 환경 의존 기능보다 직접 만든 포맷 함수를 선호합니다.

실무 예 2: 고정길이 전문 필드 만들기

금융 기관 사이의 통신 메시지를 전문(電文)이라고 합니다. 많은 전문이 고정길이(fixed-length) 형식이며, 각 필드의 시작 위치와 길이(바이트)가 규격서에 정해져 있습니다. 대표적인 규칙은 다음과 같습니다.

  • 숫자형(N) 필드: 오른쪽 정렬, 남는 앞자리는 0으로 채움. 예) 길이 13의 금액 1,500,000 → 0000001500000
  • 문자형(AN) 필드: 왼쪽 정렬, 남는 뒷자리는 공백으로 채움. 예) 길이 14의 계좌번호 → 11012345678␣␣␣

printf 계열 함수의 %0Nd와 %-Ns가 정확히 이 규칙에 들어맞습니다. 실무에서는 화면 출력 대신 sprintf/snprintf(12장)로 메모리 버퍼에 써서 송신합니다.

첫째 줄은 규격대로 31바이트입니다. 그런데 둘째 줄은 셋째 줄보다 2바이트가 깁니다. 언뜻 보면 둘 다 그럴듯해 보이기 때문에 더 위험합니다.

왜 그럴까? — 폭은 '최소'일 뿐, 최대가 아니다

%-14s의 14는 최소 폭입니다. 문자열이 16바이트면 자르지 않고 16바이트를 다 출력합니다. 그래서 둘째 줄 전문은 31바이트가 아니라 33바이트가 되고, 수신 측은 규격대로 19번째 바이트부터 13바이트를 금액으로 읽으므로 계좌번호 끝 두 자리 "23"이 섞인 2300000000700, 즉 23억 원이 넘는 엉뚱한 금액을 읽게 됩니다.

셋째 줄의 %-14.14s는 정밀도 14로 최대 14바이트까지만 출력하므로 길이가 정확히 유지됩니다. 하지만 이 경우 계좌번호가 잘린 것이므로 정상 처리가 아닙니다. 올바른 처리는 출력 전에 길이를 검증해 오류로 거절하는 것입니다(입력 검증, 22장).

넷째 줄처럼 %013lld에 음수를 주면 부호가 한 자리를 차지합니다. 많은 전문 규격은 금액 필드에 부호를 넣지 않고 별도의 부호 필드(+/-)나 거래 구분 코드로 입출금을 표시하므로, 금액은 절댓값으로 넣어야 합니다.

은행 시스템에서는 — 전문 1바이트 밀림 장애

대외계 장애 유형 중 고전적인 것이 '필드 밀림'입니다. 고객명 필드(예: 20바이트)에 UTF-8 한글 7글자(21바이트)가 들어오거나, 폭만 지정하고 정밀도를 지정하지 않아 긴 값이 그대로 들어가면 뒤쪽 필드 전체가 1바이트 이상 밀립니다. 수신 기관은 금액, 수수료, 응답코드를 모두 잘못 읽게 되고, 최악의 경우 응답코드 위치에 엉뚱한 숫자가 들어가 "정상 처리"로 오인될 수도 있습니다. 그래서 전문 조립 코드는 (1) 필드마다 바이트 길이를 검증하고, (2) %-N.Ns처럼 폭과 정밀도를 함께 지정하며, (3) 조립된 전문의 총 길이를 송신 직전에 다시 확인하는 3중 방어를 둡니다. 한글 필드는 EUC-KR로 변환한 뒤 바이트 수를 세고, 한글 한 글자의 중간(2바이트 중 1바이트)에서 잘리지 않도록 처리하는 것도 실무에서 꼭 챙기는 부분입니다.

예제 2-7 난이도 ★★★

다음 규격에 맞게 전문 한 줄을 출력하는 printf 문장을 작성하십시오. 거래코드 "0300"(4바이트), 지점코드 "0123"(문자, 4바이트), 고객명 "HONG GILDONG"(문자, 10바이트, 초과분 절단), 금액 25000(숫자, 12바이트). 끝에 줄바꿈 하나를 붙이고 전체 길이를 쓰십시오.

정답과 해설 보기

지점코드 "0123"은 정수 상수 0123으로 쓰면 8진수 83이 되므로 반드시 문자열로 다룹니다. 고객명은 12바이트이므로 %-10.10s로 10바이트 "HONG GILDO"만 출력됩니다(실무에서는 절단 대신 오류 처리 여부를 규격에 따라 결정). 금액은 %012lld로 000000025000. 전체 길이는 4 + 4 + 10 + 12 = 30바이트이고 줄바꿈을 포함하면 31바이트입니다.

핵심 정리

  • C 프로그램은 전처리 지시자(#include)와 함수들로 이루어지며, 실행은 main에서 시작합니다. 문장은 ;로 끝나고 블록은 { }로 묶습니다.
  • 전처리 지시자는 줄 단위로 처리되며 세미콜론을 붙이지 않습니다. < >는 시스템 헤더, " "는 사용자 헤더에 씁니다.
  • printf는 서식 문자열만 보고 인수를 해석하므로 변환 문자와 인수의 자료형·개수가 반드시 일치해야 합니다. 불일치는 UB입니다. 외부 문자열을 서식 문자열로 쓰지 않습니다.
  • 출력은 stdout 버퍼를 거칩니다. 리다이렉트 시 완전 버퍼링되므로 중요한 로그는 fflush(stdout) 또는 stderr를 씁니다.
  • 이스케이프 시퀀스: \n \t \r \\ \" \' \0 \xhh. % 자체는 %%로 출력합니다.
  • 블록 주석은 중첩되지 않습니다. 코드 블록을 막을 때는 #if 0 ... #endif.
  • 정수 상수: 10진, 8진(0으로 시작), 16진(0x). 접미사 U, L, LL. 앞에 0이 붙은 코드값은 문자열로 다룹니다.
  • 실수 상수는 기본 double. %f %e %g. 2진 표현 오차 때문에 printf 반올림은 금액 계산에 쓰지 않습니다.
  • 문자 상수 'A'는 정수(65)이고 C에서 자료형은 int입니다. 문자열 "A"는 끝에 '\0'이 붙은 2바이트 배열입니다.
  • %[플래그][폭][.정밀도][길이]변환. 폭은 최소값이며, 문자열 정밀도는 최대 바이트 수입니다. 폭과 정밀도는 바이트 단위입니다.
  • size_t는 %zu, long long은 %lld로 출력합니다.
  • 전문 숫자 필드는 %0Nlld, 문자 필드는 %-N.Ns로 만들고 길이를 반드시 검증합니다.

Q1. #include <stdio.h>와 #include "stdio.h"의 차이는 무엇인가요?

둘 다 전처리기가 해당 파일 내용을 그 자리에 복사해 넣는 것은 같지만 검색 경로가 다릅니다. 꺾쇠는 컴파일러가 정한 시스템 헤더 디렉터리에서 찾고, 큰따옴표는 현재 소스 파일의 디렉터리를 먼저 찾은 뒤 시스템 디렉터리를 찾습니다(정확한 순서는 구현 정의). 그래서 표준 헤더는 꺾쇠, 프로젝트 헤더는 큰따옴표를 씁니다.

꼬리 질문 대비: "헤더에 함수 정의를 넣으면 어떤 문제가?" → 여러 .c에서 포함하면 같은 함수가 여러 번 정의되어 링크 단계에서 multiple definition 오류가 납니다.

Q2. printf는 어떻게 가변 개수의 인수를 처리하나요? 서식 지정자가 틀리면 어떻게 되나요?

printf는 <stdarg.h>의 va_list 메커니즘을 쓰는 가변 인자 함수로, 호출 시 인수의 자료형 정보가 전달되지 않기 때문에 서식 문자열을 해석해 다음 인수의 형과 크기를 결정합니다. 따라서 지정자와 실제 인수가 다르면 잘못된 위치나 크기로 값을 읽게 되고 이는 미정의 동작입니다. 또한 가변 인자로 넘어갈 때 float는 double로, char와 short는 int로 승격됩니다.

꼬리 질문 대비: "서식 문자열 취약점이란?" → 사용자 입력을 서식 문자열로 그대로 쓰면 %x로 스택을 읽거나 %n으로 메모리에 쓰는 공격이 가능해지는 취약점입니다.

Q3. 'A'와 "A"의 차이를 메모리 관점에서 설명해 주세요.

'A'는 문자 코드 65라는 정수 값 하나이며 C에서 자료형은 int라 sizeof('A')는 4입니다. "A"는 'A'와 널 문자 '\0'으로 이루어진 길이 2의 char 배열이며, 보통 읽기 전용 데이터 영역에 저장되고 식에서 쓰이면 첫 글자의 주소로 변환됩니다. 그래서 %c에는 'A'를, %s에는 "A"를 줘야 합니다.

꼬리 질문 대비: "C++에서 sizeof('A')는?" → C++에서는 문자 상수가 char형이라 1입니다.

Q4. 표준 출력 버퍼링이란 무엇이며, 줄 버퍼와 완전 버퍼의 차이는?

출력 함수를 호출할 때마다 시스템 호출을 하면 비싸므로, 라이브러리가 메모리 버퍼에 모아 두었다가 한꺼번에 내보내는 것이 버퍼링입니다. 줄 버퍼링은 줄바꿈을 만날 때 비우며 보통 터미널에 연결된 stdout에 적용되고, 완전 버퍼링은 버퍼가 가득 찰 때 비우며 파일이나 파이프로 리다이렉트된 경우에 적용됩니다. stderr는 기본적으로 버퍼링되지 않습니다. 비정상 종료 시 버퍼 내용이 유실될 수 있으므로 fflush나 stderr를 활용합니다.

Q5. 0.1 + 0.2가 0.3이 아닌 이유는 무엇인가요?

double은 IEEE 754 2진 부동소수점 형식이라 0.1, 0.2, 0.3 같은 10진 소수 대부분을 정확히 표현하지 못하고 가장 가까운 2진 값으로 근사합니다. 그 근사 오차가 더해지면서 0.1 + 0.2는 0.30000000000000004441…이 되고, 0.3의 근사값과 달라집니다. 그래서 금융 계산에서는 금액을 최소 단위의 정수로 다루거나 10진 고정소수점 라이브러리를 사용합니다.

꼬리 질문 대비: "실수 비교는 어떻게?" → 허용 오차(epsilon)를 둔 비교를 쓰되, 금액은 애초에 정수로 다루는 것이 정답입니다.

Q6. 16진수를 프로그래밍에서 많이 쓰는 이유는 무엇인가요?

16진수 한 자리가 정확히 4비트에 대응해 1바이트를 두 자리로 표현할 수 있으므로, 비트 패턴을 직관적으로 읽고 쓸 수 있기 때문입니다. 메모리 주소, 메모리 덤프, 비트 마스크, 문자 인코딩, 색상 값 등에서 표준적으로 사용합니다.

Q7. size_t는 무엇이고 왜 %zu로 출력해야 하나요?

size_t는 sizeof 연산자의 결과형이자 객체 크기를 나타내는 부호 없는 정수형으로, 플랫폼의 주소 공간 크기에 맞춰 정의됩니다(64비트에서 보통 8바이트). int와 크기·부호가 다를 수 있으므로 %d로 출력하면 불일치가 생기고, C99에서 도입된 %zu를 써야 이식성 있게 출력할 수 있습니다.

Q8. 문자 인코딩 EUC-KR과 UTF-8의 차이가 C 프로그램에 어떤 영향을 주나요?

EUC-KR(CP949)은 한글 한 글자를 2바이트로, UTF-8은 대부분 3바이트로 표현합니다. C의 char 배열과 printf 폭, strlen은 모두 바이트 단위이므로 같은 한글 문자열이라도 인코딩에 따라 길이가 달라지고, 고정길이 전문이나 보고서 정렬에서 필드 밀림이 생길 수 있습니다. 시스템 간 연동 시 인코딩을 명확히 정하고 바이트 기준으로 길이를 검증해야 합니다.

다음 출력 결과를 공백까지 정확히 쓰십시오.

printf("[%6.2f][%-6d][%+.1e]\n", 12.345, -7, 12345.0);
printf("[%c%c][%d]\n", 72, 'i', 'i' - 'a');
정답과 해설 보기

%6.2f로 12.345를 출력하면 결과는 12.35 또는 12.34일 수 있는데, 12.345는 2진수로 12.3450000000000006394884621840901672840118408203125로 저장되어 중간보다 약간 크므로 12.35가 됩니다(5글자, 앞 공백 1개). %-6d로 -7은 2글자 + 공백 4개. %+.1e로 12345.0 = 1.2345×104 → 소수 1자리 1.2, 부호 + 강제 → +1.2e+04. 72는 'H', 'i'(105) - 'a'(97) = 8.

연습문제 2-4 난이도 ★★☆

버그를 찾으십시오. 다음 코드는 무엇이 잘못되었고 실행하면 어떤 일이 생길 수 있습니까?

정답과 해설 보기
  1. 인수 순서가 바뀌었습니다. %s에 정수 15000이 가서 printf가 15000번지를 문자열 주소로 읽으려다 Segmentation fault로 죽을 가능성이 큽니다.
  2. %d에 문자열 주소가 갑니다.
  3. %f에 정수 3이 갑니다. printf는 정수를 실수로 변환하지 않으므로 엉뚱한 값이 나옵니다.
  4. 마지막 % 뒤에 \n이 와서 %\n이라는 잘못된 변환 지정자가 됩니다. %%로 써야 합니다.

모두 UB이며 gcc -Wall이 경고로 잡아 줍니다. 고친 코드: printf("계좌 %s, 잔액 %d원, 이율 %f%%\n", "1002-333", 15000, 3.0);

다음 중 컴파일 오류가 나는 상수와, 오류는 없지만 의도와 다른 값이 될 수 있는 상수를 고르고 그 값을 쓰십시오: 0x1F, 019, 0755, 1e3, 'AB', .5f

정답과 해설 보기

컴파일 오류: 019(8진수에 9 사용 불가). 의도와 다를 수 있는 것: 0755는 10진수 755가 아니라 8진수로 493(7×64 + 5×8 + 5)입니다. 'AB'는 다중 문자 상수로 값이 구현 정의(gcc에서는 'A'×256 + 'B' = 16706)이며 경고가 납니다. 1e3은 정수가 아니라 double 1000.0입니다. 0x1F는 31, .5f는 float 0.5로 정상입니다.

연습문제 2-7 난이도 ★★☆

다음 출력 결과를 쓰고 이유를 설명하십시오.

printf("%zu %zu %zu\n", sizeof("ABC"), sizeof('A'), sizeof("A\0B"));
정답과 해설 보기

"ABC"는 3글자 + 자동으로 붙는 '\0' = 4바이트. 'A'는 C에서 int이므로 4. "A\0B"는 'A', '\0', 'B'에 자동 '\0'까지 4바이트입니다. 중간에 '\0'이 있어도 sizeof는 배열 전체 크기를 세지만, printf("%s")로 출력하면 첫 '\0'에서 멈춰 "A"만 출력됩니다. sizeof(배열 크기)와 문자열 길이(strlen)가 다르다는 점은 12장의 핵심입니다.

연습문제 2-8 난이도 ★★★

다음 두 줄의 출력 결과를 쓰고, 왜 이런 결과가 나오는지 메모리(2진 표현) 관점에서 설명하십시오. 또 금융 계산에서 어떻게 대처해야 하는지 쓰십시오.

printf("%.1f\n", 0.15);
printf("%.17f\n", 0.1 + 0.2);
정답과 해설 보기

0.15는 2진수로 정확히 표현되지 않아 0.1499999999999999944488848768742172978818416595458984375로 저장되므로 소수 첫째 자리 반올림 결과는 0.1입니다. 0.1과 0.2도 각각 근사값으로 저장되며, 더한 결과는 0.3000000000000000444089209850062616169452667236328125가 되어 17자리로 출력하면 오차가 드러납니다.

대처: 금액은 원(또는 센트) 단위 정수로 저장·계산하고, 비율은 정수 배율(bp)로 다루며, 반올림·절사는 정수 연산으로 명시적으로 구현합니다. printf의 반올림은 표시용으로만 씁니다.

연습문제 2-9 난이도 ★★☆

배치 프로그램을 ./batch > batch.log로 실행했는데, 프로그램이 중간에 Segmentation fault로 죽은 뒤 batch.log에 "처리 시작"조차 기록되어 있지 않았습니다. 코드는 맨 처음에 printf("처리 시작\n");을 호출합니다. 원인과 해결책을 쓰십시오.

정답과 해설 보기

stdout이 파일로 리다이렉트되어 완전 버퍼링 모드가 되었기 때문입니다. \n이 있어도 버퍼가 비워지지 않고, 비정상 종료 시 라이브러리의 종료 처리(버퍼 비우기)가 실행되지 않아 버퍼 내용이 사라졌습니다. 해결책: 중요한 로그 뒤에 fflush(stdout);를 호출하거나, fprintf(stderr, ...)로 오류·진행 로그를 남기거나, 프로그램 시작 시 setvbuf(stdout, NULL, _IOLBF, 0);로 줄 버퍼링을 지정합니다. 근본적으로는 Segmentation fault의 원인을 core 파일과 gdb로 분석해 고쳐야 합니다.
