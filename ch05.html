선택문(if, switch-case)

지금까지의 프로그램은 위에서 아래로 한 줄씩 그대로 실행되었습니다. 하지만 실제 프로그램은 "잔액이 부족하면 출금을 거절하고, 충분하면 승인한다"처럼 상황에 따라 다른 길을 가야 합니다. 이 장에서는 프로그램에 판단력을 주는 선택문을 배우고, 그 판단이 CPU 안에서 어떻게 이루어지는지까지 파고듭니다.

이 장에서 배울 것

  • if, if-else 문의 문법과 실행 흐름을 순서도로 그리고 읽을 수 있습니다.
  • C에서 "참"과 "거짓"이 실제로는 0과 0이 아닌 값이라는 사실과 그 결과를 이해합니다.
  • =와 ==를 혼동하는 실수, dangling else 문제를 스스로 찾아내고 고칠 수 있습니다.
  • else if 체인과 중첩 if로 범위 판별 프로그램을 작성합니다.
  • switch-case의 동작 원리(fall-through, break, default)와 점프 테이블 개념을 이해합니다.
  • 거래코드 분기, 수수료 등급, 등급별 금리처럼 금융 시스템에서 선택문이 쓰이는 방식을 익힙니다.

05-1if문

프로그램의 실행 순서를 제어 흐름(control flow)이라고 합니다. 아무것도 하지 않으면 C 프로그램은 main 함수의 첫 문장부터 마지막 문장까지 순서대로 실행됩니다. 이것을 순차 구조라고 부릅니다. 그런데 순차 구조만으로는 할 수 있는 일이 매우 제한적입니다. 입력된 값에 따라 다른 일을 하려면 "갈림길"이 필요합니다. 이 갈림길을 만드는 문장을 선택문(selection statement) 또는 조건문이라고 하며, C에는 if문과 switch문 두 가지가 있습니다.

구조적 프로그래밍 이론에 따르면 모든 프로그램은 세 가지 구조, 즉 순차(sequence), 선택(selection), 반복(iteration)의 조합만으로 작성할 수 있습니다. 이번 장이 그 두 번째인 선택이고, 다음 장이 반복입니다. 이 두 장을 마치면 여러분은 원리적으로 "어떤 계산이든" 표현할 수 있는 도구를 모두 갖추게 됩니다.

if-else문과 블록

조건이 거짓일 때도 무언가를 해야 한다면 else를 붙입니다. if-else문은 두 갈래 중 정확히 하나만 실행됩니다. 둘 다 실행되거나 둘 다 실행되지 않는 경우는 절대 없습니다.

그런데 조건이 참일 때 실행할 문장이 두 개 이상이면 어떻게 할까요? 이때는 중괄호 { }로 여러 문장을 묶어 블록(block), 정식 용어로는 복합문(compound statement)을 만듭니다. C 문법에서 블록은 "문장 하나"로 취급됩니다. 그래서 if 뒤에 "문장 하나"가 올 자리에 블록을 넣으면 여러 문장을 한꺼번에 실행할 수 있습니다.

세미콜론 하나는 그 자체로 "아무 일도 하지 않는 문장", 즉 빈 문장(null statement)입니다. 따라서 if는 빈 문장을 지배하고 끝나며, 아래의 블록은 if와 무관한 독립 블록이 되어 항상 실행됩니다. 문법 오류가 아니므로 컴파일은 잘 되는데, 그래서 더 위험합니다. -Wextra 옵션을 주면 gcc가 -Wempty-body 경고로 알려 줍니다.

블록과 변수의 유효 범위

블록 안에서 선언한 변수는 그 블록 안에서만 살아 있습니다. 이를 블록 유효 범위(block scope)라고 합니다. C99부터는 블록 중간 어디서든 변수를 선언할 수 있습니다(C89에서는 블록 맨 앞에서만 가능했습니다).

왜 그럴까? — 블록 변수는 어디에 저장될까

지역 변수는 함수가 호출될 때 스택이라는 메모리 영역에 자리를 잡습니다(7장에서 자세히 그림으로 봅니다). 블록 안의 변수도 대부분의 컴파일러는 함수 시작 시 스택에 미리 자리를 잡아 두지만, 언어 규칙상 블록이 끝나면 그 이름은 더 이상 쓸 수 없고 값의 수명도 끝난 것으로 봅니다. 그래서 컴파일러는 블록이 끝난 뒤 그 자리를 다른 변수에 재사용할 수 있습니다. 변수를 필요한 블록 안에서만 선언하면 "이 변수는 여기서만 쓰인다"는 의도가 드러나 코드를 읽기 쉬워지고, 실수로 다른 곳에서 값을 바꾸는 일도 막을 수 있습니다.

C에는 원래(C89까지) 참/거짓을 나타내는 전용 자료형이 없었습니다. 대신 매우 단순한 규칙 하나를 씁니다.

여기서 잠깐 — C99의 _Bool과 stdbool.h

C99부터는 _Bool 자료형이 생겼고, <stdbool.h>를 포함하면 bool, true(1), false(0)를 쓸 수 있습니다. _Bool 변수에 0이 아닌 어떤 값을 넣어도 1로 저장된다는 점이 일반 int와 다릅니다. (C23에서는 bool, true, false가 아예 키워드가 되었습니다.)

왜 그럴까? — 왜 하필 "0이 아니면 참"일까

CPU 관점에서 보면 이유가 명확합니다. 대부분의 CPU에는 "직전 연산 결과가 0인가"를 기록하는 제로 플래그(ZF)가 있고, "0이면 점프(jz/je)", "0이 아니면 점프(jnz/jne)" 명령이 기본으로 제공됩니다. 어떤 값이 0인지 아닌지는 한 번의 test 명령으로 알 수 있지만, "정확히 1인지"를 확인하려면 비교를 한 번 더 해야 합니다. C는 하드웨어에 가까운 언어로 설계되었기 때문에 가장 싸게 판별할 수 있는 "0 / 0 아님"을 참·거짓의 기준으로 삼았습니다.

자주 하는 실수 — 실수(float/double)를 ==로 비교

조건식에서 실수를 ==로 비교하면 예상과 다른 결과가 나옵니다.

0.1, 0.2, 0.3은 2진수로 정확히 표현할 수 없는 수라서 각각 가장 가까운 근삿값이 저장됩니다. 0.1 + 0.2의 결과는 0.30000000000000004이고, 리터럴 0.3은 0.29999999999999999에 해당하는 값이어서 두 값의 비트가 다릅니다.

이렇게 해결합니다

일반 계산에서는 "차이가 아주 작으면 같다고 본다"는 허용오차 비교를 씁니다: if (fabs(x - 0.3) < 1e-9) (<math.h> 필요). 그러나 금액은 아예 실수로 저장하지 않는 것이 정답입니다. 은행 시스템은 금액을 원 단위 정수(long long)로, 외화는 센트 단위 정수 등 최소 화폐 단위의 정수로 다룹니다. 정수 비교에는 오차가 없습니다.

= 와 == 를 혼동하는 실수

C 초보자가 가장 많이 하는, 그리고 숙련자도 가끔 하는 실수가 비교 연산자 == 대신 대입 연산자 =를 쓰는 것입니다.

왜 그럴까?

C에서 대입도 값을 가지는 식(expression)입니다. grade = 1은 grade에 1을 저장하고, 식 전체의 값은 저장된 값인 1이 됩니다. 따라서 if (grade = 1)은 if (1)과 같아 항상 참입니다. 게다가 부작용으로 grade의 원래 값 3이 1로 덮어써졌습니다. 고객 등급이 실수로 VIP로 바뀌는 셈이니, 금융 시스템이라면 수수료 면제 같은 혜택이 잘못 적용되는 사고로 이어집니다. 반대로 if (x = 0)은 항상 거짓이 되고 x를 0으로 만들어 버립니다.

문법적으로 합법이므로 컴파일 오류가 나지 않습니다. 이것이 이 버그가 무서운 이유입니다.

이렇게 해결합니다

  1. 경고 옵션을 켜고 경고를 오류처럼 다룹니다. gcc -Wall은 이 경우 "suggest parentheses around assignment used as truth value" 경고를 출력합니다. 실무에서는 -Wall -Wextra -Werror로 경고 자체를 빌드 실패로 만드는 경우가 많습니다.
  2. 요다 조건(Yoda condition): 상수를 왼쪽에 씁니다. if (1 == grade)에서 실수로 if (1 = grade)라고 쓰면 상수에 대입할 수 없으므로 컴파일 오류가 납니다. 다만 요즘은 컴파일러 경고가 충분히 똑똑해서 가독성을 이유로 쓰지 않는 팀도 많습니다. 팀 코딩 표준을 따르십시오.
  3. 의도적으로 대입 결과를 조건으로 쓰는 경우(예: while ((c = getchar()) != EOF))에는 반드시 비교 연산을 명시하거나 괄호를 한 겹 더 씌워 의도를 드러냅니다.

dangling else — else는 누구의 짝인가

if문 안에 또 if문이 들어가고, 거기에 else가 하나만 있으면 그 else가 어느 if의 짝인지 애매해집니다. 이를 dangling else(매달린 else) 문제라고 합니다. 다음 코드의 의도는 "잔액이 있는 고객 중 VIP면 우대 메시지, 잔액이 0 이하면 안내 메시지"입니다.

왜 그럴까?

C 문법 규칙: else는 짝이 없는 가장 가까운 if와 짝을 이룹니다. 들여쓰기는 무시되므로 컴파일러가 보는 실제 구조는 다음과 같습니다.

balance가 0이므로 바깥 if가 거짓이 되어 안쪽 전체를 건너뜁니다. 그래서 "잔액이 없습니다."가 출력되지 않습니다. 더 나쁜 점은, 잔액이 있는 일반 고객에게 "잔액이 없습니다."라는 엉뚱한 메시지가 나간다는 것입니다. 이 규칙은 문법을 모호하지 않게 만들기 위해 거의 모든 C 계열 언어(C++, Java, C#, JavaScript)가 공통으로 채택하고 있습니다.

이렇게 해결합니다

중괄호로 안쪽 if의 범위를 명시적으로 닫아 주면 else가 바깥 if의 짝이 됩니다. "항상 중괄호" 습관만 있으면 dangling else는 원천적으로 생길 수 없습니다.

else는 가장 가까운 if (b)의 짝입니다. 구조는 if (a) { if (b) X; else Y; } 그리고 Z입니다.

  • a=1, b=0: 바깥 참 → 안쪽 거짓 → "Y", 그리고 "Z".
  • a=0, b=0: 바깥 거짓 → 안쪽 전체 건너뜀 → "Z"만 출력.

조건식을 잘 쓰는 법 — 논리 연산자와 단락 평가

실무 조건은 하나로 끝나지 않습니다. "계좌가 정상 상태이고 그리고 잔액이 충분하면" 같은 복합 조건은 논리 연산자 &&(AND), ||(OR), !(NOT)로 표현합니다. 이때 꼭 알아야 할 성질이 단락 평가(short-circuit evaluation)입니다.

  • A && B: A가 거짓(0)이면 결과는 무조건 거짓이므로 B를 아예 계산하지 않습니다.
  • A || B: A가 참이면 결과는 무조건 참이므로 B를 계산하지 않습니다.

이 성질은 C 표준이 보장하는 것이며, 두 연산자의 왼쪽 피연산자 계산 뒤에는 순서점(sequence point)이 있어 A의 계산(부작용 포함)이 완전히 끝난 뒤 B를 계산합니다.

왜 그럴까? — 순서를 바꾸면 프로그램이 죽는다

조건을 total / count > 100000 && count != 0처럼 순서를 바꾸면 count가 0일 때 나눗셈이 먼저 실행됩니다. 정수를 0으로 나누는 것은 C 표준상 미정의 동작(UB)이며, x86 리눅스에서는 실제로 CPU가 예외를 일으켜 프로세스가 SIGFPE(Floating point exception)로 종료됩니다. 단락 평가는 "앞의 조건이 뒤의 조건을 보호하는" 가드(guard) 역할을 하므로 안전 검사를 항상 앞에 둡니다.

여기서 잠깐 — 범위 조건 0 < x < 10 은 수학처럼 동작하지 않는다

if (0 < x < 10)은 (0 < x) < 10으로 해석됩니다. 앞부분의 결과는 0 또는 1이고, 0이든 1이든 10보다 작으므로 항상 참입니다. x가 500이어도 참입니다. 올바른 표현은 if (0 < x && x < 10)입니다.

복잡한 업무 규칙은 바로 코드로 쓰기보다 순서도로 먼저 그려 보면 빠진 경우(예외 경로)가 눈에 잘 띕니다. 예로 "ATM 출금 승인" 규칙을 생각해 봅시다.

  3. 요청액 + 수수료가 잔액보다 크면 "잔액 부족"으로 거절합니다.

위 코드는 if-else를 깊게 중첩하지 않고 "실패하면 즉시 끝낸다"는 방식을 썼습니다. 이를 가드 절 또는 조기 반환(early return) 패턴이라고 합니다. 정상 경로(happy path)가 들여쓰기 없이 맨 아래로 곧게 흐르므로 읽기 쉽고, 검사 항목을 추가하기도 쉽습니다. 이 장의 후반에서 같은 로직을 중첩 if로 쓴 버전과 비교해 봅니다.

else if 체인 — 여러 갈래로 나누기

세 갈래 이상으로 나눌 때는 else 뒤에 다시 if를 붙이는 else if 체인을 씁니다. 사실 C에 else if라는 별도 문법은 없습니다. else 뒤에 "문장 하나"로 if문이 온 것뿐인데, 이를 보기 좋게 한 줄에 붙여 쓰는 관례입니다.

else if 체인은 위에서부터 차례로 조건을 검사하다가 처음으로 참인 조건의 문장 하나만 실행하고 체인 전체를 빠져나갑니다. 아무 조건도 참이 아니면 마지막 else가 실행됩니다. 마지막 else는 생략할 수 있지만, 생략하면 "어느 것도 실행되지 않는" 경우가 생깁니다.

왜 그럴까? — 조건에 "미만"을 다시 쓰지 않아도 되는 이유

골드 조건을 avg_balance >= 30000000 && avg_balance < 100000000처럼 쓰지 않아도 되는 이유는, 그 줄까지 왔다는 것 자체가 "앞의 조건(1억 이상)이 거짓이었다"는 뜻이기 때문입니다. else if 체인에서는 앞의 조건들의 부정이 뒤의 조건에 자동으로 AND되는 셈입니다. 그래서 체인은 순서가 생명입니다. 만약 >= 0을 맨 위에 두면 양수 잔액은 모두 "일반"으로 분류되고 아래 조건은 영원히 검사되지 않습니다.

자주 하는 실수 — else if 대신 if를 나열

독립된 if 두 개는 각각 검사되므로 4천5백만원은 두 조건 모두 만족해 "골드", "실버"가 둘 다 출력됩니다. "여러 갈래 중 하나"를 원하면 반드시 else if로 연결해야 합니다.

switch-case문의 기본

하나의 정수 값이 여러 개의 특정 값 중 무엇인지에 따라 갈라질 때는 switch문이 더 깔끔합니다. 예를 들어 거래코드가 1이면 입금, 2면 출금, 3이면 이체, 4면 조회처럼 "값이 딱 떨어지는" 분기입니다.

규칙을 정리하면 다음과 같습니다.

  1. switch 괄호 안의 식은 정수형이어야 합니다(char, short, int, long, long long, 열거형 포함). double이나 문자열은 쓸 수 없습니다.
  2. case 뒤에는 정수 상수식만 올 수 있습니다. case 1:, case 'A':, case 2+3:은 되지만 case x:(변수)는 안 됩니다. 같은 값의 case가 두 번 나오면 컴파일 오류입니다.
  3. 식의 값과 일치하는 case 레이블로 점프하여 그 지점부터 실행을 시작합니다.
  4. break를 만나면 switch 블록 전체를 빠져나갑니다.
  5. 일치하는 case가 없으면 default로 점프하고, default도 없으면 아무것도 실행하지 않습니다.

fall-through와 break — switch의 가장 큰 함정

case 레이블은 "여기서부터 실행하라"는 입구 표시일 뿐, 끝을 나타내지 않습니다. 따라서 break가 없으면 실행은 다음 case 레이블을 무시하고 그대로 아래로 흘러내려 갑니다. 이를 fall-through(낙하)라고 합니다.

왜 그럴까? — case는 goto의 목적지 레이블이다

switch문을 컴파일러 관점에서 보면 "값에 맞는 레이블로 goto 한 번"입니다. case 2: 레이블로 점프한 뒤에는 CPU가 그냥 다음 명령을 차례로 실행합니다. 기계어에는 "case의 끝"이라는 개념이 없고, 다음 case 레이블은 단지 주소에 붙은 이름이므로 그냥 지나칩니다. break는 "switch 블록의 끝 주소로 점프"하는 명령으로 번역됩니다. 이런 설계는 1970년대 C의 전신인 B언어와 어셈블리 관습에서 이어진 것으로, 여러 case가 코드를 공유할 수 있다는 장점이 있지만 실수의 원천이기도 합니다. 그래서 Java, C#도 같은 문법을 이어받았고, C#은 아예 비어 있지 않은 case의 fall-through를 컴파일 오류로 만들었습니다.

이렇게 해결합니다

  1. 모든 case 끝에 break;를 쓰는 것을 기본으로 합니다. 마지막 case나 default에도 쓰는 습관을 들이면 나중에 아래에 case를 추가할 때 안전합니다.
  2. 의도적인 fall-through라면 반드시 주석으로 표시합니다(/* fall through */). gcc 7 이상은 -Wimplicit-fallthrough(-Wextra에 포함) 경고를 지원하며, 이 주석이나 C23의 [[fallthrough]]; 속성이 있으면 경고를 내지 않습니다.
  3. 코드 리뷰 체크리스트에 "switch의 break 누락"을 항목으로 넣습니다.

의도적인 fall-through: 여러 값이 같은 처리를 공유할 때

fall-through가 항상 나쁜 것은 아닙니다. 여러 case 레이블을 연속으로 붙이면 "이 값들 중 하나면"을 표현할 수 있습니다.

레이블 사이에 문장이 하나도 없는 이런 형태는 관용적으로 널리 쓰이며, 컴파일러도 경고하지 않습니다.

default의 역할과 위치

default는 생략할 수 있지만, 실무 코드에서는 항상 쓰는 것이 원칙입니다. 예상하지 못한 값(잘못된 전문, 새로 추가됐지만 아직 처리 로직이 없는 코드, 메모리 손상 등)이 들어왔을 때 조용히 아무것도 하지 않고 넘어가면 장애 원인을 찾기가 매우 어렵기 때문입니다. default에서는 오류 코드를 세팅하고 로그를 남기는 것이 정석입니다.

default는 문법적으로 switch 블록 어디에 두어도 됩니다(맨 앞에 두어도 일치하는 case가 있으면 그 case로 갑니다). 하지만 가독성을 위해 맨 끝에 두는 것이 관례입니다.

자주 하는 실수 — switch에서 하면 안 되는 것들

  • 실수 값 분기: switch (rate)에서 rate가 double이면 컴파일 오류입니다.
  • 문자열 분기: switch (name)이나 case "KRW":는 불가능합니다. 문자열은 8장의 배열, 12장의 strcmp로 비교해야 합니다. (한 글자 문자 case 'D':는 정수 상수이므로 가능합니다.)
  • 범위 분기: case 1..10:은 표준 C에 없습니다(GCC 확장 문법 case 1 ... 10:은 이식성이 없음). 범위는 if-else if로 처리합니다.
  • case 안에서 변수 선언: case 1: int x = 5;는 C에서 컴파일 오류가 날 수 있습니다(C23 이전에는 레이블 뒤에 선언이 바로 올 수 없음). 또한 초기화를 건너뛰는 점프가 생길 수 있으므로 case 본문을 { } 블록으로 감싸고 그 안에서 선언합니다.

switch의 동작 원리 — 점프 테이블

"switch가 if-else if 체인보다 빠르다"는 말을 들어 본 적이 있을 것입니다. 정확히는 "그럴 수 있다"입니다. 그 이유가 점프 테이블(jump table)입니다.

case 값들이 1, 2, 3, 4, 5처럼 촘촘하게 모여 있으면, 컴파일러는 각 case 코드의 시작 주소를 배열(표)로 만들어 둡니다. 그리고 실행 시에는 다음 세 단계만 합니다.

  1. 값에서 최소 case 값을 빼서 인덱스를 만듭니다: idx = tx_code - 1
  2. 인덱스가 표 범위를 벗어나면 default로 갑니다(비교 1번).
  3. table[idx]에 적힌 주소로 바로 점프합니다(간접 점프 1번).

case가 100개여도 비교는 한 번뿐입니다. if-else if 체인은 최악의 경우 100번 비교해야 하므로, case가 많고 값이 조밀할수록 switch가 유리합니다.

왜 그럴까? — 항상 점프 테이블이 만들어지지 않는 이유

case 값이 1, 1000, 50000처럼 띄엄띄엄 있으면 표를 만들려면 5만 칸이 필요하고 대부분 default 주소로 채워야 합니다. 메모리 낭비가 심하므로 컴파일러는 이런 경우 이진 탐색 형태의 비교 트리(값을 반씩 나눠 비교, O(log n))나 단순한 비교 체인을 만듭니다. 반대로 if-else if 체인도 조건이 단순 상수 비교라면 최적화 컴파일러가 점프 테이블로 바꿀 수 있습니다. 결론적으로 "switch가 항상 빠르다"가 아니라 "switch는 컴파일러가 최적화하기 좋은 형태를 제공한다"가 정확한 설명입니다. 성능보다 중요한 switch의 장점은 "하나의 값에 따른 다중 분기"라는 의도가 코드에 명확히 드러난다는 것입니다.

여기서 잠깐 — 조건 연산자 ?: 로 짧은 if-else 대체하기

값 하나를 고르는 단순한 if-else는 조건 연산자(삼항 연산자)로 쓸 수 있습니다. fee = (is_vip ? 0 : 500);는 "VIP면 0, 아니면 500"입니다. 식이므로 printf 인자 안에서도 쓸 수 있습니다: printf("%s\n", balance < 0 ? "마이너스" : "정상");. 다만 중첩해서 쓰면 읽기 어려워지므로 한 단계까지만 쓰는 것을 권장합니다.

핵심 정리

  • 선택문은 조건에 따라 실행 경로를 바꾸며, 기계어 수준에서는 "비교 + 조건 점프"입니다.
  • C에서 0은 거짓, 0이 아닌 모든 값은 참입니다. 관계·논리 연산의 결과는 int 1 또는 0입니다.
  • if 본문이 여러 문장이면 중괄호 블록이 필요합니다. 한 줄이어도 항상 중괄호를 쓰는 것이 실무 표준입니다.
  • if (x = 1)은 대입이므로 항상 참이 됩니다. -Wall 경고를 켜고, 필요하면 요다 조건을 씁니다.
  • else는 가장 가까운 짝 없는 if와 짝을 이룹니다(dangling else). 중괄호로 의도를 명시합니다.
  • &&, ||는 단락 평가를 하므로 안전 검사(0 나누기, 범위)를 앞에 둡니다. 0 < x < 10은 항상 참입니다.
  • else if 체인은 위에서부터 검사하며 처음 참인 곳만 실행합니다. 조건 순서와 경계값(이상/초과/이하/미만)이 핵심입니다.
  • 중첩이 깊어지면 가드 절(조기 반환)로 평평하게 만듭니다.
  • switch는 정수식과 정수 상수 case만 비교하며, case는 입구 레이블일 뿐이므로 break가 없으면 아래로 낙하합니다.
  • default는 항상 두고 오류를 기록합니다. case 값이 조밀하면 컴파일러가 점프 테이블을 만들어 O(1)로 분기할 수 있습니다.
  • 금액은 정수(원 단위 long long), 금리는 bp 정수로 다루고, 곱셈 후 나눗셈 순서로 정밀도를 지킵니다.

Q1. C에서 참과 거짓은 어떻게 표현되나요? bool 타입이 있나요?

C는 0을 거짓, 0이 아닌 모든 값을 참으로 판단하며, 관계·논리 연산자의 결과는 int형 1 또는 0입니다. 원래 전용 불리언 타입이 없었지만 C99에서 _Bool이 추가되었고 <stdbool.h>로 bool/true/false를 쓸 수 있으며, C23에서는 키워드가 되었습니다. _Bool에는 0이 아닌 값을 대입하면 1로 정규화된다는 점이 int와 다릅니다.

꼬리 질문 대비: "왜 0이 아니면 참인가?" — CPU의 제로 플래그와 jz/jnz 명령으로 한 번에 판정할 수 있어 하드웨어 친화적이기 때문입니다.

Q2. if (a = b) 와 if (a == b) 의 차이는? 컴파일 오류가 나지 않는 이유는?

앞의 것은 b를 a에 대입하고 그 대입된 값을 조건으로 쓰며, 뒤의 것은 두 값을 비교합니다. C에서는 대입도 값을 가지는 식이기 때문에 문법적으로 합법이고 컴파일 오류가 나지 않습니다. 방지책으로 -Wall 경고 확인, -Werror 사용, 상수를 왼쪽에 두는 요다 조건, 정적 분석 도구 사용을 말할 수 있습니다.

Q3. 단락 평가(short-circuit evaluation)란 무엇이고 어디에 활용하나요?

&&는 왼쪽이 거짓이면, ||는 왼쪽이 참이면 오른쪽 피연산자를 평가하지 않는 성질로, C 표준이 보장합니다. 널 포인터 검사 후 역참조(p != NULL && p->x > 0), 0 나누기 방지, 비용이 큰 검사를 뒤로 미루는 데 씁니다.

꼬리 질문 대비: "비트 연산자 &도 단락 평가를 하나요?" — 아니요. &와 |는 양쪽을 모두 평가하며, 평가 순서도 정해져 있지 않습니다.

Q4. switch문에서 break를 생략하면 어떻게 되나요? 왜 그렇게 설계되었나요?

일치한 case부터 아래 case들의 문장을 break나 switch 끝을 만날 때까지 계속 실행하는 fall-through가 일어납니다. case는 점프 목적지 레이블일 뿐 블록의 끝을 의미하지 않기 때문입니다. 여러 case가 코드를 공유하도록 하려는 설계지만 버그가 잦아서, 의도한 경우 주석이나 C23의 [[fallthrough]]로 표시하고 -Wimplicit-fallthrough 경고를 켭니다.

Q5. switch와 if-else if 중 무엇이 더 빠른가요?

case 값이 조밀하면 컴파일러가 점프 테이블을 만들어 비교 한 번과 간접 점프로 O(1) 분기가 가능하고, 희소하면 이진 탐색 비교 트리로 O(log n)이 됩니다. if-else if 체인은 기본적으로 순차 비교라 최악 O(n)입니다. 하지만 최적화 컴파일러는 둘을 서로 변환하기도 하므로 "switch가 항상 빠르다"는 정확하지 않고, 가독성과 의도 표현을 기준으로 고르는 것이 맞다고 답합니다.

꼬리 질문 대비: "점프 테이블의 단점은?" — 값이 희소하면 메모리 낭비, 간접 점프는 분기 예측이 어려울 수 있습니다.

Q6. switch의 case에 올 수 없는 것은 무엇인가요?

case 레이블은 컴파일 시간에 값이 정해지는 정수 상수식이어야 하므로 변수, 실수, 문자열은 올 수 없고 중복 값도 안 됩니다. switch 식 자체도 정수형이어야 합니다. 문자열 분기는 strcmp 연쇄나 해시값, 테이블 탐색으로 처리합니다.

Q7. dangling else 문제란?

중첩 if에 else가 하나만 있을 때 어느 if의 짝인지 모호해지는 문제로, C는 "가장 가까운 짝 없는 if와 결합"하는 규칙으로 해결합니다. 들여쓰기와 실제 의미가 달라 버그가 생기므로 항상 중괄호를 사용해 범위를 명확히 합니다.

Q8. 분기 예측(branch prediction)이란 무엇이고 if문 성능과 어떤 관계인가요?

현대 CPU는 파이프라인으로 명령을 미리 실행하기 때문에 조건 분기의 결과를 기다리지 않고 예측해서 진행합니다. 예측이 틀리면 미리 실행한 작업을 버려야 해서 수십 사이클 손해를 봅니다. 그래서 패턴이 일정한 분기는 빠르고 무작위 분기는 느리며, 정렬된 데이터에서 같은 루프가 더 빠른 현상이 이 때문입니다. GCC의 __builtin_expect(likely/unlikely)로 힌트를 줄 수도 있습니다.
