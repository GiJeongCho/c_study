04

연산자

이자 = 원금 × 이율 ÷ 10000. 이 식 하나도 곱셈과 나눗셈의 순서, 정수 나눗셈의 버림, 자료형 변환에 따라 결과가 몇 원씩 달라집니다. 금융 프로그램에서 '몇 원'은 곧 장애입니다. 이 장에서는 C의 연산자가 정확히 어떻게 계산하는지, 왜 그런 결과가 나오는지를 비트와 메모리 수준까지 내려가 살펴봅니다.

이 장에서 배울 것

  • 정수 나눗셈과 나머지 연산의 규칙(0 방향 버림, 나머지의 부호)을 정확히 압니다.
  • 증감 연산자의 전위·후위 차이를 메모리 동작으로 설명할 수 있습니다.
  • 관계·논리 연산의 결과가 0과 1이라는 것과 단락 평가를 활용합니다.
  • 암시적 형 변환(정수 승격, 일반 산술 변환)과 명시적 형 변환(캐스트)을 구분합니다.
  • sizeof, 복합 대입, 콤마, 조건 연산자, 비트 연산자를 사용합니다.
  • 우선순위·결합 규칙과 평가 순서의 차이, i = i++ 같은 미정의 동작을 이해합니다.

04-1산술 연산자, 관계 연산자, 논리 연산자

연산자(operator)는 값을 가지고 계산하는 기호이고, 연산의 대상이 되는 값을 피연산자(operand)라고 합니다. a + b에서 +는 연산자, a와 b는 피연산자입니다. 피연산자가 하나면 단항(-a, !a), 둘이면 이항, 셋이면 삼항 연산자(?:)입니다. 연산자와 피연산자가 결합된 것을 식(expression)이라 하며, 모든 식은 값을 가집니다.

산술 연산자

연산자의미예 (a=17, b=5)결과
+덧셈a + b22
-뺄셈a - b12
*곱셈a * b85
/나눗셈 (정수끼리는 몫)a / b3
%나머지 (정수 전용)a % b2
- (단항)부호 반전-a-17

정수 나눗셈: 소수점 이하는 버린다

왜 그럴까? — 정수끼리 나누면 왜 소수점이 사라질까?

C의 연산 결과 자료형은 피연산자의 자료형으로 정해집니다. int / int의 결과는 int이므로 소수 부분을 담을 공간이 처음부터 없습니다. CPU 차원에서도 정수 나눗셈 명령(x86의 idiv)과 실수 나눗셈 명령(divsd)은 완전히 다른 명령이며, 정수 나눗셈 명령은 몫과 나머지를 정수 레지스터 두 개에 동시에 돌려줍니다. 컴파일러는 피연산자가 둘 다 정수면 정수 명령을 고릅니다. 그래서 double r = 7 / 2;라고 써도 r은 3.0입니다. 오른쪽의 7 / 2가 이미 정수 3으로 계산된 뒤에 double로 바뀌기 때문입니다.

C89에서는 음수가 포함된 정수 나눗셈의 버림 방향(0 방향인지 음의 무한대 방향인지)이 구현 정의였습니다. C99부터 0 방향으로 고정되었고, 나머지의 부호는 피제수(왼쪽)를 따르도록 정해졌습니다.

나머지 연산 %의 활용

  • 짝수·홀수 판별: n % 2 == 0이면 짝수. 단, 음수 홀수는 n % 2가 -1이므로 n % 2 == 1로 홀수를 판별하면 음수에서 틀립니다. n % 2 != 0을 쓰십시오.
  • 자릿수 분리: n % 10은 일의 자리, n / 10 % 10은 십의 자리. 2장의 천 단위 출력에 썼습니다.
  • 주기 계산: 오늘이 일요일(0)이면 100일 뒤 요일은 (0 + 100) % 7 = 2(화요일).
  • 검증 번호: 계좌번호의 마지막 자리 검증 숫자(check digit)는 각 자리에 가중치를 곱해 더한 뒤 % 10, % 11 등으로 계산하는 방식이 많습니다.
  • %는 실수에 쓸 수 없습니다. 실수의 나머지는 <math.h>의 fmod를 씁니다.

곱셈과 나눗셈의 순서: 금융 계산의 1원 차이

왜 그럴까?

*와 /는 우선순위가 같고 왼쪽부터 계산합니다. principal / 10000 * rate_bp에서는 먼저 1234567 / 10000 = 123(소수 0.4567 버림)이 되고, 버려진 0.4567 × 275 ≈ 125.6원어치 정보가 영원히 사라집니다. 반면 곱셈을 먼저 하면 1234567 × 275 = 339,505,925를 10000으로 나눠 33950.59…에서 마지막에 한 번만 버리므로 오차가 1원 미만입니다. 정수 계산에서는 버림을 맨 마지막에 한 번만 하는 것이 원칙입니다.

이렇게 해결합니다 — 곱셈 먼저, 그러나 오버플로 확인

곱셈을 먼저 하면 중간값이 커집니다. 원금 1조 원 × 275 = 2.75×1014는 long long(약 9.2×1018)에 충분히 들어가지만, int로 계산하면 원금 800만 원만 넘어도 오버플로입니다(800만 × 275 = 22억). 금액 계산식은 (1) 변수를 long long으로, (2) 곱셈 먼저, (3) 나눗셈은 마지막에, (4) 중간값의 최대 크기를 설계 단계에서 계산해 둡니다.

은행 시스템에서는 — 절사, 반올림, 절상을 정수로

은행 상품 규정에는 "이자는 원 미만 절사", "수수료는 10원 미만 절사", "세금은 10원 미만 절사"처럼 끝처리 규칙이 명시되어 있습니다. 양수 금액에 대해 정수 연산으로 구현하면 다음과 같습니다.

여기서 x / 10 * 10은 수학적으로는 x와 같아 보이지만, 정수 나눗셈의 버림 때문에 일의 자리가 0이 됩니다. 이처럼 정수 나눗셈의 '결함'처럼 보이는 성질을 정확히 이해하고 의도적으로 이용하는 것이 금융 계산의 기본기입니다. 음수(환불, 역거래)는 0 방향 버림 때문에 결과가 달라지므로 절댓값으로 처리한 뒤 부호를 붙이는 등 별도 규칙이 필요합니다(21장).

예제 4-1 난이도 ★★☆

총 1,000,000원을 3명이 똑같이 나눠 내고, 나누어떨어지지 않는 나머지는 첫 번째 사람이 더 내기로 했습니다. 각자 낼 금액을 정수 연산만으로 계산해 출력하십시오.

정답과 해설 보기

1인당 기본 금액은 total / 3 = 333,333원, 나머지는 total % 3 = 1원입니다. 첫 사람은 333,334원을 냅니다. 합계가 정확히 1,000,000원이 되는지 검산하는 습관(a + b + c == total)이 중요합니다. 금융에서 "나눴더니 1원이 사라졌다"는 대사 불일치의 대표 원인입니다.

대입 연산자와 식의 값

=도 연산자이며, 대입식 자체도 값을 가집니다. 대입식의 값은 왼쪽 변수에 저장된 값입니다. 그래서 a = b = 0;은 오른쪽부터 결합되어 a = (b = 0);이 되고, b = 0의 값 0이 a에 대입됩니다. 3장의 while ((ch = getchar()) != '\n')도 대입식의 값을 비교에 사용한 것입니다.

증감 연산자: 전위와 후위

++는 변수의 값을 1 증가, --는 1 감소시킵니다. 변수 앞에 붙이면 전위(prefix), 뒤에 붙이면 후위(postfix)입니다. 변수 값이 1 변하는 것은 같지만 식의 값이 다릅니다.

  • ++a: a를 1 증가시키고, 식의 값은 증가된 값.
  • a++: a를 1 증가시키되, 식의 값은 증가 전의 값.

왜 그럴까? — 전위가 더 빠르다는 말은 사실일까?

개념적으로 후위 연산은 '옛 값의 복사본'을 따로 보관해야 하므로 전위보다 일이 많아 보입니다. 그러나 i++;처럼 식의 값을 쓰지 않는 단독 문장이라면 현대 C 컴파일러는 두 경우를 완전히 같은 기계어로 만듭니다. int 같은 기본형에서 성능 차이는 없습니다. (C++에서 객체의 연산자를 오버로딩한 경우에는 실제로 복사 비용이 생길 수 있어 전위를 권장하는 것입니다.) C에서는 식의 값을 쓰는지에 따라 의미가 달라지는 것만 정확히 알면 됩니다.

자주 하는 실수 — 한 식에서 같은 변수를 두 번 바꾸기

i = i++;, n = n++ + ++n;, printf("%d %d\n", i, i++); 같은 코드는 결과를 '예측'하는 문제가 아니라 미정의 동작입니다. 컴파일러마다, 최적화 옵션마다 결과가 다릅니다. 이유는 이 장 마지막 소절(시퀀스 포인트)에서 자세히 설명합니다. 원칙: 하나의 식에서 같은 변수를 두 번 이상 변경하거나, 변경하면서 다른 곳에서 읽지 마십시오.

관계 연산자: 결과는 0 또는 1

연산자의미예 (a=10, b=20)결과
>크다a > b0
>=크거나 같다a >= 101
<작다a < b1
<=작거나 같다b <= 190
==같다a == 101
!=다르다a != b1

C에는 (C99 이전) 별도의 참/거짓 자료형이 없었고, 관계 연산의 결과는 int형 1(참) 또는 0(거짓)입니다. 그리고 조건을 판단할 때는 0이면 거짓, 0이 아닌 모든 값은 참으로 봅니다. C99의 <stdbool.h>가 제공하는 bool, true, false도 결국 1과 0입니다.

자주 하는 실수 — =와 ==

status = 0은 비교가 아니라 대입입니다. status가 0으로 바뀌고, 대입식의 값 0이 조건이 되어 항상 거짓입니다. 반대로 if (status = 1)이었다면 정지 계좌가 항상 정상으로 처리되고 원장의 상태값까지 바뀝니다. gcc -Wall은 "suggest parentheses around assignment used as truth value" 경고를 냅니다. 일부 조직은 if (0 == status)처럼 상수를 왼쪽에 쓰는 요다 표기(Yoda condition)를 쓰기도 합니다(0 = status는 컴파일 오류가 나므로).

자주 하는 실수 — 수학식처럼 이어 쓴 비교

if (1 <= month <= 12)는 month가 무엇이든 항상 참입니다. 관계 연산자는 왼쪽부터 결합되므로 (1 <= month) <= 12가 되고, 앞의 결과는 0 또는 1이므로 언제나 12 이하이기 때문입니다. month가 99여도 통과합니다. 올바른 형태는 1 <= month && month <= 12입니다.

왜 그럴까? — 실수는 ==로 비교하면 안 된다

0.1 + 0.2 == 0.3의 결과는 0(거짓)입니다. 2장에서 본 것처럼 0.1 + 0.2는 실제로 0.30000000000000004441…이고, 0.3은 0.29999999999999998889…로 저장되어 서로 다른 비트 패턴이기 때문입니다. 실수끼리는 fabs(a - b) < 1e-9처럼 허용 오차로 비교해야 하며, 금액처럼 정확한 비교가 필요한 값은 처음부터 정수로 다뤄야 합니다.

논리 연산자와 단락 평가

연산자의미결과가 1인 경우
&&논리곱 (AND, 그리고)양쪽 모두 참(0이 아님)
||논리합 (OR, 또는)둘 중 하나 이상 참
!논리부정 (NOT)피연산자가 0일 때 (!0 = 1, !5 = 0)

논리 연산자의 가장 중요한 성질은 단락 평가(short-circuit evaluation)입니다. &&는 왼쪽이 거짓이면 전체가 거짓으로 확정되므로 오른쪽을 아예 계산하지 않습니다. ||는 왼쪽이 참이면 오른쪽을 계산하지 않습니다. 이것은 최적화가 아니라 표준이 보장하는 규칙이므로 안전장치로 활용할 수 있습니다.

왜 그럴까? — 단락 평가가 보장되는 이유

&&와 ||는 C 표준에서 "왼쪽 피연산자의 평가가 끝난 뒤에 시퀀스 포인트가 있다"고 정의되어 있습니다. 즉 왼쪽의 계산과 그 부수 효과(변수 변경 등)가 완전히 끝난 다음에 오른쪽을 평가할지 결정합니다. 기계어로는 조건 분기(jump) 명령으로 번역되어, 왼쪽 결과에 따라 오른쪽 코드로 아예 건너가지 않습니다. 그래서 "포인터가 NULL이 아니면 그 내용을 본다"(p != NULL && p->balance > 0) 같은 관용구가 안전합니다. 반대로 오른쪽에 ++calls처럼 부수 효과를 넣으면 그것이 실행될지 말지가 왼쪽에 달려 있으므로, 부수 효과는 논리식 밖으로 빼는 것이 읽기 좋은 코드입니다.

여기서 잠깐 — 드모르간의 법칙

"정상 계좌이고 한도 이내인 경우가 아니면 거절"을 코드로 옮기면 !(is_normal && within_limit)입니다. 드모르간의 법칙에 따라 이는 !is_normal || !within_limit(정상 계좌가 아니거나 한도를 넘으면 거절)와 같습니다. 부정이 섞인 복잡한 조건은 이 법칙으로 풀어 쓰면 읽기 쉬워지고 버그가 줄어듭니다.

예제 4-2 난이도 ★★☆

다음 코드의 출력 결과를 쓰십시오.

int a = 0, b = 5, c = 0;
int r1 = a && (c = b);
int r2 = b || (c = 9);
int r3 = !a + !b + (a < b < 3);
printf("%d %d %d %d\n", r1, r2, r3, c);
정답과 해설 보기

r1: a가 0이므로 (c = b)는 실행되지 않고 r1 = 0, c는 0 그대로. r2: b가 0이 아니므로(참) (c = 9)는 실행되지 않고 r2 = 1. r3: !a = 1, !b = 0, a < b < 3은 (0 < 5) < 3 = 1 < 3 = 1, 합계 2. c는 한 번도 바뀌지 않아 0입니다.

04-2그 외 유용한 연산자

형 변환: 암시적 변환과 명시적 변환(캐스트)

CPU는 같은 자료형끼리만 연산할 수 있습니다. 정수 덧셈 회로와 실수 덧셈 회로가 다르고, 4바이트 덧셈과 8바이트 덧셈도 다른 명령입니다. 그래서 int + double처럼 자료형이 다른 값이 만나면 컴파일러가 연산 전에 한쪽을 다른 쪽 자료형으로 변환하는 기계어를 넣습니다. 이를 암시적 형 변환(implicit conversion)이라 하고, 프로그래머가 (double)x처럼 직접 지시하는 것을 명시적 형 변환(캐스트, cast)이라고 합니다.

규칙 1: 정수 승격(integer promotion)

char, short(그리고 그 unsigned 버전) 값은 연산에 쓰일 때 먼저 int로 변환됩니다. 대부분의 CPU에서 int가 가장 자연스럽고 빠른 연산 단위이기 때문입니다. 그래서 char a = 100, b = 100;일 때 a + b는 오버플로 없이 int 200이 됩니다. 그 결과를 다시 char에 저장할 때 범위를 넘는 것이 문제일 뿐입니다.

규칙 2: 일반 산술 변환(usual arithmetic conversions)

이항 연산의 두 피연산자 자료형이 다르면 더 넓은 쪽으로 맞춥니다. 대략의 순서는 다음과 같습니다.

왜 그럴까? — (double)sum / cnt와 (double)(sum / cnt)의 차이

캐스트 연산자 (자료형)는 단항 연산자로 우선순위가 /보다 높습니다. 그래서 (double)sum / cnt는 ((double)sum) / cnt입니다. sum이 7.0이 된 뒤 일반 산술 변환에 따라 cnt도 2.0으로 바뀌어 실수 나눗셈 3.5가 됩니다. 반면 (double)(sum / cnt)는 괄호 안의 정수 나눗셈이 먼저 끝나 3이 된 뒤 3.0으로 바뀌므로, 이미 잃어버린 0.5는 돌아오지 않습니다. 캐스트는 변환 시점이 핵심입니다.

실수를 정수로 변환하면 소수부는 0 방향으로 버려집니다(3.99 → 3, -3.99 → -3). 변환 결과가 정수형 범위를 넘으면(예: (int)1e20) 미정의 동작입니다.

가장 위험한 함정: signed와 unsigned의 비교

왜 그럴까?

int와 unsigned int는 같은 순위(크기)이므로 일반 산술 변환 규칙에 따라 int 쪽이 unsigned int로 변환됩니다. signed → unsigned 변환은 "232를 더해 범위 안에 넣는다"로 정의되어 있어 -1은 4294967295가 됩니다. 2의 보수 환경에서는 비트 패턴이 그대로이고 해석만 바뀌는 것입니다. sizeof의 결과 size_t도 unsigned이므로 -1 < sizeof(int)도 거짓입니다(이 경우 -1은 64비트 unsigned 최대값이 됩니다). gcc는 -Wextra(정확히는 -Wsign-compare)로 경고합니다.

이렇게 해결합니다

  • 금액, 건수, 인덱스 비교에서 signed와 unsigned를 섞지 않습니다. 금액은 모두 long long으로 통일합니다.
  • 섞어야 한다면 비교 전에 음수 여부를 먼저 검사하거나 명시적으로 캐스트합니다: if (n < 0 || (size_t)n < len).
  • -Wall -Wextra로 컴파일하고 -Wsign-compare, -Wconversion 경고를 확인합니다.

은행 시스템에서는 — 암시적 변환이 만든 한도 우회

이체 한도 검사 함수가 if (amount > daily_limit) reject();였고, amount는 long long, daily_limit은 다른 모듈에서 unsigned long long으로 선언되어 있었다고 합시다. 정상 금액에서는 문제가 없지만, 전문 파싱 오류로 amount에 -1이 들어오면 -1은 unsigned long long 최대값(약 1,844경)으로 변환되어 한도 초과로 거절됩니다. 반대 방향, 즉 한도 쪽이 signed이고 금액 쪽이 unsigned라면 음수 한도(설정 오류)가 거대한 양수가 되어 모든 이체가 통과할 수 있습니다. 실무 원칙은 (1) 금액 관련 자료형을 프로젝트 전체에서 하나로 통일하고, (2) 외부 입력 금액은 변환 직후 범위(0 < 금액 ≤ 최대)를 검사하며, (3) 컴파일 경고 0건을 빌드 기준으로 삼는 것입니다.

예제 4-3 난이도 ★★★

다음 출력 결과를 쓰십시오(64비트 리눅스 gcc).

char a = 100, b = 100;
char c = a + b;
unsigned char u = 200;
int x = 5;
printf("%d %d %d %f\n", a + b, c, u + x, x / 2 * 2.0);
정답과 해설 보기

a + b는 정수 승격으로 int 200입니다. 이를 signed char(x86 gcc에서 char는 signed) c에 저장하면 범위(-128~127)를 넘어 구현 정의 변환이 일어나며, gcc는 하위 8비트(1100 1000)를 취해 -56이 됩니다. u + x는 둘 다 int로 승격되어 205. x / 2 * 2.0은 왼쪽부터 x / 2 = 2(정수 나눗셈)를 먼저 하고 2 * 2.0 = 4.0이 됩니다. 2.0이 있다고 식 전체가 실수 계산이 되는 것이 아니라, 각 연산마다 그 연산의 두 피연산자만 보고 변환한다는 점이 핵심입니다.

sizeof 연산자 다시 보기

sizeof는 컴파일 시간에 크기를 계산하는 연산자입니다(가변 길이 배열 VLA만 예외). 그래서 괄호 안의 식은 실행되지 않습니다.

sizeof(1 + 2.0)은 double이므로 8, 'A' + 1은 int이므로 4입니다. sizeof arr / sizeof arr[0]은 배열 원소 개수를 구하는 관용구로 8장에서 자주 씁니다.

복합 대입 연산자

a = a + b를 a += b로 줄여 쓸 수 있습니다. -=, *=, /=, %=, 그리고 비트 연산의 &=, |=, ^=, <<=, >>=가 있습니다.

왜 그럴까? — x *= 2 + 3이 50인 이유

복합 대입 연산자는 대입 연산자와 같은 가장 낮은 우선순위 그룹에 속합니다. 그래서 오른쪽 식 2 + 3이 먼저 완전히 계산된 뒤 x = x * (5)가 됩니다. 또 a += b는 a = a + b와 거의 같지만 a를 한 번만 평가한다는 차이가 있습니다. arr[i++] += 1은 i를 한 번 증가시키지만, arr[i++] = arr[i++] + 1은 i를 두 번 바꾸는 UB 코드가 됩니다.

콤마 연산자

콤마 연산자 ,는 왼쪽 식을 평가한 뒤(결과는 버림) 오른쪽 식을 평가하고, 오른쪽 식의 값을 전체 값으로 합니다. 왼쪽과 오른쪽 사이에는 시퀀스 포인트가 있어 순서가 보장됩니다. 우선순위가 모든 연산자 중 가장 낮습니다.

함수 인수를 구분하는 콤마(printf("%d", a, b))나 변수 선언의 콤마(int a, b;)는 콤마 연산자가 아니라 구분자입니다. 콤마 연산자는 주로 for (i = 0, j = n; i < j; i++, j--)처럼 반복문에서 씁니다(6장). 그 외의 곳에서는 읽기 어려우므로 남용하지 않습니다.

조건 연산자 ?:

조건 ? 식1 : 식2는 조건이 참이면 식1, 거짓이면 식2의 값을 가집니다. C의 유일한 삼항 연산자이며, 선택된 쪽만 평가됩니다(조건 뒤에 시퀀스 포인트).

자주 하는 실수 — 조건 연산자의 결과 자료형

조건 연산자의 두 결과 식도 일반 산술 변환을 거쳐 공통 자료형이 됩니다. printf("%d\n", 1 ? 1 : 2.0);은 결과가 double 1.0이 되어 %d와 불일치(UB)입니다. 또 cond ? -1 : 1U는 unsigned가 되어 -1이 4294967295가 됩니다. 조건 연산자는 짧고 명확한 선택에만 쓰고, 중첩(a ? b : c ? d : e)은 if문(5장)으로 바꾸는 것이 좋습니다.

비트 연산 입문

비트 연산자는 정수를 비트 단위로 계산합니다. 하드웨어 제어, 압축, 암호, 그리고 금융 시스템에서는 계좌 상태 플래그나 권한 코드를 한 정수에 묶어 저장할 때 씁니다(20장에서 깊이 다룹니다).

연산자이름규칙예 (0x0C=1100, 0x0A=1010)
&비트 AND둘 다 1이면 10x0C & 0x0A = 1000 = 0x08
|비트 OR하나라도 1이면 10x0C | 0x0A = 1110 = 0x0E
^비트 XOR서로 다르면 10x0C ^ 0x0A = 0110 = 0x06
~비트 NOT0과 1을 뒤집음(unsigned char)~0x0C = 1111 0011 = 0xF3
<<왼쪽 시프트비트를 왼쪽으로 n칸, 오른쪽은 01 << 3 = 8
>>오른쪽 시프트비트를 오른쪽으로 n칸40 >> 2 = 10

왜 그럴까? — 비트 연산에는 왜 unsigned를 쓸까?

왼쪽 시프트는 2를 곱하는 것과 같고(x << n = x × 2n), 오른쪽 시프트는 양수에서 2n으로 나눈 몫과 같습니다. 그러나 signed 정수에서는 함정이 있습니다. 음수를 왼쪽으로 시프트하거나 결과가 범위를 넘으면 UB이고, 음수를 오른쪽으로 시프트한 결과는 구현 정의입니다(대부분 부호 비트를 복사하는 산술 시프트). 또 시프트 횟수가 자료형 비트 수 이상이면(1 << 32, int 기준) UB입니다. 플래그와 비트 마스크에는 unsigned를 쓰고 상수에도 1u처럼 접미사를 붙이는 것이 안전한 습관입니다.

자주 하는 실수 — &와 &&, 그리고 우선순위

  • &(비트 AND)와 &&(논리 AND)는 다릅니다. 1 & 2는 0이지만 1 && 2는 1입니다. 또 &는 단락 평가를 하지 않습니다.
  • if (status & ST_STOP == 0)은 ==가 &보다 우선순위가 높아서 status & (ST_STOP == 0), 즉 status & 0 = 항상 0이 됩니다. 비트 연산은 반드시 괄호로 감쌉니다: if ((status & ST_STOP) == 0). 이는 C 설계자 데니스 리치도 인정한 역사적 실수입니다.

예제 4-4 난이도 ★★☆

unsigned int perm = 0x5;(이진수 0101)일 때 다음 각 식의 값을 16진수로 쓰십시오. (1) perm | 0x8 (2) perm & 0x4 (3) perm ^ 0xF (4) perm << 2 (5) perm & ~0x1u

정답과 해설 보기

(1) 0101 | 1000 = 1101 = 0xD (2) 0101 & 0100 = 0100 = 0x4 (3) 0101 ^ 1111 = 1010 = 0xA (XOR with 1은 뒤집기) (4) 0101을 왼쪽으로 2칸 = 1 0100 = 0x14 (= 5 × 4 = 20) (5) ~0x1u = 1111…1110이므로 bit0만 지움 → 0100 = 0x4.

연산자 우선순위와 결합 규칙

하나의 식에 여러 연산자가 있으면 우선순위(precedence)가 높은 것부터 묶이고, 우선순위가 같으면 결합 규칙(associativity)에 따라 왼쪽부터(또는 오른쪽부터) 묶입니다.

여기서 잠깐 — 외우는 요령

"단항 > 산술(곱 > 덧) > 시프트 > 관계 > 동등 > 비트(& ^ |) > 논리(&& ||) > 조건 > 대입 > 콤마". 그리고 오른쪽 결합은 단항, 조건, 대입 세 그룹뿐입니다. 하지만 실무의 진짜 요령은 헷갈리면 괄호를 친다입니다. 괄호는 성능에 아무 영향이 없고, 코드를 읽는 다음 사람(6개월 뒤의 자신 포함)을 구합니다.

평가 순서와 시퀀스 포인트: i = i++는 왜 UB인가

많은 사람이 오해하는 사실이 있습니다. 우선순위와 결합 규칙은 '어떻게 묶이는가'만 정할 뿐, '어느 피연산자를 먼저 계산하는가'(평가 순서)는 정하지 않습니다. f() + g() * h()에서 곱셈이 덧셈보다 먼저 '묶이는' 것은 확실하지만, f, g, h 중 어떤 함수가 먼저 호출될지는 지정되지 않은(unspecified) 사항이라 컴파일러 마음입니다.

C 표준은 이를 시퀀스 포인트(sequence point)라는 개념으로 정리합니다(C11에서는 sequenced-before 관계로 더 정교하게 표현). 시퀀스 포인트는 "그 이전의 모든 부수 효과(변수 변경 등)가 완료되고, 이후의 것은 아직 시작되지 않은" 지점입니다. 대표적인 시퀀스 포인트는 다음과 같습니다.

  • 완전한 식의 끝(문장 끝 ;)
  • &&, ||, 콤마 연산자 ,의 왼쪽 피연산자 평가 후
  • ?:의 조건 평가 후
  • 함수 호출 직전(모든 인수 평가 후)

그리고 핵심 규칙: 두 시퀀스 포인트 사이에서 같은 객체를 두 번 이상 수정하거나, 수정하면서 (새 값을 정하기 위한 목적 외로) 그 값을 읽으면 미정의 동작입니다.

왜 그럴까? — 표준은 왜 평가 순서를 정하지 않았을까?

평가 순서를 고정하지 않으면 컴파일러가 CPU 레지스터 사용과 명령 배치를 가장 효율적으로 고를 수 있습니다. 예를 들어 x86-64 리눅스에서 함수 인수는 레지스터로 전달되는데, 인수를 어떤 순서로 계산해야 레지스터를 덜 쓰는지는 상황마다 다릅니다. 실제로 gcc와 clang은 같은 printf("%d %d\n", i, i++)에 대해 서로 다른 결과를 내는 것으로 잘 알려져 있습니다. 그래서 "우리 컴파일러에서는 6 5가 나오더라"는 아무 의미가 없습니다. 이런 코드는 결과를 맞히는 문제가 아니라 고쳐야 하는 버그이며, gcc는 -Wall(-Wsequence-point)로 경고합니다.

세 가지를 구분하십시오

(1) 우선순위·결합: 식이 어떻게 묶이는가(문법). (2) 평가 순서: 피연산자를 어떤 순서로 계산하는가(대부분 지정되지 않음, && || , ?:만 왼쪽 먼저 보장). (3) 시퀀스 포인트 규칙: 그 사이에서 같은 변수를 두 번 수정하거나 수정과 읽기를 섞으면 UB. 면접에서 i = i++의 결과를 묻는다면 숫자가 아니라 "미정의 동작이므로 결과를 보장할 수 없다"가 정답입니다.

예제 4-5 난이도 ★★★

다음 중 정의된 동작인 것과 미정의 동작인 것을 구분하고, 정의된 것은 실행 후 i의 값을 쓰십시오(각각 i = 1에서 시작).
(1) i = i + 1; (2) i++ && i++; (3) i = i++ + 1; (4) i = (i++, i + 1); (5) int j = i++ * i;

정답과 해설 보기
  1. 정의됨, i = 2. i를 읽는 것은 새 값을 계산하기 위한 것이고 수정은 한 번뿐입니다.
  2. 정의됨, i = 3. && 왼쪽 평가 후 시퀀스 포인트가 있습니다. 왼쪽 i++의 값 1(참)이므로 오른쪽도 평가되어 i는 최종 3.
  3. 미정의 동작. i++의 부수 효과와 대입이 같은 i를 순서 없이 수정합니다.
  4. 정의됨, i = 3. 콤마 연산자에 시퀀스 포인트가 있어 i++(i=2) 완료 후 i + 1 = 3을 계산해 대입합니다.
  5. 미정의 동작. i를 수정(i++)하면서 같은 식의 다른 부분에서 읽습니다(* i).

은행 시스템에서는 — 코드 리뷰 체크리스트의 연산자 항목

금융권 개발 표준이나 코드 리뷰 체크리스트에는 이 장의 내용이 거의 그대로 들어 있습니다. 예를 들면 다음과 같습니다. (1) 금액 계산식에서 나눗셈은 마지막에 한 번만 하는가. (2) 끝처리(절사·반올림·절상) 규칙이 상품 규정과 일치하는가. (3) 금액 변수는 모두 같은 64비트 signed 자료형인가. (4) signed/unsigned 혼합 비교가 없는가. (5) 하나의 식에서 같은 변수를 두 번 이상 변경하지 않는가. (6) 비트 연산과 비교를 섞을 때 괄호를 썼는가. (7) 0으로 나누기 가능성을 단락 평가나 사전 검사로 막았는가. 이런 항목은 정적 분석 도구로도 상당 부분 자동 점검합니다.

핵심 정리

  • 정수끼리의 /는 몫만 남기고 0 방향으로 버립니다(C99). %의 부호는 왼쪽 피연산자를 따르며 (a/b)*b + a%b == a가 항상 성립합니다.
  • 정수 금액 계산은 곱셈 먼저, 나눗셈은 마지막에 한 번. 중간값 오버플로를 고려해 long long을 씁니다. 절사 x/10*10, 반올림 (x+5)/10*10, 절상 (x+9)/10*10(양수).
  • 대입식도 값을 가지며 대입은 오른쪽부터 결합합니다.
  • ++a는 증가 후 값, a++는 증가 전 값이 식의 값입니다. 단독 문장에서는 차이가 없습니다.
  • 관계·논리 연산의 결과는 int 0 또는 1이고, 조건에서는 0이 아니면 참입니다. =와 ==를 혼동하지 않고, 1 <= x <= 12처럼 이어 쓰지 않습니다. 실수는 ==로 비교하지 않습니다.
  • &&, ||는 단락 평가가 보장되며, 0으로 나누기·NULL 접근을 막는 안전장치로 씁니다.
  • 암시적 변환: char/short는 int로 승격, 서로 다른 형은 넓은 쪽으로. 같은 순위의 signed와 unsigned가 만나면 unsigned로 바뀌어 -1 < 1U가 거짓이 됩니다.
  • 캐스트는 변환 시점이 중요합니다: (double)a/b와 (double)(a/b)는 다릅니다. 실수 → 정수 변환은 0 방향 버림입니다.
  • sizeof는 컴파일 시간 연산자이며 안의 식을 실행하지 않습니다.
  • 복합 대입 x *= 2 + 3은 x = x * (2 + 3)입니다. 콤마 연산자는 오른쪽 값을 갖습니다. 조건 연산자 ?:는 선택된 쪽만 평가합니다.
  • 비트 연산 & | ^ ~ << >>는 unsigned와 함께 쓰고, 플래그는 |=로 설정, &로 검사, &= ~로 해제합니다. 비교와 섞을 때는 괄호 필수.
  • 우선순위는 묶는 방법일 뿐 평가 순서가 아닙니다. 시퀀스 포인트 사이에서 같은 변수를 두 번 수정하거나 수정과 읽기를 섞으면 UB입니다(i = i++).

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. i = i++; 를 실행하면 i의 값은 어떻게 되나요?

결과를 말할 수 없습니다. 하나의 식 안에서 i에 대한 두 번의 수정(후위 증가의 부수 효과와 대입)이 시퀀스 포인트 없이 일어나므로 C 표준상 미정의 동작입니다. 컴파일러와 최적화 옵션에 따라 결과가 다를 수 있고, 아예 예상치 못한 코드가 생성될 수도 있습니다. 의도가 증가라면 i++;만 쓰면 됩니다.

꼬리 질문 대비: "그럼 i++ && i++는요?" → &&에는 시퀀스 포인트가 있어 정의된 동작입니다.

Q2. 전위 증가와 후위 증가의 차이는? 성능 차이가 있나요?

둘 다 변수를 1 증가시키지만, 식의 값이 전위는 증가 후 값, 후위는 증가 전 값입니다. C의 기본 자료형에서는 식의 값을 쓰지 않는 경우 컴파일러가 동일한 기계어를 생성하므로 성능 차이가 없습니다. C++에서 사용자 정의 타입의 후위 연산자는 이전 값의 복사본을 만들어야 하므로 전위가 더 효율적일 수 있습니다.

Q3. 단락 평가(short-circuit evaluation)란 무엇이며 어디에 활용하나요?

&&는 왼쪽이 거짓이면, ||는 왼쪽이 참이면 오른쪽 피연산자를 평가하지 않고 결과를 확정하는 규칙으로, C 표준이 보장합니다. 이를 이용해 p != NULL && p->x처럼 널 포인터 역참조를 막거나, cnt != 0 && sum / cnt처럼 0으로 나누기를 방지합니다. 오른쪽에 부수 효과가 있으면 실행 여부가 조건에 따라 달라지므로 주의해야 합니다.

Q4. 연산자 우선순위와 평가 순서의 차이를 설명해 주세요.

우선순위와 결합 규칙은 식이 어떤 구조로 묶이는지를 정하는 문법 규칙이고, 평가 순서는 실행 시 피연산자를 어떤 순서로 계산하는지입니다. C는 &&, ||, 콤마, 조건 연산자를 제외하면 피연산자와 함수 인수의 평가 순서를 지정하지 않습니다. 따라서 f() + g()에서 f와 g의 호출 순서에 의존하는 코드는 이식성이 없습니다.

Q5. -1 < sizeof(int)의 결과가 거짓인 이유는?

sizeof의 결과형인 size_t는 부호 없는 정수형입니다. int와 size_t를 비교하면 일반 산술 변환에 의해 -1이 size_t로 변환되는데, 부호 없는 형으로의 변환은 모듈러 연산으로 정의되어 -1이 해당 형의 최댓값이 됩니다. 결국 '최댓값 < 4'를 비교하므로 거짓입니다. signed와 unsigned의 혼합 비교는 피하고 -Wsign-compare 경고를 활성화해야 합니다.

Q6. 정수 승격(integer promotion)이란 무엇인가요?

int보다 작은 정수형(char, short, 비트필드 등)이 산술 연산에 쓰일 때 먼저 int(값을 표현할 수 없으면 unsigned int)로 변환되는 규칙입니다. CPU의 자연스러운 연산 단위인 int로 계산해 효율을 높이고 중간 오버플로를 줄이기 위한 것입니다. 그래서 unsigned char a = 200, b = 100;에서 a + b는 300이고, 이를 다시 unsigned char에 저장할 때 44가 됩니다.

Q7. 비트 연산으로 특정 비트를 설정, 해제, 토글, 검사하는 방법은?

n번 비트 마스크를 1u << n으로 만든 뒤, 설정은 x |= mask, 해제는 x &= ~mask, 토글은 x ^= mask, 검사는 (x & mask) != 0입니다. 부호 있는 정수의 시프트는 UB나 구현 정의 결과가 생길 수 있으므로 unsigned를 사용합니다. 또 ==가 &보다 우선순위가 높으므로 괄호를 반드시 씁니다.

꼬리 질문 대비: "2의 거듭제곱 판별은?" → x != 0 && (x & (x - 1)) == 0.

Q8. 정수 나눗셈에서 음수는 어떻게 처리되나요?

C99 이후 정수 나눗셈은 0 방향으로 버림하므로 -7 / 2는 -3이고, 나머지는 피제수의 부호를 따라 -7 % 2는 -1입니다. (a/b)*b + a%b == a 관계가 항상 성립합니다. C89에서는 음수 나눗셈의 버림 방향이 구현 정의였으며, Python처럼 내림(floor)하는 언어와 결과가 다르므로 언어 간 로직 이식 시 주의해야 합니다.

Q9. 금융 계산에서 나눗셈을 마지막에 해야 하는 이유는?

정수 나눗셈은 매번 소수점 이하를 버리므로, 나눗셈을 먼저 하면 버려진 오차에 이후의 곱셈 배수가 곱해져 오차가 커집니다. 곱셈을 먼저 해 정밀도를 유지한 뒤 마지막에 한 번만 나누고, 그때 규정된 끝처리(절사, 반올림)를 적용해야 합니다. 대신 곱셈 결과가 자료형 범위를 넘지 않도록 64비트 정수를 쓰고 최대값을 검토합니다.

Q10. 왼쪽 시프트가 곱셈보다 빠르다는 말은 맞나요?

역사적으로는 시프트가 곱셈보다 빨랐지만, 현대 컴파일러는 상수 곱셈을 자동으로 시프트와 덧셈 조합으로 바꾸는 최적화를 하므로 소스에서 직접 시프트로 바꿀 필요가 거의 없습니다. 오히려 signed 음수의 시프트는 UB나 구현 정의 동작이 될 수 있어 위험합니다. 의미가 곱셈이면 곱셈으로, 비트 조작이면 시프트로 쓰는 것이 올바릅니다.

y = ++b * 2;

정답과 해설 보기

연습문제 4-5 난이도 ★★☆

int s = 10, c = 4;

연습문제 4-6 난이도 ★★☆

이체 금액 long long amt에 대해 다음 수수료 규칙을 조건 연산자 하나로 구현하십시오: 금액이 0 이하이면 수수료 -1(오류 표시), 10만 원 이하이면 0원, 그 외에는 금액의 0.1%를 10원 미만 절사(정수 연산). amt = 1,234,567일 때 결과를 계산하십시오.

정답과 해설 보기

1,234,567 × 1 / 1000 = 1234(0.1%, 원 미만 버림), 1234 / 10 * 10 = 1230. 조건 연산자는 오른쪽 결합이라 a ? x : (b ? y : z)로 묶입니다. 이 정도 중첩까지는 줄바꿈으로 읽기 쉽게 쓸 수 있지만, 규칙이 더 늘어나면 if-else(5장)로 바꾸는 것이 좋습니다.

연습문제 4-7 난이도 ★★★

다음 코드의 출력 결과를 쓰고 이유를 설명하십시오(64비트 리눅스 gcc).

unsigned int limit = 100;
int amount = -50;
if (amount < limit)
    printf("한도 이내\n");
else
    printf("한도 초과\n");
unsigned char x = 255;
printf("%d %d\n", x + 1, (unsigned char)(x + 1));
정답과 해설 보기

amount(int)와 limit(unsigned int)를 비교하면 amount가 unsigned로 변환되어 -50이 4294967246이 되므로 "한도 초과"가 출력됩니다. 음수 금액이라는 잘못된 입력이 우연히 거절된 것일 뿐, 논리는 틀렸습니다. 두 번째 줄에서 x + 1은 정수 승격으로 int 256이고, unsigned char로 캐스트하면 256 mod 256 = 0입니다.

연습문제 4-8 난이도 ★★☆

다음 중 미정의 동작인 문장을 모두 고르십시오(int i = 0, a[5] = {0}; 가정).
(1) a[i] = i; (2) a[i++] = i; (3) i = i * 2 + 1; (4) i++, i++; (5) a[i] = ++i; (6) i = (i > 0) ? i++ : 0;

정답과 해설 보기

미정의 동작: (2), (5). 둘 다 i를 수정하면서 같은 식의 다른 곳에서 i를 읽는데 그 사이에 순서가 정해져 있지 않습니다. (1)과 (3)은 수정이 한 번이고 읽기는 새 값 계산용이라 정의됨. (4)는 콤마 연산자의 시퀀스 포인트로 정의됨(i = 2). (6)은 i = 0이므로 조건이 거짓이라 0이 선택되어 실행 결과 자체는 문제가 없지만, i > 0인 상황에서는 i = i++와 같은 형태가 되어 UB입니다. 이런 코드는 조건에 따라 UB가 되므로 작성하지 말아야 합니다.

연습문제 4-9 난이도 ★★★

원금 long long p = 25000000;(2,500만 원), 연이율 3.45%(만분율 345), 예치 일수 int days = 90;일 때 일할 계산 이자 = 원금 × 이율 × 일수 / 365를 원 미만 절사로 계산하는 정수 연산식을 작성하고 결과를 구하십시오. 그리고 int로 계산했다면 어떤 문제가 생기는지 설명하십시오.

정답과 해설 보기

만분율이므로 분모는 10000 × 365입니다. 곱셈을 모두 먼저 하고 마지막에 나눕니다.

25,000,000 × 345 = 8,625,000,000, × 90 = 776,250,000,000, ÷ 3,650,000 = 212,671.23… → 212,671원. 중간값 7,762억은 int 범위(약 21억)를 크게 넘으므로 int로 계산하면 signed 오버플로(UB)가 발생해 엉뚱한 이자가 나옵니다. 분모도 10000LL * 365처럼 long long으로 계산해 두는 것이 안전합니다(10000 * 365 = 3,650,000은 int 범위 안이지만 습관이 중요합니다).

연습문제 4-10 난이도 ★★☆

8비트 권한 코드 unsigned int perm에서 bit0 = 조회, bit1 = 이체, bit2 = 해지, bit7 = 관리자 권한입니다. 다음을 코드로 작성하십시오. (1) 조회와 이체 권한을 부여 (2) 해지 권한이 있는지 검사해 0/1 출력 (3) 관리자 권한을 회수 (4) perm = 0x83일 때 (1)~(3)을 차례로 수행한 뒤의 최종 값.

정답과 해설 보기

OR로 설정하면 이미 1인 비트는 그대로 유지되므로 '부여'를 여러 번 해도 안전합니다(멱등성). AND NOT으로 다른 비트에 영향 없이 특정 비트만 지울 수 있습니다.

연습문제 4-11 난이도 ★★★

다음 프로그램은 거래 건수가 0인 지점에서 비정상 종료합니다. 단락 평가를 이용해 한 줄만 고쳐 문제를 해결하십시오. 그리고 && 대신 &를 쓰면 왜 해결되지 않는지 설명하십시오.

정답과 해설 보기

&&는 왼쪽 cnt != 0이 거짓이면 오른쪽을 평가하지 않으므로 0으로 나누기가 일어나지 않고, big은 0이 됩니다. 우선순위상 !=, /, >=가 모두 &&보다 높아 의도대로 묶입니다. 반면 비트 AND &는 단락 평가를 하지 않고 양쪽을 모두 계산하므로 여전히 0으로 나누기(UB)가 발생합니다. &는 !=와 >=보다 우선순위가 낮아 식이 묶이는 모양은 같지만, 오른쪽 평가 자체를 막지 못한다는 점이 결정적인 차이입니다.
