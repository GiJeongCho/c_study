시큐어 코딩

C는 메모리를 직접 다루는 대신, 메모리를 지켜 주지 않습니다. 버퍼 하나를 넘쳐 쓰는 실수가 원격 코드 실행으로, 로그 한 줄이 개인정보 유출 사고로 이어집니다. 금융권은 법령과 감독규정으로 시큐어 코딩과 보안약점 진단을 요구합니다. 이 장에서는 공격이 실제로 어떻게 성립하는지 메모리 그림으로 이해하고, 그것을 막는 코딩 습관·도구·컴파일러 옵션을 실무 수준으로 익힙니다.

이 장에서 배울 것

  • 스택 버퍼 오버플로가 리턴 주소를 덮어쓰는 원리를 스택 프레임 그림으로 설명합니다.
  • gets/strcpy/sprintf의 위험과 안전한 대체 함수, strncpy의 함정을 압니다.
  • 포맷 스트링 취약점, 정수 오버플로로 인한 할당 크기 버그, off-by-one, use-after-free를 재현하고 고칩니다.
  • 계좌번호·금액 등 입력을 화이트리스트 방식으로 검증하는 함수를 작성합니다.
  • 보안약점 진단 가이드의 분류와 CERT C 대표 규칙을 실무 체크리스트로 정리합니다.
  • 계좌번호·카드번호·이름·주민등록번호 마스킹, 민감정보 메모리 제거(explicit_bzero), 로그 비식별화를 구현합니다.
  • rand()를 보안 용도로 쓰면 안 되는 이유와 OS 난수 생성기 사용법, 편향 없는 범위 난수를 구현합니다.
  • 스택 카나리, FORTIFY_SOURCE, ASLR/PIE, NX, RELRO와 정적·동적 분석 도구를 빌드 파이프라인에 적용합니다.

22-1메모리 안전과 입력 검증

C 프로그램의 보안 취약점 대부분은 메모리 안전성(memory safety) 위반에서 나옵니다. 배열 경계를 넘어 쓰기(buffer overflow), 이미 해제한 메모리 사용(use-after-free), 초기화하지 않은 메모리 읽기, 그리고 그 원인이 되는 정수 오버플로와 검증되지 않은 입력입니다. 이 절에서는 각각이 "어떻게 공격으로 이어지는지"를 메모리 그림으로 보고, 방어 코드를 작성합니다.

이 장의 공격 예시에 대하여

이 장의 취약 코드는 왜 위험한지 이해하고 방어하기 위한 교육용 예시입니다. 실제 메모리 배치는 컴파일러, 최적화 옵션, 보호 기법에 따라 달라지므로 그림은 개념도입니다. 운영 시스템이나 타인의 시스템에 대한 시험은 반드시 승인된 범위 안에서만 해야 하며, 무단 시도는 정보통신망법 등에 따라 처벌 대상입니다.

스택 버퍼 오버플로의 원리

PART 1에서 함수를 호출하면 스택에 스택 프레임이 만들어진다고 배웠습니다. x86-64에서 call 명령은 "돌아갈 주소(리턴 주소)"를 스택에 넣고, 함수 시작 부분(프롤로그)은 이전 프레임 포인터(rbp)를 저장한 뒤 지역 변수 공간을 확보합니다. 스택은 높은 주소에서 낮은 주소 쪽으로 자라지만, 배열은 낮은 주소에서 높은 주소 쪽으로 채워집니다. 바로 이 방향 차이가 문제의 핵심입니다.

32바이트를 넣자 프로그램이 "stack smashing detected"를 출력하고 강제 종료되었습니다. 이것은 컴파일러가 심어 둔 스택 카나리(22-2절)가 오버플로를 감지하고 프로세스를 죽인 것입니다. 보호 기법을 끄고(-fno-stack-protector) 빌드하면 같은 입력으로 Segmentation fault가 나거나, 입력을 정교하게 만들면 authed만 0이 아닌 값으로 덮어 "인증 결과: 1"을 얻을 수도 있습니다. 즉 프로그램이 죽는 것은 운이 좋은 경우입니다.

왜 리턴 주소를 덮으면 제어권이 넘어갈까?

함수가 끝날 때 ret 명령은 스택 꼭대기의 8바이트를 꺼내 그 주소로 점프합니다. CPU는 그 값이 "원래 호출한 곳"인지 확인하지 않습니다. 그래서 입력 데이터가 리턴 주소 자리를 덮으면, 함수가 끝나는 순간 공격자가 입력에 넣은 주소로 실행이 이동합니다. 고전적인 공격은 버퍼 안에 기계어(셸코드)를 넣고 그 주소로 점프시켰고, 스택 실행 금지(NX)가 도입된 뒤에는 프로그램 안에 이미 있는 코드 조각들을 이어 붙이는 ROP(Return-Oriented Programming)로 발전했습니다. 방어 기법(카나리, ASLR, NX, CFI)은 이 단계들을 하나씩 어렵게 만들지만, 근본 해결은 애초에 경계를 넘어 쓰지 않는 코드입니다.

이렇게 해결합니다 — 길이를 먼저 검사하고, 경계를 아는 함수로 복사

입력 길이를 복사하기 전에 확정하는 것이 핵심입니다. strnlen은 최대 길이까지만 세므로, 종료 문자가 없는 거대한 입력에서도 안전합니다(POSIX 2008 함수, C23 표준에도 포함).

위험한 함수와 안전한 대체 함수

C 표준 라이브러리의 문자열 함수 중 일부는 목적지 버퍼 크기를 받지 않습니다. 버퍼 크기를 모르는 함수는 넘쳐 쓰는 것을 막을 방법이 없습니다.

위험 함수문제대체 방법
gets(buf)입력 길이 제한이 아예 없음. C11에서 표준에서 삭제fgets(buf, sizeof buf, stdin) 후 개행 제거·잘림 검사
strcpy(d, s)d 크기 모름길이 검사 후 memcpy, 또는 snprintf(d, sz, "%s", s), BSD/glibc 2.38+ strlcpy
strcat(d, s)d 크기 모름, 매번 끝을 찾아 O(n²)현재 길이를 추적하며 snprintf/memcpy, strlcat
sprintf(d, fmt, …)결과 길이를 예측하기 어려움snprintf(d, sz, fmt, …) + 반환값으로 잘림 검사
scanf("%s", buf)길이 제한 없음scanf("%15s", buf)(크기−1) 또는 fgets + 파싱
strncpy(d, s, n)s가 n 이상이면 NUL을 붙이지 않음, 짧으면 나머지를 0으로 채워 느림고정 길이 필드(전문) 복사 용도로만 쓰고, 문자열에는 위 방법 사용
atoi/atol오류 보고 없음, 범위 초과는 UBstrtol/strtoll + errno·endptr 검사(21장의 전용 파서)

자주 하는 실수 — strncpy를 "안전한 strcpy"로 착각

strncpy는 원래 고정 길이 필드(유닉스 디렉터리 엔트리)를 채우기 위한 함수입니다. 원본이 n 이상이면 NUL 종료 문자를 넣지 않습니다. 굳이 쓴다면 strncpy(d, s, sz - 1); d[sz - 1] = '\0';처럼 직접 종료해야 하고, 그래도 잘림을 알려 주지 않습니다. 계좌번호나 이름이 잘린 채로 처리되는 것도 버그입니다.

마지막 줄을 보십시오. 넘칠 결합은 거부되었고, msg는 이전 상태 그대로입니다. "실패하면 아무것도 바꾸지 않는다"는 원칙은 금융 코드의 데이터 일관성에 중요합니다. snprintf도 잘림 검사에 유용합니다. 반환값은 "버퍼가 충분했다면 썼을 길이"이므로 if (n < 0 || (size_t)n >= sz)면 잘림 또는 오류입니다.

C11 Annex K의 strcpy_s는?

C11은 선택 사항(Annex K)으로 strcpy_s, sprintf_s 같은 "경계 검사 인터페이스"를 정의했지만, glibc와 대부분의 리눅스 환경은 구현하지 않았습니다. MSVC에는 비슷한 이름의 함수가 있으나 표준과 세부 동작이 다릅니다. 이식성이 필요한 금융 시스템에서는 위처럼 프로젝트 공통 안전 문자열 라이브러리를 만들어 쓰고, 코딩 표준에서 위험 함수 사용을 금지(정적분석 규칙으로 강제)하는 방식이 일반적입니다.

포맷 스트링 취약점

printf는 첫 번째 인자인 포맷 문자열을 해석하면서, % 지시자를 만날 때마다 다음 인자를 꺼내 씁니다. 인자가 실제로 몇 개 전달되었는지는 모릅니다. 그래서 사용자 입력을 포맷 문자열 자리에 그대로 넣으면, 사용자가 % 지시자로 printf를 조종할 수 있습니다.

x86-64 System V 호출 규약에서 printf의 2~6번째 인자는 레지스터(rsi, rdx, rcx, r8, r9)로, 그 뒤는 스택으로 전달됩니다. 인자가 없는데 %p를 여러 개 쓰면 printf는 레지스터에 남아 있던 값과 스택 내용을 차례로 출력합니다. 스택에는 카나리 값, 리턴 주소(ASLR 우회 정보), 다른 지역 변수(비밀번호 버퍼일 수도)가 있습니다. %n은 더 위험해서 메모리에 값을 씁니다.

이렇게 해결합니다 — 포맷은 항상 상수 문자열

gcc의 -Wformat -Wformat-security는 "포맷 인자 없는 비상수 포맷"을 경고하고, -Werror=format-security로 빌드를 실패시킬 수 있습니다(여러 리눅스 배포판의 기본 패키지 빌드 옵션). 직접 만든 가변 인자 로깅 함수에는 __attribute__((format(printf, …)))를 붙여 같은 검사를 받게 합니다. syslog(LOG_INFO, msg), fprintf(fp, msg)도 같은 취약점이므로 주의합니다.

정수 오버플로로 인한 할당 크기 버그

20장에서 본 정수 오버플로는 그 자체로도 금액 오류를 만들지만, 메모리 할당 크기 계산에서 일어나면 힙 버퍼 오버플로로 이어집니다. 패턴은 이렇습니다. ① 외부에서 받은 개수 × 원소 크기로 할당 크기를 계산, ② 곱셈이 넘쳐 작은 값이 됨, ③ 작은 버퍼가 할당됨, ④ 원래 개수만큼 쓰면서 힙을 덮어씀.

이렇게 해결합니다 — 외부 개수는 세 겹으로 검사

① 업무 상한: 일괄 이체 최대 건수처럼 도메인에서 나올 수 없는 값을 먼저 거부합니다. ② 실제 길이 대조: 헤더가 말하는 건수와 실제로 받은 바이트 수가 맞는지 확인합니다(나눗셈으로 비교해 곱셈 오버플로를 피함). ③ 안전한 할당: glibc의 calloc은 count * size 오버플로를 검사해 NULL을 반환합니다. malloc(a * b)를 쓸 때는 if (b != 0 && a > SIZE_MAX / b)로 직접 검사합니다(glibc 2.26+의 reallocarray도 같은 검사를 합니다).

off-by-one 오류

off-by-one은 경계를 딱 1만큼 잘못 잡는 오류입니다. "겨우 1바이트"지만, 그 1바이트가 다음 변수의 첫 바이트나 힙 청크의 크기 정보, 저장된 프레임 포인터의 최하위 바이트를 덮어 실제 공격에 이용된 사례가 많습니다.

이렇게 해결합니다 — 경계 규칙을 습관으로

  • 문자열 버퍼는 항상 "내용 길이 + 1"로 선언합니다: char acct[ACCT_LEN + 1];
  • 반복문은 반열린 구간 [0, N)으로 씁니다: for (i = 0; i < N; i++). <=를 보면 일단 의심합니다.
  • 길이 검사는 strlen(in) >= sizeof name(NUL 자리 포함)처럼 "크기 − 1까지만 허용"으로 씁니다.
  • 배열 크기는 sizeof arr / sizeof arr[0] 매크로로 구하고, 숫자 리터럴을 여러 곳에 반복해 쓰지 않습니다.
  • 고정 길이 전문 필드처럼 NUL 종료가 없는 데이터는 "문자열"로 다루지 말고 (포인터, 길이) 쌍으로 다룹니다.

use-after-free와 double free

use-after-free(UAF)는 free로 반납한 메모리를 가리키는 포인터(dangling pointer)를 계속 사용하는 오류입니다. 반납된 메모리는 힙 관리자가 다음 malloc 요청에 재사용하므로, 해제 후 같은 크기의 할당이 일어나면 옛 포인터와 새 객체가 같은 메모리를 공유하게 됩니다.

일반 빌드에서 role이 1094795585(= 0x41414141, 즉 'AAAA')가 되었습니다. 해제된 세션 메모리가 메모 버퍼로 재사용되어, 메모에 쓴 내용이 권한 값으로 읽힌 것입니다(정확한 결과는 할당기와 버전에 따라 다름). AddressSanitizer(ASan)로 빌드하면 해제된 메모리를 일정 기간 격리(quarantine)하고 접근을 감시하므로, 사용·해제·할당 위치를 정확히 알려 줍니다.

이렇게 해결합니다 — 소유권을 분명히, 해제 후 즉시 무효화

  • 소유권 규칙: 메모리를 할당한 모듈이 해제도 책임지고, 다른 곳에는 "빌려준 포인터"만 줍니다. 세션 테이블처럼 여러 곳이 참조하는 객체는 테이블에서 먼저 제거한 뒤 해제합니다.
  • 해제 후 NULL: 같은 변수를 통한 재사용과 double free를 막습니다(free(NULL)은 아무 일도 하지 않음). 다른 변수에 복사된 포인터까지 막지는 못하므로 소유권 규칙과 함께 씁니다.
  • double free(같은 포인터를 두 번 해제)도 힙 관리 구조를 망가뜨려 공격에 이용됩니다. 오류 처리 경로에서 자주 생기므로 "정리(cleanup) 코드는 한 곳에서" 작성합니다(goto cleanup 패턴).
  • 테스트 빌드에는 항상 -fsanitize=address,undefined를 켜고, 배치 프로그램은 Valgrind로도 주기적으로 점검합니다.

은행 시스템에서는 — 1년에 한 번 죽는 서버

어느 대외계 전문 중계 서버가 몇 달에 한 번, 특정 시간대에만 원인 모를 크래시를 일으켰습니다. 코어 덤프를 보면 매번 다른 곳에서 죽어 원인을 잡기 어려웠습니다. 결국 ASan으로 빌드한 검증 환경에서 대외기관 응답 지연 상황을 재현하자 문제가 드러났습니다. 타임아웃 처리 루틴이 요청 컨텍스트를 해제한 직후, 늦게 도착한 응답이 같은 컨텍스트 포인터로 결과를 기록하는 use-after-free였습니다. 평소에는 해제된 메모리가 아직 재사용되지 않아 "우연히" 문제가 없었고, 트래픽이 몰려 재사용이 빨라지는 시간대에만 다른 요청의 데이터가 오염되었던 것입니다.

해결은 컨텍스트에 상태와 일련번호를 두어 "이미 타임아웃 처리된 요청의 응답은 버린다"는 규칙을 넣고, 해제 대신 상태 전이 후 지연 회수하는 방식으로 바꾸는 것이었습니다. 교훈: 메모리 오류는 재현이 어렵고 증상이 원인과 멀리 떨어져 나타납니다. 그래서 사후 디버깅보다 ASan·정적분석으로 사전에 잡는 것이 훨씬 쌉니다.

입력 화이트리스트 검증

모든 공격은 입력에서 시작합니다. 입력 검증의 원칙은 "허용할 것을 정의하고(화이트리스트), 나머지는 전부 거부한다"입니다. 위험한 문자를 골라 지우는 블랙리스트 방식(예: ', ;, < 제거)은 반드시 빠뜨리는 경우가 생기고, 제거 후 새로운 위험 문자열이 만들어지기도 합니다.

  1. 정규화(canonicalize): 비교 전에 표현을 하나로 맞춥니다. 예: 하이픈 제거, 전각 숫자 거부, 앞뒤 공백 처리 규칙.
  2. 길이 검사: 최소·최대 길이를 먼저 확인합니다(복사·파싱 전에).
  3. 문자 집합 검사: 허용 문자만 있는지 확인합니다.
  4. 형식·구조 검사: 자리 구성, 검증번호(Luhn 등), 날짜 유효성.
  5. 업무 규칙 검사: 범위(금액 한도), 존재 여부(DB 조회), 권한.

"110-123-456789; rm -rf /"는 24자라서 문자 검사 전에 길이 검사에서 걸렸습니다. 길이 검사를 먼저 하면 거대한 입력을 끝까지 훑는 비용(서비스 거부 공격 표면)도 줄어듭니다. 검증이 끝난 정규화 값(norm)만 이후 로직(DB 조회, 전문 생성)에 넘기고, 원문은 다시 쓰지 않습니다.

왜 "고쳐서 받기"보다 "거부하기"가 나을까?

공백을 지워 주고, 전각 숫자를 반각으로 바꿔 주고, 이상한 문자를 무시해 주는 "친절한" 입력 처리는 사용자 경험에는 좋아 보이지만, 시스템 안에 같은 값을 나타내는 여러 표현이 생기게 합니다. 화면에서 검증한 값과 서버에서 처리한 값이 미묘하게 다르면, 검증을 우회하는 입력이 생깁니다(예: 화면은 "1,000"을 1000으로, 서버의 다른 모듈은 1로 해석). 금융 시스템은 형식을 엄격하게 정의하고, 화면(UI)에서 사용자를 돕되 서버는 정의된 형식만 받습니다. 클라이언트 검증은 편의 기능일 뿐 보안 통제가 아니므로, 서버는 모든 입력을 다시 검증합니다.

{

개인정보·계좌번호 마스킹

화면, 로그, 출력물, 테스트 데이터에 개인정보와 금융정보를 그대로 노출하면 개인정보보호법과 신용정보법 위반이 될 수 있습니다. 표시가 꼭 필요한 경우에도 업무 목적에 필요한 최소한만 보여 주는 마스킹(masking)을 적용합니다. 마스킹 위치는 기관 내부 기준과 업계 관행을 따르며, 카드번호는 국제 카드 보안 표준(PCI DSS)이 "앞 6자리와 뒤 4자리까지만 표시 가능"으로 제한합니다.

자주 하는 실수 — 바이트 단위로 이름 마스킹

이름을 dst[1] = '*'처럼 바이트 단위로 가리면 UTF-8 한글(3바이트)의 중간 바이트가 깨져, 화면에 깨진 문자가 나오거나 뒤 시스템에서 문자 변환 오류가 납니다. EUC-KR/CP949(한글 2바이트)를 쓰는 레거시 시스템과 연계할 때는 인코딩마다 글자 경계 판단이 다르므로, 마스킹 함수가 어떤 인코딩을 가정하는지 이름과 주석에 명시합니다(24장의 문자 코드 변환 참고). 또한 마스킹은 표시 단계의 통제일 뿐이므로, 저장 단계에서는 암호화가 별도로 필요합니다.

민감정보 메모리 제거

비밀번호, PIN, 암호키, 세션 토큰은 사용이 끝나면 메모리에서 즉시 지워야 합니다. 지우지 않으면 ① 해제된 메모리가 다른 요청에 재사용되며 내용이 노출되고, ② 코어 덤프·스왑 파일·메모리 덤프에 평문으로 남고, ③ 앞에서 본 포맷 스트링이나 범위 밖 읽기 취약점으로 유출될 수 있습니다. 그런데 "그냥 memset으로 0을 쓰면 되지 않나?"라는 생각에는 함정이 있습니다.

왜 컴파일러가 memset을 지워도 될까?

C 표준의 "as-if 규칙"에 따르면 컴파일러는 프로그램의 관찰 가능한 동작(volatile 접근, 입출력, 종료 상태)만 보존하면 어떤 변형도 할 수 있습니다. pw는 함수가 끝나면 수명이 끝나는 지역 변수이고, memset 이후 아무도 읽지 않으므로, 0을 쓰든 안 쓰든 표준 관점에서 프로그램의 동작은 같습니다. 컴파일러는 memset의 의미를 알고 있으므로(내장 함수) 이 "쓸모없는" 쓰기를 제거합니다. 보안 관점의 의도는 표준이 말하는 관찰 가능한 동작에 포함되지 않는다는 것이 문제의 본질입니다. 같은 이유로 free 직전의 memset도 제거될 수 있습니다.

이렇게 해결합니다 — 제거되지 않는 소거 함수

C23에는 같은 목적의 표준 함수 memset_explicit이 추가되었습니다. 추가로 고려할 사항: ① 비밀번호를 담은 버퍼를 realloc하면 이전 위치에 사본이 남으므로 민감정보 버퍼는 크기를 고정합니다. ② 함수 인자로 값 복사된 구조체, 문자열 변환 중간 버퍼 등 사본을 모두 지웁니다. ③ 장시간 메모리에 머무는 키는 mlock으로 스왑을 막고, 운영 환경에서는 코어 덤프에 민감 영역이 포함되지 않게 설정합니다(madvise(MADV_DONTDUMP) 등). ④ 가장 좋은 방법은 애초에 평문 키를 애플리케이션 메모리에 두지 않고 HSM(하드웨어 보안 모듈)에서 처리하는 것입니다.

로그에 민감정보를 남기지 않기

장애 분석을 위해 "전문 전체를 로그로 남기자"는 유혹은 매우 큽니다. 하지만 로그 파일은 운영자·개발자·외주 인력·로그 수집 시스템 등 원장보다 훨씬 많은 사람과 시스템이 접근합니다. 금융권 보안 사고의 상당수는 원장이 아니라 로그, 백업, 테스트 데이터에서 발생합니다.

로그에 절대 남기면 안 되는 것마스킹 후 남길 수 있는 것그대로 남겨도 되는 것(예)
비밀번호, PIN, CVC/CVV, 카드 마그네틱·IC 데이터, 암호키, 인증 토큰, OTP 값계좌번호, 카드번호, 이름, 전화번호, 주민등록번호(기관 기준에 따라)거래 고유번호, 전문 코드, 응답 코드, 처리 시간, 금액(정책에 따라)

핵심은 마스킹을 개발자가 로그를 찍을 때마다 기억해서 하는 것이 아니라, 전문 레이아웃 정의에 "민감도"를 메타데이터로 넣고 공통 로그 함수가 자동으로 적용하게 하는 것입니다. 새 필드가 추가되어도 레이아웃 정의만 맞게 하면 됩니다. 그리고 길이 오류 같은 비정상 전문일수록 "원문을 통째로 찍고 싶은" 유혹이 크지만, 그때도 원문 대신 길이·전문 코드 같은 메타 정보만 남깁니다.

은행 시스템에서는 — 디버그 로그 한 줄의 대가

한 금융회사에서 장애 분석을 위해 대외 연계 모듈의 로그 레벨을 일시적으로 DEBUG로 올렸습니다. DEBUG 레벨에서는 송수신 전문 전체가 16진 덤프로 기록되도록 되어 있었고, 그 안에는 고객의 카드번호와 유효기간이 평문으로 들어 있었습니다. 장애는 하루 만에 해결되었지만 로그 레벨은 몇 주간 그대로였고, 그 로그는 로그 통합 시스템을 거쳐 여러 부서가 조회할 수 있는 저장소에 보관되었습니다. 정기 점검에서 발견되어 해당 로그를 파기하고 신고 대상 여부를 검토하는 등 큰 비용을 치렀습니다.

교훈: ① DEBUG 레벨에서도 마스킹은 꺼지지 않게 설계합니다. ② 로그 레벨 변경은 변경 관리 대상으로 기한을 정해 자동 원복합니다. ③ 로그 저장소에 대해서도 민감정보 패턴(카드번호 Luhn 검사 통과 16자리 숫자 등)을 주기적으로 스캔합니다.

난수: rand()를 쓰면 안 되는 이유

OTP 대체 인증번호, 세션 ID, 일회용 토큰, 암호키, 거래 고유번호의 무작위 부분처럼 예측되면 안 되는 값에 rand()를 쓰는 것은 대표적인 보안약점입니다.

  • rand()는 대개 선형 합동 생성기(LCG)나 그와 비슷한 단순 알고리즘이라, 출력 몇 개를 관찰하면 내부 상태를 복원해 다음 값을 예측할 수 있습니다.
  • srand(time(NULL))로 시드하면 시드가 "초 단위 현재 시각"이라, 생성 시각을 대략 아는 공격자는 수천 개 후보만 시도하면 됩니다.
  • RAND_MAX는 최소 32767만 보장되어 범위가 좁고(MSVC는 실제로 32767), rand() % 1000000은 범위 자체가 부족하거나 편향됩니다.

보안 용도의 난수는 운영체제가 제공하는 암호학적으로 안전한 의사난수 생성기(CSPRNG)를 씁니다. 리눅스는 getrandom()(glibc 2.25+) 또는 /dev/urandom, 윈도우는 BCryptGenRandom, BSD/macOS는 arc4random_buf입니다.

왜 r % bound만 하면 편향이 생길까?

32비트 난수는 0~4,294,967,295의 4,294,967,296가지 값을 균등하게 냅니다. 이를 1,000,000으로 나눈 나머지를 쓰면, 4,294,967,296 = 1,000,000 × 4,294 + 967,296이므로 0~967,295는 4,295번, 967,296~999,999는 4,294번 나옵니다. 차이는 작지만 특정 값이 더 자주 나온다는 것은 암호학적으로 결함입니다. 마지막 "자투리 구간"(limit 이상)에 걸린 값을 버리고 다시 뽑으면 모든 결과가 정확히 같은 확률이 됩니다. 버려질 확률은 967,296/232 ≈ 0.02%라 성능 부담도 없습니다.

자주 하는 실수 — 난수 실패 시 조용히 대체

"getrandom이 실패하면 어쩌지?"라며 rand()로 폴백하는 코드를 종종 봅니다. 이렇게 하면 공격자가 난수 소스를 고갈시키거나 실패를 유도하는 것만으로 예측 가능한 값을 만들 수 있습니다. 보안 난수 생성 실패는 치명적 오류로 처리해 거래를 중단해야 합니다. 또 하나, 인증번호의 안전성은 난수만으로 결정되지 않습니다. 시도 횟수 제한(예: 5회 실패 시 폐기), 유효 시간(예: 3분), 1회 사용 후 폐기가 함께 있어야 6자리(100만 가지)가 의미를 가집니다.

한 줄 요약

컴파일러·OS 보호 기법은 공격의 비용을 올릴 뿐 버그를 고치지 않습니다. 카나리는 "인증 플래그 덮기" 같은 논리 공격을, ASLR은 정보 유출이 있으면, NX는 ROP를 막지 못합니다. 안전한 코드 + 보호 기법 + 분석 도구를 겹겹이 쌓는 것이 정답입니다.

한 결제 대행 시스템은 가맹점에서 오는 가변 길이 전문을 파싱하는 C 모듈을 운영하고 있었습니다. 수년간 문제가 없었지만, 신규 개발자가 위와 같은 퍼징 하네스를 만들어 하룻밤 돌리자 수십 개의 크래시 입력이 나왔습니다. 대부분은 "길이 필드가 실제 데이터보다 큰 경우" 범위 밖 읽기였고, 하나는 "반복부 건수 × 항목 길이"의 정수 오버플로였습니다. 정상 가맹점은 그런 전문을 보내지 않았기에 드러나지 않았을 뿐, 악의적 입력에는 무방비였던 것입니다. 이후 그 팀은 외부 입력을 다루는 모든 파서에 퍼징을 상시 적용(CI에서 매일 일정 시간)하는 규칙을 만들었습니다.

막는다고 할 수 없는 것: ②③④⑤. 카나리는 리턴 주소 바로 아래에 놓여 "리턴 직전"에 검사하므로 ①만 막습니다(그것도 함수가 반환해야 감지). ② 카나리보다 아래(낮은 주소)에 있는 다른 지역 변수는 카나리를 건드리지 않고도 덮을 수 있습니다. gcc는 배열을 다른 지역 변수보다 높은 주소로 재배치해 이를 완화하지만, 배열 여러 개나 구조체 내부 배치에서는 한계가 있습니다. ③⑤ 힙에는 카나리가 없습니다(힙 관리자의 무결성 검사·ASan이 담당). ④ 카나리 값을 알면 같은 값으로 덮어 검사를 통과합니다.

핵심 정리

  • 스택에서 배열은 높은 주소 쪽으로 채워지고 그 위에 저장된 rbp와 리턴 주소가 있습니다. 경계 검사 없는 복사는 인접 변수(인증 플래그)와 리턴 주소를 덮어 인증 우회·제어 흐름 탈취로 이어집니다.
  • gets(C11에서 삭제), strcpy, strcat, sprintf, scanf("%s")는 목적지 크기를 모릅니다. 길이를 먼저 확정하고 memcpy/snprintf/fgets를 쓰며, 잘림은 오류로 처리합니다. strncpy는 NUL을 보장하지 않습니다.
  • 사용자 입력을 포맷 문자열로 쓰면 %p로 메모리 유출, %n으로 메모리 쓰기가 가능합니다. 포맷은 항상 상수, 입력은 "%s"의 인자로 넘기고 -Wformat-security를 켭니다.
  • 외부에서 온 개수 × 크기 계산이 넘치면 작은 버퍼가 할당되어 힙 오버플로가 됩니다. 업무 상한, 실제 길이 대조, calloc/나눗셈 검사의 세 겹으로 막습니다.
  • off-by-one은 버퍼를 "길이 + 1"로, 반복을 [0, N)으로, 길이 검사를 >=로 쓰는 습관으로 막습니다.
  • use-after-free는 해제된 메모리가 재사용되며 남은 포인터가 남의 데이터를 가리키는 문제입니다. 소유권 규칙, 해제 후 NULL, 단일 정리 경로, ASan으로 대응합니다.
  • 입력은 정규화 → 길이 → 문자 집합 → 형식 → 업무 규칙 순으로 화이트리스트 검증하고, 검증된 정규화 값만 이후에 사용합니다. 서버는 클라이언트 검증을 믿지 않습니다.
  • 보안약점 진단가이드의 7개 분류와 CERT C 규칙(STR31, INT32, MEM30, FIO30, ERR33, MSC30 등)을 공통 라이브러리와 코딩 표준에 반영합니다.
  • 계좌·카드·주민번호·이름은 표시 단계에서 마스킹합니다(카드 앞6·뒤4 이내). 이름은 UTF-8 글자 단위로 처리합니다.
  • 민감정보 소거용 memset은 최적화로 제거될 수 있으므로 explicit_bzero/SecureZeroMemory/memset_explicit(C23)를 씁니다. 사본과 realloc 잔재까지 지웁니다.
  • 로그에는 비밀번호·PIN·CVC·키를 절대 남기지 않고, 전문 레이아웃 메타데이터로 공통 로그 함수가 자동 마스킹하게 합니다. DEBUG 레벨에서도 마찬가지입니다.
  • 보안 난수는 rand()가 아니라 getrandom/BCryptGenRandom 같은 OS CSPRNG를 쓰고, 범위 변환은 거부 표본추출로 편향을 제거하며, 실패 시 대체하지 말고 중단합니다.
  • 스택 카나리, FORTIFY_SOURCE, NX, ASLR/PIE, RELRO, CET는 공격 비용을 올리는 2차 방어입니다. 정적 분석·Sanitizer·퍼징을 CI 파이프라인에 넣어 매 커밋마다 검사합니다.

Q1. 버퍼 오버플로가 무엇이고 어떻게 공격에 이용되며, 어떻게 방어합니까?

버퍼 오버플로는 할당된 버퍼의 경계를 넘어 쓰는 오류입니다. 스택에서는 배열이 높은 주소로 채워지고 그 위에 리턴 주소가 있어, 넘친 데이터가 리턴 주소를 덮으면 함수 반환 시 공격자가 정한 주소로 실행이 이동합니다. 근본 방어는 길이를 검사하고 크기를 받는 함수를 쓰는 것이고, 보조 방어로 스택 카나리, NX, ASLR, FORTIFY_SOURCE가 있습니다.

꼬리 질문 대비: "NX가 있는데 어떻게 공격하나?" → 기존 코드 조각을 이어 붙이는 ROP를 쓰며, ASLR이 이를 어렵게 하지만 주소 유출이 있으면 우회됩니다.

Q2. 스택 카나리와 ASLR의 원리를 설명해 주십시오.

스택 카나리는 함수 시작 시 리턴 주소와 지역 버퍼 사이에 무작위 값을 넣고, 반환 직전에 값이 바뀌었는지 확인해 바뀌었으면 프로세스를 종료합니다. 리턴 주소까지 덮으려면 카나리를 반드시 지나야 하기 때문입니다. ASLR은 실행할 때마다 스택·힙·라이브러리·(PIE이면) 실행 파일의 주소를 무작위로 배치해 공격자가 점프할 주소를 예측하지 못하게 합니다.

꼬리 질문 대비: "카나리의 첫 바이트가 0인 이유?" → 문자열 함수가 NUL에서 멈추므로 문자열 기반 오버플로로 카나리를 읽거나 그대로 재현하기 어렵게 하려는 것입니다.

Q3. 포맷 스트링 취약점이란?

printf(user_input)처럼 외부 입력을 포맷 문자열로 쓰면, printf가 % 지시자마다 존재하지 않는 인자를 레지스터와 스택에서 꺼내 읽으므로 %p, %s로 메모리 내용이 유출되고, %n으로 임의 주소에 값을 쓸 수 있는 취약점입니다. 포맷을 항상 상수로 두고 printf("%s", s)로 쓰면 해결되며, 컴파일러의 -Wformat-security가 탐지합니다.

Q4. use-after-free와 메모리 누수의 차이, 각각의 위험은?

메모리 누수는 할당한 메모리를 해제하지 않아 사용 가능한 메모리가 점점 줄어드는 문제로, 장시간 실행되는 서버에서 결국 할당 실패나 OOM 종료를 일으킵니다(가용성 문제). use-after-free는 해제한 메모리를 계속 사용하는 문제로, 그 메모리가 다른 객체에 재사용되면 데이터 오염이나 공격자가 제어하는 데이터로의 접근이 일어나 코드 실행까지 가능합니다(무결성·기밀성 문제). 누수는 Valgrind·LeakSanitizer로, UAF는 ASan으로 탐지합니다.

Q5. 민감정보를 지울 때 memset만으로 부족한 이유는?

컴파일러는 이후에 읽히지 않는 메모리에 대한 쓰기를 "관찰 불가능한 동작"으로 보고 최적화로 제거할 수 있습니다(dead store elimination). 함수 끝이나 free 직전의 memset이 그 대상입니다. 그래서 explicit_bzero, SecureZeroMemory, C23의 memset_explicit처럼 제거되지 않음이 보장된 함수를 쓰거나, volatile 포인터를 통해 씁니다.

꼬리 질문 대비: "그것만으로 충분한가?" → 레지스터·다른 스택 위치에 남은 사본, realloc 이전 영역, 스왑·코어 덤프도 고려해야 하며, 가능하면 HSM에서 처리해 평문 키를 메모리에 두지 않습니다.

Q6. 보안 용도에 rand()를 쓰면 안 되는 이유는?

rand()는 통계적 용도의 단순한 의사난수 생성기라 출력 몇 개로 내부 상태를 추정해 다음 값을 예측할 수 있고, 시드가 현재 시각이면 탐색 공간이 매우 작습니다. RAND_MAX도 32767까지만 보장됩니다. 세션 ID, 인증번호, 키에는 OS의 암호학적 난수 생성기(getrandom, /dev/urandom, BCryptGenRandom)를 써야 하며, 범위를 줄일 때는 나머지 편향이 없도록 거부 표본추출을 합니다.

Q7. strncpy가 안전하지 않은 이유는?

원본 길이가 n 이상이면 목적지에 NUL 종료 문자를 넣지 않아, 이후 문자열 함수가 버퍼 끝을 넘어 읽게 됩니다. 또한 잘림이 일어났는지 알려 주지 않으며, 원본이 짧으면 남은 공간을 모두 0으로 채워 비효율적입니다. 원래 고정 길이 필드용 함수이므로, 문자열 복사에는 길이 검사 후 memcpy나 snprintf를 쓰고 잘림을 오류로 처리합니다.

Q8. 입력 검증에서 화이트리스트와 블랙리스트의 차이는?

블랙리스트는 위험한 것으로 알려진 패턴을 거부하거나 제거하고, 화이트리스트는 허용할 형식을 정의해 그 외를 모두 거부합니다. 블랙리스트는 새로운 우회 패턴·인코딩 변형을 막지 못하고 제거 후 위험 문자열이 재조합되기도 하므로, 보안 검증은 화이트리스트가 원칙입니다. 또한 검증 전에 정규화해서 같은 값의 여러 표현을 하나로 만들어야 합니다.

Q9. 정적 분석과 동적 분석의 차이는?

정적 분석은 실행하지 않고 코드를 분석해 모든 경로를 볼 수 있고 개발 초기에 적용할 수 있지만, 실행 시 값에 의존하는 버그를 놓치거나 오탐이 많습니다. 동적 분석은 계측된 프로그램을 실행하면서 실제로 일어나는 오류를 정확히 잡지만, 실행된 경로만 검사하고 느립니다. 그래서 둘을 함께 쓰고, 테스트 입력의 다양성을 퍼징으로 보완합니다.

Q10. 정수 오버플로가 어떻게 메모리 취약점으로 이어집니까?

외부 입력으로 받은 개수와 원소 크기를 곱해 할당 크기를 계산할 때 곱셈이 넘치면 실제보다 훨씬 작은 버퍼가 할당되고, 이후 원래 개수만큼 쓰면서 힙 버퍼 오버플로가 일어납니다. 길이 계산의 뺄셈이 unsigned에서 순환해 거대한 복사 길이가 되는 경우도 있습니다. 업무 상한 검사, 실제 데이터 길이와의 대조, calloc이나 나눗셈 기반 사전 검사로 막습니다.

  3. atoi: 오류 검출 불가, 범위 초과 UB, 금액이 int라 21억 원 이상 표현 불가. 21장의 parse_amount와 int64_t 사용.
  4. strcpy(memo, …): 길이 검사 없는 스택 오버플로.
  5. 로그에 비밀번호 평문 기록(pw=%s), 계좌번호 비마스킹.
  6. log_printf(memo): 포맷 스트링 취약점.
  7. 비밀번호를 평문으로 받아 비교하고 사용 후 지우지 않음(req 버퍼에 남음) → 소거 필요, 실제로는 암호화 채널·검증 모듈 사용.
  8. strtok은 내부 정적 상태를 써서 스레드 안전하지 않음(strtok_r 사용).
  9. 비밀번호 오류 횟수 제한 등 인증 실패 처리 부재(업무 규칙).
