반복문

은행의 야간 일마감 배치는 수백만 개의 계좌를 하나씩 읽어 이자를 계산하고 원장을 갱신합니다. 같은 일을 정확히, 지치지 않고 수백만 번 되풀이하는 것, 이것이 컴퓨터가 사람보다 압도적으로 잘하는 일이며 그 도구가 바로 반복문입니다.

이 장에서 배울 것

  • while, for, do-while 문의 문법과 실행 순서를 순서도로 정확히 추적할 수 있습니다.
  • 반복 조건을 설계하고 무한 루프와 off-by-one 오류를 예방합니다.
  • 중첩 반복, break, continue를 이용해 별찍기, 누적합, 최대·최소, 소수 판별을 작성합니다.
  • 복리 이자 시뮬레이션과 원리금균등 상환 스케줄 표를 직접 만들어 봅니다.
  • 입력 검증 루프와 goto를 이용한 에러 처리 관용구를 이해합니다.

06-1while문, for문, do-while문

1부터 5까지 출력하라고 하면 printf를 다섯 번 쓰면 됩니다. 하지만 1부터 100만까지라면? 또는 "사용자가 0을 입력할 때까지"처럼 몇 번 반복할지 미리 알 수 없다면? 이럴 때 필요한 것이 반복문(iteration statement, loop)입니다. C에는 while, for, do-while 세 가지 반복문이 있습니다. 셋은 표현력이 같아서 어느 것으로든 서로 바꿔 쓸 수 있지만, 상황에 따라 가장 자연스러운 것이 있습니다.

while문 — 조건이 참인 동안 반복

while문의 동작은 다음과 같습니다.

  1. 조건식을 계산합니다.
  2. 결과가 0(거짓)이면 반복을 끝내고 while 다음 문장으로 갑니다.
  3. 0이 아니면(참) 본문을 한 번 실행합니다.
  4. 다시 1번으로 돌아갑니다.

핵심은 조건을 먼저 검사한다는 점입니다. 처음부터 조건이 거짓이면 본문은 한 번도 실행되지 않습니다. 이런 반복문을 사전 검사 반복(pre-test loop)이라고 합니다.

반복 과정을 표로 추적(trace)해 보면 이해가 확실해집니다. 이런 표를 손으로 그리는 습관은 반복문 디버깅의 기본기입니다.

회차검사 시 ii <= 5출력갱신 후 i
11참12
22참23
33참34
44참45
55참56
66거짓 → 종료--

조건 검사는 6번, 본문 실행은 5번입니다. 반복이 끝난 뒤 i는 6이라는 점도 꼭 기억하십시오. "조건이 거짓이 되어서" 끝났으므로 반복 후의 i는 조건을 처음으로 만족하지 못한 값입니다.

왜 그럴까? — 반복문은 기계어에서 "뒤로 점프"다

5장에서 if문이 "조건에 따라 앞으로 건너뛰는 점프"라고 했습니다. 반복문은 여기에 "본문 끝에서 조건 검사 위치로 되돌아가는 점프"를 하나 더한 것입니다.

CPU에는 반복이라는 명령이 따로 없고, 단지 프로그램 카운터(다음에 실행할 명령의 주소)를 과거 주소로 되돌릴 뿐입니다. 최적화 컴파일러는 이를 조금 바꿔 조건 검사를 루프 끝으로 옮기기도 하는데(루프 회전), 의미는 같습니다.

정답과 해설 보기

초기값 10, 조건 i >= 1(또는 i > 0), 갱신 i--. 초기화·조건·갱신 세 요소가 서로 맞물려야 반복이 정확한 횟수만큼 돌고 끝납니다.

for문 — 횟수가 정해진 반복의 표준 형식

while 예제를 보면 반복문은 거의 항상 초기화 → 조건 → 본문 → 갱신의 네 요소를 가집니다. 그런데 while에서는 이 요소들이 여러 줄에 흩어져 있어서 실수로 갱신을 빼먹기 쉽습니다. for문은 세 요소를 한 줄에 모아 놓은 문법입니다.

순서를 정확히 외워 두십시오. ① 초기식(한 번만) → ② 조건 → ③ 본문 → ④ 증감 → ② 조건 → ③ → ④ → ... 증감식은 본문 다음에 실행됩니다. 위의 for문은 다음 while문과 정확히 같은 동작을 합니다(continue가 없다는 가정에서. continue와의 차이는 06-2에서 다룹니다).

for문의 다양한 모양

코드의미
for (i = 0; i < n; i++)0부터 n-1까지 n번 — C의 표준 관용구
for (i = n - 1; i >= 0; i--)n-1부터 0까지 거꾸로
for (i = 0; i < 100; i += 10)0, 10, 20, ..., 90
for (i = 0, j = 10; i < j; i++, j--)쉼표 연산자로 변수 두 개 동시 제어
for (;;)세 식 모두 생략: 조건 생략은 "항상 참" → 무한 루프

여기서 잠깐 — 왜 i는 0부터, 조건은 < n 일까

C 프로그래머는 for (i = 1; i <= n; i++)보다 for (i = 0; i < n; i++)를 압도적으로 많이 씁니다. 이유는 8장에서 배울 배열의 인덱스가 0부터 시작하기 때문입니다. 또한 "0 이상 n 미만"이라는 반열린 구간 [0, n)은 반복 횟수가 정확히 n - 0 = n으로 바로 보이고, 구간을 이어 붙일 때([0,n) + [n,m)) 경계가 겹치거나 빠지지 않는다는 장점이 있습니다. 컴퓨터 과학자 다익스트라가 이 표기를 권장한 것으로 유명합니다.

do-while문 — 최소 한 번은 실행

do-while은 본문을 먼저 실행하고 나서 조건을 검사합니다(사후 검사 반복, post-test loop). 따라서 조건이 처음부터 거짓이어도 본문은 최소 한 번 실행됩니다. 메뉴를 먼저 보여 주고 선택을 받는 프로그램이나, 일단 입력을 받고 그 입력이 올바른지 검사하는 경우에 딱 맞습니다.

왜 그럴까? — switch 안의 break는 반복문을 끝내지 않는다

ex06-3.c의 case 0:에 있는 break는 switch만 빠져나갑니다. 반복을 끝내는 것은 while (menu != 0) 조건입니다. break는 "자신을 감싸는 가장 안쪽의 switch 또는 반복문 하나"만 탈출하기 때문입니다. 반면 scanf 실패 시의 break는 switch 바깥, do-while 안에 있으므로 반복문을 탈출합니다. 이 규칙은 06-2에서 중첩 반복과 함께 다시 봅니다.

자주 하는 실수 — 세미콜론 위치

  • do { ... } while (x) 끝에 세미콜론을 빠뜨리면 컴파일 오류입니다.
  • 반대로 while (x);나 for (i = 0; i < 10; i++);처럼 while/for 뒤에 세미콜론을 붙이면 빈 문장이 본문이 됩니다. while의 경우 조건이 참이면 아무것도 바뀌지 않으므로 무한 루프, for의 경우 빈 반복을 10번 한 뒤 아래 블록이 단 한 번 실행됩니다.

반복 조건 설계와 무한 루프

반복문이 정상적으로 끝나려면 본문이 반복될수록 조건이 언젠가 반드시 거짓이 되어야 합니다. 이 성질을 종료성(termination)이라고 합니다. 종료성이 깨지면 무한 루프(infinite loop)가 됩니다.

의도하지 않은 무한 루프의 대표 원인

왜 그럴까? — 예 3과 예 4의 속사정

예 3: 0.1은 2진수로 0.000110011001100...처럼 무한히 반복되는 소수라서 double에는 근삿값이 저장됩니다. 이 오차가 10번 누적되면 결과는 0.9999999999999999가 되어 1.0과 비트가 다릅니다. 그래서 != 조건이 영원히 참입니다. 해결: 반복 제어 변수는 정수로 하고(for (int k = 0; k < 10; k++) { double r = k * 0.1; ... }), 실수를 꼭 써야 한다면 <로 비교합니다.

예 4: unsigned 정수는 음수를 표현할 수 없고, 0에서 1을 빼면 표준에 따라 모듈로 232 연산으로 최댓값 4294967295가 됩니다(이것은 UB가 아니라 정의된 동작입니다). 따라서 i >= 0은 언제나 참입니다. gcc는 -Wextra에서 "comparison of unsigned expression >= 0 is always true" 경고를 냅니다. 해결: 부호 있는 int를 쓰거나, for (unsigned i = 5; i-- > 0; )처럼 검사 후 감소하는 관용구를 씁니다.

의도적인 무한 루프

서버 프로그램, 은행의 대외계 통신 데몬처럼 "꺼질 때까지 계속 요청을 기다리는" 프로그램은 일부러 무한 루프를 씁니다. 관용구는 while (1) 또는 for (;;)이며, 탈출은 내부의 break나 return으로 합니다.

"0"처럼 반복의 끝을 알리기 위해 정해 둔 특별한 값을 보초값(sentinel value)이라고 합니다. 보초값은 정상 데이터로는 나올 수 없는 값으로 골라야 합니다. 거래 금액이 0인 거래가 정상적으로 존재할 수 있다면 -1 같은 다른 값을 써야 합니다.

여기서 잠깐 — 무한 루프에 빠졌을 때

터미널에서 실행 중인 프로그램이 멈추지 않으면 Ctrl + C를 눌러 강제 종료합니다(SIGINT 신호를 보냄). 서버에서 백그라운드로 도는 프로세스라면 ps로 프로세스 번호를 찾아 kill합니다. CPU 사용률이 100%에 붙어 있는 프로세스가 있다면 무한 루프를 가장 먼저 의심하십시오.

off-by-one 오류 — 한 번 더, 한 번 덜

반복 횟수가 의도보다 하나 많거나 적은 오류를 off-by-one 오류(OBOE)라고 합니다. 울타리 기둥 문제(fencepost error)라고도 하는데, "10미터 울타리에 1미터마다 기둥을 세우면 기둥은 몇 개?"라는 질문에 10개라고 답하는 실수(정답은 11개)에서 나온 이름입니다.

반복문반복 횟수공식
for (i = 0; i < n; i++)n끝 - 시작
for (i = 0; i <= n; i++)n + 1끝 - 시작 + 1
for (i = 1; i <= n; i++)n끝 - 시작 + 1
for (i = a; i < b; i++)b - a (b > a일 때)반열린 구간 [a, b)

은행 시스템에서는 — 이자 일수의 "양편넣기"와 "한편넣기"

off-by-one은 금융에서 곧바로 돈 문제가 됩니다. 예를 들어 3월 1일에 예금하고 3월 31일에 해지하면 이자 일수는 며칠일까요? 시작일과 종료일 중 한쪽만 포함하는 한편넣기는 30일, 양쪽 모두 포함하는 양편넣기는 31일입니다. 예금 이자는 보통 한편넣기, 대출 연체 이자 등은 상품에 따라 양편넣기를 쓰는 식으로 상품별 약관에 정해져 있습니다. 일자별 이자를 반복문으로 더할 때 <와 <= 하나 차이로 하루치 이자가 모든 계좌에서 틀어질 수 있으므로, 계정계 개발자는 "이 루프는 시작일 포함인가, 종료일 포함인가"를 반드시 설계서와 대조합니다.

예제 6-3 난이도 ★★☆

다음 반복문들의 본문 실행 횟수는 각각 몇 번입니까?

정답과 해설 보기
  • (a) 10-3 = 7회 (3~9)
  • (b) 10-3+1 = 8회 (3~10)
  • (c) i = 10, 7, 4, 1 → 4회 (다음 값 -2는 조건 거짓)
  • (d) 비교 시 값: 0,1,2,3,4는 참, 5는 거짓 → 5회. 후위 증가는 "비교에는 옛값, 이후 증가"입니다. 종료 후 i는 6입니다.
  • (e) 전위 증가는 증가 후 비교: 1,2,3,4 참, 5 거짓 → 4회. 종료 후 i는 5입니다.

06-2반복문 활용

중첩 반복 — 반복 안의 반복

반복문의 본문에 또 반복문을 넣는 것을 중첩 반복(nested loop)이라고 합니다. 시계를 떠올리면 쉽습니다. 분침이 한 바퀴(60칸) 돌 때마다 시침이 한 칸 움직입니다. 바깥 반복이 한 번 돌 때 안쪽 반복은 처음부터 끝까지 전부 돕니다.

왜 그럴까? — 중첩 반복은 왜 느려지기 쉬운가

바깥이 n번, 안쪽이 n번이면 본문은 n2번 실행됩니다. n이 1,000이면 100만 번, n이 100만이면 1012번입니다. 1초에 약 10억(109) 번의 간단한 연산을 한다고 해도 1012번은 약 17분이 걸립니다. 그래서 "100만 건 거래 내역에서 중복 거래를 찾는" 문제를 모든 쌍을 비교하는 이중 루프로 풀면 배치가 시간 안에 끝나지 않습니다. 이렇게 입력 크기에 따라 실행 횟수가 늘어나는 정도를 시간 복잡도라고 하며, O(n2)처럼 표기합니다. 해결책(정렬 후 인접 비교, 해시)은 24장 자료구조에서 다룹니다.

별찍기 — 중첩 반복 연습의 고전

별찍기는 "행 번호와 출력 개수의 관계식"을 찾는 연습입니다. 바깥 반복은 행, 안쪽 반복은 그 행에 찍을 문자 수를 담당합니다.

행 i(0부터 시작)마다 공백 i개, 별 n-i개입니다. 0부터 시작하면 식이 더 단순해지는 경우가 많습니다.

break와 continue

반복 도중에 흐름을 바꾸는 두 가지 키워드가 있습니다.

  • break: 자신을 감싸는 가장 안쪽의 반복문(또는 switch) 하나를 즉시 빠져나갑니다.
  • continue: 이번 회차의 남은 본문을 건너뛰고 다음 회차로 갑니다. while/do-while에서는 조건 검사로, for에서는 증감식으로 갑니다.

자주 하는 실수 — while문에서 continue가 갱신을 건너뜀

for를 while로 기계적으로 바꾸면 continue 때문에 동작이 달라질 수 있습니다.

for문의 continue는 증감식으로 가지만, while문에는 증감식 자리가 따로 없으므로 continue는 곧장 조건 검사로 갑니다. 본문 끝에 있던 i++가 실행되지 않아 무한 루프가 됩니다.

이렇게 해결합니다

카운터 기반 반복은 for로 쓰거나, while이라면 갱신을 continue보다 앞에 둡니다.

중첩 반복에서 한 번에 탈출하기

break는 가장 안쪽 반복 하나만 빠져나가므로, 이중 루프 전체를 끝내려면 별도의 방법이 필요합니다. 흔히 쓰는 방법은 플래그 변수입니다.

다른 방법으로는 반복을 함수로 분리해 return하는 방법(7장, 가장 권장), 그리고 goto로 바깥으로 점프하는 방법(이 장 마지막에서 다룸)이 있습니다.

sum / n은 둘 다 정수이므로 정수 나눗셈이 되어 소수점 아래가 버려집니다. (double)(sum / n)도 이미 버려진 결과를 변환하므로 소용없습니다. (double)sum / n처럼 나누기 전에 한쪽을 double로 바꾸어야 n도 double로 승격되어 실수 나눗셈이 됩니다. 캐스트 연산자는 나눗셈보다 우선순위가 높기 때문에 이 식은 ((double)sum) / n으로 해석됩니다.

소수 판별 — 반복의 효율을 생각하기

소수(prime)는 1과 자기 자신으로만 나누어떨어지는 2 이상의 정수입니다. 암호 알고리즘(RSA)의 기초여서 금융 보안과도 연결되는 주제입니다. 가장 단순한 판별법은 2부터 n-1까지 나눠 보는 것입니다.

왜 그럴까? — 왜 제곱근까지만 나눠 봐도 될까

n이 합성수라면 n = a × b (1 < a ≤ b)로 쓸 수 있습니다. 이때 a ≤ √n입니다. 왜냐하면 a와 b가 모두 √n보다 크면 a × b > n이 되어 모순이기 때문입니다. 따라서 √n 이하에서 약수를 하나도 찾지 못하면 n은 소수입니다. 이 개선으로 n = 1,000,003을 판별할 때 나눗셈 횟수가 약 100만 번에서 약 1,000번으로 줄어듭니다.

조건을 d <= sqrt(n) 대신 d * d <= n으로 쓴 이유도 있습니다. sqrt는 실수 함수라 매 반복마다 호출 비용이 있고 부동소수점 오차 위험이 있습니다. 정수 곱셈은 빠르고 정확합니다. (단 n이 int 최댓값 근처면 d * d가 오버플로할 수 있으므로 그때는 long long으로 계산합니다.)

n % 10은 일의 자리, n / 10은 일의 자리를 제거한 수입니다. n이 0이 될 때까지 반복하면 모든 자리를 한 번씩 꺼낼 수 있습니다. 반복 횟수가 자릿수에 따라 다르므로 while이 자연스럽습니다.

복리 이자 시뮬레이션

단리는 원금에만 이자가 붙고, 복리는 이자에도 이자가 붙습니다. 복리 원리금은 수학적으로 원금 × (1 + r)n이지만, 실제 은행 계산은 매 기간 이자를 계산해 원 미만을 절사한 뒤 원금에 더하는 과정을 반복합니다. 그래서 공식 한 번이 아니라 반복문으로 기간마다 계산하는 것이 실무와 일치하는 방법입니다.

왜 그럴까? — 공식 대신 반복문을 쓰는 이유

pow(1.035, 5) * 10000000을 계산하면 11876863.06...이 나옵니다. 반복문 결과(11,876,862원)와 1원 차이가 납니다. 반복문은 매년 원 미만을 절사했기 때문에 절사된 부분에는 다음 해 이자가 붙지 않은 것이고, 공식은 연속된 실수 계산이라 절사가 없습니다. 실제 통장에는 매 기간 정수 원 단위로 이자가 입금되므로 반복 시뮬레이션이 실제 통장과 일치합니다. 또한 중간에 금리가 바뀌거나(변동금리), 중도 입금이 있는 상품도 반복 구조라면 해당 회차에서만 처리를 바꾸면 되므로 확장이 쉽습니다.

예제 6-7 난이도 ★★☆

원금 1천만원을 연 3.5% 연복리(매년 원 미만 절사)로 맡기면 몇 년 뒤에 처음으로 2천만원 이상이 될까요? 반복 횟수를 미리 알 수 없는 문제입니다.

정답과 해설 보기

"목표에 도달할 때까지"는 횟수를 모르는 반복이므로 while이 자연스럽습니다.

금융에서 쓰는 어림셈인 72의 법칙(원금이 2배가 되는 기간 ≈ 72 ÷ 연이율%)으로 72 ÷ 3.5 ≈ 20.6년이므로 결과와 잘 맞습니다. 단, 금리가 0 이하이면 이 루프는 영원히 끝나지 않으므로 실무 코드라면 금리 검증이나 최대 반복 횟수 제한이 필요합니다.

원리금균등 상환 스케줄 표

대출 상환 방식 중 원리금균등 상환은 매달 같은 금액(원금 + 이자)을 갚는 방식입니다. 초기에는 잔액이 커서 이자 비중이 크고, 갈수록 원금 비중이 커집니다. 월 상환액은 다음 공식으로 구합니다.

월상환액 = P × r × (1 + r)n ÷ ((1 + r)n − 1)

여기서 P는 대출 원금, r은 월 이율(연이율 ÷ 12), n은 상환 개월 수입니다. 공식으로 월상환액을 한 번 구한 뒤, 반복문으로 매달 이자와 원금 상환분을 계산해 잔액을 줄여 나가면 상환 스케줄 표가 됩니다.

왜 그럴까? — 마지막 회차를 따로 처리하는 이유

월상환액을 원 단위로 반올림했고 매달 이자도 원 미만 절사했기 때문에, 12번을 그대로 반복하면 잔액이 정확히 0이 되지 않고 몇 원이 남거나 모자랍니다. 이것을 끝전(단수) 차이라고 합니다. 실무에서는 마지막 회차에 남은 잔액 전부를 원금으로 상환하게 하여 끝전을 정리합니다. 위 결과에서 12회차 상환액이 1,032,794원으로 3원 적은 이유가 이것입니다. 이 처리를 빠뜨리면 대출이 완제되지 않고 "잔액 3원"이 남아 계좌가 해지되지 않는 실제 장애가 생길 수 있습니다.

또 (long long)(x + 0.5)는 양수 실수를 반올림해 정수로 바꾸는 고전적인 방법입니다. 형변환 (long long)은 소수점 아래를 0 쪽으로 버리므로 0.5를 더한 뒤 버리면 반올림이 됩니다(음수에는 맞지 않음. C99의 llround 함수를 쓰면 안전합니다).

은행 시스템에서는 — 상환 스케줄은 배치와 온라인이 같은 결과를 내야 한다

대출 실행 시 고객에게 보여 주는 상환 예정표(온라인 거래)와, 매달 자동이체일에 실제 상환을 처리하는 월 배치는 서로 다른 프로그램인 경우가 많습니다. 두 프로그램이 이자 절사 규칙, 반올림 위치, 끝전 처리, 이자 일수(실제 일수/365 또는 월 단위) 계산을 조금이라도 다르게 하면 고객이 받은 예정표와 실제 출금액이 1원 단위로 달라지고, 이는 곧 민원과 감사 지적으로 이어집니다. 그래서 금융 시스템은 이자 계산 로직을 공통 함수(모듈)로 만들어 모든 프로그램이 같은 코드를 호출하게 합니다. 이것이 다음 장(7장 함수)이 중요한 이유입니다. 실무의 이자 계산은 월 단위가 아니라 일 단위(잔액 × 연이율 × 일수 ÷ 365)로 하는 경우가 많다는 점도 기억해 두십시오.

입력 검증 루프

사용자 입력은 믿을 수 없습니다. 금액에 문자를 넣거나, 범위를 벗어난 값을 넣을 수 있습니다. 올바른 값이 들어올 때까지 다시 묻는 입력 검증 루프는 do-while이나 무한 루프 + break로 작성합니다. 그런데 scanf에는 함정이 있습니다.

왜 그럴까? — 읽지 못한 입력은 버퍼에 남는다

키보드 입력은 엔터를 누르는 순간 입력 버퍼(stdin 버퍼)에 한 줄이 통째로 들어갑니다. scanf("%d")는 버퍼 앞에서부터 숫자를 읽으려 하는데, 첫 글자가 'a'이면 변환에 실패하고 아무것도 소비하지 않은 채 0을 반환합니다. menu에는 값이 저장되지 않습니다(이전 값 또는 쓰레기 값). 루프가 다시 돌면 scanf는 또 같은 "abc"를 보고 또 실패합니다. 이것이 무한히 반복되며 "메뉴(1~3): "가 화면을 가득 채웁니다.

이렇게 해결합니다 — 반환값 검사 + 줄 비우기

"7"을 입력했을 때는 scanf가 성공(7을 소비)하고 "\n"만 남는데, 비우기 루프가 그 "\n"을 읽고 끝나므로 다음 입력이 정상적으로 됩니다.

주의: 입력 버퍼를 비운다고 fflush(stdin)을 쓰는 코드를 인터넷에서 자주 볼 수 있습니다. C 표준에서 fflush는 출력 스트림에만 정의되어 있으며 입력 스트림에 쓰는 것은 미정의 동작(UB)입니다. 일부 윈도우 컴파일러(구버전 MSVC 런타임)에서만 우연히 동작할 뿐이므로 절대 쓰지 마십시오. 실무에서는 아예 fgets로 한 줄을 통째로 읽은 뒤 strtol로 변환하는 방식을 더 선호합니다(12장).

여기서 잠깐 — 빈 본문 반복문 표기

위의 while (...) ;처럼 본문이 빈 반복문은 앞서 "실수"로 소개했던 모양과 똑같습니다. 의도적인 경우에는 세미콜론을 다음 줄에 따로 쓰거나 { } 또는 /* empty */ 주석을 달아 "일부러 비웠다"는 것을 드러내는 것이 좋은 관례입니다.

goto와 에러 처리 관용구

goto 레이블;은 같은 함수 안의 레이블: 위치로 무조건 점프합니다. 1968년 다익스트라의 논문 "Go To Statement Considered Harmful" 이후 goto는 스파게티 코드의 주범으로 지목되어 왔고, 일반적인 반복과 분기에 goto를 쓰는 것은 금지에 가깝습니다. 하지만 C에서는 예외적으로 널리 인정되는 용도가 두 가지 있습니다.

  1. 중첩 반복의 한 번에 탈출: 플래그 변수 없이 깔끔하게 빠져나갈 수 있습니다.
  2. 에러 처리와 자원 정리(cleanup): 여러 단계에서 자원(파일, 메모리, DB 연결)을 얻는 함수에서, 어느 단계에서 실패하든 이미 얻은 자원을 역순으로 해제하는 코드로 모으는 관용구입니다. 리눅스 커널 코드에서 매우 흔히 쓰입니다.

왜 그럴까? — 왜 이 경우엔 goto가 더 나을까

goto 없이 같은 일을 하려면 실패 지점마다 "지금까지 얻은 자원 해제" 코드를 복사하거나(1단계 실패: 없음, 2단계 실패: in 닫기, 3단계 실패: out, in 닫기...), if를 깊게 중첩해야 합니다. 복사된 정리 코드는 단계가 추가될 때 한 곳을 빠뜨리기 쉽고, 그 결과가 자원 누수(파일 핸들 고갈, 메모리 누수)입니다. 24시간 돌아가는 금융 서버에서 거래 한 건마다 파일 핸들 하나가 새면 며칠 뒤 "Too many open files"로 서비스가 멈춥니다. goto cleanup 패턴은 정리 코드를 한 곳에 모아 이 문제를 구조적으로 막습니다. C++의 소멸자(RAII), Java의 try-finally가 언어 차원에서 해결하는 문제를 C에서는 이 관용구로 해결하는 것입니다.

goto 사용 규칙

  • 앞으로(아래로)만 점프합니다. 뒤로 점프해 반복을 만들지 않습니다(그건 반복문의 일입니다).
  • 레이블은 함수 끝부분의 정리 코드나 반복 탈출 직후에만 둡니다.
  • 변수 선언과 초기화를 건너뛰는 점프에 주의합니다. 특히 가변 길이 배열(VLA)의 선언 범위 안으로 점프하는 것은 금지(제약 위반)입니다.
  • 팀 코딩 표준이 goto를 금지한다면 따릅니다. MISRA C는 goto를 권고 규칙으로 제한하고 있습니다.

핵심 정리

  • 반복문은 기계어에서 "조건 검사 + 뒤로 점프"입니다. 모든 반복에는 초기화, 조건, 본문, 갱신의 네 요소가 있습니다.
  • while과 for는 조건을 먼저 검사(0회 가능), do-while은 본문을 먼저 실행(최소 1회)합니다. do-while 끝에는 세미콜론이 필요합니다.
  • for의 실행 순서는 초기식(1회) → [조건 → 본문 → 증감식] 반복입니다. 반복이 끝난 뒤 카운터는 조건을 처음 만족하지 못한 값입니다.
  • 무한 루프의 원인: 갱신 누락, 갱신 방향 반대, 실수 != 비교, unsigned의 >= 0 비교, while/for 뒤 세미콜론.
  • off-by-one: [0, n)은 n회, [0, n]은 n+1회. 경계(시작 포함/끝 포함)를 설계서와 대조합니다.
  • break는 가장 안쪽 반복(또는 switch) 하나만 탈출합니다. continue는 for에서는 증감식으로, while에서는 조건으로 갑니다.
  • 중첩 반복의 실행 횟수는 곱으로 늘어나 O(n2)이 되기 쉽습니다.
  • 최대·최소는 0이 아니라 첫 데이터(또는 LLONG_MIN/MAX)로 초기화합니다. 평균은 0건 검사와 형변환 위치에 주의합니다.
  • 소수 판별은 √n까지(d * d <= n)만 나눠 봅니다.
  • 금융 계산(복리, 상환 스케줄)은 매 기간 정수 원 단위로 절사하며 반복하는 것이 실제 통장과 일치하며, 마지막 회차에서 끝전을 정리합니다.
  • scanf 실패 시 입력이 버퍼에 남습니다. 반환값을 검사하고 getchar로 줄을 비웁니다. fflush(stdin)은 UB입니다.
  • goto는 중첩 반복 탈출과 goto cleanup 에러 처리 관용구에서만 제한적으로 사용합니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. while과 do-while의 차이는 무엇이고 각각 언제 쓰나요?

while은 조건을 먼저 검사하므로 본문이 0번 실행될 수 있고, do-while은 본문을 먼저 실행한 뒤 검사하므로 최소 1번 실행됩니다. 메뉴 출력이나 입력을 일단 받고 검증하는 경우에는 do-while이, 파일 끝까지 읽기처럼 처음부터 조건이 거짓일 수 있는 경우에는 while이 적합합니다.

꼬리 질문 대비: "매크로에서 do { ... } while (0)을 쓰는 이유는?" — 여러 문장으로 된 매크로를 하나의 문장처럼 만들어 if-else 안에서 써도 안전하게 하기 위함입니다(17장).

Q2. for문에서 continue를 만나면 어디로 가나요? while과 다른 점은?

for문에서는 증감식으로 이동한 뒤 조건을 검사합니다. while문에는 증감식 자리가 없으므로 곧바로 조건 검사로 가며, 그래서 본문 끝에 둔 카운터 증가가 건너뛰어져 무한 루프가 생길 수 있습니다. for를 while로 변환할 때 continue가 있으면 동작이 같지 않다는 것이 포인트입니다.

Q3. off-by-one 오류란 무엇이고 어떻게 예방하나요?

반복 횟수나 인덱스 경계가 1만큼 어긋나는 오류로, <와 <=의 혼동, 0부터인지 1부터인지의 혼동에서 생깁니다. 반열린 구간 [0, n) 관용구를 일관되게 쓰고, 경계값(0, 1, n-1, n)으로 테스트하며, 루프 불변식을 주석으로 명시하는 방법으로 예방합니다. 배열에서는 범위 밖 접근이라는 UB로 이어지므로 더 치명적입니다.

Q4. 무한 루프는 언제 의도적으로 쓰나요? CPU를 100% 쓰지 않으려면?

서버의 요청 대기 루프, 임베디드의 메인 루프, 배치 데몬처럼 종료 신호가 올 때까지 계속 동작하는 프로그램에서 while(1)이나 for(;;)로 씁니다. 이때 루프 안에서 아무 대기 없이 상태를 계속 확인하면(busy waiting) CPU를 100% 점유하므로, accept/read/select 같은 블로킹 호출이나 sleep, 조건 변수로 대기해 CPU를 양보해야 합니다.

Q5. goto는 왜 나쁘다고 하나요? 그럼에도 C에서 쓰이는 경우는?

임의 위치로 점프하면 제어 흐름을 추적하기 어려워 스파게티 코드가 되고, 구조적 프로그래밍의 원칙(순차·선택·반복)을 깨기 때문입니다. 그러나 C에는 예외 처리나 소멸자가 없어서, 여러 자원을 획득하는 함수에서 실패 시 정리 코드로 한 번에 점프하는 goto cleanup 패턴과 다중 루프 탈출에는 오히려 가독성과 안전성을 높이는 용도로 널리 쓰이며 리눅스 커널에서도 표준 관용구입니다.

Q6. 이중 for문의 시간 복잡도는? 더 줄일 수 있는 방법은?

각각 n번이면 O(n2)이고, 안쪽이 바깥 인덱스부터 시작하는 삼각형 형태(j = i+1 ~ n)여도 n(n-1)/2번이므로 여전히 O(n2)입니다. 중복 찾기라면 정렬 후 인접 비교로 O(n log n), 해시 테이블로 평균 O(n)으로 줄일 수 있습니다.

Q7. 루프 언롤링(loop unrolling)이란?

반복 본문을 여러 번 복사해 반복 횟수를 줄이는 최적화로, 조건 검사와 점프 횟수를 줄이고 CPU 파이프라인과 SIMD 활용을 높입니다. 대신 코드 크기가 커져 명령어 캐시 효율이 나빠질 수 있습니다. 보통 -O2/-O3 최적화에서 컴파일러가 자동으로 수행하므로 직접 할 일은 드뭅니다.

Q8. 부동소수점을 루프 카운터로 쓰면 안 되는 이유는?

0.1 같은 값은 2진수로 정확히 표현되지 않아 누적 오차가 생기므로, 반복 횟수가 예상과 달라지거나 != 비교에서 무한 루프가 생길 수 있습니다. 정수 카운터로 반복하고 실수 값은 k * step처럼 계산하는 것이 안전합니다. 같은 이유로 금융 금액도 정수로 다룹니다.

Q9. 배치 프로그램에서 수백만 건을 루프로 처리할 때 고려할 점은?

건별 오류가 전체를 중단시키지 않도록 오류 건은 기록 후 continue하고, 일정 건수마다 커밋해 재시작 지점(체크포인트)을 남기며, 합계·건수를 집계해 원천 데이터와 대사(reconciliation)합니다. 또한 루프 안의 불필요한 I/O나 DB 조회를 줄이고, 오버플로를 막기 위해 합계는 충분히 큰 자료형을 씁니다.

문제 7 (금융 응용 — 적금 시뮬레이션) 난이도 ★★★

매월 초 30만원씩 12개월 적금을 붓습니다. 월 이율 0.25%(25bp)로 매월 말 잔액에 이자를 붙여(원 미만 절사) 원금에 편입한다고 할 때, 12개월 후 잔액, 총 납입액, 총 이자를 출력하세요.

정답과 해설 보기

매달 ① 납입 → ② 이자 계산·편입 순서로 반복합니다. 순서를 바꾸면(이자 먼저) 첫 달 이자가 0이 되어 결과가 달라지므로, 업무 규칙의 순서를 코드 순서에 그대로 반영해야 합니다.

1개월 차를 손으로 추적하면 300000 → 이자 750 → 300750, 2개월 차는 600750 → 이자 1501 → 602251입니다. 결과를 받으면 반드시 상식으로 타당성을 검증하십시오. 잔액은 납입액보다 커야 하고, 이자는 대략 "평균 잔액 × 월이율 × 개월 수"와 비슷해야 합니다. 평균 잔액은 약 195만원(첫 달 30만 ~ 마지막 달 360만의 평균)이므로 195만 × 0.0025 × 12 ≈ 58,500원으로, 실제 결과 59,032원과 잘 맞습니다(차이는 복리 효과). 이런 어림 검증 습관이 금융 개발자의 실수를 크게 줄여 줍니다.

문제 8 (입력 검증) 난이도 ★★☆

이체 금액을 입력받되, 숫자가 아니거나 1원 미만, 또는 1회 한도 5,000,000원 초과이면 사유를 출력하고 다시 입력받으세요. 최대 3번까지만 재시도하고, 3번 모두 실패하면 "거래 취소"를 출력하세요.

정답과 해설 보기

시도 횟수 카운터를 둔 for 루프에서 성공하면 break합니다. 반복 후에 "성공해서 끝났는지, 횟수를 다 써서 끝났는지"를 구분하기 위해 플래그(또는 카운터 값)를 확인합니다.

문제 9 (금융 응용 — 원금균등 상환) 난이도 ★★★

원금균등 상환은 매달 원금을 똑같이 나눠 갚고 이자는 잔액에 대해 따로 냅니다. 1,200만원, 연 6%(월 50bp), 12개월일 때 회차별 원금·이자·상환액·잔액을 출력하고, 원리금균등(본문 ex06-12) 방식과 총 이자를 비교하세요.

정답과 해설 보기

매달 원금 상환분 = 12,000,000 / 12 = 1,000,000원(나누어떨어지지 않으면 마지막 회차에서 끝전 정리). 이자 = 잔액 × 50 / 10000.

이자는 60000, 55000, 50000, ..., 5000이므로 총 이자 = 5000 × (12+11+...+1) = 5000 × 78 = 390,000원입니다. 원리금균등의 393,561원보다 적습니다. 원금을 초기에 더 많이 갚아 잔액이 빨리 줄기 때문입니다. 대신 초기 상환 부담(1회차 106만원)이 원리금균등(약 103만원)보다 큽니다.

i: 1(+1), 2(+2), 3(skip), 4(+4), 5(+5), 6(skip), 7(+7), 8 → 8 % 3 ≠ 0이고 8 > 7이므로 break. s = 1+2+4+5+7 = 19.

문제 11 (코드 작성 — 소수 개수) 난이도 ★★☆

문제 12 (버그 찾기 — 무한 루프) 난이도 ★★☆

다음 코드가 끝나지 않는 이유를 설명하고 고치세요.

정답과 해설 보기

unsigned는 0보다 작아질 수 없어 i >= 0이 항상 참입니다. 0에서 1을 빼면 4294967295로 감싸집니다(정의된 동작). 해결: int i로 바꾸거나, unsigned를 유지하려면 for (i = 11; i-- > 0; ) 관용구를 씁니다. 이 관용구는 검사 시 옛값(11~1)을 비교하고, 본문에서는 감소된 값(10~0)을 사용합니다.
