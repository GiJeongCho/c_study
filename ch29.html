DB 연동과 트랜잭션

은행의 진짜 돈은 C 프로그램의 변수가 아니라 데이터베이스의 원장 테이블에 있습니다. 계정계 C 프로그램의 대부분은 "DB에서 읽고, 계산하고, DB에 쓰고, 커밋한다"입니다. 이 장에서는 C 코드 안에 SQL을 직접 쓰는 Embedded SQL(Pro*C)과, 돈이 사라지거나 두 번 생기지 않게 지켜 주는 트랜잭션, 그리고 수천 건의 거래를 동시에 처리하는 TP 모니터 구조를 익힙니다.

이 장의 코드에 대하여

Pro*C와 TP 모니터는 상용 제품(Oracle 데이터베이스와 프리컴파일러, Tuxedo 계열 TP 모니터)이 설치된 환경에서만 빌드됩니다. 이 장의 코드는 Oracle 문법을 기준으로 개념적으로 정확하게 작성했지만, 여러분의 PC에서 바로 컴파일되지는 않을 수 있습니다. 대신 각 코드가 전처리 후 어떤 C 코드가 되는지, DB에서 어떤 일이 벌어지는지를 그림과 함께 자세히 설명합니다. 실무에 들어가면 회사의 개발 서버에서 같은 코드를 그대로 써 볼 수 있습니다. 테이블은 다음 두 개를 가정합니다.

29-1Embedded SQL(Pro*C)

C 프로그램이 데이터베이스를 쓰는 방법은 크게 두 가지입니다. 하나는 OCI(Oracle Call Interface)나 ODBC 같은 함수 호출 API로, SQL 문자열을 만들어 라이브러리 함수에 넘기고, 결과를 함수로 하나씩 꺼내는 방식입니다. 다른 하나는 C 소스 안에 SQL을 그대로 섞어 쓰는 Embedded SQL입니다. Oracle의 Embedded SQL 구현이 Pro*C/C++이며, 국내 금융권 계정계 C 프로그램의 상당수가 이 방식으로 작성되어 있습니다. SQL을 SQL답게 읽을 수 있고, C 변수와 컬럼을 직접 연결할 수 있어 업무 로직이 한눈에 보이기 때문입니다.

Pro*C 전처리 과정: .pc에서 실행 파일까지

C 컴파일러는 EXEC SQL SELECT ... 같은 문장을 이해하지 못합니다. 그래서 컴파일 전에 프리컴파일러(precompiler) proc가 .pc 파일을 읽어, EXEC SQL 문장을 Oracle 런타임 라이브러리 함수 호출(sqlcxt 등)로 바꾼 순수 C 파일(.c)을 만듭니다. 그다음은 우리가 아는 일반 C 빌드 과정입니다.

왜 프리컴파일러가 필요할까?

SQL과 C는 서로 다른 언어입니다. DB 서버는 SQL 문자열을 받아 파싱하고, 실행 계획을 세우고, 결과를 네트워크로 돌려줍니다. C 프로그램이 이를 하려면 "이 SQL 문자열을 보내고, 바인드 변수 1번은 이 메모리 주소의 8바이트 정수이고, 결과 1번 컬럼은 저 주소에 최대 40바이트로 받아라" 같은 정보를 런타임 라이브러리에 일일이 알려 줘야 합니다. OCI로 직접 쓰면 SELECT 하나에 수십 줄의 함수 호출이 필요합니다. 프리컴파일러는 이 지루하고 실수하기 쉬운 코드를 자동으로 생성해 줍니다. sqlcheck=semantics를 주면 빌드 시점에 DB에 접속해 테이블·컬럼 이름과 타입까지 검사하므로 오타가 운영에서야 발견되는 일을 줄여 줍니다. 생성된 .c 파일은 사람이 읽기 어렵고 다시 생성되므로 절대 직접 수정하지 않습니다.

EXEC SQL과 호스트 변수

C 변수 중 SQL 문장 안에서 쓰는 변수를 호스트 변수(host variable)라고 합니다. SQL 안에서는 이름 앞에 콜론(:)을 붙여 C 변수임을 표시합니다. 호스트 변수는 BEGIN DECLARE SECTION과 END DECLARE SECTION 사이에 선언하는 것이 전통적인 방식입니다(최신 Pro*C는 옵션에 따라 생략도 가능하지만, 명시하는 편이 이식성과 가독성이 좋습니다).

왜 char 배열 크기를 컬럼 길이 + 1로 잡을까?

Pro*C의 기본 설정(char_map=charz, MODE=ORACLE)에서 char[n] 호스트 변수는 널 종료 문자열로 취급됩니다. 컬럼 값을 받을 때 오른쪽을 공백으로 채우고 마지막에 '\0'을 붙입니다. 따라서 VARCHAR2(40)을 손실 없이 받으려면 41바이트가 필요합니다. 배열이 작으면 값이 잘리고(truncation), 지시자 변수가 없으면 경고 플래그만 남거나 오류가 됩니다. 한글은 DB 문자셋(AL32UTF8이면 한글 한 글자가 3바이트)에 따라 바이트 수가 달라지므로, 컬럼 길이가 BYTE 단위인지 CHAR 단위인지까지 확인해 넉넉히 잡아야 합니다. 18장에서 배운 "문자열 버퍼에는 항상 널 문자 자리"가 DB에서도 그대로 적용되는 것입니다.

NUMBER와 C 타입의 대응

Oracle NUMBER는 최대 38자리 십진수입니다. 금액 컬럼 NUMBER(15)는 C의 long long(최대 약 9.2×1018)에 안전하게 들어갑니다. 소수가 있는 이율 같은 컬럼을 double로 받으면 부동소수점 오차가 생기므로(7장), 금융 계산에서는 이율을 "만분율 정수"로 저장하거나 문자열로 받아 고정소수점으로 처리하는 경우가 많습니다. int(4바이트)로 금액을 받으면 21억 원을 넘는 순간 오류(ORA-01455 등)나 오버플로가 나니 금액은 무조건 long long입니다.

지시자 변수로 NULL 처리하기

DB의 NULL은 "값이 없음"이라는 특별한 상태입니다. 그런데 C의 char나 long long에는 "값 없음"을 나타낼 방법이 없습니다. 0은 0원이라는 값이고, 빈 문자열도 값입니다. 그래서 Pro*C는 호스트 변수 옆에 지시자 변수(indicator variable)라는 short 변수를 짝지어 NULL 여부를 따로 알려 줍니다.

NULL이 될 수 있는 컬럼을 지시자 없이 받으면, 기본 설정(UNSAFE_NULL=NO)에서는 ORA-01405: fetched column value is NULL 오류(sqlcode -1405)가 납니다. 개발 DB에서는 모든 데이터가 채워져 있어 통과했다가, 운영의 오래된 계좌 하나에 NULL이 있어 야간 배치가 그 지점에서 멈추는 일이 흔합니다. 또 지시자가 -1일 때 호스트 변수에는 이전 FETCH의 값이 그대로 남아 있으므로, 지시자를 확인하지 않고 호스트 변수를 쓰면 앞 계좌의 날짜가 다음 계좌에 찍힙니다. 해결: 테이블 정의서에서 NULL 허용 컬럼을 모두 찾아 지시자를 붙이거나, SQL에서 NVL(LAST_TX_DT, ' ')처럼 기본값으로 바꿔 받습니다.

VARCHAR 호스트 변수

Pro*C는 VARCHAR라는 특별한 의사 타입을 제공합니다. 프리컴파일러가 이를 길이와 바이트 배열을 가진 구조체로 바꿔 줍니다.

VARCHAR는 널 문자로 끝나지 않습니다. 길이는 len 필드에 따로 있습니다. 그래서 다음 규칙을 반드시 지켜야 합니다.

왜 VARCHAR라는 타입이 따로 있을까?

C 문자열은 "0바이트를 만날 때까지"가 길이라서 길이를 알려면 매번 처음부터 세어야 하고, 데이터 안에 0바이트가 있으면 표현할 수 없습니다. DB의 VARCHAR2는 길이와 내용을 따로 관리합니다. Pro*C의 VARCHAR는 DB 쪽 표현과 같은 "길이 + 바이트" 모양이라 변환 없이 주고받을 수 있고, CHAR 컬럼의 오른쪽 공백 채움 같은 혼란도 없습니다. 대신 C 표준 문자열 함수(strlen, printf("%s"))를 바로 쓸 수 없다는 대가가 있습니다. 실무에서 가장 흔한 버그가 len 설정을 빠뜨려 이전 길이로 검색하는 것과, arr[len] = '\0'을 했는데 len이 배열 크기와 같아 바로 옆 변수를 덮어쓰는 것입니다.

매 SQL마다 if문을 쓰는 대신 WHENEVER 지시문으로 오류 처리를 일괄 지정할 수도 있습니다.

WHENEVER는 실행 흐름이 아니라 소스 위치 기준

WHENEVER는 함수 호출처럼 런타임에 동작하는 것이 아니라, 프리컴파일러가 소스 파일에서 그 지시문 아래에 나오는 EXEC SQL 문장들에 검사 코드를 끼워 넣는 방식입니다. 그래서 파일 위쪽 함수에 쓴 WHENEVER가 파일 아래쪽 다른 함수에도 적용되고, if문 안에 써도 조건과 무관하게 이후 모든 문장에 적용됩니다. WHENEVER NOT FOUND GOTO end_loop;를 썼는데 그 레이블이 없는 다른 함수에서 컴파일 오류가 나는 것이 흔한 혼란입니다. 많은 팀이 WHENEVER는 CONTINUE로 두고 매 SQL 직후 sqlcode를 명시적으로 검사하는 규칙을 씁니다. 코드가 길어지는 대신 흐름이 명확합니다.

사고 사례: 무시된 sqlcode 하나가 만든 이중 입금

한 이자 지급 배치는 거래내역 INSERT 후 잔액 UPDATE를 하도록 되어 있었는데, INSERT의 sqlcode를 검사하지 않았습니다. 어느 날 배치가 중간에 비정상 종료되어 운영자가 재실행했고, 이미 처리된 계좌의 거래내역 INSERT는 ORA-00001(중복 키)로 실패했지만 코드는 이를 무시하고 잔액 UPDATE를 그대로 수행했습니다. 결과적으로 수천 계좌에 이자가 두 번 입금되었고, 거래내역에는 한 번만 남아 원장과 내역이 불일치했습니다. 다음 날 대사 작업에서 발견되어 회수 처리에 며칠이 걸렸습니다. 재발 방지책은 (1) 모든 SQL 직후 sqlcode 검사 의무화와 정적 분석 규칙 추가, (2) 배치의 재실행 안전성(멱등성) 확보 — 처리 완료 여부를 먼저 확인하고 건너뛰는 로직, (3) 내역 INSERT와 잔액 UPDATE를 같은 트랜잭션으로 묶어 함께 커밋/롤백하는 것이었습니다.

커서와 FETCH 루프

단건 SELECT INTO는 결과가 정확히 한 행일 때만 씁니다. 결과가 0행이면 1403, 두 행 이상이면 ORA-01422(exact fetch returns more than requested number of rows) 오류입니다. 여러 행을 처리하려면 커서(cursor)를 씁니다. 커서는 결과 집합 위를 움직이는 "책갈피"입니다.

날짜를 YYYYMMDD 문자열로 저장하는 이유

위 코드의 LAST_TX_DT < :h_base_dt에서 보듯 SQL 안의 문자열 비교는 CHAR(8) 'YYYYMMDD' 형식이라 사전순 비교가 곧 날짜 비교가 됩니다. 날짜를 'YYYYMMDD' 고정 길이 문자열로 저장하는 관행은 이 성질 덕분입니다. 'MM/DD/YYYY' 같은 형식이었다면 문자열 비교가 날짜 순서와 달라 대상 계좌가 틀어집니다.

배열 FETCH로 배치 성능 끌어올리기

위의 FETCH 루프는 100만 계좌를 처리하면 FETCH를 100만 번 호출합니다. FETCH 한 번마다 애플리케이션 서버와 DB 서버 사이에 네트워크 왕복(round trip)이 일어나고, 같은 데이터센터 안이라도 왕복 한 번에 0.2~0.5밀리초가 걸립니다. 100만 번이면 왕복 대기만 3~8분입니다. 배열 FETCH는 호스트 변수를 배열로 선언해 한 번에 수백~수천 행을 가져옵니다.

자주 하는 실수: 1403을 받자마자 break

배열 FETCH에서 1403은 "이번 FETCH에서 배열을 다 채우지 못했다(데이터가 끝났다)"는 뜻이지 "이번에 한 행도 없다"는 뜻이 아닙니다. 1,234행이면 500, 500을 받고 세 번째 FETCH는 234행을 받으면서 동시에 1403을 반환합니다. 단건 FETCH 습관대로 if (sqlcode == 1403) break;를 처리 전에 두면 마지막 234행이 조용히 누락됩니다. 배치 결과 건수가 매번 "조금씩" 모자라는데 오류 로그는 없는, 찾기 매우 어려운 버그입니다. 위 코드처럼 누적 행 수 차이로 이번 회차 행 수를 구하고, 처리한 뒤에 종료합니다.

대용량 배치와 커밋 주기

위 코드는 마지막에 한 번만 커밋합니다. 100만 행을 하나의 트랜잭션으로 처리하면 언두(UNDO) 공간이 커지고, 중간 실패 시 전부 롤백되어 처음부터 다시 해야 합니다. 그래서 실무 배치는 1만 행 단위 등으로 중간 커밋하고 "어디까지 처리했는지"(마지막 계좌번호)를 재시작 테이블에 함께 커밋해, 실패 시 그 지점부터 이어서 처리합니다. 단 커서를 연 상태로 같은 테이블을 갱신하며 오래 커밋을 반복하면 ORA-01555(snapshot too old)가 날 수 있어, 키 범위로 나누어 커서를 다시 여는 방식을 함께 씁니다.

동적 SQL과 바인드 변수, SQL 인젝션 방지

지금까지의 SQL은 프리컴파일 시점에 문장이 정해진 정적 SQL입니다. 조회 화면에서 "조건이 입력된 항목만 WHERE에 넣기"처럼 실행 시점에 SQL 문장이 정해지는 경우 동적 SQL을 씁니다. Pro*C는 네 가지 방법을 제공합니다.

왜 바인드 변수는 인젝션에 안전할까?

DB는 SQL을 파싱(문법 분석과 실행 계획 수립)한 뒤, 실행할 때 바인드 변수 자리에 값을 끼워 넣습니다. 바인드 값은 파싱이 끝난 뒤에 "데이터"로만 전달되므로, 그 안에 ' OR '1'='1이 들어 있어도 SQL 문법의 일부가 될 수 없고 그냥 "그런 이름을 가진 고객"을 찾을 뿐입니다. 반면 문자열 연결은 값이 파싱 전에 SQL 텍스트에 섞이므로, 값이 SQL의 구조를 바꿀 수 있습니다. 이것이 핵심 차이입니다. 덤으로 성능 이점도 큽니다. 값만 다른 같은 SQL은 텍스트가 동일하므로 DB가 공유 풀에서 실행 계획을 재사용(소프트 파싱)합니다. 값을 문자열로 붙이면 계좌번호마다 다른 SQL이 되어 매번 하드 파싱이 일어나고, 초당 수천 건의 온라인 거래에서는 DB CPU와 공유 풀 래치 경합으로 전체가 느려집니다.

바인드 변수로 바꿀 수 없는 것

바인드 변수는 값 자리에만 쓸 수 있습니다. 테이블명, 컬럼명, ORDER BY 대상 컬럼, ASC/DESC 같은 SQL 구조는 바인드할 수 없습니다. 이런 것을 사용자 입력으로 정해야 한다면, 입력값을 SQL에 직접 넣지 말고 허용 목록(whitelist)과 비교해 미리 정해 둔 문자열 중 하나를 고르게 하십시오. 예: 정렬 기준 코드 "1"이면 "ORDER BY ACCT_NO", "2"면 "ORDER BY BAL DESC", 그 외는 오류.

은행 시스템에서는: 보안 점검 단골 항목

금융권은 정기적인 취약점 점검과 소스 코드 보안 점검을 받습니다. 동적 SQL에서 sprintf로 사용자 입력을 연결한 코드는 거의 항상 지적 대상입니다. 내부 관리자 화면이라도 예외가 아닙니다. 실무 규칙은 단순합니다. (1) 정적 SQL을 우선한다, (2) 동적 SQL이 필요하면 구조만 동적으로 만들고 값은 모두 바인드한다, (3) 구조를 바꾸는 입력은 허용 목록으로만 받는다, (4) 동적 SQL을 쓴 곳에는 왜 정적 SQL로 안 되는지 주석을 단다.

29-1 한 줄 요약

Pro*C는 EXEC SQL을 라이브러리 호출로 바꿔 주는 프리컴파일러입니다. 호스트 변수 크기는 널 문자까지, NULL 가능 컬럼에는 지시자, 모든 SQL 뒤에는 sqlcode 검사, 대량 처리는 배열 FETCH, 값은 반드시 바인드 변수로 전달합니다.

29-2트랜잭션과 TP 모니터

28장에서 우리는 mutex로 "두 계좌의 잔액을 한 덩어리로" 바꾸는 법을 배웠습니다. 하지만 mutex는 한 프로세스의 메모리만 보호합니다. 프로그램이 이체 도중 죽으면? 서버 전원이 나가면? 여러 서버의 여러 프로세스가 같은 계좌를 만지면? 이 모든 상황에서 "돈이 사라지거나 두 번 생기지 않음"을 보장하는 장치가 데이터베이스의 트랜잭션입니다. 이 절에서는 트랜잭션의 성질과 C 코드에서의 사용법, 동시성 제어(락)와 격리 수준, 그리고 대규모 온라인 시스템의 뼈대인 TP 모니터를 다룹니다.

트랜잭션과 ACID

트랜잭션(transaction)은 "모두 성공하거나 모두 없던 일이 되어야 하는" 작업의 논리적 단위입니다. 계좌이체라면 "A 출금 + B 입금 + 거래내역 2건 기록"이 하나의 트랜잭션입니다. 트랜잭션은 다음 네 가지 성질, ACID를 보장합니다.

왜 커밋이 "디스크에 데이터를 다 쓰는 것"이 아닌데도 지속성이 보장될까?

데이터 파일의 블록을 매번 디스크에 쓰면 너무 느립니다(테이블, 인덱스 여기저기의 무작위 쓰기). 그래서 DB는 변경 내용을 리두 로그라는 순차 파일에 먼저 기록하고, 커밋 시점에는 이 로그가 디스크에 확실히 기록(fsync)된 것만 확인합니다. 이를 WAL(Write-Ahead Logging)이라고 합니다. 데이터 블록은 나중에 천천히 씁니다. 장애가 나면 재기동 시 리두 로그를 재생해 커밋된 변경을 복구하고(roll forward), 커밋되지 않은 변경은 언두 정보로 되돌립니다(roll back). 순차 쓰기 한 번은 무작위 쓰기 여러 번보다 훨씬 빠르기 때문에 이 방식이 성능과 지속성을 동시에 잡습니다. 커밋 응답 시간의 상당 부분이 이 "로그 디스크 기록 대기"이므로, 건마다 커밋하는 배치가 느린 이유이기도 합니다.

이체 트랜잭션: COMMIT과 ROLLBACK

Oracle에서는 첫 번째 DML(INSERT/UPDATE/DELETE)이 실행될 때 트랜잭션이 암묵적으로 시작되고, COMMIT이나 ROLLBACK으로 끝납니다. 이제 실무 수준의 이체 함수를 Pro*C로 작성해 봅시다.

왜 UPDATE 후 sqlerrd[2]가 1인지까지 확인할까?

UPDATE는 조건에 맞는 행이 0개여도 오류가 아닙니다(sqlcode 0, 처리 행 수 0). 계좌번호에 공백이 섞였거나 앞의 SELECT와 다른 변수를 바인드하는 실수가 있으면, 출금 UPDATE는 1행, 입금 UPDATE는 0행인 채로 "성공"해서 커밋되어 돈이 증발합니다. 금융 코드에서는 "몇 행이 바뀌어야 하는지"를 알고 있다면 반드시 행 수까지 검증합니다. 이것이 sqlcode만 보는 코드와 베테랑 코드의 차이입니다.

SAVEPOINT: 부분 롤백

EXEC SQL SAVEPOINT sp_fee;로 중간 지점을 표시하고 EXEC SQL ROLLBACK TO SAVEPOINT sp_fee;로 그 이후만 되돌릴 수 있습니다. 예를 들어 "이체는 진행하되 수수료 우대 쿠폰 적용이 실패하면 쿠폰 부분만 취소하고 일반 수수료로 처리" 같은 경우에 씁니다. 세이브포인트로 되돌려도 트랜잭션은 계속 열려 있으므로 마지막에 COMMIT이나 ROLLBACK을 해야 합니다.

자주 하는 실수: 커밋 없이 종료, 그리고 RELEASE

Pro*C 프로그램이 COMMIT 없이 정상 종료하면 Oracle 클라이언트 동작에 따라 커밋될 수도 롤백될 수도 있어(버전과 설정에 따라 다름) 의존하면 안 됩니다. 비정상 종료(세그폴트)면 연결이 끊기며 DB가 롤백합니다. 배치 마지막에는 EXEC SQL COMMIT WORK RELEASE;(커밋하고 연결 해제)를, 오류 종료 시에는 EXEC SQL ROLLBACK WORK RELEASE;를 명시하십시오. 또 COMMIT 직전에 프로그램이 죽으면 그 트랜잭션은 롤백되므로, 온라인 거래에서는 "응답을 받지 못한 거래"가 실제로 처리되었는지 거래 추적 ID로 조회하는 결과 확인 거래가 필요합니다(30장).

왜 Oracle의 조회는 갱신을 기다리지 않을까? (MVCC)

Oracle은 다중 버전 동시성 제어(MVCC)를 씁니다. 행을 수정하면 이전 값을 언두 영역에 보관하고, 다른 세션이 그 행을 읽으면 "쿼리 시작 시점에 커밋되어 있던 버전"을 언두에서 재구성해 보여 줍니다. 그래서 읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않습니다. 잔액 조회가 아무리 많아도 이체가 느려지지 않는 이유입니다. 대신 일반 SELECT는 락을 걸지 않으므로, 읽은 값을 근거로 갱신하는 코드는 그림 29-5처럼 Lost Update에 노출됩니다. 이를 막는 두 가지 방법이 다음의 비관적 락과 낙관적 락입니다. 또한 해결책 중 가장 간단한 것은 "읽어서 계산해 덮어쓰기" 대신 UPDATE ... SET BAL = BAL - :amt WHERE ACCT_NO = :a AND BAL >= :amt처럼 DB 안에서 원자적으로 계산하고 처리 행 수(0이면 잔액 부족)를 확인하는 것입니다.

SELECT FOR UPDATE: 비관적 락

비관적 락(pessimistic lock)은 "누군가 반드시 끼어들 것이다"라고 보고, 읽는 시점에 미리 행을 잠그는 방식입니다. SELECT ... FOR UPDATE는 조회한 행에 행 단위 배타 락을 걸고, 트랜잭션이 COMMIT/ROLLBACK할 때까지 다른 트랜잭션의 UPDATE와 FOR UPDATE를 대기시킵니다(일반 SELECT는 여전히 막지 않음).

정답과 해설 보기

UPDATE 문장은 대상 행에 배타 락을 건 상태에서 WHERE 조건을 평가하고 값을 바꿉니다. 다른 트랜잭션이 같은 행을 갱신 중이면 그 커밋을 기다린 뒤 최신 값으로 조건을 다시 평가합니다(Oracle의 재시작 동작). 따라서 잔액 확인(BAL >= :amt)과 차감이 하나의 원자적 연산이 되어 TOCTOU 틈이 없고, 애플리케이션이 읽은 옛 값으로 덮어쓰지 않으므로 Lost Update도 없습니다. 판별은 처리 행 수로 합니다.

2단계 커밋: 여러 자원을 하나의 트랜잭션으로

지금까지는 DB 하나 안의 트랜잭션이었습니다. 그런데 예금 원장은 계정계 DB에, 카드 결제 대금은 카드 DB에 있다면? 또는 DB 갱신과 메시지 큐 전송을 "함께 성공하거나 함께 실패"하게 해야 한다면? 서로 다른 자원 관리자(Resource Manager, RM)에 걸친 트랜잭션을 분산 트랜잭션이라고 하며, 이를 원자적으로 끝내는 표준 프로토콜이 2단계 커밋(2PC, Two-Phase Commit)입니다. X/Open의 XA 인터페이스가 그 표준 API이고, TP 모니터가 보통 조정자 역할을 합니다.

  1. 준비 단계: 조정자가 모든 RM에 "커밋할 준비가 되었는가?"를 묻습니다. 각 RM은 변경 내용을 리두 로그에 확실히 기록하고, 이후 어떤 장애가 나도 커밋할 수 있는 상태가 되면 YES를 답합니다. 이 순간부터 RM은 혼자 롤백할 권리를 포기합니다.
  2. 결정 기록: 조정자는 모두 YES면 "커밋" 결정을 자신의 로그에 기록합니다. 이 기록이 트랜잭션의 운명을 확정하는 순간입니다.
  3. 커밋 단계: 조정자가 모든 RM에 커밋을 지시하고, RM은 커밋 후 락을 풉니다. 하나라도 NO였으면 모두에게 롤백을 지시합니다.

왜 "2단계"가 필요할까? 그냥 차례로 커밋하면 안 될까?

RM1을 커밋한 직후 RM2의 커밋이 실패하면(디스크 가득, 제약 위반, 네트워크 단절), RM1은 이미 커밋되어 되돌릴 수 없습니다. 출금은 됐는데 입금이 안 된 상태가 됩니다. 2PC는 "실패할 수 있는 모든 일"을 1단계에서 미리 해 두고 "이제 무슨 일이 있어도 커밋할 수 있다"는 약속만 받은 뒤에 결정을 내립니다. 그래서 2단계의 커밋은 실패할 이유가 없고, 장애가 나도 재기동 후 로그를 보고 커밋을 완료합니다. 대가도 분명합니다. 준비를 마친 RM은 조정자의 결정을 받을 때까지 락을 쥔 채 기다려야 하는데, 그 사이 조정자가 죽으면 그 행들이 결정이 날 때까지 잠긴 상태(in-doubt 트랜잭션)로 남습니다. 이것이 2PC의 블로킹 문제이며, 네트워크 왕복도 두 배라 느립니다. 그래서 대외기관처럼 조직 경계를 넘는 거래에는 2PC 대신 다음에 볼 보상 트랜잭션을 씁니다.

TP 모니터와 계정계 온라인 구조

은행 온라인 시스템에는 영업점 단말, 인터넷·모바일 뱅킹, ATM, 대외기관에서 초당 수천 건의 거래가 들어옵니다. 거래마다 프로세스를 띄우거나 DB 연결을 새로 맺는다면 감당할 수 없습니다. TP 모니터(Transaction Processing Monitor)는 이런 대량 온라인 거래 처리를 위한 미들웨어입니다. Tuxedo가 대표적인 제품이며, 국내 금융권에도 유사한 개념의 제품들이 널리 쓰입니다. 핵심 개념은 다음과 같습니다.

왜 서비스 안에서 COMMIT하지 않을까?

tpbegin으로 시작된 전역 트랜잭션 안에서 여러 서비스(출금 서비스, 수수료 서비스, 원장 서비스)가 호출된다고 합시다. 출금 서비스가 자기 마음대로 COMMIT해 버리면, 뒤의 수수료 서비스가 실패해도 출금은 이미 확정되어 원자성이 깨집니다. 그래서 트랜잭션의 경계(시작과 끝)는 업무 흐름 전체를 아는 쪽 한 곳에서만 정하고, 각 서비스는 자기 일만 하고 성공/실패(TPSUCCESS/TPFAIL)를 보고합니다. 서비스가 TPFAIL을 반환하면 TP 모니터가 전역 트랜잭션을 롤백 전용(rollback-only)으로 표시합니다. 마찬가지로 tpreturn은 C의 return과 달리 함수로 돌아오지 않으므로(내부적으로 longjmp와 유사), 그 뒤에 정리 코드를 두면 실행되지 않습니다.

사고 사례: 타임아웃은 났는데 이체는 됐다

채널계가 tpcall의 블로킹 타임아웃을 10초로, 계정계 서비스의 트랜잭션 타임아웃을 30초로 잡아 둔 시스템이 있었습니다. DB 부하가 높던 날, 이체 서비스가 12초 만에 정상 커밋되었지만 채널계는 이미 10초에 타임아웃으로 고객에게 "이체 실패"를 표시한 뒤였습니다. 고객이 다시 이체해 결국 두 번 출금되었습니다. 원인은 호출자의 타임아웃이 피호출자의 처리 시간보다 짧았던 것과, 타임아웃을 "실패"로 단정한 것입니다. 타임아웃은 "실패"가 아니라 "결과를 모름"입니다. 재발 방지책은 (1) 타임아웃 계층 정렬(바깥쪽이 안쪽보다 길게), (2) 타임아웃 시 고객에게 "처리 결과 확인 중"으로 안내하고 GUID로 결과 조회 거래 수행, (3) 동일 GUID 거래의 중복 처리 방지(거래내역의 GUID 유일 제약)였습니다.

원장과 거래내역 동시 갱신

계정계에서 거의 모든 거래는 두 종류의 데이터를 함께 바꿉니다. 원장(마스터)은 계좌의 현재 상태(잔액)이고, 거래내역은 어떤 거래로 잔액이 변했는지에 대한 기록입니다. 이 둘은 항상 맞아야 합니다. "어제 잔액 + 오늘 거래내역의 입금 합계 - 출금 합계 = 오늘 잔액"이라는 등식이 깨지면 대사 오류입니다. 이를 지키는 실무 원칙은 다음과 같습니다.

  1. 같은 트랜잭션: 원장 UPDATE와 거래내역 INSERT는 반드시 하나의 트랜잭션에서 함께 커밋합니다. 따로 커밋하면 그 사이 장애 시 불일치가 생깁니다.
  2. 원장 락 먼저: 원장 행을 먼저 잠그고(FOR UPDATE 또는 조건부 UPDATE), 그 잔액을 기준으로 거래 후 잔액을 계산해 거래내역에 기록합니다. 락 없이 읽은 잔액으로 거래 후 잔액을 기록하면, 동시 거래 시 내역의 "거래 후 잔액"이 서로 꼬입니다.
  3. 일련번호 채번: 계좌별 거래 일련번호를 원장 행의 컬럼으로 두고 UPDATE ... SET LAST_SEQ = LAST_SEQ + 1로 원장 락 안에서 채번하면, 계좌별로 빈틈없이 연속된 번호를 얻습니다(시퀀스 객체는 롤백 시 번호가 비는 것을 허용).
  4. 중복 방지 키: 거래내역에 거래 추적 ID(GUID)나 "채널+전문번호"의 유일 제약을 두어, 재전송된 같은 거래가 두 번 처리되지 않게 합니다(ORA-00001이 곧 중복 거래 탐지).
  5. 대사 배치: 매일 마감 후 원장 잔액과 거래내역 합계를 비교하는 배치를 돌려, 어떤 경로로든 생긴 불일치를 다음 날 영업 전에 찾아냅니다.

보상 트랜잭션: 되돌릴 수 없을 때 되돌리는 법

타행 이체를 생각해 봅시다. 우리 은행에서 출금하고, 대외기관 망을 통해 다른 은행에 입금을 요청합니다. 다른 은행의 DB는 우리가 2PC로 묶을 수 없습니다. 조직도 다르고, 상대가 응답하지 않는 동안 우리 고객 계좌의 락을 쥐고 기다릴 수도 없습니다. 그래서 각 단계를 독립된 로컬 트랜잭션으로 커밋하고, 뒤 단계가 실패하면 앞 단계의 효과를 반대 거래로 상쇄합니다. 이 반대 거래를 보상 트랜잭션(compensating transaction)이라고 하며, 이런 단계별 커밋과 보상의 연쇄를 사가(Saga) 패턴이라고도 부릅니다.

왜 보상은 "ROLLBACK"이 아니라 "반대 거래"일까?

T1은 이미 커밋되어 다른 트랜잭션들이 그 결과를 보았을 수 있습니다(고객이 잔액을 조회했고, 그 뒤 다른 출금도 있었을 수 있음). 커밋된 과거를 지울 수는 없습니다. 그래서 금융에서는 기록을 지우지 않고 "취소 거래"라는 새 기록을 추가해 효과를 상쇄합니다. 거래내역에는 출금 1건과 출금취소 1건이 모두 남고, 이것이 감사 추적(audit trail)이 됩니다. 이 때문에 보상 트랜잭션에는 몇 가지 조건이 따릅니다. (1) 원거래를 가리키는 키(원거래 GUID)를 가져야 하고, (2) 멱등해야 합니다. 보상 요청이 재전송되어도 한 번만 반영되어야 합니다. (3) 보상 자체가 실패하면 재시도 큐에 넣어 결국 성공시켜야 합니다(사람이 개입하는 미결 목록 포함). ACID의 격리성은 포기한 것이므로, 그 사이 다른 거래가 중간 상태를 볼 수 있다는 점도 업무적으로 수용 가능한지 검토해야 합니다.

타임아웃 시 바로 보상하면 안 됩니다

대외 입금 요청에 응답이 없을 때 "실패했겠지" 하고 즉시 출금 취소를 하면, 사실은 상대 은행에서 입금이 처리된 경우 고객은 돈을 받기도 하고 돌려받기도 해서 이중 지급이 됩니다. 응답 없음은 결과 불명입니다. 정해진 절차(결과 조회 전문, 일정 시간 후 재조회, 그래도 불명이면 마감 후 대사 파일로 확정)에 따라 결과를 확정한 뒤에만 보상합니다. 이것이 금융 대외계 프로그램에 "미결 거래 처리" 모듈이 꼭 있는 이유입니다.

29-2 한 줄 요약

원장과 거래내역은 같은 트랜잭션에서 함께 커밋하고, 읽고-판단하고-쓰는 갱신은 FOR UPDATE나 조건부 UPDATE로 보호하며, 여러 행 락은 계좌번호 순서로 잡습니다. 트랜잭션 경계는 한 곳에서 정하고, 조직을 넘는 거래는 보상 트랜잭션으로, 타임아웃은 "결과 불명"으로 다룹니다.

핵심 정리

  • Pro*C는 프리컴파일러 proc가 EXEC SQL을 런타임 라이브러리 호출로 바꾼 C 파일을 만들고, 그 파일을 일반 C처럼 컴파일·링크합니다. 생성된 .c 파일은 수정하지 않습니다.
  • 호스트 변수는 SQL 안에서 :를 붙여 쓰며, char 배열은 컬럼 길이 + 1(널 문자), 금액은 long long으로 받습니다.
  • NULL 가능 컬럼에는 short 지시자 변수를 붙입니다. -1은 NULL, 양수는 잘림(원래 길이). 지시자 없이 NULL을 받으면 ORA-01405입니다.
  • VARCHAR는 len + arr 구조체로 바뀌며 널 종료되지 않습니다. 입력 시 len 설정, 출력 후 직접 널 종료가 필요합니다.
  • 모든 SQL 뒤에 sqlca.sqlcode를 검사합니다(0 성공, 1403 데이터 없음, 음수 오류). 갱신은 sqlerrd[2]로 처리 행 수까지 확인합니다.
  • 여러 행은 커서(DECLARE-OPEN-FETCH-CLOSE)로 처리하고, 대량 처리는 배열 FETCH와 FOR :n 배열 DML로 왕복 횟수를 줄입니다. 배열 FETCH의 1403에는 마지막 묶음이 들어 있습니다.
  • 동적 SQL에서도 값은 반드시 바인드 변수로 전달해 SQL 인젝션을 막고 실행 계획을 재사용합니다. 구조를 바꾸는 입력은 허용 목록으로만 받습니다.
  • ACID는 언두(원자성), 제약과 로직(일관성), 락과 MVCC(격리성), WAL 리두 로그(지속성)로 구현됩니다.
  • Oracle 기본 격리 수준은 READ COMMITTED이며, Lost Update는 SELECT FOR UPDATE(비관적 락), 버전 컬럼(낙관적 락), 또는 조건부 UPDATE로 막습니다.
  • 2PC는 준비-커밋 두 단계로 여러 자원의 원자성을 보장하지만 블로킹 문제가 있습니다. TP 모니터는 서비스, tpcall, tpbegin/tpcommit으로 대량 온라인 거래와 분산 트랜잭션을 관리합니다.
  • 조직을 넘는 거래는 로컬 커밋 + 보상 트랜잭션으로 처리하며, 타임아웃은 실패가 아니라 결과 불명입니다.

이 장에서 나오는 면접 질문

Q1. 트랜잭션의 ACID를 설명해 주세요.

원자성은 트랜잭션의 작업이 모두 반영되거나 하나도 반영되지 않는 성질이고, 일관성은 트랜잭션 전후로 데이터가 무결성 규칙을 만족하는 성질입니다. 격리성은 동시에 실행되는 트랜잭션이 서로의 중간 결과에 영향을 받지 않는 성질, 지속성은 커밋된 결과가 장애 후에도 유지되는 성질입니다. 계좌이체로 예를 들면 출금과 입금이 함께 반영되고, 총액이 보존되며, 이체 중간 상태가 다른 거래에 보이지 않고, 커밋 직후 정전이 나도 결과가 남아야 합니다. 꼬리 질문: 지속성은 WAL 방식으로 리두 로그를 커밋 시 디스크에 먼저 기록해 보장합니다.

Q2. 트랜잭션 격리 수준과 각 수준에서 발생하는 이상 현상을 말해 주세요.

READ UNCOMMITTED는 커밋되지 않은 데이터를 읽는 Dirty Read까지 허용하고, READ COMMITTED는 Dirty Read는 막지만 같은 행을 다시 읽을 때 값이 바뀌는 Non-Repeatable Read를 허용합니다. REPEATABLE READ는 그것까지 막지만 새 행이 나타나는 Phantom Read가 표준상 가능하고, SERIALIZABLE은 모두 막습니다. 격리 수준이 높을수록 동시성이 떨어집니다. Oracle은 기본이 READ COMMITTED이고 MVCC로 읽기가 쓰기를 막지 않는다는 점을 덧붙이면 좋습니다.

Q3. 비관적 락과 낙관적 락의 차이와 선택 기준은?

비관적 락은 충돌이 잦다고 가정해 읽을 때 SELECT FOR UPDATE로 미리 잠그고, 낙관적 락은 충돌이 드물다고 가정해 잠그지 않고 쓸 때 버전 컬럼을 비교해 그사이 변경이 있었으면 실패시킵니다. 잔액 차감처럼 짧고 경합이 많은 처리는 비관적 락이, 사용자가 화면을 오래 보는 정보 수정처럼 락 보유 시간이 길어지는 작업은 낙관적 락이 적합합니다. 낙관적 락은 경합이 많으면 재시도가 폭증한다는 단점이 있습니다.

Q4. DB 데드락은 어떻게 발생하고 어떻게 처리되나요?

두 트랜잭션이 서로 상대가 잠근 행을 기다리면 발생합니다. 예를 들어 A→B 이체와 B→A 이체가 동시에 각자 첫 행을 잠근 경우입니다. Oracle은 이를 자동으로 탐지해 한쪽 문장을 ORA-00060으로 실패시키고, 애플리케이션은 롤백 후 재시도해야 합니다. 예방은 여러 행을 잠글 때 계좌번호 오름차순처럼 일정한 순서를 지키는 것이고, 트랜잭션을 짧게 유지하는 것도 중요합니다.

Q5. 2단계 커밋(2PC)이란 무엇이고 단점은?

여러 자원 관리자에 걸친 분산 트랜잭션의 원자성을 보장하는 프로토콜입니다. 1단계에서 조정자가 모든 참여자에게 준비를 요청하고, 참여자는 커밋할 수 있는 상태를 로그에 기록한 뒤 YES를 답합니다. 모두 YES면 2단계에서 커밋을, 하나라도 NO면 롤백을 지시합니다. 단점은 준비를 마친 참여자가 결정을 받을 때까지 락을 쥐고 기다려야 해 조정자 장애 시 블로킹되는 문제와, 왕복이 늘어나는 성능 비용입니다. 그래서 조직 간 거래는 보상 트랜잭션(사가 패턴)을 많이 씁니다.

Q6. SQL 인젝션이란 무엇이고 어떻게 막나요?

사용자 입력이 SQL 문자열에 그대로 연결되어 SQL의 구조를 바꾸는 공격입니다. 예를 들어 이름 입력에 ' OR '1'='1을 넣으면 조건이 항상 참이 되어 전체 데이터가 조회됩니다. 바인드 변수(Prepared Statement)를 쓰면 SQL 파싱이 끝난 뒤 값이 데이터로만 전달되므로 구조를 바꿀 수 없습니다. 테이블명이나 정렬 컬럼처럼 바인드할 수 없는 부분은 허용 목록으로 검증합니다. 바인드 변수는 실행 계획 재사용으로 성능에도 유리합니다.

Q7. DB의 NULL을 C 프로그램에서 어떻게 다루나요?

C 변수에는 "값 없음"을 표현할 방법이 없으므로, Pro*C에서는 short형 지시자 변수를 호스트 변수와 짝지어 씁니다. 조회 시 지시자가 -1이면 NULL이고 호스트 변수의 내용은 의미가 없으며, 양수면 값이 잘린 것입니다. 입력 시 지시자를 -1로 두면 NULL이 저장됩니다. 지시자 없이 NULL을 FETCH하면 ORA-01405 오류가 나므로, NULL 허용 컬럼에는 지시자를 붙이거나 NVL로 기본값을 줍니다.

Q8. 대량 데이터 배치의 성능을 높이는 방법은?

가장 큰 비용은 DB와의 네트워크 왕복이므로 배열 FETCH와 배열 INSERT/UPDATE로 왕복 횟수를 줄입니다. 또 건마다 커밋하면 리두 로그 동기화 대기가 커지므로 적당한 단위로 묶어 커밋하되, 재시작 지점을 함께 기록해 실패 시 이어서 처리할 수 있게 합니다. SQL 자체는 인덱스와 실행 계획을 점검하고, 가능하면 C 루프 대신 집합 연산 SQL 한 문장으로 처리합니다. 필요하면 키 범위로 나눠 여러 프로세스가 병렬 처리합니다.

Q9. TP 모니터는 왜 필요한가요?

대량의 짧은 온라인 거래를 효율적으로 처리하기 위해서입니다. 서버 프로세스와 DB 연결을 미리 만들어 풀로 관리하고, 요청을 서비스 이름으로 라우팅해 부하를 분산하며, 프로세스 장애 시 재기동하고, 처리 시간 제한을 관리합니다. 또 XA 기반으로 여러 자원에 걸친 전역 트랜잭션의 경계(tpbegin, tpcommit)를 관리해 2단계 커밋을 수행합니다. 클라이언트마다 DB 연결을 맺는 2계층 구조보다 자원 사용이 훨씬 효율적입니다.

Q10. 타임아웃이 발생한 이체 거래는 어떻게 처리해야 하나요?

타임아웃은 실패가 아니라 결과를 모르는 상태이므로, 바로 실패 처리하거나 재시도하면 이중 처리가 생길 수 있습니다. 거래마다 고유한 거래 추적 ID를 부여하고, 타임아웃 시 그 ID로 결과 조회 거래를 수행해 처리 여부를 확정한 뒤 후속 처리를 합니다. 서버 쪽에서는 같은 ID의 중복 요청을 유일 제약 등으로 막아 멱등성을 보장하고, 호출 계층의 타임아웃은 바깥쪽이 안쪽보다 길도록 정렬합니다.

연습문제 29-6 난이도 ★★☆

READ COMMITTED에서 다음 두 트랜잭션이 동시에 실행됩니다. 잔액 초기값은 10만 원입니다. 최종 잔액으로 가능한 값을 모두 쓰고, 정답이 항상 나오게 고치십시오.

정답과 해설 보기
