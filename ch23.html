실전 자료구조

C에는 리스트도, 맵도, 정렬된 컨테이너도 내장되어 있지 않습니다. 그래서 금융 C 개발자는 거래 대기열, 전문 수신 버퍼, 계좌 캐시, 주문 호가창을 직접 만들거나 사내 공통 라이브러리를 이해하고 써야 합니다. 이 장에서는 면접 단골인 기본 자료구조를 "교과서 예제"가 아니라 금융 시스템의 실제 쓰임새에 맞춰 구현하고, 각 선택이 성능과 정확성에 어떤 영향을 주는지 따져 봅니다.

이 장에서 배울 것

  • 배열과 연결 리스트의 메모리 구조 차이와 장단점을 설명합니다.
  • 단일 연결 리스트의 삽입·삭제를 포인터의 포인터 기법으로 깔끔하게 구현합니다.
  • 더미 노드를 둔 이중 연결 리스트로 O(1) 삭제(주문 취소)를 구현합니다.
  • 스택으로 괄호 짝 검사를, 원형 큐로 TCP 전문 수신 버퍼와 메시지 경계 처리를 구현합니다.
  • 계좌번호 → 계좌 정보 해시 테이블을 체이닝·리사이즈까지 구현하고, 해시 함수와 로드 팩터를 이해합니다.
  • 이진 탐색, qsort/bsearch, 퀵 정렬과 병합 정렬을 구현·비교하고 비교 함수의 함정을 피합니다.
  • 안정 정렬이 거래 정렬에서 왜 중요한지 실험으로 확인합니다.
  • 이진 힙 우선순위 큐로 가격-시간 우선 원칙의 주문 체결을 구현합니다.

23-1연결 리스트, 스택, 큐

자료구조를 고를 때 던져야 할 질문은 항상 같습니다. "어떤 연산이 가장 자주 일어나는가? 데이터는 몇 개이고, 개수가 얼마나 변하는가? 순서가 중요한가?" 이 절에서는 순서가 있는 데이터를 담는 세 가지 기본 구조를 금융 업무에 대입해 봅니다.

배열과 연결 리스트

배열은 원소를 메모리에 연속으로 놓습니다. 그래서 i번째 원소의 주소를 시작 주소 + i × 원소 크기로 바로 계산할 수 있고(임의 접근 O(1)), CPU 캐시가 연속된 메모리를 미리 읽어 오므로 순회도 매우 빠릅니다. 대신 중간에 끼워 넣거나 빼려면 뒤의 원소를 모두 밀거나 당겨야 하고(O(n)), 크기를 늘리려면 새 공간을 잡아 통째로 복사해야 합니다.

연결 리스트는 각 원소(노드)가 다음 노드의 주소를 품고 있어 메모리 여기저기에 흩어져 있어도 순서를 유지합니다. 삽입·삭제 위치의 노드 포인터를 알고 있으면 포인터 몇 개만 바꾸면 되므로 O(1)입니다. 대신 i번째 원소를 찾으려면 처음부터 따라가야 하고(O(n)), 노드마다 포인터 공간이 추가로 들며, 메모리가 흩어져 캐시 효율이 나쁩니다.

왜 실무에서는 생각보다 배열이 자주 이길까?

현대 CPU에서 메인 메모리 접근은 L1 캐시 접근보다 수십~수백 배 느립니다. 배열은 한 번 메모리를 읽을 때 캐시 라인(보통 64바이트)에 이웃 원소가 함께 올라오고, 하드웨어 프리페처가 다음 영역을 미리 가져옵니다. 연결 리스트는 다음 노드의 주소를 읽어야 다음 위치를 알 수 있어(pointer chasing) 매 노드마다 캐시 미스가 날 수 있습니다. 그래서 원소가 수천 개 이하라면 "중간 삽입을 위해 배열을 밀어내는 비용"이 "리스트를 따라가는 비용"보다 싼 경우가 많습니다. 연결 리스트는 노드 포인터를 이미 들고 있어서 O(1) 삭제가 필요한 경우(주문 취소, LRU 캐시)나, 노드가 다른 구조(해시 테이블 체인)에 함께 소속되는 경우에 진가를 발휘합니다.

단일 연결 리스트의 삽입과 삭제

당일 거래 내역을 시간순으로 유지하는 리스트를 만들어 보겠습니다. 거래가 늦게 도착할 수도 있으므로(재전송, 대외기관 지연) 맨 뒤에 붙이는 것이 아니라 시간순 위치에 삽입합니다.

연결 리스트 코드에서 가장 지저분한 부분은 "맨 앞에 삽입/삭제하는 경우"를 따로 처리하는 것입니다. 포인터의 포인터(tx_node **pp)를 쓰면 "head 변수"와 "이전 노드의 next 필드"를 똑같이 "다음을 가리키는 칸"으로 다룰 수 있어 특수 경우가 사라집니다.

자주 하는 실수 — 해제하면서 순회

for (p = head; p; p = p->next) free(p);는 free(p) 뒤에 증감식에서 p->next를 읽으므로 use-after-free입니다. 대부분의 환경에서 "우연히" 동작하기 때문에 오래 숨어 있다가 할당기가 바뀌거나 ASan을 켰을 때 드러납니다. 위 free_all처럼 다음 포인터를 먼저 저장한 뒤 해제합니다.

이중 연결 리스트와 더미 노드

증권 시스템의 호가창에서 같은 가격의 주문들은 도착 순서대로 줄을 섭니다(시간 우선). 고객이 주문을 취소하면 줄 중간에서 그 주문을 빼야 합니다. 주문 번호 → 노드 포인터를 해시 테이블로 바로 찾을 수 있다면, 이중 연결 리스트는 이전 노드도 알고 있으므로 O(1)에 삭제할 수 있습니다.

이중 연결 리스트 구현을 단순하게 만드는 기법이 더미(센티널) 노드입니다. 데이터가 없는 노드 하나를 원형으로 두면, 리스트가 비어 있어도 "앞·뒤 노드가 항상 존재"하므로 NULL 검사와 맨 앞/맨 뒤 특수 처리가 모두 사라집니다. 리눅스 커널의 list_head가 바로 이 구조입니다.

침입형(intrusive) 리스트

위 코드처럼 링크(dnode)를 데이터 구조체 안에 넣는 방식을 침입형 리스트라고 합니다. 노드를 따로 malloc하지 않아도 되고, 한 주문 객체가 여러 리스트(가격대 대기열, 고객별 주문 목록)에 동시에 소속될 수 있습니다. 링크가 첫 멤버가 아니면 offsetof를 이용한 container_of 매크로로 바깥 구조체 주소를 구합니다. 금융 매칭 엔진과 커널 코드에서 널리 쓰는 패턴입니다.

스택과 괄호 검사

스택(stack)은 마지막에 넣은 것을 먼저 꺼내는(LIFO) 구조입니다. 연산은 넣기(push), 꺼내기(pop), 맨 위 보기(peek) 세 가지뿐이고 모두 O(1)입니다. 함수 호출 스택, 실행 취소(undo), 수식 계산, 그리고 중첩 구조 검사에 쓰입니다.

금융 시스템에서도 중첩 구조는 흔합니다. 수수료·우대 조건을 표현하는 규칙식(IF((AMT>100000)AND[GRADE=1])), 반복부가 중첩된 전문 레이아웃 정의, JSON/XML 메시지 등입니다. 이런 입력을 파싱하기 전에 괄호 짝부터 검사하면 잘못된 규칙이 운영에 반영되는 것을 막을 수 있습니다.

왜 스택 깊이에 상한을 둘까?

상한이 없는 스택(동적으로 늘어나는 배열)이나 재귀로 구현하면, ((((((…를 수백만 개 넣은 입력 하나로 메모리를 고갈시키거나 콜 스택을 넘치게 할 수 있습니다. 외부 입력을 처리하는 모든 자료구조에는 업무상 의미 있는 상한(중첩 깊이, 원소 수, 길이)을 두고, 넘으면 명시적으로 거부합니다. 22장의 "모든 입력은 범위가 있다"는 원칙이 자료구조에도 그대로 적용됩니다.

원형 큐와 전문 수신 버퍼

큐(queue)는 먼저 넣은 것을 먼저 꺼내는(FIFO) 구조입니다. 배열로 큐를 만들면서 꺼낼 때마다 원소를 앞으로 당기면 O(n)이 되므로, 배열의 끝과 처음을 이어 붙인 것처럼 쓰는 원형 큐(circular queue, ring buffer)를 씁니다. 읽기 위치(head)와 원소 수(count)만 관리하면 넣기·꺼내기 모두 O(1)이고, 메모리를 새로 할당하지 않습니다.

원형 버퍼의 대표적인 금융 실무 쓰임새는 TCP 전문 수신 버퍼입니다. TCP는 바이트 스트림이라 메시지 경계를 보존하지 않습니다. 상대가 전문 두 개를 보내도 recv 한 번에 1.5개가 오거나, 한 전문이 세 번에 나눠 올 수 있습니다. 그래서 받은 바이트를 버퍼에 쌓아 두고, "길이 헤더 + 본문"이 완성된 전문만 꺼내는 프레이밍(framing) 처리가 필요합니다.

두 번째 수신에서 tail이 6이 된 것을 보십시오. 11바이트를 쓰는 중에 배열 끝(15)을 넘어 처음으로 감겼습니다(rb_write의 두 번째 memcpy). 첫 조각의 끝 "00"과 두 번째 조각의 "03"이 합쳐져 길이 헤더 "0003"이 완성되었고, 세 번째 조각에서 "TEST"가 완성되었습니다. 전문 경계가 조각 경계와 전혀 맞지 않아도 정확히 복원됩니다.

왜 head와 tail 대신 head와 count를 저장할까?

head와 tail만 저장하면 버퍼가 꽉 찼을 때와 비었을 때 모두 head == tail이 되어 구분할 수 없습니다. 해결책은 세 가지입니다. ① 한 칸을 항상 비워 두고 "tail+1 == head면 가득"으로 판정(용량이 1 줄어듦), ② 별도의 count를 유지(위 코드), ③ head·tail을 모듈러 없이 계속 증가시키고 차이로 개수를 계산(용량이 2의 거듭제곱이면 & (CAP-1)로 인덱스 계산, 단일 생산자·단일 소비자 lock-free 큐에서 선호). 면접에서 "원형 큐의 full/empty 구분 방법"으로 자주 나옵니다.

은행 시스템에서는 — "가끔 전문이 깨진다"의 정체

대외기관과 TCP로 전문을 주고받는 한 시스템에서, 평소에는 문제가 없다가 거래량이 많은 월말·급여일에만 "전문 형식 오류"가 간헐적으로 발생했습니다. 원인은 수신 코드가 recv(sock, buf, 300, 0) 한 번이 전문 하나(300바이트 고정)를 돌려준다고 가정한 것이었습니다. 트래픽이 적을 때는 상대가 보낸 단위 그대로 도착했지만, 네트워크가 바쁠 때는 TCP가 여러 전문을 합치거나 쪼개 전달했고, 그때마다 전문이 밀려 엉뚱한 필드가 금액으로 해석되었습니다(다행히 형식 검증에서 대부분 걸렸습니다).

해결은 위와 같은 수신 버퍼 + 프레이밍 계층을 두고, 전문 시작 문자·길이 필드·전문 종료 문자를 모두 검증하도록 바꾼 것입니다. 교훈: TCP는 메시지가 아니라 바이트 스트림입니다. 부분 수신, 합쳐진 수신, 0바이트(연결 종료) 수신을 모두 처리해야 합니다(소켓 프로그래밍은 뒤 장에서 자세히 다룹니다).

예제 23-2 난이도 ★★☆

배열 기반 원형 큐(용량 5, "한 칸 비우기" 방식, head와 tail 저장)에서 다음 연산 후 head, tail, 원소 수를 쓰십시오. 초기 head = tail = 0. enqueue A, B, C, D → dequeue 2회 → enqueue E, F → enqueue G

정답과 해설 보기

"한 칸 비우기" 방식은 용량 5 배열에 최대 4개를 저장하며, (tail + 1) % 5 == head이면 가득입니다.

  1. A, B, C, D 넣기: 인덱스 0~3, tail = 4, 원소 4개(가득: (4+1)%5 = 0 == head).
  2. 2회 꺼내기(A, B): head = 2, 원소 2개.
  3. E 넣기: 인덱스 4, tail = 0. F 넣기: 인덱스 0, tail = 1. 원소 4개.
  4. G 넣기: (1+1)%5 = 2 == head → 가득 참, 실패.

최종: head = 2, tail = 1, 원소 4개(C, D, E, F).

23-2해시 테이블, 정렬, 탐색

계정계 온라인 거래의 첫 단계는 거의 항상 "이 계좌번호의 계좌 정보를 찾아라"입니다. 대부분은 DB가 인덱스(B-트리)로 처리하지만, 초당 수만 건을 처리하는 중계 서버, 일마감 배치, 대외기관 대사 프로그램은 수백만 건을 메모리에 올려 직접 찾고 정렬합니다. 이 절에서는 "찾기"의 두 가지 길(해시와 정렬+이진 탐색)과 정렬 알고리즘의 성질, 그리고 우선순위가 있는 데이터를 다루는 힙을 다룹니다.

해시 테이블의 원리

해시 테이블은 키(계좌번호)를 해시 함수로 정수로 바꾼 뒤, 그 값을 배열 인덱스로 써서 데이터를 저장합니다. 해시 계산이 O(1)이고 배열 접근이 O(1)이므로, 평균적으로 삽입·검색·삭제가 모두 O(1)입니다. 문제는 서로 다른 키가 같은 인덱스로 가는 충돌(collision)인데, 버킷 수보다 키가 많으면 비둘기집 원리에 따라 충돌은 반드시 생깁니다.

충돌 해결 방식은 크게 두 가지입니다.

  • 체이닝(separate chaining): 각 버킷이 연결 리스트를 가지고, 같은 버킷으로 온 원소를 리스트에 매답니다. 구현이 단순하고 삭제가 쉬우며 로드 팩터가 1을 넘어도 동작합니다.
  • 개방 주소법(open addressing): 충돌하면 배열의 다른 빈칸을 정해진 규칙(선형 탐사, 이차 탐사, 이중 해싱)으로 찾아 저장합니다. 포인터가 없어 캐시 효율이 좋지만, 삭제 시 "삭제됨" 표시(tombstone)가 필요하고 로드 팩터가 높아지면 급격히 느려집니다.

해시 함수 고르기

좋은 해시 함수는 ① 빠르고, ② 비슷한 키도 전혀 다른 값으로 흩어 놓으며(눈사태 효과), ③ 출력이 고르게 분포해야 합니다. 계좌번호처럼 앞자리(지점·과목 코드)가 같고 뒷자리만 조금 다른 키는 나쁜 해시 함수에서 한 버킷으로 몰립니다.

문자 합 해시는 세 키 모두 344로 같습니다. 숫자만으로 된 계좌번호는 자릿수 합이 비슷한 범위에 몰려 있어 문자 합 해시를 쓰면 수백만 계좌가 소수의 버킷에 집중됩니다. FNV-1a는 한 글자만 바뀌어도 결과가 크게 달라집니다.

왜 버킷 수를 2의 거듭제곱으로 하고 & (cap-1)을 쓸까?

h % cap의 나눗셈은 CPU에서 수십 사이클이 걸리지만, cap이 2의 거듭제곱이면 h & (cap - 1)(하위 비트만 취함)로 한 사이클에 끝납니다(20장의 마스크). 대신 해시의 하위 비트가 잘 섞여 있어야 합니다. 하위 비트가 약한 해시(예: 주소값, 단순 곱셈)를 쓸 때는 소수 크기 + %를 쓰거나, 상위 비트를 섞어 주는 마무리(finalizer) 단계를 추가합니다.

해시 충돌 공격(HashDoS)

해시 함수와 버킷 수가 공개되어 있으면, 공격자가 같은 버킷으로 가는 키를 대량으로 만들어 보낼 수 있습니다. 그러면 체인이 수만 개로 길어져 O(1) 검색이 O(n)으로 무너지고 서버 CPU가 마비됩니다. 외부 입력을 키로 쓰는 해시 테이블(예: HTTP 파라미터, 전문의 임의 필드)에는 프로세스 시작 시 무작위 시드를 섞는 키 기반 해시(SipHash 등)를 쓰고, 체인 길이 상한이나 원소 수 상한을 둡니다. 계좌번호처럼 내부에서 검증된 키만 쓰는 테이블이라면 FNV 같은 빠른 해시로 충분한 경우가 많습니다.

계좌번호 → 계좌 정보 해시 테이블 구현

이제 일마감 대사 배치에서 쓸 법한, 계좌번호로 계좌 정보를 찾는 해시 테이블을 체이닝 방식으로 구현합니다. 로드 팩터가 0.75를 넘으려 하면 버킷 수를 두 배로 늘립니다.

로드 팩터와 리사이즈

로드 팩터(load factor) α = 원소 수 / 버킷 수입니다. 해시가 고르다면 체이닝에서 평균 체인 길이는 α이므로, 성공한 검색은 평균 약 1 + α/2번, 실패한 검색은 약 α번의 비교가 필요합니다. α를 0.75 정도로 유지하면 검색이 사실상 상수 시간이 됩니다. 원소가 늘어 α가 기준을 넘으면 버킷 수를 늘리고 모든 원소를 새 위치로 옮기는 리해시(rehash)를 합니다.

왜 두 배씩 늘리면 평균 O(1)일까? (분할 상환 분석)

용량 1에서 시작해 두 배씩 늘리며 n개를 넣는다고 합시다. 리사이즈 때 옮기는 원소 수는 1 + 2 + 4 + … + n/2 < n입니다. 즉 n번의 삽입에 드는 이동 비용 총합이 n보다 작으므로, 삽입 한 번당 평균(분할 상환) 비용은 O(1)입니다. 반대로 "10개씩" 늘리면 이동 총량이 n²/20이 되어 삽입당 O(n)이 됩니다. 동적 배열(벡터)의 용량 증가도 같은 원리이며, 배수는 1.5나 2를 씁니다.

은행 시스템에서는 — 배치 시작 직후 30초의 정체

어느 대사 배치는 대외기관 파일(약 800만 건)을 읽어 해시 테이블에 넣은 뒤 자체 원장과 맞추는 구조였습니다. 초기 버킷 수를 1,024로 잡아 두었기 때문에 적재 중에 리사이즈가 13번 일어났고, 마지막 몇 번은 수백만 노드를 옮기느라 각각 수 초씩 걸렸습니다. 게다가 리사이즈 중 할당 실패 처리가 없어 메모리가 부족한 날에는 배치가 비정상 종료되었습니다. 파일 헤더의 총건수를 읽어 처음부터 적정 용량(건수 / 0.75 이상의 2의 거듭제곱)으로 만들도록 바꾸자 적재 시간이 크게 줄었고, 할당 실패 시 명확한 오류 코드로 종료하게 했습니다. 예상 크기를 알면 미리 잡는 것, 그리고 리사이즈 실패에도 기존 데이터가 온전하게 설계하는 것이 실무 포인트입니다.

이진 탐색

데이터가 정렬되어 있으면 가운데 원소와 비교해 탐색 범위를 절반씩 줄이는 이진 탐색으로 O(log n)에 찾을 수 있습니다. 100만 건이면 최대 20번, 10억 건이면 30번의 비교면 충분합니다. 해시 테이블과 달리 범위 검색("계좌번호 1100으로 시작하는 모든 계좌", "금액 100만~500만 원 거래")과 순서 순회가 가능하다는 장점이 있습니다.

실무에서 가장 유용한 형태는 "값이 있으면 그 위치, 없으면 들어갈 위치"를 돌려주는 lower_bound(key 이상인 첫 위치)입니다.

자주 하는 실수 — 이진 탐색의 세 가지 버그

  • 중간값 오버플로: (lo + hi) / 2는 lo + hi가 타입 최대값을 넘으면 깨집니다(실제로 유명 라이브러리에서 수년간 숨어 있던 버그). lo + (hi - lo) / 2를 씁니다.
  • 무한 루프: 구간 정의(닫힌 [lo, hi] vs 반열린 [lo, hi))와 갱신식(hi = mid vs hi = mid - 1)을 섞으면 구간이 줄지 않습니다. 한 가지 정의로 통일합니다. 특히 size_t로 hi = mid - 1을 쓰면 mid가 0일 때 순환해 거대한 값이 됩니다.
  • 정렬 기준 불일치: 금액순으로 정렬한 배열을 계좌번호로 이진 탐색하면 엉뚱한 결과가 나옵니다. 탐색의 비교 기준은 정렬 기준과 정확히 같아야 합니다.

qsort와 bsearch

C 표준 라이브러리는 범용 정렬 qsort와 이진 탐색 bsearch를 제공합니다. 원소 타입을 모르므로 void *와 원소 크기, 그리고 비교 함수 포인터를 받습니다. 비교 함수는 첫 인자가 작으면 음수, 같으면 0, 크면 양수를 반환해야 합니다.

나쁜 비교 함수는 30억 원이 0원보다 "작다"고 판정했습니다. int64 차이(3,000,000,000)를 int로 변환하면서 잘렸기 때문입니다(20장). 이런 비교 함수로 정렬하면 결과가 틀릴 뿐 아니라, 비교가 일관되지 않아(a < b이고 b < c인데 c < a) qsort 구현에 따라 배열 범위 밖을 접근하는 사고까지 날 수 있습니다. 비교 함수는 반드시 일관된 전순서(반사·반대칭·추이)를 정의해야 합니다.

qsort는 퀵 정렬일까?

표준은 qsort의 알고리즘도, 시간 복잡도도, 안정성도 규정하지 않습니다. glibc는 오랫동안 메모리가 충분하면 병합 정렬(결과적으로 안정)을 썼지만, 최근 버전에서는 인트로 정렬 계열로 바뀌어 안정성이 보장되지 않습니다. MSVC와 다른 libc도 제각각입니다. "지금까지 qsort가 안정적으로 동작했다"는 경험은 근거가 될 수 없으므로, 안정성이 필요하면 직접 보장해야 합니다(다음 절).

퀵 정렬과 병합 정렬

면접과 실무 모두에서 가장 중요한 두 정렬 알고리즘입니다.

  • 퀵 정렬: 기준값(피벗)을 하나 골라, 피벗보다 작은 것은 왼쪽, 큰 것은 오른쪽으로 나눈(partition) 뒤 양쪽을 재귀로 정렬합니다. 제자리(in-place) 정렬이라 추가 메모리가 적고 평균적으로 가장 빠르지만, 피벗이 계속 최솟값/최댓값으로 걸리면(이미 정렬된 입력에 끝 원소 피벗) O(n²)이 됩니다. 원소를 멀리 교환하므로 불안정합니다.
  • 병합 정렬: 배열을 반으로 나눠 각각 재귀로 정렬한 뒤, 정렬된 두 배열을 하나로 합칩니다(merge). 항상 O(n log n)이고 안정하지만, 합칠 때 O(n)의 추가 메모리가 필요합니다. 파일처럼 순차 접근만 가능한 대용량 데이터의 외부 정렬(external sort)에 적합합니다.

왜 비교 기반 정렬은 O(n log n)보다 빠를 수 없을까?

원소 n개의 가능한 순서는 n!가지이고, 비교 한 번은 결과가 두 가지(예/아니오)입니다. 어떤 순서인지 확정하려면 비교들로 만든 결정 트리의 잎이 n!개 이상이어야 하므로, 트리 높이(최악 비교 횟수)는 log₂(n!) 이상입니다. 스털링 근사로 log₂(n!) ≈ n log₂ n − 1.44n이므로 하한은 Ω(n log n)입니다. 계수 정렬·기수 정렬처럼 비교 대신 키의 자릿값을 이용하는 정렬은 이 하한을 받지 않아, 키 범위가 제한된 경우(예: 0~999 지점 코드) O(n)에 정렬할 수 있습니다.

안정 정렬이 거래 정렬에서 중요한 이유

안정 정렬(stable sort)은 비교 기준이 같은 원소들의 원래 상대 순서를 보존하는 정렬입니다. 금융 데이터는 대개 이미 시간순으로 쌓여 있고, 이를 계좌별·지점별로 다시 정렬하는 일이 많습니다. 이때 정렬이 불안정하면 같은 계좌 안에서 거래의 시간 순서가 뒤섞입니다.

왜 문제가 될까요? 거래내역 조회 화면과 통장 인쇄는 "계좌별, 그 안에서 시간순"이어야 하고, 잔액 재계산 배치는 같은 계좌의 거래를 발생 순서대로 적용해야 중간 잔액이 맞습니다. 순서가 바뀌면 "잔액 부족" 판정이나 이자 계산의 기준 잔액이 달라질 수 있습니다.

이렇게 해결합니다 — 순서를 "운"에 맡기지 않는다

  1. 비교 기준을 완전하게: (계좌, 거래시각, 거래일련번호)처럼 동률이 생기지 않도록 고유한 마지막 키까지 비교 함수에 넣습니다. 그러면 어떤 정렬 알고리즘(qsort 포함)을 써도 결과가 하나로 정해집니다. 가장 권장되는 방법입니다.
  2. 안정 정렬 사용: 원래 순서 자체에 의미가 있고 별도 키가 없다면, 병합 정렬처럼 안정성이 보장된 정렬을 직접 구현하거나 공통 라이브러리를 씁니다.
  3. 원래 인덱스를 키로 추가: 정렬 전에 각 원소에 원래 위치를 기록해 두고 마지막 비교 기준으로 쓰면, 불안정 정렬도 안정 정렬과 같은 결과를 냅니다.

은행 시스템에서는 — 플랫폼 이전 후 달라진 거래내역 순서

유닉스 서버에서 리눅스로 시스템을 이전한 뒤, 일부 고객의 거래내역 조회 화면에서 같은 시각(초 단위까지 동일)의 거래 순서가 이전과 다르게 나온다는 민원이 접수되었습니다. 원인은 정렬 비교 함수가 "계좌번호, 거래시각"까지만 비교하고 있었고, 이전 플랫폼의 qsort 구현은 우연히 원래 순서를 유지했지만 새 플랫폼의 구현은 그렇지 않았기 때문입니다. 화면 순서만의 문제가 아니라, 같은 정렬 결과를 쓰던 통장 이월 잔액 계산에서도 중간 잔액 표시가 바뀌는 영향이 있었습니다. 비교 함수에 거래일련번호를 추가하는 한 줄 수정으로 해결되었지만, 영향 범위 분석과 재검증에는 몇 주가 걸렸습니다. 정렬 결과가 업무 의미를 가진다면 그 순서를 완전히 정의하라는 것이 교훈입니다.

우선순위 큐(힙)와 주문 체결 우선순위

증권 거래소의 매매 체결은 가격 우선, 시간 우선 원칙을 따릅니다. 매수 주문은 높은 가격이 먼저, 같은 가격이면 먼저 들어온 주문이 먼저 체결됩니다(매도는 낮은 가격 우선). 주문이 계속 들어오고 체결로 빠져나가는 상황에서 "지금 가장 우선순위가 높은 주문"을 빠르게 꺼내는 자료구조가 우선순위 큐이고, 대표적인 구현이 이진 힙(binary heap)입니다.

이진 힙은 "부모가 항상 자식보다 우선순위가 높거나 같은" 완전 이진 트리입니다. 완전 이진 트리이므로 포인터 없이 배열에 저장할 수 있습니다. 인덱스 i의 자식은 2i+1, 2i+2이고 부모는 (i−1)/2입니다. 삽입은 맨 끝에 넣고 부모와 비교하며 올리고(sift-up), 꺼내기는 루트를 빼고 마지막 원소를 루트에 올린 뒤 자식과 비교하며 내립니다(sift-down). 둘 다 트리 높이만큼, 즉 O(log n)입니다.

B3(70,500원, 09:00:00)은 가장 먼저 들어왔지만 가격이 낮아 뒤로 밀렸고, 같은 70,700원인 B4와 B2는 접수 시각이 빠른 B4가 먼저 체결되었습니다. 70,500원 두 건이 남았을 때는 B3가 B1보다 먼저 들어왔으므로 최우선입니다. "가격 → 시간 → 일련번호"의 비교 함수 하나가 체결 규칙 전체를 표현하고 있다는 점에 주목하십시오.

왜 정렬된 배열이나 연결 리스트가 아니라 힙일까?

정렬된 배열은 최우선 원소를 O(1)에 보지만 새 주문 삽입이 O(n)(밀어내기)입니다. 정렬된 연결 리스트도 삽입 위치를 찾는 데 O(n)입니다. 정렬되지 않은 배열은 삽입 O(1)이지만 최우선을 찾는 데 O(n)입니다. 힙은 삽입과 꺼내기가 모두 O(log n)이라 "계속 들어오고 계속 빠지는" 흐름에 균형이 맞습니다. 다만 실제 거래소 매칭 엔진은 주문 취소(임의 원소 삭제)와 가격대별 일괄 처리가 많아서, 가격대별 이중 연결 리스트(23-1-3) + 가격 정렬 구조(트리나 가격 인덱스 배열) 조합을 주로 씁니다. 힙은 타이머 관리(가장 먼저 만료되는 타임아웃), 작업 스케줄링, 상위 K개 추출에도 널리 쓰입니다.

예제 23-3 난이도 ★★☆

위 힙(B4 B2 B3 B1 B5)에서 heap_pop을 한 번 했을 때의 배열 상태를 단계별로 쓰십시오.

정답과 해설 보기
  1. 루트 B4를 제거하고 마지막 원소 B5를 루트로: [B5, B2, B3, B1], n=4.
  2. i=0: 자식 B2(70,700), B3(70,500). B5(70,600)보다 우선인 B2와 교환 → [B2, B5, B3, B1], i=1.
  3. i=1: 자식 l=3(B1, 70,500), r=4(없음). B5(70,600)가 B1보다 우선이므로 멈춤.

결과: [B2, B5, B3, B1]. 루트가 다음 최우선 주문 B2입니다.

핵심 정리

  • 배열은 연속 메모리라 임의 접근 O(1)·캐시 효율이 뛰어나고, 연결 리스트는 노드 포인터를 알 때 삽입·삭제 O(1)이지만 탐색 O(n)·캐시 효율이 나쁩니다. 데이터 수가 적으면 배열이 이기는 경우가 많습니다.
  • 연결 리스트 삽입은 "새 노드가 다음을 먼저 잡고 → 앞 링크를 새 노드로", 삭제는 "링크 우회 → 해제" 순서입니다. 포인터의 포인터(node **pp)를 쓰면 맨 앞 특수 처리가 사라집니다. 해제하며 순회할 때는 다음 포인터를 먼저 저장합니다.
  • 더미 노드를 둔 원형 이중 연결 리스트는 NULL 검사 없이 O(1) 삭제를 제공하며, 주문 취소처럼 "포인터를 이미 아는 원소 삭제"에 적합합니다. 링크를 구조체에 내장하는 침입형 리스트가 실무에서 흔합니다.
  • 스택(LIFO)은 중첩 구조 검사에, 큐(FIFO)는 순서대로 처리할 작업에 씁니다. 외부 입력을 다루는 스택·큐에는 반드시 상한을 둡니다.
  • 원형 버퍼는 head와 count(또는 한 칸 비우기)로 full/empty를 구분하고, TCP 바이트 스트림에서 길이 헤더로 전문 경계를 복원하는 수신 버퍼로 씁니다. TCP는 메시지 경계를 보존하지 않습니다.
  • 해시 테이블은 평균 O(1)이지만 충돌 처리(체이닝/개방 주소법), 좋은 해시 함수(FNV-1a 등), 로드 팩터 관리(약 0.75에서 2배 리사이즈, 분할 상환 O(1))가 성능을 좌우합니다. 최종 비교는 항상 원래 키로 합니다. 외부 키는 HashDoS에 대비합니다.
  • 정렬된 배열의 이진 탐색은 O(log n)이며 범위 검색이 가능합니다. 중간값은 lo + (hi - lo) / 2, 구간은 반열린 [lo, hi)로 통일합니다.
  • qsort/bsearch의 비교 함수는 (x > y) - (x < y)로 쓰고 뺄셈을 쓰지 않습니다. qsort의 알고리즘과 안정성은 표준이 보장하지 않습니다.
  • 퀵 정렬은 평균 최고속·제자리지만 최악 O(n²)·불안정, 병합 정렬은 항상 O(n log n)·안정이지만 O(n) 메모리가 필요합니다. 비교 기반 정렬의 하한은 Ω(n log n)입니다.
  • 같은 키 안의 원래 순서가 업무 의미를 가지면(계좌별 거래 순서) 안정 정렬을 쓰거나, 비교 기준에 고유 키(일련번호)까지 넣어 순서를 완전히 정의합니다.
  • 이진 힙은 배열 기반 완전 이진 트리로 삽입·꺼내기 O(log n), 최우선 조회 O(1)입니다. 비교 함수 하나로 가격-시간 우선 같은 업무 규칙을 표현합니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. 배열과 연결 리스트의 차이를 설명하고, 각각 언제 쓰는지 말해 주십시오.

배열은 연속된 메모리에 저장되어 인덱스로 O(1) 접근이 가능하고 캐시 효율이 좋지만, 중간 삽입·삭제가 O(n)이고 크기 변경 시 재할당·복사가 필요합니다. 연결 리스트는 노드가 포인터로 이어져 삽입·삭제가 O(1)(위치를 알 때)이지만, 탐색이 O(n)이고 노드마다 포인터 메모리가 들며 캐시 효율이 낮습니다. 임의 접근과 순회가 많으면 배열, 노드를 직접 가리킨 상태에서 빈번한 삽입·삭제가 필요하면(LRU 캐시, 주문 취소) 연결 리스트를 씁니다.

꼬리 질문 대비: "연결 리스트 뒤집기를 구현해 보라" → prev/cur/next 세 포인터로 O(n), O(1) 공간(예제 23-1).

Q2. 스택과 큐의 차이와 구현 방법은?

스택은 마지막에 넣은 것을 먼저 꺼내는 LIFO, 큐는 먼저 넣은 것을 먼저 꺼내는 FIFO 구조입니다. 스택은 배열과 top 인덱스로 간단히 구현하고, 큐는 배열을 원형으로 써서 head와 tail(또는 count)로 구현하면 모든 연산이 O(1)입니다. 연결 리스트로도 구현할 수 있습니다. 스택은 함수 호출, 괄호 검사, 실행 취소에, 큐는 작업 대기열, BFS, 버퍼링에 씁니다.

꼬리 질문 대비: "스택 두 개로 큐를 만들라" → 입력 스택에 넣고, 출력 스택이 비었을 때 입력 스택을 모두 옮겨 꺼내면 분할 상환 O(1)입니다.

Q3. 원형 큐에서 가득 찬 상태와 빈 상태를 어떻게 구분합니까?

head와 tail만 두면 둘 다 head == tail이 되어 구분할 수 없습니다. 해결책은 ① 한 칸을 비워 두고 (tail + 1) % N == head를 가득 참으로 보는 방법, ② 원소 개수 count를 따로 유지하는 방법, ③ head·tail을 계속 증가시키고 그 차이로 개수를 구하는 방법(용량을 2의 거듭제곱으로 두고 마스크로 인덱싱)이 있습니다.

Q4. 해시 테이블의 충돌 해결 방법과 각각의 장단점은?

체이닝은 버킷마다 연결 리스트를 두어 충돌한 원소를 매다는 방식으로, 구현과 삭제가 쉽고 로드 팩터가 높아도 성능이 완만히 저하되지만 포인터 오버헤드와 캐시 미스가 있습니다. 개방 주소법은 충돌 시 정해진 탐사 순서로 다른 빈칸을 찾는 방식으로, 메모리가 연속이라 캐시 효율이 좋지만 클러스터링이 생기고 삭제에 tombstone이 필요하며 로드 팩터가 높으면 급격히 느려집니다.

꼬리 질문 대비: "최악 시간 복잡도는?" → 모든 키가 한 버킷에 몰리면 O(n)입니다. 그래서 좋은 해시 함수, 리사이즈, 외부 입력에는 시드 기반 해시가 필요합니다.

Q5. 로드 팩터란 무엇이고, 리사이즈는 왜·어떻게 합니까?

로드 팩터는 저장된 원소 수를 버킷 수로 나눈 값으로, 체이닝에서는 평균 체인 길이입니다. 값이 커지면 검색 비용이 늘어나므로 보통 0.75 정도를 넘으면 버킷 수를 두 배로 늘리고 모든 원소를 새 버킷 위치로 다시 배치합니다. 한 번의 리사이즈는 O(n)이지만 두 배씩 늘리면 전체 삽입의 분할 상환 비용은 O(1)입니다. 실시간 시스템에서는 리사이즈 순간의 지연을 피하기 위해 초기 용량을 넉넉히 잡거나 점진적 리해시를 씁니다.

Q6. 이진 탐색의 전제 조건과 구현 시 주의점은?

데이터가 탐색 키 기준으로 정렬되어 있어야 하고, 임의 접근이 가능한 구조(배열)여야 합니다. 시간 복잡도는 O(log n)입니다. 구현 시 중간 인덱스를 (lo + hi) / 2로 계산하면 오버플로가 날 수 있으므로 lo + (hi - lo) / 2를 쓰고, 구간 정의(닫힌/반열린)와 갱신식을 일관되게 맞춰 무한 루프를 피해야 합니다.

Q7. 퀵 정렬과 병합 정렬을 비교해 주십시오. 퀵 정렬의 최악은 언제입니까?

둘 다 분할 정복이며 평균 O(n log n)입니다. 퀵 정렬은 제자리 정렬이라 추가 메모리가 적고 캐시 효율이 좋아 평균적으로 빠르지만 불안정하고, 피벗이 매번 최솟값이나 최댓값으로 골라지면(이미 정렬된 배열에서 첫/끝 원소를 피벗으로 쓸 때) O(n²)이 됩니다. 병합 정렬은 항상 O(n log n)이고 안정하지만 O(n) 추가 메모리가 필요합니다. 퀵 정렬의 최악을 피하려고 무작위 피벗, 세 값의 중앙값 피벗, 재귀가 깊어지면 힙 정렬로 바꾸는 인트로 정렬을 씁니다.

Q8. 안정 정렬이란 무엇이고 왜 중요합니까?

정렬 키가 같은 원소들의 원래 상대 순서를 유지하는 정렬입니다. 여러 기준으로 차례로 정렬할 때(먼저 시간순, 그다음 계좌순) 앞선 정렬 결과를 보존하려면 안정성이 필요합니다. 금융에서는 같은 계좌 거래의 발생 순서가 잔액 계산에 영향을 주므로 중요하며, 불안정 정렬을 쓴다면 비교 키에 일련번호 같은 고유 키를 포함해 순서를 완전히 정의해야 합니다. 병합·삽입·Timsort는 안정, 퀵·힙·선택 정렬은 불안정입니다.

Q9. 힙이란 무엇이고 삽입·삭제의 시간 복잡도는?

힙은 부모가 자식보다 항상 크거나(최대 힙) 작은(최소 힙) 완전 이진 트리로, 배열에 인덱스 규칙(자식 2i+1, 2i+2)으로 저장합니다. 삽입은 맨 끝에 넣고 위로 올리며, 최댓값 삭제는 루트를 마지막 원소로 바꾼 뒤 아래로 내리므로 둘 다 O(log n), 최댓값 조회는 O(1)입니다. n개로 힙을 한 번에 만드는 heapify는 O(n)입니다. 우선순위 큐, 힙 정렬, 타이머 관리, 상위 K개 추출에 씁니다.

Q10. qsort 비교 함수에서 return a - b;를 쓰면 안 되는 이유는?

뺄셈이 오버플로하면(int에서 큰 양수와 큰 음수의 차) signed 오버플로로 UB이고, 64비트 값의 차이를 int로 반환하면 잘려서 부호가 뒤집힐 수 있습니다. 그러면 비교 결과가 일관되지 않아 정렬이 틀리거나 구현에 따라 범위 밖 접근까지 발생할 수 있습니다. (a > b) - (a < b)처럼 비교 결과로 −1, 0, 1을 만들면 안전합니다.

본문의 매수 호가 힙에 "주문 ID로 임의 주문 취소" 기능을 O(log n)에 추가하려면 무엇이 필요합니까? 설계를 설명하십시오.

정답과 해설 보기
  1. 위치 추적: 주문 ID → 힙 배열 인덱스를 저장하는 해시 테이블(또는 주문 객체 안의 heap_idx 필드)을 두고, sift-up/sift-down에서 원소를 교환할 때마다 인덱스를 갱신합니다.

  4. 실무형 구조: 같은 가격의 주문은 가격대별 이중 연결 리스트(시간 우선, O(1) 취소)에 두고, 가격대 자체만 힙이나 정렬 구조로 관리하면 취소와 체결이 모두 효율적입니다.
