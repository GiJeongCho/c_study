빌드, 성능, 이식성

코드를 잘 짜는 것과 그 코드를 수백 개의 소스 파일, 수십 대의 서버, 서로 다른 유닉스 위에서 안정적으로 빌드하고 빠르게 돌리는 것은 전혀 다른 기술입니다. 이 장은 "내 PC에서는 되는데요"를 졸업하고, 은행 운영 서버에 올라가는 바이너리를 책임지는 개발자가 되기 위한 마지막 관문입니다.

이 장에서 배울 것

  • Makefile의 규칙·변수·자동 변수·패턴 규칙을 이해하고, 헤더 의존성까지 자동으로 추적하는 실무형 Makefile을 작성합니다.
  • 정적 라이브러리(.a)와 동적 라이브러리(.so)를 직접 만들고, -fPIC, soname, LD_LIBRARY_PATH, rpath의 의미를 설명할 수 있습니다.
  • "undefined reference" 링크 오류의 원인인 링크 순서 문제를 링커의 동작 원리로 설명하고, nm·ldd·objdump로 진단합니다.
  • 성능 최적화는 반드시 측정에서 출발한다는 원칙 아래 time, gprof, perf를 사용합니다.
  • 캐시 계층과 지역성을 이해하고, 행 우선 순회·메모리 풀·I/O 버퍼링으로 실제 성능을 끌어올립니다.
  • -O2 최적화에서 미정의 동작(UB)이 어떻게 "멀쩡하던 코드"를 망가뜨리는지 사례로 익힙니다.
  • AIX·HP-UX·Linux의 차이, LP64와 LLP64, 엔디안, 정렬, 컴파일러 차이를 고려한 이식성 있는 코드를 작성합니다.

31-1make와 라이브러리

19장에서 분할 컴파일을 배울 때 우리는 소스 파일 두세 개를 gcc a.c b.c main.c 처럼 한 줄로 컴파일했습니다. 그런데 실제 은행 계정계 시스템은 어떨까요? 수신(예금)·여신(대출)·외환·공통 모듈을 합치면 C 소스 파일이 수천 개, 줄 수로는 수백만 줄에 이릅니다. 이 모든 파일을 매번 처음부터 다시 컴파일하면 수십 분에서 몇 시간이 걸립니다. 이번 절에서는 "바뀐 것만 다시 만드는" 도구인 make와, 공통 코드를 묶어 여러 프로그램이 함께 쓰게 하는 라이브러리를 깊이 있게 다룹니다.

빌드 도구가 필요한 이유: 의존성 그래프

C 프로그램이 실행 파일이 되는 과정을 다시 떠올려 봅시다. 각 .c 파일은 전처리 → 컴파일 → 어셈블을 거쳐 오브젝트 파일(.o)이 되고, 링커가 여러 .o와 라이브러리를 묶어 하나의 실행 파일을 만듭니다. 여기서 중요한 관찰이 하나 있습니다. .c 파일 하나를 고쳤다면 그 파일의 .o만 다시 만들고 링크만 다시 하면 된다는 것입니다. 다른 .o는 이미 최신이므로 건드릴 필요가 없습니다.

단, 헤더 파일은 이야기가 다릅니다. account.h에 있는 구조체의 필드 하나를 바꾸면, 그 헤더를 #include하는 모든 .c 파일을 다시 컴파일해야 합니다. 구조체 크기와 필드 오프셋이 바뀌었기 때문에, 예전 오프셋으로 컴파일된 .o가 섞이면 메모리를 엉뚱한 위치에서 읽는 무서운 버그가 생깁니다. 이렇게 "무엇이 무엇에 의존하는가"를 그림으로 그린 것을 의존성 그래프라고 합니다.

사람이 이 그래프를 머릿속에 넣고 "account.h를 고쳤으니 main.c, account.c, txn.c를 다시 컴파일하고 링크해야지" 하고 판단하는 것은 파일이 몇 개일 때나 가능합니다. 파일이 수천 개가 되면 반드시 빠뜨리게 되고, 빠뜨린 결과는 "가끔 잔액이 이상하게 나오는" 재현 불가능한 버그로 돌아옵니다. make는 이 그래프를 파일(Makefile)로 기술해 두면, 각 파일의 수정 시각(타임스탬프)을 비교해서 다시 만들어야 할 것만 정확히 다시 만들어 주는 도구입니다.

왜 그럴까? — make는 왜 타임스탬프로 판단할까

make는 파일 내용을 비교하지 않습니다. 대신 "타깃 파일의 수정 시각이 그것이 의존하는 파일들 중 하나라도 더 오래되었는가?"만 봅니다. 파일 시스템은 파일마다 마지막 수정 시각(mtime)을 기록하고 있어서, stat() 시스템 호출 한 번이면 값을 얻을 수 있습니다. 내용을 해시로 비교하는 것보다 압도적으로 빠르기 때문에, 1970년대에 만들어진 make가 이 방식을 택했고 지금까지 이어져 왔습니다.

이 단순함에는 대가가 있습니다. 서버 간 시계가 어긋난 NFS 공유 디렉터리에서 빌드하면 "미래의 파일"이 생겨 make가 계속 재빌드하거나, 반대로 재빌드를 건너뛸 수 있습니다. 소스를 백업에서 복원하면서 mtime이 옛날 값으로 돌아가도 같은 문제가 생깁니다. 그래서 운영 배포용 빌드는 항상 make clean 후 전체 빌드(clean build)로 하는 것이 원칙입니다.

Makefile 규칙의 기본

Makefile은 규칙(rule)의 모음입니다. 규칙 하나는 다음 세 부분으로 이루어집니다.

  • 타깃: 만들고자 하는 파일 이름(예: account.o, bankd).
  • 선행조건: 타깃을 만들기 위해 필요한 파일들. 이 중 하나라도 타깃보다 새것이면 레시피를 실행합니다.
  • 레시피: 실제로 실행할 셸 명령. 반드시 탭(Tab) 문자로 시작해야 합니다. 공백 4칸이면 *** missing separator. Stop. 오류가 납니다.

앞의 의존성 그래프를 그대로 Makefile로 옮기면 다음과 같습니다.

처음 make를 실행하면 오브젝트 파일이 하나도 없으므로 전부 컴파일됩니다. 이제 txn.c만 고치고 다시 make를 실행해 봅시다.

txn.o만 다시 만들고 링크만 다시 했습니다. 아무것도 바뀌지 않았다면 "up to date"라며 아무 일도 하지 않습니다. make가 내부에서 하는 일을 단계로 풀어 보겠습니다.

  1. 기본 타깃 bankd를 만들려고 합니다. 먼저 선행조건 main.o, account.o, txn.o 각각을 재귀적으로 최신 상태로 만듭니다.
  2. main.o의 선행조건 main.c, account.h의 mtime을 main.o의 mtime과 비교합니다. 둘 다 더 오래되었으므로 아무것도 하지 않습니다. account.o도 마찬가지입니다.
  3. txn.o는 txn.c보다 오래되었으므로 레시피 gcc -Wall -c txn.c를 실행합니다. 이제 txn.o가 가장 새 파일이 됩니다.
  4. 돌아와서 bankd와 선행조건을 비교합니다. 방금 만든 txn.o가 bankd보다 새것이므로 링크 레시피를 실행합니다.

자주 하는 실수 — 탭 대신 공백

에디터가 탭을 공백으로 자동 변환하도록 설정되어 있으면 레시피 줄이 공백으로 시작하게 되고, make는 Makefile:2: *** missing separator. Stop.라는 알쏭달쏭한 오류를 냅니다. vi에서는 :set list로 탭이 ^I로 보이는지 확인하고, VS Code에서는 Makefile에 대해 "Insert Spaces"를 끄십시오. cat -A Makefile로 확인하면 탭은 ^I로 표시됩니다.

변수와 자동 변수

1단계 Makefile은 컴파일 옵션 -Wall이 세 번, 오브젝트 목록이 두 번 반복됩니다. 옵션을 -O2로 바꾸려면 세 군데를 다 고쳐야 합니다. 변수를 쓰면 이런 반복이 사라집니다.

여기서 $@, $<, $^는 자동 변수입니다. 규칙마다 make가 자동으로 값을 채워 줍니다.

자동 변수의미txn.o: txn.c account.h 규칙에서의 값
$@타깃 이름txn.o
$<첫 번째 선행조건txn.c
$^모든 선행조건(중복 제거)txn.c account.h
$?타깃보다 새로운 선행조건만예: txn.c
$*패턴 규칙에서 %에 매치된 부분(stem)txn

컴파일 규칙에서 $<를 쓰는 이유를 생각해 봅시다. 만약 $^를 쓰면 gcc -c -o txn.o txn.c account.h가 실행되는데, 헤더 파일을 gcc에 직접 넘기면 gcc는 그것을 미리 컴파일된 헤더(.gch)로 만들려 하거나 "-o와 여러 입력 파일을 함께 쓸 수 없다"는 오류를 냅니다. 컴파일할 대상은 .c 하나뿐이고 헤더는 "바뀌었는지 감시만 할 대상"이므로 $<가 맞습니다. 반면 링크 규칙에서는 모든 .o가 필요하므로 $^를 씁니다.

= 와 := 의 차이

make 변수에는 대입 방식이 두 가지 있습니다. 이 차이는 면접에서도 가끔 나오고, 큰 Makefile에서 미묘한 버그의 원인이 됩니다.

연산자이름평가 시점특징

?=조건부 대입정의되지 않았을 때만환경 변수나 명령줄 값을 기본값으로 둘 때
+=덧붙이기원래 변수의 방식을 따름CFLAGS += -DDEBUG

X2는 대입 시점에 Y가 아직 정의되지 않아 빈 문자열로 확정되었습니다. 레시피 앞의 @는 "실행하는 명령 자체는 화면에 찍지 말라"는 뜻입니다.

여기서 잠깐 — 명령줄에서 변수 덮어쓰기

make CFLAGS="-O0 -g3"처럼 명령줄에서 지정한 변수는 Makefile 안의 대입보다 우선합니다. 장애 분석용 디버그 빌드를 잠깐 만들 때 Makefile을 고치지 않아도 되므로 매우 편리합니다. 반대로 Makefile에서 무조건 지켜야 하는 옵션은 override CFLAGS += -fno-strict-aliasing처럼 override를 붙입니다.

패턴 규칙과 가짜(phony) 타깃

2단계 Makefile에도 여전히 "X.o는 X.c를 컴파일해서 만든다"는 똑같은 규칙이 파일 수만큼 반복됩니다. 패턴 규칙은 %를 와일드카드처럼 써서 이 반복을 하나로 줄입니다.

몇 가지 문법을 짚고 넘어갑시다.

  • $(SRCS:.c=.o)는 치환 참조로, main.o account.o txn.o가 됩니다. $(patsubst %.c,%.o,$(SRCS))와 같습니다.
  • 레시피 없이 선행조건만 적은 규칙($(OBJS): account.h)은 기존 규칙에 선행조건을 덧붙입니다. 그래서 각 .o는 자기 .c와 account.h 둘 다에 의존하게 됩니다.
  • .PHONY는 "이 타깃은 파일이 아니다"라고 선언합니다.

왜 그럴까? — .PHONY가 없으면 무슨 일이 생기나

make는 타깃을 기본적으로 파일 이름으로 해석합니다. 누군가 실수로 디렉터리에 clean이라는 이름의 파일을 만들었다고 해 봅시다(예: ./batch > clean 처럼 출력 리다이렉션을 잘못 썼을 때). 그러면 make clean은 "clean 파일이 이미 있고, 선행조건이 없으니 최신이다"라고 판단해서 make: 'clean' is up to date.라고만 하고 아무것도 지우지 않습니다. 운영 배포 직전에 clean이 동작하지 않아 옛 .o가 섞여 들어가면 심각한 사고로 이어집니다. .PHONY: clean으로 선언하면 make는 같은 이름의 파일이 있든 없든 항상 레시피를 실행합니다. 덤으로 파일 존재 여부를 검사하지 않으므로 아주 조금 빨라집니다.

여기서 잠깐 — 내장 규칙

사실 GNU make에는 %.o: %.c 규칙이 이미 내장(built-in)되어 있습니다. 레시피는 $(CC) $(CPPFLAGS) $(CFLAGS) -c -o $@ $<입니다. 그래서 컴파일 규칙을 아예 적지 않아도 동작합니다. 그러나 실무에서는 빌드 동작을 명확히 보여 주기 위해 직접 적는 경우가 많습니다. make -p로 내장 규칙과 변수를 모두 볼 수 있고, make -r로 내장 규칙을 끌 수 있습니다. 변수 이름 관례도 기억해 두십시오: 전처리기 옵션(-I, -D)은 CPPFLAGS, 컴파일 옵션은 CFLAGS, 링커 옵션(-L, -Wl,...)은 LDFLAGS, 라이브러리(-lm)는 LDLIBS에 넣습니다.

자주 하는 실수 — 병렬 빌드에서만 깨지는 Makefile

make로는 잘 되는데 make -j8에서는 가끔 실패한다면, 선행조건이 빠진 규칙이 있다는 신호입니다. 예를 들어 gen_code.h를 만드는 규칙이 있는데 그 헤더를 쓰는 .o의 선행조건에 gen_code.h를 적지 않았다면, 순차 빌드에서는 "우연히" 순서가 맞아 성공하지만 병렬 빌드에서는 헤더가 생기기 전에 컴파일이 시작될 수 있습니다. 해결: 의존성은 "순서상 먼저 실행된다"에 기대지 말고 반드시 명시적으로 선언합니다.

헤더 의존성 자동 생성

3단계 Makefile에는 아직 큰 약점이 있습니다. $(OBJS): account.h처럼 헤더 의존성을 손으로 적었다는 점입니다. 누군가 txn.c에 #include "msg.h"를 추가하고 Makefile을 고치지 않으면, msg.h가 바뀌어도 txn.o는 다시 컴파일되지 않습니다. 이것이 바로 앞에서 말한 "구조체 레이아웃 불일치" 사고의 전형적인 원인입니다.

해결책은 컴파일러에게 의존성을 계산시키는 것입니다. 전처리기는 어차피 #include를 모두 따라가므로, 어떤 헤더가 포함되었는지 정확히 알고 있습니다. gcc의 -MMD -MP 옵션을 주면 컴파일하면서 .d 파일에 의존성 규칙을 적어 줍니다.

옵션의미
-M의존성 규칙만 출력하고 컴파일은 하지 않음(시스템 헤더 포함)
-MM-M과 같되 <stdio.h> 같은 시스템 헤더는 제외
-MD / -MMD컴파일은 정상적으로 하면서 부산물로 .d 파일 생성
-MP각 헤더에 대해 빈 규칙(txn.h:)을 추가
-MF file의존성 파일 이름 지정

왜 그럴까? — -MP의 빈 규칙은 왜 필요할까

어떤 헤더 old.h를 더 이상 쓰지 않게 되어 삭제했다고 합시다. 그런데 이전 빌드에서 만들어진 txn.d에는 여전히 txn.o: ... old.h가 적혀 있습니다. make는 old.h를 만들 방법을 찾다가 없으므로 No rule to make target 'old.h' 오류로 멈춥니다. -MP가 추가하는 old.h:라는 빈 규칙은 "이 파일을 만드는 방법은 '아무것도 안 하기'다"라고 알려 주므로, 파일이 없어도 오류 없이 넘어가고 txn.o는 재컴파일되면서 새 .d가 만들어집니다.

이제 실무에서 그대로 쓸 수 있는 Makefile을 완성해 봅시다. 소스는 src/, 오브젝트와 .d는 build/에 분리해 소스 트리를 깨끗하게 유지합니다.

새로 등장한 문법을 정리합니다.

  • $(wildcard src/*.c): 패턴에 맞는 파일 목록을 얻습니다. 새 소스 파일을 추가해도 Makefile을 고칠 필요가 없습니다.
  • | $(BUILDDIR): 파이프 뒤는 순서 전용 선행조건(order-only prerequisite)입니다. "디렉터리가 존재해야 하지만, 디렉터리의 mtime이 바뀌었다고 재빌드하지는 마라"는 뜻입니다. 디렉터리 mtime은 안에 파일이 생길 때마다 바뀌므로 일반 선행조건으로 두면 매번 전체가 재빌드됩니다.
  • debug: CFLAGS := ...: 타깃별 변수입니다. debug 타깃과 그 선행조건을 만들 때만 적용됩니다.
  • -include $(DEPS): .d 파일들을 Makefile의 일부로 읽어들입니다. 앞의 -는 파일이 없어도 무시하라는 뜻입니다.
  • DEPFLAGS = ...에는 :=가 아니라 =를 썼습니다. $@는 규칙 실행 시점에만 값이 있으므로, 사용할 때 확장되는 재귀 확장 변수여야 합니다.

예제 31-1 난이도 ★★☆

다음 Makefile에서 common.h를 수정한 뒤 make를 실행했더니 아무것도 다시 컴파일되지 않았습니다. main.c와 calc.c 모두 common.h를 포함합니다. 원인과 해결 방법을 설명하십시오.

정답과 해설 보기

패턴 규칙 %.o: %.c는 .o가 .c에만 의존한다고 선언합니다. make는 common.h라는 파일이 이 빌드와 관련 있다는 사실을 전혀 모릅니다. 따라서 common.h의 mtime이 바뀌어도 비교 대상이 아니므로 "최신"으로 판단합니다.

해결 방법은 두 가지입니다. ① 손으로 main.o calc.o: common.h 규칙을 추가합니다. ② 더 좋은 방법은 컴파일러가 의존성을 생성하게 하는 것입니다. 이렇게 하면 앞으로 헤더가 추가되어도 Makefile을 고칠 필요가 없습니다.

정적 라이브러리: ar로 오브젝트 묶기

은행에는 업무와 상관없이 모든 프로그램이 쓰는 공통 기능이 있습니다. 영업일 계산(휴일 달력), 금액 반올림, 계좌번호 검증(체크디지트), 전문 필드 변환, 로그 출력, 암호화 같은 것들입니다. 이 코드를 각 업무팀이 복사해서 쓰면 버그 수정이 한 곳에만 반영되는 재앙이 생깁니다. 그래서 공통팀이 라이브러리로 만들어 배포합니다.

정적 라이브러리(static library)는 오브젝트 파일 여러 개를 하나의 아카이브 파일로 묶은 것입니다. 유닉스에서는 확장자가 .a(archive)이고, 이름은 관례상 lib으로 시작합니다. 예제로 쓸 공통 모듈 두 개를 먼저 만들어 봅시다.

이제 정적 라이브러리를 만들고 사용합니다.

$ gcc -std=c11 -Wall -O2 -Iinclude -c src/acctchk.c -o acctchk.o
$ gcc -std=c11 -Wall -O2 -Iinclude -c src/amount.c  -o amount.o
$ ar rcs libfincomm.a acctchk.o amount.o     # 아카이브 생성
$ ar t libfincomm.a                           # 목록 확인
acctchk.o
amount.o
$ gcc -Iinclude -o feecalc feecalc.c -L. -lfincomm
  • ar rcs: r은 아카이브에 넣기(있으면 교체), c는 아카이브가 없으면 조용히 생성, s는 심볼 인덱스 생성(ranlib과 같은 효과)입니다. 인덱스가 있어야 링커가 "이 심볼은 어느 멤버에 있는가"를 빠르게 찾습니다.
  • -L.: 라이브러리를 찾을 디렉터리에 현재 디렉터리를 추가합니다.
  • -lfincomm: libfincomm.a(또는 libfincomm.so)를 찾아 링크하라는 뜻입니다. 앞의 lib과 뒤의 확장자를 빼고 씁니다. 같은 디렉터리에 .so와 .a가 모두 있으면 링커는 기본적으로 .so를 우선합니다. 정적 링크를 강제하려면 -Wl,-Bstatic -lfincomm -Wl,-Bdynamic 또는 파일 경로(./libfincomm.a)를 직접 줍니다.

체크디지트를 손으로 확인해 봅시다. 110123456789를 오른쪽부터 읽으면 9,8,7,6,5,4,3,2,1,0,1,1입니다. Luhn 알고리즘은 오른쪽에서 두 번째 자리부터 한 칸 건너 하나씩(8,6,4,2,0,1) 2배 하고, 결과가 9를 넘으면 9를 뺍니다: 16→7, 12→3, 8, 4, 0, 2 → 합 24. 나머지 자리(9,7,5,3,1,1)의 합은 26. 총합 50이 10의 배수이므로 정상입니다. 마지막 자리를 다른 숫자로 바꾸면 총합이 10의 배수가 아니게 되어 오류로 판정됩니다. 수수료는 12,345,678 × 15 / 10000 = 18,518.5167 → 원 미만 절사하여 18,518원입니다.

왜 그럴까? — 링커는 아카이브에서 "오브젝트 단위"로 가져온다

정적 링크에서 링커는 아카이브 전체를 실행 파일에 넣지 않습니다. 아직 정의를 찾지 못한(미해결) 심볼이 있을 때, 그 심볼을 정의하는 멤버 오브젝트 파일 전체를 가져옵니다. 함수 하나 단위가 아니라 .o 하나 단위입니다. 그래서 거대한 util.c에 함수 100개를 넣어 두면, 그중 하나만 써도 100개가 모두 실행 파일에 들어갑니다. 공통 라이브러리를 "파일 하나에 함수 하나 또는 관련 함수 묶음" 단위로 쪼개는 이유가 여기에 있습니다. (gcc의 -ffunction-sections와 링커의 --gc-sections를 함께 쓰면 함수 단위로 제거할 수도 있습니다.)

동적 라이브러리(.so)와 -fPIC

정적 라이브러리는 단순하고 배포가 쉽지만 두 가지 단점이 있습니다. 첫째, 라이브러리를 쓰는 프로그램이 200개라면 같은 코드 사본이 200개의 실행 파일과 200개 프로세스의 메모리에 각각 들어갑니다. 둘째, 공통 라이브러리에서 버그를 고치면 그것을 쓰는 모든 프로그램을 다시 링크해서 재배포해야 합니다.

동적 라이브러리(shared library, 공유 라이브러리)는 이 문제를 해결합니다. 실행 파일에는 "libfincomm.so.1이 필요하다"는 기록만 남고, 실제 코드는 프로그램이 시작될 때 동적 링커(ld.so, 리눅스에서는 /lib64/ld-linux-x86-64.so.2)가 메모리에 올려 연결합니다. 여러 프로세스가 같은 .so를 쓰면 운영체제는 코드 영역을 물리 메모리 한 벌만 두고 각 프로세스의 가상 주소 공간에 매핑합니다.

$ gcc -std=c11 -Wall -O2 -Iinclude -fPIC -c src/acctchk.c -o acctchk.o
$ gcc -std=c11 -Wall -O2 -Iinclude -fPIC -c src/amount.c  -o amount.o
$ gcc -shared -Wl,-soname,libfincomm.so.1 -o libfincomm.so.1.2.0 acctchk.o amount.o
$ ln -sf libfincomm.so.1.2.0 libfincomm.so.1     # 실행 시 찾는 이름(soname)
$ ln -sf libfincomm.so.1     libfincomm.so       # 링크 시 -lfincomm이 찾는 이름
$ gcc -Iinclude -o feecalc feecalc.c -L. -lfincomm

-fPIC: 위치 독립 코드

-fPIC(Position Independent Code)는 어느 주소에 적재되어도 수정 없이 동작하는 기계어를 만들라는 옵션입니다. 왜 이것이 필요할까요?

왜 그럴까? — 공유 라이브러리는 왜 위치 독립이어야 할까

실행 파일은 보통 정해진 주소(또는 PIE라면 프로세스마다 하나의 기준 주소)에 적재되지만, 공유 라이브러리는 프로세스마다 서로 다른 주소에 매핑될 수 있습니다. 프로세스 A에서는 0x7f12_3400_0000에, 프로세스 B에서는 0x7f98_aa00_0000에 올라갈 수 있습니다(ASLR 때문에 매번 바뀝니다).

만약 기계어 안에 "전역 변수 g_count는 절대 주소 0x601040에 있다"처럼 절대 주소가 박혀 있다면, 적재할 때마다 그 주소들을 고쳐 써야(재배치, relocation) 합니다. 코드 페이지를 고쳐 쓰는 순간 그 페이지는 프로세스 전용 사본이 되어(copy-on-write) 더 이상 공유되지 않습니다. 공유 라이브러리를 쓰는 의미가 사라지는 것입니다.

PIC 코드는 절대 주소 대신 "현재 명령어 위치(PC/RIP)로부터 얼마 떨어진 곳"이라는 상대 주소를 씁니다. 외부 심볼의 주소는 GOT(Global Offset Table)라는 데이터 영역의 표를 통해 간접적으로 얻고, 외부 함수 호출은 PLT(Procedure Linkage Table)를 거칩니다. 고쳐 써야 할 것은 데이터 영역인 GOT뿐이므로 코드 페이지는 모든 프로세스가 공유할 수 있습니다. x86-64에서 -fPIC 없이 만든 오브젝트로 .so를 만들려고 하면 relocation R_X86_64_32 against ... can not be used when making a shared object; recompile with -fPIC 오류가 납니다.

soname과 버전 관리

위에서 이름이 세 개나 등장했습니다. 각각의 역할이 다릅니다.

이름예누가 쓰나설명
실제 파일 이름(real name)libfincomm.so.1.2.0파일 시스템주(major).부(minor).패치 버전
sonamelibfincomm.so.1실행 시 동적 링커실행 파일의 NEEDED 항목에 기록됨. 주 버전만 포함
링커 이름(linker name)libfincomm.so빌드 시 -lfincomm개발 환경에만 있으면 됨

핵심 규칙은 ABI(이진 호환성)를 깨면 주 버전을 올린다는 것입니다. 함수를 추가하거나 버그를 고치는 것은 기존 실행 파일과 호환되므로 1.2.0 → 1.3.0으로 올리고 심볼릭 링크 libfincomm.so.1만 새 파일을 가리키게 하면, 재링크 없이 모든 프로그램이 새 라이브러리를 씁니다. 그러나 함수의 인자 타입이나 공개 구조체의 크기를 바꿨다면 libfincomm.so.2로 새 soname을 써야 합니다. 그래야 옛 프로그램은 계속 .so.1을 쓰고, 새로 빌드한 프로그램만 .so.2를 씁니다.

자주 하는 실수 — 공개 구조체에 필드를 추가하고 주 버전을 안 올림

공통팀이 typedef struct { char acct[13]; long long bal; } FcAcct;에 int status;를 중간에 추가하고 .so.1 그대로 배포했다고 합시다. 재컴파일하지 않은 업무 프로그램들은 여전히 옛 크기(24바이트)로 구조체를 할당해 넘기는데, 새 라이브러리는 새 레이아웃(32바이트)으로 읽고 씁니다. 결과는 스택 오염과 엉뚱한 잔액입니다. 해결: 공개 헤더의 구조체를 바꿀 때는 주 버전을 올리거나, 처음부터 구조체를 불투명 포인터(typedef struct FcAcct FcAcct;)로 감추고 생성·접근 함수만 공개합니다(ch17 참조).

실행 시 라이브러리 찾기: LD_LIBRARY_PATH와 rpath

방금 만든 feecalc를 실행하면 대부분 다음과 같이 실패합니다.

빌드할 때 -L.로 위치를 알려 줬는데 왜 못 찾을까요? -L은 빌드 시 링커(ld)에게만 하는 말이고, 실행 시 라이브러리를 찾는 것은 동적 링커(ld.so)라는 전혀 다른 프로그램이기 때문입니다. 동적 링커는 다음 순서로 라이브러리를 찾습니다(리눅스 glibc 기준).

  1. 실행 파일에 기록된 DT_RPATH(DT_RUNPATH가 없을 때만)
  2. 환경 변수 LD_LIBRARY_PATH에 적힌 디렉터리들
  3. 실행 파일에 기록된 DT_RUNPATH
  4. /etc/ld.so.cache (/etc/ld.so.conf에 등록된 디렉터리를 ldconfig로 캐싱)
  5. 기본 디렉터리 /lib, /usr/lib (64비트는 /lib64, /usr/lib64 등)
# 방법 1: 환경 변수 (개발·테스트용)
$ export LD_LIBRARY_PATH=/app/fincomm/lib:$LD_LIBRARY_PATH
$ ./feecalc

# 방법 2: rpath를 실행 파일에 기록 ($ORIGIN = 실행 파일이 있는 디렉터리)
$ gcc -o feecalc feecalc.c -Iinclude -L../lib -lfincomm -Wl,-rpath,'$ORIGIN/../lib'

# 방법 3: 시스템에 등록 (root 권한, 서버 표준 위치에 설치할 때)
$ echo /app/fincomm/lib | sudo tee /etc/ld.so.conf.d/fincomm.conf
$ sudo ldconfig

은행 시스템에서는 — LD_LIBRARY_PATH 사고

운영 서버에서 가장 흔한 라이브러리 장애는 "배치는 잘 도는데 cron으로 돌리면 실패한다"입니다. 개발자가 로그인 셸의 .profile에 LD_LIBRARY_PATH를 설정해 두었기 때문에 수동 실행은 되지만, cron이나 배치 스케줄러(Control-M 같은 작업 스케줄러)는 로그인 셸 환경을 읽지 않으므로 라이브러리를 못 찾는 것입니다. 또 하나는 테스트 서버의 LD_LIBRARY_PATH에 개발용 라이브러리 경로가 앞쪽에 남아 있어, 운영 반영 직전 검증이 엉뚱한 버전으로 이루어지는 사고입니다.

그래서 금융권 운영 표준은 보통 ① 배치 실행 래퍼 스크립트가 환경 변수를 명시적으로 처음부터 설정하고, ② 운영 바이너리에는 고정된 설치 경로를 rpath(또는 RUNPATH)로 기록하며, ③ 배포 후 반드시 ldd로 실제 연결되는 라이브러리 경로를 점검 항목으로 남기는 방식을 씁니다. 또한 LD_LIBRARY_PATH는 setuid 프로그램에서는 보안상 무시된다는 점도 알아 두십시오.

링크 순서 문제: undefined reference의 정체

C 개발자가 평생 가장 많이 보는 링크 오류는 undefined reference to `...'입니다. 원인은 크게 세 가지입니다. ① 함수를 정말 정의하지 않았거나, ② 정의한 오브젝트·라이브러리를 링크 명령에 넣지 않았거나, ③ 넣었는데 순서가 틀렸습니다. 세 번째가 가장 당황스럽습니다.

왜 그럴까? — 링커는 왼쪽에서 오른쪽으로 한 번만 훑는다

GNU ld는 명령줄의 입력을 왼쪽에서 오른쪽으로 한 번 처리하면서 "아직 정의를 못 찾은 심볼 목록(미해결 목록)"을 관리합니다.

  • 오브젝트 파일(.o)을 만나면 무조건 전부 포함하고, 그 안의 정의는 해결 목록에, 그 안에서 참조만 하는 심볼은 미해결 목록에 추가합니다.
  • 아카이브(.a)를 만나면 현재 미해결 목록에 있는 심볼을 정의하는 멤버만 꺼내 포함합니다. 그리고 아카이브를 지나가면 다시 돌아보지 않습니다.

잘못된 예에서는 -lfincomm을 먼저 만났을 때 미해결 목록이 비어 있습니다. 아무도 fc_acct_valid를 원하지 않았으니 아무것도 꺼내지 않고 지나갑니다. 그다음 feecalc.o를 처리하면서 비로소 fc_acct_valid가 미해결 목록에 들어가지만, 라이브러리는 이미 지나갔으므로 끝까지 해결되지 않습니다. 그래서 규칙은 "사용하는 쪽이 왼쪽, 제공하는 쪽이 오른쪽"입니다.

공유 라이브러리도 요즘 배포판(Ubuntu 등)은 링커에 --as-needed가 기본으로 켜져 있어서, 그 시점에 필요 없는 .so는 NEEDED에 기록하지 않습니다. 따라서 .so도 순서를 지키는 것이 안전합니다.

라이브러리끼리 서로 참조할 때

업무 라이브러리 libdeposit.a가 공통 라이브러리 libfincomm.a의 함수를 쓰면 순서는 -ldeposit -lfincomm이어야 합니다. 더 곤란한 경우는 두 라이브러리가 서로 참조하는 순환 의존입니다. 이때는 한쪽을 두 번 적거나(-la -lb -la), 링커 그룹을 씁니다.

$ gcc main.o -Wl,--start-group -ldeposit -lfincomm -Wl,--end-group -o app

--start-group ... --end-group 사이의 아카이브들은 더 이상 새로 해결되는 심볼이 없을 때까지 반복해서 훑습니다. 편리하지만 링크가 느려지고 설계상 순환 의존을 숨기므로, 근본적으로는 모듈 구조를 정리하는 것이 좋습니다.

여기서 잠깐 — 다른 원인의 undefined reference

  • 수학 함수: sqrt, pow 등은 리눅스에서 libm에 있으므로 맨 뒤에 -lm을 붙입니다.
  • C++ 이름 맹글링: C++로 컴파일된 라이브러리 함수를 C에서 부르거나 그 반대일 때. C++ 쪽 선언을 extern "C"로 감쌉니다.
  • static 함수: 다른 파일에서 쓰려는 함수가 static으로 선언되어 있으면 외부 링크가 없으므로 찾을 수 없습니다.
  • 32/64비트 혼용: 64비트 실행 파일에 32비트 라이브러리를 링크하면 "skipping incompatible ... when searching for -lfincomm" 경고 후 undefined reference가 납니다.

심볼 확인: nm, ldd, objdump

링크 오류를 감으로 고치지 말고 도구로 확인하는 습관을 들여야 합니다. 핵심 도구 세 가지를 익혀 둡시다.

nm — 오브젝트·라이브러리의 심볼 목록

기호의미
T / t코드(.text) 영역에 정의된 심볼. 대문자는 외부 공개, 소문자는 static(파일 내부)
D / d초기화된 데이터(.data)에 정의된 전역/정적 변수
B / b초기화되지 않은 데이터(.bss)
R / r읽기 전용 데이터(.rodata) — const 전역, 문자열 상수 등
U정의되지 않음(Undefined) — 다른 곳에서 찾아야 함
W약한(weak) 심볼 — 강한 정의가 있으면 그것에 밀림

"fc_acct_valid가 undefined라는데 라이브러리에 있긴 한가?"는 nm -A libfincomm.a | grep fc_acct_valid 한 줄로 확인됩니다. T로 나오면 있는 것이고 순서 문제를 의심합니다. 아무것도 안 나오거나 t(소문자)로 나오면 정의가 없거나 static입니다. 공유 라이브러리는 nm -D libfincomm.so로 동적 심볼 테이블을 봅니다. C++ 심볼은 nm -C로 맹글링을 풀어 볼 수 있습니다.

ldd — 실행 파일이 실제로 연결할 공유 라이브러리

못 찾는 라이브러리는 libfincomm.so.1 => not found로 표시됩니다. 주의할 점: ldd는 내부적으로 동적 링커를 특별 모드로 실행하므로, 신뢰할 수 없는 실행 파일에 ldd를 쓰면 안 됩니다. 그런 경우 objdump -p file | grep NEEDED로 정적으로만 확인합니다.

예제 31-2 난이도 ★★☆

배치 프로그램 링크 시 undefined reference to `fc_holiday_next'가 났습니다. nm -A libfincomm.a | grep fc_holiday_next의 결과가 libfincomm.a:holiday.o:0000000000000140 t fc_holiday_next였습니다. 원인은 무엇입니까?

정답과 해설 보기

기호가 소문자 t이므로 fc_holiday_next는 holiday.c 안에서 static 함수로 정의되어 있습니다. static 함수는 내부 링크(internal linkage)를 가지므로 해당 파일 밖에서는 이름으로 찾을 수 없습니다. 순서를 아무리 바꿔도 해결되지 않습니다. 공통팀에 공개 API로 만들어 달라고 요청하거나(헤더에 선언하고 static 제거), 공개된 다른 함수(예: fc_holiday_add)를 써야 합니다. 링크 오류는 "있는지(T/t/U)" → "순서" → "비트 수/이름 맹글링" 순으로 점검합니다.

금융권 공통 라이브러리 배포 구조

지금까지 배운 것을 모아, 실제 금융권에서 흔히 볼 수 있는 빌드·배포 구조를 그려 봅시다. 기관마다 세부는 다르지만 큰 틀은 비슷합니다.

  • 빌드 서버 단일화: 개발자 PC에서 만든 바이너리는 운영에 올리지 않습니다. 운영과 동일한 OS 버전·컴파일러 버전·옵션으로 빌드 서버에서 clean build한 결과만 배포합니다. 어떤 소스 리비전으로 만들었는지 바이너리에 버전 문자열로 박아 두는 것도 흔한 관행입니다(-DBUILD_REV=\"r1234\" 후 what/strings로 확인).
  • 헤더와 라이브러리는 한 쌍: include/와 lib/를 같은 버전으로 함께 배포합니다. 헤더는 새 버전인데 라이브러리는 옛 버전이면 앞에서 본 ABI 불일치가 생깁니다.
  • 심볼릭 링크 교체로 무중단 반영: 새 파일 libfincomm.so.2.4.2를 먼저 복사해 두고, 링크 libfincomm.so.2를 원자적으로 바꿉니다(ln -sfn 또는 임시 링크 후 mv -T). 이미 실행 중인 프로세스는 옛 파일을 계속 쓰고(열려 있는 파일은 삭제해도 inode가 유지됨), 재기동하는 프로세스부터 새 버전을 씁니다.
  • 롤백 계획: 옛 버전 파일을 지우지 않고 남겨 두면, 장애 시 링크만 되돌리고 재기동하면 됩니다.
  • 정적 vs 동적 선택: 대외계 단말 통신 모듈처럼 독립 배포가 중요한 프로그램은 정적 링크로 "자기 완결적" 바이너리를 만들기도 하고, 온라인 서버 수백 개가 공유하는 공통 모듈은 동적 라이브러리로 만듭니다.

은행 시스템에서는 — 배포 체크리스트

운영 반영 절차서에는 보통 다음 항목이 들어갑니다. ① 반영 대상 파일 목록과 각 파일의 체크섬(sha256sum) ② file로 확인한 비트 수·아키텍처 ③ ldd(또는 AIX의 dump -H)로 확인한 의존 라이브러리 경로 ④ 버전 문자열 ⑤ 반영 순서(라이브러리 먼저, 업무 바이너리 나중) ⑥ 재기동 대상 프로세스 ⑦ 롤백 방법. "파일만 복사하면 끝"이라고 생각하는 순간 사고가 납니다.

한 줄 요약

make는 의존성 그래프와 타임스탬프로 "바뀐 것만" 다시 만들고, 헤더 의존성은 -MMD -MP로 컴파일러에게 맡깁니다. 정적 라이브러리는 링크 시 필요한 .o를 복사하고, 동적 라이브러리는 실행 시 동적 링커가 찾아 연결하며, 링크 순서는 "쓰는 쪽 왼쪽, 주는 쪽 오른쪽"입니다.

31-2성능 최적화와 이식성

"일마감 배치가 영업 개시 전까지 안 끝납니다." 금융권 개발자가 한 번쯤 받게 되는 전화입니다. 계좌 수와 거래량은 해마다 늘어나는데 배치 시간 창(batch window)은 그대로이기 때문입니다. 이번 절의 앞부분은 이런 상황에서 무엇을, 어떤 순서로 해야 하는지를 다루고, 뒷부분은 같은 코드를 AIX·HP-UX·Linux처럼 서로 다른 시스템에서 올바르게 동작시키는 이식성을 다룹니다. 두 주제는 별개처럼 보이지만 "컴파일러와 하드웨어가 실제로 무엇을 하는지 아는 것"이라는 공통 뿌리를 가지고 있습니다.

측정 먼저: 추측하지 말고 재십시오

성능 최적화의 제1원칙은 "측정하지 않은 것은 최적화하지 않는다"입니다. 개발자의 직감은 놀라울 정도로 자주 틀립니다. "이 계산 루프가 무거워 보이니 여기를 고치자" 하고 하루를 쓰고 나서야 실제 시간의 90%가 파일 I/O나 DB 조회에서 쓰이고 있었다는 것을 알게 되는 일이 흔합니다. 도널드 커누스의 유명한 말처럼 성급한 최적화는 만악의 근원이며, 아무리 빠르게 만들어도 전체 시간의 1%를 차지하는 부분은 전체를 1% 이상 줄여 주지 못합니다(암달의 법칙).

왜 그럴까? — 암달의 법칙

전체 실행 시간 중 비율 p인 부분을 s배 빠르게 하면 전체 속도 향상은 1 / ((1 − p) + p/s)입니다. 계산 부분이 전체의 20%일 때 그것을 10배 빠르게 해도 1 / (0.8 + 0.02) ≈ 1.22배에 그칩니다. 반면 80%를 차지하는 I/O를 2배만 빠르게 해도 1 / (0.2 + 0.4) ≈ 1.67배입니다. 그래서 가장 큰 덩어리부터 찾아야 하고, 그것을 찾는 유일한 방법이 측정입니다.

time 명령: 첫 번째 진단

항목의미해석
real벽시계 시간(시작부터 끝까지)사용자가 체감하는 시간
user사용자 모드에서 CPU를 쓴 시간내 코드와 라이브러리의 계산 시간
sys커널 모드에서 CPU를 쓴 시간시스템 호출(read, write, open...) 처리 시간

위 예에서 real은 42초인데 user+sys는 10초 정도입니다. 나머지 32초 동안 프로세스는 CPU를 쓰지 않고 기다리고 있었습니다. 디스크 I/O, 네트워크, 잠금 대기 같은 것들입니다. 이 경우 계산 루프를 최적화해 봐야 최대 6초밖에 줄일 수 없습니다. 반대로 user가 real에 가깝다면 CPU 계산이 병목이고, sys가 크다면 시스템 호출이 너무 잦다는 신호(예: 1바이트씩 read)입니다. 멀티스레드 프로그램에서는 user가 real보다 클 수도 있습니다(여러 코어가 동시에 일했으므로).

코드 안에서 구간 측정

프로그램 전체가 아니라 특정 구간을 재려면 clock_gettime을 씁니다. CLOCK_MONOTONIC은 시스템 시각이 NTP로 조정되어도 뒤로 가지 않으므로 구간 측정에 적합합니다. time()은 초 단위라 너무 거칠고, gettimeofday()는 시각 조정의 영향을 받습니다.

자주 하는 실수 — 측정 자체의 함정

  • 한 번만 재기: 첫 실행은 파일이 페이지 캐시에 없어 느리고, 두 번째부터는 빠릅니다. 최소 3~5회 반복해서 중앙값을 봅니다. 운영 배치의 "첫 실행" 성능이 중요하다면 캐시를 비운 상태(테스트 서버에서만!)도 따로 잽니다.
  • 디버그 빌드로 재기: -O0 빌드는 운영과 전혀 다른 프로파일을 보입니다. 측정은 운영과 같은 옵션으로 합니다.
  • 최적화가 지워 버린 코드 재기: 결과를 쓰지 않는 계산 루프는 -O2에서 통째로 삭제될 수 있습니다. 결과를 출력하거나 volatile 변수에 저장해서 "쓰이게" 만듭니다.
  • 작은 데이터로 재기: 1천 건과 1천만 건은 병목이 다릅니다(1천 건은 전부 캐시에 들어갑니다). 운영 규모의 데이터로 잽니다.

프로파일러: gprof와 perf

time으로 "CPU가 병목이다"를 확인했다면, 다음은 어느 함수가 CPU를 쓰는지 찾을 차례입니다. 이것을 해 주는 도구가 프로파일러입니다.

gprof — 컴파일러가 심어 주는 계측

$ gcc -O2 -pg -o batch_interest batch_interest.c   # -pg: 프로파일링 코드 삽입
$ ./batch_interest accounts.dat                       # 실행 후 gmon.out 생성
$ gprof ./batch_interest gmon.out | head -20

이 결과는 "이자 계산"이 아니라 레코드 파싱(parse_record)이 CPU 시간의 61%를 쓰고 있음을 보여 줍니다. 아마 필드마다 sscanf를 쓰거나 strlen을 반복 호출하고 있을 것입니다. gprof는 두 가지 방법을 섞습니다. -pg가 각 함수 입구에 mcount 호출을 넣어 호출 횟수와 호출 관계를 정확히 세고, 실행 중 일정 간격으로 프로그램 카운터를 샘플링해서 함수별 시간을 추정합니다. 단점은 재컴파일이 필요하고, 공유 라이브러리 안의 시간이나 커널 시간은 잘 보이지 않으며, 멀티스레드 지원이 약하다는 것입니다.

perf — 재컴파일 없는 샘플링 프로파일러(Linux)

$ perf stat ./batch_interest accounts.dat        # 전체 카운터 요약
$ perf record -g ./batch_interest accounts.dat   # 호출 스택 포함 샘플 기록
$ perf report                                     # 대화형으로 함수별 비율 확인

perf는 CPU의 하드웨어 성능 카운터(PMU)를 이용합니다. 사이클 수, 명령어 수, 캐시 미스, 분기 예측 실패 같은 것을 거의 오버헤드 없이 셀 수 있습니다. 위 출력에서 IPC(사이클당 명령어 수)가 0.83으로 낮고 캐시 미스 비율이 높다는 것은 CPU가 계산보다 메모리를 기다리느라 시간을 쓰고 있다는 뜻입니다. 현대 CPU는 사이클당 3~4개 명령어를 처리할 능력이 있으므로 IPC가 1보다 낮으면 메모리 접근 패턴을 의심합니다. 이것이 다음 소절의 주제입니다. (AIX에는 tprof, HP-UX에는 Caliper/prof 같은 각자의 도구가 있습니다.)

은행 시스템에서는 — 배치 성능 개선의 실제 순서

배치 시간 단축 요청을 받았을 때 경험 많은 개발자의 순서는 대체로 이렇습니다. ① 배치 스케줄러의 작업별 소요 시간 이력에서 가장 오래 걸리는 작업과 최근 늘어난 작업 확인 ② time으로 CPU 바운드인지 I/O 바운드인지 구분 ③ DB를 쓰는 배치라면 SQL 실행 계획과 건별 커밋 여부 확인(대부분의 문제가 여기 있음) ④ 파일 배치라면 I/O 단위(버퍼 크기)와 정렬 단계 확인 ⑤ 그다음에야 프로파일러로 C 코드의 핫스팟 확인 ⑥ 마지막으로 작업 분할(계좌번호 범위별 병렬 처리) 검토. C 코드 미세 최적화는 생각보다 뒤에 있습니다.

캐시 계층과 지역성

"메모리 접근"이라고 하면 모두 같은 비용처럼 느껴지지만, 실제로는 데이터가 어디에 있느냐에 따라 수백 배 차이가 납니다. CPU는 매우 빠르고 DRAM은 상대적으로 느리기 때문에, 그 사이에 작고 빠른 캐시를 여러 단계로 둡니다.

캐시는 데이터를 바이트 단위가 아니라 캐시 라인(대부분 64바이트) 단위로 가져옵니다. int 하나(4바이트)를 읽으려 해도 그 주변 64바이트가 통째로 캐시에 올라옵니다. 그리고 CPU의 하드웨어 프리페처는 주소가 일정하게 증가하는 접근 패턴을 감지하면 다음 라인들을 미리 가져옵니다. 이 두 가지 특성 때문에 프로그램의 메모리 접근 패턴이 성능을 좌우합니다. 이것을 지역성(locality)이라고 합니다.

  • 시간 지역성: 최근에 접근한 데이터는 곧 다시 접근할 가능성이 높다. (루프 카운터, 자주 쓰는 수수료 테이블)
  • 공간 지역성: 접근한 데이터 근처의 데이터도 곧 접근할 가능성이 높다. (배열 순차 순회, 구조체의 연속 필드)

왜 그럴까? — 연결 리스트는 왜 배열보다 느린가

같은 100만 개의 계좌를 순회해도 배열은 메모리에 연속으로 놓여 있어서, 캐시 라인 하나에 원소 여러 개가 들어오고 프리페처가 다음 라인을 미리 가져옵니다. 연결 리스트는 각 노드가 malloc으로 흩어진 위치에 있으므로, 다음 노드 주소를 알려면 현재 노드를 읽어야 하고(포인터 추적, pointer chasing), 그 주소가 캐시에 없으면 매번 수백 사이클을 기다립니다. 프리페처도 다음 주소를 예측할 수 없습니다. 이론상 둘 다 O(n)이지만 실측은 수 배~수십 배 차이가 나기도 합니다. 빅오 표기법은 상수를 무시하지만, 실무 성능은 그 상수에서 결정되는 경우가 많습니다.

행 우선 순회 성능 실험

C의 2차원 배열은 행 우선(row-major)으로 저장됩니다(ch14). int a[R][C]에서 a[i][j]와 a[i][j+1]은 메모리상 바로 옆(4바이트 차이)이고, a[i][j]와 a[i+1][j]는 한 행 전체(C×4바이트)만큼 떨어져 있습니다. 같은 합계를 구하는 두 가지 순회 방법을 비교해 봅시다.

합계는 같은데 시간은 약 10배 차이가 납니다. (합계 검산: (i+j)&7은 0~7이 고르게 나오므로 평균 3.5, 4096×4096×3.5 = 58,720,256입니다.) 정확한 배율은 CPU, 캐시 크기, 컴파일러 버전에 따라 3배에서 20배 이상까지 다양하지만, 열 우선 순회가 느리다는 결론은 거의 모든 환경에서 같습니다.

왜 그럴까? — 10배 차이의 정체

행 우선 순회에서는 64바이트 캐시 라인 하나를 가져오면 그 안의 int 16개를 연달아 씁니다. 메모리 대기는 16번에 한 번이고, 그마저도 프리페처가 다음 라인을 미리 가져오므로 거의 숨겨집니다. 게다가 컴파일러는 연속 접근을 SIMD 명령(한 번에 int 4~8개 덧셈)으로 벡터화할 수 있습니다.

열 우선 순회에서는 한 번 접근할 때마다 주소가 4096×4 = 16,384바이트씩 뜁니다. 한 열을 다 내려가는 동안 4096개의 서로 다른 캐시 라인을 건드리는데, 이는 4096×64B = 256KB로 L1(수십 KB)을 훌쩍 넘습니다. 다음 열(j+1)로 넘어갔을 때 아까 가져온 라인들은 이미 L1에서 밀려나 있습니다. 또 16KB 간격 접근은 4KB 페이지 경계를 매번 넘으므로 TLB(가상→물리 주소 변환 캐시) 미스도 함께 늘어납니다.

이렇게 해결합니다 — 구조체 배열과 핫/콜드 분리

금융 배치에서 이 원리는 "레코드 배열을 어떻게 설계하느냐"로 나타납니다. 이자 계산 루프가 잔액과 이율만 쓰는데 계좌 구조체가 고객명·주소·메모 등 300바이트짜리라면, 캐시 라인의 대부분이 쓰지도 않는 데이터로 채워집니다. 자주 쓰는 필드(hot)와 드물게 쓰는 필드(cold)를 분리하면 같은 캐시 라인에 더 많은 계좌의 잔액이 들어옵니다.

예제 31-3 난이도 ★★☆

다음 코드는 지점(100개) × 상품(5000개) 실적 행렬 long long perf[100][5000]에서 상품별 합계를 구합니다. 더 빠르게 바꾸십시오.

정답과 해설 보기

안쪽 루프에서 행 인덱스 b가 바뀌므로 접근 간격이 5000×8 = 40,000바이트입니다. 루프 순서를 바꿔 안쪽에서 p가 바뀌게 하면 perf와 total 모두 순차 접근이 됩니다. total(5000×8 = 40KB)은 L1~L2에 머무르며 반복 사용되고, perf는 한 번씩 순차로 스트리밍됩니다. 결과는 같고(덧셈 순서가 정수이므로 결과 동일) 접근 패턴만 바뀝니다.

주의: 정수 덧셈은 순서를 바꿔도 결과가 같지만, double 덧셈은 결합법칙이 성립하지 않아 순서를 바꾸면 마지막 자리가 달라질 수 있습니다(ch21). 금액을 정수로 다루는 또 하나의 이유입니다.

메모리 풀과 객체 재사용

온라인 거래 서버는 요청 하나마다 전문 버퍼, 거래 컨텍스트, 응답 버퍼 등을 할당하고 해제합니다. 초당 수천 건이면 malloc/free가 초당 수만 번 호출됩니다. malloc은 범용 할당기라서 다양한 크기 요청을 처리하기 위한 탐색, 멀티스레드 잠금(또는 스레드별 아레나 관리), 단편화 관리 비용이 듭니다. 또 장시간 운영하면 힙이 조각나서 메모리 사용량이 서서히 늘기도 합니다.

요청 크기가 고정되어 있고 생명 주기가 뚜렷하다면, 미리 한 덩어리를 할당해 두고 같은 크기의 칸으로 나누어 빌려주고 돌려받는 메모리 풀(고정 크기 할당기)이 훨씬 빠르고 예측 가능합니다.

왜 그럴까? — 풀이 빠르고 안전한 이유

  • O(1) 연산: 할당과 해제가 포인터 두세 번 대입으로 끝납니다. 크기 탐색이나 병합이 없습니다.
  • 단편화 없음: 모든 칸 크기가 같으므로 어떤 빈 칸이든 어떤 요청에나 맞습니다.
  • 상한이 명확: 풀 크기가 곧 동시 처리 한도입니다. 과부하 시 메모리를 무한정 먹다 서버 전체가 죽는 대신, 정해진 한도에서 "잠시 후 재시도" 응답을 줄 수 있습니다. 금융 온라인에서는 이 예측 가능성이 속도보다 더 중요하기도 합니다.
  • 캐시 친화: 칸들이 연속 메모리에 있고, 최근 반납한 칸(LIFO)을 바로 다시 주므로 그 칸은 캐시에 남아 있을 가능성이 높습니다.

자주 하는 실수 — 풀이 숨기는 버그

풀은 해제된 칸을 바로 재사용하므로 use-after-free가 즉시 다른 거래의 데이터를 오염시킵니다. 또 Valgrind나 ASan은 malloc/free를 감시하는데, 풀 내부의 칸 단위 할당은 모르므로 이런 버그를 잡지 못합니다. 해결: 디버그 빌드에서는 #ifdef POOL_DEBUG로 pool_alloc/pool_free를 진짜 malloc/free로 바꾸거나, 해제 시 칸을 0xDD 같은 패턴으로 채워 오염을 빨리 드러나게 합니다. 또 이 풀은 스레드 안전하지 않으므로 멀티스레드 서버라면 스레드별 풀을 두거나 뮤텍스로 보호합니다.

I/O 버퍼링

배치 프로그램에서 가장 흔한 병목은 I/O입니다. 같은 데이터를 쓰더라도 시스템 호출 횟수에 따라 성능이 크게 달라집니다. write() 같은 시스템 호출은 사용자 모드에서 커널 모드로 전환하고, 인자를 검사하고, 다시 돌아오는 고정 비용이 있습니다. 1바이트를 쓰든 64KB를 쓰든 이 고정 비용은 비슷합니다.

A는 시스템 호출을 100만 번 하므로 sys 시간이 대부분입니다. B는 stdio가 내부 버퍼(보통 4KB~8KB, BUFSIZ 또는 파일 시스템 블록 크기)에 모았다가 가득 차면 한 번에 write하므로 호출 횟수가 수십 분의 일로 줄어듭니다. C는 버퍼를 1MB로 키워 호출 횟수를 100번 정도로 더 줄였습니다. B→C의 이득은 A→B보다 훨씬 작다는 점에 주목하십시오. 시스템 호출 고정 비용이 충분히 분산되고 나면 그다음은 실제 데이터 복사와 디스크 속도가 지배합니다.

자주 하는 실수 — 버퍼링과 데이터 안전성

버퍼링은 성능을 주지만, 버퍼에 있는 데이터는 아직 파일에 없습니다. 프로그램이 비정상 종료(SIGKILL, 세그폴트, _exit)하면 버퍼 내용은 사라집니다. 또 fflush는 데이터를 커널의 페이지 캐시로 넘길 뿐, 디스크에 기록되었음을 보장하지 않습니다. 정전에도 살아남아야 하는 거래로그는 fflush(fp) 후 fsync(fileno(fp))까지 해야 하고, 그 비용(수 ms)을 감수합니다. 반면 재처리 가능한 배치 중간 파일은 큰 버퍼로 몰아 쓰고 마지막에 한 번 fsync합니다. 무엇을 언제 디스크까지 내릴지가 곧 금융 시스템의 정합성 설계입니다(ch32에서 실제로 구현합니다).

또 하나: fwrite의 반환값만 보고 안심하면 안 됩니다. 버퍼에 들어가기만 해도 성공이므로, 디스크 풀(ENOSPC) 같은 오류는 나중의 fflush나 fclose에서야 드러납니다. fclose의 반환값을 반드시 검사하십시오.

은행 시스템에서는 — 대용량 파일 배치의 I/O 설계

대외기관과 주고받는 일괄 이체 파일, 원장 언로드 파일은 수 GB에 이릅니다. 이런 파일 배치는 ① 고정 길이 레코드를 큰 블록(수백 KB~수 MB) 단위로 읽어 메모리에서 레코드로 쪼개고, ② 출력도 큰 버퍼로 모아 쓰며, ③ 중간 체크포인트마다 fsync와 함께 처리 건수를 기록해 재시작 지점을 남깁니다(ch25). "한 건 읽고 한 건 쓰고 커밋"하는 구조를 블록 단위 구조로 바꾸는 것만으로 배치 시간이 몇 분의 일로 줄어드는 일이 흔합니다.

-O2인라인, 루프 최적화, 명령 스케줄링, 공통 부분식 제거, (gcc 12+부터 일부 벡터화) 등운영 표준
-O3공격적 인라인·루프 펼치기·벡터화. 코드 크기 증가수치 계산 핫스팟
-Os크기 우선 최적화임베디드
-Og디버깅 경험을 해치지 않는 최적화개발 중 빌드

여기서 금융권 개발자가 반드시 알아야 할 현상이 있습니다. "-O0에서는 잘 돌던 프로그램이 -O2로 빌드하니 이상하게 동작한다"는 것입니다. 이때 개발자들은 흔히 "컴파일러 버그"를 의심하지만, 99%는 코드에 있던 미정의 동작(UB)이 최적화로 드러난 것입니다.

왜 그럴까? — 컴파일러는 "UB는 일어나지 않는다"고 가정한다

C 표준은 UB가 발생한 프로그램에 대해 어떤 요구도 하지 않습니다. 컴파일러 입장에서 이것은 "올바른 프로그램은 UB를 일으키지 않는다. 따라서 UB가 일어나는 경로는 존재하지 않는다고 가정하고 최적화해도 된다"는 허가입니다. 예를 들어 부호 있는 정수 오버플로는 UB이므로, 컴파일러는 x + 1 > x가 항상 참이라고 가정할 수 있습니다. -O0에서는 컴파일러가 이런 추론을 하지 않으므로 하드웨어의 실제 동작(2의 보수 랩어라운드)이 그대로 보일 뿐입니다. 즉 -O0에서 "잘 돌던" 것은 운이 좋았던 것이지 올바른 것이 아닙니다.

사례 1: 부호 있는 오버플로 검사가 사라진다

-O2에서 gcc는 balance + amount < balance를 amount < 0으로 바꿔 버립니다. 수학적으로는 같은 식이고, 오버플로는 "일어나지 않으므로" 이 변환은 합법입니다. 결과적으로 오버플로 검사는 전혀 동작하지 않습니다.

사례 2: 역참조 뒤의 NULL 검사가 사라진다

(1)에서 이미 acc를 역참조했으므로, 컴파일러는 "acc가 NULL이었다면 (1)에서 UB이므로, 여기 도달했다면 acc는 NULL이 아니다"라고 추론하고 (2)의 검사를 통째로 삭제할 수 있습니다(-fdelete-null-pointer-checks, -O2에서 기본 활성). 실제로 리눅스 커널에서 이 패턴 때문에 보안 취약점이 생긴 사례가 있습니다. 해결: 검사는 항상 사용 전에 합니다.

사례 3: 엄격한 별칭 규칙(strict aliasing) 위반

C 표준은 객체를 그 객체의 타입(또는 호환 타입, 부호만 다른 타입, 문자 타입) 이외의 lvalue로 접근하는 것을 UB로 정합니다. 그래서 컴파일러는 "int *와 float *는 서로 다른 객체를 가리킨다"고 가정하고 읽기·쓰기 순서를 재배치하거나 값을 레지스터에 캐싱합니다. read_len은 별칭 규칙 위반(선언 타입이 char 배열인 버퍼를 uint32_t로 읽음)이면서 동시에 정렬 위반(buf가 4의 배수 주소가 아닐 수 있음)이기도 해서 이식성 측면에서 이중으로 위험합니다.

이렇게 해결합니다 — UB를 찾아내는 도구들

  • -fsanitize=undefined(UBSan): 실행 중 부호 있는 오버플로, 잘못된 시프트, 정렬 위반 등을 잡아 보고합니다. 테스트 빌드에 항상 켜 두는 것을 권장합니다.
  • -fsanitize=address(ASan): 버퍼 넘침, use-after-free(ch30).
  • -Wall -Wextra -Wstrict-aliasing=2 -Wnull-dereference: 컴파일 시점 경고.
  • -fwrapv: 부호 있는 오버플로를 랩어라운드로 정의합니다. 레거시 코드를 당장 고칠 수 없을 때의 안전장치이지, 올바른 해결책은 아닙니다.
  • -fno-strict-aliasing: 별칭 기반 최적화를 끕니다. 오래된 전문 처리 코드가 포인터 캐스팅을 남발한다면 운영 빌드에 넣는 경우가 많습니다(리눅스 커널도 이 옵션을 씁니다).
  • 교차 검증: 같은 테스트를 -O0, -O2, 다른 컴파일러(gcc/clang)로 돌려 결과가 다르면 UB를 의심합니다.

정답과 해설 보기

i는 1, 2, 4, …, 230까지 가고, 그다음 230 × 2는 int 범위를 넘으므로 부호 있는 오버플로(UB)입니다. -O0에서는 하드웨어가 랩어라운드해서 INT_MIN(음수)이 되어 루프가 끝나고 31을 반환합니다. 하지만 -O2에서 컴파일러는 "양수 i에 2를 곱해도 오버플로는 없으므로 결과는 여전히 양수"라고 추론해 조건 i > 0을 항상 참으로 바꿀 수 있고, 그러면 무한 루프가 됩니다. 고치는 방법은 오버플로가 일어나기 전에 멈추는 조건을 쓰거나, 랩어라운드가 정의된 부호 없는 타입을 쓰는 것입니다.

i = 1(20)부터 230까지 31번 n이 증가하고, i = 230일 때 230 > INT_MAX/2(= 230 − 1)이 참이 되어 종료하므로 31을 반환합니다.

자주 하는 실수 — char의 부호

AIX에서 오래 쓰던 코드에 char c = getc(fp); if (c == EOF) break;가 있었다고 합시다. AIX에서는 char가 unsigned라서 c는 절대 -1이 될 수 없으므로 원래부터 무한 루프 버그였는데, 마침 그 경로를 타지 않아 몰랐습니다. 반대로 리눅스로 옮기면 0xFF 바이트(EUC-KR 한글의 일부일 수 있음)를 만나는 순간 c가 -1이 되어 파일 중간에서 읽기가 끝납니다. 해결: getc의 반환값은 반드시 int로 받고, 바이트 값을 다룰 때는 unsigned char를 명시합니다. 이식 시에는 gcc의 -funsigned-char로 원래 동작을 흉내 내 차이를 확인해 볼 수도 있습니다.

왜 그럴까? — 윈도우는 왜 LLP64를 택했을까

윈도우 API와 수많은 기존 코드는 LONG, DWORD 같은 타입이 32비트라는 가정 위에 만들어져 있었고, 파일 포맷과 구조체에도 그대로 쓰였습니다. long을 64비트로 바꾸면 그 모든 바이너리 레이아웃이 깨지므로, 마이크로소프트는 포인터만 64비트로 늘리고 long은 32비트로 두었습니다. 유닉스 진영은 1990년대 초 여러 회사가 합의해 LP64를 택했습니다. 어느 쪽이 옳다기보다는 호환성 결정의 결과이며, 개발자는 "long은 몇 비트"라고 가정하지 않는 것이 유일한 정답입니다.

정렬(alignment)과 패딩

CPU는 N바이트 데이터를 N의 배수 주소에서 읽을 때 가장 효율적이고, 어떤 아키텍처는 그렇지 않으면 아예 예외(SIGBUS)를 일으킵니다. 그래서 컴파일러는 구조체 필드 사이에 패딩을 넣습니다(ch17). 이 패딩의 양은 플랫폼의 정렬 규칙에 따라 달라집니다. 예를 들어 32비트 x86 리눅스(i386 System V ABI)에서는 구조체 안의 double과 long long이 4바이트 정렬이지만, 대부분의 64비트 플랫폼에서는 8바이트 정렬입니다.

LP64 계산: acct_no 0~12, 패딩 3, seq 16~23, balance 24~31, status 32, 끝 패딩 7 → 40바이트. i386: seq 16~19, balance 20~27(4바이트 정렬), status 28, 끝 패딩 3 → 32바이트. 같은 소스인데 레코드 크기가 다르므로, 이런 구조체를 그대로 파일에 쓰면 플랫폼 간 호환이 깨집니다.

이렇게 해결합니다 — 외부 레이아웃은 구조체가 아니라 명세로

  • 파일·전문 레이아웃은 "오프셋 0부터 12바이트 계좌번호(ASCII), 오프셋 12부터 15바이트 잔액(숫자 문자열)…"처럼 바이트 단위 명세로 정의하고, 필드별로 읽고 쓰는 함수를 둡니다(ch24).
  • 구조체를 그대로 쓰고 싶다면 모든 필드를 char 배열로 정의해 패딩이 생기지 않게 하고, _Static_assert(sizeof(struct X) == 77, "layout");로 크기를 컴파일 시점에 고정합니다.
  • #pragma pack(1)이나 __attribute__((packed))는 컴파일러 확장이고, 정렬되지 않은 필드에 포인터로 접근하면 정렬 엄격 아키텍처에서 SIGBUS가 날 수 있으므로 신중히 씁니다.

이식성 코드에서 #ifdef _AIX, #ifdef __hpux, #ifdef __linux__가 소스 곳곳에 흩어지면 유지보수가 불가능해집니다. 플랫폼 차이는 platform.h/platform.c 같은 추상화 계층 한 곳에 모으고, 업무 코드는 plat_fsync(), plat_now_usec() 같은 공통 이름만 쓰게 합니다. 또 플랫폼 이름보다 기능으로 분기하는 것이 좋습니다(#ifdef HAVE_CLOCK_GETTIME). 빌드 시스템이 기능을 검사해 매크로를 정의하게 하면, 새 플랫폼이 추가되어도 코드를 고칠 필요가 줄어듭니다.

은행 시스템에서는 — 유닉스에서 리눅스로의 이전 점검표

상용 유닉스 계정계를 x86 리눅스로 이전하는 프로젝트에서 C 코드 점검표에 거의 항상 들어가는 항목입니다. ① 바이너리 파일·공유 메모리·소켓으로 주고받는 정수의 엔디안 ② char 부호 차이(AIX unsigned) ③ long 크기와 printf 형식 지정자 ④ 구조체를 통째로 쓰는 파일의 패딩 ⑤ EBCDIC/EUC-KR/UTF-8 문자 코드 변환(ch24) ⑥ 시스템 헤더·라이브러리 함수 차이(errno 값, 시그널 번호, ioctl) ⑦ 컴파일러가 다르게 해석하는 UB. 특히 ⑦은 "원래 버그였지만 xlc에서는 우연히 맞게 돌던" 코드가 gcc -O2에서 드러나는 경우로, 이전 테스트에서 신·구 시스템의 결과를 건별로 대조하는 병행 검증이 필수인 이유입니다.

한 줄 요약

성능은 측정 → 병목 확인 → 큰 덩어리부터 개선 순서로, 캐시 지역성·할당 비용·시스템 호출 횟수를 줄이는 방향으로 다룹니다. 이식성은 크기·엔디안·정렬·부호를 가정하지 않고 고정 크기 타입과 명시적 직렬화를 쓰며, UB는 최적화가 반드시 드러낸다는 전제로 코드를 씁니다.

핵심 정리

  • make는 Makefile에 적힌 의존성 그래프를 따라가며 선행조건이 타깃보다 새것인 경우에만 레시피를 실행합니다. 레시피는 반드시 탭으로 시작합니다.
  • 자동 변수 $@(타깃), $<(첫 선행조건), $^(모든 선행조건)와 패턴 규칙 %.o: %.c로 반복을 없앱니다. :=는 즉시 확장, =는 사용 시 확장입니다.
  • 파일이 아닌 타깃(all, clean)은 .PHONY로 선언하고, 헤더 의존성은 -MMD -MP로 자동 생성해 -include합니다.
  • 정적 라이브러리(ar rcs libX.a *.o)는 링크 시 필요한 멤버 오브젝트 단위로 실행 파일에 복사됩니다.
  • 동적 라이브러리는 -fPIC로 컴파일하고 -shared -Wl,-soname,libX.so.N으로 만듭니다. 코드 영역은 프로세스 간 공유되고, ABI를 깨면 주 버전(soname)을 올립니다.
  • 실행 시 라이브러리는 동적 링커가 rpath/RUNPATH, LD_LIBRARY_PATH, ld.so.cache, 기본 경로 순으로 찾습니다. -L은 빌드 시에만 의미가 있습니다.
  • 링커는 입력을 왼쪽에서 오른쪽으로 한 번 훑으므로 쓰는 쪽을 왼쪽, 제공하는 라이브러리를 오른쪽에 둡니다. 진단은 nm(T/U/t), ldd, readelf -d로 합니다.
  • 최적화는 측정에서 시작합니다. time의 real/user/sys로 병목 종류를 구분하고, gprof/perf로 핫스팟을 찾습니다(암달의 법칙).
  • 캐시는 64바이트 라인 단위로 동작하므로 순차 접근(행 우선 순회), 핫/콜드 분리, 연속 메모리 자료구조가 빠릅니다.
  • 고정 크기 메모리 풀은 O(1) 할당·해제, 단편화 없음, 명확한 상한을 제공하지만 메모리 검사 도구의 감시를 우회합니다.
  • I/O는 시스템 호출 횟수가 비용을 좌우하므로 버퍼링하되, 내구성이 필요한 데이터는 fflush + fsync, 그리고 fclose 반환값 검사가 필수입니다.
  • -O2는 "UB는 없다"는 가정으로 최적화하므로 부호 있는 오버플로, 역참조 후 NULL 검사, 별칭 위반 같은 UB가 드러납니다. UBSan/ASan과 교차 빌드로 찾습니다.
  • 이식성: LP64(유닉스)와 LLP64(윈도우)의 long 차이, 엔디안, 정렬·패딩, char 부호(AIX unsigned)를 가정하지 말고 <stdint.h> 고정 크기 타입, PRId64, 명시적 직렬화를 씁니다.
  • 표준 준수 플래그(-std=c11 -pedantic -Wall -Wextra -Wconversion)와 기능 테스트 매크로(_POSIX_C_SOURCE)로 컴파일러 확장 의존을 줄입니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. 정적 라이브러리와 동적 라이브러리의 차이와 장단점을 설명해 주세요.

정적 라이브러리는 링크 시점에 필요한 오브젝트 코드가 실행 파일 안으로 복사되므로, 실행 파일이 자기 완결적이고 배포 환경의 라이브러리 버전에 영향을 받지 않으며 실행 시 심볼 해석 비용이 없습니다. 대신 실행 파일이 커지고, 같은 코드가 프로세스마다 메모리에 중복되며, 라이브러리를 고치면 모든 프로그램을 재링크해야 합니다. 동적 라이브러리는 실행 시점에 동적 링커가 적재·연결하므로 코드 영역을 여러 프로세스가 공유해 메모리를 절약하고, 라이브러리만 교체해 버그 수정을 반영할 수 있습니다. 대신 실행 환경에 올바른 버전이 있어야 하고(LD_LIBRARY_PATH, soname 관리), PLT/GOT 간접 호출로 약간의 오버헤드가 있습니다.

꼬리 질문: "동적 라이브러리를 왜 -fPIC로 컴파일하나요?" → 프로세스마다 다른 주소에 적재되더라도 코드 페이지를 수정하지 않고 공유하기 위해, 절대 주소 대신 PC 상대 주소와 GOT를 통한 간접 참조를 쓰는 위치 독립 코드를 만들기 위해서입니다.

Q2. 컴파일과 링크의 차이는 무엇이고, undefined reference 오류는 어느 단계에서 나나요?

컴파일(전처리·컴파일·어셈블)은 소스 파일 하나를 독립적으로 기계어 오브젝트 파일로 바꾸는 과정이고, 이때 다른 파일에 있는 함수는 선언만 보고 "미해결 심볼"로 남겨 둡니다. 링크는 여러 오브젝트와 라이브러리를 모아 미해결 심볼을 실제 주소로 연결하고 하나의 실행 파일을 만드는 과정입니다. undefined reference는 링크 단계 오류로, 선언은 있었지만 정의를 어디에서도 찾지 못했다는 뜻입니다. 원인은 정의 누락, 오브젝트·라이브러리 미포함, 링크 순서, static 함수, C/C++ 이름 맹글링 등입니다.

꼬리 질문: "-lm을 앞에 쓰면 왜 실패하나요?" → GNU ld는 아카이브를 왼쪽에서 오른쪽으로 한 번만 보며 그 시점의 미해결 심볼만 해결하기 때문입니다.

Q3. make는 어떻게 다시 빌드할 파일을 결정하나요?

Makefile에 기술된 타깃–선행조건 관계로 의존성 그래프를 만들고, 기본 타깃부터 깊이 우선으로 내려가며 각 타깃의 수정 시각과 선행조건의 수정 시각을 비교합니다. 선행조건 중 하나라도 타깃보다 새것이거나 타깃이 없으면 레시피를 실행합니다. 내용 비교가 아니라 타임스탬프 비교라 빠르지만, 시계가 어긋나거나 헤더 의존성이 누락되면 잘못된 판단을 합니다. 그래서 헤더 의존성은 -MMD -MP로 자동 생성하고, 운영 빌드는 clean build로 합니다.

Q4. 캐시 지역성이란 무엇이고, 코드에서 어떻게 활용하나요?

시간 지역성은 최근 접근한 데이터를 곧 다시 접근하는 경향, 공간 지역성은 접근한 주소 근처를 곧 접근하는 경향입니다. 캐시는 64바이트 라인 단위로 데이터를 가져오고 순차 패턴을 프리페치하므로, 2차원 배열은 행 우선으로 순회하고, 연결 리스트보다 연속 배열을 쓰며, 자주 함께 쓰는 필드를 한 구조체에 모으는(핫/콜드 분리) 방식으로 활용합니다. 같은 O(n) 알고리즘이라도 접근 패턴에 따라 실측 성능이 수 배에서 수십 배 차이 납니다.

꼬리 질문: "False sharing이 뭔가요?" → 서로 다른 스레드가 쓰는 서로 다른 변수가 같은 캐시 라인에 있어서, 한 스레드의 쓰기가 다른 코어의 라인을 계속 무효화하는 현상입니다. 변수를 캐시 라인 크기로 떨어뜨려(패딩/정렬) 해결합니다.

Q5. 최적화 옵션을 켰더니 프로그램이 다르게 동작합니다. 무엇을 의심해야 하나요?

가장 먼저 미정의 동작을 의심합니다. 컴파일러는 UB가 발생하지 않는다고 가정하고 최적화하므로, 부호 있는 정수 오버플로, 초기화되지 않은 변수 사용, 배열 범위 초과, 엄격한 별칭 규칙 위반, 역참조 후 NULL 검사 같은 코드가 -O0에서는 우연히 동작하다가 -O2에서 다르게 동작합니다. UBSan·ASan으로 실행해 보고, -Wall -Wextra 경고를 모두 확인하며, 멀티스레드 코드라면 데이터 레이스(volatile만으로는 동기화가 안 됨)도 의심합니다. 컴파일러 버그는 마지막에 의심합니다.

Q6. LP64와 LLP64의 차이를 설명하고, 이식성 있는 코드를 어떻게 작성하나요?

둘 다 포인터는 64비트이지만 LP64(64비트 리눅스·유닉스)는 long이 64비트이고, LLP64(64비트 윈도우)는 long이 32비트입니다. 따라서 long에 포인터를 담거나 long으로 큰 금액을 다루는 코드는 플랫폼에 따라 깨집니다. 크기가 중요한 곳은 int64_t 같은 고정 크기 타입, 포인터를 정수로 다룰 때는 intptr_t, 크기는 size_t를 쓰고, 출력은 %zu, PRId64를 씁니다. 파일·전문 같은 외부 데이터는 구조체 덤프 대신 명시적 직렬화를 합니다.

Q7. 성능 문제를 받았을 때 어떤 순서로 접근하나요?

먼저 재현 가능한 조건과 목표 수치를 정하고, 운영과 같은 빌드 옵션과 데이터 규모로 측정합니다. time으로 CPU 바운드인지 I/O·대기 바운드인지 구분한 뒤, 프로파일러(perf, gprof)로 시간이 가장 많이 드는 지점을 찾습니다. 암달의 법칙에 따라 가장 큰 비중부터 알고리즘·자료구조 개선, I/O 묶음 처리, 캐시 친화적 구조, 불필요한 할당 제거 순으로 손대고, 매 단계 다시 측정해 효과와 결과의 정합성(합계·건수 일치)을 확인합니다.

Q8. LD_LIBRARY_PATH는 무엇이고, 운영 환경에서 왜 주의해야 하나요?

동적 링커가 공유 라이브러리를 찾을 때 시스템 기본 경로보다 먼저 탐색하는 디렉터리 목록을 지정하는 환경 변수입니다. 개발·테스트에는 편리하지만, 실행 환경(cron, 배치 스케줄러, 서비스 매니저)마다 값이 달라 "수동 실행은 되는데 자동 실행은 안 되는" 문제나, 의도하지 않은 버전이 연결되는 문제를 만듭니다. 또 보안상 setuid 프로그램에서는 무시됩니다. 운영에서는 rpath/RUNPATH나 ldconfig 등록으로 경로를 고정하고, 배포 후 ldd로 확인하는 것이 안전합니다.

Q9. 엔디안 문제는 언제 발생하고 어떻게 해결하나요?

멀티바이트 정수를 바이트열로 기계 밖에 내보낼 때, 즉 네트워크 전송, 바이너리 파일 저장, 다른 아키텍처와 공유 메모리를 쓸 때 발생합니다. 같은 기계 안의 연산에는 영향이 없습니다. 해결은 바이트 순서를 명세로 고정하는 것으로, 네트워크 바이트 순서(빅 엔디안)와 htonl/ntohl을 쓰거나, 시프트 연산으로 엔디안 독립적으로 직렬화하거나, 금융 전문처럼 숫자를 ASCII 문자열로 표현합니다.

Q10. 메모리 풀을 왜 쓰나요? 단점은요?

malloc/free는 범용 할당기라서 크기 탐색, 잠금, 단편화 관리 비용이 있고 장시간 운영 시 힙 단편화가 생길 수 있습니다. 고정 크기 객체를 대량으로 할당·해제한다면 미리 큰 블록을 잡아 같은 크기 칸으로 나누고 프리 리스트로 관리하는 풀이 O(1)로 빠르고 단편화가 없으며 사용량 상한이 명확합니다. 단점은 풀 크기를 잘못 잡으면 메모리 낭비나 고갈이 생기고, use-after-free 같은 버그를 Valgrind·ASan이 잡지 못하며, 멀티스레드에서는 별도 동기화가 필요하다는 점입니다.

[금융 응용] 일마감 배치가 원장 파일(고정 길이 200바이트, 2,000만 건)을 읽어 이자 계산 결과 파일을 쓰는데 70분이 걸립니다. strace -c 결과 read 2,000만 회, write 2,000만 회, fsync 2,000만 회가 관찰되었습니다. 개선안을 단계별로 제시하고, 정합성(재처리 가능성)을 어떻게 유지할지 설명하십시오.

정답과 해설 보기

건마다 read, write, fsync를 하고 있어 시스템 호출만 6,000만 회이고, 특히 fsync는 매번 디스크 기록 완료를 기다리므로(수 ms) 전체 시간의 대부분을 차지할 것입니다.

  1. 읽기 블록화: 레코드 길이의 배수(예: 200B × 5,000건 = 1MB)로 read하고 메모리에서 레코드를 잘라 처리합니다. 또는 fopen + setvbuf(1MB) + fread를 씁니다. read 호출이 2,000만 회 → 약 4,000회로 줄어듭니다.
  2. 쓰기 버퍼링: 결과도 큰 버퍼에 모아 씁니다.
  3. fsync 주기화(체크포인트): 예를 들어 10만 건마다 출력 파일을 fflush + fsync하고, 그 직후 "처리 완료 건수와 출력 파일 오프셋"을 체크포인트 파일에 기록하고 그것도 fsync합니다. 장애 시에는 체크포인트를 읽어 출력 파일을 그 오프셋으로 잘라내고(ftruncate) 입력의 해당 건부터 재개합니다. 건별 fsync가 없어도 재처리가 가능합니다.
  4. 최종 확정: 정상 종료 시 마지막 fsync 후 출력 파일을 임시 이름에서 최종 이름으로 rename(원자적)하고, 총 건수·금액 합계를 트레일러에 기록해 후속 작업이 검증하게 합니다.
  5. 개선 전후 결과 파일의 건수·합계·해시를 대조해 정합성을 확인합니다.
