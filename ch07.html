함수

은행 시스템에는 "이자 계산", "수수료 계산", "계좌번호 검증" 같은 기능이 수백 개의 프로그램에서 똑같이 쓰입니다. 이 기능을 한 번만 만들어 이름을 붙이고 어디서든 불러 쓰는 장치가 함수입니다. 함수를 이해하면 큰 프로그램을 작은 부품으로 나누어 설계할 수 있고, 호출 스택을 이해하면 포인터와 메모리, 재귀까지 한 줄로 꿰어집니다.

  • 반환값·매개변수 유무에 따른 함수 유형과 void의 의미를 압니다.

  • math.h, stdlib.h의 주요 함수를 사용하고, 금융 계산 로직을 함수로 분리하는 설계 원칙을 익힙니다.

07-1함수의 작성과 사용

함수가 왜 필요한가

6장의 상환 스케줄 프로그램에서 "잔액 × 월이율 ÷ 10000, 원 미만 절사"라는 이자 계산이 반복문 안에 들어 있었습니다. 같은 이자 계산이 예금 해지, 대출 상환, 연체 이자, 일마감 배치에도 필요하다면 어떻게 할까요? 코드를 복사해서 붙여 넣으면 당장은 동작합니다. 하지만 절사 규칙이 "반올림"으로 바뀌면 복사한 모든 곳을 찾아 고쳐야 하고, 한 곳이라도 빠뜨리면 프로그램마다 이자가 달라집니다.

함수(function)는 특정 작업을 수행하는 코드 묶음에 이름을 붙인 것입니다. 한 번 정의하면 이름으로 몇 번이든 호출할 수 있습니다. 함수가 주는 이점은 다음과 같습니다.

  • 재사용: 같은 코드를 반복해서 쓰지 않습니다(DRY: Don't Repeat Yourself).
  • 유지보수: 규칙이 바뀌면 함수 한 곳만 고칩니다.
  • 추상화: 호출하는 쪽은 "무엇을 하는지"만 알면 되고 "어떻게 하는지"는 몰라도 됩니다. printf가 내부에서 어떻게 화면에 글자를 찍는지 몰라도 쓸 수 있는 것과 같습니다.
  • 분할 정복과 테스트: 큰 문제를 작은 함수로 나누면 각각을 따로 이해하고 테스트할 수 있습니다.

여러분은 이미 함수를 써 왔습니다. main도 함수이고, printf, scanf는 표준 라이브러리가 제공하는 함수입니다. 이 장에서는 함수를 직접 만듭니다.

함수 호출의 흐름

함수를 호출하면 실행 흐름이 함수 몸통으로 점프하고, return을 만나면 호출했던 바로 그 자리로 되돌아옵니다. 그리고 호출식 add(x, y) 자리는 반환값으로 바뀐 것처럼 계산이 이어집니다.

return 문의 두 가지 역할

  1. 값 반환: return 뒤의 식을 계산해 반환형으로 변환한 뒤 호출한 곳에 돌려줍니다. 예를 들어 반환형이 int인데 return 3.7;이면 3이 반환됩니다(소수점 버림).
  2. 즉시 종료: return 아래에 문장이 더 있어도 실행하지 않습니다. 그래서 5장의 가드 절처럼 "조건이 맞지 않으면 일찍 return"하는 데 씁니다.

자주 하는 실수 — 모든 경로에서 return하지 않기

반환형이 void가 아닌 함수가 return 없이 끝나고, 호출한 쪽이 그 반환값을 사용하면 미정의 동작(UB)입니다. 실제로는 반환값을 담는 레지스터(x86-64의 eax)에 우연히 남아 있던 값이 나오는데, 최적화 수준에 따라 결과가 달라집니다. gcc는 -Wall에서 "control reaches end of non-void function" 경고를 냅니다. 마지막에 return -1;을 추가해 모든 경로가 값을 반환하게 하십시오. (예외: main 함수는 C99부터 끝에 return이 없으면 0을 반환한 것으로 간주됩니다.)

매개변수와 인수

두 용어는 자주 섞어 쓰이지만 정확히는 다릅니다.

  • 매개변수(parameter, 형식 매개변수): 함수 정의에 적힌 변수. int add(int a, int b)의 a, b. 함수가 호출될 때 만들어지는 지역 변수입니다.
  • 인수(argument, 실 매개변수): 호출할 때 실제로 넘기는 값. add(x, y)의 x, y, 또는 add(10, 20)의 10, 20. 상수, 변수, 식 모두 가능합니다.

호출 시 인수의 값이 계산되어 매개변수에 순서대로 복사됩니다. 개수가 같아야 하고, 자료형이 다르면 매개변수 형으로 자동 변환됩니다(원형이 있을 때).

여기서 잠깐 — 인수의 평가 순서는 정해져 있지 않다

f(a(), b())에서 a()와 b() 중 무엇이 먼저 호출될지는 C 표준이 정하지 않았습니다(unspecified). gcc x86-64에서는 오른쪽부터 계산되는 경우가 많지만 보장되지 않습니다. 따라서 printf("%d %d\n", i++, i++);처럼 같은 변수를 한 호출의 인수 안에서 두 번 수정하면 순서점이 없으므로 미정의 동작입니다. 인수에는 부작용이 있는 식을 넣지 마십시오.

함수 원형(선언)

C 컴파일러는 소스 파일을 위에서 아래로 한 번 읽으며 번역합니다. 그래서 함수를 main보다 아래에 정의하고 main에서 호출하면, 컴파일러는 호출 시점에 그 함수의 반환형과 매개변수를 모릅니다.

왜 그럴까? — 암시적 선언(implicit declaration)의 함정

C89에서는 처음 보는 함수를 만나면 "int를 반환하고 인수는 아무거나 받는 함수"로 암시적 선언했습니다. 위 코드에서 컴파일러는 half가 int를 반환한다고 가정하고 정수 반환 레지스터(eax)에서 값을 꺼냅니다. 그런데 실제 half는 double을 실수 레지스터(xmm0)에 담아 반환하므로, main은 엉뚱한 쓰레기 값을 받습니다. 게다가 나중에 실제 정의(double 반환)를 만나면 "conflicting types for 'half'" 오류가 납니다. C99부터는 암시적 선언 자체가 제거되었고, 최신 gcc(14 이상)는 이를 기본적으로 오류로 처리합니다.

이렇게 해결합니다 — 함수 원형을 앞에 선언

함수의 머리 부분만 세미콜론과 함께 미리 적어 두는 것을 함수 원형(function prototype) 또는 함수 선언이라고 합니다. 원형은 컴파일러에게 "이런 이름, 이런 반환형, 이런 매개변수를 가진 함수가 어딘가에 있다"고 약속하는 것입니다.

원형이 있으면 컴파일러는 호출할 때마다 다음을 검사하고 처리합니다.

  1. 인수 개수가 맞는지 검사합니다(틀리면 오류).
  2. 인수를 매개변수 자료형으로 자동 변환합니다(예: half(7.9)는 7로 변환. 경고 옵션에 따라 경고).
  3. 반환값을 올바른 자료형으로 받습니다.

#include <stdio.h>를 쓰는 이유가 바로 이것입니다. stdio.h 헤더 파일 안에는 printf, scanf 등의 원형이 들어 있습니다. 실제 정의(기계어)는 C 표준 라이브러리(libc)에 있고 링크 단계에서 연결됩니다. 여러 파일로 이루어진 프로그램에서는 원형을 헤더 파일(.h)에 모아 두고 공유합니다(18장 분할 컴파일).

자주 하는 실수 — int f() 와 int f(void) 는 다르다 (C17까지)

C17 이전의 C에서 int f();는 "매개변수 정보를 알려 주지 않음"이라는 뜻이어서 f(1, 2, 3)으로 호출해도 컴파일러가 검사하지 않습니다. "매개변수가 없음"을 명확히 하려면 int f(void);라고 써야 합니다. 그래서 이 과정에서는 int main(void)라고 씁니다. (C23에서는 f()도 f(void)와 같은 뜻이 되었지만, 이식성을 위해 void를 쓰는 습관을 권장합니다. C++에서는 원래부터 같은 뜻입니다.)

호출 스택과 스택 프레임

함수가 호출될 때마다 그 함수의 매개변수와 지역 변수가 저장될 공간이 필요합니다. 이 공간은 메모리의 스택(stack) 영역에 만들어지며, 함수 하나의 호출에 해당하는 공간 덩어리를 스택 프레임(stack frame) 또는 활성 레코드(activation record)라고 합니다.

스택은 접시 쌓기와 같습니다. 함수를 호출하면 새 프레임(접시)이 맨 위에 쌓이고(push), 함수가 끝나면 맨 위 프레임이 제거됩니다(pop). 항상 가장 나중에 호출된 함수가 가장 먼저 끝나므로 LIFO(Last In, First Out) 구조입니다.

스택 프레임에는 보통 다음이 들어갑니다(정확한 배치는 CPU와 호출 규약에 따라 다름).

  • 복귀 주소(return address): 함수가 끝난 뒤 돌아갈 호출한 곳의 다음 명령 주소. call 명령이 자동으로 스택에 넣습니다.
  • 이전 프레임 포인터: 호출한 함수의 프레임 위치(rbp)를 저장.
  • 지역 변수와, 레지스터로 전달되지 못한 매개변수.

왜 그럴까? — 지역 변수가 함수가 끝나면 사라지는 이유

함수가 return하면 스택 포인터(rsp)가 이전 위치로 돌아갑니다. 프레임이 차지하던 메모리를 실제로 지우지는 않고, "여기부터는 빈 공간"이라고 표시만 옮기는 것입니다. 그래서 프레임 생성과 제거는 포인터 하나를 더하고 빼는 것으로 끝나 매우 빠릅니다(힙 메모리 할당보다 훨씬 빠른 이유). 대신 그 공간은 다음 함수 호출이 덮어쓰므로, 함수가 끝난 뒤 그 지역 변수의 주소를 사용하면 미정의 동작이 됩니다. 9장 포인터에서 "지역 변수의 주소를 반환하지 말라"는 규칙이 여기서 나옵니다.

x86-64 리눅스(System V 호출 규약)에서는 정수·포인터 인수 앞의 6개가 레지스터(rdi, rsi, rdx, rcx, r8, r9)로, 실수 인수 앞의 8개가 xmm0~xmm7로 전달되고, 반환값은 rax(정수) 또는 xmm0(실수)에 담깁니다. 윈도우 x64 호출 규약은 레지스터 4개(rcx, rdx, r8, r9)를 쓰는 등 다릅니다.

값에 의한 전달(call by value)

C의 함수 호출은 언제나 값에 의한 전달입니다. 인수의 값이 매개변수에 복사되므로, 함수 안에서 매개변수를 바꿔도 호출한 쪽의 원래 변수는 바뀌지 않습니다.

왜 그럴까? — scanf에 &가 필요한 진짜 이유

이제 3장부터 외워 왔던 "scanf에는 &를 붙인다"의 이유를 설명할 수 있습니다. scanf("%d", x)라고 쓰면 x의 값(예: 쓰레기 값 32767)이 복사되어 넘어갈 뿐이고, scanf는 main의 x가 어디 있는지 알 수 없으므로 x에 값을 넣어 줄 방법이 없습니다. &x는 x의 주소입니다. 주소 값이 복사되어 넘어가면, scanf는 그 주소가 가리키는 곳에 직접 값을 써 넣을 수 있습니다. 주소도 "값"으로 전달된다는 점에서 C는 여전히 call by value이지만, 주소를 넘김으로써 원본을 바꾸는 효과를 내는 것입니다. 이 방법으로 swap을 고치는 것은 9장 포인터에서 다룹니다.

지금 단계에서의 해결 — 결과는 반환값으로 받는다

포인터를 배우기 전에는 "함수는 매개변수로 입력을 받고, 결과는 return으로 돌려준다"는 원칙을 지키십시오. 원본을 바꾸고 싶으면 x = f(x);처럼 반환값을 다시 대입합니다.

main이 몇 줄 안 되는 "목차"처럼 읽힌다는 점에 주목하십시오. 세부 동작은 함수 이름이 설명해 줍니다. 이것이 함수로 분리했을 때 얻는 가장 큰 가독성 이득입니다.

자주 하는 실수 — void 함수의 반환값을 사용

long long b = print_balance(balance);처럼 void 함수의 결과를 쓰려고 하면 컴파일 오류("void value not ignored as it ought to be")입니다. 반대로 반환값이 있는 함수의 결과를 무시하는 것은 합법이지만(printf도 출력한 글자 수를 반환하는데 보통 무시합니다), scanf나 fopen처럼 성공/실패를 반환하는 함수의 결과를 무시하는 것은 버그의 원천입니다.

재귀 함수 — 자기 자신을 호출하는 함수

함수가 자기 자신을 호출하는 것을 재귀(recursion)라고 합니다. 처음엔 이상하게 들리지만, "큰 문제를 같은 모양의 더 작은 문제로 바꿔 푸는" 수학적 귀납법과 같은 사고방식입니다. 재귀 함수는 반드시 두 부분을 가져야 합니다.

  1. 기저 사례(base case): 더 이상 쪼개지 않고 바로 답을 아는 가장 작은 문제. 재귀를 멈추는 조건입니다.
  2. 재귀 사례(recursive case): 문제를 한 단계 작게 만들어 자기 자신을 호출하고, 그 결과로 현재 답을 만듭니다. 반드시 기저 사례 쪽으로 다가가야 합니다.

팩토리얼

n! = n × (n-1) × ... × 1 이고, 이를 재귀적으로 정의하면 0! = 1(기저), n! = n × (n-1)!(재귀)입니다.

왜 그럴까? — 같은 이름의 n이 서로 섞이지 않는 이유

fact(4), fact(3), fact(2), fact(1)은 모두 같은 코드를 실행하지만, 호출될 때마다 새 스택 프레임이 만들어지고 각자의 매개변수 n이 그 프레임 안에 따로 저장됩니다. 그래서 fact(1)이 실행되는 동안에도 아래 프레임의 n=2, 3, 4는 그대로 보존되어 있다가 복귀할 때 사용됩니다. 재귀는 특별한 마법이 아니라, 이미 배운 "함수 호출 = 새 프레임 push"가 같은 함수에 반복 적용된 것뿐입니다.

자주 하는 실수 — 기저 사례 누락과 스택 오버플로

재귀가 끝나지 않으면 프레임이 계속 쌓여 스택 영역(리눅스 기본 8MB, 윈도우 기본 1MB)을 다 써 버리고 스택 오버플로(stack overflow)가 발생합니다. 리눅스에서는 Segmentation fault로 프로그램이 죽습니다. 기저 사례가 있어도 fact_rec(-5)처럼 기저에 도달할 수 없는 값이 들어오면 같은 일이 생길 수 있으므로, 위 코드처럼 n <= 1로 넓게 잡거나 입력을 검증합니다. 또 21!부터는 long long 범위(약 9.2×1018)를 넘어 부호 있는 정수 오버플로(UB)가 일어납니다.

피보나치 수열과 재귀의 비용

피보나치 수열은 F(0)=0, F(1)=1, F(n)=F(n-1)+F(n-2)입니다. 정의를 그대로 재귀로 옮기면 매우 간단합니다.

왜 그럴까? — fib(30) 하나에 269만 번 호출되는 이유

fib(n)은 fib(n-1)과 fib(n-2)를 각각 처음부터 계산하는데, fib(n-1) 안에서도 fib(n-2)를 또 계산합니다. 같은 부분 문제가 트리 전체에 반복 등장하므로 호출 수는 대략 1.618n(황금비의 거듭제곱)에 비례해 늘어납니다. 정확히는 fib(n)의 호출 횟수 = 2×F(n+1) − 1이고, n=30이면 2×1,346,269 − 1 = 2,692,537번입니다. n=50이면 약 400억 번이 되어 일반 PC에서 수 분이 걸립니다. 반면 반복 버전은 n번의 덧셈이면 끝납니다(O(n)).

재귀의 비용은 두 가지입니다. ① 시간: 함수 호출 자체의 오버헤드(프레임 생성, 레지스터 저장, 점프)와 위와 같은 중복 계산. ② 공간: 재귀 깊이만큼 스택 프레임이 쌓임. fact(10만)은 계산 결과가 오버플로하기 전에 스택이 넘칠 수도 있습니다.

이렇게 해결합니다 — 재귀를 쓸 때와 쓰지 말아야 할 때

  • 중복 계산이 있는 재귀는 결과를 저장해 재사용(메모이제이션, 배열을 배운 뒤 8장 연습문제)하거나 반복문으로 바꿉니다(동적 계획법).
  • 깊이가 입력 크기에 비례하는 재귀(팩토리얼, 리스트 순회)는 반복문으로 바꾸는 것이 안전합니다. 특히 24시간 도는 금융 서버에서 입력에 따라 스택이 넘칠 수 있는 코드는 금지 대상입니다.
  • 재귀가 빛나는 곳: 깊이가 log n 정도로 얕은 분할 정복(이진 탐색, 퀵 정렬, 병합 정렬), 트리 구조 순회(디렉터리 탐색, 25장 트리) 등. 이런 문제는 재귀로 쓰면 코드가 훨씬 짧고 명확합니다.
  • 재귀 호출이 함수의 마지막 동작인 꼬리 재귀(tail recursion)는 gcc -O2에서 반복문으로 최적화될 수 있지만, C 표준이 보장하지는 않으므로 의존하지 않습니다.

예제 7-3 난이도 ★★☆

양의 정수의 각 자릿수 합을 재귀 함수 int digit_sum(long long n)으로 구하세요. (6장 예제 6-6을 재귀로)

정답과 해설 보기

기저: n이 0이면 0. 재귀: (마지막 자리) + (나머지 자리들의 합) = n % 10 + digit_sum(n / 10). n이 매번 10배씩 줄어드므로 깊이는 자릿수(최대 19)뿐이라 재귀를 써도 안전합니다.

다음 재귀 함수에서 f(3)을 호출하면 무엇이 출력됩니까? 호출 전 출력과 복귀 후 출력의 순서에 주목하세요.

정답과 해설 보기

출력: in3 in2 in1 out1 out2 out3

재귀 호출 전의 문장은 스택이 쌓이는 순서(3, 2, 1)로, 재귀 호출 후의 문장은 스택이 풀리는 역순(1, 2, 3)으로 실행됩니다. 이 성질 때문에 재귀를 이용하면 입력을 거꾸로 출력하는 등의 작업을 쉽게 할 수 있습니다(예: 정수를 2진수로 출력할 때 상위 비트부터 출력).

표준 라이브러리 함수 — math.h

C 표준은 자주 쓰는 기능을 표준 라이브러리로 제공합니다. 원형은 헤더 파일에 있으므로 해당 헤더를 #include하고 호출하면 됩니다. 수학 함수는 <math.h>에 있으며, 리눅스 gcc에서는 링크할 때 수학 라이브러리를 지정하는 -lm 옵션이 필요할 수 있습니다.

왜 그럴까? — rint는 왜 2.5를 2로 만들까 (은행가 반올림)

rint는 IEEE 754 표준의 기본 반올림 모드인 "가장 가까운 값, 동점이면 짝수 쪽(round half to even)"을 따릅니다. 2.5는 2와 3의 정확히 중간이므로 짝수인 2를, 3.5는 짝수인 4를 고릅니다. 이를 은행가 반올림(banker's rounding)이라고 부르는데, 대량의 데이터를 반올림할 때 항상 올리는 방식(사사오입)은 합계가 위로 치우치는(편향) 반면, 짝수 쪽 반올림은 올림과 내림이 반반씩 일어나 합계 편향이 줄어들기 때문입니다. 단, 한국 금융 실무의 원 단위 처리는 대부분 절사 또는 사사오입이 약관으로 정해져 있으므로, 함수를 고르기 전에 반드시 업무 규칙을 확인해야 합니다.

자주 하는 실수 — math.h를 빼먹거나 정수 거듭제곱에 pow 사용

  • #include <math.h> 없이 sqrt를 호출하면 원형이 없어 경고/오류가 나거나(C99 이후) 엉뚱한 값이 나옵니다.
  • pow(10, 2)는 double 계산이라 대부분 정확히 100.0이 나오지만, 큰 정수의 거듭제곱을 (long long)pow(...)로 변환하면 오차 때문에 1 작은 값(99999999999999 등)이 나올 수 있습니다. 정수 거듭제곱은 반복문으로 직접 곱하는 함수를 만드는 것이 안전합니다.
  • sqrt에 음수를 넣으면 NaN(Not a Number)이 반환됩니다. log(0)은 -inf입니다. 입력 범위를 먼저 검증하십시오.

왜 그럴까? — rand()는 진짜 난수가 아니다

rand()는 정해진 수식(예: 선형 합동 생성기)으로 다음 값을 계산하는 의사 난수(pseudo-random) 생성기입니다. 같은 시드로 시작하면 항상 같은 수열이 나옵니다. srand를 호출하지 않으면 시드가 1인 것처럼 동작하므로 매번 같은 결과가 나옵니다. 이 성질은 테스트를 재현할 때는 장점이지만, 보안 용도(OTP, 인증번호, 암호 키, 거래 일련번호 추측 방지)에는 절대 쓰면 안 됩니다. 시드(현재 시각)를 추측하면 다음 값을 모두 예측할 수 있기 때문입니다. 금융 보안에는 운영체제의 암호학적 난수(/dev/urandom, getrandom(), 윈도우 BCryptGenRandom)나 검증된 암호 라이브러리를 사용합니다. 또 rand() % n은 RAND_MAX+1이 n의 배수가 아니면 작은 값이 조금 더 자주 나오는 편향이 있습니다.

함수 설계 원칙

함수를 "문법적으로" 만드는 것은 쉽습니다. 어려운 것은 잘 나누는 것입니다. 실무에서 통용되는 원칙을 정리합니다.

  1. 하나의 함수는 하나의 일만 한다(단일 책임). 함수 이름을 "~하고 ~한다"로밖에 지을 수 없다면 둘로 나눌 신호입니다. 예: calc_and_print_interest → calc_interest + print_interest.
  2. 계산과 입출력을 분리한다. 계산 함수는 printf/scanf를 하지 않고 값만 반환해야 다른 곳(화면, 배치, 전문 응답)에서 재사용하고 자동 테스트할 수 있습니다.
  3. 이름이 곧 문서다. 동사+목적어(calc_fee, is_valid_account), 불리언 반환은 is_, has_로 시작합니다. 단위가 있으면 이름에 넣습니다(rate_bp, amount_won, days).
  4. 짧게 유지한다. 한 화면(약 40~60줄)을 넘으면 나눌 곳을 찾습니다. 들여쓰기 깊이 3단계 이내.
  5. 매개변수는 적게. 4~5개를 넘으면 구조체(15장)로 묶는 것을 고려합니다.
  6. 부작용을 최소화한다. 전역 변수를 몰래 바꾸는 함수는 호출 순서에 따라 결과가 달라져 버그를 만듭니다. 같은 입력에 항상 같은 출력을 내는 함수(순수 함수)가 가장 다루기 쉽습니다.
  7. 오류를 반환값으로 알린다. C에는 예외가 없으므로 "0 성공, 음수 오류 코드" 같은 규약을 정해 일관되게 씁니다. 결과값과 오류를 둘 다 반환해야 하면 포인터 매개변수(9장)를 씁니다.

금융 예제 — 이자 계산 함수 분리

정기예금 만기 해지 처리를 함수로 설계해 봅니다. 규칙: 이자 = 원금 × 연이율(bp) × 예치일수 ÷ (10000 × 365), 원 미만 절사(한편넣기 일수). 세금 = 이자 × 15.4%, 원 미만 절사. 지급액 = 원금 + 이자 − 세금.

왜 그럴까? — 10000LL 의 LL은 왜 붙였을까

10000 * 365는 int끼리의 곱이라 3,650,000으로 int 범위 안이므로 사실 괜찮습니다. 하지만 상수 곱이 커지는 경우(예: 이율 단위를 0.0001%로 바꿔 1000000 × 365)에는 int 범위(약 21억)를 넘어 부호 있는 정수 오버플로(UB)가 됩니다. 결과를 long long 변수에 담더라도 계산은 피연산자의 자료형(int)으로 먼저 이루어지기 때문입니다. 상수에 LL 접미사를 붙이면 처음부터 long long으로 계산되어 안전합니다. 분자 principal * rate_bp * days는 principal이 long long이므로 왼쪽부터 long long으로 승격되어 계산됩니다(5,000,000 × 350 × 90 = 1.575×1011, int라면 넘침).

은행 시스템에서는 — 공통 모듈과 단위 테스트

은행 계정계에서는 이자 계산, 세금 계산, 영업일 계산, 계좌번호 검증 같은 함수를 공통 모듈(공통 라이브러리)로 만들고 모든 업무 프로그램(수신, 여신, 외환, 배치)이 호출합니다. 공통 모듈은 변경 시 영향 범위가 매우 크기 때문에 별도의 승인 절차와 회귀 테스트(기존 테스트 케이스를 모두 다시 돌려 결과가 바뀌지 않았는지 확인)를 거칩니다. calc_interest처럼 입출력이 없는 순수 함수로 만들어 두면 "입력 → 기대 결과" 표만으로 수천 개의 테스트를 자동으로 돌릴 수 있습니다. 반대로 함수 안에서 printf를 하거나 전역 변수를 바꾸면 이런 자동 테스트가 어려워집니다. 계산과 입출력의 분리는 취향이 아니라 품질 관리의 핵심 요건입니다.

은행 시스템에서는 — 오류 코드 체계

예제의 ERR_AMOUNT, ERR_RATE처럼 실무 시스템은 전사적인 오류 코드(응답 코드) 체계를 가지고 있습니다. 함수는 오류 코드를 반환하고, 최상위 거래 처리부는 그 코드를 화면 메시지나 대외 전문의 응답 코드로 변환합니다. 함수마다 제멋대로 -1, 0, 1을 반환하면 "이 -1이 금액 오류인가 계좌 오류인가"를 구분할 수 없어 장애 분석이 어려워집니다. 그래서 신입 개발자가 가장 먼저 익히는 사내 문서 중 하나가 오류 코드 표입니다.

예제 7-5 난이도 ★★☆

원 미만을 사사오입(반올림)하는 정수 나눗셈 함수 long long div_round(long long num, long long den)을 실수 연산 없이 작성하세요(num ≥ 0, den > 0 가정). 예: div_round(7, 2) = 4, div_round(5, 3) = 2, div_round(43150684, 1000) = 43151.

정답과 해설 보기

반올림은 "0.5를 더하고 버림"입니다. 정수에서는 분자에 den/2를 더하면 됩니다: (num + den / 2) / den. den이 홀수일 때 den/2가 내림되어 미세한 차이가 생기므로, 정확히 하려면 (2 * num + den) / (2 * den)을 씁니다(오버플로 주의).

이 함수를 공통 모듈로 두면, 이자 계산 규칙이 "절사"에서 "사사오입"으로 바뀌어도 calc_interest 안의 나눗셈 한 줄만 바꾸면 됩니다.

핵심 정리

  • 함수는 이름 붙은 코드 묶음으로 재사용, 유지보수, 추상화, 테스트를 가능하게 합니다.
  • 함수 정의 = 반환형 + 이름 + 매개변수 목록 + 몸통. return은 값을 돌려주고 즉시 함수를 끝냅니다. void가 아닌 함수는 모든 경로에서 return해야 합니다.
  • 매개변수는 함수의 지역 변수이고, 인수는 호출 시 넘기는 값입니다. 인수의 평가 순서는 정해져 있지 않습니다.
  • 호출보다 정의가 뒤에 있으면 함수 원형을 앞에 선언합니다. 헤더 파일(stdio.h 등)은 원형의 모음입니다. 매개변수가 없으면 (void)로 씁니다.
  • 호출마다 스택 프레임(복귀 주소, 지역 변수, 매개변수)이 push되고 반환 시 pop됩니다(LIFO). 함수가 끝나면 지역 변수는 사라집니다.
  • C는 항상 call by value입니다. 매개변수를 바꿔도 원본은 그대로이며, 원본을 바꾸려면 주소를 넘겨야 합니다(scanf의 &, 9장).
  • 함수 유형은 매개변수·반환값 유무로 네 가지이며, void는 "없음"을 뜻합니다.
  • 재귀 = 기저 사례 + 기저로 다가가는 재귀 사례. 기저가 없거나 깊이가 크면 스택 오버플로가 납니다.
  • 단순 재귀 피보나치는 중복 계산으로 지수 시간이 걸립니다. 반복문, 메모이제이션으로 개선합니다.
  • math.h(sqrt, pow, floor, ceil, round, rint)와 stdlib.h(abs, rand, srand, exit, strtol) 사용법과 함정(-lm, NaN, rand의 보안 부적합)을 압니다.
  • 계산과 입출력을 분리하고, 하나의 함수는 하나의 일만 하며, 오류는 일관된 반환 코드로 알립니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. Call by value와 Call by reference의 차이는? C는 어느 쪽인가요?

Call by value는 인수의 값을 복사해 전달하므로 함수 안에서 바꿔도 원본이 변하지 않고, call by reference는 원본 변수 자체(별칭)를 전달해 함수 안의 변경이 원본에 반영됩니다. C는 오직 call by value만 지원합니다. 포인터를 넘기는 것도 "주소 값"을 복사해 넘기는 call by value이며, 그 주소를 통해 원본에 접근하므로 참조 전달과 같은 효과를 낼 뿐입니다. C++의 참조(&)가 진짜 call by reference입니다.

꼬리 질문 대비: "Java는?" — Java도 항상 값 전달이며, 객체의 경우 참조값이 복사됩니다.

Q2. 함수 호출 시 스택에서 무슨 일이 일어나나요?

호출 측이 인수를 레지스터나 스택에 준비하고 call 명령으로 복귀 주소를 push한 뒤 점프합니다. 피호출 함수는 이전 프레임 포인터를 저장하고 스택 포인터를 내려 지역 변수 공간을 확보합니다. 반환 시 반환값을 rax(또는 xmm0)에 넣고 스택 포인터와 프레임 포인터를 복원한 다음 ret으로 복귀 주소로 돌아갑니다.

꼬리 질문 대비: "스택 버퍼 오버플로 공격이란?" — 지역 배열의 범위를 넘겨 써서 복귀 주소를 덮어쓰고 공격 코드로 점프시키는 것이며, 스택 카나리, ASLR, NX 비트로 방어합니다(8장 연결).

Q3. 스택과 힙의 차이는?

스택은 함수 호출 시 자동으로 할당·해제되는 지역 변수 영역으로, 스택 포인터 이동만으로 관리되어 매우 빠르지만 크기가 작고(수 MB) 수명이 함수 호출 기간으로 고정됩니다. 힙은 malloc/free로 프로그래머가 명시적으로 관리하는 영역으로, 크고 수명을 자유롭게 정할 수 있지만 할당이 상대적으로 느리고 누수·단편화 문제가 있습니다. 스택은 스레드마다 하나씩, 힙은 프로세스가 공유합니다.

Q4. 재귀 함수의 장단점과 스택 오버플로를 피하는 방법은?

장점은 트리 탐색, 분할 정복처럼 자기 유사 구조의 문제를 짧고 명확하게 표현한다는 것입니다. 단점은 호출 오버헤드와 깊이만큼의 스택 사용, 중복 계산 가능성입니다. 반복문으로 변환하거나, 명시적 스택 자료구조를 쓰거나, 메모이제이션으로 중복을 없애고, 재귀 깊이를 입력 검증으로 제한해 피합니다.

꼬리 질문 대비: "꼬리 재귀 최적화란?" — 재귀 호출이 마지막 연산이면 현재 프레임을 재사용해 점프로 바꾸는 최적화로, gcc -O2에서 수행될 수 있지만 C 표준은 보장하지 않습니다.

Q5. 피보나치를 재귀로 구현하면 시간 복잡도는? 개선 방법은?

단순 재귀는 같은 부분 문제를 반복 계산해 O(φn) ≈ O(1.618n), 흔히 O(2n)으로 말합니다. 메모이제이션(top-down DP)이나 반복문(bottom-up DP)으로 O(n), 행렬 거듭제곱으로 O(log n)까지 줄일 수 있습니다.

Q6. 함수 원형(prototype)은 왜 필요한가요?

C 컴파일러는 파일을 위에서 아래로 한 번 읽기 때문에, 호출 시점에 반환형과 매개변수 정보를 알아야 인수 개수 검사, 자료형 변환, 올바른 반환값 수신을 할 수 있습니다. 원형이 없으면 C89에서는 int 반환으로 암시적 선언되어 잘못된 값이 전달되었고, C99부터는 암시적 선언이 금지되었습니다. 여러 파일에서 공유하는 원형은 헤더 파일에 둡니다.

Q7. 인라인 함수와 매크로 함수의 차이는?

매크로는 전처리기가 텍스트를 치환하므로 자료형 검사가 없고, 인수가 여러 번 평가되는 부작용(예: SQUARE(i++))과 연산자 우선순위 문제가 있습니다. inline 함수(C99)는 진짜 함수라 자료형 검사와 한 번 평가가 보장되며, 컴파일러가 호출 오버헤드를 없애기 위해 본문을 펼칠 수 있습니다(강제는 아님). 17장 전처리기에서 자세히 다룹니다.

Q8. 함수 호출 오버헤드란 무엇이고, 언제 신경 써야 하나요?

인수 준비, 복귀 주소 저장, 프레임 생성·해제, 점프로 인한 파이프라인 영향 같은 비용입니다. 대부분은 수 나노초 수준이고 최적화 컴파일러가 작은 함수를 인라인하므로 가독성을 위해 함수를 나누는 것을 주저할 필요가 없습니다. 수억 번 도는 핫 루프에서만 프로파일링 후 고려합니다.

Q9. rand()를 보안 용도로 쓰면 안 되는 이유는?

rand는 시드로부터 결정적으로 계산되는 의사 난수라 시드나 출력 몇 개를 알면 이후 값을 예측할 수 있습니다. OTP, 세션 키, 인증번호에는 OS의 암호학적으로 안전한 난수 생성기(/dev/urandom, getrandom, CryptGenRandom 계열)를 써야 합니다.

  • 전역 변수 부작용: 어떤 함수가 언제 g_balance를 바꿨는지 추적이 어렵고, 계좌가 여러 개면 쓸 수 없습니다.
  • 계산과 출력 혼합: 배치나 전문 응답에서 재사용할 수 없고 자동 테스트가 어렵습니다.
  • 오류 보고 없음: 잔액 부족을 호출자가 알 수 없습니다(화면에만 찍힘). 알 수 없는 code도 조용히 무시합니다.

개선: long long deposit(long long bal, long long amt), int can_withdraw(long long bal, long long amt), void print_result(...)로 분리하고, 잔액은 매개변수로 받고 결과를 반환하며, 오류는 반환 코드로 알립니다. 포인터(9장)와 구조체(15장)를 배우면 int withdraw(Account *acc, long long amt) 형태로 더 자연스럽게 설계할 수 있습니다.

문제 10 (math.h) 난이도 ★★☆

원금 P를 연이율 r%로 연복리 운용할 때 원금이 2배가 되는 기간(년)을 log를 이용해 계산하는 함수 double years_to_double(double rate_percent)를 작성하고, 3.5%, 7.2%일 때 결과를 72의 법칙과 비교하세요.

정답과 해설 보기

(1 + r)n = 2 → n = ln 2 / ln(1 + r).

72의 법칙은 이율 6~10% 근처에서 잘 맞는 어림셈입니다. 6장 예제 6-7에서 반복 시뮬레이션이 21년이었던 것은 연 단위로만 확인했고 매년 절사했기 때문입니다(20.15년이 지난 첫 연말은 21년차).

문제 11 (출력 예측 — 인수 평가) 난이도 ★★★

다음 코드의 출력을 확정할 수 있습니까? 이유를 설명하세요.

정답과 해설 보기

확정할 수 없습니다. 함수 인수의 평가 순서는 미지정(unspecified)이므로 "1 2"일 수도 "2 1"일 수도 있습니다(gcc x86-64에서는 흔히 "2 1"). 다만 각 함수 호출은 서로 겹치지 않고 순서대로 하나씩 실행되므로 UB는 아니고, 둘 중 하나의 결과가 나옵니다. 순서가 중요하면 int a = next(); int b = next();로 먼저 변수에 받습니다.

문제 12 (코드 작성 — 계좌번호 체크 디지트) 난이도 ★★★

가상의 규칙: 10자리 계좌번호의 앞 9자리 각각에 가중치 2,3,4,5,6,7,2,3,4를 곱해 더한 합 S에 대해, 검증번호 = (11 − S % 11) % 10. 마지막(10번째) 자리가 검증번호와 같으면 유효. 함수 int check_digit(long long first9)와 int is_valid_account(long long acc10)를 작성하세요. (실제 은행별 규칙은 다르며 공개되지 않는 경우가 많습니다.)

정답과 해설 보기

앞 9자리를 오른쪽 자리부터 꺼내면 가중치도 뒤에서부터(4,3,2,7,6,5,4,3,2) 적용해야 합니다. 가중치를 위치 계산식으로 구하는 대신 switch나 배열(8장)로 처리할 수도 있습니다. 여기서는 오른쪽에서 i번째(0부터) 자리의 가중치 = 앞에서부터 (8 − i)번째 가중치로 계산합니다.

검증번호는 계좌번호 입력 시 한 자리 오타나 인접 자리 뒤바뀜을 서버에 보내기 전에 걸러 내는 장치입니다. 계산 함수를 분리해 두었기 때문에 은행별 가중치가 달라도 weight_at만 바꾸면 됩니다.
