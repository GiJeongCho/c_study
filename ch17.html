사용자 정의 자료형

계좌 하나에는 계좌번호, 예금주, 잔액, 상태가 함께 붙어 다닙니다. 이 서로 다른 자료를 하나의 이름으로 묶어 다루는 도구가 구조체입니다. 은행의 원장 레코드, 대외기관과 주고받는 전문, 거래 로그는 모두 구조체로 표현되므로, 이 장은 금융 IT 코드를 읽기 위한 가장 직접적인 준비 과정입니다.

이 장에서 배울 것

  • 구조체를 선언하고 변수를 만들며 멤버에 .과 ->로 접근하는 방법
  • 구조체 초기화(순서 초기화, 지정 초기화), 구조체 대입이 실제로 무엇을 복사하는지
  • 구조체를 함수에 값으로 넘길 때와 포인터로 넘길 때의 차이와 선택 기준
  • 계좌 구조체 Account를 설계하고 입금·출금·이체 함수를 작성하는 방법
  • 구조체 배열, 중첩 구조체, 자기 참조 구조체(연결 리스트의 출발점)
  • 패딩과 정렬이 생기는 이유(CPU의 정렬 접근)와 크기를 줄이는 멤버 배치
  • 공용체(union)의 메모리 공유 원리와 용도, 열거형(enum)으로 상태 코드 정의, typedef

17-1구조체

구조체가 필요한 이유

지금까지 우리는 int, double, char 배열 같은 기본 자료형으로 데이터를 표현했습니다. 그런데 은행 계좌 하나를 표현하려고 하면 곧바로 불편함이 드러납니다. 계좌 하나에는 최소한 다음 정보가 필요합니다.

  • 계좌번호: 문자열(예: "110-234-567890")
  • 예금주 이름: 문자열
  • 잔액: 원 단위 정수(long long)
  • 계좌 상태: 정상, 정지, 해지 등을 나타내는 정수

구조체가 없다면 이 정보를 각각 별도의 변수, 계좌가 여러 개라면 별도의 배열로 관리해야 합니다.

이 방식의 문제는 세 가지입니다. 첫째, 논리적으로 하나인 데이터가 물리적으로 흩어져 있습니다. 잔액으로 정렬하면서 네 배열을 모두 같은 순서로 바꿔야 하는데, 하나라도 빠뜨리면 김철수의 계좌번호에 이영희의 잔액이 붙는 대형 사고가 납니다. 둘째, 함수에 계좌를 넘길 때 인자가 많아지고 순서를 헷갈리기 쉽습니다. 셋째, 나중에 "개설일"이라는 정보가 추가되면 관련 함수의 매개변수를 전부 고쳐야 합니다.

구조체(structure)는 이 문제를 서로 다른 자료형의 변수를 하나로 묶어 새로운 자료형을 만드는 방법으로 해결합니다. 묶인 각각의 변수를 멤버(member) 또는 필드(field)라고 부릅니다.

구조체 선언과 변수 정의

구조체는 두 단계로 사용합니다. 먼저 구조체의 모양(형틀)을 선언하고, 그 형틀로 실제 변수를 만듭니다. 붕어빵 틀과 붕어빵의 관계와 같습니다. 틀을 선언하는 것만으로는 메모리가 할당되지 않습니다.

선언 문법을 하나씩 짚어 보겠습니다.

  • struct는 구조체를 만든다는 키워드이고, account는 이 구조체에 붙인 태그(tag) 이름입니다.
  • 자료형의 이름은 account가 아니라 struct account 두 단어 전체입니다. 그래서 변수를 만들 때 struct account a;라고 씁니다. (C++에서는 account a;도 되지만 C에서는 안 됩니다. 이 불편함은 17-2의 typedef로 해결합니다.)
  • 중괄호 안에는 멤버를 일반 변수 선언처럼 나열합니다. 멤버 선언에는 초기값을 줄 수 없습니다(long long balance = 0;은 C에서 오류).
  • 닫는 중괄호 뒤의 세미콜론은 필수입니다. 빠뜨리면 다음 줄에서 엉뚱한 오류 메시지가 나옵니다.

왜 그럴까? — 선언만으로는 왜 메모리가 생기지 않을까?

struct account { ... };는 컴파일러에게 "앞으로 struct account라는 자료형은 이런 모양이다"라고 알려 주는 설계도일 뿐입니다. 컴파일러는 이 설계도로부터 크기와 각 멤버의 위치(오프셋)를 계산해 기억해 둡니다. 실제 메모리는 struct account a;처럼 변수를 정의하는 순간 스택(지역 변수)이나 데이터 영역(전역 변수)에 할당됩니다.

멤버 접근 a.balance는 컴파일 후에는 "변수 a의 시작 주소 + balance의 오프셋" 위치를 읽는 기계어로 바뀝니다. 즉 멤버 이름은 실행 중에는 남아 있지 않고, 컴파일 시간에 고정된 거리(바이트 수)로 바뀌어 사라집니다. 이 점 때문에 구조체 멤버 접근은 배열 인덱스 접근만큼이나 빠릅니다.

구조체 선언과 동시에 변수를 만들 수도 있고, 전역으로 선언할 수도 있습니다.

자주 하는 실수

  • 닫는 중괄호 뒤 세미콜론 누락: struct a { int x; } 다음 줄의 int main(void)가 "구조체를 반환하는 main"처럼 해석되어 이상한 오류가 납니다.
  • 문자열 멤버에 = 로 대입: a.owner = "김철수";는 컴파일 오류입니다. 배열 이름은 대입의 왼쪽에 올 수 없기 때문입니다(12장 복습). strcpy 또는 더 안전하게 snprintf(a.owner, sizeof a.owner, "%s", "김철수");를 씁니다.
  • 구조체 선언을 함수 안에 넣고 다른 함수에서 사용: 함수 안에서 선언한 구조체 형은 그 함수 안에서만 보입니다. 여러 함수가 함께 쓰는 형은 파일 위쪽(또는 헤더 파일)에 선언합니다.

여기서 잠깐 — 한글 문자열의 길이

UTF-8 환경에서 한글 한 글자는 보통 3바이트입니다. "김철수"는 9바이트에 널 문자 1바이트를 더해 10바이트가 필요합니다. 윈도우 콘솔의 CP949(EUC-KR 계열)에서는 한 글자 2바이트입니다. 예금주 필드 크기를 잡을 때는 "글자 수"가 아니라 "바이트 수" 기준으로 여유 있게 잡아야 합니다. 금융권 전문에서 한글 필드가 깨지는 사고의 상당수가 이 바이트 계산 실수에서 나옵니다.

멤버 접근 연산자 . 과 ->

구조체 변수의 멤버에 접근할 때는 멤버 접근 연산자 .(점)을 씁니다. a.balance는 "a 안에 있는 balance"라는 뜻입니다. 멤버는 해당 자료형의 일반 변수와 똑같이 다룰 수 있습니다. 즉 a.balance += 10000;, scanf("%lld", &a.balance);, printf("%c", a.owner[0]); 모두 가능합니다.

왜 그럴까? — &a.balance는 왜 괄호 없이 되나요?

연산자 우선순위 때문입니다. 멤버 접근 연산자 .과 ->는 후위 연산자 그룹으로 가장 높은 우선순위를 가집니다. 단항 &보다 높으므로 &a.balance는 &(a.balance), 즉 "a의 balance 멤버의 주소"로 해석됩니다. 우리가 원하는 그대로입니다. 반면 a.acc_no는 배열이므로 이름 자체가 첫 원소의 주소로 변환되어 &가 필요 없습니다.

구조체를 포인터로 가리킬 때는 사정이 달라집니다. 포인터 p가 구조체 a를 가리키면 *p가 곧 a이므로 (*p).balance로 접근할 수 있습니다. 그런데 괄호가 꼭 필요합니다. *p.balance라고 쓰면 .의 우선순위가 *보다 높아서 *(p.balance)로 해석되고, 포인터 p에는 balance라는 멤버가 없으므로 컴파일 오류가 납니다.

이 괄호가 매번 번거롭기 때문에 C는 간접 멤버 접근 연산자 ->(화살표)를 제공합니다. p->balance는 (*p).balance와 완전히 같은 뜻입니다.

한 줄 요약

왼쪽이 구조체 변수면 ., 왼쪽이 구조체를 가리키는 포인터면 ->. p->m은 (*p).m의 줄임 표기입니다.

구조체 초기화

구조체 변수는 배열처럼 중괄호로 초기화할 수 있습니다. 두 가지 방식이 있습니다.

  1. 순서대로 초기화(C89부터): 멤버를 선언한 순서대로 값을 나열합니다.
  2. 지정 초기화(designated initializer)(C99부터): .멤버이름 = 값 형태로 어떤 멤버에 무엇을 넣는지 명시합니다.

왜 그럴까? — 일부만 초기화하면 나머지가 왜 0이 될까?

C 표준은 "초기화 목록이 멤버보다 적으면, 남은 멤버는 정적 저장 기간 객체처럼 초기화된다"고 정합니다. 정적 객체의 기본 초기값은 정수 0, 실수 0.0, 포인터 NULL입니다. 그래서 { 0 }은 첫 멤버를 명시적으로 0으로, 나머지는 규칙에 따라 0으로 만드는 "전부 0" 관용구가 됩니다. 반대로 초기화 목록 자체가 없는 지역 구조체 변수(struct account a;)는 쓰레기값을 가집니다. 스택 메모리에 이전 함수가 남긴 값이 그대로 있기 때문입니다.

이렇게 해결합니다 — 실무 권장 초기화 습관

  • 지역 구조체는 정의와 동시에 = { 0 }으로 초기화합니다. 쓰레기값이 섞인 레코드가 파일이나 전문으로 나가는 사고를 막습니다.
  • 멤버가 다섯 개 이상이면 지정 초기화를 씁니다. 나중에 구조체 중간에 멤버가 추가되어도 값이 엉뚱한 멤버에 들어가지 않습니다.
  • 이미 만든 변수를 다시 0으로 만들 때는 memset(&a, 0, sizeof a); 또는 a = (struct account){ 0 };(C99 복합 리터럴)을 씁니다.

자주 하는 실수 — 초기화와 대입은 다릅니다

중괄호 목록은 정의할 때만 쓸 수 있습니다.

구조체 대입과 복사

배열과 구조체의 결정적인 차이가 여기서 나옵니다. 배열은 arr1 = arr2;처럼 통째로 대입할 수 없지만, 구조체는 같은 형끼리 =로 통째로 대입할 수 있습니다. 구조체 안에 배열 멤버가 있어도 그 배열까지 모두 복사됩니다.

왜 그럴까? — 배열은 대입이 안 되는데 구조체 안의 배열은 왜 복사될까?

배열 이름은 대부분의 식에서 "첫 원소의 주소"로 변환되어(배열의 포인터 변환, decay) 더 이상 배열 전체를 나타내지 않습니다. 주소에 주소를 대입하는 것은 의미가 없으므로 배열 대입은 금지됩니다. 반면 구조체 이름은 변환되지 않고 구조체 객체 전체를 나타냅니다. 컴파일러는 구조체 대입을 sizeof(struct account) 바이트를 그대로 옮기는 코드(작으면 레지스터 몇 번의 이동, 크면 memcpy 호출)로 번역합니다. 배열 멤버도 그 바이트 안에 들어 있으므로 함께 복사됩니다.

이 성질은 역사적으로도 재미있습니다. 초기 C(K&R 1판)에서는 구조체 대입이 없었고, C89 표준에서 정식으로 추가되었습니다. 덕분에 "배열을 값으로 복사하고 싶으면 구조체로 감싸라"는 기법도 쓸 수 있습니다.

하지만 이 복사는 얕은 복사(shallow copy)입니다. 구조체 멤버가 포인터라면 포인터 값(주소)만 복사되고, 가리키는 대상은 복사되지 않습니다.

자주 하는 실수 — 구조체 비교에 == 사용

대입은 되지만 ==로 구조체 두 개를 비교할 수는 없습니다(컴파일 오류). 그렇다고 memcmp(&a, &b, sizeof a)로 비교하는 것도 위험합니다. 17-2에서 배울 패딩 바이트에 쓰레기값이 들어 있을 수 있어, 멤버 값이 모두 같아도 다르다고 나올 수 있습니다. 멤버를 하나씩 비교하는 함수를 직접 작성하는 것이 정석입니다.

예제 17-2 난이도 ★★☆

다음 프로그램의 출력을 예측하십시오.

#include <stdio.h>
struct wrap { int arr[3]; };

void twice(struct wrap w)
{
    for (int i = 0; i < 3; i++) w.arr[i] *= 2;
}

int main(void)
{
    struct wrap a = { { 1, 2, 3 } }, b;
    b = a;
    b.arr[0] = 100;
    twice(a);
    printf("%d %d %d / %d\n", a.arr[0], a.arr[1], a.arr[2], b.arr[0]);
    return 0;
}
정답과 해설 보기

출력: 1 2 3 / 100

b = a;는 배열 멤버까지 통째로 복사하므로 b는 a와 독립된 사본입니다. b.arr[0]을 바꿔도 a는 그대로입니다. twice(a)는 구조체를 값으로 넘기므로 함수 안의 w는 a의 사본이고, 사본의 배열을 두 배로 해도 a는 변하지 않습니다. 배열을 그냥 넘기면 주소가 넘어가 원본이 바뀌지만, 구조체로 감싸면 값 복사가 일어난다는 점이 핵심입니다.

구조체 포인터

구조체 포인터는 구조체 변수의 시작 주소를 저장하는 포인터입니다. 선언은 struct account *p;이고, 포인터 연산의 규칙도 다른 포인터와 같습니다. p + 1은 주소에 1을 더하는 것이 아니라 sizeof(struct account) 바이트만큼 이동한 주소입니다. 그래서 구조체 배열을 포인터로 순회할 수 있습니다.

왜 그럴까? — 주소가 왜 0x18(24)씩 증가할까?

acc_no[16]이 16바이트, long long이 8바이트로 합계 24바이트입니다. 포인터 산술은 "가리키는 자료형의 크기" 단위로 움직이므로 p++는 24바이트를 건너뜁니다. 16진수로 0x...b10 + 0x18 = 0x...b28 입니다. 만약 acc_no[20]이었다면 20 + 8 = 28이 아니라 32바이트가 됩니다. 이유는 17-2의 패딩에서 자세히 다룹니다.

구조체 포인터는 다음과 같은 경우에 반드시 필요합니다.

  • 함수가 호출한 쪽의 구조체를 수정해야 할 때(입금 함수가 잔액을 바꾸는 경우)
  • 큰 구조체를 복사하지 않고 효율적으로 전달할 때
  • malloc으로 구조체를 동적 할당할 때(16장 복습): struct account *p = malloc(sizeof *p);
  • 연결 리스트처럼 구조체끼리 서로 연결할 때(17-2 자기 참조 구조체)

여기서 잠깐 — sizeof *p 관용구

malloc(sizeof(struct account))보다 malloc(sizeof *p)가 낫습니다. 나중에 p의 형을 다른 구조체로 바꿔도 malloc 인자를 고칠 필요가 없고, 형 이름을 잘못 적어 크기가 틀리는 실수도 막습니다. sizeof는 (가변 길이 배열이 아닌 한) 피연산자를 실제로 평가하지 않으므로 p가 아직 초기화되지 않았어도 안전합니다.

함수에 구조체 전달하기: 값 vs 포인터

구조체를 함수에 넘기는 방법은 두 가지입니다. 이 선택은 성능과 정확성 모두에 영향을 주므로 원리를 확실히 이해해야 합니다.

왜 그럴까? — C에는 call by reference가 없다

C의 함수 호출은 언제나 값에 의한 전달(call by value)입니다. 구조체를 넘기면 구조체 값이 복사되고, 포인터를 넘기면 포인터 값(주소)이 복사됩니다. "포인터로 넘기면 참조 전달"이라는 말은 정확히는 "주소를 값으로 전달해서 참조 전달 효과를 낸다"는 뜻입니다. 함수 안의 p 자체는 사본이므로 p = NULL;로 바꿔도 호출한 쪽의 포인터는 변하지 않습니다. 하지만 *p(가리키는 대상)는 원본이므로 p->balance를 바꾸면 원본이 바뀝니다.

성능 측면에서, x86-64 리눅스 호출 규약(System V ABI)은 16바이트 이하의 작은 구조체는 레지스터로 넘기지만, 그보다 큰 구조체는 메모리(스택)에 복사해서 넘깁니다. 수백 바이트짜리 고객 레코드를 값으로 넘기면 호출할 때마다 그만큼 메모리 복사가 일어납니다. 초당 수천 건을 처리하는 계정계 거래 처리에서는 무시할 수 없는 비용입니다.

이렇게 해결합니다 — 전달 방식 선택 기준

  1. 함수가 구조체를 수정해야 하면: struct T *p
  2. 수정하지 않지만 구조체가 크면(대략 16바이트 초과): const struct T *p
  3. 작은 구조체(좌표, 날짜 등)이고 읽기만 하면: 값 전달도 좋습니다. 코드가 단순하고 NULL 걱정이 없습니다.
  4. 포인터로 받는 함수는 첫 줄에서 NULL을 검사하거나, 주석으로 "NULL 금지"를 명시합니다.

함수가 구조체를 반환할 수도 있습니다. 작은 구조체를 만들어 돌려주는 "생성 함수"에 자주 씁니다.

자주 하는 실수 — 지역 구조체의 주소 반환

t는 지역 변수이므로 함수가 반환되는 순간 수명이 끝납니다. 반환된 주소를 역참조하는 것은 미정의 동작입니다. 우연히 값이 남아 있어 테스트에서는 통과하다가, 다음 함수 호출이 그 스택을 덮어쓰는 순간 값이 바뀝니다. 구조체를 값으로 반환하거나, 호출한 쪽이 공간을 마련해 포인터로 넘기거나, malloc으로 할당해 반환하십시오.

은행의 계좌 원장(ledger)은 위의 struct Account를 훨씬 크게 확장한 레코드입니다. 계좌번호, 고객번호, 상품코드, 잔액, 지급정지 여부, 최종거래일자, 이자 계산 기준 잔액, 거래 일련번호 등이 들어갑니다. 실제 시스템에서 이체는 위 예제처럼 메모리 안의 두 구조체를 고치는 것이 아니라 데이터베이스 트랜잭션으로 처리됩니다. 출금 계좌 UPDATE와 입금 계좌 UPDATE, 거래 내역 INSERT가 하나의 트랜잭션으로 묶여 모두 성공(COMMIT)하거나 모두 취소(ROLLBACK)됩니다. 우리 예제의 "보상 처리"는 이 원자성(Atomicity)을 흉내 낸 것입니다.

17-2구조체 활용, 공용체, 열거형

구조체 배열

같은 형의 구조체 여러 개는 배열로 관리합니다. 구조체 배열은 "레코드의 목록"이며, 데이터베이스의 테이블이나 파일의 레코드 묶음을 메모리에 올린 모습과 같습니다. 원소 접근은 arr[i].member입니다. []와 .은 우선순위가 같고 왼쪽부터 결합하므로 "i번째 원소의 멤버"로 해석됩니다.

왜 그럴까? — 구조체 배열을 함수에 넘기면 원본이 정렬되는 이유

구조체 하나를 값으로 넘기면 복사가 일어나지만, 배열을 넘기면 배열 이름이 첫 원소의 주소로 변환되어 struct Account *가 넘어갑니다. 매개변수 struct Account a[]는 사실 struct Account *a와 같습니다. 그래서 함수 안에서 a[i] = ...로 바꾸면 main의 list가 직접 바뀝니다. 이 규칙은 int 배열의 경우와 완전히 같습니다.

여기서 잠깐 — 큰 레코드는 포인터 배열로 정렬하기

위 예제는 교환할 때마다 구조체 전체(40바이트)를 세 번 복사합니다. 레코드가 수백 바이트이고 수십만 건이라면 비용이 큽니다. 이때는 struct Account *idx[N];처럼 포인터 배열을 만들어 포인터만 정렬하면 8바이트씩만 움직입니다. 원본 순서도 보존됩니다. 데이터베이스의 인덱스와 같은 발상입니다. 표준 라이브러리의 qsort를 쓰면 정렬 알고리즘을 직접 짤 필요도 없습니다.

중첩 구조체

구조체의 멤버로 다른 구조체를 넣을 수 있습니다. 예를 들어 거래 내역에는 "거래 일시"가 있는데, 날짜와 시각을 각각 구조체로 만들어 두면 다른 곳에서도 재사용할 수 있습니다. 접근은 .을 연달아 씁니다.

자주 하는 실수 — 자기 자신을 멤버로 넣기

구조체는 다른 구조체를 멤버로 가질 수 있지만, 자기 자신과 같은 형을 멤버로 가질 수는 없습니다. struct node { int v; struct node next; };는 오류입니다. node 안에 node가 있고 그 안에 또 node가 있어 크기가 무한대가 되기 때문입니다. 컴파일러는 "field has incomplete type"이라고 알려 줍니다. 대신 자기 자신을 가리키는 포인터는 가능합니다. 포인터의 크기는 가리키는 대상과 무관하게 8바이트로 정해져 있기 때문입니다(17-2-4).

구조체의 크기: 패딩과 정렬

구조체의 크기는 멤버 크기의 단순 합이 아닐 수 있습니다. 다음 실험을 보십시오.

같은 멤버인데 순서만 바꿨더니 크기가 12와 8, 24와 16으로 달라졌습니다. 컴파일러가 멤버 사이와 끝에 아무 의미 없는 빈 바이트, 즉 패딩(padding)을 끼워 넣었기 때문입니다.

왜 그럴까? — CPU는 왜 정렬된 주소를 좋아할까?

CPU는 메모리를 1바이트씩 읽지 않습니다. 메모리 버스와 캐시는 4바이트, 8바이트, 그리고 캐시 라인(보통 64바이트) 단위로 데이터를 가져옵니다. 4바이트 int가 주소 4, 8, 12처럼 4의 배수에 있으면 한 번의 접근으로 읽을 수 있습니다. 그런데 주소 1부터 걸쳐 있으면(1~4번 바이트) 두 개의 워드(0~3, 4~7)에 걸치게 되어, CPU는 두 번 읽고 필요한 바이트를 잘라 붙여야 합니다. 이것을 비정렬 접근(unaligned access)이라고 합니다.

  • x86-64는 비정렬 접근을 하드웨어가 처리해 주지만 느려질 수 있고, 캐시 라인 경계에 걸치면 더 느립니다. 원자적(atomic) 연산은 정렬되어 있어야 보장됩니다.
  • 일부 ARM, SPARC 같은 CPU는 비정렬 접근 시 버스 오류(bus error)로 프로그램이 죽기도 합니다.

그래서 각 자료형에는 정렬 요구(alignment requirement)가 있습니다. x86-64 리눅스에서 char=1, short=2, int=4, long/long long/double/포인터=8입니다. C11의 _Alignof(int)(또는 <stdalign.h>의 alignof)로 확인할 수 있습니다. 컴파일러는 각 멤버의 오프셋이 그 정렬 값의 배수가 되도록 앞에 패딩을 넣습니다.

꼬리 패딩은 왜 필요할까요? 구조체 배열을 생각하면 됩니다. struct A의 크기가 9라면 arr[1]은 주소 9에서 시작하고, 그 안의 i는 주소 13에 놓여 4의 배수가 아닙니다. 그래서 구조체 전체 크기는 가장 큰 정렬 요구를 가진 멤버의 정렬 값의 배수로 맞춰집니다. A는 int(4)가 최대이므로 9를 12로, C는 double(8)이 최대이므로 20을 24로 올립니다.

규칙을 정리하면 다음과 같습니다.

  1. 각 멤버는 자신의 정렬 값의 배수인 오프셋에 놓인다. 필요하면 앞에 패딩을 넣는다.
  2. 구조체 전체의 정렬 값은 멤버 정렬 값 중 최댓값이다.
  3. 구조체 크기는 전체 정렬 값의 배수가 되도록 끝에 패딩을 넣는다.
  4. 첫 멤버의 오프셋은 항상 0이다(표준이 보장). 그래서 구조체 주소와 첫 멤버 주소는 같다.

예제 17-5 난이도 ★★☆

x86-64 리눅스에서 다음 구조체의 크기를 구하고, 크기를 최소로 만드는 멤버 순서를 제시하십시오.

struct Tx {
    char      type;        /* 'D' / 'W' */
    long long amount;
    short     branch;      /* 지점 코드 */
    int       teller_id;   /* 창구 직원 번호 */
    char      channel;     /* 'B' 영업점, 'I' 인터넷 */
};

원래 순서: type@0(1) → amount는 8의 배수여야 하므로 패딩 7, amount@8~15 → branch@16~17 → teller_id는 4의 배수여야 하므로 패딩 2, @20~23 → channel@24 → 끝 25를 8의 배수로 올려 32바이트. 실제 데이터는 1+8+2+4+1=16바이트인데 절반이 패딩입니다.

정렬 값이 큰 순서로 배치합니다: amount@0~7, teller_id@8~11, branch@12~13, type@14, channel@15 → 16바이트로 패딩 0. 이 기법을 "큰 것부터 배치"라고 하며, 수백만 건의 레코드를 메모리에 올리는 배치 프로그램에서 메모리를 크게 절약합니다.

은행 시스템에서는 — 전문(電文)과 구조체 패딩

은행과 대외기관(타 은행, 카드사, 결제 중계기관 등)은 정해진 바이트 배치의 고정 길이 전문으로 통신합니다. 예를 들어 "전문 종별 코드 4바이트, 거래 일자 8바이트, 계좌번호 16바이트, 금액 13바이트(숫자 문자)…"처럼 각 필드의 위치가 바이트 단위로 고정됩니다. 이때 구조체를 그대로 소켓으로 보내면(send(sock, &msg, sizeof msg, 0)) 다음 문제가 생깁니다.

  • 컴파일러가 넣은 패딩이 필드 사이에 끼어 필드 위치가 어긋납니다.
  • 숫자 필드를 int로 두면 엔디안(바이트 순서)이 상대 시스템과 다를 수 있습니다.
  • 패딩 바이트에 쓰레기값이 들어가 로그에 이상한 문자가 찍히거나, 메모리에 남아 있던 민감 정보 조각이 새어 나갈 수 있습니다.

그래서 금융 전문은 대개 모든 필드를 char 배열로 정의합니다(char amt[13];처럼 숫자도 문자로). char 배열은 정렬 요구가 1이므로 패딩이 생기지 않습니다. 그리고 _Static_assert(sizeof(struct Msg) == 300, "전문 길이 불일치");로 컴파일 시점에 길이를 검증합니다. gcc의 __attribute__((packed))나 #pragma pack(1)으로 패딩을 없앨 수도 있지만, 비정렬 접근과 이식성 문제가 있어 신중히 사용합니다(19장에서 #pragma를 다룹니다).

왜 그럴까? — 왜 strcpy가 아니라 memcpy를 썼을까?

전문 필드는 널 문자로 끝나지 않는 고정 길이 바이트열입니다. strcpy(m.msg_type, "0200")은 "0200" 4바이트 뒤에 널 문자 1바이트를 더 써서 다음 필드(tx_date)의 첫 바이트를 덮어씁니다. 마지막 필드라면 구조체 밖을 침범하는 버퍼 오버플로가 됩니다. 정확히 필요한 바이트 수만큼 memcpy하고, 출력할 때도 %.*s로 길이를 지정해야 합니다.

자기 참조 구조체 입문

멤버로 자기와 같은 형을 가리키는 포인터를 가진 구조체를 자기 참조 구조체(self-referential structure)라고 합니다. 이것이 연결 리스트, 트리, 큐 같은 동적 자료구조의 기초입니다. 여기서는 개념만 익히고, 본격적인 구현은 자료구조 장에서 다룹니다.

왜 그럴까? — 해제할 때 next를 먼저 보관하는 이유

free(head); head = head->next; 순서로 쓰면 이미 해제한 메모리에서 next를 읽게 됩니다. 이것은 해제 후 사용(use-after-free)으로 미정의 동작입니다. 해제된 메모리는 할당기가 내부 관리 정보로 덮어쓸 수 있어, 엉뚱한 주소로 이동하거나 보안 취약점이 됩니다. 반드시 next를 지역 변수에 먼저 복사한 뒤 free합니다.

또 하나, 왜 포인터 멤버는 허용될까요? 컴파일러가 struct TxNode의 크기를 계산하는 시점에는 아직 TxNode가 완성되지 않은 불완전형(incomplete type)입니다. 불완전형의 객체는 크기를 모르므로 멤버로 둘 수 없지만, 불완전형을 가리키는 포인터의 크기는 항상 8바이트로 알려져 있으므로 문제가 없습니다.

공용체 union

공용체(union)는 문법이 구조체와 똑같지만 결정적인 차이가 있습니다. 구조체의 멤버는 각자 자기 공간을 가지지만, 공용체의 모든 멤버는 같은 시작 주소의 메모리를 공유합니다. 따라서 공용체의 크기는 가장 큰 멤버의 크기(에 정렬을 위한 꼬리 패딩을 더한 값)이며, 한 번에 의미 있는 값은 하나의 멤버뿐입니다.

왜 그럴까? — 왜 78 56 34 12 순서로 나올까?

x86 계열 CPU는 리틀 엔디안(little endian)으로, 여러 바이트 정수를 저장할 때 가장 낮은 자리 바이트(0x78)를 가장 낮은 주소에 둡니다. 공용체는 같은 4바이트를 int로도, 바이트 배열로도 볼 수 있게 해 주므로 이 저장 순서를 그대로 드러냅니다. 네트워크 표준 바이트 순서와 IBM 메인프레임 등은 빅 엔디안이라 0x12가 먼저 옵니다. 메인프레임 계정계와 유닉스/리눅스 대외계가 섞인 금융권에서 숫자를 바이너리로 주고받을 때 엔디안 변환을 빠뜨리면 금액이 완전히 다른 숫자로 해석됩니다.

표준 관점에서, 마지막으로 쓴 멤버가 아닌 다른 멤버로 읽는 것(type punning)은 C99 TC3 이후의 C에서 허용되며, 저장된 바이트를 새 형으로 재해석한 값이 나옵니다(그 결과는 표현 방식에 따라 다르고, 트랩 표현이면 문제가 될 수 있음). C++에서는 미정의 동작이니 C++ 코드로 옮길 때는 memcpy를 쓰십시오.

공용체의 실제 용도는 크게 세 가지입니다.

  1. 메모리 절약: 동시에 쓰이지 않는 데이터를 겹쳐 저장합니다.
  2. 바이트 재해석: 위 엔디안 검사처럼 같은 데이터를 다른 형으로 봅니다(프로토콜 파싱, 하드웨어 레지스터).
  3. 태그 있는 공용체(tagged union): "종류 표시(tag)" 멤버와 공용체를 구조체로 묶어, 종류에 따라 다른 데이터를 담습니다. 가장 많이 쓰는 패턴입니다.

왜 그럴까? — 크기가 왜 40일까?

공용체 u의 멤버 크기는 account가 4+16=20, card가 20+4=24(card_no 20바이트 뒤 int는 오프셋 20, 4의 배수이므로 패딩 없음), cash가 4입니다. 가장 큰 24바이트, 정렬 4이므로 u는 24바이트입니다. 바깥 구조체는 kind(4)@0, amount는 8 정렬이라 패딩 4 후 @8~15, u@16~39이고, 전체 정렬 8에 대해 40이 이미 8의 배수이므로 40바이트입니다. 세 결제 수단을 각각 구조체 멤버로 나열했다면 4+4+8+20+24+4=64바이트가 필요했을 것입니다.

참고로 카드 번호 예시는 마스킹된 18글자 문자열로 card_no[20]에 널 문자까지 들어갑니다. 실제 카드 번호(16자리)를 평문으로 저장하거나 출력하는 것은 금융 규제상 금지이며 반드시 마스킹하거나 암호화합니다.

자주 하는 실수 — 태그와 실제 내용 불일치

공용체는 컴파일러가 "지금 어느 멤버가 유효한지" 추적해 주지 않습니다. kind를 PAY_CARD로 바꾸고 u.card를 채우지 않으면 이전 account 데이터의 바이트를 카드 번호로 잘못 읽습니다. 태그와 내용을 항상 함께 설정하는 생성 함수(make_card_payment(...))를 만들어 직접 대입을 피하는 것이 안전합니다.

열거형 enum과 거래 상태 코드

거래의 상태를 0, 1, 2 같은 숫자로 관리하면 코드에 if (st == 3) 같은 의미 불명의 숫자(매직 넘버)가 등장합니다. 열거형(enumeration)은 정수 상수에 이름을 붙여 하나의 형으로 묶는 방법입니다.

열거형의 규칙은 다음과 같습니다.

  • 값을 지정하지 않으면 첫 상수는 0, 이후는 앞의 값 + 1입니다.
  • 값을 직접 줄 수 있습니다: enum RespCode { RC_OK = 0, RC_INVALID_ACC = 14, RC_NO_FUNDS = 51, RC_TIMEOUT = 91 }; 값을 지정하지 않은 다음 상수는 바로 앞 값 + 1이 됩니다.
  • 열거 상수의 형은 C에서 int입니다. 열거형 변수의 실제 저장 형은 구현 정의(보통 int)입니다.
  • C는 열거형 변수에 범위 밖의 정수를 넣는 것을 막지 않습니다(s = 42;도 컴파일됨). C++보다 느슨합니다.

왜 그럴까? — #define 상수 대신 enum을 쓰는 이유

#define TX_APPROVED 1도 같은 일을 하는 것처럼 보이지만, 전처리기가 컴파일 전에 단순히 글자를 바꿔 버리므로 컴파일러와 디버거는 TX_APPROVED라는 이름을 모릅니다. enum 상수는 컴파일러가 아는 진짜 식별자라서 (1) gdb에서 print s를 하면 TX_SETTLED로 보이고, (2) 변수의 형이 enum TxState로 문서화되며, (3) switch에서 열거 상수 중 하나를 처리하지 않으면 gcc -Wall(-Wswitch)이 경고해 줍니다. 상태 코드가 하나 추가되었을 때 처리 누락을 컴파일러가 찾아 주는 것은 실무에서 매우 큰 장점입니다. 단, 이 경고는 default가 있으면 나오지 않으므로, 누락이 치명적인 곳에서는 default 없이 모든 case를 나열하기도 합니다.

은행 시스템에서는 — 응답 코드와 상태 코드

카드 승인이나 대외 이체에서 상대 기관은 응답 코드를 돌려줍니다. 승인(정상), 잔액 부족, 계좌 오류, 시간 초과(타임아웃) 등이 각각 정해진 코드로 표현됩니다. 실무 코드는 이 코드를 enum이나 상수 표로 정의하고, 코드별로 "고객에게 보여 줄 메시지", "재시도 가능 여부", "망 취소(reversal) 필요 여부"를 매핑합니다. 특히 타임아웃은 "상대방은 처리했는데 우리는 응답을 못 받은" 상태일 수 있어서, 재시도하면 이중 출금이 되고 무시하면 돈이 공중에 뜹니다. 그래서 타임아웃을 별도의 상태(예: TX_UNKNOWN)로 두고, 이후 조회 전문이나 일마감 대사(reconciliation)로 확정하는 설계가 일반적입니다.

typedef로 형 이름 짓기

typedef는 기존 자료형에 새 이름(별칭)을 붙입니다. 새로운 형을 만드는 것이 아니라 이름만 하나 더 붙이는 것입니다. 문법은 변수 선언 앞에 typedef를 붙인 모양이라고 기억하면 쉽습니다. long long money;는 변수 선언이고, typedef long long Money;는 Money라는 형 이름 선언입니다.

왜 그럴까? — typedef와 #define의 차이

#define PTR char * 후 PTR a, b;라고 쓰면 전처리기가 char * a, b;로 바꾸므로 a만 포인터이고 b는 char입니다. 반면 typedef char *PTR; 후 PTR a, b;는 a와 b가 모두 char *입니다. typedef는 컴파일러가 이해하는 진짜 형 이름이고, #define은 글자 치환이기 때문입니다. 또한 typedef는 블록 범위 규칙을 따르고 디버거에도 이름이 남습니다.

Money 같은 typedef는 문서화 효과도 큽니다. 나중에 금액 형을 다른 형으로 바꿔야 할 때 typedef 한 줄만 바꾸면 선언부를 일일이 찾을 필요가 없습니다.

여기서 잠깐 — _t 접미사는 피하세요

size_t, int32_t처럼 표준 형들은 _t로 끝납니다. POSIX 표준은 _t로 끝나는 이름을 시스템용으로 예약하고 있으므로, 직접 만드는 typedef에는 account_t보다 Account처럼 다른 명명 규칙을 쓰는 편이 안전합니다. 실제 프로젝트에서는 팀의 코딩 표준을 따르면 됩니다.

자주 하는 실수 — 자기 참조 구조체에서 typedef 이름 사용

typedef 이름 Node는 선언이 끝나는 세미콜론에서야 생깁니다. 구조체 내부에서는 태그 이름을 써야 합니다.

예제 17-6 난이도 ★★★

다음 코드의 출력을 x86-64 리눅스 기준으로 예측하십시오.

#include <stdio.h>
typedef union { long long ll; int i[2]; char c[8]; } U;
typedef struct { char tag; U u; } S;
int main(void)
{
    U x;
    x.ll = 0;
    x.i[1] = 1;
    printf("%zu %zu %lld\n", sizeof(U), sizeof(S), x.ll);
    return 0;
}
정답과 해설 보기

출력: 8 16 4294967296

U는 가장 큰 멤버가 8바이트이고 정렬도 8이라 8바이트입니다. S는 tag@0, U는 8 정렬이므로 패딩 7 후 @8~15, 합계 16입니다. x.ll을 0으로 만든 뒤 i[1](바이트 4~7)에 1을 넣으면, 리틀 엔디안에서 바이트 4는 ll의 상위 32비트 중 가장 낮은 바이트입니다. 따라서 ll = 1 × 232 = 4294967296이 됩니다. 빅 엔디안 기계라면 i[1]이 하위 32비트가 되어 1이 출력됩니다.

핵심 정리

  • 구조체는 서로 다른 자료형을 하나로 묶은 사용자 정의 자료형입니다. 형 이름은 struct 태그 전체이며, 선언만으로는 메모리가 생기지 않고 변수를 정의할 때 할당됩니다.
  • 구조체 변수는 ., 구조체 포인터는 ->로 멤버에 접근합니다. p->m은 (*p).m과 같고, *p.m은 우선순위 때문에 틀린 식입니다.
  • 초기화는 순서 초기화와 지정 초기화(C99, .멤버 = 값)가 있고, 일부만 주면 나머지는 0이 됩니다. = { 0 }은 전체 0 초기화 관용구입니다.
  • 같은 형의 구조체는 =로 통째로 대입(배열 멤버 포함)할 수 있지만 ==로 비교할 수는 없습니다. 포인터 멤버는 얕은 복사가 되므로 필요하면 깊은 복사 함수를 만듭니다.
  • C는 항상 값 전달입니다. 구조체를 수정하거나 큰 구조체를 효율적으로 넘길 때는 포인터를, 읽기 전용이면 const 포인터를 씁니다.
  • 금액은 원 단위 정수(long long)로 다루고, 입출금 함수는 오류 코드를 반환하며 호출한 쪽에서 반드시 검사합니다.
  • 구조체 배열을 함수에 넘기면 주소가 넘어가 원본이 바뀝니다. 큰 레코드는 포인터 배열로 정렬하면 효율적입니다.
  • 패딩은 CPU의 정렬 접근 요구 때문에 생깁니다. 각 멤버는 자기 정렬 값의 배수 오프셋에, 전체 크기는 최대 정렬 값의 배수로 맞춰집니다. 큰 멤버부터 배치하면 크기를 줄일 수 있습니다.
  • 금융 전문처럼 바이트 배치가 정해진 데이터는 char 배열 필드로 정의하고 _Static_assert로 길이를 검증합니다.
  • 자기 참조 구조체는 자기 형을 가리키는 포인터 멤버를 가지며 연결 리스트의 기초입니다. 자기 형 자체를 멤버로 둘 수는 없습니다.
  • 공용체는 모든 멤버가 같은 메모리를 공유하며 크기는 가장 큰 멤버 기준입니다. 엔디안 확인, 바이트 재해석, 태그 있는 공용체에 씁니다.
  • 열거형은 이름 붙은 정수 상수 집합으로, 매직 넘버를 없애고 switch 누락 경고를 받을 수 있습니다. typedef는 형에 별칭을 붙이며 #define과 달리 컴파일러가 이해하는 형 이름입니다.

Q1. 구조체 패딩(padding)이 무엇이고 왜 생기나요?

구조체 멤버 사이나 끝에 컴파일러가 넣는 빈 바이트입니다. CPU는 자료형 크기의 배수 주소에 있는 데이터를 한 번에 읽도록 설계되어 있어, 정렬되지 않은 데이터는 두 번 읽어야 하거나 일부 아키텍처에서는 예외가 발생합니다. 그래서 컴파일러는 각 멤버를 정렬 요구에 맞는 오프셋에 두고, 구조체 배열에서도 정렬이 유지되도록 끝에 꼬리 패딩을 넣습니다. 예를 들어 char, int, char 순서면 12바이트, char, char, int면 8바이트입니다.

꼬리 질문 대비: "패딩을 없애려면?" 멤버를 정렬 값이 큰 순서로 배치하는 것이 첫 번째이고, #pragma pack이나 __attribute__((packed))도 있지만 비정렬 접근 성능 저하와 이식성 문제가 있다고 답합니다. 네트워크 전문은 char 배열로 정의하는 것이 일반적이라는 점도 덧붙이면 좋습니다.

Q2. 구조체와 공용체의 차이는 무엇인가요?

구조체는 멤버마다 별도의 메모리를 가져 모든 멤버를 동시에 저장할 수 있고, 크기는 멤버 크기 합에 패딩을 더한 값입니다. 공용체는 모든 멤버가 같은 시작 주소의 메모리를 공유해 한 번에 하나의 멤버만 의미가 있고, 크기는 가장 큰 멤버 크기에 정렬 패딩을 더한 값입니다. 공용체는 메모리 절약, 같은 바이트의 다른 형 해석, 태그 있는 공용체로 여러 형태의 데이터를 표현할 때 씁니다.

꼬리 질문 대비: "공용체로 엔디안을 확인하는 방법은?" int에 1을 넣고 char 배열 첫 바이트가 1이면 리틀 엔디안이라고 설명합니다.

Q3. 구조체를 함수에 넘길 때 값으로 넘기는 것과 포인터로 넘기는 것의 차이는?

값으로 넘기면 구조체 전체가 복사되어 함수 안에서 바꿔도 원본에 영향이 없지만, 구조체가 크면 복사 비용이 큽니다. 포인터로 넘기면 주소 8바이트만 복사되므로 빠르고 원본을 수정할 수 있습니다. 수정할 의도가 없다면 const 포인터로 받아 실수로 바꾸는 것을 컴파일러가 막게 합니다. 엄밀히 C는 언제나 값 전달이고, 포인터 전달은 주소라는 값을 넘겨 참조 효과를 내는 것입니다.

꼬리 질문 대비: "C에 call by reference가 있나요?" 없습니다. C++의 참조(&)와 구분해 설명합니다.

Q4. 얕은 복사와 깊은 복사의 차이를 설명해 주세요.

얕은 복사는 구조체의 바이트를 그대로 복사하므로 포인터 멤버는 주소만 복사되어 원본과 사본이 같은 대상을 공유합니다. 한쪽에서 수정하면 다른 쪽도 바뀌고, 둘 다 free하면 이중 해제가 됩니다. 깊은 복사는 포인터가 가리키는 대상까지 새로 할당해 복사하므로 두 객체가 완전히 독립됩니다. C의 구조체 대입은 얕은 복사이므로 동적 메모리를 가진 구조체는 복사 함수를 직접 작성해야 합니다.

Q5. 구조체를 memcmp로 비교하면 안 되는 이유는?

패딩 바이트의 값은 정해져 있지 않기 때문입니다. 멤버 값이 모두 같아도 패딩에 남은 쓰레기값이 다르면 memcmp는 다르다고 판단합니다. 또한 문자열 멤버는 널 문자 이후의 바이트가 다를 수 있고, 부동소수점은 +0.0과 -0.0처럼 값은 같지만 비트가 다른 경우가 있습니다. 멤버별 비교 함수를 작성하는 것이 정확합니다.

꼬리 질문 대비: "그럼 memset으로 0 초기화한 뒤라면 괜찮나요?" 대입 과정에서 패딩이 다시 바뀔 수 있으므로 보장되지 않는다고 답합니다.

Q6. 엔디안(endianness)이란 무엇이고 언제 문제가 되나요?

여러 바이트 데이터를 메모리에 저장하는 바이트 순서입니다. 리틀 엔디안은 하위 바이트를 낮은 주소에(x86, 대부분의 ARM 설정), 빅 엔디안은 상위 바이트를 낮은 주소에(네트워크 바이트 순서, 일부 메인프레임) 둡니다. 서로 다른 시스템이 바이너리 정수를 주고받거나 바이너리 파일을 공유할 때 문제가 됩니다. 네트워크에서는 htonl/ntohl로 변환하고, 금융 전문은 아예 숫자를 문자로 표현해 엔디안 문제를 피합니다.

Q7. enum과 #define 상수의 차이는?

#define은 전처리 단계의 단순 텍스트 치환이라 형 정보가 없고 디버거에 이름이 남지 않습니다. enum 상수는 컴파일러가 아는 int 상수로, 열거형이라는 형을 통해 의미가 문서화되고 디버거에서 이름으로 보이며 switch에서 처리하지 않은 값을 경고받을 수 있습니다. 값을 자동으로 증가시켜 주므로 상태 코드 정의에 편리합니다. 다만 C에서는 열거형 변수에 범위 밖 정수를 넣는 것을 막지 않습니다.

Q8. typedef와 #define으로 형 별칭을 만드는 것의 차이는?

typedef는 컴파일러가 처리하는 진짜 형 이름이고 #define은 텍스트 치환입니다. 대표적으로 #define PCHAR char *로 PCHAR a, b;를 선언하면 b는 char가 되지만, typedef로 만든 이름이면 둘 다 포인터가 됩니다. typedef는 범위 규칙을 따르고 함수 포인터 같은 복잡한 형을 읽기 쉽게 만들 때 특히 유용합니다.

Q9. 구조체 안에 자기 자신을 멤버로 둘 수 없는 이유는? 포인터는 왜 되나요?

자기 자신을 멤버로 가지면 크기 계산이 무한히 재귀되어 크기를 정할 수 없습니다. 구조체 정의가 끝나기 전까지 그 형은 불완전형이고, 불완전형의 객체는 멤버가 될 수 없습니다. 반면 포인터는 가리키는 대상과 무관하게 크기가 정해져 있으므로(64비트에서 8바이트) 불완전형을 가리키는 포인터는 멤버로 둘 수 있습니다. 이것이 연결 리스트와 트리의 기초입니다.

Q10. 지역 구조체 변수의 주소를 반환하면 어떻게 되나요?

지역 변수는 스택 프레임에 있고 함수가 반환되면 수명이 끝나므로, 그 주소는 댕글링 포인터가 됩니다. 역참조는 미정의 동작이며, 당장은 값이 남아 있어 정상처럼 보이다가 다음 함수 호출이 스택을 덮어쓰면 값이 바뀝니다. 구조체를 값으로 반환하거나, 호출자가 버퍼를 제공하거나, 동적 할당 후 반환하고 호출자가 해제하도록 합니다.

연습문제 17-8 금융 응용: 이자 지급 난이도 ★★★

정답과 해설 보기

실수 연산 대신 정수로 계산합니다. 곱셈을 먼저 하고 나눗셈을 나중에 해야 정밀도가 유지되지만, 곱셈 결과가 long long 범위를 넘지 않는지 확인해야 합니다. 잔액 1조 원(1012) × 250 = 2.5×1014로 범위(약 9.2×1018) 안이므로 안전합니다. 예: 잔액 1,200,000원, 250bp이면 1,200,000 × 250 / 120000 = 2500원입니다.

실무에서는 세금(이자소득세) 원천징수, 일별 잔액 기준 일할 계산, 단수 처리 규칙(절사·반올림)이 상품마다 정해져 있습니다.
