응용 포인터

포인터를 가리키는 포인터, 배열 전체를 가리키는 포인터, 함수를 가리키는 포인터, 무엇이든 가리킬 수 있는 포인터. 이름만 들으면 어렵지만 원리는 9~10장에서 배운 "주소를 담는 변수" 하나뿐입니다. 이 장의 도구들은 실무 C 코드의 뼈대입니다. 거래코드별 처리 함수를 표로 고르는 디스패치 테이블, 표준 정렬 함수 qsort, 범용 자료구조가 모두 여기서 나옵니다.

이 장에서 배울 것

  • 이중 포인터(int **)의 구조를 그림으로 설명하고, 함수에서 호출자의 포인터 값을 바꿀 수 있습니다.
  • 배열 포인터(int (*p)[4])와 포인터 배열(int *p[4])을 구분하고, a, &a, a[0]의 차이를 설명할 수 있습니다.
  • 오른쪽-왼쪽 규칙(시계방향 규칙)으로 복잡한 선언을 해석할 수 있습니다.
  • 함수 포인터를 선언·호출하고, 콜백과 qsort 비교 함수를 작성할 수 있습니다.
  • 거래코드별 처리 함수를 디스패치 테이블로 구현할 수 있습니다.
  • void *로 범용 함수를 만들고 올바르게 형 변환할 수 있습니다.
  • typedef로 복잡한 포인터 타입을 읽기 쉽게 만들 수 있습니다.

15-1이중 포인터와 배열 포인터

포인터도 결국 변수입니다. 변수이므로 메모리 어딘가에 자리를 차지하고 있고, 따라서 주소가 있습니다. 그 주소를 저장하는 변수가 바로 이중 포인터(double pointer, 포인터의 포인터)입니다. 또 포인터는 int 하나만 가리킬 수 있는 것이 아니라 배열 전체를 하나의 단위로 가리킬 수도 있습니다. 이것이 배열 포인터입니다. 이 절에서는 이 두 가지를 메모리 그림으로 분해합니다.

이중 포인터의 개념

비유로 시작하겠습니다. 은행 금고(a)에 돈이 있습니다. 금고 위치를 적은 쪽지(p)가 있습니다. 그 쪽지를 넣어 둔 서랍의 위치를 적은 또 다른 쪽지(pp)가 있습니다. pp를 들고 서랍을 찾아가면(*pp) 첫 번째 쪽지가 나오고, 그 쪽지를 따라 금고를 찾아가면(**pp) 돈이 나옵니다.

왜 그럴까? — 그냥 long long *에 p의 주소를 담으면 안 되나요?

주소는 결국 8바이트 숫자이니 long long *q = (long long *)&p;처럼 억지로 담을 수는 있습니다. 하지만 그러면 *q는 "그 자리의 8바이트를 long long 값으로 해석"하게 됩니다. 실제로 그 자리에 있는 것은 주소이므로 의미 없는 큰 숫자가 나오고, 한 번 더 따라갈 방법도 없습니다. 포인터의 타입은 "따라가서 무엇으로 해석할지"를 정하는 정보입니다. long long **는 "따라가면 long long *가 있다"는 뜻이므로 *pp의 결과를 다시 포인터로 쓸 수 있는 것입니다. 이것이 C가 포인터 단계마다 타입을 구분하는 이유입니다.

여기서 잠깐 — 삼중 포인터도 있나요?

문법적으로는 int ***, int ****처럼 얼마든지 가능합니다. 하지만 실무에서 삼중 이상은 거의 쓰지 않습니다. "함수에서 char **(문자열 배열)를 새로 할당해 돌려준다" 정도가 삼중 포인터가 나오는 드문 경우입니다. 포인터가 세 겹 이상 필요해 보이면 구조체로 설계를 정리하는 것이 좋다는 신호입니다.

함수에서 호출자의 포인터 값 바꾸기

13장에서 "함수에서 호출자의 변수를 바꾸려면 그 변수의 주소를 넘긴다"는 것을 배웠습니다. 바꾸고 싶은 변수가 int이면 int *를 넘깁니다. 그렇다면 바꾸고 싶은 변수가 포인터라면? 그 포인터의 주소, 즉 이중 포인터를 넘겨야 합니다. 규칙은 한 줄입니다.

한 줄 요약

T 타입 변수를 함수에서 바꾸려면 T*를 넘긴다. T가 int이면 int *, T가 char *이면 char **, T가 Account *이면 Account **입니다.

왜 그럴까? — 잘못된 예에서 found = ACCTS[i]는 어디를 바꿨나요?

C의 인수 전달은 언제나 값 복사입니다. find_acct("220-777", res)를 호출하면 res의 값(NULL)이 매개변수 found에 복사됩니다. 함수 안의 found = ...는 find_acct 프레임에 있는 복사본을 바꿀 뿐이고, 함수가 끝나면 그 복사본은 사라집니다. 포인터라고 특별 대우가 없습니다. int를 값으로 넘겨서 못 바꾸는 것과 정확히 같은 현상입니다. 그래서 "포인터 변수의 주소"를 넘겨야 하고, 그것의 타입이 const char **입니다.

은행 시스템에서는 — 출력 포인터 매개변수 관례

금융권 공통 모듈의 함수는 대부분 "반환값 = 처리 결과 코드, 결과 데이터 = 출력 매개변수" 형태를 따릅니다. 예를 들어 계좌 조회 모듈은 int acct_inquiry(const char *acct_no, AcctInfo **out)처럼 설계되어, 성공하면 0과 함께 *out에 조회 결과 구조체의 주소를 넣고, 실패하면 오류 코드를 반환하고 *out은 NULL로 둡니다. 호출하는 쪽은 항상 반환 코드를 먼저 확인한 다음에만 *out을 사용합니다. 이 관례가 지켜지지 않으면 실패한 조회의 쓰레기 포인터를 사용해 장애가 납니다. 또 함수 시작 부분에서 if (out) *out = NULL;로 출력 매개변수를 먼저 초기화해 두는 것이 방어적 코딩의 기본입니다.

예제 15-1 난이도 ★★☆

두 개의 const char * 변수가 가리키는 대상을 서로 맞바꾸는 함수 swap_str을 작성하세요. 문자열 내용은 복사하지 않아야 합니다.

정답과 해설 보기

바꿀 대상이 const char * 타입 변수이므로 그 주소인 const char **를 받습니다. 13장의 swap(int *, int *)에서 int를 const char *로 바꾼 것뿐입니다.

포인터 배열과 이중 포인터

14장에서 배운 포인터 배열 const char *names[5]의 이름 names는 식에서 쓰이면 첫 원소의 주소로 바뀝니다. 첫 원소의 타입이 const char *이므로 그 주소의 타입은 const char **입니다. 그래서 포인터 배열을 함수에 넘기면 이중 포인터로 받습니다. main(int argc, char **argv)가 바로 이 형태입니다.

p++는 p가 가리키는 대상(const char *, 8바이트)만큼 이동하므로 다음 원소로 넘어갑니다. 목록 끝에 NULL을 두는 방식(센티널, sentinel)은 argv와 같은 관례로, 개수를 따로 넘기지 않아도 됩니다.

배열 포인터 — 배열 전체를 가리키는 포인터

14장에서 2차원 배열을 함수에 넘기면 int (*m)[4] 타입이 된다는 것을 봤습니다. 이것이 배열 포인터(pointer to array)입니다. int 하나가 아니라 "int 4개짜리 배열 하나"를 가리키는 포인터입니다.

a, &a, a[0], &a[0]의 차이

배열 포인터를 이해하면 면접 단골 문제인 "배열 이름과 배열의 주소는 같은가?"에 정확히 답할 수 있습니다.

식타입값+1 하면
a (식에서)int * (변환됨)시작 주소4바이트 이동
&a[0]int *시작 주소4바이트 이동
&aint (*)[5]시작 주소20바이트 이동 (배열 끝 바로 뒤)
sizeof a-20 (변환되지 않음)-

왜 그럴까? — 주소는 같은데 왜 +1 결과가 다를까요?

배열의 첫 원소가 시작하는 곳과 배열 전체가 시작하는 곳은 같은 바이트이므로 주소값은 같습니다. 하지만 포인터에는 주소값 말고도 "무엇을 가리키는가(타입)"라는 정보가 붙어 있습니다. &a[0]은 int 하나를, &a는 int 5개짜리 배열 하나를 가리킵니다. 포인터 산술은 가리키는 대상의 크기만큼 움직이므로 각각 4바이트, 20바이트를 이동합니다(0x...e0 + 0x14 = 0x...f4).

또 배열 이름은 대부분의 식에서 첫 원소의 주소로 "변환(decay)"되지만 세 가지 예외가 있습니다. sizeof a, &a, 그리고 문자 배열을 초기화하는 문자열 리터럴입니다. 그래서 sizeof a는 20입니다.

예제 15-2 난이도 ★★★

long long t[4][3];의 시작 주소가 0x1000일 때 다음 식의 값(주소)과 타입을 쓰세요. (1) t + 1 (2) t[1] + 1 (3) &t + 1 (4) *t + 2 (5) &t[2][1]

정답과 해설 보기
  • (1) t는 long long (*)[3]로 변환, 한 행 = 24바이트 → 0x1018, 타입 long long (*)[3]
  • (2) t[1]은 1행(0x1018)이 long long *로 변환, +8 → 0x1020, 타입 long long *
  • (3) &t는 long long (*)[4][3], 전체 = 96바이트 → 0x1000 + 0x60 = 0x1060
  • (4) *t = t[0] → long long *(0x1000), +2 → +16 → 0x1010
  • (5) (2 × 3 + 1) × 8 = 56 = 0x38 → 0x1038, 타입 long long *

모든 문제는 "이 식의 타입이 무엇을 가리키는가 → 그 크기만큼 이동"이라는 하나의 규칙으로 풀립니다.

복잡한 선언 해석법 — 오른쪽-왼쪽 규칙

int *a[3]와 int (*a)[3]처럼 괄호 하나로 의미가 완전히 바뀌는 선언을 정확히 읽는 방법이 필요합니다. C의 선언은 "사용하는 모양대로 선언한다"는 원칙으로 만들어졌고, 이를 읽는 체계적인 방법이 오른쪽-왼쪽 규칙(right-left rule)입니다. 같은 원리를 그림으로 표현한 것을 시계방향 나선 규칙(clockwise/spiral rule)이라고 부릅니다.

  1. 변수 이름에서 출발해 "이름은"이라고 읽습니다.
  2. 오른쪽을 봅니다. [N]이 있으면 "N개짜리 배열이고, 그 원소는", ( ... )가 있으면 "함수이고, 그 반환값은"이라고 읽고 계속 오른쪽으로 갑니다.
  3. 오른쪽에서 닫는 괄호 )나 끝을 만나면 왼쪽으로 돌아갑니다. *가 있으면 "포인터이고, 그것이 가리키는 것은"이라고 읽습니다.
  4. 괄호 한 겹을 다 읽으면 괄호 밖으로 나가 다시 2번(오른쪽)부터 반복합니다.
  5. 마지막에 남은 기본 타입(int, char 등)을 읽고 끝냅니다.
선언해석
char **pp는 포인터 → char 포인터를 가리킴
char *p[5]p는 5개 배열 → 원소는 char 포인터
char (*p)[5]p는 포인터 → char 5개 배열을 가리킴
int (*p[4])(void)p는 4개 배열 → 원소는 포인터 → 인자 없이 int를 반환하는 함수를 가리킴 (함수 포인터 배열)
int (*(*p)(int))[3]p는 포인터 → int를 받는 함수 → 그 함수는 포인터를 반환 → 그 포인터는 int 3개 배열을 가리킴
void (*signal(int, void (*)(int)))(int)signal은 (int, 함수포인터)를 받는 함수 → 반환값은 포인터 → int를 받고 void를 반환하는 함수를 가리킴 (표준 라이브러리의 실제 선언)

여기서 잠깐 — 읽기 어려운 선언은 typedef로 쪼갭니다

마지막 signal의 선언은 C 프로그래머도 한 번에 읽기 어렵습니다. 그래서 실무에서는 15-2-7에서 배울 typedef로 중간 타입에 이름을 붙여 typedef void (*SigHandler)(int); SigHandler signal(int sig, SigHandler h);처럼 씁니다. 리눅스 매뉴얼 페이지도 이렇게 설명합니다. 또 명령행 도구 cdecl을 쓰면 선언을 영어 문장으로 풀어 줍니다(cdecl explain 'int (*p)[3]').

예제 15-3 난이도 ★★★

다음 선언을 해석하세요. (1) double *(*q)[4] (2) long long (*calc[3])(long long, int) (3) char *(*get_name)(int)

정답과 해설 보기
  • (1) q → (괄호 안) 왼쪽 *: q는 포인터 → 밖 오른쪽 [4]: 4개짜리 배열을 가리킴 → 왼쪽 *: 원소는 포인터 → double. "q는 double 포인터 4개짜리 배열을 가리키는 포인터"입니다.
  • (2) calc → 오른쪽 [3]: 3개 배열 → 왼쪽 *: 원소는 포인터 → 밖 오른쪽 (long long, int): 함수를 가리킴 → long long 반환. "(long long, int)를 받아 long long을 반환하는 함수를 가리키는 포인터 3개의 배열". 이자 계산 방식(단리·복리·일할) 3가지를 담는 표 같은 용도입니다.
  • (3) get_name → 왼쪽 *: 포인터 → 밖 오른쪽 (int): int를 받는 함수 → 왼쪽 *: 포인터 반환 → char. "int를 받아 char 포인터를 반환하는 함수를 가리키는 포인터"입니다.

15-2함수 포인터와 void 포인터

지금까지 포인터는 데이터를 가리켰습니다. 그런데 13장의 메모리 구조 그림을 떠올려 보면, 함수의 기계어도 코드(.text) 영역에 놓인 바이트들입니다. 메모리에 있으니 주소가 있고, 주소가 있으니 가리킬 수 있습니다. 함수를 가리키는 포인터를 함수 포인터라고 합니다. 함수 포인터를 쓰면 "어떤 함수를 호출할지"를 실행 중에 결정할 수 있습니다. 그리고 타입을 정하지 않고 아무 데이터나 가리키는 void 포인터를 함께 쓰면 자료형에 상관없이 동작하는 범용 함수를 만들 수 있습니다.

함수의 주소

함수를 호출한다는 것은 CPU가 그 함수 기계어의 시작 주소로 점프하는 것입니다(x86-64의 call 명령). 함수 이름은 식에서 쓰이면 배열 이름처럼 그 함수의 시작 주소로 변환됩니다.

함수 포인터의 선언과 호출

함수 포인터를 선언하려면 가리킬 함수의 반환형과 매개변수 목록을 똑같이 맞춰야 합니다. 함수 원형에서 함수 이름 자리를 (*포인터이름)으로 바꾸면 됩니다.

왜 그럴까? — op(...)와 (*op)(...)가 왜 같을까요?

C 표준에서 함수 호출 연산자 ()는 사실 함수 포인터를 피연산자로 받습니다. 우리가 평소 쓰는 deposit(1, 2)도 함수 이름 deposit이 먼저 함수 포인터로 변환된 다음 호출되는 것입니다. op는 이미 함수 포인터이므로 그대로 호출되고, *op는 함수를 가리키는 "함수 지정자"가 되었다가 다시 함수 포인터로 변환됩니다. 그래서 (*op)(), (**op)(), (***op)()도 모두 같습니다. 옛날 코드는 "포인터를 통한 호출"임을 드러내려고 (*op)()를 쓰고, 현대 코드는 op()를 많이 씁니다.

자주 하는 실수 — 함수 포인터의 타입 불일치

형 변환으로 컴파일러를 속이면 대입은 되지만, 호출할 때 매개변수 개수와 타입, 반환형이 실제 함수와 다르므로 미정의 동작입니다. 호출 규약상 인자가 어느 레지스터로 가는지, 반환값을 어떻게 받는지가 어긋납니다. 함수 포인터에 강제 형 변환이 필요하다는 것 자체가 설계가 잘못되었다는 신호입니다.

콜백 함수

콜백(callback)은 "함수에게 함수를 넘겨서, 그 함수가 적당한 때에 내가 준 함수를 다시 불러 주게(call back) 하는 것"입니다. 공통 처리(반복, 순회, 에러 처리)는 한 함수가 맡고, 달라지는 부분만 콜백으로 갈아 끼웁니다.

예를 들어 거래 내역 배열을 순회하면서 "조건에 맞는 거래만 세는" 함수를 생각해 봅시다. 조건이 "100만 원 이상"일 수도, "출금 거래"일 수도, "야간 거래"일 수도 있습니다. 조건마다 순회 함수를 새로 만들지 않고, 조건 판단만 콜백으로 받으면 됩니다.

출금(음수)은 −1,200,000, −30,000, −5,000,000의 3건, 고액(절대값 100만 이상)은 −1,200,000, 3,000,000, −5,000,000의 3건입니다(990,000은 100만 미만).

왜 그럴까? — 콜백이 왜 좋은 설계일까요?

콜백은 변하는 것과 변하지 않는 것을 분리합니다. 순회·검증·로깅 같은 공통 로직은 한 번만 작성하고 철저히 테스트해 두고, 업무 규칙이 바뀌면 작은 조건 함수만 추가합니다. 객체지향 언어의 인터페이스, 전략 패턴, 람다가 하는 일을 C에서는 함수 포인터로 합니다. 운영체제의 시그널 핸들러, 스레드 시작 함수(pthread_create), GUI 이벤트 처리, 표준 라이브러리의 qsort와 bsearch, atexit가 모두 콜백입니다.

qsort와 비교 함수

표준 라이브러리 <stdlib.h>의 qsort는 어떤 타입의 배열이든 정렬하는 범용 정렬 함수입니다. 어떻게 int도, double도, 구조체도 정렬할 수 있을까요? 비결은 두 가지입니다. 배열을 void *(타입 없는 주소)와 원소 크기로 받고, 두 원소를 비교하는 방법을 콜백으로 받는 것입니다.

비교 함수는 두 원소의 주소를 받아서, 첫 번째가 앞에 와야 하면 음수, 같으면 0, 뒤에 와야 하면 양수를 반환해야 합니다.

자주 하는 실수 — return x - y; 비교 함수

인터넷 예제에서 흔히 보는 형태지만 두 가지 버그가 있습니다. ① x - y가 long long 범위를 넘으면 부호 있는 정수 오버플로로 미정의 동작입니다. ② 결과를 int로 자르면 상위 비트가 버려져 부호가 뒤집힐 수 있습니다. 예를 들어 x = 9,999,999,999, y = 0이면 차이 9,999,999,999는 16진수로 0x2540BE3FF이고, 하위 32비트 0x540BE3FF는 양수 1,410,065,407이라 운 좋게 맞지만, x = 4,294,967,296(2의 32승), y = 0이면 하위 32비트가 0이 되어 "같다"고 판단합니다. int 배열이라도 INT_MIN과 양수의 차이는 오버플로합니다.

이렇게 해결합니다

뺄셈 대신 비교 연산을 씁니다. return (x > y) - (x < y);는 비교 결과(0 또는 1)끼리의 뺄셈이라 오버플로가 절대 일어나지 않고 −1, 0, 1만 나옵니다. 또는 if (x < y) return -1; if (x > y) return 1; return 0;처럼 풀어 써도 됩니다. 금액을 다루는 비교 함수에서는 반드시 이 형태를 씁니다.

왜 그럴까? — 비교 함수는 왜 값이 아니라 주소(const void *)를 받을까요?

qsort는 원소의 타입을 모르므로 원소를 "값"으로 꺼낼 수 없습니다. 원소가 4바이트 int인지 200바이트 구조체인지 모르니 레지스터에 담아 넘길 방법이 없습니다. qsort가 아는 것은 시작 주소와 원소 크기뿐이므로, (char *)base + i * size로 i번째 원소의 주소를 계산해 비교 함수에 넘깁니다. 타입을 아는 것은 비교 함수를 작성한 우리뿐이므로, 비교 함수 안에서 원래 타입으로 변환해 꺼내 읽습니다. const가 붙은 이유는 비교 함수가 원소를 바꾸면 안 되기 때문입니다.

실무 예제 — 거래코드별 처리 함수 디스패치 테이블

은행 온라인 시스템에는 하루에 수백 종류의 거래코드(예: 1001 입금, 1002 출금, 2001 이체, 3001 잔액조회)가 들어옵니다. 전문(통신 메시지)의 거래코드를 보고 알맞은 처리 함수를 호출해야 하는데, 이것을 switch문으로 쓰면 수백 개의 case가 한 함수에 몰리고, 거래 하나를 추가할 때마다 그 거대한 함수를 고쳐야 합니다.

대안은 디스패치 테이블(dispatch table)입니다. "거래코드 → 처리 함수 주소"의 대응표를 배열로 만들어 두고, 표에서 찾아 함수 포인터로 호출합니다. 새 거래를 추가하려면 표에 한 줄만 넣으면 됩니다.

왜 그럴까? — 디스패치 테이블이 switch보다 나은 점

  1. 개방-폐쇄 원칙: 새 거래를 추가할 때 dispatch 함수는 고치지 않고(폐쇄) 표에 한 줄만 추가합니다(개방). 이미 검증된 공통 로직을 건드리지 않으니 회귀 버그 위험이 줄어듭니다.
  2. 공통 처리의 일원화: 로깅, 소요시간 측정, 오류 코드 변환, 권한 검사를 dispatch 한 곳에서 하므로 거래마다 빠뜨릴 일이 없습니다.
  3. 데이터로서의 코드: 표는 데이터이므로 거래코드 목록을 출력하거나, 코드 순으로 정렬해 이진 탐색(bsearch)으로 빠르게 찾는 등 프로그램이 스스로 다룰 수 있습니다.
  4. const 표: static const로 선언했으므로 표는 읽기 전용 영역에 놓여, 실행 중 버그로 함수 포인터가 덮어써지는 사고(보안 공격 포함)를 막습니다.

단점도 있습니다. 거래코드가 몇 개 안 되면 switch가 더 읽기 쉽고, 컴파일러가 switch를 점프 테이블로 최적화하므로 속도 차이도 거의 없습니다. 거래 종류가 많고 자주 추가될 때 디스패치 테이블이 빛납니다.

은행 시스템에서는 — 거래 라우팅

실제 계정계 온라인 프레임워크(TP 모니터, 미들웨어 기반)는 바로 이 구조로 동작합니다. 대외계에서 들어온 전문의 헤더에서 거래코드(또는 서비스명)를 읽어, 등록된 서비스 테이블에서 처리 모듈을 찾아 호출합니다. 서비스 테이블은 설정 파일이나 DB로 관리되고, 처리 모듈은 공유 라이브러리(.so)로 분리되어 dlopen/dlsym으로 함수 주소를 얻어 오기도 합니다(dlsym의 반환값이 바로 함수 포인터로 변환해 쓰는 void *입니다). 개발자는 "거래 하나 = 처리 함수 하나 + 테이블 등록 한 줄"로 작업하고, 전문 파싱·로깅·트랜잭션 커밋/롤백·타임아웃은 프레임워크가 공통으로 처리합니다.

표에서 찾지 못한 거래코드를 반드시 명시적 오류(위 예제의 99)로 응답해야 한다는 점도 중요합니다. 응답 없이 무시하면 대외기관은 타임아웃 후 재전송하고, 이것이 중복 거래나 망 장애로 번질 수 있습니다.

void 포인터 — 범용 포인터

void *는 "가리키는 대상의 타입을 정하지 않은 포인터"입니다. 어떤 객체 포인터든 void *에 형 변환 없이 담을 수 있고, void *를 다른 객체 포인터 타입에 형 변환 없이 대입할 수도 있습니다(C에서. C++은 명시적 변환 필요). malloc의 반환형, memcpy/memset의 매개변수, qsort의 배열 매개변수가 모두 void *입니다.

void 포인터에는 두 가지 제약이 있습니다.

  • 역참조 불가: *vp는 컴파일 에러입니다. 몇 바이트를 어떻게 읽을지 모르기 때문입니다.
  • 포인터 산술 불가: vp + 1은 표준 C에서 허용되지 않습니다(대상 크기를 모름). gcc는 확장 기능으로 1바이트로 취급해 허용하지만 이식성이 없으므로 (char *)vp + 1로 씁니다.

왜 그럴까? — 타입을 모르는데 어떻게 바꿀 수 있나요?

맞바꾸기에 필요한 것은 "몇 바이트를 어디서 어디로 옮길지"뿐입니다. 값의 의미(정수인지 실수인지)는 필요 없습니다. 그래서 주소(void *)와 크기(size_t)만 받고, 실제 복사는 바이트 단위로 동작하는 memcpy에 맡깁니다. 이것이 qsort, bsearch, memcpy 같은 C 범용 함수의 공통 설계입니다. "void* + 크기 + (필요하면) 콜백"이 C에서 제네릭(일반화) 프로그래밍을 하는 방법입니다.

대가도 있습니다. 컴파일러가 타입 검사를 해 줄 수 없습니다. gswap(&x, &r1, sizeof x)처럼 long long과 double을 섞어도 에러가 나지 않고 이상한 값이 생깁니다. 크기를 잘못 넘기면 버퍼 오버런이 됩니다. 범용성과 타입 안전성을 맞바꾼 것이므로, void*를 쓰는 함수는 호출하는 쪽이 더 조심해야 합니다.

자주 하는 실수 — 함수 포인터를 void*에 담기

표준 C에서 void *는 객체(데이터) 포인터용입니다. 함수 포인터를 void *로, 또는 그 반대로 변환하는 것은 표준이 보장하지 않습니다(어떤 아키텍처는 코드 주소와 데이터 주소의 크기가 다름). POSIX는 dlsym 때문에 이 변환이 동작하도록 요구하므로 리눅스에서는 문제가 없지만, 이식 가능한 코드에서 "아무 함수나 담는 포인터"가 필요하면 void (*)(void) 같은 함수 포인터 타입을 범용으로 쓰고 호출 전에 원래 타입으로 되돌립니다.

여기서 잠깐 — malloc 결과에 형 변환을 할까 말까?

C에서는 long long *p = malloc(n * sizeof *p);처럼 형 변환 없이 씁니다. void *는 다른 객체 포인터로 자동 변환되기 때문입니다. 형 변환 (long long *)malloc(...)을 붙이면, 예전 C89에서는 <stdlib.h>를 빠뜨렸을 때 컴파일러가 malloc을 int 반환 함수로 가정한 것을 형 변환이 가려 64비트에서 주소 상위 비트가 잘리는 버그를 숨길 수 있었습니다. C++에서 컴파일해야 하는 코드라면 형 변환이 필요합니다. 16장에서 다시 다룹니다.

typedef로 가독성 높이기

함수 포인터 선언은 길고 읽기 어렵습니다. 특히 함수 포인터를 매개변수로 받거나 반환하거나 배열로 만들 때 괄호가 겹겹이 쌓입니다. typedef는 기존 타입에 새 이름(별칭)을 붙여 이 문제를 해결합니다. 새로운 타입을 만드는 것이 아니라 이름만 붙이는 것입니다.

typedef 문법은 "변수 선언 앞에 typedef를 붙이면, 변수 이름 자리에 있던 것이 타입 이름이 된다"로 기억하면 쉽습니다.

5,000,000 × 30 / 10000 = 15,000원입니다. 함수 포인터를 쓰기 전 NULL 검사를 한 점에 주목하세요. NULL 함수 포인터를 호출하면 주소 0으로 점프하여 즉시 Segmentation fault가 납니다.

왜 그럴까? — typedef가 #define보다 나은 이유

#define PCHAR char *로 정의하고 PCHAR a, b;라고 쓰면 전처리 후 char *a, b;가 되어 b는 포인터가 아닌 char가 됩니다. 매크로는 단순 문자열 치환이기 때문입니다. typedef char *PChar; PChar a, b;는 a, b 모두 char *입니다. typedef는 컴파일러가 이해하는 진짜 타입 이름이므로 이런 함정이 없고, 디버거에서도 이름이 보이며, 범위 규칙도 따릅니다.

자주 하는 실수 — 포인터를 typedef로 숨기기

typedef Account *AccountPtr;처럼 데이터 포인터를 typedef 뒤에 숨기면, 코드를 읽는 사람이 그것이 포인터인지 알기 어려워 NULL 검사나 해제를 빠뜨리기 쉽습니다. 또 const AccountPtr p는 "가리키는 Account가 const"가 아니라 "포인터 자체가 const"(Account *const p)가 되어 의도와 다릅니다. 많은 코딩 표준(리눅스 커널 포함)은 함수 포인터 typedef는 권장, 데이터 포인터 typedef는 지양합니다.

예제 15-8 난이도 ★★☆

다음 선언을 typedef를 이용해 읽기 쉽게 다시 쓰세요: int (*(*handlers)[5])(const char *);

정답과 해설 보기

먼저 해석합니다. handlers → *: 포인터 → [5]: 5개짜리 배열을 가리킴 → *: 원소는 포인터 → (const char *): 함수를 가리킴 → int 반환. 즉 "(const char*)를 받아 int를 반환하는 함수의 포인터 5개짜리 배열을 가리키는 포인터"입니다.

핵심 정리

  • 이중 포인터 T **는 T * 변수의 주소를 담습니다. * 하나마다 화살표 하나를 따라가고 타입에서 *가 하나 빠집니다.
  • 함수에서 T 타입 변수를 바꾸려면 T*를 넘깁니다. 포인터 변수를 바꾸려면 이중 포인터를 넘깁니다.
  • 포인터 배열의 이름은 이중 포인터로 변환되므로 char *argv[]와 char **argv는 매개변수에서 같습니다. NULL 센티널로 끝을 표시할 수 있습니다.
  • 배열 포인터 int (*p)[4]는 배열 하나를 가리키며 +1 하면 배열 크기(16바이트)만큼 이동합니다. 포인터 배열 int *p[4]와 구분합니다.
  • a와 &a는 주소값이 같지만 타입이 달라(int * vs int (*)[N]) +1 결과가 다릅니다.
  • 선언은 오른쪽-왼쪽 규칙으로 읽습니다: 이름에서 출발 → 오른쪽(배열·함수) 우선 → 막히면 왼쪽(포인터) → 괄호 밖으로 반복.
  • 함수 포인터는 코드 영역의 함수 주소를 담고, 반환형과 매개변수가 정확히 일치해야 합니다. fp()와 (*fp)()는 같습니다.
  • 콜백은 공통 로직과 변하는 규칙을 분리합니다. qsort 비교 함수는 원소의 주소를 받으며, 뺄셈 대신 (x > y) - (x < y)로 비교합니다.
  • 디스패치 테이블(코드 → 함수 포인터 표)은 거래 추가를 표 한 줄로 만들고 공통 처리를 한 곳에 모읍니다.
  • void *는 타입 없는 객체 포인터로 역참조·산술이 불가하며, 크기와 콜백을 함께 받아 범용 함수를 만듭니다. 타입 안전성은 호출자 책임입니다.
  • typedef로 함수 포인터 타입에 이름을 붙이면 배열, 매개변수, 반환형 선언이 단순해집니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. 이중 포인터는 언제 사용하나요?

대표적으로 두 경우입니다. 첫째, 함수 안에서 호출자의 포인터 변수 자체를 바꿔야 할 때입니다. 예를 들어 함수가 메모리를 할당해 그 주소를 호출자의 포인터에 넣어 주거나, 연결 리스트의 head 포인터를 수정할 때 Node **head를 받습니다. 둘째, 포인터 배열(문자열 목록, argv)을 함수에 넘길 때 배열 이름이 이중 포인터로 변환됩니다.
꼬리 질문 대비: "연결 리스트 삽입에서 이중 포인터를 쓰면 좋은 점은?" → head가 바뀌는 경우와 중간 삽입을 같은 코드로 처리할 수 있어 특수 처리가 사라집니다.

Q2. 포인터 배열과 배열 포인터의 차이는?

int *p[4]는 int 포인터 4개를 원소로 가진 배열로 크기가 32바이트입니다. int (*p)[4]는 int 4개짜리 배열 하나를 가리키는 포인터 하나로 크기가 8바이트이고, +1 하면 16바이트 이동합니다. 2차원 배열을 함수에 넘기면 배열 포인터 타입이 되고, 포인터 배열은 길이가 다른 문자열 목록 등에 씁니다. 괄호가 *를 먼저 결합시키는지가 차이를 만듭니다.

Q3. 배열 이름 a와 &a의 차이는?

둘 다 같은 주소값을 갖지만 타입이 다릅니다. a는 식에서 첫 원소의 주소(int *)로 변환되어 +1 하면 원소 크기만큼, &a는 배열 전체의 주소(int (*)[N])라서 +1 하면 배열 전체 크기만큼 이동합니다. 또 sizeof a는 배열 전체 크기를 주며, sizeof와 &의 피연산자일 때는 배열이 포인터로 변환되지 않습니다.

Q4. 함수 포인터는 무엇이고 어디에 쓰이나요?

코드 영역에 있는 함수의 시작 주소를 저장하는 포인터로, 어떤 함수를 호출할지 실행 중에 결정할 수 있게 합니다. 콜백(qsort 비교 함수, 시그널 핸들러, 스레드 시작 함수), 디스패치 테이블(명령·거래코드별 처리), 플러그인 구조(dlsym), 상태 머신 구현에 쓰입니다. C에서 다형성을 흉내 내는 핵심 도구이며 C++의 가상 함수 테이블(vtable)도 결국 함수 포인터 배열입니다.
꼬리 질문 대비: "vtable이란?" → 클래스마다 가상 함수 주소를 담은 표를 두고 객체가 그 표를 가리키는 포인터를 가져, 호출 시 표에서 함수를 찾아 부르는 구조입니다.

Q5. 콜백 함수란 무엇인가요?

다른 함수에 인자로 넘겨져 그 함수가 적절한 시점에 호출하는 함수입니다. 호출자가 "무엇을 할지"를, 호출된 쪽이 "언제 할지"를 결정하여 공통 로직과 가변 로직을 분리합니다. C에서는 함수 포인터로 구현하며, 상태가 필요하면 void *ctx 같은 사용자 데이터 포인터를 함께 넘기는 것이 관례입니다.

Q6. qsort 비교 함수에서 return a - b;가 왜 위험한가요?

a − b가 해당 정수 타입의 범위를 넘으면 부호 있는 오버플로로 미정의 동작이 되고, 실제로는 부호가 뒤집혀 정렬 순서가 틀어집니다. 예를 들어 INT_MIN과 1의 차이는 int로 표현할 수 없습니다. 비교 연산을 써서 (a > b) - (a < b)로 −1, 0, 1을 반환해야 합니다. 또한 비교 함수는 일관성(추이성)을 지켜야 하며 그렇지 않으면 qsort 결과가 정의되지 않습니다.

Q7. void 포인터의 특징과 주의점은?

어떤 객체 포인터든 형 변환 없이 담을 수 있는 범용 포인터로, malloc 반환값이나 memcpy, qsort처럼 타입에 독립적인 함수에 쓰입니다. 대상 크기를 모르므로 역참조와 포인터 산술이 불가하며, 사용하려면 올바른 타입으로 변환해야 합니다. 컴파일러의 타입 검사가 사라지므로 잘못된 타입으로 해석하거나 크기를 틀리게 넘기는 버그를 스스로 막아야 합니다.
꼬리 질문 대비: "함수 포인터를 void*에 담아도 되나요?" → 표준은 보장하지 않으며 POSIX 환경에서만 허용됩니다.

Q8. typedef와 #define의 차이는?

#define은 전처리기의 문자열 치환이고 typedef는 컴파일러가 처리하는 타입 별칭입니다. 그래서 #define P char* 후 P a, b;는 b가 char가 되지만 typedef는 둘 다 포인터가 됩니다. typedef는 범위 규칙을 따르고 디버거에 이름이 남으며, 함수 포인터·배열 타입처럼 치환으로 표현하기 어려운 타입에도 이름을 붙일 수 있습니다.

Q9. 복잡한 C 선언을 어떻게 해석하나요?

오른쪽-왼쪽 규칙을 씁니다. 식별자에서 시작해 오른쪽에 []나 ()가 있으면 배열/함수로 읽고, 닫는 괄호나 끝을 만나면 왼쪽의 *를 포인터로 읽으며, 괄호를 벗어날 때마다 반복하고 마지막에 기본 타입을 읽습니다. 예를 들어 int (*fp[3])(void)는 "인자 없이 int를 반환하는 함수를 가리키는 포인터 3개의 배열"입니다. 실무에서는 typedef로 쪼개 가독성을 높입니다.

장점: ① 하나의 구현으로 모든 타입을 처리해 코드 중복이 없습니다. ② 검증된 라이브러리 하나를 재사용하므로 버그가 줄고 유지보수가 쉽습니다.

단점: ① 컴파일러의 타입 검사가 사라져 잘못된 타입·크기를 넘겨도 에러가 나지 않습니다. ② 비교를 함수 포인터로 간접 호출하므로 인라인 최적화가 어려워 타입별 전용 함수보다 느릴 수 있습니다. ③ 코드를 읽을 때 실제 타입을 추적하기 어렵습니다.

보완: 타입별 얇은 래퍼 함수(sort_amounts(long long *a, size_t n))를 만들어 내부에서만 void* 함수를 호출하게 하면, 외부에는 타입 안전한 인터페이스를 제공할 수 있습니다. 크기는 항상 sizeof a[0]처럼 변수에서 계산해 넘기고, C11의 _Generic으로 타입별 함수를 자동 선택하는 매크로를 만들 수도 있습니다.
