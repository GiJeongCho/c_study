포인터

포인터는 C 언어의 심장입니다. 메모리를 "이름"이 아니라 "주소"로 다루는 법을 익히면, 함수가 호출한 쪽의 잔액을 직접 바꾸고, 수백 바이트짜리 원장 레코드를 복사 없이 넘기고, 배열·문자열·동적 메모리·자료구조까지 하나의 원리로 이해할 수 있게 됩니다. 이 장은 천천히, 그림과 함께, "왜 그런가"를 끝까지 따라가 봅니다.

이 장에서 배울 것

  • 메모리 주소가 무엇이고, 변수가 메모리에 어떻게 자리 잡는지 그림으로 이해합니다.
  • 주소 연산자 &, 간접 참조 연산자 *, 포인터 선언의 정확한 의미를 구분합니다.
  • 포인터의 크기가 가리키는 자료형과 무관하게 일정한 이유, NULL 포인터의 역할을 설명합니다.
  • 포인터에 자료형이 왜 필요한지, 포인터 연산(p+1)이 왜 바이트 단위가 아닌지 이해합니다.
  • const와 포인터의 4가지 조합을 읽고 쓸 수 있습니다.
  • 포인터로 두 변수를 swap 해야 하는 이유(값에 의한 전달)를 스택 그림으로 설명합니다.
  • 댕글링 포인터·와일드 포인터의 원인과 해결책을 알고, 잔액 수정 함수를 안전하게 작성합니다.

09-1포인터의 기본 개념

포인터를 어렵게 느끼는 가장 큰 이유는 "포인터"라는 낯선 단어 때문입니다. 하지만 포인터는 사실 아주 단순한 것입니다. 포인터는 메모리 주소를 저장하는 변수입니다. 정수를 저장하는 변수가 int 변수이듯이, 주소를 저장하는 변수가 포인터 변수일 뿐입니다. 이 한 문장을 제대로 이해하려면 먼저 "메모리 주소"가 무엇인지부터 확실히 해야 합니다.

메모리와 주소 — 변수는 어디에 사는가

컴퓨터의 메모리(RAM)는 거대한 사물함 줄이라고 생각하면 편합니다. 사물함 하나의 크기는 1바이트(8비트)이고, 각 사물함에는 0번부터 시작하는 고유한 번호가 붙어 있습니다. 이 번호가 바로 메모리 주소(address)입니다. CPU는 "1000번 사물함에 있는 값을 가져와라", "1004번 사물함에 이 값을 넣어라"처럼 오직 번호로만 메모리를 다룹니다. CPU는 변수 이름을 전혀 모릅니다.

그렇다면 우리가 코드에 쓰는 변수 이름 a, balance는 무엇일까요? 변수 이름은 사람을 위한 별명입니다. 컴파일러가 소스 코드를 기계어로 바꾸면서 "a는 1000번부터 4칸", "balance는 1008번부터 8칸"처럼 이름을 주소로 바꿔 줍니다. 즉, 변수를 선언한다는 것은 "자료형 크기만큼의 사물함을 빌리고, 그 첫 번째 사물함에 이름표를 붙이는 일"입니다.

그림 9-1에서 중요한 사실 세 가지를 꼭 기억하세요.

  1. 주소는 바이트마다 붙습니다. 그래서 4바이트짜리 int a는 1000, 1001, 1002, 1003 네 개의 주소를 차지합니다.
  2. 변수의 주소는 첫 바이트의 주소입니다. a의 주소는 1000입니다. 1001~1003은 "a의 일부"이지 a의 주소가 아닙니다.
  3. 변수 사이에 빈칸이 생길 수 있습니다. CPU는 8바이트 값을 8의 배수 주소에서 읽을 때 가장 빠르기 때문에 컴파일러가 일부러 칸을 비워 둡니다. 이를 정렬(alignment)이라 하며, 구조체 장에서 "패딩"으로 다시 만납니다. 그러므로 변수들이 선언 순서대로 붙어 있을 것이라고 가정하면 안 됩니다.

왜 주소를 1바이트 단위로 붙일까?

문자 하나(char)가 1바이트이기 때문입니다. 만약 4바이트마다 주소를 붙인다면 문자열의 세 번째 글자처럼 1바이트짜리 데이터를 하나만 가리킬 방법이 없어집니다. 그래서 오늘날 거의 모든 범용 CPU는 바이트 주소 지정(byte addressing) 방식을 씁니다. C 표준도 char의 크기를 1로 정의하고, 모든 객체의 크기를 char의 배수로 잽니다.

또 하나, 우리가 프로그램에서 보는 주소는 RAM의 실제 물리 주소가 아니라 운영체제가 프로세스마다 따로 만들어 주는 가상 주소(virtual address)입니다. 그래서 두 프로그램이 똑같이 0x7ffd1000이라는 주소를 써도 서로 다른 실제 메모리를 가리키며, 서로의 데이터를 망가뜨리지 못합니다. 이 구조 덕분에 은행 서버에서 한 업무 프로세스가 죽어도 다른 프로세스의 메모리는 안전합니다.

주소 연산자 & — 변수의 주소 알아내기

변수 이름 앞에 &를 붙이면 그 변수의 주소를 얻습니다. 이 연산자를 주소 연산자(address-of operator)라고 합니다. 이미 scanf("%d", &a);에서 써 본 바로 그 기호입니다. 주소를 출력할 때는 변환 명세 %p를 사용하고, 인자는 void *로 형변환해서 넘기는 것이 표준에 맞는 방법입니다.

왜 실행할 때마다 주소가 바뀔까?

리눅스·윈도우·macOS 같은 현대 운영체제는 ASLR(Address Space Layout Randomization, 주소 공간 배치 무작위화)를 사용합니다. 프로그램을 실행할 때마다 스택, 힙, 라이브러리의 시작 위치를 무작위로 옮겨 놓는 보안 기법입니다. 해커가 "이 프로그램의 버퍼는 항상 0x7ffc1234에 있다"는 사실을 이용해 공격 코드를 심는 것을 어렵게 만듭니다. 그래서 여러분의 출력은 위 결과와 숫자가 다른 것이 정상입니다. 중요한 것은 주소 값 자체가 아니라 주소 사이의 관계(몇 바이트 떨어져 있는가)입니다.

또 0x7ffc...처럼 매우 큰 값으로 시작하는 이유는 지역 변수가 스택 영역에 있고, 64비트 리눅스에서 스택은 사용자 주소 공간의 가장 높은 쪽에 배치되기 때문입니다.

자주 하는 실수 — 주소를 %d나 %x로 출력하기

printf("%d", &a);는 64비트 시스템에서 8바이트 주소를 4바이트 정수 자리로 읽으라고 지시하는 셈이므로 미정의 동작(UB)입니다. 실제로 앞 4바이트만 잘려서 엉뚱한 음수가 찍히는 경우가 흔합니다. 주소는 반드시 %p로, 인자는 (void *)로 형변환해서 넘기세요. gcc에서 -Wall을 켜면 "format '%d' expects argument of type 'int', but argument 2 has type 'int *'" 경고가 나옵니다.

왜 scanf에는 &가 필요했는지도 이제 설명할 수 있습니다. scanf는 키보드로 입력받은 값을 여러분의 변수에 써 넣어야 하는 함수입니다. 그런데 C의 함수는 인자를 언제나 복사해서 받습니다(값에 의한 전달). scanf("%d", a)라고 쓰면 a에 들어 있던 쓰레기 값의 복사본이 넘어갈 뿐이라 scanf는 a가 어디 있는지 알 길이 없습니다. 그래서 "여기에 써 주세요"라는 의미로 주소를 넘기는 것입니다. 이 원리는 09-2의 swap 함수에서 그림으로 다시 확인합니다.

포인터 변수의 선언과 대입

주소도 결국 하나의 값(정수처럼 생긴 수)입니다. 값이면 변수에 저장할 수 있겠지요? 주소를 저장하는 변수가 포인터 변수입니다. 선언할 때는 "어떤 자료형의 주소를 저장하는가"를 함께 밝히고, 변수 이름 앞에 *를 붙입니다.

int *pi;는 "pi는 int를 가리키는(pointer to int) 변수"라고 읽습니다. 자료형은 int *입니다. 이제 실제로 주소를 저장해 봅시다.

그림 9-2를 보면 포인터가 신비한 존재가 아니라는 것을 알 수 있습니다. pa는 그냥 8바이트짜리 변수이고, 그 안에 0x...2a4c라는 수가 들어 있을 뿐입니다. 그 수가 마침 a의 주소이므로 우리는 "pa가 a를 가리킨다(point to)"고 말하고, 그림에서는 화살표로 그립니다.

자주 하는 실수 — 한 줄에 포인터 여러 개 선언하기

*는 자료형 쪽이 아니라 변수 이름 쪽에 붙는 선언자입니다. 위 코드는 int *p1; int p2;와 같습니다. 그래서 p2 = &a;를 쓰면 "int에 포인터를 대입한다"는 경고가 납니다.

int *p 와 int* p, 무엇이 맞나요?

둘 다 문법적으로 같습니다. 공백은 의미가 없습니다. 다만 C 커뮤니티에서는 위의 실수를 피하려고 int *p처럼 별표를 이름 쪽에 붙이는 스타일을 더 많이 씁니다. C++ 쪽에서는 "p의 자료형은 int*"라는 점을 강조해 int* p를 선호하기도 합니다. 팀의 코딩 표준을 따르면 됩니다.

포인터에는 같은 자료형 변수의 주소를 넣어야 합니다. double d; int *p = &d;는 자료형이 맞지 않으므로 컴파일러가 "incompatible pointer type" 경고를 냅니다. 왜 자료형이 맞아야 하는지는 09-2에서 자세히 다룹니다.

간접 참조 연산자 * — 주소를 따라가서 값 다루기

포인터의 진짜 힘은 주소를 "따라가는" 데 있습니다. 포인터 변수 앞에 *를 붙이면 "그 포인터가 가리키는 곳에 있는 변수"를 뜻합니다. 이를 간접 참조(indirection) 또는 역참조(dereference)라고 합니다. pa가 a를 가리키고 있다면 *pa는 a 그 자체입니다. 읽을 수도 있고, 쓸 수도 있습니다.

*pa = 20 이 실행될 때 CPU 안에서 일어나는 일

  1. CPU는 먼저 변수 pa가 있는 곳(0x...2a50)에서 8바이트를 읽어 옵니다. 읽은 값은 0x...2a4c입니다.
  2. 그 값을 주소로 사용하여 0x...2a4c 위치로 갑니다.
  3. pa의 자료형이 int *이므로 "그곳에 4바이트 int가 있다"고 판단하고, 4바이트에 20을 씁니다.

즉, a = 20은 메모리 접근 1번이지만 *pa = 20은 "포인터 읽기 + 그 주소에 쓰기" 2번입니다. 그래서 "간접(indirect)" 참조라고 부릅니다. 어셈블리로 보면 mov rax, [rbp-16](pa 읽기) → mov DWORD PTR [rax], 20(그 주소에 쓰기)처럼 두 단계로 나타납니다.

자주 하는 실수 — *p++ 와 (*p)++

후위 ++는 간접 참조 *보다 우선순위가 높습니다. 그래서 *p++는 *(p++)로 해석되어 "p가 가리키는 값을 읽고, 포인터 p를 다음 칸으로 옮긴다"는 뜻이 됩니다. 값을 1 늘리려면 반드시 (*p)++라고 써야 합니다. 반면 전위 ++*p는 오른쪽에서 왼쪽으로 결합하므로 ++(*p)가 되어 값이 증가합니다. 헷갈리면 괄호를 쓰는 것이 정답입니다.

&와 *는 서로 반대 작업을 합니다. &는 "변수 → 주소", *는 "주소 → 변수"입니다. 그러므로 *&a는 a와 같고, &*pa는 pa와 같습니다.

char는 1바이트, double은 8바이트입니다. 그렇다면 char *와 double *의 크기는 다를까요? 직접 확인해 봅시다.

가리키는 대상의 크기와 포인터의 크기는 왜 무관할까?

포인터에 저장되는 것은 주소 하나입니다. 1바이트짜리 문자의 주소든 1,000바이트짜리 원장 레코드의 주소든, 주소는 "몇 번 사물함인가"라는 번호 하나일 뿐입니다. 사물함 번호표의 크기는 사물함 안의 물건 크기와 상관없지요. 주소를 몇 바이트로 표현할지는 CPU와 운영체제가 사용하는 주소 공간의 크기로 정해집니다.

  • 32비트 시스템: 주소가 32비트 = 4바이트 → 최대 232 = 약 4GB의 주소를 표현할 수 있습니다. 그래서 32비트 윈도우는 메모리를 4GB 이상 활용하기 어려웠습니다.
  • 64비트 시스템: 주소가 64비트 = 8바이트 → 이론상 16EB(엑사바이트). 실제 x86-64 CPU는 그중 48비트(256TB) 또는 57비트만 사용하지만, 포인터 변수 자체는 8바이트입니다.

참고로 C 표준은 "모든 포인터 형의 크기가 같아야 한다"고 보장하지는 않습니다(과거 특수 아키텍처에는 다른 경우가 있었습니다). 하지만 오늘날 일반적인 리눅스·윈도우 64비트 환경에서는 모든 데이터 포인터가 8바이트입니다.

국내 은행·증권사의 계정계는 오랫동안 유닉스(AIX, HP-UX, Solaris) 위에서 C로 작성된 업무 프로그램을 돌려 왔고, 상당수가 32비트 시절 코드입니다. 이런 코드를 64비트 리눅스로 이관(차세대 프로젝트)할 때 가장 흔히 터지는 버그가 바로 "포인터는 4바이트, long도 4바이트"라고 가정한 코드입니다. 예를 들어 주소를 int 변수에 잠시 담았다가 다시 포인터로 바꾸는 코드는 32비트에서는 멀쩡하지만 64비트에서는 주소 상위 4바이트가 잘려 엉뚱한 메모리를 건드리고 장애를 일으킵니다. 그래서 차세대 이관 점검 목록에는 반드시 "포인터를 정수형에 저장하는 코드 금지(필요하면 intptr_t 사용)", "sizeof(long) 의존 금지" 항목이 들어갑니다.

NULL 포인터 — 아무것도 가리키지 않는다는 약속

지역 변수는 초기화하지 않으면 쓰레기 값을 가집니다. 포인터도 마찬가지입니다. 초기화하지 않은 포인터에는 정체를 알 수 없는 주소가 들어 있고, 그 주소를 따라가서 값을 쓰면 무슨 일이 벌어질지 아무도 모릅니다. 그래서 "아직 가리킬 대상이 없다"는 것을 명시적으로 표시하는 특별한 값이 필요한데, 그것이 널 포인터(null pointer)이고, 매크로 이름이 NULL입니다(<stdio.h>, <stddef.h>, <stdlib.h> 등에 정의).

NULL을 역참조하면 왜 프로그램이 죽을까(Segmentation fault)?

표준상 널 포인터 역참조는 미정의 동작입니다. 하지만 실제 리눅스·윈도우에서는 거의 항상 즉시 죽습니다. 그 이유는 운영체제가 가상 주소 공간의 가장 아래쪽(0번지 근처 수 KB~수십 KB)을 어떤 물리 메모리에도 연결(매핑)하지 않기 때문입니다. CPU의 MMU(메모리 관리 장치)가 주소 0을 변환하려다 페이지 테이블에 항목이 없음을 발견하면 "페이지 폴트" 예외를 일으키고, 운영체제는 이것이 잘못된 접근임을 확인한 뒤 프로세스에 SIGSEGV 신호를 보내 종료시킵니다. 이것이 "Segmentation fault (core dumped)" 메시지의 정체입니다.

일부러 죽게 만드는 이유는 간단합니다. 잘못된 포인터로 조용히 엉뚱한 메모리를 고치는 것보다, 즉시 크게 실패하는 편이 훨씬 안전하기 때문입니다. 잔액이 조용히 틀어지는 것보다 프로그램이 멈추고 로그가 남는 편이 은행에는 훨씬 낫습니다.

NULL, 0, '\0', NUL은 같은 것인가요?

  • NULL: 널 포인터 상수를 나타내는 매크로. 보통 ((void *)0) 또는 0으로 정의됩니다. 포인터 문맥에서 사용합니다.
  • 0: 정수 0. 포인터 문맥에 쓰면 컴파일러가 널 포인터로 바꿔 줍니다. 그래서 if (p == 0), if (!p)도 올바른 검사입니다.
  • '\0': 값이 0인 문자. 문자열의 끝 표시(널 문자)입니다. 자료형은 int(C에서 문자 상수는 int)입니다.
  • NUL: ASCII 코드표에서 0번 문자의 이름. '\0'과 같은 것을 가리킵니다.

값은 모두 0과 관련 있지만 의도가 다르므로, 포인터에는 NULL, 문자에는 '\0'을 쓰는 것이 읽기 좋은 코드입니다. C23부터는 C++처럼 nullptr도 도입되었습니다.

포인터 안전 수칙 3가지

  1. 선언과 동시에 초기화: 가리킬 대상이 있으면 그 주소로, 없으면 NULL로.
  2. 역참조 전에 NULL 검사: 특히 함수가 외부에서 포인터를 받을 때.
  3. 다 쓴 포인터는 NULL로: 가리키던 대상이 사라지면(동적 메모리 해제 등) 즉시 p = NULL;로 바꿔 댕글링 포인터를 막습니다(09-2에서 자세히).

은행 시스템에서는 — 큰 레코드는 주소로 넘긴다

계정계의 계좌 원장 레코드는 계좌번호, 고객번호, 상품코드, 잔액, 이자 기산일, 최종 거래일시, 상태 코드 등 수십~수백 개 필드로 이루어져 보통 수백 바이트~수 KB입니다. 하루 수백만 건의 거래를 처리하는 온라인 업무에서 함수를 부를 때마다 이 레코드를 통째로 복사한다면 CPU와 메모리 대역폭이 낭비됩니다. 그래서 C로 작성된 업무 모듈은 거의 예외 없이 레코드의 주소(포인터)를 넘깁니다. 8바이트 주소 하나만 복사하면 되고, 호출된 함수가 수정한 내용이 원본에 바로 반영되기 때문입니다. 조회만 하는 함수에는 const를 붙여 "수정하지 않겠다"는 약속을 컴파일러가 강제하게 합니다(09-2-3).

09-2포인터 완전 정복을 위한 포인터 이해하기

09-1에서 포인터의 문법을 익혔다면, 이제는 포인터를 "제대로" 쓰기 위한 원리를 살펴볼 차례입니다. 포인터에 자료형이 붙는 이유, 포인터에 1을 더하면 주소가 4나 8씩 늘어나는 이유, const의 위치에 따라 의미가 달라지는 이유, 그리고 함수에 포인터를 넘겨야만 하는 이유를 하나씩 따져 봅니다. 이 절을 이해하면 10장(배열과 포인터)과 12장(문자열)이 훨씬 쉬워집니다.

포인터에 자료형이 왜 필요한가

포인터는 주소만 저장한다고 했습니다. 주소는 모두 8바이트로 크기도 같습니다. 그렇다면 그냥 "주소형" 하나만 있으면 될 텐데, 왜 굳이 int *, double *처럼 가리키는 대상의 자료형을 밝혀야 할까요?

답은 주소는 시작점만 알려 줄 뿐이라는 데 있습니다. "1000번 사물함부터"라는 정보만으로는 몇 칸을 읽어야 하는지, 읽은 비트를 정수로 해석할지 실수로 해석할지 알 수 없습니다. 포인터의 자료형이 바로 그 정보를 제공합니다.

  1. 몇 바이트를 읽고 쓸 것인가: char *면 1바이트, int *면 4바이트, double *면 8바이트.
  2. 읽은 비트를 어떻게 해석할 것인가: 같은 32비트라도 int는 2의 보수 정수로, float는 IEEE 754 부동소수점으로 해석합니다.
  3. 포인터 연산 시 몇 바이트씩 이동할 것인가: 다음 소절에서 다룹니다.

같은 주소를 서로 다른 자료형의 포인터로 읽어 보면 차이가 확실히 보입니다. 어떤 객체든 unsigned char *로 바이트 단위 접근을 하는 것은 표준이 허용하는 방법이므로 안전하게 실험할 수 있습니다.

왜 78이 맨 앞에 저장될까? — 엔디안(Endianness)

여러 바이트로 이루어진 값을 메모리에 놓는 순서를 엔디안이라고 합니다.

  • 리틀 엔디안(little endian): 낮은 자리 바이트(0x78)를 낮은 주소에 둡니다. 인텔·AMD x86, 대부분의 ARM이 이 방식입니다. 덧셈이 낮은 자리부터 진행되므로 하드웨어 설계가 단순해지는 장점이 있습니다.
  • 빅 엔디안(big endian): 높은 자리 바이트(0x12)를 낮은 주소에 둡니다. 사람이 읽는 순서와 같습니다. IBM 메인프레임, 과거 SPARC·PowerPC(AIX) 등이 이 방식이고, 네트워크 바이트 순서도 빅 엔디안입니다.

포인터의 자료형이 없다면 CPU는 1000번지에서 몇 바이트를 읽을지조차 모릅니다. int *라는 정보가 있기에 컴파일러는 "4바이트를 읽는 명령"(mov eax, DWORD PTR [rax])을, unsigned char *이면 "1바이트를 읽는 명령"(movzx eax, BYTE PTR [rax])을 생성합니다.

은행 시스템에서는 — 대외 전문과 엔디안

은행은 금융공동망, 카드사, 증권사 등 대외기관과 정해진 형식의 전문(電文, message)을 주고받습니다. 금액이나 길이 필드를 2진 정수로 보내는 전문에서는 반드시 "빅 엔디안(네트워크 바이트 순서)으로 보낸다" 같은 규약이 있습니다. 리틀 엔디안 리눅스 서버가 int 메모리를 그대로 소켓에 쓰면 상대 시스템은 1,000원(0x000003E8)을 0xE8030000, 즉 약 39억 원으로 읽게 됩니다. 그래서 전문 처리 모듈은 htonl()/ntohl()로 바이트 순서를 변환하거나, 아예 금액을 "000000001000"처럼 고정 길이 숫자 문자열로 보내 엔디안 문제를 원천 차단합니다. 국내 대외 전문 상당수가 숫자를 문자열로 주고받는 데에는 이런 이유가 있습니다.

자주 하는 실수 — 다른 자료형 포인터로 억지로 읽기

double d = 1.5; int *p = (int *)&d; printf("%d", *p);처럼 형변환으로 컴파일러 경고를 꺼 버리고 다른 자료형으로 읽는 코드는 엄격한 별칭 규칙(strict aliasing rule) 위반으로 미정의 동작입니다. 최적화(-O2)를 켜면 컴파일러가 "int 포인터와 double 포인터는 같은 곳을 가리킬 리 없다"고 가정하고 코드를 재배치하여 예상과 다른 결과를 낼 수 있습니다. 바이트를 들여다보고 싶다면 unsigned char *를 쓰고, 비트를 다른 형으로 옮기고 싶다면 memcpy를 쓰는 것이 올바른 방법입니다.

포인터 연산 — p + 1은 왜 1바이트 뒤가 아닐까

포인터에는 정수를 더하거나 뺄 수 있습니다. 그런데 결과가 조금 독특합니다. int *p에 1을 더하면 주소가 1이 아니라 4 늘어납니다. double *이면 8, char *이면 1 늘어납니다. 규칙은 다음 한 줄로 정리됩니다.

포인터 연산 규칙

p + n의 실제 주소 = p의 주소 + n × sizeof(*p)

즉, 포인터 연산의 단위는 바이트가 아니라 "가리키는 자료형 한 개"입니다. p + 1은 "다음 int", "다음 double"을 뜻합니다.

왜 이렇게 설계했을까?

포인터 연산은 배열을 순회하기 위해 존재합니다. 배열은 같은 자료형의 요소가 빈틈없이 연속으로 놓인 것이므로, "다음 요소"는 항상 sizeof(요소)바이트 뒤에 있습니다. 만약 p+1이 1바이트 뒤라면 프로그래머가 매번 p + i * sizeof(int)처럼 계산해야 하고, 자료형을 바꿀 때마다 코드를 고쳐야 합니다. C는 이 곱셈을 컴파일러에게 맡겨서, 같은 코드 p + i가 어떤 자료형에서도 "i번째 요소"를 뜻하도록 만들었습니다. 이것이 10장에서 배울 arr[i] == *(arr + i)의 근거입니다.

포인터로 할 수 있는 연산과 할 수 없는 연산을 정리하면 다음과 같습니다.

연산가능 여부의미 / 결과 자료형
p + n, p - n, p++, p--, p += n가능n개 요소만큼 앞/뒤를 가리키는 포인터
p2 - p1 (같은 배열 안)가능두 포인터 사이의 요소 개수, 자료형 ptrdiff_t(<stddef.h>), 출력은 %td
p1 == p2, p1 < p2 등 비교가능같은 배열 안에서 위치의 앞뒤 비교. ==, !=는 아무 포인터끼리도 가능

자주 하는 실수 — 배열 범위 밖으로 나가는 포인터

포인터 연산은 같은 배열 안에서만 의미가 있습니다. 표준은 배열 요소들과 "마지막 요소 바로 다음(one past the end)" 위치까지만 포인터 계산을 허용합니다. 위 예제에서 first + 5를 계산하고 비교하는 것은 허용되지만, 역참조하면 UB입니다. first - 1이나 first + 6은 계산하는 것만으로도 UB입니다. 서로 다른 배열의 포인터를 빼거나 <로 비교하는 것도 UB입니다. 그래서 반복문은 흔히 for (p = amt; p < amt + 5; p++)처럼 "끝 다음 위치"와 <로 비교하는 관용구를 씁니다.

  1. rates[1]의 주소 = 2000 + 1×8 = 2008
  2. p + 2 = 2008 + 2×sizeof(double) = 2008 + 16 = 2024 (rates[3]의 주소)
  3. *(p + 2) = rates[3] = 3.0
  4. *p + 2: 간접 참조가 덧셈보다 우선순위가 높으므로 (*p) + 2 = 2.0 + 2 = 4.0. 괄호 위치 하나로 의미가 완전히 달라집니다.
  5. &rates[3] - p = (2024 − 2008) / 8 = 2 (요소 개수)

const와 포인터 — 4가지 조합

포인터에는 "보호할 것"이 두 가지 있습니다. ① 포인터가 가리키는 대상의 값, ② 포인터 자신의 값(어디를 가리키는가). const를 어디에 붙이느냐에 따라 보호 대상이 달라집니다.

헷갈리지 않는 읽기 비법 — 오른쪽에서 왼쪽으로

선언을 변수 이름부터 오른쪽에서 왼쪽으로 읽고, *는 "~를 가리키는 포인터"로 읽습니다.

  • const int *p → "p는 / 포인터인데 / int를 가리키고 / 그 int는 const" → 대상이 상수.
  • int *const p → "p는 / const인 / 포인터인데 / int를 가리킴" → 포인터 자신이 상수.

더 간단한 규칙: const가 *의 왼쪽에 있으면 대상 보호, 오른쪽에 있으면 포인터 보호입니다.

const int *p는 "대상이 상수"가 아니라 "p를 통해서는 수정 불가"

위 예제 마지막에서 a = 12;가 잘 되는 것을 보세요. const int *p1은 a를 진짜 상수로 만드는 것이 아니라, p1이라는 통로로는 수정하지 않겠다는 약속입니다. 그래서 "읽기 전용 뷰(read-only view)"라고 이해하는 것이 정확합니다. 이 약속은 컴파일 시점에 검사되므로 실행 비용이 전혀 없습니다.

반대로, 진짜 const int c = 5;로 선언된 변수의 주소를 형변환으로 int *에 넣어 수정하는 것은 UB입니다. 컴파일러가 c를 읽기 전용 메모리에 두었거나, c를 쓰는 곳에 5를 직접 박아 넣었을 수 있기 때문입니다.

실무에서 가장 많이 쓰는 것은 두 번째, 함수 매개변수의 const T *입니다. "이 함수는 넘겨받은 데이터를 읽기만 한다"는 사실을 함수 원형에 새겨 두는 것입니다. 표준 라이브러리 size_t strlen(const char *s);도 같은 이유로 const가 붙어 있습니다.

  4. 가능. x 자체는 const가 아니므로 직접 수정됩니다. d를 통해서만 수정이 막힙니다.

포인터로 두 변수를 swap 하는 이유

두 변수의 값을 맞바꾸는(swap) 함수를 만들어 봅시다. 포인터를 배우기 전의 지식으로는 다음처럼 작성하게 됩니다.

함수 안에서는 분명히 바뀌었는데, main으로 돌아오면 그대로입니다. 이 현상을 이해하는 것이 포인터를 이해하는 핵심입니다.

왜 바뀌지 않을까? — C의 모든 인자 전달은 "값 복사"

함수를 호출하면 운영체제가 마련해 준 스택 영역에 그 함수만의 공간(스택 프레임)이 새로 생깁니다. 매개변수 x, y는 이 새 공간에 만들어진 별개의 변수이고, 호출 순간 a, b의 값이 복사되어 들어갑니다. 함수 안에서 바꾼 것은 복사본일 뿐이며, 함수가 return 하면 스택 프레임 전체가 사라집니다. main의 a, b는 다른 주소에 있으므로 영향이 없습니다.

이것은 버그가 아니라 의도된 안전장치입니다. 함수가 호출한 쪽의 변수를 마음대로 바꿀 수 없으니, 함수를 블랙박스처럼 믿고 쓸 수 있습니다. 그렇다면 "정말로 바꾸고 싶을 때"는? 바꿀 변수의 위치(주소)를 알려 주면 됩니다.

C에는 "참조에 의한 전달"이 없다

엄밀히 말해 C의 함수 호출은 오직 값에 의한 전달(call by value)뿐입니다. swap_ptr(&a, &b)에서도 복사되는 것은 주소값(1000, 1004)입니다. 다만 그 복사된 주소를 따라가면 원본에 닿기 때문에 "참조에 의한 전달처럼" 동작합니다. 이를 흔히 call by address 또는 "포인터를 이용한 참조 전달 흉내"라고 부릅니다. C++의 참조자(int &x)나 Java·C#의 ref 같은 진짜 참조 전달은 C에 없습니다. 면접에서 자주 묻는 함정 질문이니 꼭 정확히 말할 수 있어야 합니다.

자주 하는 실수 — 포인터 자체를 바꾸는 swap

pa, pb도 결국 복사본입니다. 복사본끼리 주소를 바꿔 봐야 main의 a, b는 그대로입니다. 값을 바꾸려면 반드시 *pa, *pb처럼 간접 참조로 대상에 써야 합니다. (만약 main의 포인터 변수 자체를 바꾸고 싶다면 그 포인터의 주소, 즉 이중 포인터 int **를 넘겨야 합니다. 이는 이후 장에서 다룹니다.)

예제 9-6 난이도 ★★☆

세 정수의 주소를 받아 값을 오름차순으로 정렬해 주는 함수 void sort3(int *a, int *b, int *c)를 작성하세요. 앞에서 만든 swap_ptr를 재사용합니다. 입력 9, 1, 5 → 출력 1 5 9.

정답과 해설 보기

세 개를 정렬하려면 비교·교환을 세 번 하면 됩니다. (a,b) 비교 후 교환 → (b,c) 비교 후 교환하면 가장 큰 값이 c로 갑니다 → 다시 (a,b) 비교 후 교환하면 a ≤ b ≤ c가 됩니다. 이미 포인터를 받았으므로 swap_ptr에는 & 없이 그대로 넘깁니다(a 자체가 주소이므로).

추적: (9,1,5) → a>b 교환 (1,9,5) → b>c 교환 (1,5,9) → a>b? 1>5 아님 → (1,5,9).

포인터를 쓰는 또 다른 이유 — 여러 개의 결과 돌려주기

C 함수의 return은 값을 하나만 돌려줄 수 있습니다. 그런데 이자를 계산하는 함수라면 "세전 이자"와 "원천징수 세액"을 함께 알려 주고 싶습니다. 이때 결과를 담을 변수의 주소를 받아서 함수가 직접 써 넣는 방식을 씁니다. 이런 매개변수를 출력 매개변수(output parameter)라고 부릅니다. scanf가 바로 이 방식입니다.

왜 반환값은 상태 코드, 결과는 포인터로?

함수가 실패할 수도 있다면 "결과"와 "성공 여부"를 구분해서 알려야 합니다. 이자 0원이 정상 결과인지 오류인지 반환값 하나로는 구분할 수 없기 때문입니다. 그래서 C 업무 코드에서는 반환값 = 처리 결과 코드, 계산 결과 = 출력 매개변수라는 관례가 널리 쓰입니다. 표준 라이브러리 scanf(성공 개수 반환), strtol(끝 위치를 char **로 돌려줌)도 같은 생각으로 설계되었습니다.

또 금액 계산에 double을 쓰지 않고 정수(원 단위 long long)와 bp 단위 이율을 쓴 점도 눈여겨보세요. 부동소수점은 0.1을 정확히 표현하지 못해 1원 단위 오차가 생길 수 있으므로, 금융 계산은 정수 연산과 명시적인 절사·반올림 규칙으로 처리합니다. 단, 곱셈 결과가 long long 범위(약 9.2 × 1018)를 넘지 않는지 업무 한도로 확인해야 합니다.

댕글링 포인터와 와일드 포인터

포인터 버그는 C 프로그램 장애의 가장 큰 원인입니다. 그중 대표적인 두 가지를 확실히 알고 넘어갑시다.

구분와일드 포인터 (wild pointer)댕글링 포인터 (dangling pointer)
정의한 번도 초기화되지 않아 쓰레기 주소를 가진 포인터한때 올바른 대상을 가리켰지만, 그 대상이 사라진 뒤에도 옛 주소를 들고 있는 포인터
대표 원인int *p; 후 바로 *p = 1;지역 변수의 주소 반환, free 후 계속 사용, 블록이 끝난 변수의 주소 보관

왜 죽거나 엉뚱한 값이 나올까?

make_fee가 return 하는 순간 그 스택 프레임은 "비어 있음"으로 표시되고, 다음 함수 호출(other_work)이 같은 스택 자리를 재사용합니다. pfee는 여전히 그 자리를 가리키므로 500이 아니라 other_work가 남긴 값이 읽힐 수 있습니다. 더구나 최신 gcc는 지역 변수 주소를 반환하는 코드를 발견하면 아예 NULL을 반환하도록 바꿔 버리기도 하므로 즉시 segfault가 나기도 합니다. 어느 쪽이든 결과를 예측할 수 없는 UB입니다. 가장 위험한 경우는 우연히 500이 그대로 남아 있어 "테스트에서는 잘 되는" 경우입니다. 운영 환경에서 부하가 걸릴 때만 수수료가 엉뚱하게 계산되는 최악의 장애가 됩니다.

이렇게 해결합니다

  1. 값으로 반환: 작은 값이면 long long make_fee(void) { return 500; }처럼 값 자체를 반환합니다. 가장 간단하고 안전합니다.
  2. 호출자가 공간을 마련: void make_fee(long long *out) { *out = 500; }처럼 결과를 담을 변수를 호출한 쪽이 소유하게 합니다. 수명 문제가 원천적으로 사라집니다(앞의 calc_interest 방식).
  3. 정적·동적 메모리 사용: static 지역 변수(13장)나 malloc(동적 메모리 장)으로 수명이 함수보다 긴 공간을 씁니다. 단, static은 다중 스레드에서 공유되는 문제가 있고, malloc은 해제 책임이 생깁니다.
  4. 컴파일러 경고를 오류로: gcc -Wall -Werror로 빌드하면 "returns address of local variable" 경고가 빌드 실패로 바뀌어 운영 반영 전에 걸러집니다. 정적 분석 도구(금융권에서 의무화된 소스코드 보안 약점 진단 도구 등)도 이 패턴을 잡아냅니다.

와일드 포인터가 무서운 이유는 "운이 좋으면 죽고, 운이 나쁘면 산다"는 데 있습니다. 쓰레기 주소가 마침 매핑되지 않은 곳이면 즉시 segfault로 끝나지만, 다른 변수가 있는 곳이면 그 변수를 조용히 덮어써서 전혀 관계없는 곳에서 이상 증상이 나타납니다. 원인과 증상이 멀리 떨어져 있어 디버깅이 가장 어려운 유형입니다. 해결책은 단 하나, 모든 포인터를 선언과 동시에 초기화하는 것입니다.

포인터 버그를 잡는 도구

  • gcc -Wall -Wextra: 초기화되지 않은 사용, 지역 변수 주소 반환 등을 경고합니다.
  • gcc -fsanitize=address -g (AddressSanitizer): 실행 중 범위 밖 접근, 해제 후 사용, 스택 범위를 벗어난 사용을 잡아 정확한 줄 번호와 함께 보고합니다.
  • valgrind ./a.out: 리눅스에서 메모리 오류와 누수를 찾는 고전 도구입니다.

다음 코드에서 댕글링 포인터가 생기는 지점을 찾고, 고치는 방법을 두 가지 제시하세요.

정답과 해설 보기

limit는 중괄호 블록 안에서 선언된 자동 변수이므로 블록이 끝나는 }에서 수명이 끝납니다. 그 뒤 *p로 읽는 것은 수명이 끝난 객체에 접근하는 UB입니다. 함수가 끝날 때만 댕글링 포인터가 생기는 것이 아니라 블록이 끝날 때도 생긴다는 점이 함정입니다(실제 스택 공간은 남아 있어 3000000이 찍힐 수도 있지만, 그것이 더 위험합니다).

해결 ① limit을 블록 밖(포인터와 같은 수명 범위)으로 옮깁니다. ② 주소가 아니라 값을 복사해 둡니다: int saved = limit;. 블록 안에서만 쓸 값이라면 블록 안에서 출력까지 끝내는 것도 방법입니다.

금융 예제 — 잔액을 함수로 수정하기

왜 이렇게 설계했을까?

  • from == to 비교: 두 포인터가 같은 주소이면 같은 계좌입니다. 이 검사가 없으면 *from -= amount; *to += amount;가 같은 변수에 대해 실행되어 결과적으로 잔액은 그대로인데 거래 로그에는 이체가 기록되는 이상한 상황이 생깁니다. 포인터 비교는 "같은 대상인가?"를 묻는 가장 정확한 방법입니다.
  • 검사 후 반영: 만약 withdraw를 먼저 호출해 A에서 돈을 빼고, 그다음 B의 포인터가 NULL이라 실패한다면 돈이 허공으로 사라집니다. 모든 검사를 먼저 끝내고, 실패할 일이 없는 대입 두 줄만 남겨 두는 구조는 데이터베이스의 트랜잭션 원자성(Atomicity)을 흉내 낸 것입니다.
  • 잔액 부족 시 아무것도 바꾸지 않음: 실패한 함수는 상태를 건드리지 않아야 호출한 쪽이 안심하고 재시도하거나 오류를 보고할 수 있습니다.

은행 시스템에서는 — 결과 코드와 원장 갱신

실제 계정계에서는 잔액이 C 변수 하나가 아니라 데이터베이스의 원장 테이블에 있고, 업무 프로그램은 레코드를 메모리 구조체로 읽어 와(SELECT ... FOR UPDATE로 잠금) 포인터로 넘기며 검증한 뒤 UPDATE하고 COMMIT합니다. 이때 함수 설계 원칙은 위 예제와 똑같습니다. ① 모든 함수는 응답 코드(예: "0000" 정상, "E102" 잔액 부족)를 돌려주고, ② 검증이 끝나기 전에는 원장을 바꾸지 않으며, ③ 하나라도 실패하면 ROLLBACK합니다. 또 이체에서 두 계좌를 잠글 때는 항상 계좌번호가 작은 쪽부터 잠그는 규칙을 둡니다. A→B 이체와 B→A 이체가 동시에 들어와 서로 상대 계좌의 잠금을 기다리는 교착 상태(deadlock)를 막기 위해서입니다. 포인터 비교로 "같은 계좌인가"를 걸러 내는 것과 같은 맥락의 방어 코드입니다.

앞으로 만날 포인터들 미리 보기

  • void *: 자료형 정보가 없는 "범용 주소". 어떤 객체 포인터든 담을 수 있지만, 크기 정보가 없으므로 그대로 역참조하거나 포인터 연산을 할 수 없습니다. malloc, memcpy, qsort가 이 형을 씁니다.
  • 이중 포인터 int **: 포인터 변수의 주소를 담는 포인터. 함수가 호출자의 포인터를 바꿔야 할 때 씁니다.
  • 함수 포인터: 함수의 주소를 담아 호출 대상을 실행 중에 바꿀 수 있습니다. 거래 코드별 처리 함수 테이블에 많이 쓰입니다.

모두 "주소를 값으로 저장한다"는 이 장의 원리에서 출발합니다.

핵심 정리

  • 메모리는 1바이트마다 주소가 붙은 칸의 나열이고, 변수의 주소는 그 변수가 차지한 첫 바이트의 주소입니다. 프로그램이 보는 주소는 가상 주소이며 ASLR 때문에 실행마다 달라집니다.
  • &변수는 주소를 얻고, *포인터는 주소를 따라가 대상 그 자체가 됩니다. 둘은 역연산입니다. 주소 출력은 %p와 (void *) 형변환으로 합니다.
  • 포인터는 주소를 저장하는 변수입니다. 크기는 가리키는 자료형과 무관하게 주소 공간 크기로 정해지며, 64비트에서 8바이트, 32비트에서 4바이트입니다.
  • 선언문의 *는 "포인터다"라는 표시이고, 실행문의 *는 간접 참조 연산자입니다. int *p1, p2;에서 p2는 int입니다.
  • 가리킬 대상이 없으면 NULL로 초기화하고, 역참조 전에 검사합니다. 널 포인터 역참조는 UB이며 실제로는 Segmentation fault가 납니다.
  • 포인터 자료형은 ① 읽고 쓸 바이트 수, ② 비트 해석 방법, ③ 포인터 연산의 이동 단위를 결정합니다.
  • p + n은 n × sizeof(*p)바이트 뒤를 가리킵니다. 같은 배열 안 포인터끼리의 뺄셈은 요소 개수(ptrdiff_t)이고, 포인터끼리 덧셈·곱셈은 불가입니다.
  • const가 * 왼쪽이면 대상 보호(const int *p), 오른쪽이면 포인터 보호(int *const p)입니다. 조회 함수의 매개변수에는 const T *를 씁니다.
  • C의 인자 전달은 오직 값 복사입니다. 호출한 쪽의 변수를 바꾸려면 그 주소를 값으로 넘기고 함수 안에서 간접 참조로 써야 합니다(swap, scanf, 출력 매개변수).
  • 와일드 포인터(초기화 안 됨)와 댕글링 포인터(수명이 끝난 대상)는 UB의 대표 원인입니다. 초기화, 값 반환/호출자 소유 공간, 해제 후 NULL, -Wall·AddressSanitizer로 예방합니다.
  • 금융 업무 함수는 "결과 코드 반환 + 포인터로 원장 수정 + 검증 완료 후 반영" 패턴으로 작성합니다.

Q1. 포인터란 무엇이고, 왜 사용하나요?

포인터는 메모리 주소를 값으로 저장하는 변수입니다. 사용하는 이유는 크게 세 가지입니다. 첫째, 함수가 호출자의 변수를 직접 수정하거나 여러 결과를 돌려줄 수 있습니다. 둘째, 큰 구조체나 배열을 복사하지 않고 8바이트 주소만 넘겨 성능을 높입니다. 셋째, 동적 메모리, 연결 리스트·트리 같은 자료구조, 하드웨어 레지스터 접근처럼 주소 없이는 불가능한 작업을 할 수 있습니다.

꼬리 질문 대비: "포인터의 단점은?" → 잘못 쓰면 댕글링·와일드 포인터, 버퍼 오버플로 같은 메모리 안전성 문제가 생기고, 이것이 Java·Rust 등이 포인터를 숨기거나 제한하는 이유라고 답합니다.

Q2. 64비트 시스템에서 char 포인터와 double 포인터의 크기는 각각 얼마인가요? 이유는?

둘 다 일반적으로 8바이트입니다. 포인터에는 대상 자체가 아니라 주소 하나가 저장되고, 주소의 크기는 가리키는 대상의 크기가 아니라 시스템의 주소 공간 폭으로 정해지기 때문입니다. 32비트 시스템이라면 4바이트입니다.

꼬리 질문: "그러면 포인터에 자료형은 왜 필요하죠?" → 역참조할 때 읽을 바이트 수와 해석 방법, 그리고 포인터 연산의 단위(p+1이 몇 바이트 이동인지)를 알려 주기 때문입니다.

Q3. C에서 call by value와 call by reference의 차이를 설명하고, swap 함수를 예로 들어 주세요.

값에 의한 전달은 인자의 복사본을 넘기므로 함수가 원본을 바꿀 수 없고, 참조에 의한 전달은 원본 자체에 대한 별칭을 넘겨 원본을 바꿀 수 있습니다. 엄밀히 C는 값에 의한 전달만 지원합니다. swap(a, b)로 값을 넘기면 복사본만 바뀌어 실패하고, swap(&a, &b)처럼 주소를 값으로 넘긴 뒤 함수 안에서 *pa, *pb로 간접 참조해야 원본이 바뀝니다. 이를 call by address라고 부르며, 참조 전달을 흉내 내는 방식입니다.

꼬리 질문: "C++의 참조자와 포인터의 차이는?" → 참조자는 반드시 초기화되어야 하고 재지정이 불가하며 NULL이 없고, 문법적으로 간접 참조 연산자가 필요 없다는 점을 답합니다.

Q4. 댕글링 포인터와 와일드 포인터의 차이는 무엇이며 어떻게 예방하나요?

와일드 포인터는 초기화되지 않아 임의의 주소를 담은 포인터이고, 댕글링 포인터는 원래 유효한 객체를 가리켰지만 그 객체의 수명이 끝난 뒤에도 옛 주소를 들고 있는 포인터입니다. 대표적으로 지역 변수의 주소를 반환하거나 free 후에 다시 사용하는 경우입니다. 예방법은 선언 시 반드시 초기화하기, 해제 직후 NULL 대입하기, 지역 변수 주소 반환 금지, 그리고 -Wall과 AddressSanitizer·Valgrind 같은 도구로 검증하는 것입니다.

Q5. NULL 포인터를 역참조하면 어떤 일이 일어나나요? 왜 그런가요?

C 표준상으로는 미정의 동작입니다. 실제 리눅스·윈도우에서는 운영체제가 가상 주소 0번지 근처 페이지를 매핑하지 않기 때문에, CPU의 MMU가 주소 변환에 실패해 페이지 폴트가 발생하고 운영체제가 프로세스에 SIGSEGV를 보내 Segmentation fault로 종료됩니다. 잘못된 포인터로 조용히 데이터를 망가뜨리는 것보다 즉시 실패하게 만든 설계입니다.

꼬리 질문: "NULL과 0과 '\0'의 차이는?" → 값은 모두 0과 관련 있지만 각각 널 포인터 상수 매크로, 정수 0, 값 0인 문자 상수(문자열 종료 표시)로 쓰임새가 다르다고 답합니다.

Q6. const int *p, int *const p, const int *const p의 차이를 설명하세요.

const int *p는 p를 통해 가리키는 값을 바꿀 수 없지만 p가 다른 주소를 가리키게 할 수는 있습니다. int *const p는 반대로 p 자신이 상수라 다른 곳을 가리킬 수 없지만 가리키는 값은 바꿀 수 있고, 선언 시 초기화해야 합니다. const int *const p는 둘 다 불가합니다. const가 * 왼쪽이면 대상, 오른쪽이면 포인터를 보호한다고 기억합니다. 실무에서는 읽기만 하는 함수 매개변수에 const T *를 붙여 의도를 드러내고 실수를 컴파일 단계에서 막습니다.

Q7. 리틀 엔디안과 빅 엔디안을 설명하고, 현재 시스템의 엔디안을 확인하는 코드를 말해 보세요.

여러 바이트 값을 메모리에 저장하는 순서입니다. 리틀 엔디안은 최하위 바이트를 가장 낮은 주소에, 빅 엔디안은 최상위 바이트를 가장 낮은 주소에 저장합니다. x86과 대부분의 ARM은 리틀 엔디안이고, 네트워크 바이트 순서는 빅 엔디안입니다. 확인은 int x = 1; unsigned char *p = (unsigned char *)&x; 후 *p == 1이면 리틀 엔디안이라고 판단합니다.

꼬리 질문: "네트워크 프로그래밍에서는 어떻게 처리하나요?" → htons/htonl/ntohs/ntohl로 변환하고, 전문 설계 시 숫자를 문자열로 보내기도 한다고 답합니다.

Q8. int *p가 0x1000을 가리킬 때 p + 1의 값은? char *, double *라면?

포인터 연산은 가리키는 자료형 크기 단위로 이루어지므로 int *이면 0x1004, char *이면 0x1001, double *이면 0x1008입니다. 같은 배열 안의 두 포인터를 빼면 바이트 차이가 아니라 요소 개수가 나오고, 결과형은 ptrdiff_t입니다. 포인터끼리 더하거나 곱하는 것은 의미가 없어 컴파일 오류입니다.

Q9. 함수에서 지역 변수의 주소를 반환하면 왜 안 되나요?

지역 변수는 함수의 스택 프레임에 있고, 함수가 반환되면 그 프레임은 해제되어 다음 함수 호출이 같은 공간을 재사용합니다. 따라서 반환된 주소는 수명이 끝난 객체를 가리키는 댕글링 포인터가 되고, 그 주소로 접근하는 것은 미정의 동작입니다. 값으로 반환하거나, 호출자가 공간을 마련해 포인터로 넘기거나, static 또는 동적 할당을 사용해야 합니다.

Q10. void 포인터는 무엇이며 왜 바로 역참조할 수 없나요?

void *는 가리키는 대상의 자료형 정보가 없는 범용 포인터로, 어떤 객체 포인터든 형변환 없이 담을 수 있습니다. 그러나 대상의 크기와 해석 방법을 모르기 때문에 역참조나 포인터 연산을 할 수 없고, 사용할 때 구체적인 자료형 포인터로 변환해야 합니다. malloc의 반환형, memcpy·qsort의 매개변수처럼 자료형에 무관한 일반 함수를 만들 때 사용합니다.

연습문제 9-12 개념 서술 난이도 ★★☆

"scanf("%d", &n)에서 &를 빼면 왜 안 되는가?"를 값에 의한 전달, 주소, 스택 프레임이라는 단어를 모두 사용해 5문장 이내로 설명하세요.

정답과 해설 보기

모범 답안: C의 함수 인자는 값에 의한 전달이므로, scanf에 n을 그대로 넘기면 n의 현재 값(쓰레기 값)의 복사본이 scanf의 스택 프레임에 전달될 뿐입니다. scanf는 그 복사본만 가지고는 main의 n이 메모리 어디에 있는지 알 수 없으므로 입력값을 n에 써 넣을 수 없습니다. 오히려 쓰레기 값을 주소로 착각해 그곳에 쓰려 하므로 미정의 동작(대개 segfault)이 됩니다. &n으로 주소를 넘기면 scanf는 그 주소를 따라가 main의 n에 직접 값을 저장할 수 있습니다.
