30-1디버깅 도구: gdb, core, Valgrind, ASan

C는 메모리를 직접 다루는 언어라서 버그의 증상이 원인과 멀리 떨어져 나타납니다. 함수 A에서 배열 범위를 1바이트 넘겨 쓴 것이 한참 뒤 함수 B에서 free할 때 프로그램을 죽이기도 합니다. 그래서 C 개발자는 "코드를 다시 읽어서 찾는" 방법만으로는 부족하고, 실행 중인(또는 죽은) 프로그램의 상태를 직접 들여다보는 도구가 필요합니다. 먼저 어떤 증상에 어떤 도구를 쓰는지 지도를 그려 봅시다.

디버깅용 컴파일: -g와 -O0

디버거가 "지금 fee.c 12번째 줄이고, 변수 amt는 50000"이라고 알려 주려면, 실행 파일 안에 기계어 주소와 소스 줄, 변수 이름과 위치의 대응표가 있어야 합니다. 이 정보를 디버그 정보(리눅스에서는 DWARF 형식)라고 하며, -g 옵션이 넣어 줍니다.

왜 디버깅할 때는 -O0을 쓸까?

최적화(-O2)를 켜면 컴파일러는 같은 결과를 더 빨리 내기 위해 코드를 크게 바꿉니다. 변수를 메모리 대신 레지스터에만 두거나 아예 없애고, 함수를 호출한 곳에 펼쳐 넣고(inline), 문장 순서를 바꾸고, 루프를 펼칩니다. 그 결과 gdb에서 print amt를 하면 "<optimized out>"이 나오고, next로 한 줄씩 진행하면 실행 위치가 위아래로 튀며, 브레이크포인트를 건 함수가 inline되어 멈추지 않기도 합니다. -O0은 소스 한 줄이 기계어 덩어리 하나에 정직하게 대응하고 모든 변수가 스택에 실제로 존재하므로 디버거가 보여 주는 것과 소스가 일치합니다. 다만 최적화를 켰을 때만 나타나는 버그(대부분 미정의 동작이 원인)도 있으므로, 운영 빌드에도 -g를 넣어 두면 최적화된 상태 그대로 코어를 분석할 수 있습니다. -g는 실행 속도에 영향을 주지 않고 파일 크기만 늘립니다.

경고는 무료 디버거입니다

-Wall -Wextra만 켜도 초기화하지 않은 변수 사용, printf 형식 지정자 불일치(%d에 long long), 부호 있는/없는 비교, 반환값 누락 같은 버그를 컴파일 시점에 잡아 줍니다. 금융권 프로젝트에서는 "경고 0개"를 빌드 통과 조건으로 두는 곳이 많습니다. -Werror로 경고를 오류로 취급하게 할 수도 있습니다.

gdb 기본 명령과 실습 세션

gdb(GNU Debugger)는 프로그램을 원하는 지점에서 멈추고, 변수를 보고, 한 줄씩 실행하고, 호출 스택을 거슬러 올라갈 수 있게 해 줍니다. 먼저 자주 쓰는 명령을 정리합니다. 괄호 안은 축약형입니다.

왜 NULL 역참조는 "세그멘테이션 폴트"가 될까?

리눅스는 프로세스 가상 주소 공간의 맨 앞 영역(0번지 근처, 보통 첫 64KB 정도)을 일부러 어떤 물리 메모리에도 매핑하지 않습니다. a->bal은 주소 0 + offsetof(Acct, bal), 즉 16번지를 읽는 명령이 됩니다(acct[15] 뒤 8바이트 정렬). CPU의 MMU가 이 주소를 물리 주소로 바꾸려다 페이지 테이블에 항목이 없음을 발견하면 페이지 폴트 예외를 일으키고, 커널은 "이 프로세스에 허용되지 않은 접근"이라 판단해 SIGSEGV 시그널을 보냅니다. 기본 동작은 프로세스 종료 + 코어 덤프입니다. 즉 세그폴트는 하드웨어와 OS가 함께 "잘못된 주소 접근"을 잡아 준 결과이며, C 표준 입장에서는 NULL 역참조가 미정의 동작이라 "반드시 죽는다"는 보장도 없습니다(최적화로 검사 코드가 사라지는 경우도 있음).

이렇게 해결합니다

"찾기" 함수가 NULL을 반환할 수 있다면, 호출하는 모든 곳에서 검사해야 합니다. 함수 주석에 "실패 시 NULL"을 명시하고, 코드 리뷰에서 반환값 검사를 확인합니다.

이번에는 watch로 "누가 이 값을 바꿨는가"를 찾는 실습입니다. 잔액이 엉뚱하게 바뀌는데 어디서 바꾸는지 모를 때 매우 강력합니다.

감시점은 값이 바뀐 직후의 다음 문장에서 멈추고, 이전 값과 새 값을 보여 줍니다. 위 세션의 apply_withdraw는 설명을 위해 가정한 함수입니다. x86-64는 하드웨어 디버그 레지스터로 최대 4개 정도의 감시점을 속도 저하 없이 지원합니다.

실행 중인 프로세스에 붙기

gdb -p <PID>로 이미 실행 중인 프로세스에 붙을 수 있습니다(같은 사용자이거나 권한 필요, 리눅스 ptrace_scope 설정 영향). 붙는 순간 프로세스 전체가 멈추므로, 운영 서버에서는 반드시 필요한 정보만 빠르게 얻고 detach해야 합니다. hang 분석의 정석은 gdb -p PID -batch -ex "thread apply all bt"로 모든 스레드의 스택을 파일로 떨군 뒤 즉시 떨어지는 것입니다. 몇 초 간격으로 2~3번 떠서 비교하면 "계속 같은 곳에 있는 스레드"가 범인 후보입니다. gcore PID로 프로세스를 죽이지 않고 코어 파일만 만들어 나중에 분석할 수도 있습니다.

core dump 활성화와 분석

운영 서버에서 새벽에 죽은 프로그램을 gdb로 다시 실행해 재현하기는 어렵습니다. 대신 프로세스가 죽는 순간의 메모리 전체(스택, 힙, 레지스터)를 파일로 남기게 할 수 있습니다. 이것이 코어 덤프(core dump)입니다. 비행기의 블랙박스와 같습니다.

해석: 전문 파서가 길이 필드를 믿고 len = 전체길이 - off를 계산했는데, 수신한 전문이 200바이트로 예상(212바이트 이상)보다 짧아 len이 -12가 되었습니다. memcpy의 세 번째 인자는 size_t(부호 없음)이므로 -12는 약 1.8×1019로 변환되어 엄청난 범위를 복사하다가 접근 불가 영역에서 죽었습니다. 원인은 "수신 길이 검증 누락"이고, 해결은 파싱 전에 rlen >= 최소 길이를 검사하는 것입니다. 27장의 "전문 길이 검증"이 왜 중요한지 보여 주는 전형적인 코어입니다.

코어가 안 남는 흔한 이유

  • 데몬의 코어 크기 제한이 0(로그인 셸에서 ulimit -c unlimited를 해도 이미 떠 있는 데몬에는 적용 안 됨).
  • core_pattern 경로가 없거나 프로세스 사용자에게 쓰기 권한이 없음, 디스크 가득 참.
  • setuid 프로그램 등 보안상 코어가 금지된 경우(fs.suid_dumpable).
  • 프로그램이 SIGSEGV 핸들러를 등록해 스스로 exit()해 버림. 시그널 핸들러에서 로그를 남기고 싶다면, 기본 동작으로 되돌린 뒤 같은 시그널을 다시 발생시켜(signal(sig, SIG_DFL); raise(sig);) 코어가 남게 하십시오.

또한 코어 파일에는 그 순간 메모리의 모든 내용, 즉 고객 계좌번호, 전문, 경우에 따라 비밀번호 블록까지 들어 있습니다. 금융권에서 코어 파일은 개인정보·보안 자료로 취급해 접근 권한을 제한하고, 분석 후 정해진 절차로 삭제해야 합니다.

은행 시스템에서는: 같은 실행 파일을 보관하라

한 대외계 서버에서 코어가 남았지만, 운영 담당자가 이미 "핫픽스" 버전으로 실행 파일을 교체한 뒤였습니다. 새 실행 파일로 옛 코어를 열자 함수 이름과 줄 번호가 엉뚱하게 표시되어 분석이 하루 넘게 지연되었습니다. gdb는 실행 파일의 심볼 정보로 코어의 주소를 해석하므로, 코어를 만든 바로 그 빌드가 필요합니다. 그래서 성숙한 조직은 (1) 배포하는 모든 빌드의 실행 파일과 디버그 정보를 빌드 번호별로 보관하고, (2) 프로그램 기동 로그에 빌드 번호·빌드 일시를 남기며, (3) 코어 수집 스크립트가 코어와 함께 실행 파일, 공유 라이브러리 목록(ldd), 설정 파일을 묶어 보관하게 합니다.

Valgrind memcheck 출력 해석

Valgrind는 프로그램을 가상 CPU 위에서 실행하면서 모든 메모리 접근을 검사하는 도구입니다. 재컴파일 없이(디버그 정보는 있으면 좋음) 쓸 수 있고, 초기화되지 않은 값 사용, 해제된 메모리 접근, 범위 밖 힙 접근, 메모리 누수를 찾아 줍니다. 대가는 속도로, 보통 10~50배 느려지므로 운영이 아닌 테스트 환경에서 씁니다.

읽는 법을 하나씩 보겠습니다.

  • HEAP SUMMARY: 종료 시점에 해제되지 않은 메모리가 100블록, 4,800바이트(48 × 100)입니다. 전체 할당 101회 중 1회만 해제되었습니다(나머지 1회 1,024바이트는 printf가 내부적으로 할당한 stdout 버퍼이고 정상 해제됨).
  • loss record: "어디서 할당했는데 안 풀었는지"를 호출 스택으로 보여 줍니다. 아래에서 위로 읽으면 main의 27행이 parse_msg를 호출했고, 그 15행의 malloc이 누수의 출처입니다. 누수 지점은 "할당한 곳"이지 "해제를 빠뜨린 곳"이 아니라는 점에 주의하십시오. 해제 책임이 어디 있는지는 사람이 판단해야 합니다.
  • LEAK SUMMARY 분류: definitely lost(어떤 포인터도 가리키지 않음, 확실한 누수), indirectly lost(누수된 블록 안의 포인터만 가리킴, 예: 누수된 연결 리스트의 다음 노드), possibly lost(블록 중간을 가리키는 포인터만 있음, 의심), still reachable(종료 시 전역 포인터 등으로 아직 닿을 수 있음, 보통 덜 위험).

Valgrind는 누수 외에도 다음 오류들을 보고합니다. 메시지 이름을 알아 두면 바로 원인을 짐작할 수 있습니다.

누수 고치기: 단일 출구 패턴

free(NULL)은 아무 일도 하지 않도록 표준이 보장하므로, 해제 코드를 경로마다 흩어 두지 말고 한 곳에 모으는 것이 누수 예방의 핵심입니다.

AddressSanitizer와 UBSan

AddressSanitizer(ASan)는 컴파일러가 모든 메모리 접근 앞에 검사 코드를 끼워 넣는 방식의 도구입니다. Valgrind보다 훨씬 빠르고(보통 2배 정도 느려짐), 스택과 전역 배열의 범위 초과까지 잡아 줍니다. gcc와 clang 모두 지원합니다.

"14바이트 영역 바로 오른쪽 0바이트 지점"에 썼다는 메시지가 핵심입니다. 14자리 계좌번호에 malloc(14)를 했으니 널 문자를 쓸 자리가 없었던 것입니다. 할당 위치(7행)와 잘못 쓴 위치(9행)를 모두 알려 주므로 원인이 바로 보입니다. 이 버그는 일반 실행에서는 대개 아무 증상이 없습니다. malloc이 내부적으로 16바이트 단위로 할당해 여유가 있기 때문입니다. 그러다 계좌번호 길이가 16자리로 바뀌는 날, 다른 블록의 관리 정보를 덮어써 엉뚱한 곳의 free에서 죽습니다.

왜 ASan은 Valgrind보다 빠르고, 스택 오류도 잡을까?

Valgrind는 실행 파일의 기계어를 실행 시간에 하나하나 해석·변환하며 검사하므로 느립니다. 그리고 컴파일이 끝난 바이너리만 보기 때문에 "스택의 이 배열이 어디서 끝나는지" 같은 소스 수준 정보를 모릅니다. ASan은 컴파일 시점에 검사 코드를 넣습니다. 컴파일러는 모든 배열의 크기를 알기에 스택 배열과 전역 배열 주위에도 레드존을 배치할 수 있고, 검사 코드는 네이티브 기계어로 돌아 빠릅니다. 대신 재컴파일이 필요하고 메모리를 2~3배 더 씁니다. 실무에서는 단위 테스트와 통합 테스트를 ASan+UBSan 빌드로 돌리는 것을 CI의 기본으로 두고, 소스가 없는 라이브러리 문제나 초기화 안 된 값 추적에는 Valgrind를 씁니다.

UBSan은 미정의 동작이 실제로 일어난 순간을 알려 줍니다. 위 메시지는 금액을 int로 누적하다 21억을 넘긴 경우입니다. 부호 있는 정수 오버플로는 미정의 동작이라 결과가 음수로 "돌아가는" 것조차 보장되지 않으며, 최적화된 코드에서는 오버플로 검사 if문이 삭제될 수도 있습니다. 금액은 long long, 그리고 경계 검사는 연산 전에(if (a > LLONG_MAX - b)) 해야 합니다.

strace와 ltrace

프로그램이 "멈춘 것 같다", "느리다", "파일을 못 연다"는데 로그가 없을 때, 프로그램과 운영체제 사이의 대화를 엿들으면 많은 것이 보입니다. strace는 프로세스가 호출하는 시스템 콜(open, read, write, connect, poll 등)과 그 결과를, ltrace는 공유 라이브러리 함수 호출(malloc, strcmp 등)을 보여 줍니다.

읽는 법: 300바이트 전문을 보낸 뒤 recvfrom에서 30초 동안 응답을 기다렸고, 결국 0(상대가 연결 종료)을 받았습니다. 즉 "우리 프로그램이 멈춘 것"이 아니라 상대 기관이 응답하지 않은 것입니다. 이어서 설정 파일이 없다는 ENOENT도 보입니다. 로그에 "설정 파일 오류"만 찍혔다면 어느 파일인지 몰랐을 텐데, strace는 경로까지 정확히 보여 줍니다. 각 줄 끝 <초>가 그 시스템 콜에 걸린 시간이므로, 느린 구간을 바로 찾을 수 있습니다.

운영 서버에서 strace를 쓸 때

strace는 ptrace로 모든 시스템 콜마다 프로세스를 멈추고 기록하므로, 시스템 콜이 많은 프로세스는 수 배~수십 배 느려집니다. 초당 수천 건을 처리하는 온라인 프로세스에 오래 붙여 두면 그 자체가 장애가 됩니다. -e로 필요한 시스템 콜만, 짧은 시간만 붙이고, 출력에 전문 내용(개인정보)이 그대로 찍힌다는 점도 유의하십시오(-s 옵션으로 문자열 출력 길이를 줄일 수 있음).

printf 디버깅의 한계

가장 원시적이면서 여전히 많이 쓰는 방법은 의심 가는 곳에 printf를 넣는 것입니다. 간단한 논리 오류에는 충분히 효과적입니다. 하지만 C에서는 다음과 같은 한계와 함정이 있습니다.

  1. 버퍼링 때문에 죽기 직전 출력이 사라집니다. stdout은 터미널이면 줄 단위, 파일이나 파이프로 리다이렉트하면 완전 버퍼링(보통 4KB)입니다. 세그폴트로 죽으면 버퍼에 남은 내용은 출력되지 않아, "마지막으로 찍힌 printf 이후에서 죽었다"는 추론이 틀립니다. 디버그 출력은 버퍼링되지 않는 stderr로 하거나 fflush(stdout)를 붙여야 합니다.
  2. 관찰이 현상을 바꿉니다(하이젠버그). printf를 넣으면 스택 배치, 레지스터 사용, 타이밍이 바뀌어 미정의 동작이나 경쟁 조건 버그가 사라지기도 합니다. "printf를 넣으면 안 죽는다"는 메모리 오류나 레이스의 강력한 신호입니다.
  3. 멀티스레드에서 출력이 섞이고 순서가 왜곡됩니다. 출력 순서가 실제 실행 순서를 보장하지 않습니다.
  4. 운영에 남으면 사고가 됩니다. 디버깅용 printf로 전문 전체나 카드번호를 찍어 놓고 지우지 않은 채 배포하면 개인정보 유출 사고입니다. 성능 저하도 생깁니다.
  5. 재컴파일·재배포가 필요합니다. 운영에서 이미 일어난 장애는 printf로 분석할 수 없습니다. 그때 필요한 것이 다음 절의 설계된 로그와 코어 덤프입니다.

30-2로그 설계와 장애 분석

운영 중인 금융 시스템에서 장애가 나면 디버거를 붙일 수 없는 경우가 대부분입니다. 이미 지나간 일이고, 수많은 거래 중 하나에서 생긴 일이며, 서버는 여러 대입니다. 그때 유일한 증거는 로그입니다. 로그는 "나중의 나(또는 새벽 당직자)를 위한 편지"입니다. 이 절에서는 장애 분석에 실제로 쓸모 있는 로그를 설계하고 C로 구현한 뒤, 장애 대응 절차와 유형별 사례 추적을 연습합니다.

업무 오류는 ERROR가 아닙니다

"잔액 부족", "비밀번호 오류", "해지 계좌" 같은 업무적 거절은 시스템이 정상적으로 판단한 결과이므로 INFO(응답코드와 함께)로 남깁니다. 이를 ERROR로 찍으면 하루 수만 건의 "ERROR"가 쌓여 진짜 시스템 오류가 묻히고, 경보가 계속 울려 당직자가 경보를 무시하게 되는 경보 피로가 생깁니다. ERROR는 "누군가 들여다봐야 하는 일"에만 씁니다.

거래 추적 ID(GUID)로 온라인-대외-배치 연결

고객 한 명의 타행이체 한 건은 모바일 앱 → 채널계 → 계정계(TP 모니터) → 원장 DB → 대외계 → 대외기관으로 이어지고, 야간에는 대사 배치에서 다시 등장합니다. 서버도 다르고 프로세스도 다르고 로그 파일도 다릅니다. 고객이 "어제 오후 3시에 보낸 돈이 안 갔다"고 할 때, 수십 개의 로그 파일에서 이 거래와 관련된 줄을 어떻게 찾을까요? 답은 거래가 처음 시스템에 들어올 때 전역적으로 유일한 ID를 하나 부여하고, 이후 모든 구간의 전문과 로그, DB 거래내역에 그 ID를 실어 보내는 것입니다. 이를 거래 추적 ID, 글로벌 ID(GUID), 또는 트레이스 ID라고 부릅니다.

GUID는 다음 조건을 만족하게 만듭니다. (1) 전역 유일: 서버가 여러 대여도 겹치지 않도록 날짜 + 시스템/서버 식별자 + 프로세스 식별 + 일련번호를 조합합니다. (2) 사람이 읽을 수 있음: 날짜와 채널이 보이면 grep 범위를 좁히기 쉽습니다. (3) 고정 길이: 전문 헤더의 고정 필드에 넣기 좋습니다.

GUID를 중간에 새로 만들지 마십시오

가장 흔한 실수는 각 시스템이 "자기 편한 대로" 새 ID를 만드는 것입니다. 계정계가 채널계의 GUID를 무시하고 자기 ID를 만들면, 두 시스템의 로그를 잇는 고리가 끊깁니다. 원칙은 "받은 GUID가 있으면 그대로 쓰고, 없을 때(최초 진입점)만 만든다"입니다. 대외기관처럼 상대가 정한 전문번호 체계를 써야 하는 구간에서는 "우리 GUID ↔ 기관 전문번호" 매핑을 반드시 로그와 DB에 남깁니다. 또한 스레드 풀에서 GUID를 스레드 로컬 변수에 둘 때는 요청 시작마다 설정하고 끝나면 지워야 이전 거래의 ID가 섞이지 않습니다(28장).

로그 포맷과 매크로 구현

좋은 로그 한 줄에는 "언제, 어디서(서버·프로세스·스레드·소스 위치), 어떤 거래에서, 무엇이, 얼마나 걸려" 일어났는지가 들어 있어야 합니다. 그리고 사람이 읽기 쉬우면서도 grep·awk 같은 도구로 자르기 쉽게 필드 순서와 구분자가 고정되어야 합니다.

매번 날짜, 레벨, 파일명, 줄 번호를 손으로 쓰는 것은 불가능하므로 매크로로 자동화합니다. C 전처리기가 제공하는 __FILE__(소스 파일명), __LINE__(줄 번호), C99의 __func__(함수 이름)와 가변 인자 매크로 __VA_ARGS__를 씁니다.

왜 이렇게 만들었을까? 설계 포인트 다섯 가지

  1. do { ... } while (0): 매크로가 if (x) LOG_INFO(...); else ... 안에서도 한 문장처럼 동작하게 합니다(15장 매크로 함정). 그냥 if로 펼치면 뒤의 else가 매크로 안의 if에 붙어 버립니다.
  2. 레벨 검사를 매크로에서: DEBUG가 꺼져 있으면 log_write 호출도, 인자 계산(예: 큰 구조체 덤프 함수 호출)도 일어나지 않아 운영 성능에 영향이 없습니다.
  3. format(printf, 5, 6) 속성: gcc가 LOG_INFO("amt=%d", amt_ll)처럼 형식 지정자와 인자 타입이 맞지 않으면 경고합니다. 로그 형식 오류는 그 자체로 미정의 동작이며, %s에 정수를 주면 장애 순간에 로그를 찍다가 죽는 최악의 상황이 됩니다.
  4. 한 줄 = 한 번의 write + O_APPEND: 여러 스레드(그리고 같은 파일에 쓰는 여러 프로세스)의 로그가 한 줄 중간에 섞이지 않게 합니다. O_APPEND는 "파일 끝으로 이동 + 쓰기"를 커널이 원자적으로 하므로 서로 덮어쓰지 않습니다. stdio의 fprintf를 쓰면 버퍼링 때문에 죽기 직전 로그가 유실될 수 있지만, write는 커널에 즉시 넘어갑니다(전원 장애까지 대비하는 fsync는 하지 않음).
  5. errno 보존: 오류 처리 코드 중간에 로그를 찍었더니 로그 함수 내부 호출이 errno를 바꿔, 그다음 strerror(errno)가 엉뚱한 원인을 출력하는 일이 흔합니다.

참고로 위 코드는 설명을 위해 단순화했습니다. 날짜 비교를 위해 g_cur_date와 g_fd를 락 없이 읽는 부분은 28장 기준으로 엄밀히는 데이터 레이스이므로, 실무 라이브러리는 이 둘을 _Atomic으로 두거나 "현재 날짜 번호"를 원자 정수 하나로 관리하고, 교체된 옛 fd는 바로 닫지 않고 잠시 뒤에 닫아 다른 스레드의 진행 중인 write를 보호합니다.

경과 시간은 반드시 MONOTONIC 시계로

CLOCK_REALTIME은 NTP 동기화나 관리자의 시각 변경으로 앞뒤로 튈 수 있습니다. 시각이 1초 뒤로 조정되는 순간 측정한 소요 시간이 음수가 되거나, 타임아웃 계산이 엉망이 됩니다. 로그에 찍는 "현재 시각"은 REALTIME, 구간 "소요 시간"과 타임아웃 계산은 CLOCK_MONOTONIC을 씁니다. 모든 서버의 시각은 NTP로 맞춰야 서버 간 로그를 시간순으로 비교할 수 있습니다.

자주 하는 실수: 전문 통째로 덤프

장애 분석이 편하다는 이유로 수신 전문 전체를 LOG_DEBUG("recv=[%.*s]", len, buf)로 찍는 코드가 많습니다. 전문 안에는 계좌번호, 성명, 경우에 따라 암호화된 비밀번호 블록까지 들어 있습니다. "DEBUG라서 운영에서는 안 찍힌다"고 생각하지만, 장애 때 DEBUG를 켜는 순간 그대로 기록됩니다. 해결책은 전문 레이아웃 정의에 필드별 마스킹 속성을 두고, 덤프 함수가 그 속성에 따라 민감 필드를 자동으로 가리게 하는 것입니다. 또한 정기적으로 로그 파일을 패턴(13~19자리 연속 숫자, 주민번호 형식)으로 검사하는 점검 스크립트를 돌리는 조직이 많습니다.

사고 사례: 디버그 로그가 만든 개인정보 유출

한 금융회사의 카드 승인 모듈에서 응답 지연 장애가 났고, 개발자가 원인 파악을 위해 운영 서버의 로그 레벨을 DEBUG로 올렸습니다. 원인은 찾았지만 레벨을 되돌리는 것을 잊었고, 이후 몇 주 동안 승인 전문 전체(카드번호 평문 포함)가 로그에 쌓였습니다. 이 로그는 로그 수집 서버를 거쳐 여러 부서가 조회할 수 있는 검색 시스템에 들어갔고, 정기 점검에서 발견되어 대규모 파기와 보고 절차를 밟아야 했습니다. 재발 방지책: (1) 전문 덤프 함수에 필드별 자동 마스킹 적용, (2) 운영 DEBUG 활성화는 승인 절차를 거치고 일정 시간 후 자동 복귀하는 기능 추가, (3) 로그 수집 단계에서 민감 패턴 탐지·차단.

로그 로테이션

로그를 한 파일에 계속 쓰면 언젠가 디스크가 가득 찹니다. 디스크가 차면 로그만 못 쓰는 것이 아니라, 같은 파일 시스템을 쓰는 DB나 임시 파일, 코어 덤프까지 실패해 시스템 전체 장애로 번집니다. 그래서 로그 파일을 날짜나 크기 기준으로 나누고(rotate), 오래된 것은 압축·이관·삭제합니다.

방식동작장점주의

왜 로그 파일을 지웠는데 디스크 공간이 돌아오지 않을까?

유닉스에서 rm은 디렉터리에서 파일 이름(링크)을 지울 뿐이고, 파일의 실제 데이터는 그 파일을 열고 있는 프로세스가 하나라도 있으면 해제되지 않습니다(23장 파일 디스크립터와 inode). 서버가 로그 fd를 계속 열어 둔 채로 운영자가 큰 로그 파일을 rm하면, df는 여전히 가득 차 있다고 나오고 프로그램은 이름 없는 파일에 계속 써 나갑니다. lsof +L1 또는 ls -l /proc/PID/fd에서 "(deleted)" 표시로 확인할 수 있습니다. 해결은 프로그램이 파일을 다시 열게 하거나(재오픈 신호), 재기동하는 것입니다. 이 때문에 로그 정리는 "이미 닫힌 지난 날짜 파일"만 대상으로 하는 날짜별 파일 방식이 안전합니다.

시그널 핸들러 안에서 직접 open이나 LOG_INFO(내부에서 snprintf, localtime_r 사용)를 호출하면 안 됩니다. 이들은 비동기 시그널 안전(async-signal-safe) 함수가 아니어서, 메인 코드가 같은 함수 안에서 락을 쥔 순간 시그널이 오면 교착이나 데이터 손상이 생깁니다(28장 재진입성). 핸들러는 플래그만 세우고 실제 작업은 메인 흐름에서 합니다.

보존 기간

금융권의 거래 관련 로그와 접속 기록은 관련 법규와 내부 규정에 따라 일정 기간 이상 보존해야 하는 경우가 많습니다. 그래서 "오래된 로그 삭제"는 단순히 find -mtime +7 -delete가 아니라, 보존 대상은 압축해 별도 저장소로 이관하고 보존 기간이 지난 것만 파기하는 절차로 운영합니다. 반대로 개인정보가 포함된 로그는 목적 달성 후 지체 없이 파기해야 하므로, 무엇을 얼마나 남길지 설계 단계에서 정해야 합니다.

장애 대응 절차: 감지-전파-원인-복구-재발방지

장애가 났을 때 가장 위험한 것은 당황해서 아무거나 해 보는 것입니다. 원인을 모른 채 재기동부터 하면 증거(메모리 상태, 락 대기 상황)가 사라지고, 같은 장애가 반복됩니다. 반대로 원인 분석에만 매달리면 고객 피해 시간이 길어집니다. 금융권은 이 균형을 위해 정해진 절차를 따릅니다.

  1. 감지: 이상적인 감지는 고객보다 먼저 시스템이 알아차리는 것입니다. 오류율(ERROR 로그 건수, 응답코드 비율), 응답 시간, 처리량(초당 거래 수)이 갑자기 0이 되는 것, 큐 길이, 프로세스 생존, 디스크 사용률을 지표로 감시합니다. 특히 hang은 프로세스가 살아 있어 생존 감시로 못 잡으므로 처리량 0 감시가 필수입니다.
  2. 전파: 영향 범위(어떤 채널, 어떤 거래, 고객 수, 금액)를 빠르게 파악해 장애 등급을 정하고, 정해진 연락 체계로 관련 부서·책임자에게 알립니다. 대외기관 연계 장애면 상대 기관에도 통보하고, 고객 공지 여부를 결정합니다. "아직 원인을 모른다"도 중요한 전파 내용입니다.
  3. 원인 파악: 복구 조치(재기동 등)를 하기 전에 증거를 먼저 확보합니다. hang이면 gdb -batch -ex "thread apply all bt"나 gcore, 죽었으면 코어 파일, 그리고 해당 시간대 로그, top/vmstat/netstat 출력, 최근 변경 이력(배포, 설정 변경, 데이터 변경)입니다. "최근에 바뀐 것이 무엇인가?"는 가장 강력한 질문입니다.
  4. 복구: 서비스 정상화가 최우선입니다. 프로세스 재기동, 이전 버전으로 롤백, 대기 서버로 전환, 문제 거래 차단 같은 조치를 합니다. 그리고 금융에서는 데이터 정합성 확인까지가 복구입니다. 장애 시간대의 미결 거래(타임아웃 등)를 GUID로 하나씩 확정하고, 원장과 거래내역 대사를 돌려 불일치를 정리합니다.
  5. 재발 방지: 직접 원인(버그 한 줄)만이 아니라 "왜 테스트에서 못 잡았나, 왜 감지가 늦었나, 왜 영향이 커졌나"까지 근본 원인을 찾아 개선 과제로 만들고, 장애 보고서로 공유합니다.

재기동은 증거를 지웁니다

hang 장애에서 습관적으로 프로세스를 재기동하면 서비스는 돌아오지만, 어떤 스레드가 어떤 락을 기다렸는지라는 결정적 증거가 사라집니다. 같은 장애가 일주일 뒤 다시 납니다. 재기동 전 1~2분만 투자해 스택 덤프를 떠 두는 습관이 베테랑의 표시입니다. 이를 위해 "증거 수집 스크립트"(모든 스레드 스택, 열린 파일·소켓 목록, 메모리 사용량, 최근 로그 꼬리를 한 번에 저장)를 미리 만들어 두고, 장애 대응 매뉴얼의 재기동 단계 바로 앞에 넣어 두십시오.

장애 보고서는 누군가를 탓하기 위한 문서가 아니라, 조직이 같은 실수를 반복하지 않기 위한 학습 기록입니다. 사실 위주로, 시각을 정확히, 추측과 확인된 사실을 구분해 씁니다. 다음은 일반적인 양식의 예입니다(내용은 가상).

"왜?"를 다섯 번

근본 원인 분석에서 자주 쓰는 기법이 "5 Whys"입니다. 왜 장애가 났나? 타임아웃이 없었다. 왜 없었나? 공통 함수를 안 썼다. 왜 안 썼나? 존재를 몰랐다. 왜 몰랐나? 문서화·교육이 없었다. 왜 리뷰에서 못 잡았나? 체크리스트에 없었다. 이렇게 파고들면 "개발자 실수"에서 멈추지 않고, 시스템과 절차를 고치는 재발 방지책이 나옵니다. 이 과정의 "왜 그럴까?"가 이 과정 전체를 관통하는 질문이기도 합니다.

유형별 장애 사례 추적 연습

이제 실무에서 가장 흔한 네 가지 유형을, 증상에서 출발해 원인까지 추적해 봅시다. 각 사례는 실제로 자주 일어나는 패턴을 일반화한 가상의 이야기입니다.

사례 1. 세그폴트: 해지 계좌 하나가 배치를 멈췄다

증상: 매일 잘 돌던 야간 이자 배치가 02:13에 "Segmentation fault"로 종료. 재실행해도 같은 지점에서 죽음. 로그 마지막 줄은 [INFO] 처리 중 120000건.

  1. 증거 확보: 코어 파일 확인(/var/crash/core.intr_batch.*). 같은 빌드의 실행 파일로 gdb ./intr_batch core....
  2. bt: #0 strlen() #1 calc_tax(cust=0x0...) at tax.c:57 #2 process_acct(...) at intr.c:140. 세금 계산 함수에 NULL 고객 포인터가 들어옴.
  3. frame 2 → print: p h_acct_no → 특정 계좌, p cust_found → 0. 고객 정보 조회 실패를 검사하지 않고 진행.
  4. DB 확인: 그 계좌는 어제 고객 정보만 먼저 삭제(해지 처리 순서 오류)되어 계좌는 있는데 고객이 없는 상태.
  5. 복구: 해당 계좌 예외 처리 후 배치 재실행(재시작 지점부터). 재발 방지: 조회 실패 시 해당 계좌만 오류 목록에 기록하고 다음 계좌로 진행하는 구조로 변경(한 건의 불량 데이터가 전체를 멈추지 않게), 해지 처리 순서 수정, 참조 무결성 점검 배치 추가.

교훈

배치는 "한 건의 이상 데이터"를 반드시 만납니다. 건별 오류는 격리해서 기록하고 계속 진행하되, 오류 건수가 임계치를 넘으면 중단하는 구조가 기본입니다.

사례 2. 메모리 누수: 매주 목요일마다 느려지는 서버

증상: 월요일 아침 정기 재기동 후 정상이던 대외계 서버가 목요일 오후쯤부터 응답이 느려지고, 금요일에 한 번 메모리 부족(OOM Killer)으로 강제 종료됨.

  1. 관찰: ps -o pid,rss,vsz -p PID를 1시간마다 기록하니 RSS가 시간당 일정하게 증가. 거래량이 많은 시간대에 기울기가 큼 → 거래 건당 누수로 추정.
  2. 재현: 테스트 환경에서 거래 1만 건을 흘리며 valgrind --leak-check=full 또는 ASan(LeakSanitizer) 빌드로 실행.
  3. 결과: definitely lost: 2,560,000 bytes in 10,000 blocks, 할당 위치 build_reply (reply.c:77). 건당 256바이트.
  4. 코드 확인: 응답 전문 버퍼를 malloc하고, 정상 경로에서는 송신 후 free하지만 대외기관이 "거래 불가" 응답을 준 경로에서는 조기 return으로 free를 건너뜀. 하루 거래 중 이 응답이 일정 비율로 섞여 있었음.
  5. 수정: 단일 출구(goto cleanup) 패턴으로 모든 경로의 해제를 한 곳에 모음. 재발 방지: CI에 LeakSanitizer 빌드 테스트 추가, 운영 모니터링에 프로세스 RSS 추세 경보 추가.

사례 3. 데드락: CPU 0%인데 응답이 없다

증상: 계좌 관리 서버의 처리량이 10:32부터 0. 프로세스는 살아 있고 CPU 0%, 메모리 정상. 신규 요청은 접수 큐에 쌓이기만 함.

  1. 증거 확보(재기동 전): gdb -p PID -batch -ex "thread apply all bt" > stack_1032.txt, 10초 뒤 한 번 더.
  2. 분석: 두 덤프 모두 작업 스레드 대부분이 __lll_lock_wait → pthread_mutex_lock → get_account에서 대기. 특히 다음 두 스레드가 눈에 띔.
  1. 해석: 스레드 12(이체)는 계좌 ...003을 이미 쥐고(transfer.c는 오름차순 규칙 준수: 003 < 005) ...005를 기다리고, 스레드 7(신규 기능인 계좌 통합)은 ...005를 먼저 쥐고 ...003을 기다림. p *(pthread_mutex_t *)0x1a2b3c0의 __owner 필드로 각 락의 소유 스레드(LWP)를 확인해 순환을 확정. 나머지 스레드들은 이 두 계좌의 락을 기다리며 줄줄이 막힘.
  2. 원인: 신규 개발된 merge_accounts가 "원본 → 대상" 순서로 잠가 계좌번호 오름차순 규칙을 위반.
  3. 복구: 스택 확보 후 재기동, 계좌 통합 기능 일시 중지. 재발 방지: 락 획득을 공통 함수 lock_two_accounts()로만 하도록 강제, 개발·테스트 빌드에서 PTHREAD_MUTEX_ERRORCHECK와 락 순서 검증 코드(오름차순 위반 시 즉시 abort) 활성화, "처리량 30초간 0" 경보 추가.

사례 4. 타임아웃 폭주: 작은 지연이 전체 장애로

증상: 오전 9시, 한 대외기관의 응답 시간이 평소 0.2초에서 5초로 늘어남. 몇 분 뒤 그 기관과 무관한 자행 이체와 잔액 조회까지 타임아웃이 폭증하고, 채널 전체 응답이 멈춤.

왜 5초 지연이 전체 장애가 될까? 리틀의 법칙

동시에 처리 중인 요청 수(L)는 도착률(λ) × 평균 처리 시간(W)입니다. 이 기관으로 초당 200건이 들어오고 응답이 0.2초면 동시 처리 중인 요청은 평균 40건이라 스레드 64개로 충분합니다. 응답이 5초가 되면 200 × 5 = 1,000건이 동시에 스레드를 붙잡아야 합니다. 스레드는 64개뿐이니 순식간에 바닥나고, 이 풀을 함께 쓰는 자행 이체와 조회도 스레드를 못 얻어 대기합니다. 여기에 채널의 타임아웃 → 고객 재시도가 도착률 λ를 더 키워 상황이 악화됩니다. 외부 지연이 "느려짐"에서 그치지 않고 "전체 정지"로 번지는 수학적 이유입니다.

  1. 추적: 로그에서 elapsed가 큰 요청을 기관 코드별로 집계(grep ERROR | awk) → 특정 기관에 집중. 스택 덤프에서 작업 스레드 대부분이 recv(그 기관 소켓)에서 대기.
  2. 복구: 해당 기관 거래를 일시 차단(즉시 "기관 장애" 응답)해 스레드를 풀어 주자 나머지 서비스가 즉시 회복.
  3. 재발 방지: (1) 모든 외부 호출에 짧은 타임아웃(SO_RCVTIMEO 또는 poll로 구현, 27장), (2) 서킷 브레이커: 특정 기관의 실패율이 임계치를 넘으면 일정 시간 동안 호출 자체를 하지 않고 즉시 실패 응답, 주기적으로 소량만 시험 호출해 회복 확인, (3) 기관별 스레드 풀 분리(격벽), (4) 재시도는 횟수 제한 + 지수 백오프 + 무작위 지연, 그리고 멱등한 거래만 자동 재시도, (5) 큐 포화 시 빠른 거절(부하 차단).

HALF_OPEN 상태에서는 실제로는 소수의 요청만 통과시키는 것이 좋지만, 위 코드는 이해를 위해 단순화했습니다. 핵심은 "망가진 곳에 계속 요청을 보내 자원을 묶어 두지 말고, 빨리 실패해서 나머지를 살린다"는 생각입니다.

은행 시스템에서는: 빨리 실패하는 것이 고객을 지킨다

금융 시스템의 장애 대부분은 "한 곳이 완전히 죽는 것"보다 "한 곳이 느려지는 것"에서 시작해 퍼집니다. 그래서 베테랑 설계자는 기능을 만들 때 항상 세 가지를 묻습니다. "이 호출이 영원히 안 돌아오면 어떻게 되나?(타임아웃)", "이 호출이 실패하면 무엇을 붙잡고 있나?(자원 격리)", "결과를 모를 때 어떻게 확정하나?(GUID와 결과 조회)". 이 장에서 배운 도구와 로그는 결국 이 세 질문에 답하기 위한 것입니다.

30-2 한 줄 요약

로그는 레벨·시각·PID/TID·GUID·소스 위치가 고정 형식으로 찍히고, 민감정보는 마스킹되며, 날짜별로 나뉘어야 합니다. 장애 때는 재기동 전에 증거부터 확보하고, 감지-전파-원인-복구-재발방지를 따릅니다.

핵심 정리

  • 디버깅에는 -g -O0을, 운영 빌드에도 -g를 넣고 빌드 산출물을 보관해 코어를 분석할 수 있게 합니다.
  • gdb의 핵심은 bt(어떻게 여기까지 왔나), frame+print(원인 프레임의 값), watch(누가 바꿨나)입니다. 죽은 곳과 잘못된 곳은 다를 수 있습니다.
  • 코어 덤프는 ulimit -c, core_pattern, 데몬의 제한 설정을 확인해 켜고, 같은 실행 파일로 분석합니다. 코어에는 민감정보가 들어 있습니다.
  • Valgrind는 재컴파일 없이 누수·잘못된 접근·미초기화 값을 찾고(느림), ASan/UBSan은 컴파일 시 검사 코드를 넣어 빠르게 범위 초과와 미정의 동작을 찾습니다. TSan은 데이터 레이스용입니다.
  • strace는 시스템 콜과 소요 시간, ltrace는 라이브러리 호출을 보여 줍니다. 운영에서는 짧게, 필요한 것만 추적합니다.
  • printf 디버깅은 버퍼링, 관찰자 효과, 스레드 섞임, 운영 잔존 위험이 있습니다.
  • 로그 레벨은 FATAL/ERROR/WARN/INFO/DEBUG로 나누고, 업무 거절은 ERROR가 아닙니다.
  • 거래 추적 ID는 최초 진입점에서 한 번 만들어 모든 구간의 전문·로그·DB에 그대로 전달합니다.
  • 로그 매크로는 __FILE__, __LINE__, __func__, __VA_ARGS__와 do { } while (0)로 만들고, 한 줄을 한 번의 write로 O_APPEND 파일에 씁니다.
  • 계좌·카드·주민번호는 마스킹하고, 비밀번호·인증값은 기록하지 않습니다. 로그는 날짜별로 나누고 보존·파기 기준을 지킵니다.
  • 장애 대응은 감지-전파-원인-복구-재발방지이며, 재기동 전 증거 확보, 복구 후 데이터 정합성 확인까지가 복구입니다.
  • 세그폴트는 코어+bt, 누수는 RSS 추세+Valgrind/LSan, 데드락은 스택 덤프의 락 대기 순환, 타임아웃 폭주는 타임아웃·서킷 브레이커·격벽·재시도 제한으로 다룹니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. 세그멘테이션 폴트는 왜 발생하고 어떻게 디버깅하나요?

프로세스가 접근 권한이 없는 가상 메모리 주소, 예를 들어 매핑되지 않은 NULL 근처 주소나 해제된 영역, 읽기 전용 영역에 접근하면 MMU가 예외를 일으키고 커널이 SIGSEGV를 보내 발생합니다. 디버깅은 코어 덤프를 활성화해 같은 실행 파일과 함께 gdb로 열고, bt로 호출 경로를 본 뒤 frame과 print로 원인 프레임의 변수 값을 확인합니다. 죽은 위치와 원인 위치가 다를 수 있어 메모리 오류가 의심되면 ASan 빌드로 재현합니다. 꼬리 질문: NULL 역참조가 항상 세그폴트인가? C 표준상 미정의 동작이라 보장되지 않습니다.

Q2. 메모리 누수는 어떻게 찾나요?

운영에서는 프로세스 RSS가 시간이나 처리 건수에 비례해 계속 증가하는지 추세를 봅니다. 의심되면 테스트 환경에서 같은 부하를 주며 Valgrind memcheck의 leak-check나 AddressSanitizer의 LeakSanitizer로 실행해 할당 위치의 호출 스택을 얻습니다. 보고된 위치는 할당한 곳이므로 그 메모리의 해제 책임이 어느 경로에서 빠졌는지 코드로 추적하고, 오류 경로의 조기 return이 흔한 원인입니다. 예방은 goto cleanup 같은 단일 출구 패턴과 CI의 sanitizer 테스트입니다.

Q3. 디버깅할 때 왜 최적화를 끄나요?

최적화된 코드는 변수를 레지스터에만 두거나 없애고, 함수를 인라인하며, 문장 순서를 바꾸기 때문에 디버거에서 변수가 optimized out으로 나오거나 실행 위치가 소스와 어긋납니다. -O0이면 소스와 기계어가 일대일에 가깝게 대응해 단계 실행과 변수 확인이 정확합니다. 다만 최적화 시에만 드러나는 버그도 있어서 운영 빌드에도 -g를 넣어 코어를 분석할 수 있게 합니다. -g는 실행 속도에 영향이 없습니다.

Q4. Valgrind와 AddressSanitizer의 차이는?

Valgrind는 바이너리를 가상 CPU에서 동적으로 변환·실행하며 검사하므로 재컴파일이 필요 없지만 10배 이상 느리고, 스택 배열 범위 초과는 잘 잡지 못합니다. ASan은 컴파일러가 메모리 접근마다 섀도 메모리 검사 코드를 삽입하므로 재컴파일이 필요하지만 2배 정도로 빠르고 스택·전역 배열의 범위 초과까지 잡습니다. 초기화 안 된 값 사용 추적은 Valgrind가 강하고, ASan에서는 MemorySanitizer(clang)가 따로 있습니다.

Q5. 프로그램이 hang 상태일 때 어떻게 원인을 찾나요?

먼저 CPU 사용률을 봅니다. 0%면 락이나 I/O 대기, 100%면 무한 루프나 라이브락을 의심합니다. 재기동 전에 gdb -p로 붙어 thread apply all bt로 모든 스레드의 스택을 몇 초 간격으로 두세 번 떠서 비교합니다. 여러 스레드가 pthread_mutex_lock에서 대기하고 서로 다른 순서로 락을 쥔 순환이 보이면 데드락이고, recv 같은 시스템 콜에서 대기하면 외부 응답 지연입니다. strace -p로 현재 막힌 시스템 콜을 볼 수도 있습니다.

Q6. 좋은 로그의 조건은 무엇인가요?

시각(밀리초), 레벨, 프로세스·스레드 ID, 거래 추적 ID, 소스 위치, 메시지가 고정된 형식으로 기록되어 사람과 도구 모두 읽기 쉬워야 합니다. 요청의 시작과 끝, 응답코드, 소요 시간처럼 장애 분석에 필요한 사실을 남기되, 민감정보는 마스킹하고 비밀번호는 기록하지 않습니다. 레벨을 구분해 운영에서는 필요한 만큼만 남기고, 업무 거절은 ERROR로 찍지 않습니다. 로그가 errno를 바꾸거나 성능을 떨어뜨리지 않아야 하고, 로테이션으로 디스크를 보호해야 합니다.

Q7. 분산 시스템에서 하나의 요청을 어떻게 추적하나요?

요청이 처음 들어오는 지점에서 전역적으로 유일한 추적 ID를 생성하고, 이후 모든 시스템 간 전문 헤더, 각 시스템의 로그, DB의 거래 기록에 같은 ID를 전달·기록합니다. 그러면 ID 하나로 여러 서버의 로그를 시간순으로 모아 전체 흐름을 재구성할 수 있습니다. 중간 시스템이 ID를 새로 만들면 고리가 끊기므로 받은 ID는 그대로 쓰고, 외부 기관 번호와는 매핑을 남깁니다. 서버 시각을 NTP로 맞추는 것도 전제 조건입니다.

Q8. 장애가 나면 어떤 순서로 대응하나요?

감지, 전파, 원인 파악, 복구, 재발 방지 순서입니다. 감지 후 영향 범위를 판단해 정해진 체계로 보고·공지하고, 재기동 같은 조치 전에 스택 덤프·코어·로그 같은 증거를 먼저 확보합니다. 서비스 정상화를 우선하되, 금융에서는 미결 거래 확정과 대사로 데이터 정합성까지 확인해야 복구가 끝납니다. 이후 근본 원인을 분석해 코드뿐 아니라 테스트·감시·절차까지 개선하고 장애 보고서로 공유합니다.

Q9. 타임아웃이 연쇄적으로 퍼지는 장애를 어떻게 막나요?

외부 호출마다 적절히 짧은 타임아웃을 두고, 호출 계층에서 바깥쪽 타임아웃이 안쪽보다 길도록 정렬합니다. 실패율이 높은 대상에는 서킷 브레이커로 일정 시간 호출을 차단해 빨리 실패시키고, 대상별로 스레드 풀을 분리하는 격벽 패턴으로 한 곳의 지연이 전체 자원을 묶지 않게 합니다. 재시도는 횟수 제한과 지수 백오프·무작위 지연을 두고 멱등한 요청에만 적용하며, 큐가 차면 빠르게 거절하는 부하 차단을 둡니다.

연습문제 30-3 난이도 ★★☆ 출력 해석

Valgrind가 다음을 보고했습니다. 무엇을 의미하며 어디부터 봐야 합니까?

정답과 해설 보기

해제된 메모리 사용(use-after-free)입니다. list.c 30행에서 24바이트 블록을 free한 직후, 31행에서 그 블록 안 8바이트 오프셋(예: 연결 리스트 노드의 next 포인터)을 읽었습니다. 전형적인 코드는 free(p); p = p->next;입니다. 해제 전에 다음 포인터를 저장해야 합니다: Node *nx = p->next; free(p); p = nx;. 이 버그는 대개 우연히 동작하다가 다른 스레드나 malloc이 그 영역을 재사용하는 순간 엉뚱한 값을 읽어 장애가 납니다.

연습문제 30-4 난이도 ★★☆ 버그 찾기

다음 로그 매크로를 썼더니 특정 위치에서 컴파일 오류(else without if)가 납니다. 이유와 수정 방법을 쓰십시오.

정답과 해설 보기

매크로 끝에 이미 세미콜론이 있는데 사용하는 쪽에서 ;를 또 붙여, if (rc) if (...) log_write(...); ;가 됩니다. 두 번째 ;는 빈 문장이라 바깥 if의 본문이 끝나고, 뒤의 else는 짝이 없어 오류입니다. 세미콜론을 빼더라도 매크로 안의 if가 바깥 else를 가로채는 "dangling else" 문제가 남습니다. 해결은 do { ... } while (0)로 감싸고 끝에 세미콜론을 두지 않는 것입니다.

연습문제 30-6 난이도 ★★☆

운영자가 꽉 찬 디스크를 비우려고 100GB짜리 acct_svr.log를 rm했는데 df의 사용률이 그대로입니다. 이유와 올바른 조치를 설명하십시오.

정답과 해설 보기

rm은 디렉터리 항목(이름)만 지우고, 서버 프로세스가 그 파일을 열어 둔 상태라 inode와 데이터 블록은 해제되지 않습니다. 프로세스는 이름 없는 파일에 계속 기록합니다. lsof +L1이나 ls -l /proc/PID/fd로 "(deleted)" 파일을 확인할 수 있습니다. 조치: 프로그램에 재오픈 신호(SIGHUP)를 보내 새 파일을 열게 하거나 재기동합니다. 급하면 : > /proc/PID/fd/N으로 열린 파일을 비울 수도 있지만 내용이 사라집니다. 근본적으로는 날짜별 파일 로테이션과 지난 파일만 정리하는 배치, 디스크 사용률 경보를 둡니다.

연습문제 30-7 난이도 ★★☆

다음 시그널 핸들러의 문제점을 지적하고 고치십시오.

정답과 해설 보기

(1) LOG_FATAL은 내부에서 snprintf, localtime_r 등 비동기 시그널 안전하지 않은 함수를 호출합니다. 세그폴트가 malloc 내부 락을 쥔 상태에서 났다면 교착에 빠질 수 있습니다. (2) exit(1)은 atexit 핸들러와 stdio 버퍼 정리를 수행해 손상된 상태에서 2차 오류를 낼 수 있고, 무엇보다 코어 덤프가 남지 않아 원인 분석 증거가 사라집니다. 수정: 비동기 안전한 write로 미리 만들어 둔 고정 메시지만 쓰고, 기본 동작으로 되돌려 시그널을 다시 발생시킵니다.

연습문제 30-8 난이도 ★★★ 장애 추적

야간 배치가 평소 40분이던 것이 오늘 3시간째 끝나지 않습니다. CPU 사용률은 2%이고 로그는 1시간 전 "계좌 230000건 처리"에서 멈춰 있습니다. 어떤 순서로 무엇을 확인하겠습니까?

정답과 해설 보기
  1. CPU가 낮으므로 무한 루프보다 대기(락, I/O, DB)를 의심합니다.
  2. 재기동 전에 gdb -p PID -batch -ex "thread apply all bt"를 몇 초 간격으로 두 번 뜹니다. Pro*C 호출(예: sqlcxt → OCI 내부 → read)에서 멈춰 있으면 DB 응답 대기입니다.
  3. strace -p PID -T로 현재 막힌 시스템 콜(소켓 read 등)을 확인합니다.
  4. DB 쪽에서 해당 세션의 대기 이벤트를 확인합니다(DBA 협조). 행 락 대기라면 어떤 세션이 그 행을 잡고 있는지 찾습니다. 흔한 원인은 온라인 거래나 다른 배치가 같은 행을 잠그고 커밋하지 않은 채 멈춘 것입니다.
  5. 원인 세션 처리(커밋/종료 판단) 후 배치를 재시작 지점부터 이어서 실행합니다.
  6. 재발 방지: 배치의 FOR UPDATE에 WAIT n 지정과 대기 초과 시 경보, 진행 로그를 건수뿐 아니라 일정 시간 간격으로도 남기기(로그가 멈춘 시점을 정확히 알 수 있게), 배치 소요 시간 이상 경보 추가.

연습문제 30-9 난이도 ★★★

대외기관 A로 초당 150건의 요청이 가고, 평소 응답 시간은 0.1초입니다. 처리 스레드는 32개입니다. (1) 평소 동시에 사용 중인 스레드 수는 평균 몇 개입니까? (2) 응답 시간이 2초로 늘면 몇 개가 필요합니까? (3) 이때 다른 기관 거래에 어떤 일이 생기며, 어떻게 막아야 합니까?

정답과 해설 보기

리틀의 법칙 L = λ × W를 씁니다. (1) 150 × 0.1 = 15개. 32개로 여유가 있습니다. (2) 150 × 2 = 300개. 32개를 훨씬 넘으므로 스레드가 모두 A 응답 대기에 묶이고 큐가 쌓입니다. (3) 같은 풀을 쓰는 다른 기관 거래와 자행 거래도 스레드를 얻지 못해 지연·타임아웃이 발생하고, 재시도까지 겹치면 전체 장애로 번집니다. 대책: A 호출 타임아웃을 짧게(예: 3초가 아니라 업무상 허용 최소치), 기관별 스레드 풀(격벽)로 A가 최대 N개만 쓰게 제한, A의 실패율이 높으면 서킷 브레이커로 즉시 "기관 장애" 응답, 재시도 제한과 백오프, 큐 포화 시 빠른 거절.

연습문제 30-10 난이도 ★★★ 금융 응용

고객이 "어제 14시 5분경 모바일로 50만 원 타행이체를 했는데 돈은 빠져나갔고 상대는 못 받았다"고 민원을 냈습니다. 거래 추적 ID 체계가 갖춰져 있다고 할 때, 사실 확인과 처리 절차를 단계별로 쓰십시오.

정답과 해설 보기
  1. 고객 계좌의 거래내역에서 해당 시각·금액의 출금 건을 찾아 GUID를 확인합니다.
  2. GUID로 채널계·계정계·대외계 로그를 검색해 전 구간을 시간순으로 재구성합니다. 대외계 로그에서 "GUID ↔ 기관 전문번호" 매핑과 대외기관의 응답 여부·응답코드를 확인합니다.
  3. 경우 판단: (가) 정상 응답이 있었다면 상대 은행 입금 완료이므로 상대 측 확인을 안내합니다. (나) 거절 응답이었는데 출금 취소(보상)가 없다면 보상 누락 버그이므로 즉시 출금 취소 처리합니다. (다) 무응답(결과 불명)이었다면 미결 거래 목록에 있는지, 결과 조회 전문이 수행되었는지 확인하고, 미확정이면 결과 조회 또는 기관과의 대사 파일로 확정합니다.
  4. 확정된 결과에 따라 입금 완료 안내 또는 보상 처리(원거래 GUID 참조, 멱등)를 하고, 고객에게 회신합니다.
  5. 같은 시간대에 같은 유형(결과 불명 후 미확정)이 더 있는지 GUID 목록으로 일괄 점검하고, 원인(예: 결과 조회 배치 실패)을 장애로 등록해 재발 방지책을 세웁니다.

GUID가 없다면 이 과정은 시각·금액·계좌번호로 여러 시스템 로그를 일일이 대조해야 하며, 같은 금액의 거래가 여러 건이면 확정이 불가능할 수도 있습니다. 이것이 추적 ID 설계의 가치입니다.

연습문제 30-11 난이도 ★★☆

"printf를 넣으면 버그가 사라진다"는 현상이 발생했습니다. 무엇을 의심하고, 어떤 도구로 확인하겠습니까?

정답과 해설 보기

printf 추가로 바뀌는 것은 스택 배치, 레지스터 할당, 실행 타이밍입니다. 따라서 (1) 초기화되지 않은 지역 변수(스택에 남은 값이 printf 호출로 바뀜), (2) 스택 버퍼 범위 초과(배치가 바뀌어 덮어쓰는 대상이 달라짐), (3) 데이터 레이스(printf의 내부 락과 지연이 타이밍을 바꿈), (4) 최적화와 결합된 미정의 동작을 의심합니다. 확인 도구는 -Wall -Wextra(미초기화 경고), ASan(스택 범위 초과), Valgrind memcheck(미초기화 값 사용), UBSan(미정의 동작), 멀티스레드라면 TSan입니다. printf로 증상이 사라졌다고 해결된 것이 아니라 숨은 것입니다.
