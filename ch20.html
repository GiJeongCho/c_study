20-1정수의 내부 표현: 2의 보수와 오버플로

PART 1에서 우리는 int는 4바이트, long long은 8바이트라고 배웠습니다. 그런데 4바이트 안에 -1은 정확히 어떤 비트 모양으로 들어 있을까요? 2147483647 + 1은 왜 -2147483648이 "될 수도" 있고, 왜 "아무 일이나 일어날 수도" 있다고 할까요? 이 절은 이런 질문에 하나하나 답하면서, 금융 프로그램에서 금액을 다룰 때 반드시 알아야 할 정수의 내부 표현을 정리합니다.

2진수와 16진수: 비트로 수를 쓰는 방법

컴퓨터의 메모리는 결국 전기가 "있다(1)/없다(0)"인 스위치의 나열입니다. 이 스위치 하나를 비트(bit), 8개를 묶은 것을 바이트(byte)라고 합니다. 10진수에서 각 자리가 1, 10, 100, 1000…의 무게(자리값)를 가지듯, 2진수에서는 각 자리가 1, 2, 4, 8, 16…의 무게를 가집니다.

예를 들어 8비트 2진수 10110101을 10진수로 바꾸려면, 1이 켜진 자리의 무게만 더하면 됩니다. 128 + 32 + 16 + 4 + 1 = 181입니다.

2진수는 길어서 사람이 읽기 어렵습니다. 그래서 4비트(니블, nibble)씩 묶어 한 글자로 쓰는 16진수를 씁니다. 4비트는 0~15를 표현하므로 0~9 다음에 A(10)~F(15)를 씁니다. 10110101을 앞 4비트 1011(=11=B)와 뒤 4비트 0101(=5)로 나누면 0xB5입니다. 16진수 한 글자 = 정확히 4비트이기 때문에, 16진수는 "비트를 사람이 읽기 좋게 압축한 표기"라고 생각하면 됩니다.

C에서 16진수 상수는 0x로, 8진수는 0으로 시작합니다. C23부터는 0b10110101 같은 2진 상수가 표준이 되었고, gcc/clang은 그 이전부터 확장으로 지원했습니다. 출력할 때는 %x(소문자), %X(대문자), %o(8진)를 쓰며, 2진 출력 서식은 C23의 %b 이전에는 없으므로 직접 함수를 만들어 씁니다.

마지막 두 줄을 보면 -5는 앞쪽이 온통 1로 채워져 있습니다. 이것이 바로 다음에 배울 2의 보수 표현입니다. 참고로 print_bits에서 (uint32_t)m처럼 unsigned로 바꾼 이유는, 음수를 오른쪽으로 시프트하는 동작이 구현 정의(implementation-defined)이기 때문입니다. unsigned로 바꾸면 비트 모양은 그대로 두고 "부호 없는 수"로 다루므로 시프트 결과가 표준으로 보장됩니다.

16진수 암산 요령

실무에서는 덤프(dump)를 보며 16진수를 읽을 일이 매우 많습니다. 전문 수신 로그, 코어 덤프, 네트워크 패킷이 전부 16진수입니다. 다음 몇 가지만 외워 두면 편합니다.

  • 0xFF = 255 (1바이트 최대), 0xFFFF = 65535, 0x7FFFFFFF = 2147483647 (INT_MAX)
  • 0x80000000 = 2147483648 (32비트에서 최상위 비트만 1, int로 보면 INT_MIN)
  • 0x10 = 16, 0x100 = 256, 0x400 = 1024, 0x1000 = 4096 (메모리 페이지 크기)
  • ASCII: '0' = 0x30, 'A' = 0x41, 'a' = 0x61, 공백 = 0x20

음수를 표현하는 세 가지 방법과 2의 보수

비트로 음수를 표현하는 방법은 역사적으로 세 가지가 있었습니다.

  1. 부호-크기(sign-magnitude): 최상위 비트(MSB)를 부호로 쓰고 나머지를 크기로 씁니다. 8비트에서 +5 = 00000101, -5 = 10000101. 사람에게는 직관적이지만 +0(00000000)과 -0(10000000)이 둘 다 존재하고, 덧셈 회로가 부호를 따로 처리해야 해서 복잡합니다.
  2. 1의 보수(ones' complement): 음수는 양수의 모든 비트를 뒤집습니다. -5 = 11111010. 여전히 +0과 -0(11111111)이 둘 다 있고, 덧셈 시 끝자리 올림(end-around carry)을 다시 더해야 합니다.
  3. 2의 보수(two's complement): 음수는 "모든 비트를 뒤집고 1을 더한" 값입니다. -5 = 11111010 + 1 = 11111011. 0이 하나뿐이고, 덧셈 회로 하나로 양수·음수 덧셈과 뺄셈을 모두 처리할 수 있습니다.

현대의 모든 범용 CPU는 2의 보수를 씁니다. C 표준은 C17까지 세 방식을 모두 허용했지만, C23부터 2의 보수만 허용하도록 바뀌었습니다. 실무에서는 "정수는 2의 보수"라고 가정해도 되지만, 그렇다고 오버플로가 정의되는 것은 아니라는 점(뒤에서 설명)을 꼭 기억해야 합니다.

그림 20-2는 4비트만으로 2의 보수를 보여 줍니다. 핵심은 세 가지입니다.

  • 최상위 비트(MSB)가 0이면 unsigned와 signed 해석이 같습니다.
  • MSB가 1이면 signed에서는 "unsigned 값 − 2N"입니다. 4비트에서 1011은 unsigned로 11이고, signed로는 11 − 16 = −5입니다. 다른 말로 MSB의 무게를 −2N−1로 보는 것입니다: 1011 = −8 + 0 + 2 + 1 = −5.
  • N비트 signed 범위는 −2N−1 ~ 2N−1−1로 비대칭입니다. 4비트는 −8~7, 8비트는 −128~127, 32비트는 −2147483648~2147483647입니다. 음수가 하나 더 많은 이유는 0이 "양수 쪽" 패턴(MSB=0)을 하나 차지하기 때문입니다.

왜 "뒤집고 1 더하기"가 음수일까?

N비트 레지스터는 2N에 도달하면 다시 0으로 돌아가는 "모듈러 2N" 세계입니다. 자동차의 주행거리계가 999999 다음에 000000이 되는 것과 같습니다. 이 세계에서 −x란 "x를 더하면 0이 되는 수"이므로 −x ≡ 2N − x입니다.

그런데 2N − x = (2N − 1 − x) + 1이고, 2N − 1은 "모든 비트가 1"이므로 거기서 x를 빼는 것은 x의 각 비트를 뒤집는 것과 같습니다(빌림이 전혀 생기지 않음). 따라서 −x = ~x + 1입니다.

이 방식의 위대함은 CPU가 덧셈기 하나만 있으면 된다는 점입니다. a − b는 a + (~b + 1)로 계산되고, signed든 unsigned든 같은 회로가 같은 비트 결과를 냅니다. 차이는 결과를 어떻게 해석하느냐(그리고 어떤 플래그—캐리 vs 오버플로—를 보느냐)뿐입니다.

마지막 줄이 흥미롭습니다. −128의 부호를 뒤집으면 +128이어야 하지만 8비트 signed에는 +128이 없어서 다시 −128이 됩니다. 이것이 "최솟값의 절댓값은 표현할 수 없다"는 2의 보수의 함정입니다. 그래서 abs(INT_MIN)과 -INT_MIN은 C에서 미정의 동작입니다. (위 예제에서는 ~x + 1이 int로 승격되어 +128로 계산된 뒤 int8_t로 축소되었으므로 UB는 아니고 구현 정의 변환이며, gcc는 하위 8비트를 그대로 취해 −128이 됩니다.)

자주 하는 실수 — 음수 금액의 절댓값

"환불 금액은 음수로 저장되어 있으니 llabs(amount)로 양수를 만들자"는 코드는 거의 항상 잘 동작합니다. 하지만 amount가 LLONG_MIN이라면(초기화 안 된 메모리, 잘못된 전문 파싱, 센티널 값 등) UB입니다. 실무에서는 절댓값을 구하기 전에 if (amount == LLONG_MIN) return ERR_RANGE;처럼 경계를 먼저 막습니다. 금액이 정상 범위(예: ±1경 원 이내)인지 검사하는 도메인 범위 검사를 함께 두면 이런 경계 값은 자연스럽게 걸러집니다.

정답과 해설 보기

(1) MSB가 1이므로 음수입니다. 방법 ①: unsigned로 읽으면 128+64+32+4+2 = 230이고, 230 − 256 = −26. 방법 ②: MSB 무게를 −128로 보면 −128+64+32+4+2 = −26. 방법 ③: 뒤집고 1 더하면 00011001 + 1 = 00011010 = 26이므로 원래 수는 −26.

(2) 42 = 32+8+2 = 00101010. 뒤집으면 11010101, 1을 더하면 11010110, 16진수로 0xD6입니다. 확인: 0xD6 = 214, 214 − 256 = −42.

부호 확장과 축소 변환

작은 타입의 정수를 큰 타입으로 옮길 때, 늘어난 상위 비트를 무엇으로 채울까요? 규칙은 간단합니다.

  • 원래 타입이 unsigned이면 상위 비트를 0으로 채웁니다. 이를 제로 확장(zero extension)이라 합니다.
  • 원래 타입이 signed이면 상위 비트를 원래 부호 비트(MSB)로 채웁니다. 이를 부호 확장(sign extension)이라 합니다.

부호 확장을 하는 이유는 값을 보존하기 위해서입니다. 8비트 −5(0xFB)를 32비트로 옮길 때 상위를 0으로 채우면 0x000000FB = 251이 되어 값이 바뀌지만, 1로 채우면 0xFFFFFFFB = −5로 값이 그대로입니다.

반대로 큰 타입을 작은 타입에 넣는 축소 변환(narrowing)은 어떨까요? 표준 규칙은 다음과 같습니다.

변환 대상값이 범위 안값이 범위 밖
unsigned 타입값 그대로정의됨: 2N으로 나눈 나머지(하위 N비트만 남김)
signed 타입값 그대로구현 정의(또는 구현 정의 시그널). gcc/clang은 하위 N비트를 그대로 취함

마지막 줄을 보십시오. 30억 원이 int로 들어가는 순간 −12억 9천여만 원이 되었습니다. 3000000000 − 4294967296 = −1294967296입니다. 컴파일러는 -Wconversion 옵션을 주지 않으면 이 축소를 경고조차 하지 않습니다.

은행 시스템에서는 — "21억의 벽" 사고

어느 금융회사의 법인 자금이체 모듈은 오래전 개인 고객 위주로 설계되어, 금액 필드를 int로 받아 처리하는 중간 함수가 하나 남아 있었습니다. 원장(ledger)과 전문은 모두 13~15자리 금액을 지원했지만, 수수료 계산용 보조 함수의 매개변수 하나만 int였습니다. 수년간 문제가 없다가, 한 법인 고객이 처음으로 25억 원을 이체하자 수수료 함수가 음수 금액을 받아 "수수료 0원"을 계산했고, 동일 패턴의 거래 수십 건이 수수료 없이 처리된 뒤에야 일마감 대사(reconciliation)에서 발견되었습니다.

교훈은 세 가지입니다. ① 금액은 모든 경로에서 int64_t(또는 long long)로 통일한다. ② -Wconversion -Wsign-conversion을 켜고 경고를 0으로 유지한다. ③ 테스트 데이터에 경계 값(231−1, 231, 232, 음수, 0)을 반드시 포함한다. 한국 원화는 단위가 커서 32비트의 한계(약 21억 원)에 생각보다 쉽게 닿습니다.

이렇게 해결합니다 — 축소 변환은 검사 후 명시적으로

그리고 빌드 옵션에 -Wall -Wextra -Wconversion -Wsign-conversion을 추가하면, 암묵적 축소가 일어나는 모든 지점이 경고로 드러납니다. 레거시 코드에서는 경고가 수천 개 나올 수 있으므로, 금액·수량·인덱스 관련 모듈부터 단계적으로 정리하는 것이 현실적입니다.

오버플로: signed는 미정의 동작, unsigned는 순환

이제 이 장의 가장 중요한 주제입니다. 정수 연산 결과가 타입의 범위를 넘어서면 어떻게 될까요? C 표준은 두 경우를 완전히 다르게 다룹니다.

구분표준의 규정의미
unsigned 연산결과는 2N으로 나눈 나머지(C11 6.2.5p9: "결코 오버플로하지 않는다")UINT_MAX + 1 == 0, 0u - 1 == UINT_MAX가 보장됨
signed 연산결과가 표현 범위를 넘으면 미정의 동작(UB)(C11 6.5p5)무슨 일이든 일어날 수 있음. 컴파일러는 "일어나지 않는다"고 가정하고 최적화

왜 signed 오버플로는 UB로 남겨 두었을까?

역사적 이유와 성능상 이유가 있습니다. C가 만들어질 당시에는 1의 보수·부호-크기 기계가 있었고, 오버플로 시 하드웨어 트랩을 일으키는 기계도 있었습니다. 표준이 특정 결과를 강제하면 그런 기계에서 C를 효율적으로 구현할 수 없었습니다.

오늘날 더 중요한 이유는 최적화입니다. "signed 오버플로는 일어나지 않는다"고 가정하면 컴파일러는 다음과 같은 변형을 할 수 있습니다.

  • x + 1 > x → 항상 참(1)으로 치환
  • (x * 2) / 2 → x로 치환
  • for (int i = 0; i <= n; i++) 반복 횟수가 정확히 n+1회라고 가정하고 루프를 벡터화. 64비트 기계에서 int i를 64비트 레지스터로 확장해 인덱스 계산을 단순화

이 가정이 틀리는 순간(실제로 오버플로가 일어나는 순간) 프로그램은 "작성한 소스 코드와 다른" 동작을 합니다. 특히 오버플로를 사후에 검사하는 코드가 통째로 사라지는 것이 실무에서 가장 위험합니다.

같은 소스인데 최적화 옵션만 바꿨더니 결과가 달라졌습니다. -O0에서는 하드웨어가 실제로 순환시킨 값을 비교해서 검사가 "우연히" 동작했지만, -O2에서는 컴파일러가 sum < a를 b < 0으로 바꾸거나 분기 자체를 지워 검사가 무력화되었습니다. 이것이 UB의 무서움입니다. 디버그 빌드에서는 테스트를 통과하고, 운영 빌드에서만 사고가 납니다.

이렇게 해결합니다 — 연산 "전에" 검사한다

오버플로 검사의 원칙은 단 하나입니다. UB가 일어날 연산을 실행하기 전에, 범위 안에서만 계산되는 식으로 조건을 확인합니다.

보조 수단으로 gcc/clang의 -fsanitize=signed-integer-overflow(UBSan)를 테스트 빌드에 켜 두면, 오버플로가 일어나는 순간 파일명과 줄 번호를 출력해 줍니다. -ftrapv는 오버플로 시 프로그램을 중단시키고, -fwrapv는 signed 오버플로를 "순환"으로 정의해 버립니다. 단 -fwrapv는 UB를 없애 줄 뿐 틀린 금액을 막아 주지는 않으므로 근본 해결책이 아닙니다.

unsigned는 순환이 보장되니 안전할까요? 아닙니다. 순환은 "정의된 동작"일 뿐 "올바른 금액"이 아닙니다. 금융에서 더 흔한 사고는 오히려 unsigned 쪽에서 납니다.

1,000원 있는 계좌에서 2,000원을 출금했는데 성공했고, 잔액이 약 43억 원이 되었습니다. 1000u - 2000u는 232 − 1000 = 4294966296으로 정의된 순환을 했고, unsigned 값은 정의상 0 이상이므로 >= 0 검사는 늘 참입니다. gcc는 -Wextra를 주면 "comparison of unsigned expression in '>= 0' is always true" 경고를 냅니다.

이렇게 해결합니다 — 비교는 뺄셈 없이, 금액은 signed 64비트로

금액에 unsigned를 쓰지 않는 이유는 "음수가 아닌 값"이라는 제약을 타입이 보장해 주지 않기 때문입니다. unsigned는 음수를 막는 것이 아니라 음수를 거대한 양수로 위장시킵니다. 차액·취소·환불·조정 금액처럼 금융에는 음수가 자연스럽게 등장하므로, 금액은 signed 64비트로 두고 비즈니스 규칙(잔액 ≥ 0)은 코드로 검사합니다.

정수 승격과 signed/unsigned 비교의 함정

C는 연산을 하기 전에 피연산자의 타입을 자동으로 맞춥니다. 이 규칙을 모르면 "분명 -1이 1보다 작은데 왜 거짓이지?" 같은 상황을 만나게 됩니다. 규칙은 두 단계입니다.

  1. 정수 승격(integer promotion): char, short, _Bool, 비트필드처럼 int보다 작은 타입은 연산에 쓰이기 전에 int로 바뀝니다(int로 모든 값을 표현할 수 있으면 int, 아니면 unsigned int). 그래서 uint8_t + uint8_t의 결과 타입은 int입니다.
  2. 일반 산술 변환(usual arithmetic conversions): 승격 후에도 두 피연산자의 타입이 다르면 하나로 맞춥니다. 핵심 규칙은 "순위(rank)가 같으면 unsigned가 이긴다"입니다. int와 unsigned int가 만나면 int 쪽이 unsigned int로 변환됩니다. 순위가 다르면 더 큰 쪽으로 가되, signed 쪽이 더 크고 unsigned의 모든 값을 담을 수 있으면 signed로, 아니면 그 signed 타입의 unsigned 버전으로 갑니다.

한 줄씩 원인을 짚어 보겠습니다.

  • (1) int와 unsigned int는 순위가 같으므로 −1이 unsigned로 변환되어 4294967295가 되고, 4294967295 < 1은 거짓입니다.
  • (2) 64비트 리눅스(LP64)에서 long은 8바이트라서 unsigned int(4바이트)의 모든 값을 담을 수 있습니다. 그래서 1u가 long으로 변환되고 −1 < 1은 참입니다. 그런데 64비트 윈도우(LLP64)에서는 long이 4바이트라서 long이 unsigned int의 모든 값을 담지 못하므로 둘 다 unsigned long으로 변환되고, 결과는 0이 됩니다. 같은 코드가 플랫폼마다 다른 결과를 내는 대표적 사례입니다.
  • (3) sizeof의 결과 타입 size_t는 unsigned long이므로 −1이 18446744073709551615로 변환됩니다.
  • (4) uint8_t 두 개를 더해도 결과는 int 300입니다. 8비트로 계산되지 않습니다.
  • (5) int 300을 uint8_t에 대입할 때 축소(300 mod 256 = 44)가 일어납니다.
  • (6) x86의 gcc에서 char는 signed라서 −24, ARM 리눅스의 gcc에서는 unsigned라서 232가 출력됩니다. 한글 EUC-KR/CP949 바이트(0x80 이상)를 char로 다루다가 if (c >= 0x80) 같은 검사가 항상 거짓이 되는 버그가 실무에서 자주 나옵니다. 바이트 데이터는 unsigned char나 uint8_t로 다루십시오.

왜 "%" PRId64 같은 이상한 모양일까?

PRId64는 문자열 리터럴로 정의된 매크로입니다. 리눅스 x86-64 glibc에서는 "ld", 윈도우에서는 "lld"(또는 구형 MSVC에서 "I64d")입니다. C에서 나란히 놓인 문자열 리터럴은 컴파일 시 하나로 합쳐지므로 "잔액: %" PRId64 "원\n"은 "잔액: %ld원\n"이 됩니다. 서식 문자열과 실제 인자 타입이 맞지 않으면 UB이므로, 이 매크로는 이식성과 안정성을 동시에 지켜 줍니다.

long long vs int64_t, 무엇을 써야 할까?

C99 이후 long long은 최소 64비트가 보장되고, 사실상 모든 플랫폼에서 정확히 64비트입니다. 이 과정의 PART 1에서 금액을 long long으로 쓴 것도 그 때문입니다. 실무 코딩 표준은 대개 "금액 타입을 typedef int64_t amount_t;처럼 별칭으로 정의하고 모든 모듈이 그 별칭만 쓰게" 합니다. 나중에 128비트나 십진 고정소수점 타입으로 바꿔야 할 때 한 곳만 고치면 되기 때문입니다.

오버플로 사전 검사 함수와 __builtin_add_overflow

이제 실무에서 그대로 쓸 수 있는 오버플로 검사 함수를 만들어 보겠습니다. 원칙은 앞에서 말한 대로 "연산 전에, 오버플로하지 않는 식으로" 검사하는 것입니다. 덧셈·뺄셈은 비교적 쉽고, 곱셈은 부호 조합 4가지를 나눠야 합니다(CERT C 규칙 INT32-C의 방식).

곱셈 검사에서 (-,-) 경우를 살펴보면, a < 0, b <= 0일 때 결과는 0 이상이므로 a * b > INT64_MAX인지 봐야 합니다. 양변을 음수 a로 나누면 부등호가 뒤집혀 b < INT64_MAX / a가 됩니다. MIN x -1은 이 경로에서 INT64_MAX / INT64_MIN이 0(정수 나눗셈은 0쪽으로 절사)이므로 -1 < 0이 참이 되어 오버플로로 판정됩니다. 이렇게 경계를 하나하나 증명하며 코드를 짜는 습관이 금융 개발자의 기본기입니다.

컴파일러 내장 함수와 C23 표준

gcc 5 이상과 clang은 __builtin_add_overflow(a, b, &r), __builtin_sub_overflow, __builtin_mul_overflow를 제공합니다. 무한 정밀도로 계산한 수학적 결과를 r의 타입에 넣고, 들어가지 않으면 true를 반환합니다(반환값 의미가 위 함수와 반대인 점에 주의). CPU의 오버플로 플래그를 직접 이용하므로 손으로 짠 검사보다 빠르고, 타입이 섞여도 정확합니다. C23에는 이것이 <stdckdint.h>의 ckd_add, ckd_sub, ckd_mul로 표준화되었습니다. MSVC에는 이 내장 함수가 없으므로, 이식성이 필요하면 위의 수동 검사 버전을 폴백으로 두고 매크로로 분기합니다.

500조 × 35000 = 1.75 × 1019은 INT64_MAX(약 9.22 × 1018)를 넘습니다. 최종 이자(17.5조 원)는 int64에 충분히 들어가는데도 중간 결과가 넘친 것입니다. 금리 계산은 "곱한 뒤 나누기" 구조라 중간 값이 커지기 쉽습니다. 21장에서 이를 해결하는 기법(__int128, 몫·나머지 분할)을 자세히 다룹니다.

은행 시스템에서는 — 합계 검증은 마지막 방어선

일마감 배치는 수백만 개 계좌의 잔액·거래액을 합산해 총계정원장과 대사합니다. 한 증권사의 정산 배치는 "체결 수량 × 단가"를 int로 계산하는 부분이 있었는데, 특정 종목의 거래량이 폭증한 날 중간 곱셈이 넘쳐 음수가 되었습니다. 다행히 "원장 합계 = 거래 합계 + 전일 잔액" 검증 단계에서 불일치가 잡혀 배치가 중단되었고, 코드를 고쳐 재처리로 마무리되었습니다.

실무 원칙: ① 모든 누적·곱셈에 오버플로 검사 함수 사용, ② 오버플로 발생 시 "조용히 계속"하지 말고 배치를 실패시키고 알람, ③ 결과에 대한 독립적 교차 검증(건수 합계, 차변·대변 합계 일치)을 둔다. 오버플로 검사는 1차 방어선, 대사는 마지막 방어선입니다.

자주 하는 실수 — 논리 연산자와 비트 연산자 혼동, 우선순위

  • &&/||는 결과가 0 또는 1인 논리 연산이고 단락 평가를 합니다. &/|는 비트 연산이고 양쪽을 모두 평가합니다. if (flags && AF_SEIZED)는 "flags가 0이 아니고 AF_SEIZED가 0이 아니면" 참이라 압류가 아닌 계좌도 차단됩니다.
  • 비트 연산자는 비교 연산자보다 우선순위가 낮습니다. if (flags & AF_SEIZED == 0)은 flags & (AF_SEIZED == 0) = flags & 0 = 항상 0으로 해석됩니다. 반드시 if ((flags & AF_SEIZED) == 0)처럼 괄호를 칩니다. gcc -Wparentheses(-Wall에 포함)가 경고합니다.

시프트 연산과 미정의 동작

x << n은 비트를 왼쪽으로 n칸 밀고 빈자리를 0으로 채웁니다. 수학적으로 x × 2n입니다. x >> n은 오른쪽으로 밀며, unsigned이면 빈자리를 0으로 채우는 논리 시프트, 음수 signed이면 구현 정의인데 대부분의 컴파일러는 부호 비트로 채우는 산술 시프트를 합니다.

시프트에는 UB 함정이 많습니다. C11 6.5.7 기준으로 다음은 모두 미정의 동작입니다.

  • 시프트 횟수가 음수이거나, 승격된 왼쪽 피연산자의 비트 수 이상인 경우: 1u << 32(unsigned int 32비트), x >> -1. x86 CPU는 시프트 횟수의 하위 5비트만 쓰므로 1u << 32가 1이 되는 것을 흔히 보지만, 컴파일러가 상수로 접을 때는 0이 나오기도 합니다. 결과를 믿으면 안 됩니다.
  • 음수 signed 값의 왼쪽 시프트: -1 << 1.
  • signed 값을 왼쪽 시프트한 결과가 표현 범위를 넘는 경우: 1 << 31(int 32비트). 231은 int로 표현할 수 없기 때문입니다. 플래그 상수를 1 << 31로 정의한 코드가 아주 많은데, 엄밀히는 UB이므로 1u << 31 또는 UINT32_C(1) << 31로 씁니다.

0x3A7F의 하위 12비트는 0xA7F = 10×256 + 7×16 + 15 = 2687입니다. "시프트로 내리고, 마스크로 자른다"는 필드 추출 패턴은 전문 헤더 파싱, 상태 코드 해석, 해시 계산에서 끝없이 등장합니다.

왜 x >> 1과 x / 2는 음수에서 다를까?

C99부터 정수 나눗셈은 0쪽으로 절사하도록 정해졌습니다. −7 / 2 = −3입니다. 반면 산술 오른쪽 시프트는 음의 무한대 쪽으로 내림합니다. −7(…11111001) >> 1 = …11111100 = −4입니다. 그래서 컴파일러는 signed x / 2를 단순 시프트 하나로 바꾸지 못하고, 음수일 때 1을 더해 보정하는 명령을 추가합니다. 금액을 2로 나누는 코드를 "빠르게 하려고" >> 1로 바꾸면 음수 금액(환불·취소)에서 1원 차이가 나는 버그가 생깁니다. 최적화는 컴파일러에 맡기고, 의도를 드러내는 연산을 쓰십시오.

마스크와 비트 조작 매크로

마스크(mask)란 관심 있는 비트 자리만 1로 표시한 정수입니다. 가면(mask)처럼 원하는 부분만 드러내거나 가린다는 뜻입니다. 네 가지 기본 조작은 다음과 같습니다.

조작식원리
세트(켜기)f |= mx | 1 = 1, x | 0 = x → 마스크 자리만 1로
해제(끄기)f &= ~mx & 0 = 0, x & 1 = x → 마스크 자리만 0으로
토글(뒤집기)f ^= mx ^ 1 = ~x, x ^ 0 = x → 마스크 자리만 반전
검사(하나라도)(f & m) != 0마스크 자리 중 1이 하나라도 있으면 참
검사(모두)(f & m) == m마스크 자리가 전부 1이면 참

자주 하는 실수 — ~ 의 폭과 마스크 타입

uint64_t f; f &= ~0x10;은 괜찮습니다. 0x10은 int이고 ~0x10은 int −17(…11101111)이며, uint64_t로 변환될 때 부호 확장되어 상위 비트도 1이기 때문입니다. 그러나 f &= ~0x10u;는 버그입니다. ~0x10u는 unsigned int 0xFFFFFFEF이고 64비트로 제로 확장되어 0x00000000FFFFFFEF가 되므로, f의 상위 32비트가 전부 지워집니다. 마스크 상수는 대상 변수와 같은 폭으로 정의하는 것이 원칙입니다(UINT64_C(0x10)).

계좌 상태 플래그 설계

이제 실전입니다. 계좌 원장 레코드에 32비트 상태 플래그를 두고, 출금 가능 여부를 판정하는 모듈을 만들어 보겠습니다. 먼저 비트 배치를 설계합니다. 실무에서는 이 배치표가 설계 문서와 DB 컬럼 정의서에 그대로 들어가는 계약이므로, 한 번 정한 비트 번호는 절대 재사용하거나 바꾸지 않습니다.

왜 토글은 상태 관리에 위험할까?

예제에서는 설명을 위해 휴면 전환에 FLAG_TGL을 썼지만, 실무에서 상태 변경에 토글을 쓰는 것은 위험합니다. 같은 "휴면 전환" 요청이 네트워크 재전송 등으로 두 번 처리되면, 토글은 휴면 → 정상으로 되돌려 버립니다. 반면 FLAG_SET은 몇 번을 실행해도 결과가 같습니다. 이런 성질을 멱등성(idempotency)이라고 하며, 재처리·재전송이 일상인 금융 시스템에서는 상태 변경 연산을 멱등하게 설계하는 것이 원칙입니다. 토글은 "화면 체크박스 반전"처럼 의도가 명확히 반전일 때만 씁니다.

은행 시스템에서는 — 비트 재사용 사고

어느 금융기관의 고객 상태 플래그에서 bit 6은 원래 "이전 시스템의 특수 계좌" 표시였는데, 해당 기능이 폐지되면서 몇 년 뒤 다른 팀이 bit 6을 "해외 거래 차단"으로 재사용했습니다. 문제는 오래된 계좌 수만 개에 옛날 의미의 bit 6이 지워지지 않은 채 남아 있었다는 것입니다. 시스템 오픈 직후 해당 고객들의 해외 결제가 일제히 거절되었고, 콜센터 민원이 폭주했습니다.

교훈: ① 비트 배치는 코드 테이블(설계 문서)로 관리하고, 폐지된 비트는 "폐기(재사용 금지)"로 표시합니다. ② 새 비트를 도입할 때는 기존 데이터에서 해당 비트가 모두 0인지 사전 데이터 점검을 합니다. ③ 상태 변경은 반드시 변경 이력(이전값·이후값·변경자·사유)을 남겨 추적 가능하게 합니다.

권한 비트와 유용한 비트 기법

단말 사용자(창구 직원, 책임자, 관리자)의 권한도 비트로 표현하기 좋습니다. 역할(role)은 권한 비트의 OR 조합으로 정의하고, 어떤 거래를 실행하려면 필요한 권한이 모두 있어야 합니다.

선임직원은 취소 권한(0x04)은 있지만 책임자 승인 권한(0x08)이 없습니다. (have & need) != 0 방식은 "필요한 권한 중 하나라도 있으니 허용"으로 판정해 버려, 승인 없는 취소가 가능해집니다. 권한 검사에는 반드시 (have & need) == need를 쓰십시오.

은행 시스템에서는 — 4-eyes 원칙과 권한 분리

금융권 내부통제의 기본은 "한 사람이 거래를 만들고 승인까지 하지 못하게" 하는 직무 분리(4-eyes principle)입니다. 권한 비트만으로는 부족하고, "승인자 ID ≠ 입력자 ID" 같은 규칙이 함께 검사되어야 합니다. 또한 권한 비트 정의는 보통 중앙 권한관리 시스템의 코드 테이블에서 내려받으므로, 애플리케이션이 하드코딩한 비트 값과 테이블 값이 어긋나지 않도록 기동 시 검증(self-check)하는 루틴을 두기도 합니다.

비트필드와 이식성 문제

C는 구조체 멤버를 비트 단위 크기로 선언하는 비트필드(bit-field)를 제공합니다. 마스크와 시프트 없이 멤버 이름으로 접근할 수 있어 편리해 보입니다.

trap이 −1이 된 이유는, gcc에서 int 비트필드가 signed로 취급되고 1비트 signed 2의 보수의 표현 범위가 −1~0뿐이기 때문입니다. (plain int 비트필드가 signed인지 unsigned인지조차 구현 정의입니다.) 그 밖에도 비트필드에는 이식성 문제가 많습니다.

이렇게 해결합니다 — 외부 교환 데이터에는 비트필드 대신 명시적 마스크

비트필드는 한 프로그램 내부에서만 쓰는 메모리 절약용으로 한정하고, 전문·파일·DB·공유메모리처럼 다른 프로그램이나 다른 기계와 주고받는 데이터에는 고정폭 unsigned 정수 + 명시적 마스크·시프트(앞의 FIELD_GET32/FIELD_SET32)를 씁니다. 그러면 비트 위치가 소스 코드에 숫자로 못 박혀 플랫폼과 무관해집니다. 또 바이트 순서는 24장에서 배울 엔디안 변환 함수로 따로 맞춥니다.

패리티와 체크섬 입문

비트 연산의 또 다른 큰 쓰임새는 데이터 무결성 검사입니다. 통신 회선이나 저장 매체에서 비트가 뒤집히거나, 사람이 숫자를 잘못 입력하는 오류를 찾아내기 위해 원본 데이터로부터 짧은 검사 값을 계산해 함께 보냅니다.

  • 패리티 비트: 1의 개수가 짝수(짝수 패리티)가 되도록 1비트를 덧붙입니다. 비트 하나가 뒤집히면 개수의 홀짝이 바뀌어 검출됩니다. 두 비트가 동시에 뒤집히면 검출하지 못합니다.
  • XOR 체크섬(LRC, 종단 중복 검사): 모든 바이트를 XOR한 1바이트. 일부 레거시 단말·직렬 통신 프로토콜에서 씁니다. 구현이 간단하지만, 같은 바이트가 두 번 바뀌거나 바이트 순서가 바뀌면 검출하지 못합니다.
  • 합계 체크섬: 바이트를 더한 값의 하위 8/16비트. 역시 순서 바뀜을 못 잡습니다.
  • CRC(순환 중복 검사): 다항식 나눗셈 기반. 연속 오류(burst)에 강해 네트워크(이더넷 CRC-32), 압축 파일, 저장장치에서 표준으로 씁니다.
  • 검증번호(check digit): 카드번호의 마지막 자리(Luhn 알고리즘), 계좌번호·사업자번호·주민등록번호의 검증 자리처럼, 사람이 한 자리를 잘못 입력하거나 인접한 두 자리를 바꿔 쓰는 실수를 잡기 위한 장치입니다.

체크섬은 보안 장치가 아니다

패리티·체크섬·CRC는 우연한 오류를 찾는 장치입니다. 악의적인 공격자는 데이터를 바꾼 뒤 체크섬을 다시 계산해 붙이면 그만입니다. 위·변조 방지에는 HMAC, 전자서명 같은 암호학적 기법(22장)을 써야 합니다.

왜 XOR 접기로 패리티가 구해질까?

XOR은 "1의 개수가 홀수면 1"인 연산입니다. 8비트를 한 번에 XOR하는 대신, 상위 4비트와 하위 4비트를 겹쳐 XOR하면 하위 4비트에 "각 쌍의 홀짝"이 남습니다. 이를 다시 2비트, 1비트로 반복하면 최하위 비트에 전체 8비트의 홀짝이 모입니다. 루프 없이 3번의 연산으로 끝나므로 빠릅니다. 같은 원리로 32비트는 5번(16, 8, 4, 2, 1)이면 됩니다. gcc에는 __builtin_parity도 있습니다.

은행 시스템에서는 — 검증번호는 입력 단계의 첫 필터

카드 결제 승인 요청이 들어오면, 승인 서버는 DB를 조회하기 전에 카드번호 길이·숫자 여부·BIN(발급사 식별 앞자리)·Luhn 검증을 먼저 수행해 명백히 잘못된 번호를 걸러 냅니다. 이렇게 하면 오타 입력에 대한 불필요한 DB 조회와 대외기관 전송을 줄이고, 무작위 번호를 대입하는 공격 트래픽도 앞단에서 상당 부분 차단할 수 있습니다. 계좌번호도 기관마다 자체 검증번호 규칙을 두는 경우가 많아, 이체 화면에서 "존재하지 않는 계좌" 조회 전에 형식 오류를 먼저 알려 줍니다. 단, 검증번호를 통과했다고 실제 존재하는 번호라는 뜻은 아니라는 점을 기억하십시오.

예제 20-6 난이도 ★★☆

Luhn 검증번호를 생성하는 함수 int luhn_check_digit(const char *body)를 작성하십시오. 검증번호를 뺀 앞부분 숫자열을 받아, 붙여야 할 마지막 한 자리(0~9)를 반환합니다. "7992739871"을 넣으면 3이 나와야 합니다.

정답과 해설 보기

검증번호가 붙으면 body의 각 자리는 오른쪽에서 한 칸씩 밀립니다. 따라서 body의 가장 오른쪽 자리부터 2배를 적용합니다(검증 함수에서의 k가 1, 3, 5…인 자리). 합계를 S라 하면 검증번호 c는 (S + c) mod 10 = 0을 만족해야 하므로 c = (10 − S mod 10) mod 10입니다. "7992739871"의 S = 67(그림 20-10의 합계 70에서 검증번호 3을 뺀 값)이므로 c = (10 − 7) mod 10 = 3입니다.

핵심 정리

  • 16진수 한 자리는 정확히 4비트입니다. 덤프·전문 로그를 읽는 기본 도구이며, 0x7FFFFFFF(INT_MAX), 0x80000000, 0xFF 같은 값은 외워 둡니다.
  • 2의 보수에서 −x = ~x + 1이고, MSB의 무게는 −2N−1입니다. 범위는 비대칭(−2N−1 ~ 2N−1−1)이라 -INT_MIN, abs(INT_MIN)은 UB입니다. C23부터 2의 보수가 표준으로 강제됩니다.
  • 작은 signed 타입을 넓힐 때는 부호 확장, unsigned는 제로 확장이 일어납니다. 좁힐 때 unsigned는 mod 2N(정의됨), signed는 구현 정의입니다. 축소는 범위 검사 후 명시적 캐스트로 합니다.
  • signed 오버플로는 미정의 동작입니다. 컴파일러는 그것이 일어나지 않는다고 가정하고 최적화하므로 "사후 검사"가 사라질 수 있습니다. 반드시 연산 전에 검사하거나 __builtin_*_overflow/ckd_*를 씁니다.
  • unsigned는 순환이 정의되어 있을 뿐 금액으로서는 틀린 값입니다. 금액은 int64_t로 두고, 잔액 비교는 뺄셈 없이 balance < amount처럼 합니다.
  • int보다 작은 타입은 연산 전에 int로 승격되고, 같은 순위의 signed/unsigned가 만나면 unsigned로 변환됩니다(-1 < 1u는 거짓). -Wall -Wextra -Wconversion -Wsign-conversion을 켭니다.
  • 크기가 중요한 데이터는 <stdint.h> 고정폭 타입, 출력은 <inttypes.h>의 PRId64 등을 씁니다. 바이트 데이터는 unsigned char/uint8_t로 다룹니다.
  • 비트 조작 4종: 세트 |=, 해제 &= ~, 토글 ^=, 검사 &. 비트 연산자는 비교 연산자보다 우선순위가 낮으므로 괄호를 칩니다. 권한은 (have & need) == need로 검사합니다.
  • 시프트 횟수가 음수이거나 폭 이상이면 UB, 음수의 왼쪽 시프트와 1 << 31도 UB입니다. 마스크 상수는 대상과 같은 폭의 unsigned로 정의합니다(UINT32_C(1) << n).
  • 상태 플래그의 비트 번호는 DB·전문과 공유되는 계약이므로 재사용하지 않고, 상태 변경은 멱등한 세트/해제로 하며 이력을 남깁니다.
  • 비트필드의 배치·부호·경계 처리는 구현 정의라서 외부와 교환하는 데이터에는 쓰지 않습니다. 명시적 마스크·시프트로 대신합니다.
  • 패리티·LRC·합계·CRC·검증번호(Luhn)는 우연한 오류 검출용이고, 위·변조 방지에는 암호학적 기법이 필요합니다.

Q1. 컴퓨터는 왜 음수를 2의 보수로 표현합니까?

2의 보수는 0의 표현이 하나뿐이고, 덧셈 회로 하나로 양수·음수의 덧셈과 뺄셈을 모두 처리할 수 있기 때문입니다. N비트 레지스터는 모듈러 2N 산술을 하므로 −x를 2N−x로 두면 x + (−x) = 2N ≡ 0이 자연스럽게 성립하고, 이는 비트 반전 후 1을 더하는 것과 같습니다. 그래서 뺄셈 a − b를 a + ~b + 1로 계산할 수 있어 하드웨어가 단순해집니다.

꼬리 질문 대비: "8비트 signed 범위가 왜 −128~127로 비대칭인가?" → 0이 MSB=0인 패턴 하나를 차지하므로 양수 쪽이 하나 적습니다. 그래서 최솟값의 부호를 바꾸면 표현할 수 없습니다.

Q2. signed 정수 오버플로와 unsigned 정수 오버플로의 차이를 설명해 주십시오.

C 표준에서 unsigned 연산은 결과가 2N으로 나눈 나머지로 정의되어 있어 순환이 보장됩니다. 반면 signed 연산의 결과가 표현 범위를 벗어나면 미정의 동작입니다. 컴파일러는 signed 오버플로가 없다고 가정하고 x + 1 > x를 항상 참으로 바꾸는 등 최적화하므로, 오버플로 후에 검사하는 코드가 제거될 수 있습니다. 따라서 연산 전에 a > INT_MAX − b 같은 식으로 검사해야 합니다.

꼬리 질문 대비: "-fwrapv를 쓰면 해결되나?" → UB는 없어지지만 값이 틀린 것은 그대로라서, 금액 계산에서는 여전히 검사가 필요합니다. 테스트에는 UBSan(-fsanitize=undefined)을 씁니다.

Q3. -1 < 1u의 결과는 무엇이고 왜 그렇습니까?

결과는 0(거짓)입니다. int와 unsigned int는 순위가 같으므로 일반 산술 변환에 의해 int −1이 unsigned로 변환되어 UINT_MAX(4294967295)가 됩니다. 그래서 4294967295 < 1을 비교하게 됩니다. 비슷하게 sizeof 결과(size_t)와 음수를 비교하는 코드, 역방향 size_t 루프에서 버그가 자주 납니다.

꼬리 질문 대비: "-1L < 1u는?" → 64비트 리눅스(LP64)에서는 long이 unsigned int를 모두 표현할 수 있어 참, 64비트 윈도우(LLP64)에서는 long이 32비트라 둘 다 unsigned long으로 변환되어 거짓입니다.

Q4. 비트 연산으로 n번째 비트를 켜고, 끄고, 뒤집고, 검사하는 방법과 2의 거듭제곱 판정법을 말해 보십시오.

켜기는 x |= 1u << n, 끄기는 x &= ~(1u << n), 뒤집기는 x ^= 1u << n, 검사는 (x >> n) & 1u 또는 (x & (1u << n)) != 0입니다. 2의 거듭제곱은 1비트가 하나뿐이므로 x != 0 && (x & (x − 1)) == 0으로 판정합니다. x & (x−1)은 가장 낮은 1비트를 지우는 연산이기 때문입니다.

꼬리 질문 대비: "1을 그냥 1 << n으로 쓰면?" → int에서 n이 31이면 UB, 64비트 변수에서 n ≥ 32면 UB이므로 대상 타입과 같은 폭의 unsigned 상수를 써야 합니다.

Q5. 산술 시프트와 논리 시프트의 차이는? x >> 1과 x / 2는 같습니까?

논리 시프트는 빈자리를 0으로, 산술 시프트는 부호 비트로 채웁니다. C에서 unsigned의 오른쪽 시프트는 논리 시프트이고, 음수 signed의 오른쪽 시프트는 구현 정의인데 대부분 산술 시프트입니다. 양수에서는 x >> 1과 x / 2가 같지만, 음수에서는 나눗셈이 0쪽으로 절사(−7/2 = −3)하고 산술 시프트는 내림(−7>>1 = −4)이라 다릅니다.

꼬리 질문 대비: "그럼 컴파일러는 /2를 어떻게 최적화하나?" → 음수일 때 1을 더해 보정한 뒤 시프트하는 명령열로 바꿉니다. 개발자가 직접 바꿀 필요가 없습니다.

Q6. 금액(잔액)을 unsigned 타입으로 저장하면 안 되는 이유는 무엇입니까?

unsigned는 음수를 막아 주는 것이 아니라, 음수가 될 연산 결과를 거대한 양수로 바꿔 버립니다. 예를 들어 잔액 1000에서 2000을 빼면 약 43억이 되고, balance − amount >= 0 같은 검사는 항상 참이 되어 잔액 검사가 무력화됩니다. 또 금융에는 취소·환불·차액처럼 음수가 자연스러운 값이 많고, signed와 섞이면 비교 함정이 생깁니다. 그래서 금액은 int64_t로 두고 "잔액 ≥ 0"은 비즈니스 규칙으로 검사합니다.

꼬리 질문 대비: "그럼 unsigned는 언제 쓰나?" → 비트 플래그, 해시 값, 바이트 버퍼, 체크섬처럼 순환이나 비트 연산 자체가 의미인 데이터에 씁니다.

Q7. 비트필드의 장단점은 무엇이고, 통신 전문 구조체에 써도 됩니까?

장점은 메모리를 아끼고 멤버 이름으로 비트에 접근할 수 있다는 점입니다. 단점은 저장 단위 안의 배치 순서, plain int 비트필드의 부호, 경계 걸침 처리가 모두 구현 정의라서 컴파일러·엔디안에 따라 메모리 모양이 다르고, 주소를 얻을 수 없으며, 인접 필드 동시 수정 시 데이터 경쟁이 생긴다는 점입니다. 그래서 전문처럼 외부와 교환하는 데이터에는 쓰지 않고, 고정폭 정수와 명시적 마스크·시프트를 씁니다.

Q8. 정수 오버플로를 어떻게 검출합니까? 곱셈은 어떻게 검사합니까?

덧셈은 b > 0 && a > MAX − b 또는 b < 0 && a < MIN − b를 먼저 검사합니다. 곱셈은 부호 조합 네 가지로 나눠 a > MAX / b 같은 나눗셈 기반 비교를 합니다. gcc/clang에서는 __builtin_mul_overflow가 하드웨어 오버플로 플래그를 써서 더 빠르고 정확하며, C23에서는 <stdckdint.h>의 ckd_mul로 표준화되었습니다.

꼬리 질문 대비: "곱한 뒤 나눠서 원래 값이 나오는지 보면 안 되나?" → signed에서는 곱셈 자체가 이미 UB라 검사가 의미 없습니다. unsigned에서는 가능하지만 0 나눗셈을 따로 처리해야 합니다.

Q9. 체크섬, CRC, 암호학적 해시의 차이는 무엇입니까?

체크섬(합계, XOR)은 계산이 가장 간단하지만 바이트 순서 바뀜 같은 오류를 놓칩니다. CRC는 다항식 나눗셈 기반으로 연속 비트 오류 검출 능력이 뛰어나 통신·저장장치에 쓰입니다. 둘 다 우연한 오류만 잡으며, 공격자가 데이터를 바꾸고 값을 재계산하면 막지 못합니다. SHA-256 같은 암호학적 해시는 충돌을 찾기 어렵게 설계되었고, 키를 섞은 HMAC이나 전자서명을 써야 위·변조를 막을 수 있습니다.

Q10. char는 signed입니까, unsigned입니까?

구현 정의입니다. x86의 gcc·MSVC에서는 보통 signed, ARM 리눅스의 gcc에서는 unsigned입니다. 그래서 0x80 이상인 한글 바이트를 char로 다루면 플랫폼에 따라 음수가 되어 비교나 배열 인덱스에서 버그가 납니다. 바이트 데이터는 unsigned char/uint8_t를 쓰고, isdigit 등에 넘길 때는 (unsigned char)로 캐스트해야 합니다(음수를 넘기면 UB).

첫 빈칸은 n >= 32, 둘째 빈칸은 (f >> n) & 1u입니다. 범위 검사를 먼저 하는 이유는 32 이상의 시프트가 UB이기 때문입니다. f & (1u << n)을 그대로 반환하면 0/1이 아니라 해당 비트의 값(예: 0x80000000)이 나오고, 이를 int로 바꾸면 구현 정의 변환이 일어나므로 시프트 후 & 1u가 깔끔합니다.

연습문제 20-4 난이도 ★★☆ 버그 찾기

다음 코드는 압류되지 않은 계좌만 출금을 허용하려는 의도입니다. 버그를 모두 찾고 고치십시오.

#define AF_SEIZED 0x02
if (acct->flags & AF_SEIZED == 0 && acct->flags && AF_LIMITED == 0)
    do_withdraw(acct, amount);
정답과 해설 보기

① ==가 &보다 우선순위가 높아 flags & (AF_SEIZED == 0) = flags & 0 = 0이 되어 출금이 절대 일어나지 않습니다. ② acct->flags && AF_LIMITED == 0은 논리 AND이며 역시 우선순위 문제로 flags && (AF_LIMITED == 0)이 됩니다. ③ 한도제한계좌는 "금지"가 아니라 "추가 한도 검사" 대상이라는 업무 규칙도 반영되지 않았습니다.

연습문제 20-5 난이도 ★★☆ 버그 찾기

uint64_t flags = 0;
flags |= 1 << 40;          /* bit40: 해외 결제 차단 */
flags &= ~0x8u;            /* bit3 해제 */
정답과 해설 보기

① 1 << 40에서 1은 32비트 int이므로 시프트 횟수가 폭 이상이라 UB입니다. 대입 대상이 64비트여도 연산은 우변 타입에서 일어납니다. UINT64_C(1) << 40으로 고칩니다. ② ~0x8u는 32비트 0xFFFFFFF7이고 64비트로 제로 확장되어 0x00000000FFFFFFF7이 되므로, bit3과 함께 상위 32비트(bit40 포함)가 전부 지워집니다. flags &= ~UINT64_C(0x8);로 고칩니다.

연습문제 20-6 난이도 ★★☆ 코드 작성 — 상태 변경 이력

계좌 상태 플래그가 old에서 new로 바뀌었을 때 새로 켜진 비트, 새로 꺼진 비트, 변경된 비트를 구하는 함수를 작성하고, old=0x0B, new=0x26일 때 결과를 쓰십시오.

정답과 해설 보기

변경된 비트는 old ^ new, 켜진 비트는 "전에는 0, 지금은 1"이므로 ~old & new, 꺼진 비트는 old & ~new입니다.

old = 0000 1011, new = 0010 0110. changed = 0010 1101 = 0x2D, on = 0010 0100 = 0x24(휴면, 분실신고), off = 0000 1001 = 0x09(거래정지, 한도제한). 확인: on | off = changed.

연습문제 20-7 난이도 ★★☆ 코드 작성 — 필드 추출과 조립

16비트 응답 코드의 형식이 [상위 3비트: 채널][다음 5비트: 업무구분][하위 8비트: 결과코드]입니다. 0xA5C3을 분해한 값을 쓰고, 채널·업무·결과를 받아 코드를 조립하는 함수를 작성하십시오.

정답과 해설 보기

0xA5C3 = 1010 0101 1100 0011. 채널 = 상위 3비트 101 = 5, 업무 = 다음 5비트 00101 = 5, 결과 = 0xC3 = 195.

조립할 때 범위 검사를 하지 않으면 큰 값이 이웃 필드를 침범합니다. 예를 들어 biz=40을 넣으면 40 << 8의 상위 비트가 채널 필드로 넘어갑니다.

연습문제 20-8 난이도 ★★☆ 코드 작성 — 오버플로 없는 평균

0 이상인 두 금액 a, b(int64_t)의 평균(소수점 이하 버림)을 오버플로 없이 구하는 함수를 작성하십시오. (a + b) / 2는 왜 위험합니까?

정답과 해설 보기

a + b가 INT64_MAX를 넘으면 signed 오버플로 UB입니다(이진 탐색의 중간값 버그로도 유명합니다). 두 값이 모두 0 이상이면 a + (b - a) / 2는 오버플로는 없지만, a > b일 때 음수 나눗셈이 0쪽으로 절사되어 결과가 올림 쪽으로 나옵니다(예: a=8, b=7 → 8, 버림 평균은 7). 다음처럼 몫과 나머지를 나눠 계산하면 순서와 무관하게 정확합니다.

a/2, b/2는 각각 최대 INT64_MAX/2라 합이 넘지 않고, 나머지 합(0~2)/2로 둘 다 홀수인 경우 1을 보정합니다. 예: a=7, b=9 → 3 + 4 + (1+1)/2 = 8.

정답과 해설 보기

내장 함수는 결과를 무한 정밀도로 계산한 뒤 s의 타입에 넣고, 들어가지 않으면 true를 반환합니다. 실패 시 *sum을 바꾸지 않는 것은 "실패하면 출력 인자를 오염시키지 않는다"는 좋은 API 습관입니다. 음수(취소 거래)가 섞여 있어도 정확하게 검사됩니다.

연습문제 20-10 난이도 ★★☆ 금융 응용 — 토글의 위험

압류 해제 전문 처리에서 f ^= AF_SEIZED;를 썼습니다. 어떤 상황에서 사고가 납니까? 올바른 코드와 추가로 필요한 처리를 쓰십시오.

정답과 해설 보기

① 같은 해제 전문이 타임아웃 후 재전송되어 두 번 처리되면, 첫 번째에 해제되고 두 번째에 다시 압류됩니다. ② 이미 해제된(압류 아님) 계좌에 해제 전문이 오면 오히려 압류가 걸립니다. 상태 변경은 멱등해야 하므로 f &= ~AF_SEIZED;를 씁니다. 추가로, 전문 일련번호로 중복 처리 여부를 검사하고, 해제 전 상태가 압류가 아니었다면 경고 로그를 남기며, 변경 이력(이전값·이후값·처리자·근거 문서 번호)을 기록합니다.

연습문제 20-11 난이도 ★★☆ 코드 작성 — 짝수 패리티 바이트

7비트 ASCII 문자 c(0~127)를 받아, 최상위 비트(bit7)에 짝수 패리티 비트를 붙인 바이트를 돌려주는 함수를 작성하고, 'A'(0x41)와 'C'(0x43)의 결과를 쓰십시오.

정답과 해설 보기

짝수 패리티: 전체 8비트의 1 개수가 짝수가 되도록 bit7을 정합니다. 즉 하위 7비트의 1 개수가 홀수면 bit7=1입니다. 0x41 = 100 0001 → 1이 2개(짝수) → bit7=0 → 0x41. 0x43 = 100 0011 → 3개(홀수) → bit7=1 → 0xC3.

연습문제 20-12 난이도 ★★★ 서술 — 설계 리뷰

신입 개발자가 대외기관과 주고받을 전문의 상태 영역을 다음과 같이 설계했습니다. 리뷰 의견을 세 가지 이상 쓰십시오.

struct tx_status {
    int approved : 1;
    int retry    : 3;
    unsigned int amount : 28;   /* 거래 금액(원) */
};
/* send(sock, &st, sizeof st, 0); 으로 그대로 전송 */
정답과 해설 보기
  1. 비트필드를 전문에 사용: 배치 순서·패딩이 구현 정의라서 상대 시스템(다른 컴파일러·엔디안)이 같은 비트를 읽는다는 보장이 없습니다. 전문 명세에 바이트 단위로 정의하고 명시적으로 직렬화해야 합니다.
  2. int approved : 1: plain int 비트필드는 부호가 구현 정의이며, gcc에서는 1을 넣으면 −1이 됩니다. approved == 1 비교가 실패합니다. unsigned로 선언해야 합니다.
  3. int retry : 3: signed라면 −4~3만 표현되어 재시도 횟수 4 이상이 음수가 됩니다.
  4. 금액 28비트: 최대 228−1 = 268,435,455원(약 2.7억 원)이라 법인 거래를 담지 못합니다. 금액은 64비트 또는 전문 표준의 숫자 문자열 필드로 정의해야 합니다.
  5. 구조체 통째 전송: 바이트 순서(엔디안) 변환이 없고, 구조체 패딩이 포함될 수 있습니다(24장에서 다룸).
