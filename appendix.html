A아스키 코드표

아스키 코드의 구조

ASCII(American Standard Code for Information Interchange)는 문자 하나를 0~127 범위의 정수(7비트)로 표현하는 표준입니다. C의 char는 결국 작은 정수이므로, 'A'라고 쓰면 컴파일러는 65라는 숫자로 바꿉니다. 11장에서 배운 것처럼 문자 처리 코드는 이 숫자 배치를 이해하면 훨씬 쉬워집니다.

왜 그럴까? — 아스키 배치에 숨은 설계 의도

  • 숫자 '0'~'9'가 연속(48~57): c - '0'으로 문자 숫자를 정수 값으로 바꿀 수 있습니다. C 표준은 실행 문자 집합에서 숫자 문자 '0'~'9'가 연속이라고 보장합니다. 금액 문자열 "0000250000"을 정수로 바꾸는 전문 파싱 코드가 이 성질을 씁니다.
  • 대문자와 소문자가 정확히 32(0x20) 차이: 2진수로 보면 비트 5 하나만 다릅니다('A'=0100 0001, 'a'=0110 0001). 그래서 c | 0x20은 소문자로, c & ~0x20은 대문자로 바꿉니다(영문자일 때만). 다만 알파벳이 연속이라는 것은 아스키에서만 참이고 표준이 보장하지 않으므로(EBCDIC에서는 불연속), 이식성 있는 코드는 toupper/tolower를 씁니다.
  • 공백(32)보다 작은 값은 제어 문자: 화면에 찍히는 글자가 아니라 장치를 제어하는 신호입니다. isprint로 출력 가능 여부를 판단할 수 있습니다.

은행 시스템에서는 — 아스키와 EBCDIC, 그리고 한글

IBM 메인프레임은 아스키가 아닌 EBCDIC 문자 코드를 씁니다. EBCDIC에서 'A'는 0xC1, '0'은 0xF0이고 알파벳이 연속되지 않습니다. 메인프레임 계정계와 유닉스 대외계가 파일이나 전문을 주고받을 때는 반드시 코드 변환 단계가 있으며, 숫자 필드가 엉뚱한 문자로 보인다면 이 변환을 의심합니다. 또한 아스키는 0~127만 정의하므로 한글은 EUC-KR/CP949(2바이트, 각 바이트 0x80 이상)나 UTF-8(한글 3바이트)로 표현됩니다. 바이트 값이 128 이상이면 아스키 문자가 아니라는 성질은 "이 바이트가 한글의 일부인가"를 판단하는 데 쓰입니다. 이때 signed char에서는 음수가 되므로 unsigned char로 다뤄야 합니다.

B선택 정렬 알고리즘

선택 정렬의 아이디어

선택 정렬(selection sort)은 "아직 정렬되지 않은 부분에서 가장 작은 값을 선택해 맨 앞으로 보낸다"를 반복하는 정렬입니다. 카드 패를 펼쳐 놓고 가장 작은 카드를 찾아 왼쪽 끝에 놓고, 남은 카드에서 다시 가장 작은 것을 찾아 그다음 자리에 놓는 방식과 같습니다. 원리가 단순해 정렬 알고리즘 입문용으로 쓰이며, 17장에서 계좌를 잔액순으로 정렬할 때 이미 사용했습니다.

  1. i = 0부터 n-2까지 반복합니다. i 앞쪽(0 ~ i-1)은 이미 정렬이 끝난 영역입니다.
  2. i ~ n-1 범위에서 최솟값의 위치 min을 찾습니다.
  3. a[i]와 a[min]을 교환합니다(min == i면 생략 가능).
  4. 이제 0 ~ i가 정렬된 영역이 됩니다. i를 하나 늘립니다.

단계별 그림

배열 { 64, 25, 12, 22, 11 }을 오름차순으로 정렬하는 과정입니다. 회색 바탕은 정렬이 끝난 영역, 금색은 이번 회차에 찾은 최솟값, 녹색은 교환될 자리입니다.

선택 정렬 코드

자주 하는 실수

  • 최솟값 "값"을 저장하고 위치를 잃어버림: int minval = a[i];만 기억하면 교환할 위치를 알 수 없습니다. 위치(인덱스)를 저장해야 합니다.
  • 안쪽 반복 안에서 매번 교환: 더 작은 값을 찾을 때마다 교환하면 결과는 맞아도 교환 횟수가 크게 늘어 선택 정렬의 장점(교환 최소)이 사라집니다. 이런 코드는 사실상 다른 정렬입니다.
  • 바깥 반복 범위: i < n으로 써도 결과는 맞지만 마지막 회차는 비교 0회의 헛수고입니다. i < n - 1이 정확합니다.

시간 복잡도와 공간 복잡도

i번째 회차에서 비교는 n-1-i번이므로 전체 비교 횟수는

(n-1) + (n-2) + ... + 1 = n(n-1)/2

입니다. 이 값은 입력이 이미 정렬되어 있든, 역순이든, 무작위든 항상 같습니다. 최솟값을 확인하려면 남은 원소를 모두 봐야 하기 때문입니다. 따라서 최선·평균·최악 모두 O(n2)입니다. 교환은 회차마다 최대 1번이므로 최대 n-1번, 즉 O(n)입니다. 추가 메모리는 변수 몇 개뿐이므로 공간 복잡도는 O(1)(제자리 정렬, in-place)입니다.

왜 그럴까? — 교환이 적다는 장점은 언제 쓸모 있을까?

선택 정렬은 비교는 많지만 쓰기(교환)가 최대 n-1번으로 적습니다. 원소 하나를 옮기는 비용이 비교보다 훨씬 큰 경우, 예를 들어 플래시 메모리처럼 쓰기 횟수에 수명 제한이 있는 저장 장치나, 아주 큰 레코드를 직접 옮겨야 하는 경우에는 이 성질이 의미가 있습니다. 하지만 일반적인 상황에서는 큰 레코드를 정렬할 때 포인터나 인덱스만 정렬하는 방법(17장 여기서 잠깐)이 더 낫습니다.

안정성(stability)

정렬 알고리즘이 안정적(stable)이라는 것은 키가 같은 원소들의 원래 순서가 정렬 후에도 유지된다는 뜻입니다. 기본 선택 정렬은 불안정합니다. 멀리 떨어진 원소끼리 교환하면서 같은 키를 가진 원소를 앞질러 보낼 수 있기 때문입니다.

은행 시스템에서는 — 안정 정렬이 필요한 순간

거래 내역을 "거래 시각순"으로 정렬해 둔 상태에서 다시 "계좌번호순"으로 정렬한다고 합시다. 안정 정렬을 쓰면 같은 계좌 안에서는 거래 시각 순서가 그대로 유지되어, 계좌별 거래 내역이 시간순으로 나옵니다. 불안정 정렬을 쓰면 같은 계좌의 거래 순서가 뒤섞여 잔액 추이를 계산할 때 중간 잔액이 음수로 보이는 등 이상한 결과가 나옵니다. 이런 이유로 실무에서는 (1) 안정 정렬(병합 정렬 등)을 쓰거나, (2) 정렬 키에 계좌번호와 거래 일련번호를 모두 넣어 순서가 하나로 정해지게 합니다. 표준 C의 qsort는 안정성을 보장하지 않으므로 두 번째 방법을 써야 합니다.

O(n2) 정렬은 원리를 배우는 용도이고, 실제 코드에서는 표준 라이브러리 qsort(평균 O(n log n))를 씁니다. 비교 함수에서 return a - b;처럼 빼기를 쓰면 큰 금액에서 오버플로가 나므로 비교 연산으로 -1, 0, 1을 돌려줍니다.

용량로그 파일 회전(rotation)과 보관 기간이 설정되어 디스크가 가득 차지 않는가?
감사누가, 언제, 어떤 데이터에 접근·변경했는지 감사 로그가 별도로 남는가? 감사 로그는 위·변조로부터 보호되는가?
성능반복문 안의 과도한 로그가 처리 성능을 떨어뜨리지 않는가?

D-6 배치 운영 체크리스트

  • 선행 조건: 선행 배치 완료, 입력 파일 도착(완료 파일·트레일러 확인), 영업일 여부를 확인하고 시작하는가?
  • 입력 검증: 헤더·트레일러의 건수와 금액 합계를 실제 데이터와 비교하는가? 중복 수신 파일을 걸러 내는가?
  • 오류 처리: 오류 레코드는 사유와 함께 별도 파일로 분리하고, 허용 오류율을 넘으면 중단하는가?
  • 재실행: 중간 실패 후 재실행해도 이중 처리되지 않는가? 체크포인트(커밋 단위)와 재시작 지점이 정의되어 있는가?
  • 커밋 주기: 대량 갱신을 적절한 건수마다 커밋해 잠금과 롤백 세그먼트를 과도하게 점유하지 않는가?
  • 출력 파일: 임시 이름으로 쓰고 완료 후 이름 변경(rename)하는가? 다음 단계가 쓰다 만 파일을 읽지 않는가?
  • 종료 코드: 성공·경고·실패를 종료 코드로 구분해 스케줄러가 후속 작업 실행 여부를 판단할 수 있는가?
  • 처리 결과 보고: 처리 건수, 성공·오류 건수, 금액 합계, 시작·종료 시각을 결과 로그에 남기는가?
  • 시간 관리: 마감 시각까지의 예상 처리 시간을 알고 있는가? 데이터 증가에 따른 처리 시간 추이를 모니터링하는가?
  • 비상 연락: 실패 시 알림이 담당자에게 가는가? 수작업 처리 절차와 연락 체계가 문서화되어 있는가?
