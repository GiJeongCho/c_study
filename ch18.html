18

파일 입출력

프로그램이 끝나면 메모리의 데이터는 사라집니다. 오늘의 거래 내역, 고객 원장, 일마감 결과를 남기려면 파일에 써야 합니다. 은행의 야간 배치는 사실상 "파일을 읽고, 계산하고, 파일을 쓰는" 일의 연속이므로, 파일 입출력은 금융 IT 개발자가 매일 쓰는 기술입니다.

이 장에서 배울 것

  • 스트림과 버퍼의 개념, FILE *가 무엇을 가리키는지
  • fopen의 모드(r, w, a, +, b, x)와 텍스트 모드·바이너리 모드의 차이(윈도우의 \r\n)
  • fclose의 의미와 perror, errno를 이용한 오류 처리
  • 문자 단위(fgetc/fputc), 줄 단위(fgets/fputs), 서식(fprintf/fscanf), 블록 단위(fread/fwrite) 입출력
  • fseek/ftell/rewind로 원하는 위치의 레코드를 읽고 고치는 랜덤 접근
  • feof를 반복 조건으로 쓰면 안 되는 이유, 버퍼 flush가 필요한 순간
  • 거래 내역 CSV 저장·읽기, 고객 원장 파일 레코드 수정 실습

18-1파일 개방과 입출력

스트림과 FILE 구조체

C 프로그램은 키보드, 화면, 디스크 파일, 심지어 다른 프로그램과의 파이프까지 모두 스트림(stream)이라는 같은 모양으로 다룹니다. 스트림은 "바이트가 한 줄로 흘러가는 통로"라고 생각하면 됩니다. 프로그램은 통로의 한쪽 끝에서 바이트를 꺼내거나 넣기만 하고, 통로 반대편이 키보드인지 디스크인지는 운영체제와 표준 라이브러리가 알아서 처리합니다.

<stdio.h>에 정의된 FILE은 스트림 하나를 관리하는 구조체입니다. 안에는 버퍼의 주소와 크기, 버퍼 안에서 현재 읽거나 쓸 위치, 운영체제가 준 파일 번호(파일 디스크립터), 오류 표시자와 파일 끝(EOF) 표시자 등이 들어 있습니다. 우리는 이 내부를 직접 건드리지 않고 FILE * 포인터를 받아 표준 함수에 넘기기만 합니다. 17장의 구조체 포인터를 함수에 넘기는 방식 그대로입니다.

프로그램이 시작될 때 이미 세 개의 스트림이 열려 있습니다.

이름의미기본 연결버퍼링(일반적 구현)
stdin표준 입력키보드대화형이면 줄 단위
stdout표준 출력화면터미널이면 줄 단위, 파일·파이프로 리다이렉트되면 완전 버퍼
stderr표준 오류화면버퍼 없음(즉시 출력)

그래서 printf(...)는 사실 fprintf(stdout, ...)와 같고, 오류 메시지는 fprintf(stderr, ...)로 내보내는 것이 원칙입니다. 배치 프로그램을 ./batch > result.txt로 실행하면 정상 출력은 파일로 가고 오류는 여전히 화면(또는 별도 로그)에 남기 때문입니다.

왜 그럴까? — 왜 굳이 버퍼를 둘까?

운영체제에 데이터를 넘기는 write 시스템 호출은 사용자 모드에서 커널 모드로 전환해야 해서 일반 함수 호출보다 수백 배 비쌉니다. 1바이트 쓸 때마다 시스템 호출을 하면 100만 바이트를 쓰는 데 100만 번 커널을 다녀와야 합니다. 표준 라이브러리는 FILE 안의 버퍼에 데이터를 모아 두었다가 버퍼가 가득 차거나, 줄바꿈을 만나거나(줄 버퍼 모드), fflush/fclose가 호출될 때 한꺼번에 내보냅니다. 4KB 버퍼라면 시스템 호출이 약 4,000분의 1로 줄어듭니다. 대신 "썼다고 생각했는데 아직 버퍼에만 있는" 상황이 생기며, 이것이 18-2의 flush 문제로 이어집니다.

fopen으로 파일 열기

파일을 사용하려면 먼저 fopen으로 열어 스트림을 만듭니다.

모드 문자열은 파일을 어떻게 열지 정합니다. 반드시 외워 두어야 하는 표입니다.

여기에 b를 붙이면 바이너리 모드가 됩니다: "rb", "wb", "r+b"(또는 "rb+"), "ab" 등. b가 없으면 텍스트 모드입니다.

자주 하는 실수 — "w"로 열어 원장을 날려 버리기

"w"와 "w+"는 파일이 존재하면 열자마자 내용을 0바이트로 잘라 냅니다. 아무것도 쓰지 않고 닫아도 이미 내용은 사라졌습니다. 기존 원장 파일의 일부만 고치려다 "w"로 여는 실수는 실제 운영 사고로 이어집니다. 기존 내용을 고칠 때는 "r+"(바이너리면 "r+b"), 뒤에 덧붙일 때는 "a", 덮어쓰면 안 되는 새 파일을 만들 때는 C11의 "wx"를 씁니다.

여기서 잠깐 — 파일 경로와 역슬래시

윈도우 경로를 C 문자열에 쓸 때 "C:\data\new.txt"라고 쓰면 \n이 줄바꿈 문자로 해석되어 엉뚱한 경로가 됩니다. "C:\\data\\new.txt"처럼 역슬래시를 두 번 쓰거나, 윈도우도 받아 주는 "C:/data/new.txt"를 씁니다. 상대 경로("hello.txt")는 실행 파일의 위치가 아니라 현재 작업 디렉터리 기준이라는 점도 배치 스케줄러에서 실행할 때 자주 틀리는 부분입니다.

텍스트 모드와 바이너리 모드

텍스트 모드와 바이너리 모드의 차이는 단 하나, 줄바꿈 문자 변환을 하느냐입니다. 리눅스와 유닉스에서는 줄바꿈이 원래 \n(0x0A) 한 바이트이므로 두 모드가 완전히 같습니다. 윈도우에서는 텍스트 파일의 줄바꿈이 \r\n(0x0D 0x0A) 두 바이트이기 때문에, 텍스트 모드에서 다음 변환이 일어납니다.

  • 쓸 때: 프로그램의 \n → 파일에 \r\n
  • 읽을 때: 파일의 \r\n → 프로그램에 \n
  • (MSVC 런타임) 텍스트 모드에서 읽을 때 0x1A(Ctrl+Z)를 파일 끝으로 취급할 수 있음

왜 그럴까? — 바이너리 데이터를 텍스트 모드로 쓰면 왜 깨질까?

구조체나 정수를 fwrite로 저장하면 그 바이트 중에 우연히 0x0A가 섞여 있을 수 있습니다. 예를 들어 정수 10은 리틀 엔디안으로 0A 00 00 00입니다. 윈도우 텍스트 모드라면 이 0x0A 앞에 0x0D가 끼어들어 5바이트가 되고, 그 뒤의 모든 레코드 위치가 1바이트씩 밀립니다. 읽을 때는 반대로 0D 0A가 0A로 줄어들어 데이터가 망가집니다. 그래서 텍스트가 아닌 데이터는 반드시 "rb", "wb", "r+b"로 열어야 합니다. 리눅스에서는 증상이 없어서 개발 서버에서는 멀쩡하다가 윈도우 도구로 옮기면 깨지는 버그가 됩니다.

반대로 CSV처럼 사람이 읽는 파일도 플랫폼 간에 주고받을 때는 주의해야 합니다. 윈도우에서 만든 CSV를 리눅스에서 읽으면 줄 끝에 \r이 남아 마지막 필드가 "50000\r"이 됩니다. 실무에서는 읽은 줄의 끝에서 \r과 \n을 모두 제거하는 코드를 습관처럼 넣습니다.

은행 시스템에서는 — 대외기관 송수신 파일

은행은 매일 수많은 파일을 주고받습니다. 대량 이체(급여 이체) 의뢰 파일, 자동이체 출금 결과 파일, 카드 매입 파일, 금융 공동망 정산 파일 등입니다. 이런 파일의 규격서에는 "레코드 길이 300바이트 고정, 줄바꿈 없음" 또는 "각 레코드 끝 CR+LF" 같은 조항이 반드시 있습니다. 줄바꿈 1바이트 차이로 레코드 경계가 어긋나면 전체 파일이 "포맷 오류"로 반송되고, 마감 시각을 넘기면 고객 이체가 지연됩니다. 그래서 금융권 개발자는 파일을 바이너리 모드로 열고 줄바꿈 바이트까지 명시적으로 다루는 경우가 많습니다. 또한 한글 필드의 문자 인코딩(EUC-KR/CP949인지 UTF-8인지)도 규격서로 확인해야 합니다.

fclose로 파일 닫기

int fclose(FILE *fp);는 스트림을 닫습니다. 성공하면 0, 실패하면 EOF를 반환합니다. fclose가 하는 일은 세 가지입니다.

  1. 쓰기 버퍼에 남아 있는 데이터를 운영체제로 내보냅니다(flush).
  2. 운영체제의 파일 디스크립터를 닫아 자원을 돌려줍니다.
  3. FILE 구조체와 버퍼 메모리를 해제합니다. 이후 fp를 사용하는 것은 미정의 동작입니다.

왜 그럴까? — fclose를 안 하면 무슨 일이 생길까?

main에서 return하거나 exit()를 호출하면 표준 라이브러리가 열린 스트림을 모두 flush하고 닫아 줍니다. 하지만 (1) abort()나 시그널로 비정상 종료되면 버퍼의 데이터는 그대로 사라집니다. (2) 오래 실행되는 서버나 배치 프로그램이 파일을 열기만 하고 닫지 않으면 파일 디스크립터 누수가 생겨, 프로세스당 한도(리눅스 기본 1024개 등)를 넘는 순간 모든 fopen이 "Too many open files"로 실패합니다. 메모리 누수와 같은 종류의 자원 누수입니다. (3) 디스크가 가득 차서 버퍼를 내보내지 못하는 오류는 fclose 시점에야 드러나므로, 중요한 파일은 fclose의 반환값까지 검사합니다.

오류 처리: perror와 errno

fopen이 NULL을 반환했다면 왜 실패했는지 알아야 합니다. 파일이 없는지, 권한이 없는지, 디렉터리가 없는지에 따라 대응이 다르기 때문입니다. 표준 라이브러리 함수는 실패할 때 전역(스레드별) 변수 errno(<errno.h>)에 오류 번호를 넣습니다.

  • perror("접두어"): 접두어: 오류 설명 형식으로 stderr에 출력합니다.
  • strerror(errno)(<string.h>): 오류 번호를 설명 문자열로 바꿉니다. 로그에 직접 기록할 때 씁니다.

왜 그럴까? — errno를 왜 바로 복사해 두어야 할까?

errno는 "마지막으로 실패한 함수의 오류 번호"입니다. 성공한 함수는 errno를 0으로 되돌려 놓을 의무가 없지만, 그 사이에 호출한 다른 라이브러리 함수(printf 포함)가 내부적으로 실패했다가 복구하면서 errno를 바꿀 수는 있습니다. 그래서 실패 직후 지역 변수에 복사해 두는 것이 안전합니다. 또한 errno는 실패가 확인된 경우에만 의미가 있습니다. 반환값으로 실패를 먼저 확인하지 않고 errno만 보고 판단하면 오래된 값에 속습니다. 오류 번호 값(ENOENT=2 등)과 메시지 문구는 운영체제마다 다를 수 있으므로 숫자 대신 매크로 이름으로 비교합니다.

errno 매크로의미흔한 원인
ENOENT파일 또는 디렉터리 없음경로 오타, 전 단계 배치 미완료, 작업 디렉터리 착각
EACCES권한 거부배치 계정에 읽기/쓰기 권한 없음
EEXIST이미 존재"wx" 모드로 열었는데 파일이 있음

ENOSPC디스크 공간 부족로그 파일 폭증

문자 단위 입출력: fgetc와 fputc

가장 기본이 되는 입출력은 한 문자(1바이트)씩 읽고 쓰는 것입니다.

바이트 수를 확인해 봅시다. 소스 파일이 UTF-8로 저장되어 있다면 "거래일자: 20261028\n"은 한글 4글자 × 3바이트 = 12, 콜론과 공백 2, 숫자 8, 줄바꿈 1로 23바이트입니다. "파일 입출력 시작\n"은 한글 7글자 × 3바이트 = 21, 공백 2, 줄바꿈 1로 24바이트입니다. 합계 47바이트입니다. 파일을 "rb"/"wb"로 열었으므로 어느 플랫폼에서든 바이트를 변환 없이 그대로 복사합니다. 복사 프로그램이 텍스트 모드를 쓰면 윈도우에서 \r 처리 때문에 원본과 사본이 미묘하게 달라질 수 있으므로, 파일 복사는 항상 바이너리 모드로 합니다.

예제 18-1 난이도 ★★☆

같은 hello.txt를 윈도우에서, 소스 코드를 CP949(한글 1글자 2바이트)로 저장해 컴파일하고 ex18-1을 실행했습니다("w" 텍스트 모드). 만들어진 파일의 크기는 몇 바이트입니까? 이 파일을 ex18-3으로 복사하면 출력은 무엇입니까?

정답과 해설 보기

1줄 = 한글 4자 × 2 = 8 + ": " 2 + 숫자 8 + 줄바꿈 \r\n 2 = 20바이트. 2줄 = 한글 7자 × 2 = 14 + 공백 2 + \r\n 2 = 18바이트. 파일 크기는 38바이트입니다.

ex18-3은 "rb"로 읽으므로 \r(0x0D)도 그대로 한 바이트로 셉니다. 줄 수는 '\n' 개수이므로 2입니다. 출력은 38바이트, 2줄 복사입니다. 같은 내용도 인코딩과 줄바꿈 방식에 따라 크기가 달라지므로, 고정 길이 파일 규격에서는 "글자 수"가 아니라 "바이트 수"로 이야기해야 합니다.

자주 하는 실수 — fgetc의 반환값을 char에 저장

fgetc는 0~255의 바이트 값 또는 EOF(보통 -1)를 돌려주기 위해 int를 반환합니다. 256가지 바이트 값과 EOF, 총 257가지를 구별해야 하므로 char(256가지)에는 다 담을 수 없습니다.

  • char가 signed인 플랫폼(x86 gcc 기본): 0xFF 바이트를 읽으면 ch = -1이 되어 EOF와 같아집니다. 바이너리 파일이나 일부 한글 인코딩에서 0xFF가 나오는 순간 파일 중간에서 읽기가 멈춥니다.
  • char가 unsigned인 플랫폼(ARM 리눅스 gcc 기본 등): EOF(-1)를 저장하면 255가 되어 EOF와 절대 같아지지 않으므로 무한 루프가 됩니다.

이렇게 해결합니다

반환값은 항상 int ch에 받고 EOF와 비교한 뒤, EOF가 아니면 그때 char로 사용합니다. getchar, getc, fgetc 모두 같습니다.

예제 18-2 난이도 ★★☆

텍스트 파일을 읽어 숫자 문자('0'~'9')의 개수와 쉼표(',')의 개수를 세는 프로그램을 fgetc로 작성하십시오. 파일 이름은 명령행 인수 argv[1]로 받고, 인수가 없으면 사용법을 stderr에 출력합니다.

정답과 해설 보기

argc를 먼저 검사하고, fopen 실패 시 perror로 원인을 출력합니다. isdigit는 <ctype.h>에 있으며 인자로 unsigned char 범위의 값이나 EOF를 받아야 하는데, fgetc의 반환값은 정확히 그 범위이므로 그대로 넘겨도 안전합니다.

18-2다양한 파일 입출력 함수

줄 단위 입출력: fgets와 fputs

텍스트 파일은 대부분 줄 단위로 의미가 있습니다. 로그 한 줄, CSV 레코드 한 줄처럼요. 줄 단위 입출력 함수는 다음과 같습니다.

왜 그럴까? — fgets는 왜 줄바꿈까지 넣어 줄까?

fgets가 '\n'을 버퍼에 남기는 것은 "줄 전체를 다 읽었는지"를 알려 주는 신호입니다. 버퍼 끝이 '\n'이면 한 줄을 완전히 읽은 것이고, '\n' 없이 버퍼가 가득 찼다면 줄이 버퍼보다 길어서 잘린 것입니다(나머지는 다음 fgets 호출에서 이어서 읽힘). 파일의 마지막 줄에 줄바꿈이 없는 경우에도 '\n'이 없을 수 있습니다. 이 정보를 이용해 너무 긴 줄을 오류로 처리할 수 있습니다.

strcspn(line, "\r\n")은 line에서 \r이나 \n이 처음 나오는 위치(없으면 문자열 길이)를 돌려주므로, 그 자리에 '\0'을 넣으면 줄 끝 문자가 깔끔하게 제거됩니다. 윈도우에서 만든 파일을 리눅스에서 읽는 경우까지 한 줄로 처리하는 관용구입니다.

자주 하는 실수 — gets 사용, 그리고 fputs와 puts 혼동

  • gets는 버퍼 크기를 받지 않아 입력이 길면 무조건 버퍼 오버플로가 납니다. C11에서 표준에서 삭제되었습니다. 절대 쓰지 말고 fgets(buf, sizeof buf, stdin)을 씁니다.
  • puts(s)는 끝에 '\n'을 붙이지만 fputs(s, fp)는 붙이지 않습니다. fgets로 읽은 줄(\n 포함)을 fputs로 쓰면 줄바꿈이 그대로 유지되어 딱 맞습니다.

서식 입출력: fprintf와 fscanf

fprintf와 fscanf는 printf, scanf와 사용법이 같고 첫 인자로 스트림을 받는다는 점만 다릅니다. 숫자를 사람이 읽을 수 있는 텍스트로 저장할 때 가장 편리합니다.

왜 그럴까? — fscanf의 반환값을 왜 2와 비교할까?

fscanf는 성공적으로 변환해 저장한 항목의 개수를 반환하고, 첫 변환 전에 입력이 끝나면 EOF를 반환합니다. while (fscanf(...) != EOF)라고 쓰면 형식이 틀린 줄(예: 금액 자리에 "ABC")을 만났을 때 0이 반환되는데, 0은 EOF가 아니므로 반복이 계속되고, fscanf는 같은 "ABC"에서 계속 실패하므로 무한 루프가 됩니다. 기대하는 개수(여기서는 2)와 정확히 같은지 비교해야 정상 데이터만 처리하고 이상 데이터에서 멈출 수 있습니다.

또한 %s에는 반드시 폭(%15s)을 지정합니다. 폭이 없으면 공백이 나올 때까지 무한정 써서 버퍼 오버플로가 납니다. 폭은 버퍼 크기 - 1(널 문자 자리)입니다.

여기서 잠깐 — 실무에서는 fgets + sscanf

fscanf는 줄 경계를 모릅니다. 공백과 줄바꿈을 똑같이 건너뛰므로, 한 줄에 필드가 하나 빠지면 다음 줄의 필드를 끌어와 어긋난 채로 계속 읽습니다. 그래서 실무에서는 fgets로 한 줄을 읽고, sscanf나 직접 파싱으로 그 줄만 해석하는 방식을 선호합니다. 오류가 나도 그 줄만 건너뛰고 줄 번호를 정확히 보고할 수 있습니다. 다음 절의 CSV 예제가 이 방식입니다.

거래 내역 CSV 저장과 읽기

CSV(Comma-Separated Values)는 쉼표로 필드를 구분한 텍스트 형식으로, 엑셀과 데이터베이스 도구가 모두 읽을 수 있어 거래 내역 내려받기, 대사 자료, 운영 보고서에 널리 쓰입니다.

왜 그럴까? — %8[^,]는 무슨 뜻일까?

%[...]는 "대괄호 안의 문자 집합에 속하는 문자만 읽는" 변환이고, ^는 부정입니다. 즉 %[^,]는 "쉼표가 아닌 문자를 쉼표 직전까지" 읽습니다. 앞의 8은 최대 폭이므로 date[9] 버퍼를 넘치지 않습니다. 일반 %s는 공백에서만 멈추므로 쉼표로 구분된 필드를 나눌 수 없습니다. 불량 줄 "20261028,110-004,X"는 type까지 3개만 변환되고 금액이 없어 sscanf가 3을 반환하므로 오류로 걸러집니다.

다만 sscanf 방식은 빈 필드(a,,c)를 처리하지 못하고(%[^,]는 최소 1글자가 필요), 따옴표로 감싼 필드("김,철수")도 해석하지 못합니다. 이런 데이터가 있을 수 있다면 strchr로 쉼표 위치를 직접 찾아 자르는 파서를 작성해야 합니다.

은행 시스템에서는 — 배치 파일 처리의 원칙

야간 배치는 수십만~수백만 줄의 파일을 처리합니다. 실무에서 지키는 원칙은 다음과 같습니다.

  • 한 줄 오류로 전체를 멈추지 않되, 반드시 기록한다: 오류 줄은 행 번호와 함께 오류 파일(reject file)로 분리하고, 처리 건수·오류 건수·금액 합계를 결과 보고에 남깁니다.
  • 건수와 합계 검증(control total): 송신 측이 파일 끝에 붙인 트레일러 레코드(총 건수, 총 금액)와 실제로 읽은 값을 비교해 파일이 잘리거나 중복되지 않았는지 확인합니다.
  • 재실행 가능성: 배치가 중간에 실패해도 다시 돌렸을 때 이중 처리되지 않도록 처리 완료 지점(체크포인트)이나 처리 여부 플래그를 관리합니다.
  • 임시 파일 후 이름 변경: 결과 파일은 result.tmp로 쓰고 fclose 성공을 확인한 뒤 rename으로 최종 이름을 붙입니다. 다음 단계 배치가 쓰다 만 파일을 읽는 사고를 막습니다.

feof의 함정

파일 끝을 검사하는 feof(fp) 함수가 있다 보니 많은 입문서에서 다음과 같은 코드를 볼 수 있습니다. 하지만 이것은 고전적인 버그입니다.

왜 그럴까? — feof는 미래를 예측하지 못한다

feof는 "다음 읽기가 실패할 것인가"를 알려 주는 함수가 아닙니다. "이전 읽기가 파일 끝 때문에 실패했는가"를 알려 주는 함수입니다. FILE 구조체의 EOF 표시자는 읽기 함수가 파일 끝을 넘어서 읽으려다 실패하는 순간 켜집니다. 마지막 줄 "B\n"을 읽은 직후에는 파일 위치가 끝에 있지만, 아직 넘어서 읽으려고 한 적이 없으므로 표시자는 꺼져 있습니다. 그래서 반복이 한 번 더 돌고, 그 fgets는 실패하며 line을 바꾸지 않아 이전 내용이 다시 출력됩니다. 키보드나 네트워크처럼 "끝인지 미리 알 수 없는" 스트림까지 같은 방식으로 다뤄야 하므로 이렇게 설계된 것입니다.

이렇게 해결합니다

반복 조건은 항상 읽기 함수의 반환값으로 정합니다. feof와 ferror는 반복이 끝난 뒤에 "왜 끝났는지"를 구분하는 데만 씁니다.

함수별 "실패" 반환값: fgetc → EOF, fgets → NULL, fscanf → 기대 개수 미만, fread → 요청한 개수 미만.

블록 단위 입출력: fread와 fwrite로 고정 길이 레코드

텍스트 형식은 사람이 읽기 좋지만, 숫자를 문자로 바꾸고 다시 파싱하는 비용이 들고, 레코드 길이가 제각각이라 "100번째 레코드"로 바로 갈 수 없습니다. fread와 fwrite는 메모리의 바이트를 그대로 파일에 옮깁니다. 구조체 하나를 레코드 하나로 저장하면 모든 레코드의 길이가 같아지는 고정 길이 레코드 파일이 됩니다.

왜 그럴까? — fread는 왜 "항목 수"를 반환할까?

fread는 요청한 바이트를 다 못 읽을 수 있습니다(파일 끝, 오류). 반환값은 완전히 읽은 항목의 개수입니다. 48바이트 레코드를 읽으려는데 파일에 30바이트만 남아 있으면 반환값은 0이고 그 30바이트는 버퍼에 들어갔을 수 있지만 불완전합니다. 그래서 fread(&r, sizeof r, 1, fp) == 1로 검사하면 "레코드 하나를 온전히 읽었는가"를 정확히 판단할 수 있습니다. 반대로 fread(&r, 1, sizeof r, fp)로 부르면 바이트 수가 반환되므로 == sizeof r과 비교해야 합니다.

자주 하는 실수 — 구조체 바이너리 파일의 이식성

17장에서 본 것처럼 구조체를 그대로 저장한 파일은 패딩, 엔디안, 자료형 크기(long이 리눅스 8바이트, 윈도우 4바이트)에 따라 다른 시스템에서 읽을 수 없게 될 수 있습니다. 같은 프로그램이 같은 플랫폼에서 쓰고 읽는 내부용 파일에만 사용하고, 시스템 간 교환 파일은 텍스트나 명시적으로 정의한 바이트 형식을 사용합니다. 또한 char * 같은 포인터 멤버는 주소값만 저장되어 의미가 없습니다. 레코드 구조체에는 고정 크기 배열을 씁니다.

랜덤 접근: fseek, ftell, rewind

FILE 구조체는 "다음에 읽거나 쓸 위치"인 파일 위치 표시자(file position indicator)를 가지고 있습니다. 읽거나 쓰면 처리한 바이트만큼 자동으로 앞으로 이동합니다. 이 위치를 직접 옮기면 원하는 곳으로 바로 갈 수 있습니다.

왜 그럴까? — 텍스트 모드에서 fseek 오프셋을 계산하면 안 되는 이유

C 표준은 텍스트 스트림에 대해 fseek의 오프셋으로 0 또는 이전에 ftell이 돌려준 값만 SEEK_SET과 함께 쓰도록 허용합니다. 윈도우 텍스트 모드처럼 \r\n 변환이 일어나면 "프로그램이 본 바이트 수"와 "파일의 실제 바이트 위치"가 다르기 때문입니다. 계산으로 위치를 정하는 랜덤 접근은 반드시 바이너리 모드에서 합니다. 또 SEEK_END 기준 이동은 바이너리 스트림에서 표준상 의미 있게 지원될 필요가 없다고 되어 있지만, POSIX와 윈도우의 일반 파일에서는 잘 동작해 파일 크기 구하기 관용구로 널리 쓰입니다. 2GB를 넘는 파일은 long이 4바이트인 환경에서 넘치므로 POSIX의 fseeko/ftello(off_t)나 윈도우의 _fseeki64를 씁니다.

고객 원장 파일 레코드 수정하기

이제 고정 길이 레코드와 랜덤 접근을 합쳐 원장 파일의 특정 계좌 잔액을 제자리에서(in-place) 고쳐 보겠습니다. 파일 전체를 다시 쓰지 않고 해당 48바이트만 덮어씁니다.

왜 그럴까? — 읽기와 쓰기 사이에 왜 fseek가 꼭 필요할까?

갱신 모드("r+", "w+", "a+")에서 C 표준은 두 가지 규칙을 둡니다. (1) 쓰기 다음에 읽으려면 그 사이에 fflush나 위치 지정 함수(fseek, fsetpos, rewind)를 호출해야 합니다. (2) 읽기 다음에 쓰려면 그 사이에 위치 지정 함수를 호출해야 합니다(읽기가 파일 끝에 도달한 경우 제외). FILE은 하나의 버퍼를 읽기용과 쓰기용으로 번갈아 쓰기 때문에, 방향을 바꿀 때 버퍼 상태를 정리할 기회가 필요하기 때문입니다. 이 규칙을 어기면 미정의 동작으로, 실제로 엉뚱한 위치에 써지거나 쓴 내용이 사라지는 일이 생깁니다. 위 예제는 마침 읽기 후 되돌아가는 fseek이 필요했으므로 규칙을 자연스럽게 지켰습니다. 만약 다음 레코드를 계속 읽어야 한다면 fwrite 뒤에 fseek(fp, 0L, SEEK_CUR);를 한 줄 넣어 방향 전환을 알려야 합니다.

은행 시스템에서는 — 파일 원장과 동시성

오늘날 계정계 원장은 대부분 관계형 데이터베이스에 있지만, 메인프레임의 VSAM이나 C로 작성된 고속 처리 엔진, 카드 승인 시스템의 캐시 파일 등에서 고정 길이 레코드 파일은 여전히 쓰입니다. 실무에서 위 예제를 그대로 쓰면 안 되는 이유는 다음과 같습니다.

  • 동시 접근: 두 프로세스가 같은 레코드를 동시에 읽고 각자 더해서 쓰면 한쪽의 입금이 사라집니다(lost update). 파일 잠금(fcntl, flock)이나 데이터베이스 트랜잭션이 필요합니다.
  • 장애 중 쓰기: fwrite 중 전원이 나가면 레코드 절반만 바뀐 상태가 될 수 있습니다. 변경 전 이미지를 저널(로그)에 먼저 기록하는 방식(write-ahead logging)으로 복구 가능성을 확보합니다.
  • 순차 검색 비용: 계좌번호로 처음부터 찾으면 레코드 수에 비례하는 시간이 걸립니다. 계좌번호 → 레코드 번호 인덱스(해시, B-트리)를 둡니다.

버퍼와 flush

18-1에서 본 것처럼 출력은 일단 버퍼에 쌓입니다. 표준 라이브러리는 세 가지 버퍼링 방식을 씁니다.

방식상수언제 내보내나주 사용처
완전 버퍼(full)_IOFBF버퍼가 가득 찰 때디스크 파일, 리다이렉트된 stdout
줄 버퍼(line)_IOLBF'\n'을 출력할 때 또는 가득 찰 때터미널에 연결된 stdout
버퍼 없음(none)_IONBF즉시stderr

세 경우 모두 fflush(fp)를 호출하거나, fclose하거나, 프로그램이 정상 종료(main의 return, exit)하면 내보냅니다. 또한 입력 요청 시 줄 버퍼 출력 스트림이 flush되는 구현이 일반적입니다(그래서 printf 뒤 scanf의 안내 문구가 보입니다).

왜 그럴까? — 장애 원인을 남겨야 할 로그가 왜 비어 있을까?

batch.log는 디스크 파일이므로 완전 버퍼 방식입니다. 두 줄은 수십 바이트라 4KB 버퍼를 채우지 못해 아직 메모리에만 있습니다. abort(), 세그멘테이션 오류(SIGSEGV), kill -9 같은 비정상 종료에서는 표준 라이브러리가 버퍼를 비울 기회가 없으므로 버퍼 안의 데이터는 프로세스와 함께 사라집니다. 정작 "어디까지 진행하다 죽었는가"라는 가장 중요한 정보가 로그에 남지 않습니다.

이렇게 해결합니다

  • 중요한 로그는 한 줄 쓸 때마다 fflush(log);를 호출합니다.
  • 또는 열자마자 setvbuf(log, NULL, _IOLBF, 0);로 줄 버퍼 방식으로 바꿉니다(setvbuf는 해당 스트림에 다른 입출력을 하기 전에 호출해야 함).
  • 진행 상황 표시처럼 줄바꿈 없이 화면에 출력하는 경우 fflush(stdout);을 호출합니다.
  • fflush는 운영체제 커널까지만 보냅니다. 전원 장애에도 디스크에 남아야 하는 데이터(거래 저널 등)는 POSIX의 fsync(fileno(fp))로 디스크 기록까지 보장합니다.

자주 하는 실수 — fflush(stdin)

fflush는 출력 스트림(또는 마지막 동작이 출력인 갱신 스트림)용입니다. C 표준에서 입력 스트림에 대한 fflush는 미정의 동작입니다. 일부 윈도우 구현이 입력 버퍼를 비워 주었던 탓에 널리 퍼졌지만, 리눅스 glibc에서는 기대대로 동작하지 않을 수 있고 최신 MSVC에서도 보장되지 않습니다. 입력에 남은 줄을 버리려면 int c; while ((c = getchar()) != '\n' && c != EOF) ;처럼 직접 읽어서 버립니다.

예제 18-3 난이도 ★★★

다음 프로그램을 터미널에서 실행할 때와 ./a.out > out.txt로 실행할 때, 화면 또는 out.txt에 나타나는 출력 순서를 각각 예측하십시오.

#include <stdio.h>
int main(void)
{
    printf("A\n");
    fprintf(stderr, "B\n");
    printf("C\n");
    return 0;
}
정답과 해설 보기

터미널: stdout이 줄 버퍼이므로 "A\n"은 바로 출력되고, stderr는 버퍼가 없어 즉시 출력됩니다. 화면 순서는 A, B, C입니다.

리다이렉트: stdout이 파일로 가면 완전 버퍼가 되어 A와 C는 프로그램 종료 시에 함께 out.txt에 쓰입니다. B는 stderr라 리다이렉트되지 않고 즉시 화면에 나옵니다. 결과적으로 화면에는 B만, out.txt에는 "A\nC\n"이 남습니다. 만약 ./a.out > out.txt 2>&1로 둘 다 같은 파일로 보내면 파일 안의 순서는 B, A, C가 됩니다. 배치 로그에서 오류 메시지가 정상 메시지보다 "먼저" 찍혀 있는 이유가 바로 이것입니다.

핵심 정리

  • C는 모든 입출력 장치를 스트림으로 다루며, FILE *는 버퍼·위치·오류/EOF 표시자를 가진 FILE 구조체를 가리킵니다. stdin, stdout, stderr는 처음부터 열려 있습니다.
  • fopen은 실패하면 NULL을 반환하므로 항상 검사하고, perror/strerror(errno)로 원인을 기록합니다.
  • "w"와 "w+"는 기존 내용을 지웁니다. 기존 파일을 고칠 때는 "r+", 덧붙일 때는 "a", 덮어쓰기를 막으려면 C11 "wx"를 씁니다.
  • 텍스트 모드와 바이너리 모드의 차이는 줄바꿈 변환(윈도우 \n ↔ \r\n)입니다. 텍스트가 아닌 데이터와 위치 계산이 필요한 파일은 반드시 바이너리 모드로 엽니다.
  • fclose는 버퍼를 비우고 자원을 반환합니다. 닫지 않으면 데이터 유실과 파일 디스크립터 누수가 생기며, 중요한 파일은 fclose 반환값도 검사합니다.
  • fgetc의 반환값은 반드시 int에 받습니다. char에 받으면 0xFF에서 멈추거나 무한 루프가 됩니다.
  • fgets는 크기를 지정하고 줄바꿈까지 읽으므로 strcspn으로 \r\n을 제거합니다. gets는 C11에서 삭제되었습니다.
  • fscanf/sscanf는 성공 항목 수를 반환하므로 기대 개수와 비교합니다. 실무에서는 fgets + sscanf로 줄 단위 오류 처리를 합니다.
  • 반복 조건에 feof를 쓰지 않습니다. EOF 표시자는 끝을 넘어 읽으려 시도한 뒤에 켜지므로 마지막 데이터가 두 번 처리됩니다. 읽기 함수의 반환값으로 반복하고, 끝난 뒤 feof/ferror로 원인을 구분합니다.
  • fread/fwrite는 처리한 항목 수를 반환하며, 구조체를 고정 길이 레코드로 저장할 수 있습니다. 다만 패딩·엔디안·형 크기 때문에 시스템 간 교환용으로는 부적합합니다.
  • fseek/ftell/rewind로 위치를 옮겨 i × sizeof(레코드) 위치의 레코드를 바로 읽고 고칠 수 있습니다. 갱신 모드에서 읽기와 쓰기를 바꿀 때는 그 사이에 fseek(또는 쓰기 후 fflush)가 필요합니다.
  • 버퍼링은 완전/줄/없음 세 가지입니다. 비정상 종료 시 버퍼 내용은 사라지므로 중요 로그는 fflush하거나 줄 버퍼로 설정합니다. fflush(stdin)은 미정의 동작입니다.

CS 면접 단골 질문

이 장에서 나오는 면접 질문

Q1. 버퍼링된 I/O를 사용하는 이유는 무엇인가요?

시스템 호출은 사용자 모드에서 커널 모드로 전환해야 해서 비용이 큽니다. 표준 라이브러리는 데이터를 사용자 공간 버퍼에 모아 두었다가 한꺼번에 write 시스템 호출을 하므로 호출 횟수가 크게 줄어 성능이 좋아집니다. 대신 프로그램이 비정상 종료되면 버퍼에 남은 데이터가 유실될 수 있어, 중요한 데이터는 fflush로 명시적으로 내보내고, 디스크까지 보장하려면 fsync를 사용합니다.

꼬리 질문 대비: "fflush와 fsync의 차이는?" fflush는 라이브러리 버퍼 → 커널 페이지 캐시까지, fsync는 커널 캐시 → 실제 저장 장치까지 기록을 보장한다고 답합니다.

Q2. 텍스트 모드와 바이너리 모드의 차이는?

차이는 줄바꿈 변환 여부입니다. 윈도우 텍스트 모드는 쓸 때 \n을 \r\n으로, 읽을 때 \r\n을 \n으로 바꿉니다. 유닉스 계열에서는 차이가 없습니다. 바이너리 데이터를 텍스트 모드로 다루면 0x0A 바이트 앞에 0x0D가 끼어 데이터가 깨지고, 텍스트 모드에서는 fseek로 계산한 오프셋도 신뢰할 수 없으므로 구조체 저장이나 랜덤 접근은 바이너리 모드로 합니다.

Q3. while(!feof(fp))가 왜 잘못된 코드인가요?

feof는 이전 읽기가 파일 끝 때문에 실패했는지를 알려 줄 뿐, 다음 읽기가 성공할지 예측하지 못합니다. 마지막 데이터를 읽은 직후에는 EOF 표시자가 아직 꺼져 있어서 반복이 한 번 더 돌고, 그때의 읽기는 실패하지만 반환값을 검사하지 않으므로 이전 버퍼 내용이 한 번 더 처리됩니다. 읽기 함수의 반환값으로 반복을 제어하고, 끝난 뒤에 feof와 ferror로 종료 원인을 구분해야 합니다.

Q4. fgetc의 반환형이 왜 char가 아니라 int인가요?

읽을 수 있는 바이트 값 256가지와 "더 이상 없음"을 뜻하는 EOF를 모두 구별해야 하기 때문입니다. 257가지 값은 char에 담을 수 없습니다. char에 저장하면 signed char 환경에서는 0xFF 바이트가 EOF로 오인되어 읽기가 중간에 멈추고, unsigned char 환경에서는 EOF가 255가 되어 무한 루프가 됩니다.

Q5. 파일 디스크립터와 FILE 포인터의 차이는?

파일 디스크립터는 운영체제(POSIX)가 열린 파일을 식별하기 위해 프로세스에 주는 작은 정수로, open/read/write 같은 시스템 호출에 씁니다. 0, 1, 2가 표준 입력, 출력, 오류입니다. FILE 포인터는 C 표준 라이브러리 수준의 객체로, 내부에 파일 디스크립터와 사용자 공간 버퍼, 위치, 상태 플래그를 가집니다. fileno(fp)로 FILE의 디스크립터를, fdopen으로 디스크립터에서 FILE을 얻을 수 있습니다.

꼬리 질문 대비: "파일을 닫지 않으면?" 디스크립터 누수로 프로세스 한도(ulimit -n)에 도달하면 더 이상 파일이나 소켓을 열 수 없게 됩니다.

Q6. 구조체를 fwrite로 저장한 파일을 다른 시스템에서 읽으면 어떤 문제가 생기나요?

컴파일러와 아키텍처에 따라 패딩 위치, 정수의 엔디안, long 같은 형의 크기가 다를 수 있어서 같은 구조체 정의로도 값이 잘못 해석될 수 있습니다. 포인터 멤버는 주소만 저장되므로 의미가 없습니다. 교환용 파일은 고정 폭 정수형과 정해진 바이트 순서로 필드 단위 직렬화를 하거나 텍스트 형식을 사용하고, 금융 전문처럼 숫자도 문자로 표현하는 방식을 씁니다.

Q7. errno는 어떻게 동작하고 사용 시 주의할 점은?

표준 라이브러리와 시스템 호출이 실패할 때 오류 원인 번호를 저장하는 변수로, 멀티스레드 환경에서는 스레드마다 따로 존재합니다. 성공한 호출은 errno를 지우지 않으므로 반드시 반환값으로 실패를 확인한 뒤에만 errno를 보고, 다른 함수를 호출하기 전에 지역 변수에 복사해 둡니다. 비교는 숫자 대신 ENOENT, EACCES 같은 매크로로 합니다.

Q8. 같은 파일을 두 프로세스가 동시에 수정하면 어떤 문제가 생기고 어떻게 막나요?

두 프로세스가 같은 레코드를 읽고 각자 수정해서 쓰면 나중에 쓴 쪽이 먼저 쓴 변경을 덮어써 갱신이 사라지는 lost update가 생깁니다. 은행 잔액이라면 입금이 사라지는 사고입니다. 파일 잠금(fcntl의 레코드 잠금, flock)으로 읽기-수정-쓰기 구간을 상호 배제하거나, 데이터베이스 트랜잭션과 행 잠금(SELECT ... FOR UPDATE)을 사용합니다.

꼬리 질문 대비: 트랜잭션 격리 수준과 데드락으로 이어질 수 있으니 ACID 개념을 함께 정리해 두십시오.

Q9. 결과 파일을 쓸 때 임시 파일에 쓰고 rename하는 이유는?

쓰는 도중 장애가 나거나 다른 프로세스가 쓰다 만 파일을 읽는 것을 막기 위해서입니다. 같은 파일 시스템 안에서의 rename은 POSIX에서 원자적으로 동작하므로, 다른 프로세스는 이전 파일이나 완성된 새 파일 중 하나만 보게 됩니다. 배치 연계에서 "완료 파일(.done)"이나 트레일러 레코드로 완전성을 확인하는 것도 같은 목적입니다.

연습문제

연습문제 18-1 모드 선택 난이도 ★☆☆

다음 상황에 알맞은 fopen 모드를 쓰십시오. (1) 매 거래를 거래 로그 파일 끝에 덧붙인다. (2) 원장 바이너리 파일의 특정 레코드를 수정한다. (3) 오늘 날짜의 결과 파일을 새로 만들되, 이미 있으면 실수로 덮어쓰지 않고 실패하게 한다. (4) 대외기관에서 받은 고정 길이 바이너리 파일을 읽는다.

정답과 해설 보기

(1) "a": 항상 끝에 쓰므로 다른 위치를 덮어쓸 위험이 없습니다. (2) "r+b": 내용을 유지하며 읽기·쓰기, 바이너리. "w+b"는 내용을 지우므로 절대 안 됩니다. (3) "wx"(C11): 파일이 있으면 NULL을 반환하고 errno는 EEXIST가 됩니다. (4) "rb": 줄바꿈 변환이 없어 바이트가 그대로 읽힙니다.

연습문제 18-2 출력 예측 난이도 ★★☆

파일 data.txt의 내용이 "10 20 x 30\n"일 때 출력은?

int v, sum = 0, n = 0;
while (fscanf(fp, "%d", &v) == 1) { sum += v; n++; }
printf("%d %d\n", n, sum);
정답과 해설 보기

출력: 2 30. 10과 20은 읽히고, "x"에서 변환이 실패해 0이 반환되므로 반복이 끝납니다. 30은 읽히지 않습니다. 반복 조건을 != EOF로 썼다면 x에서 계속 0이 반환되어 무한 루프가 되었을 것입니다. 오류 데이터를 만나면 멈추고 보고하는 것이 올바른 동작입니다.

연습문제 18-3 버그 찾기 난이도 ★★☆

FILE *fp = fopen("log.txt", "r");
char c;
while ((c = fgetc(fp)) != EOF)
    putchar(c);

이 코드의 문제점을 모두 찾으십시오.

정답과 해설 보기

(1) fopen의 실패 검사가 없어 파일이 없으면 NULL로 fgetc를 호출해 프로그램이 죽습니다. (2) c가 char이므로 0xFF 바이트에서 읽기가 끝나거나(signed char), EOF를 영원히 감지하지 못합니다(unsigned char). int c로 바꿔야 합니다. (3) fclose가 없습니다. (4) 반복 후 ferror로 읽기 오류를 구분하지 않습니다.

연습문제 18-4 코드 작성: 줄 수, 최장 줄 난이도 ★★☆

텍스트 파일의 줄 수와 가장 긴 줄의 길이(줄바꿈 제외, 바이트)를 출력하는 프로그램을 fgetc로 작성하십시오. 마지막 줄이 줄바꿈 없이 끝나도 한 줄로 세어야 합니다.

정답과 해설 보기

현재 줄 길이를 세다가 '\n'에서 줄 수를 늘리고 최댓값을 갱신합니다. 파일이 끝났을 때 현재 줄 길이가 0보다 크면 줄바꿈 없는 마지막 줄이 있었던 것이므로 한 줄을 더 셉니다. fgets를 쓰면 버퍼보다 긴 줄을 처리하기 번거로우므로 fgetc가 이 문제에 더 알맞습니다. \r은 길이에서 제외해 윈도우 파일에도 대응합니다.

연습문제 18-7 출력 예측: feof 난이도 ★★☆

파일 내용이 정확히 3바이트 "XYZ"(줄바꿈 없음)일 때 출력은?

int c, n = 0;
while (!feof(fp)) { c = fgetc(fp); n++; }
printf("%d %d\n", n, c);
정답과 해설 보기

출력: 4 -1(EOF가 -1인 일반적 구현). X, Y, Z를 읽은 세 번의 반복 뒤에도 EOF 표시자는 꺼져 있으므로 네 번째 반복에서 fgetc가 EOF를 반환하며 그때 표시자가 켜집니다. n은 실제 바이트 수보다 1 많은 4가 됩니다. 바이트 수를 세는 프로그램이라면 결과가 틀린 것입니다.

ex18-7의 Rec 형식 원장 파일에서 인덱스 idx(0부터)인 레코드의 status를 1(정지)로 바꾸는 함수 int suspend_at(const char *path, long idx)를 작성하십시오. idx가 범위를 벗어나면 -2를 반환합니다.

정답과 해설 보기

파일 크기로 레코드 수를 구해 범위를 확인하고, idx × sizeof(Rec)로 이동해 읽은 뒤, 다시 같은 위치로 돌아가 씁니다. 읽기 → 쓰기 전환 사이에 fseek가 있으므로 갱신 모드 규칙도 지켜집니다.

연습문제 18-9 서술형: 로그 유실 난이도 ★★☆

야간 배치가 세그멘테이션 오류로 죽었는데 로그 파일에는 시작 메시지만 있고 처리 중 메시지가 하나도 없었습니다. 원인으로 가장 의심되는 것과 해결책 두 가지를 쓰십시오.

정답과 해설 보기

로그 파일 스트림이 완전 버퍼 방식이라 처리 중 메시지가 버퍼에만 있다가 비정상 종료로 사라진 것입니다(시작 메시지는 다른 이유로 flush되었거나 버퍼가 한 번 찼던 경우). 해결책: (1) 로그를 쓸 때마다 fflush 호출, (2) setvbuf(log, NULL, _IOLBF, 0)로 줄 버퍼 설정, 또는 (3) stderr처럼 버퍼 없는 스트림 사용. 디스크까지 보장해야 하면 fsync를 추가합니다. 근본 원인인 세그멘테이션 오류는 코어 덤프와 디버거로 별도 분석합니다.

연습문제 18-10 코드 작성: 안전한 결과 파일 생성 난이도 ★★★

정산 결과 문자열 배열을 result.tmp에 줄 단위로 쓰고, 모든 쓰기와 fclose가 성공했을 때만 result.txt로 이름을 바꾸는 함수를 작성하십시오. 실패하면 임시 파일을 삭제합니다.

정답과 해설 보기

각 fputs의 반환값과 fclose의 반환값을 모두 검사합니다. 표준 C의 rename(성공 시 0)과 remove를 사용합니다. 윈도우의 rename은 대상 파일이 이미 있으면 실패하므로, 이식성을 고려하면 대상 파일을 먼저 처리하는 로직이 필요합니다(POSIX는 원자적으로 교체).

연습문제 18-11 출력 예측: 버퍼 난이도 ★★☆

터미널에서 실행할 때 화면에 무엇이 보입니까?

#include <stdio.h>
#include <stdlib.h>
int main(void)
{
    printf("1");
    printf("2\n");
    printf("3");
    abort();
}
정답과 해설 보기

"12"와 줄바꿈까지만 보이고 "3"은 보이지 않습니다(그 뒤에 Aborted 같은 셸 메시지). 터미널의 stdout은 줄 버퍼이므로 "2\n"에서 "12\n"이 출력되지만, "3"은 줄바꿈이 없어 버퍼에 남았다가 abort로 사라집니다. "3" 뒤에 fflush(stdout);을 넣으면 보입니다.
