변수의 영역과 데이터 공유

변수는 "어디에서 보이는가(범위)"와 "언제까지 살아 있는가(수명)"라는 두 개의 성질을 가집니다. 이 두 성질을 정확히 구분하지 못하면 지역 변수 주소를 반환하는 치명적인 버그, 전역 변수가 여기저기서 바뀌어 잔액이 틀어지는 버그를 만들게 됩니다. 이 장에서는 변수가 메모리의 어느 영역에 놓이는지 그림으로 확인하고, 함수끼리 데이터를 안전하게 주고받는 방법을 정리합니다.

이 장에서 배울 것

  • 범위(scope)와 수명(storage duration)의 차이를 설명할 수 있습니다.
  • 지역 변수, 전역 변수, 정적(static) 변수, register 변수의 특징을 비교할 수 있습니다.
  • 블록 스코프와 섀도잉(이름 가리기)이 어떻게 동작하는지 압니다.
  • 프로세스 메모리 구조(코드·데이터·BSS·힙·스택)를 그리고 각 변수가 어디에 놓이는지 말할 수 있습니다.
  • extern으로 여러 소스 파일이 변수를 공유하는 원리를 이해합니다.
  • 값 복사, 주소 전달, 반환값이라는 세 가지 데이터 공유 방법을 상황에 맞게 고를 수 있습니다.
  • 지역 변수 주소 반환 버그를 찾아내고 고칠 수 있습니다.
  • static 지역 변수로 거래 일련번호 생성기를 만들고, 전역 변수의 위험과 대안을 설명할 수 있습니다.

13-1변수 사용 영역

지금까지 우리는 변수를 대부분 main 함수 안에 선언해서 썼습니다. 함수를 배운 뒤에는 함수마다 자기 변수를 따로 선언했지요. 그런데 이런 질문을 해 본 적이 있을 것입니다. "main에 있는 변수 balance를 다른 함수에서 그냥 쓰면 안 되나요?", "함수가 끝나면 그 안의 변수는 어디로 가나요?", "같은 이름의 변수를 두 번 선언하면 왜 어떤 때는 에러가 나고 어떤 때는 안 나나요?"

이 질문들의 답은 모두 변수의 사용 영역에 있습니다. 변수에는 두 가지 독립된 성질이 있습니다.

  • 범위(scope, 유효 범위): 소스 코드에서 그 이름을 쓸 수 있는 구간입니다. 컴파일러가 이름을 찾을 때 쓰는 개념이며, 컴파일 시간의 성질입니다.
  • 수명(lifetime, 표준 용어로는 storage duration, 저장 기간): 그 변수의 메모리가 실제로 존재하는 시간입니다. 프로그램이 실행되는 동안의 성질이므로 실행 시간의 성질입니다.

이 둘은 자주 함께 움직이지만 같은 개념이 아닙니다. 이 장 전체가 이 한 문장을 이해하기 위한 과정이라고 해도 과언이 아닙니다.

범위와 수명은 다른 개념입니다

비유를 하나 들어 보겠습니다. 은행 지점의 금고를 생각해 봅시다. 금고는 지점이 문을 연 날부터 폐점할 때까지 계속 존재합니다(수명). 그런데 금고 열쇠를 가진 사람은 지점장과 출납 책임자뿐입니다(범위). 금고가 존재한다고 해서 아무나 열 수 있는 것은 아니지요. 반대로 창구 직원의 메모지는 고객 한 명을 응대하는 동안만 쓰고 버립니다. 그 창구 직원만 볼 수 있고(범위가 좁음), 응대가 끝나면 사라집니다(수명이 짧음).

C의 변수도 같습니다. static 지역 변수는 금고처럼 프로그램 내내 살아 있지만 그 함수 안에서만 이름으로 접근할 수 있습니다. 일반 지역 변수는 메모지처럼 함수가 실행되는 동안만 존재하고, 그 함수 안에서만 보입니다.

C 표준은 저장 기간을 네 가지로 나눕니다. 지금 단계에서는 앞의 세 가지를 정확히 알면 충분합니다.

범위는 C 표준에서 네 가지로 나뉩니다. 블록 범위(중괄호 안), 파일 범위(모든 함수 바깥), 함수 범위(goto 레이블만 해당), 함수 원형 범위(원형 선언의 매개변수 이름)입니다. 실무에서 중요한 것은 블록 범위와 파일 범위 두 가지입니다.

한 줄 요약

범위는 컴파일러가 이름을 찾는 규칙(어디서 보이나), 수명은 메모리가 존재하는 시간(언제까지 있나)입니다. static 지역 변수는 범위는 좁지만 수명은 깁니다. 이 차이를 섞어서 말하면 면접에서 바로 꼬리 질문이 들어옵니다.

지역 변수(자동 변수)

지역 변수(local variable)는 함수나 블록 안에서 선언한 변수입니다. 정식 이름은 자동 변수(automatic variable)이며, 예전에는 auto int a;처럼 auto 키워드를 붙일 수 있었습니다. 하지만 블록 안 변수는 기본값이 auto이므로 아무도 붙이지 않습니다. (C23에서는 auto가 C++처럼 타입 추론 용도로 의미가 바뀌었으니 더더욱 쓰지 않는 것이 좋습니다.)

지역 변수의 특징은 세 가지입니다.

  1. 선언된 블록 안에서만 이름이 보입니다. 다른 함수에서는 같은 이름을 써도 전혀 다른 변수입니다.
  2. 블록에 들어갈 때 메모리가 생기고, 블록을 나가면 사라집니다. 보통 스택(stack)이라는 영역에 잡힙니다.
  3. 초기화하지 않으면 값이 정해지지 않습니다. 이전에 그 자리를 쓰던 다른 함수의 흔적이 그대로 남아 있을 수 있습니다.

왜 그럴까? — 두 번 호출해도 왜 똑같이 1300일까요?

함수가 호출될 때마다 CPU는 스택에 그 함수만의 작업 공간인 스택 프레임(stack frame)을 새로 만듭니다. 지역 변수 balance는 이 프레임 안에 자리를 잡고, 선언문의 초기화 = 1000이 호출될 때마다 실행됩니다. 함수가 return하면 스택 포인터(rsp 레지스터)가 원래 자리로 돌아가면서 프레임 전체가 "버린 공간"이 됩니다. 두 번째 호출은 새 프레임을 만들고 다시 1000으로 초기화하므로 이전 호출의 결과를 기억하지 못합니다.

또 main의 balance와 deposit의 balance는 이름만 같을 뿐 서로 다른 프레임에 있는 서로 다른 메모리입니다. 컴파일러는 이름을 찾을 때 "지금 있는 블록 안"부터 찾기 때문에 deposit 안의 balance는 언제나 deposit의 것입니다.

초기화하지 않은 지역 변수

이 코드는 운 좋게 1800이 나올 수도 있고, 전혀 엉뚱한 값이 나올 수도 있습니다. 최적화 옵션(-O2)을 켜면 결과가 또 달라질 수 있습니다. C 표준에서 초기화하지 않은 자동 변수의 값은 불확정 값(indeterminate value)이며, 그 값을 읽는 것은 사실상 미정의 동작(UB)으로 취급해야 합니다.

왜 그럴까? — 전역 변수는 0인데 지역 변수는 왜 쓰레기값일까요?

전역 변수는 프로그램이 시작되기 전에 운영체제가 한꺼번에 0으로 채운 영역(BSS)에 놓입니다. 한 번만 하면 되니 비용이 거의 없습니다. 반면 지역 변수는 함수가 호출될 때마다 스택에 자리가 생깁니다. 이 자리를 매번 0으로 지우려면 호출할 때마다 추가 명령어가 필요합니다. C는 "필요 없는 일은 하지 않는다"는 성능 철학을 가진 언어라서, 초기화를 프로그래머에게 맡깁니다. 그래서 그 자리에 직전에 호출된 다른 함수가 남긴 값이 그대로 보이는 것입니다.

이렇게 해결합니다

  • 지역 변수는 선언과 동시에 초기화하는 습관을 들입니다: int total = 0;
  • 컴파일할 때 gcc -Wall -Wextra -O2를 켜면 -Wmaybe-uninitialized 경고가 이런 실수를 잡아 줍니다(최적화를 켜야 분석이 더 정확해집니다).
  • 배열은 int arr[10] = {0};처럼 쓰면 모든 원소가 0이 됩니다.

블록 스코프와 섀도잉

중괄호 { }로 묶인 영역을 블록(block)이라고 합니다. 함수 본문만 블록이 아니라 if, for, while의 중괄호, 심지어 아무 조건 없이 그냥 쓴 중괄호도 모두 블록입니다. C99부터는 for (int i = 0; ...)처럼 for문의 초기식에서 선언한 변수도 그 for문 블록 안에서만 보입니다.

그렇다면 바깥 블록과 안쪽 블록에서 같은 이름을 선언하면 어떻게 될까요? 같은 블록 안에서 같은 이름을 두 번 선언하면 컴파일 에러(redefinition)이지만, 안쪽 블록에서 새로 선언하는 것은 허용됩니다. 이때 안쪽 블록에서는 안쪽 변수가 바깥 변수를 가립니다. 이것을 섀도잉(shadowing, 이름 가리기)이라고 합니다.

왜 그럴까? — 1번 출력은 왜 5일까요?

범위는 선언된 지점부터 시작합니다. main 블록의 int rate = 3;은 두 번째 줄에서 선언되었으므로, 그 앞의 첫 번째 printf 시점에서는 아직 main의 rate가 범위에 들어오지 않았습니다. 그래서 컴파일러는 바깥(파일 범위)에서 rate를 찾아 전역 변수 5를 사용합니다. 이렇게 같은 블록 안에서도 줄에 따라 같은 이름이 다른 변수를 가리킬 수 있어 매우 헷갈립니다.

섀도잉은 컴파일러 입장에서는 완전히 다른 두 변수입니다. 메모리 주소도 다릅니다. 안쪽 블록의 rate++는 안쪽 변수만 바꾸므로 블록을 나오면 바깥 변수는 그대로입니다.

자주 하는 실수 — 섀도잉으로 합계가 0이 되는 버그

복사·붙여넣기를 하다가 타입까지 같이 붙여넣는 실수입니다. 컴파일 에러가 나지 않으므로 발견하기 어렵습니다.

이렇게 해결합니다

  • gcc -Wshadow 옵션을 켜면 "declaration of 'total' shadows a previous local" 경고가 나옵니다. 금융권 코딩 표준 중에는 섀도잉 자체를 금지하는 곳이 많습니다.
  • 변수 이름을 의미 있게 구별해서 짓습니다(total과 line_amount처럼).
  • 전역 변수에는 g_ 접두어를 붙이는 관례(g_rate)를 쓰면 지역 변수와 이름이 겹칠 일이 줄어듭니다.

전역 변수

전역 변수(global variable)는 모든 함수 바깥, 즉 파일 범위에 선언한 변수입니다. 선언 지점부터 그 파일의 끝까지 모든 함수에서 이름으로 접근할 수 있고, 수명은 프로그램 전체입니다. 초기화하지 않으면 0으로 자동 초기화됩니다(포인터는 널 포인터, 실수는 0.0).

매개변수로 넘기지 않아도 모든 함수가 같은 g_balance를 보므로 편리해 보입니다. 하지만 이 편리함이 바로 위험의 근원입니다. 이 문제는 13-2절의 마지막 소주제에서 자세히 다룹니다. 여기서는 전역 변수의 동작 원리만 정확히 정리합니다.

왜 그럴까? — 전역 변수는 왜 0으로 초기화될까요?

컴파일러는 초기값이 있는 전역 변수(int a = 7;)를 실행 파일의 .data 섹션에 값과 함께 기록합니다. 반면 초기값이 없거나 0인 전역 변수는 실행 파일에 값을 기록하지 않고 "이 영역은 크기가 몇 바이트다"라는 정보만 .bss 섹션에 남깁니다. 프로그램을 실행하면 운영체제(로더)가 BSS 크기만큼 메모리를 확보하면서 0으로 채운 페이지를 줍니다. 그래서 별도의 초기화 코드 없이도 0이 보장되고, 실행 파일 크기도 줄어듭니다. 예를 들어 int big[1000000];을 전역으로 선언해도 실행 파일이 4MB 커지지 않습니다.

자주 하는 실수 — 전역 변수 초기화에 함수 호출 사용

정적 저장 기간을 가진 변수(전역, static)의 초기값은 컴파일 시간에 계산할 수 있는 상수식이어야 합니다. 프로그램이 시작되기 전에 값이 실행 파일에 박혀 있어야 하기 때문입니다. 실행 중에 계산해야 하는 값이라면 main 시작 부분에서 init() 함수를 만들어 대입합니다.

정적 변수(static)

static은 C에서 가장 헷갈리는 키워드 중 하나입니다. 어디에 붙이느냐에 따라 의미가 다르기 때문입니다. 면접에서도 "static의 의미를 모두 말해 보라"는 질문이 매우 자주 나옵니다.

static 지역 변수

지역 변수 앞에 static을 붙이면 그 변수는 스택이 아니라 데이터 영역(또는 BSS)에 놓입니다. 그래서 함수가 끝나도 사라지지 않고, 다음 호출 때 이전 값을 그대로 기억합니다. 초기화는 프로그램 시작 전에 딱 한 번만 일어납니다.

왜 그럴까? — static int static_cnt = 0; 줄은 매번 실행되지 않나요?

소스 코드에서는 함수 안에 적혀 있으니 호출할 때마다 0이 대입될 것처럼 보입니다. 하지만 이 줄은 실행되는 "명령"이 아니라 정의입니다. 컴파일러는 static_cnt를 함수의 스택 프레임이 아니라 프로그램 전체에 하나뿐인 데이터 영역에 배치하고, 초기값 0은 실행 파일(BSS)에 기록합니다. 함수의 기계어에는 "0을 대입하라"는 명령이 아예 없습니다. 그래서 호출할 때마다 같은 주소의 같은 변수를 계속 증가시키는 것입니다.

컴파일러는 static_cnt에 내부적으로 static_cnt.0처럼 다른 함수의 같은 이름과 겹치지 않는 고유한 심볼 이름을 붙입니다. 그래서 여러 함수가 각자 static int count를 가져도 충돌하지 않습니다.

static 전역 변수와 static 함수 — 파일 안에 숨기기

전역 변수는 기본적으로 외부 연결(external linkage)을 가집니다. 즉 다른 소스 파일에서 extern으로 선언하면 그 변수에 접근할 수 있습니다. 여기에 static을 붙이면 내부 연결(internal linkage)이 되어 그 파일 밖에서는 보이지 않습니다. 수명은 원래도 프로그램 전체이므로 바뀌지 않습니다.

다른 파일은 s_total_deposit을 직접 바꿀 수 없고, 반드시 add_deposit()을 거쳐야 합니다. 그 안에서 금액 검증을 하니 잘못된 값이 들어올 수 없습니다. 이것이 C에서 할 수 있는 캡슐화(정보 은닉)의 기본 형태입니다.

여기서 잠깐 — 이름 접두어 관례

실무 코딩 표준에서는 범위를 이름만 보고 알 수 있도록 접두어를 붙이는 경우가 많습니다. 전역은 g_, 파일 static은 s_ 같은 식입니다. 수십만 줄의 계정계 소스를 유지보수할 때 "이 변수가 어디서 바뀔 수 있나?"를 이름만으로 판단할 수 있어 장애 분석 시간이 크게 줄어듭니다.

참고로 함수의 주소(main)를 void *로 바꿔 %p로 찍는 것은 C 표준이 보장하지 않으므로(함수 포인터와 객체 포인터는 다른 종류) 이 예제에서는 뺐습니다. 리눅스(POSIX)에서는 실제로 동작하며 15장에서 함수 포인터를 다룰 때 다시 이야기합니다.

계정계 온라인 서버나 일마감 배치 프로그램이 비정상 종료되면 운영체제는 코어 덤프(core dump) 파일을 남깁니다. 장애 분석 담당자는 gdb로 코어 파일을 열어 "죽는 순간 스택에 어떤 함수들이 쌓여 있었는지(backtrace)", "전역 변수의 값이 무엇이었는지"를 확인합니다. 이때 메모리 구조를 모르면 아무것도 읽을 수 없습니다.

  • 힙 주소의 내용이 깨져 있다 → 버퍼 오버런이나 해제 후 사용(16장)

register 변수

register는 "이 변수는 자주 쓰니 메모리 대신 CPU 레지스터에 두면 좋겠다"고 컴파일러에게 부탁하는 키워드입니다. 레지스터는 CPU 안에 있는 아주 빠른 저장소로, 메모리(특히 캐시에 없는 메인 메모리) 접근보다 훨씬 빠릅니다.

왜 그럴까? — register 변수는 왜 주소(&)를 구할 수 없을까요?

주소라는 것은 메모리의 위치 번호입니다. 레지스터는 메모리가 아니라 CPU 내부의 저장소(rax, rbx 같은 이름이 있음)이므로 메모리 주소가 없습니다. C 표준은 실제로 레지스터에 놓였는지와 관계없이 register로 선언한 변수에 &를 쓰면 컴파일 에러를 내도록 정했습니다.

현대 컴파일러(gcc, clang)는 최적화 단계에서 어떤 변수를 레지스터에 둘지 사람보다 훨씬 잘 판단합니다(레지스터 할당 알고리즘). 그래서 register는 사실상 무시되며, C++17에서는 아예 키워드의 의미가 삭제되었습니다. 지금은 "옛날 코드에서 보면 의미를 알아볼 수 있는 정도"로 충분합니다.

extern 입문 — 여러 파일이 변수를 공유하는 방법

실무 프로그램은 파일 하나로 만들지 않습니다. 계좌 처리, 이체 처리, 로그 기록이 각각 다른 소스 파일에 있고 이것들을 따로 컴파일한 뒤 링커(linker)가 하나의 실행 파일로 합칩니다. 이때 한 파일에 정의된 전역 변수를 다른 파일에서 쓰려면 extern 선언이 필요합니다.

먼저 두 용어를 구분해야 합니다.

  • 정의(definition): 메모리를 실제로 만드는 것. int g_tx_count = 0; 프로그램 전체에서 딱 한 번만 있어야 합니다.
  • 선언(declaration): "이런 이름과 타입의 변수가 어딘가에 있다"고 컴파일러에게 알려 주는 것. extern int g_tx_count; 메모리를 만들지 않으며 여러 번 해도 됩니다.

실무에서는 extern 선언을 각 .c 파일에 직접 쓰지 않고 헤더 파일에 모아 둡니다.

gcc -Wall -c ledger.c        # ledger.o 생성
gcc -Wall -c main.c          # main.o 생성
gcc -o bank main.o ledger.o  # 링크
./bank

왜 그럴까? — 헤더에 int g_tx_count = 0;을 쓰면 왜 안 될까요?

#include는 헤더 내용을 그 자리에 그대로 붙여넣는 전처리입니다. 헤더에 정의를 쓰면 그 헤더를 포함한 모든 .c 파일에 각각 g_tx_count의 정의가 생깁니다. 각 파일을 컴파일할 때는 문제가 없지만, 링커가 합칠 때 "multiple definition of 'g_tx_count'"라며 에러를 냅니다. 그래서 규칙은 헤더에는 extern 선언, .c 파일 하나에만 정의입니다.

참고로 초기값 없이 int g_tx_count;만 쓴 것은 C에서 "잠정적 정의(tentative definition)"라는 특수한 취급을 받습니다. 예전 gcc(9 이하)는 이것을 여러 파일에 써도 하나로 합쳐 주었지만(-fcommon), gcc 10부터 기본값이 -fno-common으로 바뀌어 링크 에러가 납니다. 오래된 소스를 새 컴파일러로 빌드할 때 이 에러를 자주 만나게 됩니다.

자주 하는 실수 — 정의와 extern 선언의 타입 불일치

ledger.c에 long long g_total;이라고 정의해 놓고 main.c에서 extern int g_total;로 선언하면, 컴파일러는 파일을 따로 보기 때문에 이 불일치를 알지 못하고 링커도 이름만 맞춰 보므로 에러가 나지 않습니다. 결과는 미정의 동작이며, main.c에서는 8바이트 중 4바이트만 읽어 엉뚱한 값을 보게 됩니다.

이렇게 해결합니다

정의하는 .c 파일에서도 자기 헤더를 반드시 #include합니다(위 ledger.c처럼). 그러면 같은 파일 안에서 extern int g_total;과 long long g_total;이 만나게 되어 컴파일러가 "conflicting types" 에러로 바로 잡아 줍니다.

13-2함수의 데이터 공유 방법

함수는 각자 자기 스택 프레임 안에 갇혀 있습니다. 그렇다면 함수끼리 데이터를 어떻게 주고받을까요? 방법은 크게 네 가지입니다.

  1. 값 복사(call by value): 인수의 값을 복사해서 넘깁니다. 호출된 함수는 복사본만 만집니다.
  2. 주소 전달(포인터 전달): 변수의 주소를 복사해서 넘깁니다. 호출된 함수가 그 주소로 원본을 직접 읽고 씁니다.
  3. 반환값: 함수가 계산 결과를 return으로 돌려줍니다.
  4. 전역 변수: 모두가 같은 변수를 봅니다. 가장 쉽지만 가장 위험합니다.

이 절에서는 각 방법의 원리를 메모리 그림으로 확인하고, 어떤 상황에서 무엇을 써야 하는지 결정하는 기준을 세웁니다.

값 복사 — 원본은 절대 바뀌지 않습니다

C의 함수 호출은 언제나 값에 의한 전달(call by value)입니다. 이것은 예외가 없는 규칙입니다. 인수로 쓴 식의 값을 계산해서 매개변수라는 새 지역 변수에 복사합니다.

왜 그럴까? — C는 왜 기본을 "복사"로 정했을까요?

복사는 안전합니다. 호출된 함수가 무슨 짓을 해도 호출한 쪽의 변수는 망가지지 않습니다. 함수를 읽는 사람은 "이 함수가 내 변수를 바꿀까?"를 걱정하지 않아도 됩니다. 또 int, long long, 포인터처럼 작은 값은 x86-64에서 레지스터(rdi, rsi 등)로 바로 전달되므로 복사 비용이 거의 0입니다.

단점은 두 가지입니다. ① 호출한 쪽의 변수를 바꿀 수 없고, ② 큰 구조체를 넘기면 그 크기만큼 복사 비용이 듭니다. 이 두 가지를 해결하는 것이 다음 소주제인 주소 전달입니다.

주소 전달 — 원본의 위치를 알려 줍니다

함수가 호출한 쪽의 변수를 바꾸게 하려면, 변수의 값 대신 주소를 넘깁니다. 주소도 결국 "값"이므로 복사되어 전달되지만, 복사된 주소로 원래 변수를 찾아갈 수 있습니다. 이체 업무에 비유하면 돈(값)을 봉투에 담아 주는 대신 계좌번호(주소)를 알려 주는 것입니다. 계좌번호를 받은 사람은 그 계좌에 직접 입금할 수 있습니다.

여기서 잠깐 — "C에도 call by reference가 있나요?"

엄밀히 말하면 없습니다. C++의 참조(int &r)처럼 언어 차원에서 별명을 만드는 기능이 C에는 없습니다. C에서 하는 것은 "포인터 값을 복사해서 전달(call by value of pointer)"하여 참조 전달과 같은 효과를 내는 것입니다. 면접에서 "C에서 call by reference는 어떻게 하나요?"라고 물으면 이 구분을 짚어 주는 것이 좋은 답입니다. 증거로, 함수 안에서 pa = NULL;을 해도 main의 &acc1은 전혀 바뀌지 않습니다. 포인터 자체는 복사본이기 때문입니다.

const 포인터로 "읽기 전용 주소 전달"

큰 데이터를 복사 없이 넘기고 싶지만 함수가 바꾸면 안 되는 경우가 많습니다. 예를 들어 거래 금액 배열의 합계를 구하는 함수는 배열을 읽기만 합니다. 이때는 const를 붙여 의도를 드러내고 컴파일러가 실수를 막게 합니다.

15000 + 230000 = 245000, + 4800 = 249800, + 99000 = 348800입니다. 함수 원형만 보고도 "이 함수는 내 배열을 바꾸지 않는다"는 것을 알 수 있다는 점이 핵심입니다.

잔액 포인터와 출금액을 받아, 잔액이 충분하면 출금하고 0을, 부족하면 잔액을 바꾸지 않고 -1을 반환하는 함수 int withdraw(long long *balance, long long amount)를 작성하세요. 금액이 0 이하이면 -2를 반환합니다.

정답과 해설 보기

잔액을 바꿔야 하므로 잔액은 주소로 받고, 출금액은 읽기만 하므로 값으로 받습니다. 성공/실패는 반환값으로 알립니다. 이렇게 "바꿀 대상은 포인터, 결과 상태는 반환값"으로 나누는 것은 C 라이브러리와 금융권 공통 모듈에서 가장 흔한 함수 설계입니다.

잔액 부족일 때 잔액을 먼저 빼고 나중에 되돌리는 방식은 피해야 합니다. 중간에 다른 코드가 끼어들면(멀티스레드, 시그널) 음수 잔액이 잠깐이라도 보일 수 있기 때문입니다. 검사 후 변경이 원칙입니다.

반환값으로 공유하기

함수가 계산한 결과를 돌려주는 가장 자연스러운 방법은 return입니다. 반환값은 x86-64에서 보통 rax 레지스터에 담겨 돌아오고, 호출한 쪽은 이 값을 변수에 복사해 받습니다. 즉 반환도 값 복사입니다.

계산을 따라가 봅시다. 10,000,000 × 350 = 3,500,000,000, × 90 = 315,000,000,000. 이를 10000 × 365 = 3,650,000으로 나누면 86,301.369...이고 정수 나눗셈이므로 86,301원입니다. 곱셈을 먼저 하고 나눗셈을 나중에 해서 절사 오차를 줄였고, long long을 써서 3천억이 넘는 중간값도 넘치지 않게 했습니다.

여러 값을 돌려주고 싶을 때

return은 값을 하나만 돌려줄 수 있습니다. 이자와 세금을 함께 돌려주고 싶다면 방법은 두 가지입니다.

  1. 출력 매개변수(out parameter): 결과를 담을 변수의 주소를 받아서 거기에 씁니다. 반환값은 성공/실패 코드로 씁니다.
  2. 구조체 반환: 여러 값을 구조체로 묶어 한 번에 반환합니다(구조체는 17장에서 자세히 배웁니다).

86301 × 154 = 13,290,354, ÷ 1000 = 13,290(절사). 86301 − 13290 = 73011입니다. (실제 세금 계산은 세목별 원 단위 절사 규칙이 따로 있으나 여기서는 단순화했습니다.)

포인터 반환과 지역 변수 주소 반환 버그

함수가 포인터를 반환하는 것은 자연스러운 일입니다. 문제는 무엇의 주소를 반환하느냐입니다. 다음은 신입 개발자가 가장 자주 만드는, 그리고 테스트에서는 잘 드러나지 않아 운영에서 터지는 버그입니다.

왜 그럴까? — 어떤 때는 제대로 출력되는 이유

return을 하면 스택 포인터가 올라갈 뿐, 그 자리의 바이트를 지우지는 않습니다. 그래서 반환 직후 바로 그 메모리를 읽으면 우연히 문자열이 남아 있을 수 있습니다. 하지만 printf가 호출되면 printf의 스택 프레임이 바로 그 자리에 만들어지고 지역 변수들이 내용을 덮어씁니다. 그래서 출력이 깨지거나, 일부만 나오거나, 프로그램이 죽습니다. 최신 gcc는 최적화 시 이런 함수가 아예 NULL을 반환하도록 코드를 만들기도 해서 곧바로 Segmentation fault가 나기도 합니다. 어느 쪽이든 C 표준상 미정의 동작입니다. 수명이 끝난 객체를 가리키는 포인터의 값 자체가 불확정이 되기 때문입니다.

핵심은 "포인터의 수명과 가리키는 대상의 수명은 별개"라는 점입니다. m은 main의 지역 변수라 계속 살아 있지만, m이 가리키는 buf는 이미 수명이 끝났습니다.

이렇게 해결합니다 — 세 가지 방법

방법 1. 호출한 쪽이 버퍼를 제공(가장 권장) — 수명을 호출한 쪽이 관리합니다. 표준 라이브러리의 snprintf, strncpy가 이 방식입니다.

13자리 문자열에서 i는 3부터 시작하고 조건 i + 4 < 13은 i가 8까지 참이므로 인덱스 3~8, 총 6자리가 *가 됩니다. 앞 3자리 "110", 뒤 4자리 "8901"이 남습니다.

방법 2. static 지역 배열 반환 — 수명이 프로그램 전체이므로 댕글링은 아닙니다. 하지만 다음 호출이 이전 결과를 덮어쓰고, 여러 스레드가 동시에 부르면 결과가 섞입니다. 표준 함수 asctime, strtok, localtime이 이런 구조라 스레드 안전하지 않고, 그래서 localtime_r 같은 재진입 버전이 따로 있습니다.

방법 3. 힙에 할당해서 반환 — 호출한 쪽이 반드시 free해야 합니다(16장에서 소유권 규칙과 함께 자세히 다룹니다).

자주 하는 실수 — 문자열 리터럴 주소 반환은 괜찮을까?

문자열 리터럴은 정적 저장 기간을 가지므로 반환해도 안전합니다. 다만 char name[] = "입금"; return name;은 리터럴을 지역 배열에 복사한 것이므로 버그입니다. 생김새는 비슷하지만 메모리 위치가 완전히 다르다는 점을 꼭 구분하세요. 반환형에 const를 붙여 호출자가 리터럴을 수정하지 못하게 하는 것도 중요합니다.

static 지역 변수로 거래 일련번호 생성하기

은행의 모든 거래에는 고유한 거래 일련번호가 붙습니다. 같은 날 같은 단말에서 일어난 거래라도 번호가 겹치면 안 되며, 장애 분석이나 대사(맞춰 보기) 작업에서 이 번호로 거래를 추적합니다. 일련번호 생성기는 "이전에 몇 번까지 발급했는지"를 기억해야 하므로 상태가 필요합니다. 이 상태를 전역 변수에 두면 누구나 실수로 바꿀 수 있습니다. static 지역 변수에 두면 그 함수만 상태를 만질 수 있습니다.

왜 그럴까? — 왜 전역 변수 대신 static 지역 변수일까요?

last_date와 seq는 수명이 프로그램 전체이므로 호출과 호출 사이에 값이 유지됩니다(전역 변수와 같음). 하지만 범위가 next_tx_no 함수 안이므로 다른 함수가 실수로 seq = 0;을 할 수 없습니다(전역 변수와 다름). 즉 "수명은 길게, 범위는 좁게"라는 원칙을 정확히 구현한 것입니다. 일련번호가 꼬이는 버그가 생기면 이 함수 하나만 보면 됩니다.

은행 시스템에서는 — 실제 일련번호 채번

위 예제는 프로세스 하나 안에서만 유일한 번호를 만듭니다. 실제 계정계는 수십~수백 개의 서버 프로세스가 동시에 거래를 처리하므로, static 변수 하나로는 번호가 겹칩니다. 그래서 실무의 채번(번호 매기기)은 다음과 같이 합니다.

  • DB 시퀀스 또는 채번 테이블을 잠금(lock)과 함께 증가시킵니다.
  • 서버/프로세스 ID를 번호에 포함시켜(예: 날짜-서버02-000123) 프로세스별 static 카운터로도 전체 유일성을 보장합니다.
  • 프로세스가 재시작하면 static 변수는 0으로 돌아가므로, 시작 시 파일이나 DB에서 마지막 번호를 읽어 와 복구합니다.
  • 멀티스레드 서버에서는 static 변수의 seq++가 원자적이지 않으므로 뮤텍스나 C11 _Atomic이 필요합니다(PART 2의 동시성 장에서 다룹니다).

이처럼 "static 변수 = 프로세스 안의 상태"라는 범위를 정확히 이해해야 설계 오류를 피할 수 있습니다.

전역 변수의 위험성과 대안

전역 변수는 처음 배울 때 매우 편리해 보입니다. 매개변수를 줄줄이 넘길 필요 없이 어디서나 쓸 수 있으니까요. 하지만 프로그램이 커지면 전역 변수는 가장 비싼 기술 부채가 됩니다.

고객은 1,234,567원을 이체했는데 기록은 1,234,000원입니다. 567원이 사라졌습니다. 수수료 계산 담당자가 "계산 편의를 위해" 절사를 했는데, 그 변수가 전역이라 이체 금액 자체가 바뀌어 버린 것입니다. transfer 함수만 읽어서는 이 버그를 절대 찾을 수 없습니다.

왜 그럴까? — 전역 변수가 위험한 이유 다섯 가지

  1. 추적 불가: 값이 틀렸을 때 그 변수를 바꿀 수 있는 곳이 프로그램 전체입니다. 함수 하나만 보고 동작을 이해할 수 없습니다.
  2. 숨은 결합(coupling): 함수 원형에 드러나지 않는 의존 관계가 생깁니다. calc_fee(void)는 입력이 없어 보이지만 실제로는 g_amount를 읽고 씁니다.
  3. 재진입 불가: 재귀 호출이나 시그널 핸들러 안에서 같은 함수가 다시 불리면 전역 상태가 뒤섞입니다.
  4. 스레드 안전성 없음: 두 스레드가 동시에 g_amount를 쓰면 경쟁 조건(race condition)이 생깁니다. 온라인 거래 서버에서 치명적입니다.
  5. 테스트 어려움: 함수를 단위 테스트하려면 전역 상태를 매번 맞춰 놓아야 하고, 테스트 순서에 따라 결과가 달라집니다.

이렇게 해결합니다 — 전역 변수의 대안

대안 1. 매개변수와 반환값으로 명시적으로 주고받기

대안 2. 관련 상태를 하나의 "문맥(context)" 구조체로 묶어 포인터로 전달 — 매개변수가 너무 많아지는 문제를 해결합니다(구조체는 17장에서 자세히).

대안 3. 꼭 필요한 공유 상태는 파일 static + 접근 함수 — 13-1-5에서 본 account.c처럼, 변수는 숨기고 검증이 들어간 함수만 공개합니다.

대안 4. 읽기 전용 설정값은 const 전역 — 바뀌지 않는 값(최대 이체 한도 상수 등)은 const로 선언하면 전역이어도 위험이 거의 없습니다.

많은 금융권 C 코딩 표준은 다음과 같은 규칙을 둡니다.

  • 업무 로직(이체, 이자 계산)에서 전역 변수 사용 금지. 거래 데이터는 반드시 매개변수(거래 문맥 구조체 포인터)로 전달.
  • 프레임워크가 제공하는 공통 영역(시스템 일자, 단말 정보 등)은 읽기 전용 접근 함수로만 조회.
  • 모듈 내부 상태는 static으로 숨기고, 헤더에는 extern 변수를 두지 않음.
  • 정적 분석 도구(코드 인스펙션)로 전역 변수 신규 추가를 자동 검출하여 리뷰.

특히 온라인 서버는 하나의 프로세스가 수천 건의 거래를 연속으로 처리하므로, 이전 거래가 전역 변수에 남긴 값이 다음 거래에 섞여 들어가는 사고(예: 이전 고객의 수수료 면제 플래그가 남아 다음 고객도 면제됨)가 실제로 일어납니다. 거래 시작 시 문맥 구조체를 memset으로 초기화하는 것이 기본 패턴입니다.

다음 코드는 일마감 배치에서 지점별 합계를 출력합니다. 지점 2의 합계가 틀리게 나옵니다. 원인을 찾고 전역 변수 없이 고치세요.

정답과 해설 보기

지점 2의 올바른 합계는 1500인데 4500이 나왔습니다. g_sum이 전역이라 지점 1의 합계 3000이 남아 있는 상태에서 지점 2를 더했기 때문입니다(3000 + 1500). 전역 상태를 초기화하는 책임이 아무에게도 없다는 것이 근본 원인입니다. 합계를 지역 변수로 바꾸고 반환값으로 돌려주면 매 호출마다 0에서 시작하는 것이 언어 차원에서 보장됩니다.

핵심 정리

  • 범위(scope)는 이름이 보이는 소스 코드 구간(컴파일 시간), 수명(storage duration)은 메모리가 존재하는 시간(실행 시간)입니다.
  • 지역 변수는 블록 범위 + 자동 수명이며, 초기화하지 않으면 값이 불확정입니다. 전역·static 변수는 0으로 초기화됩니다.
  • 범위는 선언 지점부터 시작합니다. 안쪽 블록에서 같은 이름을 선언하면 바깥 이름을 가리는 섀도잉이 일어나며, -Wshadow로 검출합니다.
  • static은 지역 변수에 붙으면 수명을 늘리고, 전역 변수·함수에 붙으면 연결을 내부로 바꿔 파일 밖에서 숨깁니다.
  • 프로세스 메모리는 코드(.text), 읽기 전용(.rodata), 데이터(.data), BSS, 힙, 스택으로 나뉩니다. 스택은 크기 제한이 있어 큰 배열을 지역 변수로 두면 스택 오버플로가 납니다.
  • register는 레지스터 배치 요청이며 주소를 구할 수 없습니다. 현대 컴파일러에서는 사실상 무의미합니다.
  • extern은 선언(메모리 없음), 정의는 프로그램 전체에 하나. 헤더에는 extern 선언, .c 하나에 정의, 정의하는 .c도 헤더를 포함합니다.
  • C의 인수 전달은 항상 값 복사입니다. 원본을 바꾸려면 주소를 값으로 넘기며, 읽기만 할 큰 데이터는 const 포인터로 넘깁니다.
  • 지역 변수(매개변수 포함)의 주소를 반환하면 댕글링 포인터가 됩니다. 호출자 제공 버퍼, static 버퍼, 힙 할당 중 하나로 해결합니다.
  • static 지역 변수는 "수명은 길게, 범위는 좁게"를 구현하며 일련번호 생성기 같은 상태 보존에 적합합니다. 단, 프로세스 단위·스레드 비안전이라는 한계가 있습니다.
  • 전역 변수는 추적 불가, 숨은 결합, 재진입·스레드 문제를 일으킵니다. 매개변수, 문맥 구조체, 파일 static + 접근 함수, const 전역으로 대체합니다.

Q4. 스택과 힙의 차이는 무엇인가요?

스택은 함수 호출 시 자동으로 프레임이 생기고 반환 시 자동으로 해제되는 영역으로, 스택 포인터만 움직이면 되어 할당이 매우 빠르지만 크기가 작고(리눅스 기본 8MB) 수명이 함수에 묶여 있습니다. 힙은 malloc/free로 프로그래머가 직접 수명을 관리하는 영역으로, 크기가 크고 실행 중 크기를 정할 수 있지만 할당자 관리 비용이 있고 누수나 단편화 위험이 있습니다.

Q5. 지역 변수의 주소를 반환하면 왜 문제가 되나요? 어떻게 고치나요?

지역 변수는 함수의 스택 프레임에 있고 함수가 반환되면 그 수명이 끝납니다. 반환된 포인터는 이미 해제된 영역을 가리키는 댕글링 포인터가 되고, 다음 함수 호출이 그 자리를 덮어써 값이 깨지며 이는 미정의 동작입니다. 해결책은 호출자가 버퍼를 넘겨주는 방식, static 버퍼(재진입 불가 주의), 힙에 할당 후 호출자가 해제하는 방식이 있습니다.
꼬리 질문 대비: "매개변수의 주소를 반환하면?" → 매개변수도 지역 변수라서 똑같이 댕글링입니다.

C는 오직 call by value만 지원합니다. 포인터를 넘기는 것도 주소값을 복사해 넘기는 call by value이며, 그 주소를 역참조해 원본을 바꿀 수 있으므로 call by reference와 같은 효과를 낼 뿐입니다. 함수 안에서 포인터 매개변수 자체에 다른 주소를 대입해도 호출자의 포인터는 바뀌지 않는다는 점이 그 증거입니다.
꼬리 질문 대비: "그럼 함수 안에서 호출자의 포인터 자체를 바꾸려면?" → 이중 포인터(int **)를 넘깁니다(15장).

Q7. 전역 변수를 지양해야 하는 이유는?

어디서든 값을 바꿀 수 있어 버그 원인 추적이 어렵고, 함수 원형에 드러나지 않는 의존성이 생겨 모듈 간 결합도가 높아집니다. 또 재진입성과 스레드 안전성이 없어 멀티스레드 서버에서 경쟁 조건을 일으키고, 단위 테스트를 어렵게 만듭니다. 대신 매개변수·반환값, 문맥 구조체, 파일 static과 접근 함수를 사용합니다.
꼬리 질문 대비: "그래도 꼭 써야 한다면?" → const로 읽기 전용화하거나, 쓰기는 뮤텍스로 보호된 접근 함수로 제한합니다.

Q8. extern 키워드는 무엇이고, 선언과 정의의 차이는?

extern은 다른 번역 단위에 정의된 변수나 함수가 있음을 알리는 선언입니다. 선언은 이름과 타입만 알려 줄 뿐 메모리를 만들지 않으므로 여러 번 가능하고, 정의는 실제 메모리를 할당하므로 프로그램 전체에서 한 번만 있어야 합니다(One Definition). 헤더에 정의를 넣으면 여러 파일에서 포함될 때 링커가 multiple definition 에러를 냅니다.
꼬리 질문 대비: "extern "C"는?" → C++에서 이름 맹글링을 끄고 C 방식 심볼로 링크하게 하는 것으로 C 자체의 기능은 아닙니다.

Q9. static 지역 변수를 쓰는 함수는 스레드 안전한가요?

아닙니다. static 지역 변수는 프로세스에 하나뿐이고 모든 스레드가 공유하므로, 두 스레드가 동시에 seq++ 같은 읽기-수정-쓰기를 하면 경쟁 조건이 생깁니다. strtok, localtime이 대표적인 비안전 함수이며 그래서 strtok_r, localtime_r 같은 재진입 버전이 존재합니다. 해결하려면 뮤텍스, 원자 연산(C11 _Atomic), 또는 상태를 호출자가 넘기도록 설계합니다.
꼬리 질문 대비: "재진입(reentrant)과 스레드 안전의 차이는?" → 재진입은 실행 중 다시 호출되어도(시그널 등) 안전한 것으로, 보통 공유 상태가 아예 없어야 하며 더 엄격한 조건입니다.

Q10. 초기화하지 않은 지역 변수의 값은 무엇인가요? 왜 0이 아닌가요?

불확정 값이며 읽으면 사실상 미정의 동작입니다. 지역 변수는 매 호출마다 스택에 자리가 생기는데, 매번 0으로 지우는 비용을 C는 강제하지 않기 때문에 이전 함수가 남긴 값이 그대로 보입니다. 반면 정적 저장 기간 변수는 시작 시 한 번만 0으로 채우면 되므로 0이 보장됩니다.
꼬리 질문 대비: "보안상 문제는?" → 이전 함수의 민감 데이터(비밀번호 등)가 노출될 수 있어 정보 유출 취약점이 됩니다.

헤더 내용이 a.c와 b.c에 각각 복사되어 g_max_transfer의 정의가 두 개 생깁니다. 링커가 "multiple definition of 'g_max_transfer'" 에러를 냅니다. 해결책은 헤더에는 extern int g_max_transfer;(선언)만 두고, config.c 한 곳에 int g_max_transfer = 50000000;(정의)를 두는 것입니다. 더 좋은 방법은 한도가 바뀌지 않는 값이라면 헤더에 #define MAX_TRANSFER 50000000LL이나 static const long long MAX_TRANSFER = 50000000LL;을 두는 것입니다(static이므로 파일마다 별도 사본이 되어 충돌하지 않음).

연습문제 13-7 코드 작성 난이도 ★★☆

호출될 때마다 1, 2, 3...을 반환하되, reset 인자가 1이면 0으로 초기화하고 0을 반환하는 함수 int counter(int reset)을 전역 변수 없이 작성하세요.

정답과 해설 보기

상태 n은 static이라 호출 사이에 유지되고, 범위가 함수 안이므로 다른 코드가 직접 건드릴 수 없습니다. 초기화도 정해진 통로(reset 인자)를 통해서만 가능합니다.

연습문제 13-8 출력 예측 난이도 ★★★

정답과 해설 보기
  • p(x): main의 x(5)가 복사되어 p의 매개변수 x가 50이 됩니다. main의 x는 그대로 5.
  • q(&x): main의 x 주소를 넘깁니다. q 안의 x는 전역 x(1)입니다(q에는 지역 x가 없음). 그래서 *y = 5 + 1 = 6, main의 x가 6이 됩니다.
  • 블록 안의 extern int x;는 블록 범위에서 파일 범위의 전역 x를 가리키는 선언을 만들어 main의 x를 가립니다. 전역 x가 1 + 100 = 101.
  • 블록을 나오면 다시 main의 x(6)가 보입니다.

블록 안 extern 선언은 실무에서 쓰지 않는 것이 좋지만, 이름 해석 규칙을 이해했는지 확인하는 좋은 문제입니다.

연습문제 13-9 금융 응용 난이도 ★★★

일일 이체 한도를 관리하는 모듈 limit.c를 작성하세요. 요구사항: ① 당일 누적 이체액은 다른 파일에서 직접 바꿀 수 없어야 합니다. ② int try_transfer(long long amt)는 누적액 + amt가 한도(5,000,000원)를 넘으면 -1, 아니면 누적하고 0을 반환합니다. ③ long long remaining(void)는 남은 한도를 반환합니다. ④ void reset_day(void)는 일마감 시 누적액을 0으로 만듭니다.

정답과 해설 보기

3,000,000원은 통과, 2,500,000원은 누적 5,500,000원이 되어 거절, 2,000,000원은 누적 정확히 5,000,000원이므로 통과(> 비교이므로 한도와 같으면 허용)합니다. 실제 시스템에서는 이 상태를 DB에 저장해야 프로세스 재시작이나 여러 서버 간에도 한도가 지켜집니다.

연습문제 13-12 서술형 난이도 ★★★

"static 지역 변수로 만든 거래 일련번호 생성기를 다중 프로세스 온라인 서버에 그대로 쓰면 어떤 문제가 생기는가?"를 세 가지 이상 들어 설명하세요.

정답과 해설 보기
  1. 프로세스 간 중복: static 변수는 프로세스마다 따로 존재합니다. 서버 프로세스 10개가 각자 000001부터 발급하므로 같은 번호가 10번 나옵니다.
  2. 재시작 시 초기화: 프로세스가 재기동되면 static 변수는 다시 0이 되어 이미 발급한 번호를 다시 발급합니다.
  3. 스레드 경쟁: 한 프로세스 안에서도 여러 스레드가 동시에 seq++를 하면 두 스레드가 같은 값을 읽고 같은 번호를 받을 수 있습니다.
  4. 날짜 전환 경계: 자정이나 영업일 전환 시점에 프로세스마다 날짜 인식 시점이 달라 번호 체계가 엇갈릴 수 있습니다.

해결: DB 시퀀스나 중앙 채번 서버를 쓰거나, 번호에 서버/프로세스 ID를 포함하고 시작 시 마지막 번호를 영속 저장소에서 복구하며, 증가 연산은 원자적으로 수행합니다.
