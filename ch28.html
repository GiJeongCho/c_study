프로세스와 스레드: 무엇을 공유하는가

프로세스(process)는 실행 중인 프로그램 하나입니다. 운영체제는 프로세스마다 독립된 가상 주소 공간을 줍니다. 코드 영역, 데이터 영역(전역·static 변수), 힙, 스택이 모두 그 프로세스만의 것입니다. 프로세스 A의 주소 0x601040과 프로세스 B의 주소 0x601040은 이름만 같을 뿐 서로 완전히 다른 물리 메모리를 가리킵니다. 그래서 한 프로세스가 잘못된 포인터로 메모리를 망가뜨려도 다른 프로세스는 멀쩡합니다.

스레드(thread)는 프로세스 안에서 돌아가는 실행 흐름 하나입니다. 한 프로세스 안의 스레드들은 주소 공간을 공유합니다. 즉 코드, 전역 변수, 힙, 열린 파일 디스크립터를 모두 같이 씁니다. 대신 각 스레드는 자기만의 스택과 자기만의 레지스터 집합(프로그램 카운터, 스택 포인터 등)을 가집니다. 함수 호출 기록과 지역 변수가 스택에 저장되므로, 스레드마다 독립된 호출 흐름을 가질 수 있는 것입니다.

왜 스레드끼리는 스택만 따로 가질까?

함수를 호출하면 CPU는 복귀 주소, 이전 프레임 포인터, 지역 변수를 스택에 쌓습니다(13장 함수 호출 구조 참고). 스레드가 둘인데 스택이 하나라면, 스레드1이 f()를 호출해 프레임을 쌓는 중에 스레드2가 g()를 호출하며 같은 자리에 덮어쓰게 됩니다. 복귀 주소가 뒤섞이면 즉시 프로그램이 폭주합니다. 그래서 "독립적으로 함수를 호출하고 돌아올 수 있는 실행 흐름"이 되려면 최소한 스택과 레지스터(특히 스택 포인터와 프로그램 카운터)만큼은 반드시 따로 있어야 합니다. 반대로 나머지(코드, 전역, 힙)는 공유해도 실행 자체에는 문제가 없고, 공유하기 때문에 데이터를 주고받는 비용이 0에 가깝습니다. 바로 이 "공유하니까 빠르다"와 "공유하니까 위험하다"가 멀티스레드 프로그래밍의 양면입니다.

스레드 스택의 크기

리눅스에서 메인 스레드의 스택은 ulimit -s(보통 8MB)로 정해지고, pthread_create로 만든 스레드의 기본 스택도 glibc에서는 보통 같은 값(8MB)입니다. 스레드를 1,000개 만들면 가상 메모리만 8GB를 예약하는 셈입니다(실제 물리 메모리는 쓴 만큼만 할당). 스레드 안에서 char buf[10*1024*1024]; 같은 거대한 지역 배열을 만들면 스택 오버플로로 세그폴트가 납니다. 필요하면 pthread_attr_setstacksize로 크기를 조정합니다.

은행 시스템에서는: 프로세스냐 스레드냐

전통적인 계정계(코어뱅킹) 온라인은 TP 모니터 위에서 서버 프로세스를 여러 개 띄워 놓고 요청을 나눠 주는 멀티 프로세스 구조가 많습니다. 이유는 장애 격리입니다. 한 거래 처리 중 포인터 버그로 세그폴트가 나도 그 프로세스 하나만 죽고, TP 모니터가 자동으로 재기동합니다. 반면 대외계 게이트웨이(다른 금융기관과 전문을 주고받는 서버)나 시세 수신 서버는 수천 개의 연결을 가볍게 처리해야 하므로 멀티 스레드나 이벤트 기반 구조를 많이 씁니다. 어느 쪽이든 "공유되는 자원은 반드시 보호한다"는 원칙은 같습니다.

pthread_create와 pthread_join

POSIX 스레드는 <pthread.h>에 선언되어 있습니다. 가장 중요한 두 함수의 원형은 다음과 같습니다.

스레드 함수는 반드시 void *함수명(void *) 형태여야 합니다. 인자도 하나, 반환도 하나입니다. 여러 값을 넘기고 싶으면 구조체를 만들어 그 주소를 넘깁니다. 이 "void * 하나"라는 설계 덕분에 어떤 타입이든 넘길 수 있지만, 동시에 타입 검사를 컴파일러가 못 해 주는 위험이 생깁니다.

두 함수 모두 성공하면 0, 실패하면 오류 번호를 반환값으로 돌려줍니다. 여기서 많이 틀립니다. pthread 함수는 errno를 설정하지 않고(구현에 따라 설정할 수도 있지만 의존하면 안 됨) 오류 코드 자체를 반환하므로 perror가 아니라 strerror(rc)로 출력해야 합니다.

gcc -Wall -O2 -pthread -o ex28-1 ex28-1.c
./ex28-1

왜 출력 순서가 매번 달라질까?

pthread_create가 반환된 시점에 새 스레드는 "실행 가능" 상태가 되었을 뿐, 언제 CPU를 받을지는 운영체제 스케줄러가 결정합니다. 코어가 여러 개면 두 스레드가 진짜로 동시에 돌고, 코어가 하나면 번갈아 돕니다. 어느 쪽이 먼저 printf에 도달할지는 보장이 없습니다. 반면 마지막 줄은 항상 맨 뒤에 나옵니다. pthread_join이 두 스레드의 종료를 기다린 다음에야 출력하기 때문입니다. 즉 join은 "기다림"이자 "순서 보장 지점"입니다. POSIX는 join이 반환되면 그 스레드가 했던 메모리 쓰기가 join한 스레드에게 보인다고 보장합니다. 그래서 jobs[i].sum을 락 없이 읽어도 안전합니다.

자주 하는 실수: -pthread 빠뜨리기

예전에는 -lpthread를 링크 옵션으로 붙였지만, 지금은 -pthread를 컴파일과 링크 양쪽에 주는 것이 정석입니다. -pthread는 라이브러리 링크뿐 아니라 _REENTRANT 매크로 정의 등 스레드용 컴파일 설정까지 해 줍니다. glibc 2.34 이후로는 pthread가 libc에 합쳐져서 빠뜨려도 링크가 되는 경우가 많지만, 이식성을 위해 항상 붙이십시오.

자주 하는 실수: main이 먼저 끝나 버림

main에서 return하거나 exit()를 호출하면 프로세스 전체가 종료되며 아직 돌고 있던 다른 스레드도 모두 강제로 사라집니다. join을 빠뜨리면 "가끔 로그가 안 찍힌다", "파일이 반쯤만 써졌다" 같은 증상이 납니다. 메인 스레드만 끝내고 다른 스레드는 계속 돌리고 싶다면 pthread_exit(NULL)을 main 끝에서 호출합니다.

detach와 스레드의 생애

스레드가 끝나도 그 스레드의 반환값과 일부 자원(스레드 디스크립터, 스택)은 누군가 pthread_join으로 회수할 때까지 남아 있습니다. 프로세스의 좀비와 비슷하다고 해서 흔히 "좀비 스레드"라고 부릅니다. join하지 않을 스레드라면 detach해서 "끝나면 알아서 자원을 반납하라"고 알려 주어야 합니다.

detach는 생성 시 속성으로 줄 수도 있습니다. pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED)를 쓰면 생성되는 순간부터 detached 상태입니다. 스레드 안에서 pthread_detach(pthread_self())를 부르는 방법보다 경쟁 여지가 적어 더 깔끔합니다.

자주 하는 실수: join도 detach도 안 함

요청마다 스레드를 만들고 join도 detach도 하지 않으면, 끝난 스레드의 스택(기본 8MB 가상 메모리)이 계속 쌓입니다. 하루 수십만 건을 처리하는 대외계 서버라면 몇 시간 만에 pthread_create가 EAGAIN(자원 부족)을 반환하며 신규 연결을 못 받게 됩니다. 메모리 누수와 똑같이 "점진적으로 나빠지는 장애"라 원인 찾기가 어렵습니다. 또한 이미 detach한 스레드를 join하는 것은 미정의 동작이니 둘 중 하나만 하십시오.

pthread_t를 ==로 비교하지 마세요

pthread_t는 리눅스에서는 unsigned long이지만 표준상 불투명(opaque) 타입이라 구조체일 수도 있습니다. 두 스레드 ID가 같은지는 pthread_equal(t1, t2)로 비교하고, 로그에 찍을 때는 리눅스 전용 gettid()(glibc 2.30+)나 syscall(SYS_gettid)로 얻은 커널 스레드 번호를 쓰는 것이 top -H, gdb의 표시와 맞아 장애 분석에 유리합니다.

인자 전달 함정: 루프 변수의 주소

스레드 프로그래밍 입문자가 거의 반드시 한 번은 저지르는 버그입니다. 다음 코드는 계좌 번호 0~3번에 대한 이자 계산 스레드 4개를 만들려는 의도입니다.

0, 1, 2, 3이 한 번씩 나와야 하는데, 같은 번호가 중복되고 심지어 존재하지 않는 4번까지 나옵니다.

왜 그럴까?

&i는 네 번 모두 같은 주소입니다. pthread_create는 그 주소값(포인터)만 복사해서 넘길 뿐 그 안의 정수를 복사하지 않습니다. 새 스레드가 실제로 *(int *)arg를 읽는 시점은 스케줄러 마음이므로, 그사이 main 스레드가 i++를 몇 번 했는지에 따라 값이 바뀝니다. 루프가 끝나면 i는 4가 되고, 더 나쁘게는 for 블록을 벗어나 i의 수명이 끝난 뒤에 읽으면 수명이 끝난 객체에 접근하는 미정의 동작이 됩니다(그 스택 칸은 두 번째 for 루프의 i로 재사용될 수도 있습니다). 이것은 6장에서 배운 "값에 의한 전달"이 포인터 자체에만 적용된다는 사실의 연장입니다.

이렇게 해결합니다

방법 1(정석): 스레드마다 수명이 충분히 긴 별도의 저장 공간을 주고 그 주소를 넘깁니다. 배열 원소 하나씩, 또는 스레드마다 malloc.

방법 2(작은 정수 한정): 값을 포인터 크기 정수로 변환해 주소 자리에 값 자체를 실어 보냅니다. <stdint.h>의 intptr_t를 경유하면 경고 없이 변환됩니다.

이 방법은 정수가 포인터 크기 안에 들어갈 때만 쓰고, 구조체를 넘길 때는 반드시 방법 1을 씁니다.

사고 사례: 엉뚱한 고객에게 간 응답 전문

어느 금융기관의 대외 중계 서버에서, 접속이 몰리는 월말 오후에만 "A 기관의 조회 요청에 대한 응답이 B 기관 세션으로 나간다"는 민원이 들어왔습니다. 평소 테스트에서는 재현되지 않았습니다. 원인은 accept 루프에서 int cfd = accept(...)로 받은 소켓 번호를 &cfd로 스레드에 넘긴 것이었습니다. 접속이 드물 땐 새 스레드가 cfd를 읽은 뒤에 다음 accept가 일어나 문제가 없었지만, 접속이 몰리면 스레드가 읽기 전에 cfd가 다음 연결의 번호로 덮어써졌습니다. 두 스레드가 같은 소켓으로 응답을 쓰고, 하나의 연결은 응답을 영영 받지 못해 타임아웃이 났습니다. 수정은 위의 방법 1처럼 연결마다 malloc한 컨텍스트를 넘기는 것이었습니다. "부하가 높을 때만 나는 버그"는 동시성 버그일 확률이 매우 높습니다.

스레드 안전 함수와 _r 함수

어떤 함수를 여러 스레드가 동시에 호출해도 올바르게 동작하면 그 함수는 스레드 안전(thread-safe)하다고 합니다. 반대로 내부에 static 변수(숨은 전역 상태)를 쓰는 함수는 스레드 안전하지 않습니다. C 표준 라이브러리에는 C89 시절, 즉 스레드라는 개념이 표준에 없던 시절에 설계된 함수들이 많아서 이런 함정이 곳곳에 있습니다.

왜 strtok은 스레드 안전하지 않을까?

strtok(NULL, ...)은 "아까 하던 문자열의 다음 토큰"을 돌려줍니다. "아까 하던 위치"를 어딘가에 기억해야 하는데, 인자로 받지 않으니 함수 내부의 static char * 변수에 저장할 수밖에 없습니다. static 변수는 데이터 영역에 단 하나 존재하고, 그림 28-1에서 보았듯 데이터 영역은 모든 스레드가 공유합니다. 결국 두 스레드가 같은 "책갈피"를 서로 덮어쓰는 셈입니다. localtime도 같습니다. 반환하는 struct tm *는 내부 static 구조체의 주소이므로, 스레드 A가 받아서 읽는 중에 스레드 B의 호출이 내용을 바꿔 버릴 수 있습니다. 거래 시각이 다른 거래의 시각으로 찍히는 사고가 바로 여기서 나옵니다.

재진입성과 스레드 안전성은 같은 말이 아닙니다

재진입 가능(reentrant): 함수 실행 도중 끼어든 다른 실행(시그널 핸들러, 재귀)이 같은 함수를 다시 호출해도 안전. 공유 상태를 아예 안 쓰는 함수입니다. 스레드 안전: 여러 스레드에서 동시에 불러도 안전. 내부 상태를 mutex로 보호하면 스레드 안전해지지만, 시그널 핸들러에서 그 함수를 부르면 이미 잡힌 락을 다시 잡으려다 교착에 빠지므로 재진입 가능하지 않습니다. malloc과 printf가 대표적인 "스레드 안전하지만 재진입 불가" 함수라서 시그널 핸들러 안에서 부르면 안 됩니다.

errno는 스레드마다 따로 있다

23장에서 배운 errno는 "마지막 오류 번호를 담는 전역 변수"처럼 보입니다. 정말로 전역 변수 하나라면, 스레드 A의 open이 실패해 errno=ENOENT가 된 직후 스레드 B의 read가 실패해 errno=EAGAIN으로 덮어쓰면, A는 엉뚱한 원인을 로그에 남깁니다. 그래서 C11과 POSIX는 errno가 스레드마다 독립된 저장소(thread-local storage)여야 한다고 규정합니다. glibc에서 errno는 사실 매크로입니다.

여러분도 C11의 _Thread_local(또는 <threads.h>의 thread_local, GCC 확장 __thread)로 스레드별 변수를 만들 수 있습니다. 대표 활용이 30장에서 볼 거래 추적 ID입니다. 요청을 받은 스레드가 자기만의 전역 변수에 GUID를 넣어 두면, 깊숙한 함수의 로그 매크로가 인자로 넘겨받지 않고도 그 ID를 찍을 수 있습니다.

스레드 풀에서 스레드 로컬 변수를 쓸 때

스레드 풀(28-2 끝에서 다룸)의 작업 스레드는 요청을 끝내도 죽지 않고 다음 요청을 처리합니다. 요청 시작 시 스레드 로컬 거래 ID를 새로 설정하지 않으면, 이전 요청의 ID가 그대로 남아 전혀 다른 거래의 로그에 찍힙니다. 장애 분석 때 이 로그를 믿고 엉뚱한 거래를 추적하게 됩니다. 요청 진입 시 설정, 종료 시 초기화를 반드시 짝으로 하십시오.

28-2동기화와 계좌이체 경쟁 조건

스레드가 데이터를 공유한다는 것은 강력한 장점이지만, 금융 시스템에서는 곧바로 "돈"의 문제가 됩니다. 이 절에서는 실제로 잔액이 틀어지는 상황을 코드로 재현하고, 그 원인을 CPU 명령어 수준까지 내려가서 확인한 뒤, mutex·조건 변수·rwlock·원자적 연산으로 하나씩 해결해 나갑니다. 그리고 동기화를 잘못 쓰면 생기는 또 다른 재앙인 데드락을 두 계좌 이체 예제로 체험하고 고칩니다.

경쟁 조건: 같은 잔액에서 동시에 출금하면

잔액 100만 원인 계좌에서 ATM과 모바일 앱이 동시에 각각 70만 원을 출금하려 한다고 합시다. 정상이라면 한 건만 성공하고 다른 한 건은 "잔액 부족"으로 거절되어야 합니다. 하지만 다음처럼 확인과 차감이 따로 놀면 두 건 모두 성공할 수 있습니다.

이처럼 실행 결과가 스레드의 실행 순서(타이밍)에 따라 달라지는 상황을 경쟁 조건(race condition)이라고 합니다. 그림에서는 두 출금이 모두 승인되었는데 잔액은 70만 원만 줄었습니다. 은행은 140만 원을 내주고 장부에는 70만 원만 차감한 셈이며, 잔액 부족으로 거절되었어야 할 거래까지 승인되었습니다. 실제로 재현해 봅시다. 사람 손으로는 타이밍을 맞추기 어려우니 1원짜리 출금 100만 건씩을 두 스레드가 동시에 하겠습니다.

gcc -O0 -pthread -o race ex28-7-race.c && ./race

200만 건을 요청했으니 잔액 200만 원은 정확히 0이 되어야 하고, 승인 건수도 200만이어야 합니다. 그런데 승인 건수와 잔액이 매번 다르고, 무엇보다 "초기 잔액 - 승인액 - 남은 잔액"이 0이 아닙니다. 장부(approved)와 잔액(balance)이 서로 맞지 않는, 은행에서 가장 무서운 대사 불일치가 발생한 것입니다. 단일 코어 환경이거나 운이 좋으면 정상 값이 나올 수도 있습니다. "한 번 돌려 봤더니 맞았다"가 동시성 코드의 정확성을 증명하지 못하는 이유입니다.

왜 그럴까? balance -= amt는 한 번에 일어나지 않는다

C에서는 한 줄이지만 CPU에게 balance -= amt;는 세 단계입니다. x86-64 gcc -O0로 컴파일하면 대략 다음과 같습니다.

스레드 A가 (a)에서 1,000을 읽고 (b)까지 한 뒤 (c) 직전에 선점되었다고 합시다. 스레드 B가 같은 1,000을 읽어 999를 쓰고, A가 돌아와 자기 레지스터에 있던 999를 씁니다. 두 번 뺐는데 한 번만 빠졌습니다. 멀티코어라면 선점이 없어도 두 코어가 진짜 동시에 (a)를 실행합니다. 더구나 if (balance >= amt)와 차감 사이에도 틈이 있어서 "확인 시점의 잔액"과 "차감 시점의 잔액"이 다를 수 있습니다(TOCTOU: Time Of Check to Time Of Use). 최적화(-O2)를 켜면 컴파일러가 루프 안의 balance를 레지스터에 캐시해 더 기괴한 결과가 나오기도 합니다. 근본적으로 C11 메모리 모델에서 동기화 없이 두 스레드가 같은 객체에 접근하고 그중 하나라도 쓰기면 데이터 레이스(data race)이며 미정의 동작입니다. "가끔 틀리는 정도"가 아니라 무엇이든 일어날 수 있다는 뜻입니다.

경쟁 조건을 찾아 주는 도구: ThreadSanitizer

gcc/clang에 -fsanitize=thread -g를 주고 실행하면, 데이터 레이스가 실제로 일어난 지점을 "WARNING: ThreadSanitizer: data race" 형식으로 두 스레드의 호출 스택과 함께 알려 줍니다. 결과값이 우연히 맞더라도 레이스 자체를 잡아 주므로, 동시성 코드는 단위 테스트를 TSan 빌드로도 돌리는 것이 좋습니다(30장에서 ASan과 함께 다룹니다).

임계 구역과 mutex

공유 자원에 접근하는 코드 구간, 즉 한 번에 한 스레드만 실행해야 하는 구간을 임계 구역(critical section)이라고 합니다. 위 예에서는 if부터 approved++까지가 임계 구역입니다. 임계 구역을 보호하는 가장 기본 도구가 mutex(MUTual EXclusion, 상호 배제)입니다. 은행 금고 열쇠가 하나뿐인 것과 같습니다. 열쇠(락)를 가진 사람만 들어갈 수 있고, 나머지는 문 앞에서 기다립니다.

왜 mutex를 쓰면 맞아질까?

두 가지 보장이 동시에 일어나기 때문입니다. 첫째, 상호 배제: pthread_mutex_lock은 내부적으로 CPU의 원자적 명령(x86의 lock cmpxchg)으로 "락이 비어 있으면 내 것으로 표시"를 쪼갤 수 없게 수행합니다. 실패한 스레드는 리눅스에서 futex 시스템 콜로 커널에서 잠듭니다. 둘째, 메모리 가시성과 순서: lock/unlock은 메모리 배리어 역할을 해서, unlock 전에 한 모든 쓰기가 다음에 lock을 얻는 스레드에게 반드시 보이고, 컴파일러와 CPU가 임계 구역 안의 메모리 접근을 락 바깥으로 옮기지 못하게 막습니다. 그래서 레지스터 캐시 문제도 함께 사라집니다. 단순히 "한 명씩 들어간다"만이 아니라 "앞사람이 바꿔 놓은 것을 반드시 본다"까지 보장하는 것이 핵심입니다.

자주 하는 실수: 중간 return에서 unlock 누락

C에는 C++의 RAII(소멸자에서 자동 해제)가 없으므로, 위의 고친 코드처럼 결과 변수 + 단일 출구 패턴이나 goto out; 패턴으로 unlock 지점을 한 곳에 모으십시오. 이 실수는 30장에서 볼 "hang 장애"의 단골 원인입니다.

락의 범위(granularity)

모든 계좌를 하나의 전역 mutex로 보호하면 정확하지만, 서로 무관한 계좌 A와 B의 출금도 줄을 서게 됩니다. 실무에서는 계좌마다 락(세분화된 락, fine-grained lock)을 두어 다른 계좌끼리는 병렬로 처리되게 합니다. 대신 락이 여러 개가 되면 데드락 위험이 생깁니다. 락은 "정확성"과 "병렬성"의 줄다리기이며, 임계 구역 안에서는 I/O(로그 파일 쓰기, 소켓 송신, DB 호출)를 하지 않는 것이 기본 원칙입니다. 락을 쥔 채 느린 I/O를 하면 모든 스레드가 그 I/O 속도로 줄을 섭니다.

계좌마다 락을 두는 구조체는 다음과 같습니다. 동적으로 만든 mutex는 pthread_mutex_init으로 초기화하고 다 쓰면 pthread_mutex_destroy로 정리합니다.

다른 스레드가 같은 계좌의 balance를 쓰는 중이라면, 이 읽기와 그 쓰기는 동기화되지 않은 동시 접근이므로 데이터 레이스, 즉 미정의 동작입니다. x86-64에서 정렬된 8바이트 읽기는 하드웨어적으로 쪼개지지 않지만, 32비트 시스템에서는 long long 읽기가 두 번의 4바이트 읽기로 나뉘어 상위·하위가 서로 다른 시점의 값인 "찢어진 값(torn read)"을 읽을 수 있습니다. 또한 컴파일러는 레이스가 없다고 가정하고 최적화하므로 오래된 값을 레지스터에서 재사용할 수도 있습니다. 계좌 하나의 값은 락 안에서 읽어야 합니다.

조회가 압도적으로 많다면 뒤에서 배울 rwlock을 고려합니다.

데드락: 4가지 조건과 두 계좌 이체

이제 이체를 구현해 봅시다. 이체는 출금 계좌와 입금 계좌 두 개를 동시에 바꿔야 하므로 락 두 개를 모두 잡아야 합니다. 가장 자연스러운 코드는 "보내는 쪽을 먼저 잠그고, 받는 쪽을 잠근다"입니다.

스레드 1이 A→B 이체를 위해 A를 잠근 직후, 스레드 2가 B→A 이체를 위해 B를 잠갔습니다. 이제 스레드 1은 B를, 스레드 2는 A를 기다립니다. 둘 다 상대가 놓아주기 전에는 놓지 않으므로 영원히 멈춥니다. 이것이 데드락(deadlock, 교착 상태)입니다. CPU 사용률은 0%인데 프로세스는 살아 있고 응답이 없는, 전형적인 "hang" 증상이 나타납니다.

데드락은 다음 네 가지 조건이 모두 동시에 성립할 때만 발생합니다(Coffman 조건). 면접에서 매우 자주 나옵니다.

조건뜻이체 예에서깨는 방법
1. 상호 배제자원을 한 번에 한 스레드만 사용계좌 락은 한 명만 쥔다공유 가능 자원으로(현실적으로 어려움)
2. 점유와 대기자원을 쥔 채로 다른 자원을 기다림A를 쥐고 B를 기다림필요한 락을 한꺼번에 얻거나, 못 얻으면 다 놓기(trylock)
3. 비선점남이 쥔 자원을 강제로 빼앗을 수 없음mutex는 강제 해제 불가타임아웃 후 스스로 포기(timedlock)
4. 순환 대기대기 관계가 원을 이룸1→B, 2→A 대기가 고리락 획득 순서를 전역적으로 고정

왜 4개가 "모두" 필요할까?

하나라도 빠지면 대기가 언젠가 풀립니다. 상호 배제가 없으면 애초에 기다리지 않고, 점유와 대기가 없으면 기다리는 스레드는 아무것도 안 쥐고 있으니 남을 막지 않으며, 선점이 가능하면 누군가의 자원을 빼앗아 진행시키면 되고, 순환이 없으면 대기의 사슬 끝에는 반드시 아무것도 기다리지 않는 스레드가 있어서 그 스레드가 끝나며 사슬이 차례로 풀립니다. 그래서 데드락 예방은 "네 조건 중 하나를 구조적으로 불가능하게 만드는 것"이고, 실무에서 가장 싸고 확실한 방법이 4번 순환 대기를 깨는 락 순서 규칙입니다.

예방, 회피, 탐지

운영체제 교과서는 데드락 대처를 넷으로 나눕니다. 예방(4조건 중 하나를 구조적으로 제거, 예: 락 순서), 회피(자원 할당 전에 안전 상태인지 검사, 예: 은행원 알고리즘 — 이름과 달리 실제 은행 시스템에서 쓰는 것은 아닙니다), 탐지와 복구(대기 그래프에서 사이클을 찾아 하나를 희생, 예: DB의 데드락 탐지기가 한 트랜잭션의 문장을 실패시킴), 무시(드물다고 보고 재시작에 맡김). C 애플리케이션 코드에서는 예방(락 순서)이 기본이고, DB는 탐지와 복구를 자동으로 해 줍니다(29장).

락 순서로 해결: 계좌번호 오름차순

규칙은 단순합니다. "여러 계좌 락을 잡을 때는 언제나 계좌번호가 작은 것부터 잡는다." A(110001) < B(110002)라면 A→B 이체든 B→A 이체든 항상 A 락을 먼저 잡습니다. 그러면 B를 쥐고 A를 기다리는 상황이 원천적으로 불가능해져 순환이 생기지 않습니다.

A에서 B로 3원씩 50만 번(150만 원), B에서 A로 2원씩 50만 번(100만 원)이 옮겨졌으므로 A는 50만 원 감소, B는 50만 원 증가합니다. 두 계좌 모두 잔액이 충분하므로 모든 이체가 성공하고, 합계 2,000만 원은 어떤 실행 순서에서도 보존됩니다. 이 "총액 보존"이 은행 시스템 검증의 기본 불변식(invariant)입니다. 데드락이 나는 원래 버전으로 같은 테스트를 돌리면 대부분 몇 초 안에 프로그램이 멈춥니다.

자주 하는 실수: 주소로 순서 정하기, 같은 계좌 이체

락 순서를 포인터 주소(from < to)로 정하는 코드도 흔합니다. 한 프로세스 안에서는 실무적으로 동작하지만, 서로 다른 배열에 있는 객체의 포인터를 관계 연산자로 비교하는 것은 C 표준상 미정의 동작이고(정 필요하면 uintptr_t로 변환해 비교), 무엇보다 다른 프로세스나 DB 락과 순서를 맞출 수 없습니다. 업무 키(계좌번호)로 순서를 정하면 C 코드, DB의 SELECT ... FOR UPDATE(29장), 다른 서버까지 같은 규칙을 공유할 수 있습니다. 또한 같은 계좌 간 이체를 걸러 내지 않으면 같은 기본 mutex를 두 번 잠그게 되는데, 이는 기본 타입 mutex에서 자기 자신과의 데드락(또는 미정의 동작)입니다.

사고 사례: 급여일 오전의 서비스 정지

한 금융회사의 사내 이체 모듈이 수년간 문제없이 돌다가, 급여일 오전 급여 이체와 고객 자동이체가 겹치는 시간대에 갑자기 응답이 멈췄습니다. 프로세스는 살아 있고 CPU도 0%라 프로세스 감시 도구는 "정상"으로 판단해 감지가 늦었습니다. 담당자가 gdb -p로 붙어 thread apply all bt를 보니(30장), 두 스레드가 각각 pthread_mutex_lock에서 멈춰 있었고 하나는 법인 계좌→직원 계좌, 다른 하나는 직원 계좌→법인 계좌(과지급 급여 반환) 방향이었습니다. 평소엔 두 방향 거래가 같은 순간에 일어날 일이 거의 없었던 것입니다. 수정은 이체 공통 함수에 계좌번호 오름차순 락 규칙을 넣고, 코드 리뷰 체크리스트에 "락을 두 개 이상 잡는 코드는 순서 규칙을 주석으로 명시"를 추가하는 것이었습니다. 재발 방지책으로 "처리 건수가 N초간 0이면 경보"라는 hang 감지도 함께 도입했습니다.

예제 28-3 난이도 ★★★

한 번에 세 계좌가 관여하는 "이체 + 수수료" 거래가 있습니다. 출금 계좌 F, 입금 계좌 T, 수수료 수납 계좌 C(은행 내부 계좌)입니다. 데드락 없이 세 락을 잡는 코드를 작성하십시오. 세 계좌번호는 모두 다르다고 가정합니다.

정답과 해설 보기

락이 셋이어도 원리는 같습니다. 세 계좌를 계좌번호 기준으로 정렬한 뒤 그 순서로 잠그고 역순으로 풉니다. 모든 코드가 이 규칙만 지키면 어떤 조합의 거래가 동시에 일어나도 대기 그래프에 원이 생기지 않습니다. 세 개 정도는 정렬 함수 대신 비교-교환 세 번으로 충분합니다.

trylock과 타임아웃: 무한히 기다리지 않기

락 순서를 지키기 어려운 경우도 있습니다. 예를 들어 이미 계좌 B를 잠근 상태에서 처리 도중 "연결 계좌 A도 필요하다"는 것을 알게 되는 경우입니다. 이럴 때는 pthread_mutex_trylock으로 "잡을 수 있으면 잡고, 아니면 즉시 EBUSY로 실패"를 시도한 뒤, 실패하면 가진 락을 모두 놓고 처음부터 다시 시도합니다. 데드락 조건 2(점유와 대기)를 깨는 방법입니다.

또한 pthread_mutex_timedlock은 절대 시각(CLOCK_REALTIME 기준)까지 기다렸다가 못 얻으면 ETIMEDOUT을 반환합니다. 온라인 거래에는 대개 "응답 제한 시간"이 있으므로, 락 대기도 무한정이 아니라 그 시간 안에서만 기다리고 실패 시 "처리 지연, 잠시 후 재시도" 응답을 주는 것이 무한 hang보다 훨씬 낫습니다.

라이브락(livelock)

두 스레드가 trylock 실패 → 놓기 → 즉시 재시도를 똑같은 박자로 반복하면, 둘 다 바쁘게 움직이지만 아무도 진행하지 못하는 라이브락이 생깁니다. 좁은 복도에서 마주친 두 사람이 서로 비켜 주려고 같은 방향으로 계속 움직이는 것과 같습니다. 위 코드처럼 무작위성이나 지수 백오프를 넣어 박자를 어긋나게 합니다. 데드락은 CPU 0%, 라이브락은 CPU가 높은데 처리량은 0이라는 증상 차이가 있습니다.

mutex 타입: 오류 검사형과 재귀형

pthread_mutexattr_settype으로 mutex 종류를 정할 수 있습니다. PTHREAD_MUTEX_ERRORCHECK는 같은 스레드가 두 번 잠그면 데드락 대신 EDEADLK를, 남의 락을 풀면 EPERM을 반환하므로 개발·테스트 빌드에서 버그를 잡기 좋습니다. PTHREAD_MUTEX_RECURSIVE는 같은 스레드가 여러 번 잠글 수 있게 하지만, "내가 이미 이 락을 쥐고 있는지 모르는" 설계를 숨겨 주는 경우가 많아 남용하지 않는 것이 좋습니다.

조건 변수: 생산자-소비자 거래 큐

대외계 게이트웨이를 생각해 봅시다. 수신 스레드(생산자)는 소켓에서 전문을 받아 큐에 넣고, 처리 스레드들(소비자)은 큐에서 꺼내 거래를 처리합니다. 큐가 비어 있으면 소비자는 기다려야 하고, 큐가 가득 차면 생산자가 기다려야 합니다. "기다린다"를 어떻게 구현할까요? while (count == 0) ;처럼 계속 확인하는 바쁜 대기(busy waiting)는 CPU를 100% 태우며 정작 생산자의 실행을 방해합니다. 필요한 것은 "조건이 만족될 때까지 잠들어 있다가, 누군가 조건을 바꾸면 깨어나는" 도구, 즉 조건 변수(condition variable)입니다.

조건 변수의 핵심 함수는 세 개입니다.

  • pthread_cond_wait(&cv, &mtx): mutex를 쥔 상태에서 호출합니다. 원자적으로 mutex를 풀고 잠들며, 깨어날 때 다시 mutex를 잡은 상태로 반환합니다.
  • pthread_cond_signal(&cv): 기다리는 스레드 중 최소 하나를 깨웁니다.
  • pthread_cond_broadcast(&cv): 기다리는 모든 스레드를 깨웁니다(종료 통지 등).

왜 if가 아니라 while로 조건을 다시 확인할까?

세 가지 이유가 있습니다. (1) 가짜 깨어남(spurious wakeup): POSIX는 signal이 없어도 pthread_cond_wait가 반환될 수 있다고 명시합니다. 멀티코어에서 효율적으로 구현하기 위해 허용된 동작입니다. (2) 가로채기: 생산자가 signal로 소비자 1을 깨웠지만, 소비자 1이 mutex를 다시 잡기 전에 막 도착한 소비자 2가 먼저 mutex를 잡고 거래를 가져갈 수 있습니다. 소비자 1이 깨어났을 때 큐는 다시 비어 있습니다. (3) broadcast로 여럿을 깨우면 그중 하나만 조건을 만족합니다. 그래서 "깨어났다 = 조건이 참이다"가 아니라 "깨어났으니 조건을 다시 확인해 본다"가 올바른 사고방식이며, 이를 코드로 쓴 것이 while 루프입니다.

왜 wait는 mutex를 인자로 받을까?

만약 "mutex를 풀기"와 "잠들기"가 따로 일어난다면, 그 사이 틈에 생산자가 거래를 넣고 signal을 보낼 수 있습니다. 아직 잠들지 않은 소비자에게 보낸 signal은 아무도 받지 않고 사라지고(조건 변수는 신호를 저장하지 않습니다), 그 뒤 소비자는 잠들어 큐에 거래가 있는데도 영원히 깨지 않습니다. 이를 잃어버린 깨우기(lost wakeup)라고 합니다. pthread_cond_wait는 "풀고 잠들기"를 원자적으로 해 주어 이 틈을 없앱니다. 같은 이유로 조건(count)을 바꾸는 쪽도 반드시 같은 mutex를 쥔 채 바꿔야 합니다.

자주 하는 실수: 조건 변수를 "이벤트"처럼 쓰기

"초기화가 끝나면 signal, 작업 스레드는 wait"처럼 상태 변수 없이 조건 변수만 쓰면, 작업 스레드가 wait에 도달하기 전에 signal이 나가 버린 경우 영원히 기다립니다. 조건 변수는 항상 mutex로 보호되는 상태 변수(predicate)와 한 세트입니다. "while (!ready) wait;" 형태가 아니면 의심하십시오.

은행 시스템에서는: 큐 길이가 곧 건강 지표

대외계·카드 승인 서버에서는 이런 내부 큐의 count를 주기적으로 모니터링 지표로 내보냅니다. 평소 0~10 사이이던 큐 길이가 수백으로 치솟으면, 처리 스레드가 무언가(DB 락, 느린 대외기관 응답)에 막혀 있다는 신호입니다. 큐가 가득 차면 수신 스레드까지 막혀 TCP 수신 버퍼가 차고, 상대 기관 쪽에서 타임아웃이 연쇄적으로 발생합니다(30장의 "타임아웃 폭주"). 그래서 실무 큐는 무한정 기다리지 않고, 가득 차면 즉시 "시스템 혼잡" 응답 전문을 돌려주는 부하 차단(load shedding) 정책을 둡니다. 영원히 기다리는 것보다 빠르게 거절하는 편이 전체 시스템을 살립니다.

읽기-쓰기 락(rwlock)

환율·금리 기준표, 영업일 달력, 수수료 테이블처럼 읽기는 초당 수만 번, 쓰기는 하루 몇 번인 데이터가 있습니다. mutex로 보호하면 읽기끼리도 줄을 서야 해서 낭비입니다. 읽기끼리는 동시에 해도 안전하기 때문입니다. rwlock은 "읽기 락은 여러 스레드가 동시에, 쓰기 락은 혼자만"을 허용합니다.

rwlock이 항상 빠른 것은 아닙니다

rwlock은 내부 상태(읽는 사람 수)를 관리하는 비용이 mutex보다 큽니다. 임계 구역이 아주 짧으면(변수 하나 읽기) 오히려 mutex가 빠를 수 있습니다. 또 읽기가 끊임없이 들어오면 쓰기가 영원히 기회를 못 얻는 기아(starvation)가 생길 수 있어, glibc는 pthread_rwlockattr_setkind_np로 쓰기 우선 정책을 고를 수 있게 합니다. 그리고 읽기 락을 쥔 채 쓰기 락으로 "승격"하려 하면 데드락이 납니다(두 읽기 스레드가 동시에 승격을 시도하면 서로의 읽기 락이 풀리길 기다림). 측정 후 선택하십시오.

원자적 연산: C11 stdatomic

거래 일련번호 발급기나 처리 건수 통계처럼 정수 하나를 증가시키는 것만 보호하면 될 때 mutex는 다소 무겁습니다. C11은 <stdatomic.h>로 원자적(atomic) 연산을 표준화했습니다. 원자적 연산은 다른 스레드가 중간 상태를 절대 볼 수 없는, 쪼갤 수 없는 하나의 연산입니다. 앞서 본 "읽기-빼기-쓰기" 세 단계를 CPU의 lock xadd 같은 명령 하나로 처리합니다.

"잔액이 충분할 때만 차감" 같은 조건부 갱신은 fetch_add로는 안 되고, CAS(Compare-And-Swap)를 씁니다. "현재 값이 내가 읽은 값과 같으면 새 값으로 바꾸고, 아니면(그새 누가 바꿨으면) 실패"를 원자적으로 수행합니다.

왜 CAS 루프는 경쟁 조건이 없을까?

그림 28-4의 문제는 "읽은 값을 근거로 판단했는데, 쓰는 순간에는 값이 바뀌어 있었다"였습니다. CAS는 쓰는 순간에 "내가 근거로 삼은 값이 아직 그대로인가?"를 함께 확인합니다. 그대로면 쓰고, 바뀌었으면 쓰지 않고 새 값을 돌려줍니다. 그러면 새 값으로 다시 판단합니다. 판단의 근거와 쓰기가 하나의 원자적 단위로 묶이므로 TOCTOU 틈이 없습니다. _weak 버전은 값이 같아도 드물게 실패할 수 있는(일부 CPU의 LL/SC 명령 특성) 대신 빠르며, 어차피 루프 안에서 쓰므로 문제가 없습니다.

원자적 변수 두 개는 원자적이지 않습니다

이체는 출금 계좌와 입금 계좌 두 값을 함께 바꿔야 합니다. 두 잔액을 각각 atomic_llong으로 만들고 fetch_sub, fetch_add를 차례로 하면, 그 사이 순간에 "돈이 출금되었지만 아직 어디에도 입금되지 않은" 상태를 다른 스레드가 볼 수 있고, 중간에 실패하면 되돌리기도 어렵습니다. 원자적 연산은 변수 하나에 대한 연산만 원자적입니다. 여러 값의 일관성(불변식)을 지켜야 하면 mutex(또는 DB 트랜잭션)를 쓰십시오. 락 없는(lock-free) 자료구조는 ABA 문제 등 함정이 많아 전문가 영역입니다.

메모리 순서(memory_order)

기본 원자 연산은 가장 강한 memory_order_seq_cst(순차적 일관성)로 동작해 직관대로 움직입니다. 통계 카운터처럼 "값만 정확하면 되고 다른 메모리와의 순서는 상관없는" 경우 memory_order_relaxed로 비용을 줄일 수 있습니다. 한 스레드가 데이터를 준비한 뒤 플래그를 세우고 다른 스레드가 플래그를 보고 데이터를 읽는 패턴에는 release(쓰는 쪽)와 acquire(읽는 쪽) 쌍을 씁니다. 확신이 없으면 기본값(seq_cst)을 쓰는 것이 안전합니다.

volatile은 동기화가 아니다

오래된 코드나 인터넷 자료에서 "스레드 간 공유 변수에는 volatile을 붙여라"라는 말을 자주 봅니다. C에서 이것은 틀린 조언입니다. 20장에서 배운 것처럼 volatile은 "이 변수 접근을 컴파일러가 최적화로 없애거나 합치지 말라"는 뜻일 뿐입니다. 원래 용도는 메모리 맵 I/O 레지스터, 시그널 핸들러와 공유하는 volatile sig_atomic_t 플래그, setjmp/longjmp 사이의 지역 변수입니다.

왜 volatile로는 부족할까?

첫째, 원자성이 없습니다. processed++는 volatile이든 아니든 load-add-store 세 명령입니다. 둘째, 순서 보장이 없습니다. 스레드 A가 data = 42; ready = 1;을 하고 스레드 B가 while (!ready); use(data);를 한다고 합시다. ready만 volatile이면 컴파일러는 volatile이 아닌 data의 쓰기를 ready 뒤로 옮길 수 있고, 둘 다 volatile이어도 ARM 같은 약한 메모리 모델의 CPU는 하드웨어 수준에서 두 쓰기의 순서를 다른 코어에 뒤바꿔 보이게 할 수 있습니다. volatile은 CPU에 배리어 명령을 넣지 않기 때문입니다. 반면 atomic_store_explicit(&ready, 1, memory_order_release)는 컴파일러와 CPU 모두에게 "앞의 쓰기가 먼저 보여야 한다"를 강제합니다. 참고로 Java의 volatile은 C와 의미가 달라 가시성·순서를 보장하는데, 이 차이 때문에 생긴 오해가 많습니다.

이렇게 해결합니다

원칙: 스레드 간 공유는 mutex, 조건 변수, 또는 _Atomic. volatile은 하드웨어 레지스터와 시그널 핸들러용.

스레드 풀: 스레드를 미리 만들어 재사용하기

요청마다 스레드를 만들고 없애면, 생성 비용(수십 마이크로초)이 쌓이고, 순간 요청이 폭주하면 스레드 수가 통제 없이 늘어 메모리와 컨텍스트 스위칭 비용으로 시스템 전체가 느려집니다. 스레드 풀(thread pool)은 정해진 수의 작업 스레드를 미리 만들어 두고, 앞에서 만든 작업 큐에서 일감을 꺼내 처리하게 합니다. 은행 창구 직원 수를 고정하고 손님은 번호표를 뽑아 대기하는 것과 같습니다.

스레드 수는 몇 개가 적당할까?

계산 위주(CPU-bound) 작업이면 코어 수 정도가 최적입니다. 그 이상은 컨텍스트 스위칭만 늘립니다. DB나 대외기관 응답을 기다리는 시간이 긴(I/O-bound) 작업이면 대기 중인 스레드가 CPU를 쓰지 않으므로 더 많이 둡니다. 흔한 경험식은 스레드 수 ≈ 코어 수 × (1 + 대기시간/처리시간)입니다. 다만 금융 시스템에서는 DB 커넥션 풀 크기, 대외기관의 동시 세션 한도 같은 하위 자원의 한도가 실제 상한이 되는 경우가 많습니다. 스레드를 200개로 늘려도 DB 커넥션이 50개면 150개는 커넥션을 기다릴 뿐입니다.

사고 사례: 스레드 풀 고갈로 인한 전면 지연

어느 증권사 주문 중계 서버는 작업 스레드 64개의 풀을 쓰고 있었습니다. 장 시작 직후, 시세 조회를 위해 호출하던 외부 서버 하나가 응답을 늦게 주기 시작했고, 이 호출에는 타임아웃이 설정되어 있지 않았습니다. 몇 분 사이 64개 스레드가 모두 그 응답을 기다리며 묶였고, 큐는 가득 차 주문 접수까지 전부 "혼잡"으로 거절되었습니다. 정작 주문 처리 자체는 그 외부 서버와 무관했는데도 말입니다. 재발 방지책은 (1) 모든 외부 호출에 타임아웃 설정, (2) 업무 종류별로 스레드 풀을 분리(조회용과 주문용)해 한쪽의 지연이 다른 쪽을 막지 않게 하는 격벽(bulkhead) 패턴, (3) 풀 사용률·큐 길이 모니터링 경보였습니다.

28-2 한 줄 요약

공유 데이터를 바꾸는 코드는 mutex로 감싸고, 락이 둘 이상이면 계좌번호 오름차순으로 잡으며, 기다림은 조건 변수와 while 루프로, 단일 정수는 _Atomic으로 처리합니다. volatile은 동기화 도구가 아닙니다.

핵심 정리

  • 스레드는 같은 프로세스의 코드·전역·힙·파일 디스크립터를 공유하고, 스택과 레지스터만 각자 가집니다. 공유는 빠르지만 동기화 책임을 동반합니다.
  • pthread_create/pthread_join은 오류 코드를 반환값으로 돌려줍니다(errno 아님). 컴파일은 -pthread로 합니다.
  • 모든 스레드는 join되거나 detach되어야 자원이 회수됩니다. main이 return하면 모든 스레드가 함께 종료됩니다.
  • 루프 변수의 주소를 스레드 인자로 넘기면 모든 스레드가 같은 변수를 보게 됩니다. 스레드마다 별도 저장 공간을 주십시오.
  • strtok, localtime, rand 등 숨은 static 상태를 쓰는 함수 대신 strtok_r, localtime_r 등을 씁니다. errno는 스레드마다 따로 있습니다.
  • 동기화 없는 동시 쓰기는 데이터 레이스이자 미정의 동작입니다. "확인 후 행동(TOCTOU)"은 확인과 행동을 하나의 임계 구역에 넣어야 합니다.
  • 데드락 4조건: 상호 배제, 점유와 대기, 비선점, 순환 대기. 실무 해법은 업무 키(계좌번호) 오름차순 락 순서이며, 보조 수단으로 trylock/timedlock이 있습니다.
  • 조건 변수는 mutex로 보호되는 상태 변수와 한 세트이며, 항상 while 루프 안에서 wait합니다(가짜 깨어남, 가로채기 대비).
  • 읽기 위주 데이터에는 rwlock, 단일 정수 갱신에는 C11 _Atomic과 CAS를 씁니다. 여러 값의 일관성은 mutex나 트랜잭션으로 지킵니다.
  • volatile은 원자성도 순서도 보장하지 않습니다. 스레드 동기화에 쓰지 마십시오.
  • 스레드 풀은 스레드 수를 고정해 자원 사용을 예측 가능하게 하며, 외부 호출 타임아웃과 업무별 풀 분리로 고갈을 막습니다.

Q1. 프로세스와 스레드의 차이를 설명해 주세요.

프로세스는 운영체제로부터 독립된 가상 주소 공간을 할당받은 실행 단위이고, 스레드는 프로세스 안에서 실행되는 흐름의 단위입니다. 같은 프로세스의 스레드들은 코드, 데이터, 힙, 열린 파일을 공유하고 스택과 레지스터만 각자 가집니다. 그래서 스레드는 생성과 컨텍스트 스위칭이 가볍고 데이터 공유가 쉽지만, 동기화가 필요하고 한 스레드의 오류가 프로세스 전체를 죽입니다. 프로세스는 격리가 강한 대신 통신에 IPC가 필요합니다. 꼬리 질문 "그럼 은행 계정계는 왜 멀티 프로세스를 많이 쓰나요?"에는 장애 격리와 TP 모니터의 프로세스 재기동 구조를 들어 답합니다.

Q2. 스레드마다 스택이 따로 있어야 하는 이유는 무엇인가요?

스택에는 함수 호출의 복귀 주소, 이전 프레임 정보, 지역 변수가 저장됩니다. 스레드는 독립적으로 함수를 호출하고 반환하는 실행 흐름이므로, 스택을 공유하면 서로의 호출 프레임을 덮어써 복귀 주소가 망가집니다. 그래서 최소한 스택과 PC·SP 같은 레지스터 문맥은 스레드별로 있어야 합니다. 꼬리 질문: 다른 스레드의 지역 변수에 접근할 수 있나요? 주소만 알면 같은 주소 공간이라 접근은 가능하지만, 그 스레드의 함수가 반환된 뒤에는 무효이므로 위험합니다.

Q3. 경쟁 조건(race condition)이 무엇이고 어떻게 막나요?

여러 스레드가 공유 자원에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 상황입니다. 예를 들어 잔액을 읽고 판단하고 쓰는 사이에 다른 스레드가 끼어들면 차감 한 건이 사라집니다. 공유 자원에 접근하는 임계 구역을 mutex로 보호하거나, 단일 변수라면 원자적 연산을 사용해 막습니다. C11에서는 동기화 없는 동시 쓰기가 데이터 레이스로 미정의 동작이라는 점도 덧붙이면 좋습니다.

Q4. 데드락의 4가지 필요조건과 해결 방법을 말해 보세요.

상호 배제, 점유와 대기, 비선점, 순환 대기이며 네 가지가 모두 성립해야 데드락이 발생합니다. 그러므로 하나를 깨면 예방할 수 있습니다. 실무에서 가장 많이 쓰는 방법은 순환 대기를 깨는 락 순서 규칙으로, 예를 들어 이체 시 항상 계좌번호가 작은 계좌부터 잠급니다. 그 밖에 trylock 실패 시 가진 락을 모두 놓는 방식(점유와 대기 제거), 타임아웃 후 포기(비선점 완화)가 있습니다. 꼬리 질문: 회피와 탐지의 예로 은행원 알고리즘과 DB의 데드락 탐지 후 롤백을 들 수 있습니다.

Q5. 뮤텍스와 세마포어의 차이는 무엇인가요?

뮤텍스는 상호 배제를 위한 잠금으로, 한 번에 하나의 스레드만 소유할 수 있고 잠근 스레드가 풀어야 한다는 소유권 개념이 있습니다. 세마포어는 정수 카운터로, 값만큼의 스레드가 동시에 진입할 수 있고(예: DB 커넥션 10개), 소유권이 없어 다른 스레드가 post할 수 있으므로 신호 전달에도 쓰입니다. 값이 1인 이진 세마포어는 뮤텍스처럼 쓸 수 있지만 소유권 검사와 우선순위 상속 같은 기능이 없다는 점이 다릅니다.

Q6. 조건 변수에서 wait를 while 루프 안에서 호출해야 하는 이유는?

첫째, POSIX는 signal 없이도 깨어나는 가짜 깨어남을 허용합니다. 둘째, signal로 깨어난 스레드가 mutex를 다시 잡기 전에 다른 스레드가 먼저 조건을 소비할 수 있습니다. 셋째, broadcast로 여러 스레드가 깨면 그중 일부만 조건을 만족합니다. 따라서 깨어난 뒤 조건을 다시 확인하는 while 루프가 필수입니다. 꼬리 질문: wait가 mutex를 인자로 받는 이유는 "락 해제와 잠들기"를 원자적으로 해서 잃어버린 깨우기를 막기 위해서입니다.

Q7. C에서 volatile을 쓰면 스레드 간 동기화가 되나요?

되지 않습니다. volatile은 컴파일러가 그 변수 접근을 최적화로 제거하거나 레지스터에 캐시하지 못하게 할 뿐, 읽기-수정-쓰기의 원자성도, CPU 수준의 메모리 순서도 보장하지 않습니다. C11 기준으로 volatile 변수에 대한 동기화 없는 동시 접근도 여전히 데이터 레이스입니다. 스레드 간 공유에는 mutex나 C11 _Atomic을 쓰고, volatile은 메모리 맵 I/O나 시그널 핸들러의 sig_atomic_t 플래그에 씁니다. Java의 volatile과 의미가 다르다는 점을 함께 말하면 좋습니다.

Q8. 스레드 안전(thread-safe)과 재진입 가능(reentrant)의 차이는?

스레드 안전은 여러 스레드가 동시에 호출해도 올바르게 동작하는 성질이고, 재진입 가능은 실행 도중 시그널 핸들러나 재귀로 같은 함수가 다시 호출되어도 안전한 성질입니다. 내부 상태를 mutex로 보호한 함수는 스레드 안전하지만, 시그널 핸들러에서 다시 불리면 이미 잡힌 락을 기다리며 교착에 빠지므로 재진입 가능하지 않습니다. strtok처럼 static 상태를 쓰는 함수는 둘 다 아니며, strtok_r처럼 상태를 호출자가 넘기게 하면 둘 다 만족합니다.

Q9. CAS(Compare-And-Swap)란 무엇이고 어디에 쓰나요?

메모리의 현재 값이 기대값과 같을 때만 새 값으로 바꾸는 것을 하나의 원자적 명령으로 수행하는 연산입니다. 실패하면 현재 값을 다시 읽어 재시도하는 루프로 락 없는 갱신을 구현하며, 카운터·한도 차감·락 없는 큐 등에 쓰입니다. mutex의 내부 구현도 CAS 기반입니다. 꼬리 질문: ABA 문제는 값이 A→B→A로 바뀌어도 CAS가 변화가 없다고 착각하는 문제로, 버전 번호를 함께 비교해 해결합니다. DB의 낙관적 락(29장)이 같은 원리입니다.

Q10. 스레드 풀을 쓰는 이유와 적정 크기는?

요청마다 스레드를 생성·소멸하는 비용을 없애고, 동시 실행 스레드 수를 제한해 폭주 시에도 메모리와 컨텍스트 스위칭 비용을 예측 가능하게 하기 위해서입니다. 크기는 CPU 위주 작업이면 코어 수 정도, I/O 대기가 많으면 코어 수 × (1 + 대기시간/처리시간) 정도를 출발점으로 측정하며 조정합니다. 실무에서는 DB 커넥션 수 같은 하위 자원 한도도 고려해야 하고, 외부 호출 타임아웃이 없으면 풀이 고갈될 수 있다는 점을 언급하면 좋습니다.
