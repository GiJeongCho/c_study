배치 프로그래밍

고객이 잠든 밤, 은행 전산실에서는 수천 개의 배치 작업이 줄지어 돌아갑니다. 이자를 계산하고, 다른 기관과 하루 거래를 맞춰 보고, 다음 날 영업을 준비합니다. 배치 하나가 실패하면 아침 9시 영업 개시가 늦어질 수도 있습니다. 이 장에서는 수천만 건의 레코드를 안전하게 처리하고, 실패해도 정확히 다시 시작할 수 있는 배치 프로그램을 C로 설계하는 법을 배웁니다.

이 장에서 배울 것

  • 온라인 처리와 배치 처리의 차이, 일마감·월마감 작업 흐름을 이해합니다.
  • Header/Data/Trailer 레코드 구조의 파일을 설계하고 검증합니다.
  • 파일 전체를 메모리에 올리지 않는 스트리밍 처리와 버퍼 크기에 따른 I/O 성능을 이해합니다.
  • 정렬-병합(sort-merge) 기반 대사(reconciliation) 알고리즘을 구현합니다.
  • 배치 스케줄러와 약속하는 종료 코드 규약을 설계합니다.
  • Trailer 합계 검증, 체크섬(CRC32), 멱등성, 체크포인트·재시작을 구현합니다.
  • 임시 파일 + rename으로 원자적 교체, 락 파일로 중복 실행 방지, 배치 로그와 처리 통계를 남깁니다.
  • 실패 유형별 재처리 시나리오를 미리 설계하는 법을 익힙니다.

25-1대용량 파일 배치의 구조

온라인 처리와 배치 처리

금융 시스템의 업무 처리 방식은 크게 둘로 나뉩니다. 온라인(online) 처리는 고객이나 창구 직원이 요청한 거래 한 건을 즉시 처리하고 응답하는 방식입니다. ATM 출금, 모바일 이체가 대표적입니다. 배치(batch) 처리는 일정 시점까지 모인 많은 데이터를 한꺼번에 묶어서(batch = 한 묶음) 처리하는 방식입니다. 하루 동안의 거래를 모아 이자를 계산하거나, 카드사가 가맹점에 줄 대금을 정산하는 일이 여기에 해당합니다.

왜 모든 일을 온라인으로 즉시 처리하지 않을까요? 이유는 효율과 정합성입니다. 예금 이자를 생각해 봅시다. 수천만 계좌의 일별 이자를 고객 거래가 있을 때마다 계산하면 온라인 거래 하나하나가 무거워집니다. 대신 하루 영업이 끝나 잔액이 확정된 후, 한 번에 순차적으로 읽어 계산하면 디스크를 순서대로 읽는(sequential I/O) 가장 빠른 방식으로 처리할 수 있습니다. 또 "오늘 영업일의 거래"라는 확정된 범위에 대해 계산하므로 결과가 명확합니다.

일마감과 월마감 흐름

은행의 하루는 대략 다음과 같이 흘러갑니다. 시각과 작업 이름은 기관마다 다르지만 뼈대는 비슷합니다.

이 작업들은 선후 관계(dependency)로 엮여 있습니다. 원장이 확정되기 전에 이자를 계산하면 안 되고, 대외기관의 정산 파일을 받기 전에 대사를 하면 안 됩니다. 이 관계를 관리하는 것이 배치 스케줄러입니다. 스케줄러는 작업 A가 정상 종료(종료 코드 0)되면 작업 B를 시작하고, 비정상 종료되면 후속 작업을 멈추고 운영자에게 알립니다. 그래서 배치 프로그램의 종료 코드는 스케줄러와의 약속이며, 25-1-7에서 자세히 다룹니다.

월마감은 월말 영업일의 일마감 뒤에 추가로 돌아가는 작업입니다. 월 단위 이자 지급, 대출 이자 청구, 월 결산, 감독기관 보고 자료 생성 등이 포함되며 처리량이 일마감의 수 배에 이릅니다. 분기말·반기말·연말에는 더 많은 작업이 붙습니다. 그래서 연말 마감은 전산실의 가장 긴 밤이 됩니다.

은행 시스템에서는 — 배치 윈도우가 줄어든다

예전에는 밤 10시에 온라인을 닫고 새벽 6시까지 배치를 돌리는 "배치 윈도우"가 넉넉했습니다. 하지만 24시간 모바일 뱅킹 시대가 되면서 온라인을 완전히 닫는 시간은 거의 사라졌고, 배치는 온라인과 동시에 돌아가야 합니다. 이것은 배치 설계에 큰 영향을 줍니다. 배치가 원장 테이블을 오래 잠그면 온라인 거래가 대기하고, 배치가 CPU·I/O를 독점하면 온라인 응답이 느려집니다. 그래서 현대 금융 배치는 ① 작은 단위로 자주 커밋하고 ② 처리 속도를 조절(throttling)하며 ③ 실패 시 처음부터가 아니라 중단 지점부터 재시작할 수 있어야 합니다. 이 장의 25-2절이 바로 그 기술입니다.

Header / Data / Trailer 레코드 구조

기관 사이에 주고받는 배치 파일은 거의 예외 없이 Header-Data-Trailer 구조를 가집니다. 24장의 전문이 "한 건짜리 편지"라면, 배치 파일은 "표지 + 본문 여러 장 + 마지막 장 합계표"로 된 보고서입니다.

  • Header 레코드 (보통 1건): 파일 일자, 송신 기관, 파일 종류 등 파일 전체에 대한 정보.
  • Data 레코드 (N건): 실제 거래 한 건 한 건.
  • Trailer 레코드 (보통 1건): Data의 총 건수와 금액 합계. 파일이 중간에 잘리거나 레코드가 누락·중복되었는지 확인하는 용도.

각 레코드의 첫 바이트(레코드 구분)를 보고 종류를 판단합니다. 모든 레코드의 길이는 같습니다. 이 장에서는 다음 교육용 규격(레코드 길이 60바이트 + 줄바꿈 1바이트)을 씁니다.

왜 그럴까? — 파일 끝에 굳이 Trailer를 둘까?

파일 전송은 생각보다 자주 불완전하게 끝납니다. 네트워크가 끊기거나, 송신 측 디스크가 가득 차거나, 송신 프로그램이 파일을 쓰는 도중에 수신 측이 파일을 가져가 버리는 일이 실제로 일어납니다. 이때 받은 파일은 형식상 멀쩡한 레코드들로 끝날 수 있습니다. 1,000만 건 중 600만 건에서 레코드 경계에 딱 맞게 잘렸다면, 읽는 쪽은 아무 오류 없이 600만 건을 처리하고 "정상 종료"해 버립니다. Trailer가 있으면 ① Trailer 레코드 자체가 없으니 "파일이 끝까지 오지 않았다"를 알 수 있고 ② Trailer의 건수·합계와 실제로 읽은 값을 비교해 누락·중복·변조를 잡아낼 수 있습니다. Header의 파일일자는 "어제 파일을 오늘 또 처리"하는 사고를 막아 줍니다.

여기서 잠깐 — 줄바꿈이 있는 파일, 없는 파일

메인프레임 출신 파일은 레코드 사이에 줄바꿈이 없는 경우가 많습니다(고정 블록 레코드). 유닉스 쪽에서 만드는 파일은 보통 레코드마다 '\n'을 붙이고, 윈도우를 거친 파일은 "\r\n"이 붙어 한 레코드가 1바이트 더 길어지기도 합니다. 레코드 길이 61을 기대했는데 62바이트씩 들어온다면 CRLF를 의심하세요. 규격서에 "레코드 길이 60, 개행 문자 포함 여부"를 반드시 명시합니다.

스트리밍 처리 — 전체를 메모리에 올리지 않기

신입 개발자가 대용량 파일을 처리할 때 자주 하는 실수가 "파일 크기만큼 malloc해서 통째로 읽은 뒤 처리"입니다. 테스트 파일 10MB에서는 잘 되지만, 운영 파일 8GB를 만나면 메모리 할당 실패나 스왑(swap) 폭주로 서버 전체가 느려집니다. 같은 서버에서 온라인 프로세스도 돌고 있다는 점을 잊으면 안 됩니다.

정답은 스트리밍(streaming)입니다. 레코드를 하나 읽고, 처리하고, 버리고, 다음 레코드를 읽습니다. 메모리 사용량은 파일 크기와 무관하게 레코드 몇 개 + I/O 버퍼 크기로 일정합니다. 필요한 집계(건수, 합계)만 변수에 누적합니다.

왜 그럴까? — 왜 fgets가 아니라 fread로 읽을까?

fgets는 줄바꿈을 기준으로 읽는 함수라서 텍스트 파일에 편리하지만, 고정길이 레코드 파일에는 몇 가지 함정이 있습니다. ① 레코드 안에 우연히 '\n'(0x0A) 바이트가 들어 있으면(바이너리·팩드 필드나 깨진 데이터) 레코드가 중간에 끊겨 이후 모든 레코드가 밀립니다. ② 레코드 안에 널 바이트가 있으면 strlen으로 길이를 잴 수 없습니다. ③ 줄이 버퍼보다 길면 나머지가 다음 호출로 넘어갑니다. fread로 정확히 61바이트씩 읽고 "61번째 바이트가 '\n'인가"를 검사하면 레코드 길이 규격을 엄격하게 확인할 수 있습니다. 또 "rb" 모드로 열어 윈도우에서도 개행 변환이 일어나지 않게 했습니다.

루프가 끝난 뒤 ferror와 n을 검사하는 부분도 중요합니다. fread가 61보다 작은 값을 반환하는 경우는 세 가지입니다. 정상 EOF(n == 0), 파일이 레코드 중간에서 잘림(0 < n < 61), 그리고 디스크 I/O 오류(ferror). 이 셋을 구분하지 않으면 "디스크 오류로 중간까지만 읽고 정상 종료"하는 최악의 상황이 생깁니다. 물론 이 경우 Trailer 검증이 마지막 방어선이 되어 주지만, 오류 원인은 정확히 남겨야 합니다.

자주 하는 실수 — 합계 변수의 오버플로

금액 합계를 int로 누적하면 약 21억 원에서 오버플로가 납니다. 은행 하루 이체 합계는 수조 원 단위이므로 long long(약 922경)을 써야 합니다. 그래도 극단적인 경우를 대비해 누적 전에 if (st.sum_amt > LLONG_MAX - amt)로 검사하는 것이 안전합니다. 부호 있는 정수 오버플로는 미정의 동작이라 "음수로 돌아간다"는 보장조차 없습니다.

정답과 해설 보기

Data 0건 파일은 정상입니다. Trailer의 건수 0과 금액 0이 누적값과 일치하므로 exit=0으로 끝납니다. 거래가 없는 날도 "빈 파일"을 보내는 것이 업계 관례이며, 파일 자체가 오지 않은 것과 구분할 수 있게 해 줍니다.

왜 그럴까? — 시스템 콜은 왜 비쌀까, 그리고 왜 버퍼를 무한정 키우면 안 될까?

시스템 콜은 CPU가 사용자 모드에서 커널 모드로 전환하고, 커널이 인자를 검증하고, 다시 돌아오는 과정을 거칩니다. 한 번에 수백 나노초에서 수 마이크로초가 걸리는데, 이는 일반 함수 호출의 수백 배입니다. 1,760만 번이면 시스템 콜 비용만으로 수 초~수십 초가 됩니다. 그래서 버퍼링으로 횟수를 줄이는 것이 핵심입니다.

하지만 버퍼가 일정 크기(대략 수백 KB~수 MB)를 넘으면 시스템 콜 비용은 이미 무시할 만큼 작아지고, 실제 병목은 디스크·스토리지 대역폭으로 옮겨 갑니다. 이후로는 버퍼를 키워도 빨라지지 않고 메모리와 CPU 캐시 효율만 나빠집니다. 또 리눅스 커널은 순차 읽기를 감지하면 미리 읽기(read-ahead)로 다음 데이터를 페이지 캐시에 올려 두므로, 사용자 버퍼를 아주 크게 할 필요가 없습니다. 실무에서는 256KB~1MB 정도를 많이 씁니다. 정답은 "측정"입니다. strace -c ./batch로 시스템 콜 횟수를, time으로 user/sys 시간을 확인하세요.

자주 하는 실수 — setvbuf의 버퍼 수명

setvbuf에 넘긴 버퍼는 파일을 fclose할 때까지 살아 있어야 합니다. 함수 안의 지역 배열(자동 변수)을 넘기고 그 함수가 반환된 뒤에도 파일을 쓰면, 이미 해제된 스택 메모리를 stdio가 계속 사용하는 미정의 동작이 됩니다. 위 예제에서 static char iobuf[...]로 선언한 이유입니다(1MB를 스택에 두면 스택 크기 제한도 위험합니다). 또 setvbuf는 파일을 연 직후, 어떤 입출력도 하기 전에 호출해야 합니다.

은행 시스템에서는 — 출력 파일 한 줄마다 fflush

어느 카드사의 정산 파일 생성 배치가 평소 20분이던 처리 시간이 갑자기 2시간을 넘겨 아침 개시를 위협했습니다. 원인은 직전 배포에서 누군가 "장애 시 어디까지 썼는지 보려고" 출력 레코드를 쓸 때마다 fflush()를 추가한 것이었습니다. 레코드 3,000만 건마다 write 시스템 콜이 발생했고, 저장소가 원격 스토리지(NAS)여서 호출마다 네트워크 왕복까지 붙었습니다. 진행 상황 확인은 로그에 일정 건수마다 통계를 찍는 방식으로 해야지 데이터 파일 버퍼링을 깨뜨려서는 안 됩니다. 그리고 "어디까지 썼는지"는 25-2절의 체크포인트가 담당합니다.

정렬-병합(sort-merge)과 대사(reconciliation) 알고리즘

대사(對査)란 두 곳의 기록을 맞대어 일치하는지 확인하는 작업입니다. 우리 은행 원장의 타행이체 내역과 중계 기관이 보내 준 정산 파일, 카드사 승인 내역과 가맹점 매입 내역, 증권사 체결 내역과 거래소 체결 통보를 비교합니다. 불일치 건은 사고의 씨앗입니다. 돈은 나갔는데 상대가 받은 기록이 없거나, 상대는 처리했는데 우리 원장에는 없는 건을 찾아내야 합니다.

두 파일이 각각 수천만 건이라면 어떻게 비교할까요? 단순한 방법은 이중 루프로 A의 각 건을 B 전체에서 찾는 것인데, 이는 O(N×M)이라 1,000만 × 1,000만 = 1014번 비교로 사실상 끝나지 않습니다. 해시 테이블(23장)에 한쪽을 올리면 O(N+M)이지만 수천만 건을 메모리에 올려야 합니다. 배치의 정석은 두 파일을 같은 키로 정렬한 뒤 병합하듯 한 번씩만 훑는 정렬-병합 방식입니다.

원리는 병합 정렬(merge sort)의 병합 단계와 같습니다. 양쪽에서 현재 레코드 하나씩을 보고 키를 비교합니다.

  • 키가 같으면: 금액을 비교해 일치(MATCH) 또는 불일치(DIFF). 양쪽 모두 다음 레코드로.
  • 우리 키가 더 작으면: 그 키는 상대 파일에 없다(ONLY_OURS). 우리 쪽만 다음으로.
  • 상대 키가 더 작으면: 그 키는 우리 원장에 없다(ONLY_THEIR). 상대 쪽만 다음으로.
  • 한쪽이 끝나면 다른 쪽의 남은 레코드는 모두 "한쪽에만 있음".

왜 그럴까? — 왜 "정렬 검증"까지 넣었을까?

정렬-병합 알고리즘은 두 입력이 같은 기준으로 정렬되어 있다는 전제 위에서만 맞습니다. 만약 상대 파일의 한 레코드가 순서를 벗어나 있으면, 알고리즘은 오류 없이 "한쪽에만 있음"을 양쪽에 하나씩 잘못 보고합니다. 겉보기에는 멀쩡한 결과가 나오니 더 위험합니다. 그래서 읽으면서 직전 키보다 커지는지 검사합니다. 정렬 기준도 중요합니다. strcmp는 바이트 값으로 비교하는데, 정렬 유틸리티 sort는 로캘(LANG=ko_KR.UTF-8 등)에 따라 다른 순서를 쓸 수 있습니다. 배치에서 sort를 쓸 때는 LC_ALL=C sort로 바이트 순서를 강제하는 것이 정석입니다. 24장에서 본 EBCDIC 정렬 순서 차이도 같은 맥락입니다.

여기서 잠깐 — 메모리보다 큰 파일의 정렬: 외부 정렬

정렬할 파일이 메모리보다 크면 외부 정렬(external sort)을 씁니다. ① 메모리에 들어가는 만큼(예: 1GB)씩 읽어 qsort로 정렬한 뒤 임시 파일(run)로 씁니다. ② 생성된 여러 run 파일을 동시에 열어, 각 run의 맨 앞 레코드 중 가장 작은 것을 골라 출력하는 k-way 병합을 합니다(최소 힙을 쓰면 효율적). 유닉스 sort 명령이 내부적으로 정확히 이 방식이고, -S로 메모리 크기, -T로 임시 디렉터리를 지정합니다. 고정길이 레코드라면 LC_ALL=C sort -k1.2,1.8처럼 바이트 위치로 키를 지정할 수 있습니다. 직접 구현하는 것은 연습문제로 남깁니다.

은행 시스템에서는 — 대사 불일치는 "돈의 행방"

대사 결과 불일치 건은 자동으로 담당 부서의 확인 대상 목록에 올라갑니다. 흔한 원인은 ① 타임아웃 거래: 우리는 응답을 못 받아 실패로 처리했는데 상대는 성공 처리한 건(27장) ② 마감 시각 경계: 23:59:59에 발생한 거래가 우리는 D일, 상대는 D+1일로 집계된 건 ③ 취소 거래의 반영 시점 차이 ④ 실제 시스템 오류입니다. ①은 실제 고객 돈이 걸린 문제라 다음 영업일 오전 중 반드시 정리(망취소 또는 사후 입금)합니다. 어떤 은행에서는 경계 시각 문제로 매일 수십 건의 "가짜 불일치"가 나오자 담당자들이 불일치 목록을 습관적으로 무시하게 되었고, 그사이 섞여 있던 진짜 오류 몇 건이 몇 주 뒤에야 발견되었습니다. 노이즈 없는 대사가 중요한 이유입니다. 알려진 경계 케이스는 규칙으로 자동 해소하고, 사람에게는 진짜 불일치만 보여 줘야 합니다.

종료 코드 규약

배치 프로그램은 화면 앞에 사람이 앉아 결과를 보는 프로그램이 아닙니다. 결과를 판단하는 주체는 배치 스케줄러이고, 스케줄러가 볼 수 있는 것은 사실상 프로세스 종료 코드(exit status)뿐입니다. main의 반환값이나 exit()의 인자가 부모 프로세스(셸, 스케줄러 에이전트)에 전달되고, 셸에서는 $?로 확인합니다.

왜 그럴까? — exit(-1)을 하면 왜 255가 될까?

유닉스에서 부모가 wait로 받는 종료 상태(status)에는 자식의 종료 코드 중 하위 8비트만 담깁니다(26장의 WEXITSTATUS). -1은 2의 보수로 모든 비트가 1이므로 하위 8비트는 0xFF = 255가 됩니다. 마찬가지로 exit(256)은 0, 즉 "정상"으로 보입니다! 처리 건수나 오류 건수를 그대로 종료 코드로 반환하는 프로그램이 오류 256건일 때 정상 종료로 보고된 사례가 실제로 있습니다. 종료 코드는 0~125 범위의 작은 약속된 값만 쓰세요. 126, 127은 셸이 "실행 불가", "명령 없음"에 쓰고, 128 이상은 시그널 종료와 겹칩니다.

파이프라인의 종료 코드는 마지막 명령(tee)의 것이므로 첫 번째 줄도 실패를 숨깁니다. 해결은 다음과 같습니다.

25-2정합성 검증과 재처리 설계

배치 프로그래밍의 진짜 실력은 "정상일 때 잘 도는 것"이 아니라 "비정상일 때 어떻게 되는가"에서 드러납니다. 입력이 깨져 있으면 반드시 잡아내야 하고, 처리 도중에 죽으면 데이터가 반쯤 반영된 채 남지 않아야 하며, 다시 돌렸을 때 이미 처리한 건을 또 처리하지 않아야 합니다. 이 절에서는 그 세 가지, 즉 검증·원자성·멱등성을 구현합니다.

Trailer 건수/금액 합계 검증

25-1-4의 프로그램이 이미 Trailer 검증을 하고 있지만, 실무에서는 한 단계 더 들어가야 할 점들이 있습니다.

  1. 검증과 반영의 순서: Trailer는 파일 끝에 있습니다. 레코드를 읽으면서 바로 DB에 반영하면, Trailer에서 불일치를 발견했을 때는 이미 수백만 건을 반영한 뒤입니다. 그래서 두 가지 방법 중 하나를 씁니다. ① 2-pass: 1차로 파일 전체를 훑어 검증만 하고, 통과하면 2차로 반영합니다. 파일을 두 번 읽지만 가장 안전합니다. ② 1-pass + 롤백 가능 구조: 임시(staging) 테이블에 적재하며 검증하고, Trailer까지 통과하면 본 테이블로 한 번에 옮깁니다.
  2. 세분화된 합계: 총금액 하나만 보면 입금 +100과 출금 +100이 서로 바뀌어도 잡지 못합니다. 실무 Trailer는 입금 건수/금액, 출금 건수/금액, 취소 건수/금액처럼 구분별 합계를 담는 경우가 많습니다.
  3. Header와의 교차 검증: Header의 파일일자가 오늘 처리 대상 영업일과 같은지, 기관코드가 예상과 같은지 확인합니다. "어제 파일"을 다시 처리하는 사고를 막습니다.

체크섬 — 내용 변조와 전송 오류 잡기

Trailer 합계는 건수·금액 누락은 잘 잡지만, 계좌번호의 숫자 하나가 바뀐 것은 잡지 못합니다. 이럴 때 체크섬(checksum)을 씁니다. 파일 전체(또는 각 레코드)의 바이트로부터 짧은 값을 계산해 함께 보내고, 받는 쪽이 다시 계산해 비교합니다.

CBF43926은 CRC32의 표준 검사값(check value)입니다. 직접 구현한 CRC가 이 값을 내면 구현이 맞다고 봐도 됩니다. 두 번째 결과가 같다는 점이 중요합니다. 파일을 1MB씩 읽으며 crc32_update를 이어서 호출하면 파일 전체를 메모리에 올리지 않고도 전체 CRC를 얻을 수 있습니다. 스트리밍 처리 원칙과 잘 맞습니다.

여기서 잠깐 — 체크섬은 보안이 아닙니다

CRC32는 우연한 전송 오류를 잡기 위한 것입니다. 악의를 가진 사람은 파일 내용을 바꾼 뒤 CRC가 같아지도록 4바이트를 조정하는 것이 쉽습니다. 금융 파일 송수신에서 위·변조 방지가 필요하면 전용 회선·VPN·SFTP 같은 채널 보안에 더해 HMAC이나 전자서명을 적용합니다. 면접에서 "CRC로 무결성을 보장한다"고 말하면 꼬리 질문이 들어옵니다. "우연한 오류 검출"과 "의도적 변조 방지"를 구분해 말하세요.

중복 처리 방지 — 멱등성

멱등성(idempotency)이란 같은 연산을 여러 번 해도 결과가 한 번 한 것과 같은 성질입니다. 수학의 절댓값 함수가 그렇습니다: |(|x|)| = |x|. 배치에서 멱등성이 중요한 이유는 간단합니다. 배치는 반드시 다시 돌게 됩니다. 중간에 죽어서, 운영자가 실수로, 스케줄러가 재시도해서, 상대 기관이 같은 파일을 두 번 보내서. 그때마다 입금이 두 번 되면 안 됩니다.

왜 그럴까? — "잔액 += 금액"은 왜 멱등하지 않을까?

balance += 10000을 두 번 실행하면 20,000원이 늘어납니다. 반면 "거래번호 T123의 결과 잔액을 50,000원으로 설정"은 몇 번 실행해도 50,000원입니다. 하지만 원장 잔액을 절대값으로 덮어쓰는 방식은 동시성 문제가 있어 쓰기 어렵습니다. 그래서 실무에서는 증분 연산을 하되 "이 거래가 이미 반영되었는가"를 같은 트랜잭션 안에서 확인합니다. 예를 들어 거래내역 테이블에 (파일일자, 기관, 일련번호)를 기본키로 INSERT하고, 성공했을 때만 잔액을 갱신하여 둘을 함께 커밋합니다. 같은 레코드가 다시 오면 INSERT가 중복 키 오류로 실패하므로 잔액 갱신도 일어나지 않습니다. 키 생성 → 존재 확인 → 반영이 원자적으로 묶여야 한다는 것이 핵심입니다.

자주 하는 실수 — 중복 확인과 반영을 따로 하기

if (!db_exists(key)) { db_insert(...); db_add_balance(...); }처럼 "먼저 조회하고 없으면 반영"하는 코드는 같은 파일을 두 프로세스가 동시에 처리하면 둘 다 "없음"을 보고 둘 다 반영합니다(TOCTOU: Time Of Check to Time Of Use 경쟁). DB의 유일 키 제약처럼 확인과 반영이 하나의 원자적 연산인 메커니즘에 맡겨야 합니다. 그리고 애초에 두 프로세스가 동시에 돌지 않게 하는 것이 25-2-6의 락 파일입니다.

체크포인트와 재시작

3,000만 건 처리 배치가 2,900만 건째에서 DB 연결 끊김으로 죽었다고 해 봅시다. 처음부터 다시 돌리면 멱등성 덕분에 결과는 맞겠지만, 2,900만 건을 다시 읽고 중복 확인하는 데 몇 시간이 걸려 아침 개시를 놓칩니다. 체크포인트(checkpoint)는 "어디까지 확실히 처리했는가"를 주기적으로 저장해 두었다가, 재시작할 때 그 지점부터 이어서 처리하게 해 줍니다.

왜 그럴까? — 체크포인트와 커밋의 순서는 어떻게 해야 할까?

N건을 DB에 커밋한 뒤 체크포인트 파일을 저장한다고 합시다. 둘 사이에서 프로세스가 죽으면 DB에는 반영되었지만 체크포인트는 이전 위치를 가리킵니다. 재시작하면 그 N건을 다시 처리하게 되는데, 멱등성이 있으면 "중복 skip"으로 안전하게 지나갑니다. 반대 순서(체크포인트 먼저, 커밋 나중)는 어떨까요? 체크포인트 저장 후 커밋 전에 죽으면, 재시작 시 체크포인트 이후부터 읽으므로 그 N건은 영영 처리되지 않습니다. 데이터 누락은 중복보다 훨씬 찾기 어렵습니다. 그래서 순서는 반드시 "커밋 → 체크포인트"이고, 그 사이 구간은 멱등성으로 덮습니다.

가장 이상적인 방법은 체크포인트를 파일이 아니라 같은 DB 테이블에 저장해서 데이터와 함께 한 트랜잭션으로 커밋하는 것입니다. 그러면 "데이터는 반영됐는데 체크포인트는 아님"이라는 상태 자체가 존재하지 않습니다. 파일 기반 체크포인트는 DB가 없는 파일→파일 변환 배치에서 주로 씁니다.

본 처리 루프에서는 다음과 같이 씁니다. 핵심만 보이기 위해 오류 처리를 줄였습니다.

여기서 잠깐 — fseek 대신 fseeko를 쓰는 이유

fseek/ftell은 위치를 long으로 다룹니다. 64비트 리눅스에서 long은 8바이트라 문제없지만, 32비트 시스템이나 64비트 윈도우(long이 4바이트)에서는 2GB를 넘는 파일 위치를 표현하지 못합니다. POSIX의 fseeko/ftello는 off_t를 쓰고, 32비트 환경에서도 -D_FILE_OFFSET_BITS=64로 컴파일하면 64비트 위치를 지원합니다. 수 GB 배치 파일이 흔한 금융권에서는 습관적으로 fseeko를 씁니다.

은행 시스템에서는 — 체크포인트가 가리킨 "다른 파일"

어느 은행의 대량 이체 배치가 새벽에 죽었고, 운영자는 상대 기관에 연락해 같은 이름의 파일을 다시 받은 뒤 배치를 재기동했습니다. 그런데 재송신된 파일은 상대 기관이 오류를 수정해 레코드 몇 건이 추가된 내용이 다른 파일이었습니다. 체크포인트는 파일 이름만 비교했기 때문에 새 파일의 1,500만 번째 바이트부터 읽기 시작했고, 그 위치는 레코드 경계도 아니었습니다. 다행히 레코드 형식 검증에서 바로 실패했지만, 만약 레코드 길이가 우연히 맞았다면 중간 레코드들이 누락된 채 처리될 뻔했습니다. 이후 체크포인트의 파일 식별자를 "파일명 + 크기 + Header 레코드 + 파일 CRC"로 바꾸고, 식별자가 다르면 재시작을 거부하고 운영자 판단을 요구하도록 고쳤습니다.

임시 파일 후 rename — 원자적 교체

배치가 결과 파일 settle_20261028.dat를 만들고 있는데, 다음 작업(또는 파일 전송 데몬)이 이 파일이 생기자마자 가져가 버리면 어떻게 될까요? 반쯤 쓰인 파일이 상대 기관으로 넘어갑니다. 쓰는 도중에 프로세스가 죽어도 반쯤 쓰인 파일이 정식 이름으로 남습니다. 해결책은 유닉스의 고전적인 패턴, 임시 파일에 다 쓴 뒤 rename입니다.

왜 그럴까? — fflush와 fsync는 무엇이 다를까?

데이터가 디스크에 닿기까지는 세 단계의 버퍼가 있습니다. ① stdio 버퍼(사용자 공간) ② 커널 페이지 캐시 ③ 디스크 장치. fflush는 ①을 비워 ②로 보낼 뿐입니다. 이 시점에 다른 프로세스는 파일 내용을 볼 수 있지만, 전원이 나가면 ②의 내용은 사라집니다. fsync는 ②의 해당 파일 데이터를 ③까지 내려보내고 완료될 때까지 기다립니다. 그래서 "정말로 저장됨"이 필요한 체크포인트·결과 파일에는 fsync를 씁니다. 대신 fsync는 디스크 왕복을 기다리므로 비쌉니다. 레코드마다 호출하면 안 되고, 체크포인트 저장처럼 의미 있는 시점에만 호출합니다.

rename이 원자적이라는 것은 POSIX가 보장하는 성질입니다. 대상 이름이 이미 있으면 "기존 파일을 가리키던 이름이 새 파일을 가리키도록" 한 번에 바뀝니다. 다만 서로 다른 파일시스템 사이의 rename은 실패(EXDEV)하므로, 임시 파일은 반드시 대상과 같은 디렉터리(또는 같은 파일시스템)에 만듭니다. /tmp에 만들고 /data로 rename하는 코드는 서버 구성에 따라 실패합니다. 또 NFS 같은 네트워크 파일시스템에서는 원자성 보장이 약할 수 있으므로 확인이 필요합니다.

자주 하는 실수 — 수신 측도 "완료 신호"를 보고 가져가야 한다

임시 파일 + rename은 같은 서버 안에서 원자성을 줍니다. 파일을 다른 서버로 전송하는 경우(FTP/SFTP), 수신 측은 파일이 도착하는 동안에도 정식 이름의 파일을 볼 수 있습니다. 그래서 금융권 파일 송수신에서는 ① 임시 이름으로 전송 후 원격 rename ② 데이터 파일 전송이 끝난 뒤 빈 "완료 파일(.end, .ok)"을 따로 전송 ③ 일정 시간 동안 크기 변화가 없으면 완료로 간주(가장 약한 방법) 중 하나를 씁니다. 수신 배치는 완료 파일이 있을 때만 데이터 파일을 처리합니다.

락 파일 — 중복 실행 방지

같은 배치가 동시에 두 번 돌면 멱등성이 있더라도 DB 락 경합, 체크포인트 파일 덮어쓰기, 결과 파일 충돌 같은 문제가 생깁니다. 스케줄러 재시도와 운영자의 수동 실행이 겹치는 일은 생각보다 흔합니다. 그래서 배치는 시작하자마자 락(lock)을 잡습니다.

고전적인 방법은 open(path, O_CREAT | O_EXCL)로 락 파일을 "없을 때만 생성"하는 것입니다. 하지만 이 방법은 프로세스가 비정상 종료(kill -9, 서버 다운)하면 락 파일이 남아 다음 실행이 영원히 막히는 stale lock 문제가 있습니다. 더 나은 방법은 커널 레코드 락(fcntl)입니다. 락은 열린 파일에 걸리고, 프로세스가 어떻게 죽든 커널이 자동으로 해제합니다.

자주 하는 실수 — fcntl 락의 함정

POSIX fcntl 레코드 락은 "프로세스 + 파일" 단위로 관리되어, 같은 프로세스 안에서 그 파일을 가리키는 어떤 fd든 하나를 닫으면 락이 전부 풀립니다. 예를 들어 락을 잡은 뒤 다른 함수가 같은 락 파일을 fopen으로 열어 PID를 읽고 fclose하면 그 순간 락이 사라집니다. 또 fork한 자식에게 상속되지 않습니다. 리눅스의 flock()이나 F_OFD_SETLK(열린 파일 기술 단위 락)는 이 문제가 없지만 이식성이 떨어집니다. 사용하는 플랫폼의 의미를 정확히 알고 쓰세요. NFS 위의 락은 신뢰하기 어려우므로 락 파일은 로컬 디스크에 둡니다.

배치 로그와 처리 통계

새벽 3시에 배치가 실패했을 때 당직자가 볼 수 있는 것은 로그뿐입니다. 좋은 배치 로그는 "무슨 일이 있었는지"를 개발자에게 전화하지 않고도 알 수 있게 해 줍니다.

  • 시작 로그: 프로그램 버전, 인자, 입력 파일명·크기·CRC, 처리 대상 영업일, 재시작 여부와 체크포인트 위치.
  • 진행 로그: N건(또는 N초)마다 처리 건수, 처리 속도(건/초), 예상 남은 시간. 레코드마다 찍지 않습니다.
  • 오류 로그: 레코드 번호, 파일 offset, 키(계좌번호는 마스킹), 오류 사유. 문제 레코드를 바로 찾아갈 수 있어야 합니다.
  • 종료 통계: 읽은 건수 = 반영 + 중복 skip + 오류 skip 의 항등식이 성립하는지, 금액 합계, 소요 시간, 종료 코드.

왜 그럴까? — 소요 시간은 왜 CLOCK_MONOTONIC으로 잴까?

CLOCK_REALTIME(또는 time())은 "벽시계" 시각이라 NTP 동기화나 운영자의 시각 조정으로 앞뒤로 점프할 수 있습니다. 배치 도중 시계가 30초 뒤로 조정되면 소요 시간이 음수가 될 수도 있습니다. CLOCK_MONOTONIC은 부팅 이후 단조 증가만 하는 시계라 경과 시간 측정에 적합합니다. 반대로 로그에 찍는 "몇 시 몇 분"은 사람이 읽는 시각이므로 CLOCK_REALTIME을 씁니다. 용도에 맞는 시계를 고르는 것도 실력입니다.

한 줄 요약

견고한 배치 = 검증 먼저(Trailer, 체크섬) + 작은 단위 커밋과 체크포인트 + 멱등한 반영 + 원자적 결과 파일 + 단일 실행 락 + 항등식이 맞는 통계 로그 + 약속된 종료 코드. 이 일곱 가지가 갖춰지면 "그냥 다시 돌리세요"라는 말을 자신 있게 할 수 있습니다.

예제 25-4 난이도 ★★★

CKPT_EVERY = 10000으로 3만 5천 건 처리 중 32,500번째 레코드에서 프로세스가 kill -9로 죽었습니다. 재시작하면 몇 번째 레코드부터 읽고, 그중 몇 건이 "중복 skip"이 될 수 있습니까? 커밋은 체크포인트 시점에만 한다고 가정합니다.

정답과 해설 보기

마지막 체크포인트는 30,000건째 커밋 후 저장되었으므로 offset은 30,001번째 레코드의 시작을 가리킵니다. 재시작하면 30,001번째부터 읽습니다. 30,001~32,500번 레코드는 아직 커밋 전이었으므로 kill -9와 함께 DB 트랜잭션이 롤백(연결 끊김 시 DB가 미커밋 트랜잭션을 롤백)되었습니다. 따라서 이 가정에서는 중복 skip이 0건입니다. 중복 skip이 생기는 것은 "커밋은 끝났는데 체크포인트 저장 전에 죽은" 경우로, 최대 10,000건이 skip될 수 있습니다. 만약 apply_record처럼 레코드마다 커밋하는 구조였다면 30,001~32,499번(또는 32,500번까지)이 이미 반영되어 있어 약 2,500건이 중복 skip됩니다. 어느 쪽이든 결과는 정확하며, 이것이 체크포인트 + 멱등성 조합의 힘입니다.

핵심 정리

  • 온라인은 한 건을 즉시(응답 시간), 배치는 대량을 묶어서(처리량·완료 시각) 처리합니다. 일마감·월마감 작업은 선후 관계로 엮여 있고 배치 스케줄러가 종료 코드로 흐름을 제어합니다.
  • 기관 간 배치 파일은 Header(파일 정보)·Data(거래)·Trailer(건수·합계) 구조입니다. Trailer는 잘린 파일, 누락, 중복을 잡는 검산표입니다.
  • 대용량 파일은 통째로 올리지 말고 스트리밍으로 처리합니다. 고정길이 레코드는 fread로 정확한 길이만큼 읽고 EOF·잘림·I/O 오류를 구분합니다.
  • stdio 버퍼 크기는 시스템 콜 횟수를 결정합니다. 수백 KB~1MB면 충분하며, 레코드마다 fflush하는 것은 성능 재앙입니다.
  • 대사는 두 파일을 같은 키로 정렬한 뒤 두 포인터로 한 번씩 훑는 정렬-병합으로 O(N+M), 메모리 O(1)에 처리합니다. 입력의 정렬 여부도 검증합니다.
  • 종료 코드는 하위 8비트만 전달됩니다. 0~125의 약속된 작은 값을 쓰고, 셸 래퍼가 종료 코드를 삼키지 않게 pipefail과 exit $rc를 씁니다.
  • 검증과 반영을 분리(2-pass 또는 staging)하고, 체크섬(CRC32)으로 내용 오류를 잡습니다. CRC는 우연한 오류용이지 보안 수단이 아닙니다.
  • 멱등성은 파일 단위(처리 이력)·레코드 단위(유일 키)·연산 단위(반영 여부와 갱신을 한 트랜잭션)로 겹겹이 방어합니다.
  • 체크포인트는 "커밋 → 체크포인트" 순서로 저장하고, 그 사이 구간은 멱등성으로 덮습니다. 가능하면 체크포인트를 데이터와 같은 트랜잭션에 저장합니다.
  • 결과 파일은 같은 디렉터리의 임시 파일에 쓰고 fsync 후 rename하여 원자적으로 교체합니다. 중복 실행은 커널이 자동 해제하는 fcntl 락으로 막습니다.
  • 로그에는 시작 정보, 진행률, 오류 레코드 위치, "읽음 = 반영 + skip + 오류" 항등식을 남기고, 실패 유형별 재처리 시나리오를 미리 문서화합니다. 원장은 직접 수정하지 않고 역처리 거래로 원복합니다.

이 장에서 나오는 면접 질문

Q1. 멱등성(idempotency)이란 무엇이며, 배치나 API에서 왜 중요한가요?

같은 요청이나 작업을 여러 번 수행해도 결과가 한 번 수행한 것과 같은 성질입니다. 네트워크 타임아웃, 프로세스 재시작, 스케줄러 재시도 때문에 같은 작업은 반드시 반복 실행되므로, 멱등하지 않으면 이중 입금 같은 사고가 납니다. 구현은 거래 고유 키에 유일 제약을 두고, 반영 여부 확인과 반영을 한 트랜잭션으로 묶는 방식이 일반적입니다. 꼬리 질문: "HTTP 메서드 중 멱등한 것은?" → GET, PUT, DELETE는 멱등, POST는 아님. 그래서 결제 API는 Idempotency-Key 헤더를 둡니다.

Q2. 트랜잭션의 ACID를 설명하고, 배치의 커밋 주기를 어떻게 정하는지 말해 보세요.

원자성(전부 반영 또는 전부 취소), 일관성(제약 조건 유지), 격리성(동시 트랜잭션이 서로 간섭하지 않음), 지속성(커밋된 결과는 장애에도 보존)입니다. 배치에서 전체를 한 트랜잭션으로 묶으면 원자성은 좋지만 언두 로그가 커지고 락을 오래 잡아 온라인을 막으며, 실패 시 전부 다시 해야 합니다. 그래서 수천~수만 건 단위로 커밋하고, 그 경계를 체크포인트로 삼으며, 부분 반영 상태는 멱등성과 재시작으로 해결합니다. 커밋 주기는 처리 속도, 락 경합, 재처리 비용을 측정해 정합니다.

Q3. 메모리보다 큰 파일을 정렬하려면 어떻게 하나요?

외부 정렬을 씁니다. 메모리에 들어가는 크기만큼 읽어 내부 정렬한 뒤 run 파일로 쓰고, 여러 run을 최소 힙으로 k-way 병합합니다. 디스크 I/O가 병목이므로 run 크기를 크게 하고 순차 I/O를 유지하는 것이 중요합니다. 유닉스 sort가 이 방식이며, 바이트 순 정렬을 위해 LC_ALL=C를 지정합니다.

Q4. 두 대용량 파일에서 서로 다른 레코드를 찾는 효율적인 방법은?

메모리가 충분하면 한쪽을 해시 테이블에 넣고 다른 쪽을 훑는 O(N+M) 방법이 있고, 메모리가 부족하면 두 파일을 같은 키로 정렬한 뒤 두 포인터로 병합하며 비교하는 방법이 O(N log N + M log M) 정렬 후 O(N+M), 추가 메모리 O(1)입니다. 정렬-병합은 입력이 정렬되어 있다는 전제가 깨지면 잘못된 결과를 내므로 정렬 검증이 필요합니다.

Q5. fflush와 fsync의 차이는 무엇인가요?

fflush는 C 라이브러리(사용자 공간)의 stdio 버퍼를 커널로 넘기는 것이고, fsync는 커널 페이지 캐시의 파일 데이터를 디스크 장치까지 기록하고 완료를 기다리는 시스템 콜입니다. fflush만 하면 다른 프로세스는 데이터를 볼 수 있지만 전원 장애 시 유실될 수 있습니다. 내구성이 필요한 지점(체크포인트, 결과 파일 확정)에서만 fsync를 호출합니다. 비용이 크기 때문입니다.

Q6. 파일을 원자적으로 갱신하는 방법은?

같은 파일시스템(보통 같은 디렉터리)에 임시 파일을 만들어 전부 쓰고 fsync한 뒤 rename으로 대상 이름을 교체합니다. POSIX에서 같은 파일시스템 내 rename은 원자적이라, 읽는 쪽은 이전 파일 전체나 새 파일 전체만 보게 됩니다. 전원 장애까지 대비하려면 디렉터리도 fsync합니다. 다른 파일시스템 간에는 EXDEV로 실패합니다.

Q7. 시스템 콜이 일반 함수 호출보다 비싼 이유는?

사용자 모드에서 커널 모드로 전환하는 트랩, 레지스터 저장·복원, 커널의 인자 검증, 경우에 따라 캐시·TLB 영향이 있기 때문입니다. 그래서 작은 단위의 I/O를 많이 하면 시스템 콜 비용이 지배적이 되고, 버퍼링으로 호출 횟수를 줄이는 것이 성능의 핵심입니다. strace -c로 횟수를 측정할 수 있습니다.

Q8. CRC와 해시(SHA-256)의 차이, 그리고 CRC로 위·변조를 막을 수 있나요?

CRC는 다항식 나눗셈 기반으로 전송 중 생기는 우연한 비트 오류를 빠르게 검출하도록 설계되었고, 원하는 CRC 값을 만들도록 데이터를 조작하기가 쉽습니다. SHA-256 같은 암호학적 해시는 충돌을 찾기가 계산상 불가능하도록 설계되었습니다. 다만 해시도 공격자가 데이터와 해시를 함께 바꾸면 소용없으므로, 위·변조 방지에는 비밀키 기반 HMAC이나 전자서명이 필요합니다.

Q9. 프로세스가 죽어도 남지 않는 락은 어떻게 구현하나요?

O_CREAT|O_EXCL로 만든 락 파일은 비정상 종료 시 남아 stale lock이 됩니다. fcntl 레코드 락이나 flock은 커널이 열린 파일에 대해 관리하므로, 프로세스가 어떻게 종료되든 파일 기술자가 닫히면서 자동 해제됩니다. 단, fcntl 락은 같은 프로세스가 그 파일의 아무 fd나 닫아도 풀리고 fork 시 상속되지 않는다는 특성을 알고 써야 합니다.

정답과 해설 보기

파이프라인의 종료 코드는 마지막 명령 grep의 것입니다. 출력에 ERROR가 있으면 rc=0, 없으면 rc=1이고 batch의 2는 사라집니다. bash에서 set -o pipefail을 쓰면 0이 아닌 마지막 종료 코드(여기선 2)가 나오고, ${PIPESTATUS[0]}으로 첫 명령의 코드를 직접 볼 수도 있습니다.

연습문제 25-3 버그 찾기 난이도 ★★☆

다음 레코드 읽기 루프의 문제점을 지적하세요.

정답과 해설 보기

① feof는 "읽기를 시도했다가 EOF를 만난 후"에야 참이 됩니다. 마지막 레코드를 읽은 직후에는 아직 거짓이므로 한 번 더 루프에 들어가고, fread가 0을 반환해도 rec에 남은 마지막 레코드를 또 처리합니다(중복 처리!). ② fread의 반환값을 검사하지 않아 잘린 레코드나 I/O 오류를 구분하지 못합니다. ③ 개행 위치 검증이 없습니다. 올바른 형태는 while (fread(rec, 1, 61, fp) == 61) { ... } 후 루프 밖에서 ferror와 잔여 바이트를 검사하는 것입니다.

연습문제 25-4 코드 작성 — Trailer 생성 난이도 ★★☆

Data 레코드를 쓰면서 건수와 합계를 누적하고, 마지막에 60바이트 Trailer('T' + 건수 N(7) + 총금액 N(15) + 공백 37 + '\n')를 쓰는 함수 int write_trailer(FILE *fp, long long cnt, long long sum)을 작성하세요. 자릿수 초과는 오류로 처리합니다.

정답과 해설 보기

24장의 fld_set_num을 재사용하면 0 채움과 넘침 검사가 한 번에 해결됩니다. snprintf(rec, ..., "T%07lld%015lld", ...)도 가능하지만 넘쳐도 오류가 아니라 필드를 밀어 버리므로 별도 검사가 필요합니다. 쓰기가 끝나면 fclose의 반환값까지 확인해야 디스크 부족 같은 지연된 쓰기 오류를 놓치지 않습니다.

연습문제 25-5 정렬-병합 확장 난이도 ★★☆

recon.c를 고쳐, 불일치 결과를 화면 대신 recon_YYYYMMDD.dat 파일로 쓰되, 대사가 끝까지 성공한 경우에만 그 파일이 보이도록 하세요. 핵심 아이디어와 코드 골격을 쓰세요.

정답과 해설 보기

결과를 recon_YYYYMMDD.dat.tmp.PID에 쓰고, 루프가 오류 없이 끝나면 fflush → fsync(fileno(fp)) → fclose → rename 순서로 확정합니다. 중간에 형식·정렬 오류로 종료할 때는 임시 파일을 unlink합니다. 이렇게 하면 예제 25-2에서 본 "틀린 결과가 한 줄 나간" 문제가 후속 작업에 노출되지 않습니다.

연습문제 25-6 체크포인트 순서 난이도 ★★☆

동료가 "체크포인트를 먼저 저장하고 커밋하면 체크포인트 파일이 항상 최신이라 더 안전하다"고 주장합니다. 반례를 들어 반박하세요.

정답과 해설 보기

offset 20,000까지 처리 후 체크포인트(offset=20,000 다음 위치)를 저장했고, 커밋 직전에 DB 연결이 끊겨 10,001~20,000번 레코드가 롤백되었다고 합시다. 재시작하면 체크포인트를 믿고 20,001번부터 읽으므로 10,001~20,000번 1만 건은 영영 반영되지 않습니다. 멱등성은 "중복"은 막아 주지만 "누락"은 막아 주지 못합니다. 반대 순서(커밋 → 체크포인트)에서는 실패 시 중복 처리만 생기고 이는 멱등성이 해결합니다.

연습문제 25-7 CRC 활용 난이도 ★★☆

이 장의 crc32_update를 이용해 파일 경로를 받아 파일 전체 CRC32를 계산하는 int file_crc32(const char *path, uint32_t *out)을 작성하세요. 파일 크기와 무관하게 메모리 사용량이 일정해야 합니다.

정답과 해설 보기

crc32_update가 이전 CRC를 이어받도록 설계되었기 때문에 가능한 구조입니다(시작 시 반전, 끝에서 반전하므로 중간 값을 그대로 넘기면 됩니다). crc32_init()을 먼저 한 번 호출해야 합니다.

연습문제 25-8 멱등성 설계 난이도 ★★★

카드 가맹점 대금 지급 배치가 "가맹점별 지급액 합계를 계산해 가맹점 계좌로 입금"합니다. 이 배치를 두 번 실행해도 이중 지급되지 않도록 하려면 무엇을 키로 삼고 어떤 테이블 구조를 둬야 할까요?

정답과 해설 보기

지급 단위 자체를 식별하는 키, 예를 들어 (지급예정일, 가맹점번호, 지급회차)를 기본키로 하는 "지급 내역" 테이블을 둡니다. 배치는 각 가맹점에 대해 ① 지급 내역 INSERT(상태=처리중) ② 입금 거래 수행 ③ 상태=완료 갱신을 한 트랜잭션으로 묶거나, 대외 입금처럼 트랜잭션으로 묶을 수 없는 경우 상태 머신(요청됨→송신됨→완료/실패)으로 관리합니다. 재실행 시 이미 "완료"인 키는 건너뛰고, "송신됨"에서 멈춘 건은 상대 기관에 처리 결과를 조회한 후 결정합니다(무작정 재송신 금지). 핵심은 "합계를 다시 계산해 다시 보낸다"가 아니라 "이 지급 건이 이미 나갔는가"를 키로 판단하는 것입니다.

연습문제 25-9 버그 찾기 — 원자적 쓰기 난이도 ★★★

다음 코드의 문제점을 세 가지 이상 찾으세요.

정답과 해설 보기

① 임시 파일이 /tmp, 대상이 /data라 다른 파일시스템이면 rename이 EXDEV로 실패합니다. 같은 디렉터리에 임시 파일을 만들어야 합니다. ② fopen, fprintf, fclose, rename의 반환값을 전혀 검사하지 않습니다. 특히 디스크가 가득 차면 fclose에서야 오류가 드러날 수 있는데 이를 무시하고 잘린 파일을 rename합니다. ③ fsync가 없어 전원 장애 시 rename은 반영되었는데 내용은 비어 있는 파일이 생길 수 있습니다. ④ 임시 파일 이름이 고정이라 두 프로세스가 동시에 실행되면 서로의 임시 파일을 덮어씁니다(PID를 붙이거나 mkstemp 사용). ⑤ 실패 시 임시 파일을 정리하지 않습니다.

연습문제 25-10 종합 설계 — 이자 결산 배치 난이도 ★★★

3,000만 계좌의 일별 이자를 계산하는 배치를 설계하세요. 입력은 계좌별 잔액 파일(H/D/T), 출력은 이자 내역 파일과 원장 반영입니다. ① 처리 단계 ② 검증 지점 ③ 재시작 방법 ④ 멱등성 키 ⑤ 종료 코드를 각각 제시하세요.

정답과 해설 보기

① 단계: 락 획득 → Header 영업일 확인 → 1차 검증 패스(형식, 일련번호, Trailer, CRC) → 2차 처리 패스(계좌별 이자 = 잔액 × 연이율 ÷ 365, 정수 연산과 정해진 절사 규칙) → 이자 내역 임시 파일 + 원장 반영(1만 건 커밋) → 출력 파일 Trailer 작성 → fsync + rename → 처리 이력 기록 → 락 해제.
② 검증: 입력 Trailer, 출력 건수 = 입력 건수, 이자 합계를 별도 SQL 집계와 교차 검증, "읽음 = 반영 + skip + 오류" 항등식.
③ 재시작: 커밋과 같은 트랜잭션에 (작업ID, 영업일, 다음 offset, 누적 건수/합계)를 저장하고, 재기동 시 입력 파일 식별자가 같을 때만 그 위치부터 이어서 처리. 출력 파일은 재시작 시 체크포인트 offset까지 잘라(truncate) 이어 쓰거나, DB에서 다시 생성.
④ 멱등성 키: (영업일, 계좌번호, 이자구분) 유일 키를 가진 이자 내역 테이블에 INSERT 성공 시에만 이자 누적액 갱신.
⑤ 종료 코드: 0 정상, 1 일부 계좌 오류 skip(해지·사고 계좌), 2 입력 검증 실패, 3 시스템 오류, 4 중복 실행. 금리 계산의 반올림 규칙은 상품 규정에 따르며 부동소수점 대신 정수(또는 고정소수점) 연산을 쓰는 것이 원칙입니다.
